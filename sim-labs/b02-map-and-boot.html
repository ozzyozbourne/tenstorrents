B02. Map the chip and watch it boot

Add three small patches to ttsim, then watch a simulated Wormhole being built, explored and woken up: which tiles the host and kernels actually touch, and which of the 400 RISC-V cores leave reset, in what order, and at which PCs.

Honesty banner. ttsim is a functional, bit-exact model of the chip. It is not a timing model. Every [1234] clock stamp in this lab is ttsim's g_clock, which in slow dispatch counts host polls (see B01). We use clocks only to put events in order. A gap of 1,872 clocks says nothing about how long the same step takes on silicon.

The question

In A03 you read a map of a Wormhole: a 10 × 12 grid with 80 Tensix tiles, 18 DRAM tiles, 16 Ethernet tiles, one PCIe tile and one ARC tile. In B01 you ran add_2_integers_in_riscv, which adds 14 and 7 on one RISC-V core and prints 21. Put the two together and two questions come up.

First: of those 120 grid positions, which ones does a program that adds two integers actually touch? One Tensix tile and one DRAM tile, perhaps? Second: each Tensix tile has five RISC-V cores, so the chip has 400 of them. When the program starts they are all held in reset. Who lets them go, in what order, and where does each one start executing? The ISA documentation says BRISC always wakes up at address 0x00000. But tt-metal's firmware for BRISC is not at address 0. So how does it get there?

In this lab you answer both questions by measurement. You patch ttsim to print three things: what ttsim_init built, every distinct NoC coordinate that is read or written, and every write to the soft-reset register. Then you check what you saw against the SoC descriptor and the firmware source. All output below was captured in this orb, trimmed where marked with ….

The block appears twice. The first copy comes from UMD's short-lived probe instance, which dlopens the simulator just to learn which chip it is and then exits at clock 0 (B01, section 2). The second copy is the device that runs your program. Line by line:

  • The sizes come from config.h:13-35: NUM_T_TILES 80, RV32_CORES_PER_T_TILE 5, TENSIX_SRAM_SIZE (1464 * 1024), NUM_E_TILES 16, ETH_SRAM_SIZE (256 * 1024), and NUM_DRAM_CHANNELS 6 × DRAM_CHANNEL_SIZE 0x80000000. The comment on the channel count admits that the hardware really has 12 channels, two per group, "but doesn't matter". We will see in step 2 why it doesn't.
  • Tensix IDs are row-major over the holes. T0..T7 is physical row 1, skipping column 5 (DRAM). Row 6 (Ethernet) is skipped, so row 7 starts at T40. This is tile_to_coord (tile.cpp:660-668): x += (x >= 4) ? 2 : 1, y += (y >= 5) ? 2 : 1.
  • Physical row 8 is harvested. ttsim hard-codes the single-chip harvesting mask N150[] = {0x40} (tile.cpp:30). Bit 6 indexes TENSIX_ROWS = {1,2,3,4,5,7,8,9,10,11} (tile.cpp:63), and entry 6 is physical row 8. The broadcast opt-out row mask 0x141 is bits 0, 6 and 8: the two Ethernet rows plus the harvested row. Translated row numbers skip row 8 and give it 27, the last slot, as A03 described.
  • The Ethernet IDs alternate from the outside in, E0 at (9,0) and E1 at (1,0). This matches the order of the eth: list in wormhole_b0_80_arch.yaml.
  • Every core starts in reset. t_tile_init ends with p_tile->soft_reset_0 = RISCV_DEBUG_REGS_SOFT_RESET_0_RESET_VALUE (tile.cpp:267), which the generated register header defines as 0x47800. No hart is active, so libttsim_clock would execute nothing at all. Something must write that register before any code runs. Step 3 finds out who.
After ttsim_init the simulated chip is fully built and completely asleep. All 400 Tensix harts are held in reset by SOFT_RESET_0 = 0x47800, and L1 is all zeros. Everything that happens after that is caused by the host.

Step 2: Which coordinates get touched?

Every access in ttsim that goes to a NoC coordinate ends up in one of two functions, tile_rd_bytes or tile_wr_bytes (tile.cpp:2769-2898). Both start by calling coord_to_tile, which turns a raw coordinate into a tile type and index. Their callers are the host's PCIe BAR path (pcie.cpp:340-359, through TLB windows) and the device's own NoC commands (noc_cmd_ctrl, tile.cpp:1397-1623). So instrumenting the two functions sees everything. Here is the inverse map they use, for the special tiles:

ttsim/src/tile.cpp:723-753 @b3620244
static std::pair<char, uint32_t> coord_to_tile(uint32_t coord) {
    switch (coord) {
#if TT_ARCH_VERSION == 0
        case 0 | (0 << 6):
        case 0 | (1 << 6):
        case 0 | (11 << 6):
            return {'D', 0}; // DRAM channel 0
        case 0 | (5 << 6):
        case 0 | (6 << 6):
        case 0 | (7 << 6):
            return {'D', 1}; // DRAM channel 1
        …                    // channels 2–5 in column 5
        case 0 | (3 << 6):
            return {'P', 0}; // PCIE tile (just one)
        case 0 | (10 << 6):
            return {'A', 0}; // ARC tile (just one)

A coordinate is packed as x | (y << 6). Three different coordinates return {'D', 0}: the simulator sends all three to the same array, g_dram[0]. Keep that in mind. Anything not in the switch falls through to the Tensix and Ethernet arithmetic, and a router-only position such as (0,2) hits TTSIM_ERROR(UnimplementedFunctionality, …).

Printing every access would flood the terminal: add_2 alone makes 4,539 host reads and 7,710 host writes. So the second patch prints only the first access to each coordinate by each initiator, counts the rest, and prints a table at exit. To tell host from device, libttsim.cpp sets a flag while it serves a BAR access, and noc_cmd_ctrl records which tile issued the command:

The answer to the first question surprises most people. A program that adds two integers touches 90 coordinates: all 72 usable Tensix tiles, all 16 Ethernet tiles, the ARC tile and one DRAM endpoint. Only one of those accesses (well, three: two reads and one write) is made by the device itself. Everything else is the host setting the chip up.

  • Ethernet tiles first. The host reads 0x1EFC and 0x1104 on each. UMD names them ETH_RETRAIN_ADDR and ETH_TRAIN_STATUS_ADDR (tt-umd/api/tt-umd/types/wormhole_eth.hpp:15-16), so this is topology discovery asking whether any Ethernet link is up. ttsim seeded 0x1104 with 3, "NOT_CONNECTED", for a single chip (tile.cpp:300).
  • Then every Tensix tile, at address 0xFFB121B0. That is TENSIX_SOFT_RESET_ADDR in UMD (wormhole_implementation.hpp:285): the reset register again. Step 3 decodes these writes.
  • "via (18,18)". The host addresses Tensix tiles in translated coordinates, and the PCIe tile's translation table turns (18,18) into physical (1,1). It addresses DRAM with raw coordinates, (0,11) "via (0,11)", because translated values 0 to 15 are the identity.
  • T0 (1,1) gets 376 reads; the others get 55. The kernel runs on logical core (0,0), which is translated (18,18), which is physical (1,1). The extra 321 reads are the host polling that core until the kernel reports done.
  • What is never touched. The 8 tiles of harvested row 8, the 4 router-only positions, the PCIe tile itself, and 17 of the 18 DRAM endpoints. (The host's BAR traffic enters through the PCIe tile, but ttsim models that as a direct jump to the target coordinate, so tile_rd_bytes only sees the PCIe tile when a device core does DMA to host memory. None does here.)

The DRAM aliases: three doors to one room

The ISA overview says Wormhole has "18x DRAM tile, collectively exposing 12 GiB of GDDR6 (each 2 GiB is exposed identically on 3 tiles)" (tt-isa-documentation/WormholeB0/README.md). The SoC descriptor lists the groups, and then picks, for each 1 GiB half, which door to use:

    [5-2, 5-9, 5-10],
    [5-3, 5-4, 5-8],

# Eth and worker dram endpoints represent subchannel id from dram array for each noc.

dram_views:
  [
    { channel: 0, eth_endpoint: [0, 0], worker_endpoint: [2, 2], address_offset: 0 },
    { channel: 0, eth_endpoint: [0, 0], worker_endpoint: [1, 1], address_offset: 1073741824 },
    …

(The real file writes each view over five lines; we joined them.) The descriptor's list of channels is exactly ttsim's coord_to_tile table. A view is half a channel, 1 GiB at address_offset 0 or 1 GiB, and there are 12 of them. Each view names a worker_endpoint: an index into the channel's list of three, one for NoC 0 and one for NoC 1. Channel 0's first view uses index 2, which is (0,11), and its second view uses index 1, which is (0,1). That is exactly what the log shows: 0x2d4c40 at (0,11) and 0x402d4c40 at (0,1). Check all six channels in the figure below. Every touched endpoint is a worker_endpoint, and every untouched one is the channel's eth_endpoint, reserved for kernels on Ethernet cores, which these examples do not run.

The interleaving explains the order of the touches too. An interleaved buffer puts page 0 in bank 0, page 1 in bank 1, and so on. The log visits channel 0's two halves, then channel 1's, and so on, at the same offset 0x2d4c40 within each view. That is consistent with tt-metal using the 12 views, in file order, as its 12 DRAM banks (A03's gridinfo printed dram_grid_size = 12x1).

Why three doors? A03 gave the hardware reason: they spread NoC traffic over three routers instead of piling it onto one. The simulator has no routers and no congestion (B01, section 5). It just maps the three coordinates to g_dram[c] and does a memcpy (tile.cpp:2786, :2833). So in ttsim the choice of door changes nothing measurable, which is why config.h can say the 12-versus-6 channel split "doesn't matter". On silicon the choice matters for bandwidth, which is why tt-metal makes it in the descriptor rather than in your kernel.

Aliases are the same memory. If you write to (0,0) and then read the same address from (0,11), you get what you wrote, on silicon and in ttsim. But do not pick doors yourself: tt-metal's worker kernels reach the upper 1 GiB of channel 0 only through (0,1), and you will get a different bank than you think if you guess. If you hand-build a NoC address, take the endpoint from the bank tables (get_noc_addr_from_bank_id), not from your own reading of the YAML.

Step 3: Watch SOFT_RESET_0

What the register does

The ISA spec describes RISCV_DEBUG_REG_SOFT_RESET_0 bit by bit (WormholeB0/TensixTile/SoftReset.md:19-26). Five of its bits hold the five RISC-V cores:

BitMaskCoreUMD name (wormhole_implementation.hpp:365-369)
110x00800RISCV B (BRISC)SOFT_RESET_BRISC
120x01000RISCV T0 (TRISC0)SOFT_RESET_TRISC0
130x02000RISCV T1 (TRISC1)SOFT_RESET_TRISC1
140x04000RISCV T2 (TRISC2)SOFT_RESET_TRISC2
180x40000RISCV NC (NCRISC)SOFT_RESET_NCRISC

Add them up and you get 0x47800, the reset value from step 1: all five held. A 1 means "held in reset". Coming out of reset, says the spec, "pc will be set according to the below table" (SoftReset.md:41-48): BRISC always starts at 0x00000, and each other core starts either at a fixed default (0x06000, 0x0A000, 0x0E000, 0x12000) or, if an override bit is set, at a PC held in a configuration register. ttsim implements that table directly:

ttsim/src/tile.cpp:1096-1127 @b3620244 (trimmed)
        case RISCV_DEBUG_REGS_SOFT_RESET_0: {
            data &= 0x7FFFFFFF; // ignore bit 31 written by UMD
            TTSIM_VERIFY(!(data & ~0x47800), UnimplementedFunctionality, "SOFT_RESET_0=0x%x", data);
            static const uint32_t soft_reset_bits[] = {0x800, 0x1000, 0x2000, 0x4000, 0x40000};
            for (uint32_t rv32_id = 0; rv32_id < RV32_CORES_PER_T_TILE; rv32_id++) {
                if (data & soft_reset_bits[rv32_id]) { // put core into reset
                    ttsim_rv32_set_core_active('T', tile_id, rv32_id, false);
                } else if (!ttsim_rv32_get_core_active('T', tile_id, rv32_id)) { // take core out of reset
                    ttsim_rv32_set_core_active('T', tile_id, rv32_id, true);
                    uint32_t reset_pc;
                    switch (rv32_id) {
                        case RV32_ID_BRISC: reset_pc = 0; break; // reset PC for brisc is always zero
                        case RV32_ID_TRISC0:
                            reset_pc = (p_tile->trisc_reset_pc_override & 1) ? p_tile->trisc0_reset_pc : 0x6000;
                            break;
                        …   // TRISC1 0xA000, TRISC2 0xE000, NCRISC 0x12000, same pattern
                    }
                    p_tile->rv32[rv32_id].pc = reset_pc;
                }
            }
            p_tile->soft_reset_0 = data;

Three details matter. A core only "comes out of reset" on a 1-to-0 transition; writing 0 to a core that is already running changes nothing, so its PC is not reset. Bit 31 is masked off because UMD sets it for "staggered start" (SOFT_RESET_STAGGERED_START = 1 << 31), which ttsim does not model. And any bit outside the five, such as the Tensix-unit resets in bits 0 to 10, is rejected as unimplemented: a program that relies on them will stop with an error rather than run wrongly. On Wormhole the reset-PC registers are Tensix configuration registers 158–163 (tensix.cpp:519-524), written through the config space, not the debug-register page.

That is the whole life of one Tensix tile. Read it as a story:

  1. Clock 249: the host releases BRISC alone. 0x47800 → 0x47000 clears bit 11 only. BRISC starts at PC 0, as the spec promised, and the word it finds there is 0x3210306f.
  2. Clocks 1839–1851: BRISC writes the reset PCs for its four siblings, then sets both override registers (0x7 for the three TRISCs, 0x1 for NCRISC). The hardware defaults 0x6000…0x12000 are never used.
  3. Clock 2121: BRISC releases the other four by writing 0 to the register. Note the writer: by BRISC, not the host. All four begin with the same instruction word, 0xffb001b7.
  4. Clock 4414: the host puts all five back into reset during teardown, wherever they happen to be.

Compared with a GPU. CUDA programmers never see an SM come out of reset. The driver and the GPU's own firmware bring the chip up before your process exists, and a kernel launch only hands work to cores that are already running a scheduler. On Tenstorrent, with tt-metal, the boot is part of opening the device: the runtime library writes the firmware into every core's L1 and flips each core's reset bit itself, every time you open the device. That is more work, but it means the whole boot is ordinary, readable code, and a simulator can show you every step.

One more twist: NCRISC's IRAM dance

Run eltwise_binary on tile 0, whose reader kernel runs on NCRISC:

B02_RESET=1 B02_TILE=0 $EX/metal_example_eltwise_binary 2>&1 | grep "B02 reset" | tail -4
[4390] B02 reset T0 cfg NCRISC_RESET_PC = 0xffc00000
[4391] B02 reset T0 (1,1) by BRISC: 0x00000 -> 0x40000 stop NCRISC@0x5ecc;
[4400] B02 reset T0 (1,1) by BRISC: 0x40000 -> 0x00000 start NCRISC@0xffc00000;
[7872] B02 reset T0 (1,1) by host/NoC: 0x00000 -> 0x47800 stop BRISC@0x3fe0; stop TRISC0@0x652c; stop TRISC1@0x68f4; stop TRISC2@0x6f08; stop NCRISC@0x5af8;

Mid-program, BRISC points NCRISC's reset PC at 0xFFC00000, puts NCRISC back into reset, and releases it 9 clocks later. 0xFFC00000 is MEM_NCRISC_IRAM_BASE, NCRISC's private 16 KiB instruction RAM, where Wormhole runs NCRISC kernels. tt-metal's own comment gives the reason only as "Jumping to IRAM causes bizarre behavior" (ncrisc.cc:177-178). The ISA spec describes the underlying hazard: IRAM is written by the mover, and if NCRISC's frontend fetches from IRAM (for example because its branch predictor guesses a jump there) while the mover is writing, the contents can be corrupted. Reset helps because it erases branch-predictor history (WormholeB0/TensixTile/BabyRISCV/InstructionRAM.md:7-16). The firmware does not follow the spec's "reset during the copy" recipe literally: NCRISC itself has the mover copy its kernel into IRAM and waits for the copy (ncrisc.cc:141, :164), and only then gets reset into IRAM, so it starts there with a clean predictor. After the kernel it deliberately pollutes its branch predictor (ncrisc.cc:193-199), the last option in the spec's list, to protect the next copy. The handoff: NCRISC parks itself in wh_iram_trampoline with status RUN_SYNC_MSG_WAITING_FOR_RESET (ncrisc.cc:180-181), and BRISC's start_ncrisc_kernel_run writes the resume address, calls assert_just_ncrisc_reset(), waits with riscv_wait(5), and calls deassert_all_reset() (brisc.cc:306-323). In vecadd_multi_core all 64 worker tiles do the dance, between clocks 4302 and 4386, with gaps of 9 or 10 clocks. This only happens on Wormhole (#if defined(ARCH_WORMHOLE)); on Blackhole NCRISC jumps straight to its kernel in L1.

"Released once" is wrong. If you instrument reset expecting one release per core, Wormhole's NCRISC will confuse you: it is reset and released again for every program whose NCRISC kernel runs from IRAM. The first release starts it at its firmware (0x5940); later ones start it at 0xFFC00000, and the reset clears its registers, so the firmware saved them on the stack first.

Step 4: Exercises, with answers

Exercise 1. Run the same tile-0 trace on Blackhole (source $W/env.sh bh, $W/build_ttsim.sh boot bh). Predict the PCs before you look. What changes?

Our run: [340] … start BRISC@0x0 [0x3e10306f], reset PCs NCRISC 0x5de0, TRISC0 0x67e0, TRISC1 0x71e0, TRISC2 0x7be0, and the siblings released at clock 3124 by BRISC. The sequence is identical; the addresses moved because Blackhole's memory map has different sizes. Decode the JAL: 0x3e1… has bits 10..1 = 0x3e0, bit 11 set and bits 19..12 = 3, so it jumps to 0x3be0. On Blackhole the reset-PC writes go to debug registers (WRITE_REG(RISCV_DEBUG_REG_NCRISC_RESET_PC, …)), which ttsim handles in tile.cpp:1130-1135 instead of tensix.cpp; the patch logs both. The inventory also shows column harvesting instead of row harvesting: harvested Tensix cols=0x480, which is columns 7 and 10, and Tensix column 7 is translated to 16 and column 10 to 15, the end of the range. There is no NCRISC IRAM dance.

Exercise 2. Why is the gap between "start BRISC" and "start TRISC0" exactly 1,872 clocks on every one of the 72 tiles, even though they were released at different clocks?

Every tile runs the same BRISC firmware, with the same data apart from its coordinates, and in ttsim each active hart executes exactly one instruction per clock (B01). The path from _start to the SOFT_RESET_0 write in deassert_ncrisc_trisc doesn't depend on which tile it is on, so it takes the same number of clocks everywhere. (We checked: the set of differences across all 72 tiles is {1872}, in both add_2 and vecadd.) On silicon, L1 contention and cache behaviour would make the gaps differ slightly.

Exercise 3. A colleague's kernel hand-builds a NoC address for DRAM bank 1 using coordinate (0,0) and offset 0x2d4c40. Will it read the same data as tt-metal's reader?

No. Bank 1 is channel 0's upper 1 GiB (address_offset: 1073741824), which tt-metal reaches as (0,1) at 0x402d4c40. (0,0) is the same physical channel, so the colleague needs offset 0x402d4c40 to see the same bytes. At 0x2d4c40 they are reading bank 0's page through a different door. In ttsim both doors land in g_dram[0], so the bug shows up as wrong data, not as an error.

Exercise 4. With B02_RESET=2, add_2 makes 80 writes to Ethernet soft-reset registers, but only 32 change anything. Without reading tt-metal, what does that tell you about who writes them?

The 48 no-op writes (16 × 0x800 → 0x800 twice and 16 × 0 → 0) are the same pattern as on Tensix tiles: broadcasts or read-modify-writes that set a bit already set, or clear one already clear. In our log the first 16 writes come at clocks 196–211, one per clock, which is the per-core read-modify-write signature; the releases follow at 228–291, at irregular intervals (nine in consecutive clocks, then seven spread over 258–291). Whoever writes them uses the same assert/deassert helpers, applied to every core regardless of its current state. That is cheap on silicon and harmless, because a reset bit that is already set has no effect.

Exercise 5. In the chip-map replay for add_2, which grid positions never light up, and for each, why?

Row y = 8 (T48–T55): harvested, so tt-metal has no logical core there and never addresses it. Router-only (0,2), (0,4), (0,8), (0,9): nothing to talk to, and ttsim would raise UnimplementedFunctionality if anything tried. PCIe (0,3): host accesses enter through it but ttsim routes them straight to the target, and nothing on the device does DMA to the host in this example. 17 DRAM endpoints: add_2's buffers are small and live in bank 0 only, whose worker door is (0,11).

Exercise 6. Change one line in your patched ttsim so that TRISC1 ignores the override and always starts at its hardware default 0xA000. Predict what happens to add_2.

This is a prediction we did not run, so treat it as a hypothesis to test. With the override ignored, TRISC1 would start at 0xA000, which is outside every firmware image (TRISC2's ends at 0x6D40 + 1536 = 0x7340) and holds whatever the host put there, possibly zeros. A zero word is not a valid RISC-V instruction, so ttsim would most likely stop with an error on TRISC1 before init completes, and tt-metal would never see TRISC1 report done. Try it and check the error message; whatever you see, you will have learned that the override write at clock 1848 is load-bearing.

Recap

  • ttsim_init builds every tile of the chip with all 400 Tensix harts held in reset (SOFT_RESET_0 = 0x47800) and L1 empty. Single-chip Wormhole harvests physical row 8, translated to row 27.
  • All NoC traffic, host or device, passes through tile_rd_bytes/tile_wr_bytes and coord_to_tile, so two hooks see everything. Gate prints and count the rest, or one run prints tens of thousands of lines.
  • add_2 touches 90 coordinates, almost all of them by the host during setup. The kernel's only NoC traffic is to one DRAM door, (0,11).
  • Each Wormhole DRAM channel has three doors. tt-metal splits it into two 1 GiB views (its banks), each with a fixed worker_endpoint; the third door is the eth_endpoint. ttsim maps all three to the same array.
  • Boot order on every Tensix tile: the host loads five firmware images and a jal 0x3b20 at address 0, then clears only BRISC's reset bit. BRISC sets the four reset PCs (override on), then writes 0 to release TRISC0–2 and NCRISC at 0x6140/0x6740/0x6d40/0x5940.
  • On Wormhole, NCRISC is reset again per program to start its kernel in IRAM (0xFFC00000), because tt-metal found that jumping from L1 into IRAM misbehaves (the ISA docs describe the related IRAM/branch-predictor hazard).
  • Clock stamps order these events; they don't time them.

Check yourself

Why does tt-metal write a jal instruction to L1 address 0 instead of programming a reset PC for BRISC, as it does for the other four cores?

Because BRISC has no reset-PC register on Wormhole or Blackhole. The spec gives its reset PC as a constant 0x00000 (SoftReset.md:44), ttsim hard-codes reset_pc = 0 for it (tile.cpp:1108), and tt-metal's own comment says "no reset PC register on GS/WH/BH". So the only way to start firmware at 0x3B20 is to put a jump at 0.

SOFT_RESET_0 reads 0x47000. Which cores are running?

Only BRISC. 0x47000 is 0x47800 with bit 11 cleared, so TRISC0–2 (bits 12–14) and NCRISC (bit 18) are still held. This is the state between the host's release of BRISC and BRISC's own write of 0, clocks 249 to 2121 on tile 0.

You write 0x00000 to SOFT_RESET_0 on a tile where all five cores are already running. In ttsim, what happens to their PCs?

Nothing. ttsim only sets a PC on a 1-to-0 transition: else if (!ttsim_rv32_get_core_active(…)). Cores that are already active keep running where they were. This is why BRISC can write 0 to release its siblings without restarting itself.

Why do the host's BRISC releases arrive one per clock, while its first two reset writes reach all 72 tiles in clock 123?

The first two are broadcast writes (UMD's broadcast_tensix_risc_reset_to_cluster), which make no read, so no clock passes. The per-core release is a read-modify-write in TTSimTTDevice::deassert_risc_reset, and every host read clocks the simulator once (after_read(), B01). So one tile costs one clock.

Wormhole's SoC descriptor lists 18 DRAM tiles, but eltwise_binary only ever touches 12. Is that a bug?

No. The 12 touched tiles are the worker_endpoints of the 12 views, two per channel. The other six are the eth_endpoints, which tt-metal would use from kernels running on Ethernet cores, and this example runs none. All 18 are live: any of a channel's three tiles reaches the same 2 GiB.
