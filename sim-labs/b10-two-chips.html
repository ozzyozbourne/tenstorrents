B10. Two chips

Boot a simulated n300 with two Wormhole chips, list what tt-metal finds, run one MeshWorkload with different data on each chip, and then move bytes over the Ethernet link between them three ways. Along the way you trace why TT-Fabric starves the host's link to chip 1 in the simulator to one early return in tt-metal, and use a kernel overlay that works around it.

Honesty banner. ttsim is a functional, bit-exact model, not a timing model. An Ethernet send in ttsim is a memcpy into the peer core's L1, done inside the register write that starts it (tile.cpp:2028-2034). The bracketed clock numbers in this lab put events in order. They say nothing about link latency or bandwidth. The Ethernet firmware here is ttsim's own mock base firmware (ttsim/fw/eth/eth_fw.c), not Tenstorrent's production firmware. The TT-Fabric and all-gather results in section 4 need a kernel overlay that changes the fabric router's yield interval. It works around a simulator-only gap in tt-metal 7aad8aac and is not a fix you would ship. Every output below was run in this orb with tt-metal 7aad8aac and ttsim b3620244 (v1.15.0).

The question

An n300 card carries two Wormhole chips. Only one of them is wired to the PCIe slot. The other one has no path to the host at all except two Ethernet cables that run across the card to its sibling. The chips share no memory.

Yet the program you will run in section 2 writes 32 MiB into "one" buffer, reads it back, and prints devices=2 match=true. Half of those bytes live on the chip the host cannot reach. So who carried them? And once data is on both chips, how do you get a kernel on chip 0 to put bytes into chip 1's DRAM, with the host not involved at all?

A21 answers this in principle: Ethernet cores, MeshDevice, TT-Fabric and collectives. This lab answers it with a log. You will make ttsim print every packet that crosses the simulated link and read the exchange one header at a time. In the process you will hit a wall that A21 also hit: the fabric comes up, then the host loses chip 1. This lab traces that wall to a specific line of source code (with the evidence and its limits spelled out) and gets past it.

Line by line:

  • Two devices, one MMIO. Chip 0 has mmio=true and chip 1 has false. UMD built chip 1 as a remote simulation chip because the descriptor declared it remote (tt-umd-workload/src/cluster.cpp:305-306). Every host access to chip 1 must therefore be relayed by chip 0's Ethernet cores.
  • The links match the descriptor. Logical Ethernet core 0-8 is channel 8. On chip 0 it connects to chip 1's 0-0 (channel 0), and 0-9 connects to 0-1. The "NoC" column holds translated coordinates. Physically these are tiles (9,6) and (1,6) on chip 0 and (9,0) and (1,0) on chip 1, which matches the soc descriptor's eth: list (wormhole_b0_80_arch.yaml:104-108: entry 8 is 9-6, entry 9 is 1-6).
  • A third "active" core on chip 0 has no link. Channel 15 is reported active, but asking for its peer hits a TT_FATAL, so the program catches it. The reason is a special case in the control plane: on a Wormhole MMIO chip that tunnels to remote chips, channel 15 is always marked active because "channel 15 is used by syseng tools" (control_plane.cpp:3145-3162).
  • 8×7 workers per chip. Each chip has two harvested Tensix rows (masks 0x41 and 0x05 each have two bits set), which leaves 8 of 10 rows. One more row is set aside for dispatch cores, as on the single-chip model, where 9 rows show up as 8×8 (A17).
API trap. device.hpp:206 says get_active_ethernet_cores() returns virtual coordinates. The implementation returns logical ones (control_plane.cpp:3134 asks for CoordSystem::LOGICAL). My first version of the program passed them to logical_core_from_ethernet_core and UMD threw No core coordinate found for system LOGICAL at location: (0, 8, ROUTER_ONLY, TRANSLATED).

2. dbrw: 32 MiB through a 4 KiB keyhole

dbrw.cpp (in the workbench, see its README) is the stock distributed_buffer_rw example with the mesh shape changed from 2×4 to 2×1 and its final assert replaced by one line of output. It allocates a sharded L1 MeshBuffer across both chips, writes random data, reads it back and compares.

time $LAB_HOME/dbrw 2>&1 | grep -v "| info"
devices=2 match=true bytes=33554432
[372773] 8.0 seconds (46.4 KHz)
real    0m7.705s

bytes=33554432 is 64 * 128 * tile_size(UInt32) = 8192 × 4096 bytes = 32 MiB, the global_size in dbrw.cpp. The global shape is 64×32 "datums" split into two 32×32 shards, so each chip holds 16 MiB. Chip 0's half goes straight over PCIe. Chip 1's half has to go through chip 0.

To see it go, build a ttsim that logs every Ethernet transfer. The patch adds one logging function, called from the two places where ttsim moves bytes between chips: the data send (ETH_TXQ_CMD = 2, an L1-to-L1 copy) and the remote register write (ETH_TXQ_CMD = 4). It also prints each link at init.

27,969 transfers. Most are 32-byte headers of ttsim's mock firmware protocol, so the patch decodes those as seq/op/addr/size/data. The firmware's op codes are defined at eth_fw.c:207-217. Grouped by op:

Direction (chip:Ethernet tile)opcountwhat it is

c0:E9 → c1:E16 BLOCK_READ, 4096 B4096reading the shard back, clocks 199,139–369,075

Each chunk travels twice inside a stop-and-wait protocol. First the 4 KiB payload is shipped to the peer's BLOCK_BUF at L1 0x15600. Then a 32-byte header lands in its request inbox at 0x14900. The sender spins until the peer's acknowledgement shows up in its own response inbox at 0x14A00. The bulk chunks are sent by dram_write_to_peer (eth_fw.c:391-410); the single-request path, single_hop, shows the same pattern more compactly:

ttsim/fw/eth/eth_fw.c:433-454 @b3620244 (trimmed; end-of-line comments added)
static uint32_t single_hop(uint32_t op, uint32_t sys_lo, uint32_t sys_hi, uint32_t size, uint32_t data,
                           uint32_t block_src, uint32_t *send_seq) {
    uint32_t seq = ++(*send_seq);
    if (op == OP_BLOCK_WRITE) {
        eth_send_block(block_src, sys_lo, size);      // payload -> peer BLOCK_BUF (0x15600)
    }
    PHYS_WR32(OUTBOX_ADDR + PKT_SEQ, seq);
    PHYS_WR32(OUTBOX_ADDR + PKT_OP, op);
    ...
    eth_send(REQ_INBOX_ADDR, OUTBOX_ADDR, PKT_BYTES);  // 32-byte header -> peer inbox (0x14900)
    while (PHYS_RD32(RESP_INBOX_ADDR + PKT_SEQ) != seq) {
    }                                                 // wait for the peer's ack
    return PHYS_RD32(RESP_INBOX_ADDR + PKT_DATA);
}

And the "wire" itself is four lines of the simulator:

ttsim/src/tile.cpp:2028-2034 @b3620244
// eth_send_packet (ETH_TXQ_CMD_START_DATA): copy local L1 to the peer eth tile's L1
uint32_t saved_chip_id = g_current_chip_id;
ttsim_select_chip(remote_chip_id);

p_tile->eth_txq_cmd[queue_id] = 0;

The host side of this is the "legacy" remote queue. UMD writes a command into a request queue in chip 0's Ethernet-core L1 (REQ_QUEUE_BASE 0x11080, eth_fw.c:59), and the firmware drains it. That is the baseline data-movement service in tt-isa-documentation's BaselineDataMovementService.md: it is "how host software is expected to initially communicate with any ASICs which are only reachable via Ethernet". On real silicon, Tenstorrent's Ethernet firmware provides it. Here ttsim's mock firmware does. Nearly all the bulk traffic went over E9 rather than E8. The firmware comment says UMD "round-robins each remote-queue command over ALL of an MMIO chip's active eth cores" (eth_fw.c:156-157). Remember that sentence. It decides section 4.

GPU comparison. Two GPUs on one board each sit on PCIe (or NVLink with a host-visible BAR). Here the second chip has no host-visible address space. Everything the host does to chip 1, from loading firmware and writing buffers to launching kernels and polling for completion, is a message that chip 0's Ethernet RISC-V cores relay. That is why moving chip 1's 16 MiB in and back out accounts for about 338,000 of the run's 372,773 simulated clocks (31,205 to 369,092): the cost is the relay protocol, not the copy.

3. One MeshWorkload, two programs

dbrw only moves data. Now run a kernel on both chips with different data and different arguments. A MeshWorkload maps device ranges to programs (mesh_workload.hpp:41: add_program(const MeshCoordinateRange&, Program&&)). The stock examples add one program for the whole mesh. b10_workload.cpp adds one per chip instead:

sim-labs/workbench/host/b10_workload.cpp:21-46

...

    auto k = CreateKernel(program, "b10/add_const.cpp", core, DataMovementConfig{...});

The kernel (overlays/b10/b10/add_const.cpp) runs on BRISC. It reads one 4 KiB DRAM page into a circular-buffer slot, computes p[i] = p[i] * mul + add on 1024 words, and writes the page back. The buffers are allocated in lock step, so in and out have the same address on both chips. Only the data and the runtime arguments differ.

Check one value by hand: chip 1's first input is 1024, and 1024 × 3 + 7 = 3079. Run it again on the logging ttsim (B10_ETHLOG=1) and the launch on chip 1 shows up as messages. The one on chip 0 does not, because chip 0 is reached directly over PCIe. The next figure replays that log.

To the host, a MeshWorkload is one call. Underneath, the MMIO chip gets ordinary PCIe writes. The remote chip gets the same writes as relayed messages: kernel text, launch message, go signal, and a stream of polls for "done". Both chips ran the same binary at the same L1 and DRAM addresses with different runtime arguments.

4. Making data cross the link

So far the Ethernet link has carried only the host's traffic. Now make a kernel send bytes to the other chip. I tried three approaches, from most to least useful: the TT-Fabric API from a kernel, a ttnn all-gather (which uses the fabric), and a raw Ethernet-core kernel. The first two work after one fix, so I did not build the third (see exercise 4).

Why would turning on the fabric break the host's tunnel? Start from what the fabric does to the Ethernet cores. A fabric router is a kernel that takes over an Ethernet core and runs forever. On Wormhole, the base firmware on that core still has to service the host's remote queue. So the router must yield now and then: it calls a function pointer that the firmware stores at L1 0x9020. tt-isa-documentation defines this contract: "If the customer code is long running, it also needs to occasionally yield control back to the Tenstorrent code. This is done by reading four bytes in L1 at 0x9020 [and] calling the function pointer" (WormholeB0/EthernetTile/BabyRISCV/CallingIntoCustomerCode.md:20-22). ttsim's mock firmware installs eth_yield_entry there at boot (eth_fw.c:797), and that function runs the same eth_service() loop that drains the host queue.

So the question becomes: does every router yield? The patch has a second probe for this. With B10_ETHLOG=1, it prints a line every time an Ethernet hart's PC lands on the yield address stored at 0x9020. tt-metal/tt_metal/fabric/compute_mesh_router_builder.cpp:881-885 @7aad8aac

Every other router keeps the default of 10000 (erisc_datamover_builder.hpp:355). That only works if the host sends its tunnel traffic over the dispatch link alone. tt-metal has code that pins UMD to exactly those channels, but it skips that code unless the target is real silicon:

    ChipId mmio_chip_id, const std::set<tt_fabric::chan_id_t>& eth_chans) {
    if (this->arch_ != tt::ARCH::WORMHOLE_B0 || this->target_type_ != tt::TargetDevice::Silicon || eth_chans.empty()) {
        return;

Under ttsim, target_type_ is Simulator (tt_target_device.hpp:14-16), so UMD keeps round-robining over channels 8 and 9. The requests that land on channel 9 then wait for a router that, at ttsim's speed, did not yield again before UMD's 5 s timeout. On silicon, the requests never go to that router in the first place. tt-metal's own comment on the channel-pinning helper says the same: the other fabric routers "can hold the core for tens of seconds per transfer while fabric is active" (fabric_host_utils.hpp:99-104).

How sure is this? Shown directly: the 9↔1 routers stop yielding (figure above), the next host request on E9 is never acknowledged, the gate at tt_cluster.cpp:1404 excludes Simulator, and capping the yield interval makes every symptom go away (below). Inferred, not traced: that UMD's round-robin is what sends that request to E9. I did not instrument UMD, and I did not rebuild tt-metal without the Silicon check to confirm that pinning alone fixes it. Treat the early return as the most likely cause, not a proven one.

Two easy wrong conclusions. (1) "The fabric routers never yield in ttsim." The dispatch-link routers do (figure above). (2) "Give the Ethernet cores more steps per clock." I tried this: the patch adds B10_ETH_IDLE_STEPS=N. With N = 256, the write to chip 1 got through and the fabric kernel ran, but the read-back timed out. With N = 2048 it still timed out, after 41 s. Each yield on the 9↔1 link needs 10,000 idle passes of the router's outer loop, and each pass runs the inner loop 32 times (erisc_datamover_builder.hpp:154). More steps per clock also slows the host's clock, so the race against a wall-clock timeout keeps being lost.

The workaround: a kernel overlay for the router

The fabric router is compiled from source at run time like any other kernel, through the same search path. compute_mesh_router_builder.cpp:979 names it tt_metal/fabric/impl/kernels/edm_fabric/fabric_erisc_router.cpp, so a copy under $TT_METAL_KERNEL_PATH wins (B00). The overlay in sim-labs/overlays/b10/ changes only the yield threshold:

mkdir -p $LAB_HOME/kernels/tt_metal/fabric/impl/kernels/edm_fabric

Without the overlay (TT_METAL_KERNEL_PATH pointed at an empty directory), the same script dies at the very first ttnn.from_torch with RuntimeError: Timeout waiting for Ethernet core service remote IO request flush.

The next figure replays both runs from the Ethernet log: the single fabric write from 4b, then the all-gather's 18 link events. Each fabric packet starts with a 48-byte LowLatencyPacketHeader. It holds 40 bytes of NoC command fields (the 64-bit destination NoC address comes first), then payload_size_bytes (u16), noc_send_type (u8) and src_ch_id (u8), and then 4 bytes of routing fields (fabric_edm_packet_header.hpp:405-420, 1086-1092). Words 10 and 11 of the dump are therefore size/type and route.

How to read the dumps:

  • Word 10 packs payload_size_bytes in the low 16 bits and noc_send_type in the next byte. 0x00001000 is 4096 bytes of type 0 (NOC_UNICAST_WRITE). 0x00000800 is 2048 bytes, one bf16 tile. 0x00020000 is 0 bytes of type 2 (NOC_UNICAST_ATOMIC_INC) (fabric_edm_packet_header.hpp:95-99). For the increments, words 2–3 are the val (1) and flush fields of NocUnicastAtomicIncCommandHeader (:289-296).
  • Words 0–1 are the destination NoC address. In 4b it is 0x00000090_002d4c40, whose low part is the buffer address from buf->address() on chip 1. In the semaphore packets it is L1 0x16dfe0 or 0x16dfc0 at coordinate word 0x492, that is x = 18, y = 18, which is translated Tensix (18,18) = logical worker (0,0) (B02). I did not decode which DRAM bank the all-gather's 0x2890 and 0x0090 coordinates name.
  • Payload words confirm the data: 0x00b10b10 is the 4b pattern's seed, 0x4020/0x4028 are bf16 2.5/2.625 (chip 1's values) and 0x3f80/0x3f90 are 1.0/1.125 (chip 0's).
  • REG lines are TXQ remote-register writes of 0x40. That is 1 << REMOTE_DEST_BUF_WORDS_FREE_INC (= 1 << 6) into register index 34 (STREAM_REMOTE_DEST_BUF_SPACE_AVAILABLE_UPDATE) of stream 2 or stream 5 on the peer (noc_overlay_parameters.h:38-42, 405-408; fabric_stream_regs.hpp:97-100). These are the fabric's flow-control credits. Which logical counter each stream ID plays is a router compile-time argument, which I did not trace.
A fabric packet is a 48-byte header that says "go N hops, then perform this NoC command", followed by the payload. The routers copy the whole slot over Ethernet, return a credit, and the receiving router performs the NoC command on its own chip. The host is not involved at any point.

4d. What I did not do

A hand-written Ethernet-core kernel that drives the TX queue directly would also work in principle: ttsim implements both TXQ commands that matter, data and remote register write (tile.cpp:1992-2088). I skipped it because the fabric path already demonstrates the transfer end to end. If you try it, remember that on Wormhole your kernel shares the core with the base firmware and must yield through 0x9020, exactly as the fabric router does.

7. Exercises, with answers

Exercise 1. Change b10_workload so that one program covers both chips (MeshCoordinateRange(mesh->shape())), keeping the sharded input. Predict the output before you run it.

Both chips then run the same runtime arguments, say mul 2, add 1000, on their own shards. Chip 0 still sees 0..1023 and chip 1 sees 1024..2047, so the outputs are 1000, 1002, ... and 3048, 3050, .... The program's checker, which expects x*3+7 on row 1, reports 1024 mismatches. That is the SPMD pattern of the stock examples: one program, different data per chip, because the buffer is sharded.

Exercise 2. In the dbrw log, the 16 MiB to chip 1 took 4096 BLOCK_WRITE packets. Why 4096 and not 16,384 (1 KiB each, the limit in BaselineDataMovementService.md)?

UMD issues "host-DRAM block" requests (CMD_DATA_BLOCK_DRAM). Silicon firmware allows those up to 4 GiB per request, and ttsim's mock firmware streams them in ETH_BLOCK_CHUNK = 4096-byte pieces (eth_fw.c:145, dram_write_to_peer at :391-410): 16 MiB / 4 KiB = 4096. The 1 KiB limit applies to the L1-block variant without the DRAM flag.

Exercise 3. Make the fabric work without the router overlay by changing only the host program. Hint: which Ethernet cores does UMD use?

Not possible through the public API at this commit. The function that pins UMD to the dispatch channels, Cluster::configure_ethernet_cores_for_remote_transfers, returns early for non-silicon targets, and tt::Cluster is not part of the installed API. The alternatives are to change tt-metal (drop the Silicon check, rebuild), to change the router's yield interval (the overlay), or to avoid host access to chip 1 after fabric init, which is impossible because results must be read back. A ttsim-only change cannot help either, short of servicing requests without the firmware, which would break the simulator's contract (ttsim AGENTS.md).

Exercise 4. Write a minimal Ethernet-core kernel on chip 0's E9 that copies 16 bytes to chip 1's E1 using the TX queue. Which ttsim checks will you meet?

In eth_txq_regs_wr32 (tile.cpp:1992-2088): start address, size and destination must each be 16-byte aligned (UnimplementedFunctionality otherwise), the tile must have a peer, the range must fit in Ethernet L1 (UndefinedBehavior), a previous command must not still be pending, and on Wormhole ERISC_MAC_0/_1 must hold their trained values. Note that the public CreateKernel takes only DataMovementConfig or ComputeConfig (host_api.hpp:148). EthernetConfig is declared only in the internal impl/kernels/kernel.hpp, so you must build against internal headers or go through the experimental tt_fabric::generate_erisc_datamover_kernel (experimental/fabric/fabric.hpp:159). If it runs long, it must yield through 0x9020, or the host loses chip 1 exactly as in section 4a.

Exercise 5. Using B10_ETHLOG=1, count the link events of the all-gather when the input is 32×128 (two tiles per chip). Predict first.

Prediction: 2 tile packets each way (2096 bytes each, if the op sends one tile per packet), the same 4 semaphore packets, and two credit writes per DATA transfer: (4 + 4) × 3 = 24 events. Check with grep "B10 ETH" ag_eth.log | grep -v "dst=0x14[9a]00\|dst=0x156\|dst=0x18000 n=16" to drop the host's tunnel traffic and the routers' start-up handshakes. If the op batches tiles (the warning suggests 6144-byte packets would be optimal), you will see fewer, larger packets. Treat the prediction as a hypothesis to test.

Recap

  • wh_x2 plus wormhole_N300.yaml gives a 2×1 mesh. Chip 0 is MMIO, and chip 1 is reachable only through chip 0's Ethernet channels 8 and 9 (to chip 1's 0 and 1). ttsim's ETH_PEER_TABLE_N300 and the descriptor agree.
  • Everything the host does to chip 1 is relayed by firmware on chip 0's Ethernet cores. dbrw's 16 MiB went as 4096 four-KiB block writes, each acknowledged. A remote kernel launch is kernel text, a launch message, RUN_MSG_GO, and polls until RUN_MSG_DONE.
  • A MeshWorkload can hold one program per device range. Same binary and addresses, different runtime arguments: verified with 0 / 2048 mismatches.
  • TT-Fabric initializes under ttsim. It then starves the host's tunnel, most likely because tt-metal pins UMD to the dispatch link only on silicon (tt_cluster.cpp:1404) while the non-dispatch routers yield only every 10000 idle checks.
  • A kernel overlay that caps the router's yield interval at 16 makes the fabric usable. A kernel on chip 0 writes chip 1's DRAM with one 4144-byte packet plus two credits, and ttnn.all_gather passes exactly.
  • The stock distributed examples ask for 2×4 (eight chips). Change the shape and they run. wh_x8 fails in the mock firmware's routing, and fast dispatch fails in UMD.

Check yourself

Why does chip 1 report mmio=false, and what does that cost in this lab?

It has no PCIe connection. The descriptor's chips_with_mmio lists only chip 0, and UMD builds chip 1 as a remote chip. Every host read or write to it becomes a request in chip 0's Ethernet-core queue that the firmware relays and acknowledges. In b10_workload, that is why chip 1's launch appears in the Ethernet log as 228 polls of the go word, while chip 0's launch does not appear at all.

The inventory shows a third active Ethernet core on chip 0 (0-15) with no link. Is that a ttsim bug?

No. tt-metal adds channel 15 to the active set on any Wormhole MMIO chip that tunnels to remote chips, because "channel 15 is used by syseng tools" (control_plane.cpp:3145-3162). It has no peer, so get_connected_ethernet_core raises a TT_FATAL for it.

In section 4a, which of these would fix the timeout: (a) a faster host, (b) more ttsim steps per clock for Ethernet cores, (c) pinning UMD to channel 8, (d) a longer UMD timeout?

(c) addresses the most likely cause: requests would only go to routers that yield every 16 checks, which is what tt-metal does on silicon (not tested here, since it needs a tt-metal rebuild). (d) might also work eventually (also untested), but the wait per request on channel 9 is huge. (a) and (b) only shrink the gap. The lab measured (b) at 256 and 2048 steps and the read-back still timed out. The overlay works for a different reason: it makes every router behave like a dispatch-link router.

The 4b kernel's 4 KiB page crossed the link as one 4144-byte transfer. Where do the extra 48 bytes come from, and who writes the page into chip 1's DRAM?

They are the LowLatencyPacketHeader: 40 bytes of NoC command (destination NoC address first), 2 bytes of payload size, 1 of send type, 1 of source channel, and 4 bytes of routing fields. The receiving router on chip 1's E1 reads that header and performs the NoC write into DRAM itself. No kernel runs on chip 1.

The ttsim clock shows the all-gather's two tiles crossing 148 clocks apart (3,396,904 and 3,397,052). What does that tell you about link bandwidth?

Nothing. An Ethernet send in ttsim is a memcpy done inside the register write (tile.cpp:2032). Clocks advance with host reads, and an idle Ethernet core steps once per clock while a busy one steps 16 times (sim.h:402-405). The order of events is meaningful. The gaps are not.

Why do the stock distributed_* examples fail here, and is ttsim at fault?

They hard-code MeshShape(2, 4), eight devices. SystemMesh rejects the request because the n300 system mesh is 2×1 (system_mesh.cpp:153-159). ttsim is not involved: with the shape changed to 2×1, distributed_eltwise_add passes 2048/2048. The eight-chip simulator fails for a separate reason, in the mock Ethernet firmware's routing.
