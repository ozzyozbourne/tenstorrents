B11. TT-NN on the simulator

Use ttsim as a test bench for an operator library: run tt-metal's own TT-NN pytest suite on it, sweep an op over every dtype, layout and memory config, count the NoC bytes each memory config costs, and track one failure down to a single instruction.

Honesty banner. ttsim is a functional, bit-exact simulator. It is not a timing model. Nothing on this page measures speed: bracketed clock counts and wall times describe the simulator on this orb's CPU, not a Tenstorrent chip. What this lab measures is whether an op runs, what values it produces, which kernels it compiles and how many bytes its kernels move. "Passes on ttsim" means "passes on ttsim". ttsim's authors aim to match silicon; I have no silicon in this orb, and section 5 shows two places where the documents say silicon behaves differently. Everything below ran in this orb with tt-metal 7aad8aac and ttsim b3620244 (v1.15.0), on the Wormhole build unless the text says Blackhole.

The question

In A18 you used TT-NN as a user and in A19 you took one op apart. Both chapters ran their scripts on ttsim, one script at a time. This last lab turns the question around. Suppose you change a kernel, or write a new op, or just want to know whether a configuration is legal. You have no Tenstorrent card. Tt-metal ships thousands of TT-NN tests. So:

Can a simulator be your test bench? If 117 matmul tests run on it and 20 of them crash the process, what have you learned about your code, about the simulator, and about the chip?

The answer, worked out over five steps, is "a lot, if you read the failures". By the end you will have a pytest driver that survives simulator crashes, an explorer that tells you which kernels each configuration compiles, exact NoC byte counts for four memory configs of one matmul, and an eight-line simulator patch. That patch turns every Wormhole FP32 crash in our slice of tests into a pass (or a failure the test itself expects). Why it works is the most interesting part.

Setup: what has to be true for import ttnn to reach the simulator

Nothing about TT-NN is simulator-specific. The Python package is the one built with tt-metal, and the switch is one environment variable read deep in the runtime:

tt-metal/tt_metal/llrt/rtoptions.cpp:523-531 @7aad8aac (trimmed)

What happens under ttnn.add

To see what "the simulator runs TT-NN" means, I added call counters to ttsim's exported API (patches/b11-api-count.patch, 11 added lines in src/libttsim.cpp) and ran the same script. Its first line is an all-zero B11API line at clock 0, from a short-lived simulator instance that tt-metal opens and closes during start-up; I omit it:

B11API pci_mem_rd calls=4919 bytes=21824  pci_mem_wr calls=23551 bytes=722884  clock calls=4881 clocks=4881
[4881] 3.4 seconds (1.4 KHz)

The run is identical on a second run. Every byte of tensor data, kernel binary and runtime argument reached the chip as one of 23,551 PCIe writes into the simulated BAR windows. And the simulated chip advanced exactly 4,881 clocks, one per call. Those clocks come from the host, not from a clock of ttsim's own. UMD's simulator device ticks the chip after every read:

tt-metal/tt_metal/third_party/umd/tt-umd/src/tt_device/tt_sim_tt_device.cpp:334-338 @7aad8aac
void TTSimTTDevice::after_read() {
    // Ideally we would not auto-clock on reads at all, but some clocking is required to avoid hangs
    // in the absence of an API reliably called from all spin loops polling the device.
    communicator_->advance_clock(1);
}

So the chip only moves while the host polls it. That is why the clock count is not performance: it counts how often the host looked. The figure follows one call down the stack.

The FP32 rows matter more than they look. TT-NN routes FP32 tensors and fp32_dest_acc_en through one particular unpacker path. On Wormhole, that path crashes stock ttsim in many ops, as section 1 shows. The cause (section 2) is not a bug in the op you are testing.

Selecting tests

-k takes a boolean expression over substrings of the test names: -k "sub_devices", -k "test_sum_global and not FLOAT32", -k "matched_width_height or transpose_a_or_b". It does not accept arbitrary parameter ids. My first try failed in pytest's expression parser before any test ran:

ERROR: Wrong expression passed to '-k': sub_devices and ROW_MAJOR and out_sharded=True-input_b_sharded=True-input_a_sharded=True: at column 42: expected end of input; got =

For one exact case, pass its node id ("path::test_name[param-id]") as an argument, or use --deselect with the node id to drop one. Use --collect-only -q first to see the ids. Then count the cost. The ops themselves are cheap: about 0.4 s per bf16 add test above, and 92 s for 117 matmul tests. At that rate the full 1,260-test matmul file is a matter of tens of minutes, not hours. What is genuinely expensive is a crash, because of how ttsim reports errors:

ttsim/src/common.cpp:33-45 @b3620244 (trimmed)
void ttsim_error(TTSimErrorCategory category, const char *func, const char *fmt, ...) {
    uint64_t clock = ttsim_get_clock();
    printf("[%" PRId64 "] ERROR: %s: %s%s", clock, category_str, func, fmt ? ": " : "\n");
    ...
    fflush(stdout);
    _Exit(1);
}

_Exit(1) skips every handler. Pytest gets no chance to record a failure or to write its summary. Running reduce/test_sum.py -k test_sum_global plainly gives one line of progress, then [4767] ERROR: UndefinedBehavior: tensix_unpacr: ... and exit code 1, after the first of 96 tests. So I wrote a driver, workbench/py/b11_pytest.py. It collects the node ids, runs pytest with -v -s so that each test's id is printed before it starts, and records each outcome. When pytest dies, the test that was running is the one that killed it. The driver records it with the last ttsim ERROR line, then restarts pytest with every passed and aborted test deselected:

On a simulator, a red test can mean three different things: your op is wrong (a FAILED with a PCC message), the test does not apply here (a SKIP), or the simulator refused an instruction (an abort with a ttsim category). Only the first is about your code. Always read the category before you read the test.

Step 2: One abort, down to the instruction

The two messages name the same instruction, UNPACR, the unpacker's "move datums from L1 into SrcA, SrcB or Dst" (A04, A12). Here are the two checks in ttsim:

ttsim/src/tensix.cpp:3153, 3165, 3455-3459 @b3620244
TENSIX_EXECUTE_UNPACR() {
    ...
    TTSIM_VERIFY(!cfg_context_id, UnsupportedFunctionality, "cfg_context_id=%d", cfg_context_id);
    ...
        } else if (in_data_format == 0) { // fp32
            if (out_data_format == 0) { // fp32
                TTSIM_VERIFY(unpack_to_dst, UndefinedBehavior, "unpack_to_dst=%d in_data_format=%d out_data_format=%d",
                    unpack_to_dst, in_data_format, out_data_format);
                value = dst_encode_fp32(value);

The first message is an UNPACR that names configuration context 1 in its CfgContextId field. The second is an FP32 → FP32 unpack that is not going to Dst, so it is going to SrcA. That second one is exactly what the ISA leaves undefined. SrcA cells are 19 bits wide, so FP32 can reach SrcA only as TF32, BF16 or FP16 (Unpackers/FormatConversion.md:29). The functional model makes it explicit:

tt-isa-documentation/WormholeB0/TensixTile/TensixCoprocessor/UNPACR_Regular.md:641-647 @be83310 (trimmed)
  // FP32/INT32 with !UnpackToDst is intentionally UndefinedBehavior. SrcA/SrcB datum slots are 19 bits;
  // storing a 32-bit datum requires lossy conversion to a 16-bit or 19-bit storage format (TF32, FP16,
  // BF16, etc.). Software wanting full-precision FP32/INT32 should use UnpackToDst instead. Silicon
  // behavior in this case is not merely an UnpredictableValue(); the exact behavior has not been
  // validated and must not be relied upon by software.
  case FP32:  return UnpackToDst ? DstEncodeFP32(DatumBits) : UndefinedBehavior();

So ttsim is following the spec. The question becomes: who issues this UNPACR? The JIT descriptor of the aborted FP32 add (in the private cache, kernels/eltwise_binary_sfpu_no_bcast/*/chlkc_descriptors.h) shows that the operands do not go to SrcA. unpack_src_format = {0,0,...} and DST_ACCUM_MODE = true: both inputs are FP32 and are unpacked straight into a 32-bit Dst, because the SFPU does the add. Something else is unpacking to SrcA.

To find out what, I made ttsim say more. An editable copy (build_ttsim.sh why wh, with a few extra arguments added by hand to the two messages; this edit is not shipped as a patch) prints the unpacker, the context, both Unpack_if_sel bits, and how many unpack-to-Dst UNPACRs came first:

[4716] ERROR: UndefinedBehavior: tensix_unpacr: unpack_to_dst=0 in_data_format=0 out_data_format=0 unpacker=0 (B11: 0=SrcA/Dst, 1=SrcB) context=0 if_sel_cntx0=0 if_sel_cntx1=0 earlier_to_dst_unpacrs=4
[4634] ERROR: UnsupportedFunctionality: tensix_unpacr: cfg_context_id=1 (B11: unpacker=0 zero_write2=1 set_dat_valid=0)

The bad UNPACR comes after four unpack-to-Dst UNPACRs had already run, and after Unpack_if_sel has been switched back to "not Dst". It has zero_write2=1 (the ISA's AllDatumsAreZero) and no dvalid. That is a deliberate dummy, and the Wormhole LLK says why:

tt-metal/tt_metal/tt-llk/tt_llk_wormhole_b0/common/inc/cunpack_common.h:963, 969-985 @7aad8aac (trimmed)
inline void unpack_to_dest_tile_done(std::uint32_t &context_id, const std::uint32_t unpack_dst_format)
{
    ...
    if (context_id == 0)
    {
        cfg_reg_rmw_tensix<THCON_SEC0_REG2_Unpack_if_sel_cntx0_RMW>(0);
        ...
    // Due to a hardware bug (TEN-3868), we need to have one unpack-to-srcA instruction after the last unpack-to-dest instruction.
    TTI_SETADCXX(p_setadc::UNP_A, FACE_C_DIM - 1, 0x0);
    TT_UNPACR(SrcA, 0, 0, context_id, 0, 1 /* Set OvrdThreadId*/, 0 /*Set Dvalid*/, p_unpacr::RAREFYB_DISABLE, 1, 0, 0, 0, 1);
    TTI_SETADCXX(p_setadc::UNP_A, FACE_R_DIM * FACE_C_DIM - 1, 0x0);
}

Read the TT_UNPACR arguments against the macro in ckernel_ops.h:833-851: unpacker A, address mode 0, CfgContextId = context_id, OvrdThreadId 1, SetDatValid 0, ZeroWrite2 = 1. That one instruction explains both messages:

  • In context 0 the instruction still sees the tile's FP32 formats, with unpack-to-Dst now switched off: FP32 → FP32 into SrcA, UndefinedBehavior.
  • In context 1 (the unpacker LLK uses two configuration contexts) it carries CfgContextId = 1, which ttsim does not support at all: cfg_context_id=1. That is A18's matmul crash.

Blackhole's version of unpack_to_dest_tile_done (tt_llk_blackhole/common/inc/cunpack_common.h:976-993) has no dummy unpack. That is why the Blackhole build passed every FP32 case.

The patch

On silicon this instruction exists to work around a hardware bug, and nothing reads what it writes: it sets no dvalid, so the FPU never consumes SrcA. I first tried to "execute it properly". That took three rounds: tolerate FP32 into SrcA, then implement zero_write2 (ttsim reports it as UntestedFunctionality), then drop its writes past SrcA's 64 rows (UnsupportedFunctionality: tensix_unpacr: src_a row=64). Each round only uncovered the next unmodelled corner, so in the end I treated the dummy as the no-op it is meant to be:

sim-labs/patches/b11-ten3868.patch (against ttsim/src/tensix.cpp @b3620244)
 TENSIX_EXECUTE_UNPACR() {
+#if TT_ARCH_VERSION == 0
+    // B11: Wormhole's LLK follows every unpack-to-Dst tile with one dummy UNPACR to SrcA (hardware bug
+    // TEN-3868): all-zero datums, no dvalid, no address increment, in the tile's config context.
+    // Nothing reads what it writes, so treat it as a no-op instead of checking its (FP32) formats.
+    if (zero_write2 && !set_dat_valid && !unpack_block_selection && !addr_mode) {
+        return true;
+    }
+#endif
$W/build_ttsim.sh ten3868 wh && (cd $LAB_HOME/ttsim-ten3868 && patch -p1 < $P/b11-ten3868.patch) && $W/build_ttsim.sh ten3868 wh
export TT_METAL_SIMULATOR=$LAB_HOME/sim-ten3868-wh-release/libttsim.so
for c in add_fp32 sum_fp32 mm_fp32acc; do python $W/py/b11_s1_probe.py $c; done
add_fp32 max|err| 0.0 bit-identical True
sum 32.93839645385742 torch 32.93839645385742
PCC 0.9999958038338154

The table in section 1 has the effect: every one of the 98 aborts in the slice became a pass (or, for two matmul cases, an expected failure the test itself marks xfail). Two controls show the patch changed nothing else. test_add.py gave the same 86/16, and in the 54-case explorer of the next section, all 46 cases that did not abort had the same status, PCC and max error, to the last digit, with and without the patch.

This patch is a modelling decision, not a fix you can upstream as-is. It assumes the dummy unpack's side effects are invisible. That is what the LLK comment implies, but nothing here verifies it. A ttsim that executed the instruction exactly would need the TEN-3868 hardware behaviour itself, which is not public. Use the patched simulator to test your FP32 op's values. Do not use it to argue about the unpacker.

Step 3: An op explorer

A pytest file tells you whether someone else's chosen cases pass. When you are designing, you want the whole space: every dtype × layout × memory config of one op, with an accuracy number for each, and for each one, which kernels actually ran. workbench/py/b11_explore.py does that. Each case runs in its own process (aborts again). Each process gets a private TT_METAL_CACHE. That cache starts with only firmware and precompiled headers, hard-linked from a seed cache, so afterwards its kernels/ directory lists exactly the kernels this case compiled. A JIT cache entry is a directory per kernel name and hash:

$LAB_HOME/jit0/tt-metal-cache3486047672140553623/kernels/eltwise_binary_no_bcast/10083976056017848008/trisc0
$LAB_HOME/jit0/tt-metal-cache3486047672140553623/kernels/reader_interleaved_no_bcast/10456270060302663221/ncrisc
$LAB_HOME/jit0/tt-metal-cache3486047672140553623/kernels/writer_interleaved_no_bcast/2689147808996234265/brisc

This listing is from the 32×32 smoke test. The reader runs on NCRISC, the writer on BRISC, and the compute kernel on the three TRISCs. The cache was 93 MB, 92 MB of it precompiled headers, which is why the explorer links them instead of rebuilding.

What the matrix says, cell by cell:

  • Rejections happen on the host and cost nothing. bfp8 must be TILE (a block-float exponent is shared by 16 datums of one face row, A05), and matmul wants tilized inputs. These are TT-NN's validation, and they would happen on silicon too.
  • Within one dtype, the memory config does not change an add's result: all six bf16 cells give PCC 0.999997 and max error 0.0205. An add is element-wise, so where its tiles live cannot matter. Only bfp8 height-sharded differs slightly (0.0577 vs 0.0595). With the patch, the FP32 add is exact (max error 0.0): an SFPU add of two FP32 values, packed as FP32.
  • A ROW_MAJOR input that is height-sharded compiles 7 kernels instead of 3. TT-NN tilizes it on the device first (tilize_metal2, with its own sharded reader and writer) and untilizes the result. Same answer, but 4 extra kernels, and extra programs on every call.
  • For matmul, the memory config changes the program. The DRAM case compiles the 2D-multicast kernels (reader_bmm_tile_layout_in0_sender/receiver, in1_sender/receiver). L1-interleaved compiles bmm_metal2 and reader_bmm_8bank_output_tiles_partitioned_metal2: the plain multi-core matmul with no reuse. Height-sharded compiles the 1D variant: an in0 sender but no in0 receiver. The max error shows it too: 0.0424 for DRAM vs 0.0604 for L1 and height (256×256 bf16), because a different program sums K in a different order.
  • The stock FP32 matmul aborts only on the DRAM row, the 2D-multicast program. The L1 and height-sharded FP32 matmuls ran on stock ttsim with PCC 1.000000. "fp32 matmul aborts" (A18) is true of the program A18's call happened to get, not of every FP32 matmul.

Why would putting the output in L1 select a different program? On a GPU, the closest thing is cuBLAS choosing a different GEMM kernel for a different shape or alignment. You can see that choice with Nsight, but you rarely cause it by changing where the output lives. On Tenstorrent, placement is an input to kernel selection, so record the kernel list whenever you compare configs.

Step 4: Count the bytes of each memory config

A20 counted an element-wise add with ttsim and patches/a20-counters.patch, and found that a sharded add issues zero NoC commands. A matmul is more interesting, because its inputs are reused: each input tile is needed by a whole row or column of output tiles. The A20 counters log every NoC command a Tensix core issues, sorted by kind and by destination. I reused them unchanged with a matmul script, workbench/py/b11_traffic.py. It computes x[256, 256] @ w[256, 256] in bf16, places x and the output with one memory config, and keeps w DRAM-interleaved:

export TT_METAL_SIMULATOR=$LAB_HOME/sim-count-wh-release/libttsim.so
for m in dram l1 height block; do python -I $W/py/b11_traffic.py $m; python -I $W/py/b11_traffic.py $m prep; done

Measure:

Check the DRAM case against arithmetic. Each core needs 8 x tiles and 8 w tiles, and 64 cores × 16 = 1,024 tile arrivals. The counters show 128 DRAM reads + 896 multicast tile deliveries = 1,024. Exactly the same number of tiles land in L1 as in the no-reuse L1 case (512 + 512 reads). The difference is where they come from: one DRAM read plus a fan-out, instead of eight separate reads. The 896 atomics match the deliveries one for one, which fits the receivers' semaphore increments of the multicast handshake A16 drew. In the height-sharded case, x is already where it is consumed, so only w moves: 64 + 7 × 64 = 512 tile arrivals.

The Tensix instruction counters printed by the same patch also differ, for the same output. T1 (math) retired 25,664 instructions for the DRAM case, 20,480 for L1-interleaved, 17,792 for height-sharded and 20,784 for block-sharded. The programs block the work differently, so even the math thread's instruction stream depends on the memory config.

These are exact counts of commands, not times. ttsim completes a NoC transfer inside the instruction that issues it (B05), so it says nothing about whether 896 multicast deliveries beat 512 extra DRAM reads. On silicon, the multicast's single DRAM read is the point (A16), but contention and link widths decide the rest. Use these numbers to check a mental model of an op's data movement. Do not use them to rank configs by speed.
The per-command view is one patch away: apply b05-noclog.patch to the same copy, and each of these commands becomes a log line with its source, destination and length.

Step 5: Where ttsim and the documents disagree

A test bench is only as good as its model. Here are the places where, in this lab, what ttsim did differs from what a document says silicon does or what the series' notes say ttsim does. Each one is stated narrowly.

1. The TEN-3868 dummy unpack: tt-llk relies on what the ISA spec leaves undefined

  • The ISA spec (UNPACR_Regular.md @be83310): FP32 → FP32 into SrcA is UndefinedBehavior (lines 641-647). A non-zero ContextNumber is UnsupportedFunctionality with "No known usage, confidence in specification below is weak" (line 36).
  • tt-llk for Wormhole (cunpack_common.h:981-983) issues exactly such an instruction, with CfgContextId = context_id (0 or 1) and the tile's FP32 formats, after every unpack-to-Dst tile. It does so on purpose, to work around hardware bug TEN-3868.
  • Silicon, by implication, runs it every time an FP32 op unpacks to Dst: these tests are written for Wormhole hardware, and the LLK comment says the instruction is needed there. I could not check this on silicon.
  • ttsim follows the ISA spec literally and ends the process. That aborted 98 of the 354 tests in my slice. With the eight-line patch, 96 of them pass and 2 are the test's own expected failures (xfail), and nothing else changed.

So the usage the ISA calls unknown has a known user, and that user is tt-llk itself. The ISA describes the instruction in isolation. The LLK relies on the side effect of a hardware bug fix, which is described nowhere public. A simulator built from the spec has to choose one of them.

2. Wormhole HiFi4 + FP32 accumulation

TT-NN prints a warning when you combine them on Wormhole:

warning | Op | On Wormhole with fp32 accumulation, output accuracy can be worse with HiFi4 than HiFi3 due to a hardware bug. Prefer using HiFi3 with fp32 accumulation on Wormhole. (compute_kernel_config.cpp:66)

The source comment (compute_kernel_config.cpp:44) points to issue #38306. That issue reports, so far seen only on Wormhole, a few deterministic outputs off by roughly a power of two (1 bad point in a 4096³ matmul). It also says "Blackhole numerics look different from Wormhole". I ran a 128×1024 @ 1024×128 bf16 matmul with FP32 accumulation at HiFi2/3/4 on patched Wormhole ttsim and stock Blackhole ttsim (workbench/py/b11_s3_hifi.py; the last three lines compare the two runs' tensors, saved with B11_SAVE=<file>.pt, using torch.equal):

HiFi2: mean|err| 1.041e-01  max|err| 5.717e-01
HiFi3: mean|err| 8.225e-03  max|err| 4.194e-02
HiFi4: mean|err| 8.052e-03  max|err| 3.961e-02
HiFi3 == HiFi4 bit for bit: False  elements that differ: 16383 of 16384
HiFi2 WH==BH bitwise: True 0
HiFi3 WH==BH bitwise: True 0
HiFi4 WH==BH bitwise: True 0

In ttsim, HiFi4 is slightly better than HiFi3, and the Wormhole and Blackhole builds give bit-identical results at every fidelity. The issue says silicon numerics differ between the two. My test is far too small to have hit the rare bad points, so it does not show that ttsim lacks the bug. What it does show is that ttsim's two builds share one matmul arithmetic here (its mvmul arithmetic has no per-architecture branch; the one Wormhole-only step in its matmul, a source-format mask, leaves bf16 inputs unchanged). A Wormhole-only FPU difference is therefore not modelled, and a ttsim pass cannot vouch for one.

3. The device profiler produces data, except for the last program

The series' feasibility notes (research/06-feasibility.md) say TT_METAL_DEVICE_PROFILER=1 "produces a CSV with only the header". For a single-program metal example that is what happens (A20 reproduces it), but not for TT-NN here. Three ttnn.add calls on a 64×64 tensor wrote a 3,762-line profile_log_device.csv, with or without an explicit ttnn.ReadDeviceProfiler:

ARCH: wormhole_b0, CHIP_FREQ[MHz]: 0, Max Compute Cores: 72
PCIe slot, core_x, core_y, RISC processor type, timer_id, time[cycles since reset], data, run host ID, ...
0,1,1,BRISC,46845,4426,0,1024,,,BRISC-FW,ZONE_START,439,.../brisc.cc,

The 3,760 data rows are FW and KERNEL start/end zones for all five RISC-Vs, for run host IDs 1024 and 2048 on all 64 cores (1,280 rows each), and 1,200 rows for the last op, 3072: four of its cores are missing. The same effect most likely explains the empty file in the notes and in A20. The firmware sets RUN_MSG_DONE inside its BRISC-FW zone, and only the zone's destructor afterwards pushes the core's markers to DRAM (hw/firmware/src/tt-1xx/brisc.cc:438, 600 and hw/inc/api/debug/kernel_profiler.hpp:801-803 @7aad8aac). On silicon that push finishes long before the host reads. Under ttsim the cores only run while the host polls, and the host reads the profiler buffers as soon as it sees "done", so the last program's push has barely started. Earlier programs flush while the host polls for the next one. A metal example that runs one program therefore gets only the header; a single ttnn.add gets 704 rows, with no TRISC1 or TRISC2 zones at all; and twenty extra to_torch reads after it raise that to 884. Two things stop this from being a performance tool: the timestamps are simulated clocks (one TRISC1 kernel zone spans 4589 → 4657), and CHIP_FREQ is 0 MHz, so no tool can convert them to time. What the zones are good for is ordering: which RISC started its kernel before which.

4. Not differences, but easy to mistake for them

  • Trace is not a ttsim limitation. It is refused by tt-metal's slow-dispatch queue, and it works under ttsim in fast dispatch.
  • The 16 skipped sub-device tests are not a ttsim limitation either. The skip keys on the environment variable, and they pass in fast dispatch.
  • The 64-core grid comes from tt-metal's core descriptor, not from a ttsim limit.

Exercises, with answers

1. Without reading the counters, predict the DRAM-interleaved case's DRAM read and write bytes. Then explain the 896 atomics.

x and w are 8 × 8 = 64 tiles each, 2,048 bytes per bf16 tile. A 2D-multicast matmul reads each input tile once: 128 × 2,048 = 262,144 bytes, which matches dram_read bytes=262144. The output is 64 tiles: 131,072 bytes written, which matches too. Each of the 896 tile deliveries is acknowledged by its receiver incrementing a semaphore in the sender's L1 (the receiver-ready handshake of A16). That is one 4-byte atomic per delivery: 896 × 4 = 3,584 bytes, as printed.

2. Run the 16 sub-device add tests that slow dispatch skips. What do you have to change, and what happens? 
env -u TT_METAL_SLOW_DISPATCH_MODE pytest -p no:cacheprovider -o addopts= --import-mode=importlib -q $T/eltwise/test_add.py -k sub_devices

Only the environment variable: skip_for_slow_dispatch tests it with os.environ.get(...) == "1". In fast dispatch the clock count is far higher (1.8 M for the 16 tests). I did not break the clocks down. Since the host drives them, they mostly measure how long it polled while dispatch firmware forwarded the work. More clocks, but only 27 s.

3. Apply b11-api-count.patch and compare one 32×32 add in slow and fast dispatch. Which uses more host writes, and why? 
slow: B11API pci_mem_rd calls=4919 bytes=21824  pci_mem_wr calls=23551 bytes=722884  clock calls=4881 clocks=4881
fast: B11API pci_mem_rd calls=4960 bytes=19944  pci_mem_wr calls=18428 bytes=313140  clock calls=13440 clocks=13440

Slow dispatch writes 2.3× the bytes. In slow dispatch the host writes each worker's binaries and arguments itself. In fast dispatch the host hands command packets to the prefetcher (A17), and the dispatch firmware fans them out to the workers over the NoC, where the host's counters cannot see them. That is consistent with fewer host writes. Fast dispatch also took 2.75× the clocks; my reading is that the dispatch firmware's loops have to run before the workers start, but I did not measure that. Neither number is a time.

4. The matmul explorer's FP32 row aborts only for DRAM. Using the kernel lists, which kernel is the likely culprit, and why do the height-sharded FP32 matmuls survive with the same compute kernel?

The DRAM case is the only one that combines bmm_large_block_zm_fused_bias_activation_metal2 with the 2D in0 receiver. Height-sharded uses the same compute kernel and survives, so the compute kernel name alone does not decide it. The abort is the TEN-3868 dummy, which only runs after an unpack-to-Dst, in context 1. In this compute kernel, unpack-to-Dst is used to reload partial sums from L1 when K is split into more than one block (the "crossblock reload" that test_matmul_fp32_crossblock_reload_precision exercises, and which also aborted). The 2D config splits K into blocks. My reading is that the 1D config here did not, but I did not confirm it from the chosen in0_block_w, so treat it as a hypothesis. To test it, print ttnn.matmul's program config, or count unpack-to-Dst UNPACRs with the why build.

Recap

  • TT-NN reaches ttsim through one variable. TT_METAL_SIMULATOR switches the target, and UMD turns every device access into a call into libttsim.so. A 32×32 add was 23,551 PCIe writes and 4,881 host-driven clocks, identical on every run.
  • tt-metal's pytest suite runs unmodified, at roughly 0.3 to 0.8 s per small test. A ttsim error calls _Exit(1), so one abort kills the whole run. b11_pytest.py restarts and attributes each abort to its test and its ttsim message.
  • Every non-pass in a 354-test slice was a skip or a simulator abort, and every Wormhole abort traced to one instruction: the dummy UNPACR that tt-llk issues after unpack-to-Dst for hardware bug TEN-3868. The ISA calls that instruction undefined or unsupported. Blackhole's LLK does not issue it, and Blackhole passed everything. An eight-line ttsim patch (a modelling workaround, not a ttsim bug fix) turned the 98 aborts into 96 passes and 2 expected failures, and changed no other result.
  • The explorer shows what pytest hides: host-side rejections, the kernels each config compiles, and that a matmul's memory config selects its program. An L1-interleaved output fell back to a matmul with no reuse.
  • Exact NoC counts per memory config: DRAM reads ranged from 1 MiB (no reuse) to 128 KiB (sharded) for the same matmul, and the multicast configs swapped DRAM reads for NoC deliveries. Counts, not times.
  • Know what a pass means. ttsim's WH and BH builds gave bit-identical matmuls where silicon is reported to differ, and its profiler timestamps are host-driven clocks. A ttsim pass checks values and data movement against ttsim's model of the chip, nothing more.

Check yourself

pytest prints nothing after [4767] ERROR: UndefinedBehavior: ..., not even a failure. Why, and how would you find which test caused it?

ttsim's ttsim_error calls _Exit(1), which ends the process without running Python's exception machinery, atexit handlers or pytest's reporting. The culprit is the test that started last: run with -v -s so that pytest prints each node id before running it, then take the last id before the ERROR line. b11_pytest.py does exactly that and reruns with the test deselected.

An FP32 add aborts with unpack_to_dst=0 in_data_format=0 out_data_format=0, yet its JIT descriptor says both operands are unpacked to Dst. Resolve the contradiction.

The operands are unpacked to Dst. The failing UNPACR is a different instruction: tt-llk's dummy unpack to SrcA after the last unpack-to-Dst (TEN-3868). It runs with the tile's FP32 formats still configured but unpack-to-Dst switched off, so it is formally an FP32 → FP32 unpack into SrcA, which the ISA calls UndefinedBehavior. ttsim's instrumented message showed it directly: four earlier to-Dst UNPACRs, then this one with zero_write2=1 and no dvalid.

You change memory_config=ttnn.DRAM_MEMORY_CONFIG to ttnn.L1_MEMORY_CONFIG on a 256×256 matmul and its max error changes from 0.0424 to 0.0604. Is L1 less accurate?

No. Memory placement cannot change arithmetic, but it changed the program. With an L1 output the inputs are not all DRAM-interleaved, and the whole output is one per-core block, so the automatic config falls back to MatmulMultiCoreProgramConfig. That is a different kernel with a different accumulation order and blocking. Compare kernel lists (or program configs) before you compare numbers.

The DRAM-interleaved matmul reads 128 tiles from DRAM and the L1-interleaved one reads 512 from DRAM and 512 from other cores. Can you conclude the first is about 4× faster on silicon?

No. The first also does 896 multicast deliveries plus 896 semaphore atomics, and ttsim models none of the costs: DRAM bandwidth, NoC link occupancy, multicast fan-out, contention, or overlap of compute with data movement. The counts tell you which resources each program uses, and how much of each. Speed needs silicon or a timing model.

Which of these failed on ttsim because of tt-metal rather than ttsim: (a) trace in slow dispatch, (b) FP32 add on Wormhole, (c) bfp8 ROW_MAJOR tensor, (d) sub-device add tests?

(a) tt-metal: the slow-dispatch command queue throws Not supported for slow dispatch. Trace works in fast dispatch on ttsim. (c) TT-NN's host-side validation, the same on silicon. (d) A test-level skip keyed on the environment variable; they pass in fast dispatch. Only (b) is a ttsim decision: it enforces the ISA on an instruction the Wormhole LLK issues deliberately.
