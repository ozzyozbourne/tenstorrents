B08. Data formats and SFPU numerics

Push the same numbers through FP32, BF16, BFP8 and BFP4 on the simulated chip and watch exactly which bits fall off. Then write your own SFPI kernel with a four-way v_if and a polynomial sin, see which SFPU lane touched which Dst cell, and measure what "approximate mode" really changes.

Honesty banner. ttsim is a functional, bit-exact model of the chip. It is not a timing model. The bracketed clock numbers in the logs below are not silicon performance, and nothing on this page measures speed. What ttsim does model bit for bit is the arithmetic: format conversions in the unpacker and packer, the SFPU's FMA, its rounding and truncation. That is exactly what this lab is about, so a mismatch between your model and ttsim here is a real finding. There is one place where ttsim and tt-metal disagree about what is legal; section 2 shows it.

The question

Here is a function, written in SFPI, the C++ dialect for the vector engine. It is a soft clamp built from two parabolas:

y = -1          if x < -1
y = x * (x + 2) if -1 <= x < 0
y = x * (2 - x) if  0 <= x < 1
y = 1           otherwise

Every input is a BF16 number, every intermediate is exact in FP32 (the product of two 8-bit significands has at most 16 bits), and the output is BF16 again. A careful CPU would return the correctly rounded answer every time. I ran it over 4096 evenly spaced inputs in [−2, 2] on the simulated Wormhole. This is what came back:

fn=piecewise fmt=bf16 dst32=0 u2d=0 approx=0 expt=0 fold=1 range=[-2,2] n=4096
max_abs_err=0.00389 (at x=-0.996094) mean_abs_err=0.000812 max_rel_err=0.00715
ulp vs correctly rounded: exact=3088 1ulp=1008 >1ulp=0 max=1

A quarter of the answers are one unit in the last place (ulp) off, and every one of them is off toward zero. Nothing is wrong with the arithmetic. Something between the FP32 lanes and the BF16 output is throwing bits away instead of rounding them. By the end of this lab you will be able to point at the exact instruction, and at the line of the ISA manual and of ttsim that describes it. Along the way you will meet four more places where bits go missing: the shared exponent of block floating point, the 19-bit source registers, the 16-bit Dst, and "approximate mode".

All commands below were run in this orb, on the Wormhole model unless the text says Blackhole. Every output is real and trimmed only of tt-metal's log lines.

1. Four formats, one block of sixteen numbers

A05 asked whether 16 numbers can share one exponent and stay useful. Let's answer it with numbers chosen to hurt. I put sixteen values spanning five orders of magnitude into face 0, row 0 of a 32×32 tile, which is exactly one BFP block. Two of them (3.0 and 2.5) are large, and the rest shrink down to 0.0001. The probe sends the tile through each format twice: on the host with ttnn.from_torch(x, dtype=…), and on the device with ttnn.typecast, whose packer writes the target format.

sim-labs/workbench/py/b08_formats.py (core lines)
block = [3.0, 1.2345678, 0.7, -0.4, 0.3, 0.15, -0.1, 0.06, 0.03, 0.012, 0.007, -0.003, 0.0015, 1e-4, 2.5, -1.75]
x = torch.zeros((32, 32), dtype=torch.float32)
x[0, :16] = torch.tensor(block)
def host_rt(x, dt):    # host packer (C++), then back to float32
    return ttnn.to_torch(ttnn.from_torch(x, dtype=dt, layout=ttnn.TILE_LAYOUT)).float()
def dev_rt(x, dt):     # FP32 tile on device, device packer writes dt, read back
    t = ttnn.from_torch(x, dtype=SRC, layout=ttnn.TILE_LAYOUT, device=device)
    return ttnn.to_torch(t if dt == SRC else ttnn.typecast(t, dt)).float()

Read it column by column before reading any theory.

  • float32 is a perfect round trip. DRAM does not care what the bytes mean.
  • bfloat16 keeps every value, each with its own exponent, to about 3 significant digits: 0.0001 is still there as 0.000100136. The error is relative, at most 2−8 of each value.
  • bfloat8_b keeps the large values well, has 0.03 at one bit, and turns everything from 0.012 down into exactly 0. The error is now relative to the block's largest value, not to each value.
  • bfloat4_b keeps only multiples of 0.5. Four of sixteen values survive. And here host and device disagree: −0.4 is −0.5 on the host and 0 on the device, −1.75 is −2 on the host and −1.5 on the device.

Step through the figure to see why each number lands where it does. The values in the right-hand columns are the real device outputs above. The bit strips are computed by the page from the BF16 encoding of each input.

BF16 error is relative to each value. BFP error is relative to the largest value in the block: a value 2n below the block maximum keeps 7−n bits in BFP8 and 3−n bits in BFP4. At n = 7 (or 3) no bits are left, and the value survives only if rounding carries it up to one unit, as 0.03 did in BFP8 (and 0.3 in the host's BFP4; the device truncates it to 0). From n = 8 (or 4) on it is exactly 0. Nothing is lost gracefully below that.

Three things to take away. First, one outlier ruins its own block (BFP8 relative error in block 0 jumps from 1.2% to 62%) and leaves the neighbouring block untouched (0.63% before and after): the damage is exactly 16 values wide. Second, PCC barely notices: BFP8 goes from 0.999972 to 0.999894 while fifteen values were wrecked, the trap A05 warned about. Third, BFP4 is much worse on the device than on the host (mean relative error 0.425 vs 0.295), because the device rounds to BFP8 and then truncates, as the figure showed. The ISA states this directly for the packer (Packers/FormatConversion.md:71, cited in A05).

For Wormhole I reran the probe with a BF16 source tile (B08_SRC=bf16 python $W/py/b08_formats.py). With that source, the Wormhole and Blackhole outputs were identical line for line (checked with diff).

2. What survives the trip into Dst

The probe treated the device as a black box. Now open it. A compute kernel never touches L1 data directly. The unpacker converts a tile from its CB format into a register format, either into SrcA (for the FPU) or straight into Dst, and the SFPU only ever sees Dst (A07). The simplest experiment is the identity: B08_FN=copy does copy_tile, no math, then pack_tile. Feed it FP32 values in [1, 2) and change only how Dst is configured:

$ B08_FN=copy B08_FMT=fp32 B08_DST32=0 $LAB_HOME/b08_sfpu
max_abs_err=0.00781 (at x=1.99219) mean_abs_err=0.0039 max_rel_err=0.00751
ulp vs correctly rounded: exact=2 1ulp=0 >1ulp=4094 max=65520

$ B08_FN=copy B08_FMT=fp32 B08_DST32=1 $LAB_HOME/b08_sfpu
max_abs_err=0.000976 (at x=1.99902) mean_abs_err=0.000488 max_rel_err=0.000732
ulp vs correctly rounded: exact=2 1ulp=0 >1ulp=4094 max=8190

An FP32 tile in, an FP32 tile out, no arithmetic, and only 2 of 4096 values survive either way. The dump shows what happened to individual bit patterns:

input        Dst 16-bit   Dst 32-bit (via SrcA)
3fbffc00 ->  3fbf0000     3fbfe000
3f801802 ->  3f800000     3f800000

With a 16-bit Dst, the low 16 bits are simply cleared: 0x3fbffc00 becomes 0x3fbf0000, the BF16 value just below it, although 0x3fc00000 is closer. With a 32-bit Dst the value still went through SrcA, which holds at most 19 bits (TF32: sign, 8 exponent bits, 10 mantissa bits), and the low 13 bits are cleared. ttsim's unpacker says exactly this:

ttsim/src/tensix.cpp:3472-3482 @b3620244
            } else if (out_data_format == 4) { // tf32
                if (unpack_to_dst) {
                    value = dst_encode_fp32(value);
                } else {
                    value &= 0xFFFFE000; // drop low 13 bits of mantissa (no rounding)
                }
            } else if (out_data_format == 5) { // bf16
                ...
                value &= 0xFFFF0000; // drop low 16 bits of mantissa (no rounding)

tt-metal knows this too. A test comment says it outright: "a plain Float32 CB is lowered to Tf32 in SrcA under fp32_dest_acc_en and would round the right-hand side before the solve sees it" (tests/tt_metal/tt_metal/llk/test_triangle_solve.cpp:315-318). (The comment says "round", but the measurement and ttsim both show truncation.) The fix the test uses is UnpackToDestMode::UnpackToDestFp32, which makes the unpacker skip SrcA and write FP32 into Dst. That is B08_U2D=1. On Blackhole:

$ source $W/env.sh bh; B08_FN=copy B08_FMT=fp32 B08_U2D=1 $LAB_HOME/b08_sfpu
max_abs_err=0 (at x=0) mean_abs_err=0 max_rel_err=0
ulp vs correctly rounded: exact=4096 1ulp=0 >1ulp=0 max=0

All 4096 values are exact. On Wormhole the same run stops:

$ source $W/env.sh wh; B08_FN=copy B08_FMT=fp32 B08_U2D=1 $LAB_HOME/b08_sfpu
[4513] ERROR: UndefinedBehavior: tensix_unpacr: unpack_to_dst=0 in_data_format=0 out_data_format=0

I instrumented a copy of ttsim (build_ttsim.sh u2d wh) to print which unpacker raised it and to count the successful FP32 unpack-to-Dst datums before it. The answer was unpacker 0, with the thread-override bit set, after exactly 1024 good datums: one full tile went into Dst correctly, and then something else unpacked FP32 into SrcA. That something is a deliberate hardware workaround in the Wormhole LLK:

tt-metal/tt_metal/tt-llk/tt_llk_wormhole_b0/common/inc/cunpack_common.h:981-983 @7aad8aac
    // Due to a hardware bug (TEN-3868), we need to have one unpack-to-srcA instruction after the last unpack-to-dest instruction.
    TTI_SETADCXX(p_setadc::UNP_A, FACE_C_DIM - 1, 0x0);
    TT_UNPACR(SrcA, 0, 0, context_id, 0, 1 /* Set OvrdThreadId*/, 0 /*Set Dvalid*/, p_unpacr::RAREFYB_DISABLE, 1, 0, 0, 0, 1);

ttsim rejects an FP32-to-FP32 unpack into SrcA as undefined behaviour (tensix.cpp:3456-3458). That check is exactly the one that fires, and it follows the ISA: the unpacker table offers FP32 into SrcA only with an output format of TF32, BF16 or FP16 (Unpackers/FormatConversion.md:29), and the dummy unpack leaves the output format at FP32 from the unpack-to-Dst setup. So ttsim is not contradicting the ISA here. It is strict about a configuration the ISA does not define, which the LLK uses on purpose and whose SrcA data it never marks valid. I then tried relaxing ttsim step by step. Allowing that unpack led to UntestedFunctionality: zero_write2=1, and allowing that led to UnsupportedFunctionality: src_a row=64. So the dummy unpack uses several features ttsim does not model. I stopped there, and the patched simulator is not part of the lab. The same gap is why ttnn.typecast from FP32 fails on Wormhole ttsim in section 1: typecast also unpacks FP32 inputs straight to Dst. This is a real disagreement between the two sources: the LLK says silicon needs this instruction, and ttsim says it is undefined. Neither is "wrong" about its own domain, but the consequence is that on Wormhole ttsim you cannot test a bit-exact FP32 path through Dst; use Blackhole for that.

The way out: SFPSTORE truncates

Back to the opening question. In the piecewise run, the input reached Dst as BF16 (lossless) and the SFPU computed in FP32 (exactly, as argued). The last step is SFPSTORE writing an FP32 lane into a 16-bit Dst. The ISA:

tt-isa-documentation/WormholeB0/TensixTile/TensixCoprocessor/SFPSTORE.md:38 @be833101
As part of the conversion to FP32 / FP16 / BF16, denormals will be flushed to zero. Additionally, when
converting to FP16 / BF16, mantissa will be truncated towards zero.
ttsim/src/tensix.cpp:4134-4136 @b3620244
        } else if (instr_mod0 == 2) {
            value = denormals_as_zeros(value);
            sfpu_write_cell16(p_tensix, cell_bank, row, col, dst_encode_bf16(value >> 16));

value >> 16 keeps the top 16 bits: truncation toward zero. I checked the dump: none of the 4096 piecewise outputs is larger in magnitude than the exact answer. 3920 of them equal the exact answer truncated to BF16. The other 176 are also below it, by one more step, because their FP32 intermediate was already a hair under the exact value. That accounts for the 1008 one-ulp results.

Bits are cut at three places, and none of them rounds: the unpacker into SrcA (to 19 bits) or into a 16-bit Dst (to BF16), and SFPSTORE into a 16-bit Dst (to BF16). The packer does round when it writes BFP formats, ties away from zero (A05); whether it rounds FP32 to BF16 I did not test here (the ISA's late-conversion table says it truncates, Packers/FormatConversion.md:67). If you want correctly rounded BF16 out of an SFPU kernel, you have to round in the lanes yourself before the store. The precise reciprocal in section 6 does exactly that.

With FP32 throughout (Blackhole, B08_FMT=fp32 B08_U2D=1), the same piecewise kernel gives max_abs_err=8.77e-08, with every output within 1 FP32 ulp of correct. The algorithm was never the problem.

3. 32 lanes, and which Dst cell each one touches

A07 drew the SFPU as 32 lanes. Check that against the primary sources. The Wormhole ISA: "It can be considered as a general-purpose SIMD engine, consisting of 32 lanes of 32 bits" (VectorUnit.md:3, the same sentence in the Blackhole manual). LReg 15 is read-only and "lane i contains the integer value i*2" (LReg.md:15). ttsim implements the register file as

ttsim/src/sim.h:283-292 @b3620244
    uint32_t l_regs[16][32]; // only 8 fully usable regs, but 16 sources easier to implement this way
    ...
    bool cc_en;
    uint32_t cc;
    bool cc_en_stack[CC_STACK_SIZE];
    uint32_t cc_stack[CC_STACK_SIZE];

So: 32 lanes, one 32-bit flag word cc holding each lane's predicate bit, and a stack of saved flag words. (The ISA lists 17 LRegs; ttsim stores 16 and leaves out LReg 16, which only SFPLOADMACRO can reach. ttsim does not implement that instruction anyway, which is why env.sh sets TT_METAL_DISABLE_SFPLOADMACRO=1.)

You can make the lanes visible. The map face function ignores its input and writes, into each element, the number of the vector and the lane that stored it:

sim-labs/overlays/b08/b08/sfpu_lab.cpp:22-28
inline void b08_map_face() {
    for (int i = 0; i < 8; i++) {
        // LReg15 (vConstTileId) holds 2*lane; turn it into a float and halve it.
        sfpi::vFloat lane = sfpi::convert<sfpi::vFloat>(sfpi::as<sfpi::vSMag>(sfpi::vConstTileId), sfpi::RoundMode::Nearest);
        sfpi::dst_reg[i] = lane * 0.5f + float(32 * i);
    }
}

32 × vector + lane is at most 255, so it is exact in BF16. B08_FN=map prints face 0 of the output tile as vector.lane (first four rows shown):

4. Your own SFPI kernel: a four-way v_if

The starting point is custom_sfpi_smoothstep, the stock example whose face function loads, computes and stores eight vectors (tt_metal/hw/ckernels/wormhole_b0/metal/llk_api/experimental/llk_sfpu/ckernel_sfpu_smoothstep.h:13-22). Our kernel keeps its structure. Here is the piecewise face function:

sim-labs/overlays/b08/b08/sfpu_lab.cpp:30-46
inline void b08_piecewise_face() {
    for (int i = 0; i < 8; i++) {
        sfpi::vFloat x = sfpi::dst_reg[i];
        sfpi::vFloat y;
        v_if (x < -1.0f) {             // region A: flat at -1
            y = -1.0f;
        } v_elseif (x < 0.0f) {        // region B: x(x+2), from -1 up to 0
            y = x * (x + 2.0f);
        } v_elseif (x < 1.0f) {        // region C: x(2-x), from 0 up to 1
            y = x * (2.0f - x);
        } v_else {                     // region D: flat at +1
            y = 1.0f;
        }
        v_endif;
        sfpi::dst_reg[i] = y;
    }
}

And the call from the kernel body, between copy_tile and tile_regs_commit, exactly where my_smoothstep_tiles sits in the stock example:

Three things are worth seeing. Every comparison is against zero (sfpsetcc only tests the sign or zero-ness of an LReg, SFPSETCC.md functional model), so x < -1 becomes "is x + 1 negative". The v_elseif chain is sfpcompc then sfppushc: SFPCOMPC computes LaneFlags = Top.LaneFlags && !LaneFlags (SFPCOMPC.md:33), so "else" only ever re-enables lanes that were enabled one level up. And the compiler used SFPMOV mode 2, SFPMOV_MOD1_ALL_LANES_ENABLED (SFPMOV.md:64; ttsim tensix.cpp:4569-4570), to write region A's −1 and the merged result into every lane, ignoring the masks, then let the later regions overwrite their own lanes. Because the SFPLOAD/SFPSTORE address depends on i, the RISC-V core builds those two instruction words in a register and stores them into the instruction buffer (sw to 0xffe40000); the rest are fixed sfp* words.

Count them: 25 sfp* instructions plus the load and the store, 27 per vector, of which 3 are sfpnop. A lane does about 3 useful operations for its own region. Step through the figure to see what each lane does on each instruction. The 32 inputs are real samples from the run's input range, one per lane in a fixed shuffled order (on the device, neighbouring lanes hold neighbouring values, which would make the picture boringly tidy). The page replays the instruction sequence above in FP32 for these inputs and checks the stored results against the device's outputs for the same x values.

This is warp divergence with the decision made in advance. A GPU warp with four-way divergence also runs all four paths with lanes masked off. But a GPU skips a path that no thread takes. The SFPU's instruction stream was pushed by a RISC-V core that never sees the flags, so all 27 instructions are issued even if every lane lands in region A (A07 shows this with its "All x ≥ 0" button). Divergent SFPU code costs the sum of all its branches, always.

5. A polynomial sin, and where its error comes from

Wormhole's SFPU has no transcendental instructions (A07); everything is built from multiply-adds, exponent tricks and masks. The textbook first attempt at sin is its Taylor series, cut off after x7 and evaluated in Horner form so that it costs four FMAs. A second version first folds the input into [−π/2, π/2] with a v_if/v_elseif, using sin(x) = sin(π − x):

sim-labs/overlays/b08/b08/sfpu_lab.cpp:48-65
inline void b08_sin_face() {
    for (int i = 0; i < 8; i++) {
        sfpi::vFloat x = sfpi::dst_reg[i];
#if B08_FOLD
        v_if (x > 1.57079637f) {           // sin(x) = sin(pi - x)
            x = 3.14159274f - x;
        } v_elseif (x < -1.57079637f) {    // sin(x) = sin(-pi - x)
            x = -3.14159274f - x;
        }
        v_endif;
#endif
        sfpi::vFloat x2 = x * x;           // Horner: x(1 + x2(-1/6 + x2(1/120 + x2(-1/5040))))
        sfpi::vFloat p = x2 * -1.98412698e-4f + 8.33333377e-3f;
        p = p * x2 - 0.166666672f;
        p = p * x2 + 1.0f;
        sfpi::dst_reg[i] = x * p;
    }
}

Before running anything, predict. The first omitted Taylor term bounds the error: |x|9/9!. On [−π, π] that is π9/362880 ≈ 0.082. After folding, |x| ≤ π/2 and the bound becomes (π/2)9/9! ≈ 1.6×10−4. BF16 has an ulp of 2−8 ≈ 0.0039 just below 1, so the folded polynomial should be invisible in BF16 and visible in FP32. Four runs over [−π, π]:

$ B08_FN=sin B08_FOLD=1 $LAB_HOME/b08_sfpu                       # Wormhole, BF16
max_abs_err=0.00398 (at x=-1.69531) mean_abs_err=0.00164 max_rel_err=0.00759
ulp vs correctly rounded: exact=1642 1ulp=2454 >1ulp=0 max=1
$ B08_FN=sin B08_FOLD=1 B08_FMT=fp32 $LAB_HOME/b08_sfpu          # Wormhole, FP32 CBs + 32-bit Dst
max_abs_err=0.00195 (at x=-3.08789) mean_abs_err=0.000366 max_rel_err=0.904
$ B08_FN=sin B08_FOLD=1 B08_FMT=fp32 B08_U2D=1 $LAB_HOME/b08_sfpu   # Blackhole, FP32 unpacked to Dst
max_abs_err=0.000157 (at x=-1.57041) mean_abs_err=1.58e-05 max_rel_err=0.000157

The first, second and fourth lines match the predictions: 0.075, at most one BF16 ulp, and 1.57×10−4 exactly at ±π/2 where the remainder bound peaks. The third line is the surprise. FP32 should be better than BF16, yet its worst error, 0.00195, is twelve times the polynomial's. The value 0.00195 = 2−9 is one TF32 ulp for |x| in [2, 4): the input was truncated in SrcA (section 2), and near π the fold π − x passes that input error straight through to the output (the slope of sin is ±1 there). (The max_rel_err values near 1 or 77 come from outputs near zero, where a tiny absolute error is a large relative one. They are not a separate bug.)

The figure plots the signed error of every run, from the dumps. Each dot is the worst element in a bucket of 16 consecutive inputs, so peaks are kept.

An SFPU result's error has up to three separate sources: the algorithm (here the Taylor remainder), the input format (TF32 in SrcA, or BF16), and the output store (truncation to BF16). To measure the first, remove the other two: FP32 unpacked to Dst, a 32-bit Dst, and an FP32 output CB. In this simulator that is only possible on Blackhole.

Clamp the input from below (SFPSWAP against a constant), compute a·x + b with one SFPMAD, turn it into an integer, shift it left by 15 bits and store the integer bits as if they were a BF16 float. The integer lands in the exponent field (and the top of the mantissa), so it is 2a·x+b, with the fraction interpolated linearly between powers of two. That linear interpolation is the sawtooth in the figure's fifth view. This is Schraudolph's 1999 trick, done 32 lanes at a time: 8 instructions per vector (two of them SFPNOP), against 20 for the accurate path (A07). The LLK does not name Schraudolph; the identification is mine, from the code.

The precise path is correctly rounded on every element, as its comment promises ("correctly rounds BF16 inputs with normal BF16 reciprocals (≤0.5 ULP)", ckernel_sfpu_recip.h:20-21). It gets there by rounding in the lanes, with convert<vFloat16b>(y, RoundMode::Nearest), before SFPSTORE can truncate. That is the fix for this lab's opening question. Check every op's header before trusting APPROX. At this commit: exp_tile ignores it (template argument instead); recip_tile honours it; log_tile passes it to the LLK, but the Wormhole LLK's calculate_log documents both APPROXIMATION_MODE and FAST_APPROX as "Ignored" (ckernel_sfpu_log.h:377-378; the reason is at line 262). 8. Exercises, with answers

Each answer below was checked by running it in this orb.

1. Run the folded sin over [−6.3, 6.3] (B08_LO=-6.3 B08_HI=6.3). Predict the worst error before running.

The fold maps |x| in (π/2, 3π/2) into [−π/2, π/2], but beyond 3π/2 ≈ 4.71 the folded argument leaves that range again, reaching about 6.3 − π ≈ 3.16 in magnitude at the ends. The Taylor polynomial there is as bad as the unfolded one at π. The run gave max_abs_err=0.0815 (at x=-6.3125), with 632 outputs more than one ulp off. A real implementation reduces modulo 2π first, which needs an integer part of x/(2π), more exexp/setexp work, the kind of code in A07's exp.

2. B08_FN=map B08_FMT=fp32 makes Dst 32-bit. Does the lane-to-cell map change?

No. The run printed the same result_hash=e5c90bd9f3573383 as the BF16 run (the program hashes the FP32 value of each output, so the two formats are comparable). SFPLOAD addresses rows and columns of Dst, and with a 32-bit Dst the same row/column formula applies to 32-bit cells (SFPLOAD.md, the MOD0_FMT_FP32 case reads Dst32b[Row][Column]). What changes is how many tiles Dst holds, not the face layout.

3. Make the kernel's exp follow math_approx_mode by replacing B08_EXPT with APPROX in exp_tile_init<> and exp_tile<>. What happens?

The JIT build fails: error: 'APPROX' was not declared in this scope in the trisc0 compile. The generated chlkc_descriptors.h declares APPROX only under UCK_CHLKC_MATH and UCK_CHLKC_PACK, but the same kernel source is also compiled for the unpack TRISC, where exp_tile<APPROX> must still parse even though MATH(…) removes its body. Declaring constexpr bool APPROX = false; under #ifndef TRISC_MATH fails too (redefinition on the pack TRISC). This works: #ifdef TRISC_UNPACK constexpr bool APPROX = false; #endif. Then B08_APPROX=1 gives result_hash=c4cce016957fc383, the same bits as exp_tile<true>, and B08_APPROX=0 gives e81d3c04686cc383.

4. How many SFPU instructions does the piecewise kernel issue per tile, and how many of them does a typical lane need?

27 per vector (25 sfp* in the loop body plus SFPLOAD and SFPSTORE, 3 of them sfpnop), 8 vectors per face, 4 faces: 27 × 32 = 864 per tile. A lane in region B needs roughly load, add, multiply and store; the remaining 20-odd slots are flag management and other regions' work. This is an instruction count from the binary, not a timing measurement: ttsim is not a timing model.

5. In section 1, −1.75 became −2 in BFP4 on the host and −1.5 on the device. Reproduce both by hand.

The shared exponent is that of 3.0 (21), so BFP4's unit is 21−2 = 0.5 and BFP8's is 21−6 = 2−5. Host: 1.75 / 0.5 = 3.5, an exact tie; ties-to-even gives 4, so −2. Device: first BFP8, 1.75 / 2−5 = 56 exactly, then keep the top 3 of 7 magnitude bits, 56 >> 4 = 3, so −1.5. The same arithmetic gives −0.4 → host 0.8 → 1 (−0.5), device round(0.400391 × 32) = 13, 13 >> 4 = 0.

6. Make the piecewise kernel correctly rounded. What do you change, and what should the program print?

Round each lane to BF16 before the store, as the precise reciprocal does. Replace the store with sfpi::dst_reg[i] = sfpi::convert<sfpi::vFloat16b>(y, sfpi::RoundMode::Nearest);. That emits an SFPSTOCHRND in nearest mode, so the later truncation in SFPSTORE has nothing left to cut. The run printed ulp vs correctly rounded: exact=4096 1ulp=0 >1ulp=0 and max_abs_err=0.00195 (half an ulp at 0.5), on Wormhole and on Blackhole, with the same hash dde6989bc14dc383. One caveat: on Wormhole and Blackhole RoundMode::Nearest means NearestAway (sfpi_lib.h:839-842), ties away from zero rather than to even. None of these 4096 inputs produced a tie that would expose the difference.

Recap

  • BF16 loses precision relative to each value; BFP8/BFP4 lose it relative to the largest of 16 values sharing one exponent. A value 8 (BFP8) or 4 (BFP4) or more binades below its block's maximum is exactly 0; at 7 (or 3) only rounding up to one unit can save it. One outlier ruins exactly one 16-value block, and PCC hides it.
  • On this simulator the device BFP4 packer rounds to BFP8 and then truncates; the host rounds once. Host and device BFP4 tensors can differ by a full step.
  • Bits are cut, not rounded, at three places: unpacking to SrcA (TF32, 19 bits), unpacking FP32 to a 16-bit Dst, and SFPSTORE to a 16-bit Dst. That is why a quarter of the exact piecewise results came back 1 ulp low, all toward zero.
  • The SFPU is 32 lanes of 32 bits. dst_reg[i] is four Dst rows, every other column; eight vectors make a face, 32 a tile. The map kernel showed it with data written by the simulated device.
  • v_if/v_elseif/v_else compile to compare-against-zero, SFPCOMPC, SFPPUSHC/SFPPOPC, and all-lane SFPMOVs. Every region is issued to every lane: 27 instructions per vector for a four-region function.
  • To measure an algorithm's own error, remove format error first: FP32 unpacked to Dst (Blackhole only in ttsim), 32-bit Dst, FP32 output. The folded Taylor sin then matched its predicted remainder, 1.6×10−4 at ±π/2.
  • math_approx_mode changed nothing for exp_tile (identical hash) and changed the reciprocal from correctly rounded to 1-ulp-truncated on Wormhole, or to a 7-bit hardware estimate on Blackhole.
  • Wormhole ttsim cannot run the LLK's unpack-to-Dst FP32 path: the TEN-3868 dummy unpack is UndefinedBehavior to ttsim.

Check yourself

1. A BFP8_b block holds 8.0 and 0.05. What does 0.05 become, and why?

8.0 has exponent 23, so the BFP8 unit is 23−6 = 0.125. 0.05 / 0.125 = 0.4, which rounds to 0. The value is 7.3 binades below the block maximum, more than BFP8's 7 bits can reach. In BF16 it would have kept 8 significant bits.

2. You pass an FP32 CB into a compute kernel with fp32_dest_acc_en = true and see errors of about 10−3 relative even for copy_tile. What is happening, and what is the fix?

The unpacker writes into SrcA, which holds TF32 (10 mantissa bits), and drops the low 13 mantissa bits without rounding (ttsim tensix.cpp:3476). The datacopy then moves those truncated values into the 32-bit Dst. Set UnpackToDestMode::UnpackToDestFp32 for that CB so the unpacker writes Dst directly. In ttsim that works on Blackhole; on Wormhole the LLK's workaround instruction hits UndefinedBehavior.

3. A v_if has an expensive branch that only 1 of 32 lanes takes. How much does it cost compared with all 32 lanes taking it?

The same. The instruction stream is fixed at compile time and pushed by a RISC-V that never sees the flags, so the branch's instructions are issued in full; the 31 other lanes simply do not write. Even if no lane takes it, it is issued.

4. Why does the compiler implement x < -1.0f as sfpmad L1 = L11*L11 + L0 followed by sfpsetcc?

Wormhole's SFPSETCC only tests an LReg against zero (sign, zero or non-zero). So the comparison is rewritten as x + 1 < 0, and x + 1 is computed as (−1)·(−1) + x using the constant −1.0 that the SFPI compiler keeps in LReg 11, which costs no load. Blackhole adds comparison instructions (A07 shows sfpgt in the Blackhole build of a similar kernel).

5. A colleague sets math_approx_mode = true to speed up a softmax that uses exp_tile and recip_tile, and the results change slightly. Which op changed?

Only the reciprocal. exp_tile reads its own template argument, so its output is bit-identical with or without math_approx_mode (same hash in section 6). recip_tile's default follows APPROX: on Wormhole it switches from correctly rounded BF16 to a truncated one-step Newton result; on Blackhole to the 7-bit SFPARECIP estimate. To get the fast exp you must write exp_tile<true>.
