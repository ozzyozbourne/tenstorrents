B00. Setting up the workbench

Build the exact environment used in this series on a fresh Linux x86_64 machine: ttsim, tt-metal, three small scripts, and a smoke test that prints Success: Result is 21 with no Tenstorrent card in sight.

Honesty banner. ttsim is a functional, bit-exact simulator: it computes the same bits silicon would. It is not a timing model. The clock counts it prints, such as [4501], measure how far the host let the simulation run, not how fast a real chip would be. Every lab in this series uses them only as a determinism check, never as a performance number.

The question

Here is the program we want to run. It is the smallest example in tt-metal: copy two integers into a Tensix core's SRAM, add them on one of the core's little RISC-V processors, and copy the answer back.

$EX/metal_example_add_2_integers_in_riscv
...
Success: Result is 21

On a machine with a Wormhole card, that binary talks to a driver, the driver talks to PCIe, and PCIe reaches the chip. We have no card. So the real question of this lab is:

What exactly must be on your disk, and in your environment, for that same unmodified binary to print "Result is 21" when there is no chip at all?

The answer turns out to be short: one shared library that is the chip, one YAML file sitting next to it, a built tt-metal tree, and about a dozen environment variables. But each of those pieces has a trap, and every trap in this lab is one we actually fell into while building the environment for this series in an Amp orb (Debian 12, 8 vCPUs, 15 GiB RAM). Everything below was run there, and every output block is pasted from a real run.

What talks to what

Before typing commands, it helps to see where the simulator plugs in. Think of tt-metal as a tall building. The top floors (your program, the Metalium runtime, the user-mode driver) don't care what is in the basement. On silicon the basement is a kernel driver and a PCIe link. Under ttsim the basement is a single .so file loaded into the same process.

Two facts from ttsim's own API document make this possible. The library exports a flat C interface (config-space reads, BAR reads and writes, and libttsim_clock), and it is deliberately small: it "reads no environment variables", "never calls dlopen", and links only against the C library (refs/ttsim/docs/libttsim_api.md, "Hidden API" and "ABI" sections). You can check the last claim yourself:

$ ldd ~/sim/wh/libttsim_wh.so
	linux-vdso.so.1 (0x00007fff2fc2d000)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f599d61e000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f59a5749000)
The layering mirrors a GPU stack: libtt-umd plays the role of a user-mode driver library such as libcuda, and tt-kmd plays the role of the kernel module. What is unusual is the bottom: instead of an emulator that pretends to be a PCIe device, the "device" is a library the user-mode driver links in directly. That is why setup is so light: no kernel module, no VM, no root privileges at run time.
tt-metal does not know it is talking to a simulator above the UMD line. So the host program, the kernels and the firmware you run here are the same ones you would run on a card. What changes is where the clock comes from.

Step 1: Clone and pin

Both projects move fast; tt-metal merges dozens of commits a day. A setup guide that says "clone main" is out of date by the next afternoon. So we pin. The two hashes below are the ones every lab in this series ran against. ttsim's commit is exactly the v1.15.0 release tag (checked with git ls-remote), so its source matches the published binaries of that release.

cd ~
git clone https://github.com/tenstorrent/tt-metal.git
cd tt-metal
git checkout 7aad8aacd5bb557ee53ab7470b751cb2adadfecd
git submodule update --init --recursive

cd ~
git clone https://github.com/tenstorrent/ttsim.git
cd ttsim
git checkout v1.15.0          # = b3620244b3fedaa2e5abd645fa4f5f53c5d456b1

The submodule step pulls three repositories. Our log (refs/build-logs/submodules.log, 3.4 s) ended with:

Submodule path 'tt_metal/third_party/tracy': checked out 'a8a542194048195ca9c35725d7ebede33ccb028e'
Submodule path 'tt_metal/third_party/tt-cluster-descriptors': checked out '187a384df8e0090edc8e720b8fcb9692f75b433b'
Submodule path 'tt_metal/third_party/umd': checked out '1507ff75e000bcb923f28dbc60626be3f4283cd9'

The umd submodule matters most for us: it contains the user-mode driver's simulator support (TTSimTTDevice), so the tt-metal pin and the ttsim pin have to agree. Mixing a much older tt-metal with a new ttsim, or the reverse, is the most likely way for this recipe to break. The workbench scripts assume the default locations ~/tt-metal and ~/ttsim; you can override both (Step 6).

Step 3: Put each .so next to its soc_descriptor.yaml

Now give each simulator a home directory, and copy the matching SoC descriptor next to it under the fixed name soc_descriptor.yaml:

mkdir -p ~/sim/wh ~/sim/bh
cp ~/ttsim/src/_out/release_wh/libttsim.so ~/sim/wh/libttsim_wh.so
cp ~/ttsim/src/_out/release_bh/libttsim.so ~/sim/bh/libttsim_bh.so
cp ~/tt-metal/tt_metal/soc_descriptors/wormhole_b0_80_arch.yaml ~/sim/wh/soc_descriptor.yaml
cp ~/tt-metal/tt_metal/soc_descriptors/blackhole_140_arch.yaml  ~/sim/bh/soc_descriptor.yaml

The result is the layout used throughout the series (env.sh expects it):

~/sim/bh:  libttsim_bh.so  soc_descriptor.yaml
~/sim/wh:  libttsim_wh.so  soc_descriptor.yaml

Why one directory per chip? Because the YAML's name is fixed and its location is derived from the .so path. If you put both libraries in one directory, they would have to share one soc_descriptor.yaml, and one of them would get the wrong chip's descriptor.

Why is the file needed at all? A SoC descriptor is the map of the chip you met in A03: the grid size, and which (x, y) NoC coordinates are Tensix cores, DRAM, PCIe, ARC and Ethernet tiles. Silicon tells the driver which chip it is through the PCI device ID, and tt-metal then picks the map from its own tt_metal/soc_descriptors/. In simulator mode, tt-metal asks UMD where the simulator's descriptor lives and parses it to decide what architecture it is talking to:

tt-metal/tt_metal/llrt/tt_cluster.cpp:56-59 @7aad8aac
inline std::string get_soc_description_file(
    const tt::ARCH& arch, tt::TargetDevice target_device, const tt::llrt::RunTimeOptions& rtoptions) {
    if (target_device == tt::TargetDevice::Simulator) {
        return tt::umd::SimulationChip::get_soc_descriptor_path_from_simulator_path(rtoptions.get_simulator_path());

And UMD's answer is simply "the directory of the .so, plus a fixed file name":

tt-metal/tt_metal/third_party/umd/tt-umd/src/simulation/simulator_paths.hpp:16-22 @7aad8aac (umd 1507ff75)
inline std::filesystem::path get_simulator_artifacts_dir(const std::filesystem::path& simulator_path) {
    return (simulator_path.extension() == ".so") ? simulator_path.parent_path() : simulator_path;
}

inline std::string get_simulator_soc_descriptor_path(const std::filesystem::path& simulator_path) {
    return get_simulator_artifacts_dir(simulator_path) / "soc_descriptor.yaml";
}
A nuance in the sources. At this umd commit, UMD itself can live without the file: find_simulator_soc_descriptor_path returns empty when it is missing, and get_simulator_arch then asks the library for its PCI device ID and falls back to a built-in descriptor for Wormhole or Blackhole (simulator_paths.hpp:24-29, simulator_paths.cpp:19-44). But tt-metal builds the same path itself and parses it without checking that it exists: get_platform_architecture (llrt/get_platform_architecture.hpp:106-109, called from metal_env.cpp:168) reads the architecture from it before the Cluster is even constructed, and tt_cluster.cpp does the same again (lines 56-59 and 124-127). So in practice the run still dies. The ttsim README's rule ("must live in a directory also containing an SOC descriptor YAML file") is the one to follow. See Troubleshooting for what the failure looks like.

Step 4: Install dependencies and build tt-metal

We did not rebuild tt-metal for this lab (it takes about half an hour). The outputs in this section are excerpts of the logs saved when the series' environment was built, in refs/build-logs/. The logs record outputs, not the commands typed. The configure command line is printed verbatim by build_metal.sh; the ninja commands are reconstructed from each log's first and last lines.

tt-metal's INSTALLING.md lists Ubuntu 22.04 for its supported hardware configurations, and its "From source" path is: clone, ./build_metal.sh, ./create_venv.sh. Our orb runs Debian 12, which the dependency script recognises (Detected OS: debian 12 (apt)) but which needed three workarounds. On Ubuntu you may need none of them; we did not test Ubuntu or WSL2.

4a. System packages, and the SFPI .deb that fails

cd ~/tt-metal
sudo ./install_dependencies.sh

The script installs the build packages (git, build-essential, ninja, libhwloc, libnuma, libc++-20, ...) and CMake 4.0.2, then downloads the SFPI toolchain as a .deb. That is the compiler for the RISC-V cores inside each Tensix tile. On Debian 12 the install step fails:

...

The package was built against a newer libstdc++ than Debian 12 ships. Because the script runs with set -e (install_dependencies.sh:6), that one failure also skips everything after it in install():

tt-metal/install_dependencies.sh:560-564 @7aad8aac
    if [ "$docker" -ne 1 ]; then
        install_sfpi
        install_mpi_ulfm
    fi
    install_llvm

So two more things are now missing: clang 20 (from install_llvm) and OpenMPI/ULFM (from install_mpi_ulfm). The workarounds address each of the three:

  1. SFPI: do nothing. You don't need the system package. Unless you pass --use-system-sfpi, CMake downloads the SFPI tarball itself into runtime/sfpi, and that tarball works on Debian 12. After the build: runtime/sfpi/compiler/bin/riscv-tt-elf-g++ --version prints riscv-tt-elf-g++ (tenstorrent/sfpi:7.92.0[1080]) 15.1.0.
  2. clang 20: run the LLVM script by hand, exactly as install_llvm() would have (install_dependencies.sh:405-413): 
    wget https://apt.llvm.org/llvm.sh
chmod +x llvm.sh
sudo ./llvm.sh 20
    Our log (llvm20-install.log, 26 s) ends with Setting up clang-20 (1:20.1.8~++20250708063551+0c9f909b7976-1~exp1~20250708183702.136). The two W: Target Packages ... is configured multiple times warnings that follow are harmless: the dependency script had already added the same apt.llvm.org source.
  3. MPI: build without it. Pass --without-distributed to build_metal.sh ("Disable distributed compute support (OpenMPI dependency)", build_metal.sh:58). It sets -DENABLE_DISTRIBUTED=OFF. Nothing in the single-chip labs needs multi-host MPI.

Step 5 (optional): ttnn and python_env

The core labs only use C++ examples. A few later pages use the Python ttnn library, which needs two more steps:

cd ~/tt-metal
ninja -C build_Release install                # builds _ttnn.so and installs into build_Release (16 min here)
./create_venv.sh --python-version 3.11        # must match the python3 the build used

The version flag is the trap. create_venv.sh picks Python 3.12 on Ubuntu 24.04, 3.10 on Ubuntu 22.04, and 3.10 on everything else (create_venv.sh:231-239), which includes Debian 12. Where tt-metal looks for a kernel

Host code names a kernel by a relative path. The example does it like this (the prefix comes from a compile definition in programming_examples/CMakeLists.txt:8):

tt-metal/tt_metal/programming_examples/add_2_integers_in_riscv/add_2_integers_in_riscv.cpp:91-93 @7aad8aac
    KernelHandle kernel_id = CreateKernel(
        program,
        OVERRIDE_KERNEL_PREFIX "add_2_integers_in_riscv/kernels/reader_writer_add_in_riscv.cpp",

So the string tt-metal must resolve is tt_metal/programming_examples/add_2_integers_in_riscv/kernels/reader_writer_add_in_riscv.cpp. It tries locations in a fixed order and takes the first file that exists:

tt-metal/tt_metal/impl/kernels/kernel.cpp:48-95 @7aad8aac (trimmed)
// Kernel path resolve:
//
// If the path is not an absolute path, then it must be resolved relative to:
// 1. CWD
// 2. TT_METAL_KERNEL_PATH
// 3. System Kernel Directory
// 4. TT_METAL_HOME / SetRootDir (API)
fs::path resolve_path(const fs::path& given_file_name, ContextId context_id) {
    // Priority 0: Absolute path
    if (given_file_name.is_absolute()) { return given_file_name; }
    // Priority 1: Current working directory
    {   auto current_working_dir_search_path = fs::current_path() / given_file_name;
        if (fs::exists(current_working_dir_search_path)) { return current_working_dir_search_path; } }
    // Priority 2: Kernel directory
    if (rtoptions.is_kernel_dir_specified()) { ... rtoptions.get_kernel_dir() / given_file_name ... }
    // Priority 3: System kernel directory
    ... rtoptions.get_system_kernel_dir() / given_file_name ...
    // Priority 4: Root directory
    ... rtoptions.get_root_dir() / given_file_name ...
    // Not found
    TT_THROW("Kernel file {} doesn't exist in any of the searched paths!", given_file_name);

We checked the code against the comment and found one small mismatch. The comment says "TT_METAL_HOME", but the root directory actually comes from TT_METAL_RUNTIME_ROOT, the SetRootDir API, or a cwd that contains tt_metal/ (rtoptions.cpp:351-369). Troubleshooting

Each failure below was reproduced in this orb on purpose, and the output is real.

terminate called after throwing an instance of 'YAML::BadFile'

We copied libttsim_wh.so alone into an empty directory and pointed TT_METAL_SIMULATOR at it:

$ TT_METAL_SIMULATOR=$LAB_HOME/nosoc/libttsim_wh.so $EX/metal_example_add_2_integers_in_riscv
... | info     |           Metal | Disabling multi-erisc mode with simulator/emule target device (rtoptions.cpp:398)

  what():  bad file: /home/user/ttlab/b00/nosoc/soc_descriptor.yaml
exit=134

The message names the exact file it wanted. Copy the matching descriptor there (Step 3). The updated env.sh warns about this as soon as you source it. A wrong descriptor is worse than a missing one, because the error no longer points at the YAML. We tried a Blackhole descriptor next to the Wormhole library: UMD announced Creating TopologyDiscovery for architecture: blackhole, the library answered with Wormhole's device_id=0x401e, and the run died inside the simulator with [0] ERROR: UnimplementedFunctionality: pcie_bar0_rd: bar0: offset=0x1fd04100 size=4. Keep one chip per directory.

The stale-kernel trap: "my edit does nothing"

Symptom: you edited a kernel in $LAB_HOME/kernels/, reran, and got the old behaviour, with no error and no warning. Cause: your cwd contains a tt_metal/ tree (usually because you cd'd to $TT_METAL_HOME, as the ttsim README's example does), so priority 1 finds the stock kernel before priority 2 ever looks at your overlay. Use the third scenario of the search-order figure to see it happen. Fix: cd $LAB_HOME/run, or just re-source env.sh. To be sure which copy ran, put a deliberate change in your overlay (such as the + to * edit above) and check the result changes.

Where is the JIT cache, and should I clear it?

Compiled firmware and kernels go to $HOME/.cache/tt-metal-cache/, or /tmp/tt-metal-cache/ if $HOME doesn't exist (build.cpp:191-198). Inside it, each build configuration (architecture, debug features and so on) gets a numeric build key directory with firmware/ and kernels/<kernel name>/<hash>/ under it (build.cpp:557-558). In this orb it held four build-key directories and 430 MB. You normally never need to clear it: an edited kernel gets a new hash directory (our 8/9 hits above). Clear it (rm -rf ~/.cache/tt-metal-cache) only if you suspect corruption or need disk space; the next run just recompiles, as the 3.9 s cold run showed.

One quirk if you set TT_METAL_CACHE=/some/dir: tt-metal appends tt-metal-cache without a slash (rtoptions.cpp:505), and the build key is then pasted straight on (build.cpp:557-558). The kernels end up in sibling directories such as /some/dir/tt-metal-cache13101861097061555864/, while the precompiled headers go to /some/dir/tt-metal-cache/pch/. We saw exactly that layout in $LAB_HOME/cache. It works; it just looks odd when you go looking.

Smaller things

  • Failed to start Inspector RPC server ... Address already in use; toString() = 127.0.0.1:50051: a warning we saw while another tt-metal process was running in the same orb. Each process tries to bind the same port. It is harmless; TT_METAL_INSPECTOR_RPC=0 turns the server off (rtoptions.cpp:1663-1668).
  • clang++-20: command not found from build_host.sh, or a configure error about the toolchain file: llvm.sh 20 didn't run (Step 4a).
  • ImportError when importing ttnn: the venv's Python minor version differs from the one build_metal.sh saw (Step 5).
  • An UnsupportedFunctionality error mentioning SFPLOADMACRO: TT_METAL_DISABLE_SFPLOADMACRO is not set; source env.sh.
  • WSL2: the ttsim README lists Windows via WSL2 as a supported host. We did not test it. Keep the checkouts inside the Linux filesystem (~), not under /mnt/c, or the build will be very slow.

Recap

  • The simulator is one libttsim.so per chip that tt-metal's user-mode driver dlopens when TT_METAL_SIMULATOR is set. Everything above UMD is the same binary you would run on silicon.
  • Pin tt-metal 7aad8aac and ttsim v1.15.0 (b3620244). ttsim builds in about 10 s with ./make.py :build; the release binaries work too and give identical results.
  • Each .so lives in its own directory next to soc_descriptor.yaml, because tt-metal derives that path from the library path and parses it to learn the architecture.
  • On Debian 12: ignore the failed SFPI .deb (CMake fetches a working tarball), run llvm.sh 20 yourself, build with --without-distributed, and name the metal_example_* ninja targets explicitly.
  • For ttnn, match the venv's Python to the python3 used at configure time (--python-version 3.11 here).
  • env.sh sets the runtime root, the kernel overlay and the log paths, then cds to $LAB_HOME/run, because the cwd is searched first for kernels.
  • Smoke test: Success: Result is 21 at [4501] clocks on Wormhole, every time (with DPRINT off; DPRINT's polling thread makes the count vary). That number is a fingerprint, not a speed.

Check yourself

You set TT_METAL_SIMULATOR=~/sim/libttsim_wh.so and also put libttsim_bh.so in ~/sim. What goes wrong, and why?

Both libraries would have to share ~/sim/soc_descriptor.yaml, because the descriptor's location is "the directory of the .so" plus a fixed name (simulator_paths.hpp:16-22). Whichever chip's descriptor you copy there is wrong for the other library. tt-metal parses the file to decide the architecture and the core map, so it would mis-describe the simulated chip. Giving each chip its own directory avoids the clash.

You edit your overlay kernel, rerun, and still get "Success: Result is 21". Name two different possible causes and how to tell them apart.

(1) The cwd shadows the overlay: you're in a directory with a tt_metal/ tree, so priority 1 wins. Check with pwd, and fix it with cd $LAB_HOME/run. (2) The overlay path is wrong: it must mirror the full relative string the host passes, tt_metal/programming_examples/add_2_integers_in_riscv/kernels/.... If it doesn't, priority 2 misses and priority 4 finds the stock file. Check with ls $TT_METAL_KERNEL_PATH/<rel>. Not a cause: the JIT cache. The edit got its own hash directory, and the run reported a cache miss for it.

Why does the series set TT_METAL_RUNTIME_ROOT instead of relying on TT_METAL_HOME?

Because RunTimeOptions resolves its root from TT_METAL_RUNTIME_ROOT, the set_root_dir API, a package install, or a cwd that contains tt_metal/ (rtoptions.cpp:340-382). It does not consult TT_METAL_HOME, as our failing run with TT_METAL_HOME still exported showed. The only fallback that would work without it is "run from the repository root", and that is exactly the location that causes the stale-kernel trap.

The release libttsim_wh.so and your locally built one have different SHA-256 hashes. Should you worry that results will differ?

No. The README says local builds are functionally equivalent to the releases and byte-identical only on the release CI toolchain (Ubuntu 24.04's g++). Different compilers produce different machine code for the same C++. We checked: both gave Success: Result is 21 at exactly [4501] clocks. And a rebuild with the same toolchain reproduced the earlier binary bit for bit.

On Debian 12, install_dependencies.sh fails at the SFPI package. Why did that also leave you without clang 20, and why is SFPI itself not actually a problem?

The script runs under set -e, and install() calls install_sfpi, then install_mpi_ulfm, then install_llvm. The first failure aborts the rest, so neither MPI nor clang 20 gets installed. Hence llvm.sh 20 by hand and --without-distributed. SFPI is fine because, unless you pass --use-system-sfpi, the CMake build downloads its own SFPI tarball into runtime/sfpi, and that one runs on Debian 12 (it reports 7.92.0).

A cold run took 3.9 s and a warm run 0.35 s, but both reported [4501] clocks. What does that tell you about the clock count?

The extra time was JIT compilation on the host, which happens outside the simulation, so it doesn't add simulated clocks. The clock count only advances when UMD calls libttsim_clock, mostly one tick per device read. It measures how much the host drove the simulation, not wall time, and not how long silicon would take.
