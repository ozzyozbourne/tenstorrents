B09. Breaking things on purpose

Seven bugs a kernel author will meet, each provoked on purpose with a kernel overlay. For each one you get the exact message, how to read it, and the fix. Then you put a debugger inside the simulator, and finally drive libttsim.so by hand with no tt-metal at all.

Honesty banner. ttsim is a functional, bit-exact model of the chip. It is not a timing model. The bracketed clock numbers in every log below ([4362] and so on) count simulator steps that the host drove. They are not silicon cycles and say nothing about speed. Several bugs on this page behave differently on silicon. ttsim stops at the first rule broken, while the hardware might round, stall or carry on silently. Each section says which. Where the silicon behaviour comes from the ISA documentation and not from a run, the page says so.

The question

Here are four one-line changes to the 57-line kernel of add_2_integers_in_riscv, the example that adds 14 and 7 on one BRISC (A10):

  1. Read the first input through (uint32_t*)(src0_l1 + 2) instead of src0_l1.
  2. Store one byte to a NoC register: *(volatile uint8_t*)NOC_AT_LEN_BE = 4;
  3. Read the first input through the DRAM buffer address src0_dram, which is not an L1 address at all.
  4. Copy 32 bytes into the last 16 bytes of the core's own L1.

Run each one in ttsim. All four stop within a few clocks of each other, around clock 4362, and each prints one line. But the lines carry four different labels: NonContractualBehavior, UnsupportedFunctionality, UnimplementedFunctionality, UndefinedBehavior. Silicon would treat these four bugs in four different ways too. It would compute the right answer for the first and quietly do the wrong thing for the second. For the third it would probably hang, and for the fourth nobody can say.

So what do the labels mean, and who is at fault: you, the simulator, or the spec? And what about the bugs that print nothing at all, the hang where five CPUs sit still while the host waits forever? This lab breaks kernels on purpose, one bug at a time, until the messages feel familiar. Everything below was run in this orb on the Wormhole model, at tt-metal 7aad8aac and ttsim b3620244. Outputs are real and trimmed only where marked.

1. How ttsim says no: the error taxonomy

Before breaking anything, read how ttsim refuses. Every check in the simulator ends in a single function, and every message you will see has the shape [clock] ERROR: Category: function: detail. The category is one of nine:

ttsim/src/common.h:15-25 @b3620244
enum class TTSimErrorCategory {
    UndefinedBehavior, // as defined in tt-isa-documentation
    UnpredictableValue, // as defined in tt-isa-documentation
    NonContractualBehavior, // as defined in tt-isa-documentation
    AssertionFailure, // internal bug in simulator
    UntestedFunctionality, // implemented, but inadequate test coverage to enable yet
    UnimplementedFunctionality, // not implemented yet
    UnsupportedFunctionality, // planned to never be implemented
    SystemError, // OS errors and similar
    ConfigurationError, // bad command line options, env vars, configuration files, etc.
};

Read the comments as a question about blame. The first three are about your software, and the comments say they mean what the ISA documentation's glossary defines. The next four are about the simulator: one is a bug in it, and three mark parts of the chip it does not model. The last two are about the environment. The checks themselves are the macros TTSIM_VERIFY(cond, Category, fmt, ...) and TTSIM_ERROR(Category, fmt, ...) (common.h:27-38). Both call this:

ttsim/src/common.cpp:33-45 @b3620244
void ttsim_error(TTSimErrorCategory category, const char *func, const char *fmt, ...) {
    uint64_t clock = ttsim_get_clock();
    const char *category_str = ttsim_error_category_name(category);
    printf("[%" PRId64 "] ERROR: %s: %s%s", clock, category_str, func, fmt ? ": " : "\n");
    ...
    fflush(stdout);
    _Exit(1);
}

Three facts follow from these lines. The bracketed number is the simulator clock when the check fired. The second field is the C++ function holding the check, so you can grep for it. And the process ends with _Exit(1): no destructors, no atexit handlers, no exception for tt-metal to catch. The ttsim team explains the choice at length. After a failed check, "the simulator's internal state has been established as inconsistent with the architectural contract it is modeling", and running anyone's cleanup code over it causes secondary crashes that hide the first one (ttsim/docs/sim_error_handling.md:40-71). In practice this means you always get exit status 1 and exactly one error line, for the first violation only.

How often does each category appear? Counting the single-line TTSIM_ERROR/TTSIM_VERIFY/TTSIM_ERROR_NOFMT call sites in src/ with ripgrep gives the numbers below. They are lower bounds: calls split over several lines are missed, and so are the register-decoder checks that src/tile_gen_regs.py generates at build time.

CategoryCall sitesWhose problemWhat to do

You have already met one UnsupportedFunctionality without seeing it. env.sh exports TT_METAL_DISABLE_SFPLOADMACRO=1 because ttsim refuses the SFPU's SFPLOADMACRO instruction. The ttsim docs give the reasons for such carve-outs. About 30% of the Wormhole and Blackhole feature surface is left out on purpose: debug and test hardware, features with known silicon bugs, and anything whose cost in validation or speed is not worth paying (ttsim/docs/unsupported_functionality.md:9-12, 50-58).

Read the category before the message. UB and NCB mean the bug is yours. Unsupported means you used something ttsim refuses on purpose. Unimplemented means ttsim has no model for what you touched, which is often your bug too: a wild pointer lands somewhere nobody models. AssertionFailure means the bug is ttsim's.

3. Four kernel bugs, four categories

All four overlays change the same 57-line BRISC kernel. Each was run with Watcher off. (With TT_METAL_WATCHER=1, the first three print the same line at a later clock, 6916 or 6917, the same in every rerun, because Watcher's code adds instructions before the kernel gets there. The fourth is caught by Watcher first, as section 4.1 shows.) Here is the relevant part of the stock kernel. It reads one uint32_t from each input buffer in DRAM into L1, adds them on the RISC-V, and writes the sum back:

3.1 NonContractualBehavior: an unaligned load

The classic way to write this bug is to parse a packed byte buffer and cast a pointer into the middle of it. The overlay does it in the plainest way:

-    uint32_t* dat0 = (uint32_t*)src0_l1;
+    uint32_t* dat0 = (uint32_t*)(src0_l1 + 2);  // B09 bug: a 4-byte load from a 2-byte-aligned address
use ncb-unaligned && $EX/metal_example_add_2_integers_in_riscv; echo "exit=$?"
[0] 0.1 seconds (0.0 KHz)
[4362] ERROR: NonContractualBehavior: rv32_mem_rd: unaligned addr=0x16dfe2 size=4
exit=1

How to read it. The category says the spec does not promise what happens here. rv32_mem_rd is the RISC-V load path, and the detail gives the faulting address and the access size. The address 0x16dfe2 is src0_l1 (0x16dfe0, the last 32 bytes of allocatable L1, as B05 found) plus 2. The check is the first line of every 32-bit load:

ttsim/src/riscv_impl.h:637 @b3620244 (stores: line 689)
    TTSIM_VERIFY(!(addr & (size - 1)), NonContractualBehavior, "unaligned addr=0x%llx size=%d", uint64_t(addr), size);

What silicon does. The ISA documentation is explicit: "The baby RISCV cores cannot fault. … Unaligned memory accesses are silently rounded down to the nearest aligned address. This is a NonContractualBehavior" (tt-isa-documentation/WormholeB0/TensixTile/BabyRISCV/README.md:110-111). Rounded down, 0x16dfe2 becomes 0x16dfe0, which is exactly src0_l1. So on a Wormhole this broken kernel would most likely print Success: Result is 21. ttsim refuses because the rounding is not a promise: a later chip may handle the access differently. I did not run this on silicon; the prediction comes from the ISA text. Fix: load the bytes one at a time, or memcpy into an aligned local.

On a GPU, an unaligned global load either works more slowly or raises a misaligned-address error that kills the kernel. A baby RISC-V has no trap mechanism at all: no faults, no exceptions. That is why the simulator has to be the strict one.

3.2 UnsupportedFunctionality: a byte store to a register

     noc_async_read_barrier();
+    *(volatile uint8_t*)NOC_AT_LEN_BE = 4;  // B09 bug: a 1-byte store to a 32-bit NoC register
use unsup-byte-mmio && $EX/metal_example_add_2_integers_in_riscv
[4363] ERROR: UnsupportedFunctionality: rv32_mem_wr: 8-bit MMIO stores write the entire 32-bit register, not just the addressed byte
exit=1

How to read it. NOC_AT_LEN_BE is 0xFFB20020, a NoC command-buffer register (noc_parameters.h:29,50). It is not in L1 or in the core's local RAM, so the store takes the MMIO path. On Wormhole that path has no case for one-byte stores:

ttsim/src/riscv_impl.h:701-711 @b3620244
    if constexpr (size == 1) {
#if TT_ARCH_VERSION == 0
        TTSIM_ERROR(UnsupportedFunctionality, "8-bit MMIO stores write the entire 32-bit register, not just the addressed byte");
#else
        TTSIM_ERROR(UnsupportedFunctionality, "8-bit MMIO store");
#endif
    } else if constexpr (size == 2) {
        ...

The message tells you why the feature is refused: the Wormhole store would clobber the other three bytes. If that is right, this is a case of the "features with known hardware bugs" carve-out (unsupported_functionality.md:56-58). Modelling it would either copy the bug into the simulator or break bit-exactness. I could not find the clobbering described in tt-isa-documentation, so take ttsim's word for it. Fix: read the whole register, modify it, and write all 32 bits back. Other refusals of the same kind: fence.i ("does not flush the instruction cache on babyrisc", riscv_impl.h:1128) and ebreak, which you will meet in section 4.

3.3 UnimplementedFunctionality: dereferencing a DRAM address

-    uint32_t* dat0 = (uint32_t*)src0_l1;
+    uint32_t* dat0 = (uint32_t*)src0_dram;  // B09 bug: a DRAM buffer address used as an L1 pointer
use ub-dram-deref && $EX/metal_example_add_2_integers_in_riscv
[4362] ERROR: UnimplementedFunctionality: t_tile_mmio_rd32: addr=0x2d4c40
exit=1

I expected UndefinedBehavior here, and the overlay's name still says so. ttsim answered differently, and its answer teaches something. src0_dram is a bank-local address (0x2d4c40, the same one B05 saw in its NoC log). A RISC-V cannot reach DRAM with a load at all: DRAM is only reachable through the NoC (A09). To the core, 0x2d4c40 lies above L1 and below the MMIO region, so the load falls through every case of the register decoder to its default: TTSIM_ERROR(UnimplementedFunctionality, "addr=0x%llx", addr) (tile.cpp:2229). For silicon the ISA says "Loads from unmapped memory will usually stall forever" (BabyRISCV/README.md:112). So on hardware this bug is a hang with no message. In ttsim it is an error line naming the address. Fix: fetch DRAM data with noc_async_read into L1, as the stock kernel does.

Do not read UnimplementedFunctionality as "the simulator's fault, so it's not my problem". Often it means your pointer went somewhere nothing is modelled, because nothing should be there.

3.4 UndefinedBehavior: a NoC write off the top of L1

The fourth bug is the most realistic: a transfer whose start address is valid but whose length is wrong.

     noc_async_read_barrier();
+    // B09 bug: copy 32 bytes to this core's own L1, at a slot 16 bytes below the end of L1.
+    // The slot is real, the length is not: the last 16 bytes land past the top of L1.
+    uint64_t tail_noc_addr = get_noc_addr(my_x[noc_index], my_y[noc_index], src0_l1 + 16);
+    noc_async_write(src1_l1, tail_noc_addr, 32);
+    noc_async_write_barrier();
use noc-oob && $EX/metal_example_add_2_integers_in_riscv
[4382] ERROR: UndefinedBehavior: tile_wr_bytes: access past end of tensix_sram
exit=1

The destination is 0x16dff0 and the length is 32, so the write would end at 0x16e010. Wormhole L1 is 1464 KiB = 0x16e000 (ttsim/src/config.h:29; tt-metal's MEM_L1_SIZE agrees, dev_mem_map.h:33). The check lives where the NoC model writes bytes into a Tensix tile:

ttsim/src/tile.cpp:2868-2871 @b3620244
    } else if (tile_type == 'T') {
        if (addr < sizeof(g_t_tiles[tile_id].sram)) {
            TTSIM_VERIFY(addr + size <= sizeof(g_t_tiles[tile_id].sram), UndefinedBehavior, "access past end of tensix_sram");
            memcpy(&g_t_tiles[tile_id].sram[addr], p, size);

This message is less helpful than the others: it names neither the address nor the core. Section 6 recovers both with a debugger. Fix: make the length match the slot. Sanitize lengths, not just addresses.

Two more UB cases are covered in B05: a DRAM→L1 read whose two addresses are not congruent mod 32 (noc_cmd_ctrl: read: alignment of src_addr=… and dst_addr=… does not match), and a read that runs off the end of a 2 GiB DRAM controller (tile_rd_bytes: DRAM read overrun).

4. Watcher's nets: the sanitizer and ASSERT

ttsim checks the hardware contract when an instruction executes. tt-metal's Watcher checks it earlier, in code compiled into your kernel when TT_METAL_WATCHER is set. That code runs before the store that would start a NoC transfer. The two nets overlap without being nested, as B05 showed.

4.1 The sanitizer catches the same NoC write

      from local L1[0x16dfc0] to Tensix core w/ virtual coords 18-18 L1[addr=0x0016dff0] (NOC target address overflow).

The last waypoint is NAWW, "NoC async write wait", which is where noc_async_write sanitizes its arguments. ttsim printed nothing this time, because the bad command never reached the simulated NIU. The kernel stopped itself first. The test that fired:

The price of all this is about 12.7 s for a run that takes 0.36 s without Watcher.

4.2 ASSERT: three builds of the same line

Your own invariants can go into the kernel as asserts. The overlay states the kernel's contract, single-digit inputs, and the host then passes 14 and 7:

 #include "ckernel.h"
+#include "api/debug/assert.h"  // B09
 ...
     DPRINT("Adding integers: {} + {}\n", *dat0, *dat1);
+    ASSERT(*dat0 < 10 && *dat1 < 10);  // B09: this kernel's contract says single-digit inputs

What ASSERT turns into depends on how the kernel was built:

tt-metal/tt_metal/hw/inc/internal/debug/assert_common.h:14-41 @7aad8aac (trimmed)
#if defined(WATCHER_ENABLED) && !defined(WATCHER_DISABLE_ASSERT) && !defined(FORCE_WATCHER_OFF)
#define ASSERT(condition, ...) (void(not(condition) ? assert_and_hang(__LINE__, ##__VA_ARGS__), 0 : 0))
#elif defined(LIGHTWEIGHT_KERNEL_ASSERTS)
FORCE_INLINE void lightweight_assert_trap() { asm("ebreak"); }
#define ASSERT(condition, ...) (void(not(condition) ? lightweight_assert_trap(), 0 : 0))
#else
#define ASSERT(condition, ...) (void(sizeof(decltype(not(condition)))))
#endif

  1. Plain build: the assert compiles to nothing, and the run "succeeds" with a result the kernel's own contract forbids.
  2. Watcher: assert_and_hang writes the line number into a mailbox and spins. Watcher's host thread finds it and throws. Line 43 is the ASSERT line in the overlay. The last waypoint, NRBD ("NoC read barrier done"), shows the reads had finished. The warning in the message is real: an assert inside an included header reports that header's line number, not your file's.
  3. Lightweight: the assert is a single ebreak (0x00100073). ttsim handles ecall/ebreak on the 32-bit cores in rv32_ecall_ebreak, which has no case for ebreak and ends in TTSIM_ERROR(UnsupportedFunctionality, "inst=0x%x", inst) (riscv_impl.h:1180). On silicon, ebreak "will pause the core, as if a pause was requested via the GDB/Debug interface" (BabyRISCV/README.md:114). So the same build that hangs a real core quietly at the assert gives you an error line in ttsim. The two clocks measure different things: [4501] is the end of a complete run, and [4368] is where the ebreak fired.
The Watcher docs at this pin include the header as #include "debug/assert.h" (docs/source/tt-metalium/tools/watcher.rst:144; debug/waypoint.h the same way at lines 81 and 145). In this tree the file is tt_metal/hw/inc/api/debug/assert.h, and there is no hw/inc/debug/ directory. With the docs' spelling the kernel build fails with fatal error: debug/assert.h: No such file or directory. The overlay uses api/debug/assert.h, which compiled.

5. A hang across five RISC-Vs

Errors are the easy case: something tells you. A hang tells you nothing. Here is the bug, in the compute kernel of eltwise_binary (64 tiles of a + b, two-page CBs, reader on BRISC, writer on NCRISC, compute on the three TRISCs):

         cb_pop_front(cb_in0, 1);
         cb_pop_front(cb_in1, 1);
-        // Release the held register
-        tile_regs_release();
+        // B09 bug: tile_regs_release() forgotten, so the packer never hands the Dst half back
     }
use hang-dst && time timeout 60 $EX/metal_example_eltwise_binary
[0] 0.0 seconds (0.0 KHz)
real	1m0.007s          (exit status 124: killed by timeout; the stock kernel passes in 0.45 s)

No error, no output, no exit. Where do you start?

5.1 Waypoints: where each CPU last was

With TT_METAL_WATCHER=1, a host thread dumps the state of every core once a second into $TT_METAL_LOGS_PATH/generated/watcher/watcher.log. For each core it prints the last waypoint of each of the five RISC-Vs, a code of up to four characters that the kernel APIs write into an L1 mailbox at interesting points. By convention a final W means "waiting at the top of a loop" and a final D means "done waiting" (watcher.rst:90-99). The macro is a single store (api/debug/waypoint.h:41), and you can put your own anywhere. I ran the hang under timeout 150 and got 149 dumps for core (0,0). The figure replays one such run. Watcher samples on wall-clock time, so the writer's exact NAWW/NWBD pattern and the dumps around the packer's finish differ a little from run to run. The lanes of the other four cores and the frozen final state came out the same when I reran it.

Read the final, frozen state as Watcher prints it, BRISC first (watcher.rst:99):

grep "worker core(x= 0,y= 0)" $LAB_HOME/logs/generated/watcher/watcher.log | sed 's/.*18)://' | uniq -c | tail -3
      1  CRBW,NAWW,UABD,MWDD,   D  rmsg:H0G|BNT h_id:  0 smsg:GGGD
      5  CRBW,NKFD,UABD,MWDD,   W  rmsg:H0G|BNT h_id:  0 smsg:GGGD
     65  CRBW,   W,UABD,MWDD,   W  rmsg:H0G|BNT h_id:  0 smsg:DGGD

The tempting reading is wrong. CRBW on the reader does not mean the reader is broken. It means its output, the input CB, is full because nobody pops it. Follow the chain downstream. The unpacker pops the inputs, and its last waypoint is UABD, "unpack A/B done", so it is stuck somewhere with no waypoint of its own. The math thread shows MWDD, which claims it is done waiting for Dst. And the packer and writer, the last stage of the pipeline, are finished. In a pipeline hang, look for the stage that broke the protocol, not the one that is waiting. Here it is the stage that finished too early.

smsg:DGGD is the subordinate run message (NCRISC, TRISC0, TRISC1, TRISC2): D = done, G = go. It confirms that NCRISC and TRISC2 completed while TRISC0 and TRISC1 are still running.

5.3 Inside the coprocessor: why MWDD lies

Why does TRISC1 say MWDD (done waiting) when math is plainly stuck? Look at the wait it just "passed":

tt-metal/tt_metal/hw/ckernels/wormhole_b0/metal/llk_api/llk_math_common_api.h:54-58 and tt_metal/tt-llk/tt_llk_wormhole_b0/common/inc/cmath_common.h:307-310 @7aad8aac
inline void llk_math_wait_for_dest_available() {
    WAYPOINT("MWDW");
    _llk_math_wait_for_dest_available_<DST_SYNC_MODE>();
    WAYPOINT("MWDD");
}
inline void math_dest_wait()
{
    TTI_SEMWAIT(p_stall::STALL_MATH | p_stall::STALL_SFPU | p_stall::STALL_SYNC, semaphore::t6_sem(semaphore::MATH_PACK), p_stall::STALL_ON_MAX);
}

The "wait" is a Tensix instruction, SEMWAIT. The RISC-V pushes it into the math pipe's instruction FIFO and moves on, so it writes MWDD at once. The coprocessor is what stalls (A04: "the RISC-V runs ahead"). Waypoints follow the RISC-V's program counter, not the Tensix pipes. To see the pipes, attach lldb to the hung process running the debug ttsim, and print the simulator's own state for tile 0 (its noc_id_logical is 0x492, that is x = 18, y = 18: worker (0,0)):

lldb-20 -b -p $(pgrep -n metal_example_e) -o 'p g_chip->t_tiles[0].tensix[0].inst_rd_ptr' …
(condensed: values only, comments added)
(uint32_t[3])  ([0] = 66, [1] = 67, [2] = 236)          # inst_rd_ptr  per pipe: unpack, math, pack
(uint32_t[3])  ([0] = 96, [1] = 120, [2] = 236)         # inst_wr_ptr: unpack and math have work queued, pack is empty
(uint32_t) 0x00000003                                   # inst_pipes_active = pipes 0 and 1
(uint32_t) 0xa6a1000a                                   # inst[1][67], head of the math pipe
(uint32_t) 0x420080c1                                   # inst[0][66], head of the unpack pipe
(uint8_t) '\x02'                                        # sem[1]     (MATH_PACK)
(uint8_t) '\x02'                                        # sem_max[1]
(uint32_t) 0x00000003  (uint32_t) 0x00000003            # src_a_valid, src_b_valid

Decode the heads with ttsim's own opcode table (ttsim/data/wh/tensix_isa.json): 0xa6 is SEMWAIT, with wait_sem_cond = 2 (STALL_ON_MAX, ckernel_instr_params.h:254) and sem_sel = 2, which selects semaphore 1, MATH_PACK. That semaphore holds 2, which is its maximum. 0x42 is UNPACR, waiting because both SrcA and SrcB banks are still full (valid = 0b11), since math never consumed them. Now the whole chain fits:

  1. The packer's tile_regs_wait() is SEMWAIT … STALL_ON_ZERO on MATH_PACK (llk_pack_common.h:26-29). tile_regs_release() is the only thing that decrements it again (reg_api.h:106-108 → llk_pack_common.h:75-76, a SEMGET).
  2. With the release gone, math's two commits push MATH_PACK to 2, the SyncHalf maximum (TTI_SEMINIT(2, 0, …), llk_math_common.h:118-120). The third tile_regs_acquire() stalls the math pipe forever.
  3. MATH_PACK never returns to zero, so the packer's wait never blocks again. It packs 64 "tiles" from whatever Dst holds, and the writer ships them.
  4. Math no longer consumes SrcA/SrcB, so the unpacker stalls, the inputs are not popped after tile 2, and the reader blocks in CRBW with 4 pushed and 2 acked.

Fix: restore tile_regs_release(). The stock kernel prints Test Passed. The general lesson: acquire/commit/wait/release is two semaphore handshakes (A12). Forgetting either half does not crash anything. It shows up as a stall somewhere upstream.

On a GPU, a missing __syncthreads() is a data race: wrong answers, sometimes. Here a missing handshake is a deadlock and wrong answers, because the "threads" are separate CPUs and pipes linked only by counters. Each counter has exactly one writer, and a stage that skips its write starves the stage that waits on it.

8. Capstone: drive libttsim with no tt-metal

Everything above went through tt-metal and UMD. Underneath, the simulator is a library with ten exported functions (src/libttsim.map): config-space access, BAR reads and writes, a clock, and init/exit. B00's harness h.c called three of them and read the PCI ID. This lab's harness/b09_step.c goes all the way. It writes a RISC-V program into a core's L1, releases that core from reset, steps the clock one cycle at a time, and reads the answer back. That is what UMD and tt-metal do for every launch (A17), done here by hand.

One shortcut is closed. libttsim_tile_wr_bytes(x, y, addr, …) is still exported, but on Wormhole and Blackhole it is "illegal and calling them fails as UnsupportedFunctionality" (docs/libttsim_api.md:115-120; the body is just TTSIM_ERROR_NOFMT(UnsupportedFunctionality), libttsim.cpp:197-207). So the harness has to talk PCIe like a real host:

  1. Find BAR0 in config space (offsets 0x10 and 0x14). Memory decode is already on (pcie.cpp:172).
  2. Program two TLB windows (A17 has the layout). Window 0 maps 1 MiB of the core's L1 from address 0. Window 1 maps the core's register page at 0xFFB00000. A 1 MiB TLB's config is addr >> 20 in bits 15:0 and the coordinate x | y << 6 in the next 12 bits (pcie.cpp:234-266), written at BAR0 + 0x1FC00000 + 8 × index.
  3. Write the program at L1 address 0, because BRISC's reset PC is always 0 (tile.cpp:1108).
  4. Release BRISC by clearing bit 11 (0x800) of RISCV_DEBUG_REG_SOFT_RESET_0 = 0xFFB121B0 (hw/inc/internal/tt-1xx/wormhole/tensix.h:106,109). The reset value is 0x47800, all five cores held. In ttsim the bits are BRISC 0x800, TRISC0-2 0x1000/0x2000/0x4000, NCRISC 0x40000 (tile.cpp:1096-1126).
  5. Clock and read.
sim-labs/workbench/harness/b09_step.c (excerpt)
static uint64_t tlb_map(uint32_t index, uint32_t x, uint32_t y, uint64_t addr) {
    uint64_t cfg = (addr >> 20) | ((uint64_t)(x | (y << 6)) << 16);
    mem_wr(bar0 + TLB_CFG_BASE + 8 * index, &cfg, 8);
    return bar0 + (uint64_t)index * TLB_1M_SIZE;   // host address of the window
}

Each is a lesson in miniature. (0,0) is not a Tensix tile but DRAM tile D0 (the SoC descriptor's first DRAM entry is 0-0). Reading the soft-reset register there means reading DRAM at 0xFFB121B0, past the 2 GiB channel (tile.cpp:2785). (40,40) is outside the 32 × 32 coordinate space (tile.cpp:1152). And Blackhole's TLB configs are three 32-bit words, not one 64-bit word, so an 8-byte write is refused (pcie.cpp:637-641). This harness is Wormhole only. The clock is [0] in all three because the error fires during setup, before the first libttsim_clock.

A CUDA program never touches the GPU's BARs: the driver owns them. Here, with one dlopen, you are the driver. The ten-function surface is a stable ABI that ttsim promises to keep (libttsim.map:4-7), small enough to drive from C, Python or Rust.

9. Exercises, with answers

1. Without running it on hardware, predict what a Wormhole would print for ncb-unaligned. Then change the overlay so ttsim accepts it and the result is still 21.

The ISA says unaligned accesses are "silently rounded down" (BabyRISCV/README.md:111). 0x16dfe2 rounds down to 0x16dfe0 = src0_l1, so the load returns 14 and the kernel prints Success: Result is 21. For ttsim, read bytes and assemble them yourself, e.g. uint8_t* b = (uint8_t*)src0_l1; uint32_t v = b[0] | b[1] << 8 | b[2] << 16 | b[3] << 24;. Byte loads from L1 are fine. Only MMIO refuses narrow accesses. Or simply drop the + 2.

2. Change b09_step.c so the same program runs on TRISC0 instead of BRISC. What two lines change?

TRISC0's reset PC is 0x6000 unless overridden (tile.cpp:1109-1111), and its reset bit is 0x1000. So write the program with mem_wr(l1 + 0x6000, prog, sizeof prog) and clear 0x1000 instead of 0x800. I ran it: SOFT_RESET_0 = 0x46800, then the same 5, 9, 12, 14, 15 after clocks 5-21. The result address 0x100 is absolute (li t0, 0x100), so it does not move.

3. In hang-dst, suppose the reader's input CBs were 64 pages instead of 2. Would the program still hang? Would the output be right?

The reader could then push all 64 tiles and finish. The writer and packer finish anyway (they did in the real run). But math still stalls on its third tile_regs_acquire (MATH_PACK = 2 = max), and the unpacker behind it, so TRISC0 and TRISC1 never finish and the host still waits forever. The output would be wrong too: 64 packed tiles from 2 computed ones. Bigger buffers move a hang. They do not fix a protocol bug.

4. For noc-oob, ttsim says UndefinedBehavior while Watcher says "NOC target address overflow". Which fires first when both are on, and why does ttsim then print nothing?

Watcher's check is compiled into noc_async_write and runs on the RISC-V before the store to NOC_CMD_CTRL. When it fails, the kernel records the error in a mailbox and spins, so the command never reaches ttsim's NIU model, and the check in tile_wr_bytes (frame #1 in section 6) is never reached. The host's Watcher thread then reads the mailbox and throws.

5. In hang-sem, add one waypoint that would have told you which semaphore core (0,1) is stuck on, without reading the source.

Put WAYPOINT("RDY1") just before noc_semaphore_wait(sem_ptr, 1) in reader1.cpp, after including api/debug/waypoint.h. But noc_semaphore_wait writes NSW itself and would overwrite yours. A waypoint shows only the last one written. So put yours after the wait (RDYD) and read its absence. Or wrap the wait yourself: WAYPOINT("S1W"); while (*sem_ptr != 1) { invalidate_l1_cache(); } WAYPOINT("S1D");. The convention of ending in W/D comes from watcher.rst:94-99.

Recap

  • ttsim reports exactly one error, the first, as [clock] ERROR: Category: function: detail, then calls _Exit(1). UB and NCB are your bugs. Unsupported and Unimplemented mean you touched something ttsim does not model. AssertionFailure is ttsim's own bug.
  • The same bug can behave differently on silicon. An unaligned load rounds down and works, an unmapped load hangs, an ebreak pauses the core. ttsim turns all of them into messages.
  • Watcher checks run inside your kernel, before the hardware sees anything. The sanitizer names the core, NoC, addresses and length, and ASSERT reports a line number. Without Watcher, asserts compile to nothing.
  • A hang is diagnosed from waypoints that stop changing, plus counters. In a pipeline, the CPU that is waiting is rarely the one with the bug. Here the packer finished early because it never released Dst. TRISC waypoints follow the RISC-V, not the Tensix pipes, which can stall later.
  • Two practical tools for a live hang under ttsim: TT_METAL_SIMULATOR_SERVE_OVER_SOCKETS=1 plus tt-exalens to read L1 and registers, and lldb attached to a debug ttsim to read the coprocessor itself. tt-triage did not work over the socket at these pins.
  • For errors, breakpoint set -n ttsim_error in a debug build gives a backtrace from the failing check down to the RISC-V store that caused it.
  • libttsim.so is a 10-function PCIe device. Find BAR0, program a TLB, write L1, clear a soft-reset bit, call libttsim_clock, and a core you loaded by hand runs one instruction per clock.

Check yourself

Your own kernel dies with [4362] ERROR: UnimplementedFunctionality: t_tile_mmio_rd32: addr=0x2d4c40. Is this a simulator bug you should report?

Probably not, at least not first. The function is the Tensix register decoder, and the address is neither L1 (below 0x16e000) nor a register page (0xFFB…). A RISC-V load went somewhere nothing is mapped, most likely a pointer bug such as a DRAM bank address or a stale argument. On silicon, such a load "will usually stall forever". Check the pointer before you file anything.

Why can't tt-metal catch a ttsim error and continue with the next test?

ttsim ends the process with _Exit(1) inside the call that hit the check. No exception propagates, and no destructors or atexit handlers run. The ttsim docs argue this is deliberate: the simulator's state is known to be inconsistent at that point. Test runners are expected to isolate each test in its own process.

Watcher shows CRBW, W, UABD, MWDD, W for 60 dumps. Which CPU should you suspect first: the BRISC in CRBW?

No. CRBW means the reader cannot reserve space because its consumer stopped popping. Follow the data flow: the unpacker (TRISC0) and math (TRISC1) are stuck but still running, while the packer (TRISC2) and writer (NCRISC) finished. A stage that finishes early while its upstream is stuck is the one that broke the handshake. In this lab it was a missing tile_regs_release().

The TRISC1 waypoint is MWDD, "math wait for dest: done", yet the math pipe is stalled on that very wait. How?

The wait is the Tensix instruction SEMWAIT … STALL_ON_MAX. The RISC-V only pushes it into the math pipe's FIFO and then writes the next waypoint. The pipe stalls later, when it reaches the instruction. Waypoints track the RISC-V's progress, not the coprocessor's. lldb on the debug ttsim showed 0xa6a1000a (SEMWAIT) at the head of the math pipe and MATH_PACK at its maximum, 2.

The harness prints the first sum "after clock 5", but lldb shows the sw at g_clock = 4. Which is right?

Both. g_clock starts at 0 and is incremented after each clock (libttsim.cpp:301-313). The harness counts its libttsim_clock(1) calls from 1. The fifth call runs clock index 4, which executes the store, and the harness reads L1 after that call returns.
