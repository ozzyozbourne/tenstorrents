B03. The RISC-V interpreter

Open up the loop that runs every baby RISC-V in ttsim: read its 256-entry decode table, watch two bits turn a RISC-V word into a Tensix instruction, and count exactly how many instructions each of the five cores runs inside your kernel.

Honesty banner. ttsim is a functional, bit-exact model of the chip. It is not a timing model. Its clock counts are not silicon cycles, and the instruction counts in this lab are counts of simulator steps, not cycles on a real Wormhole. On silicon, stalls, caches and NoC latency change how long each instruction takes; ttsim models none of that.

The question

Run add_2_integers_in_compute on a simulated Wormhole. It adds two 32×32 bfloat16 tiles on one Tensix core. Five baby RISC-V cores take part: a reader on NCRISC, a writer on BRISC, and the three compute threads on TRISC0, TRISC1 and TRISC2. While it runs, ttsim's RISC-V interpreter executes 1,029,531 instruction steps across the chip. We measured that number in this orb with the instrumented simulator you will build below.

How many of those million steps belong to the five kernels you actually wrote?

Make a guess before reading on. Half? A tenth? The answer is 1,103, about one step in a thousand. The rest is firmware: 72 Tensix tiles, each with five cores, spinning in loops that wait for a "go" message that, for 71 of them, never comes. By the end of this lab you will have counted those 1,103 steps yourself, split them by core, seen which ones pushed Tensix instructions, and traced the hottest loop back to a line of C++ in the kernel source.

On the way you will read the heart of ttsim's CPU model, a function of about forty lines in src/riscv_impl.h. It does three things: fetch a 32-bit word, look at its low two bits, then either decode it as RISC-V through a 256-entry table or rotate it by two bits and push it into the Tensix coprocessor. A04 explained why that two-bit escape exists. Here you will instrument it.

Every command below was run in this orb against ttsim b3620244 and tt-metal 7aad8aac, and every output block is pasted from those runs, trimmed with ….

1. One step of a baby core

Picture the simplest CPU emulator you could write. It has a program counter, 32 registers and a pointer to memory. In a loop, it reads the word at the program counter, works out which instruction it is, and does what that instruction says. ttsim's model of a baby RISC-V is exactly that, and its whole state fits in one small struct:

ttsim/src/sim.h:11-27 @b3620244
struct Rv32HartState {
    char tile_type;
    uint32_t tile_id;
    uint32_t riscv_id;
    uint32_t pc;
    uint32_t x_regs[32];
#if TT_ARCH_VERSION >= 1
    uint32_t f_regs[32];
    uint32_t chicken_bits;
#endif

    uint8_t *p_sram;
    uint8_t *p_local_mem;
    uint32_t sram_size;
    uint32_t local_mem_base;
    uint32_t local_mem_size;
};

A hart is RISC-V's word for a hardware thread, which here means one baby core. tile_type is 'T' for a Tensix tile or 'E' for an Ethernet tile, and riscv_id says which of the five cores this is: BRISC is 0, TRISC0–2 are 1–3 and NCRISC is 4 (config.h:18-22). p_sram points at the tile's L1, and p_local_mem at the core's private data RAM, which is mapped at 0xFFB00000. Floating-point registers exist only for Blackhole (TT_ARCH_VERSION >= 1), because Wormhole's baby cores have no FPU. There is no instruction cache, no pipeline and no cycle counter in this struct. That tells you what kind of model this is before you read a single line of logic.

Each clock, ttsim's clock loop makes a pass over every busy tile and calls rv32_step once for every active hart. If the tile's coprocessor executed an instruction in that pass, it repeats the pass within the same clock (libttsim.cpp:253-284; B01 takes that loop apart). So a step is one pass, and a clock can contain several. Here is the function it calls, with the 64-bit branches trimmed:

Read it in four beats.

  • Fetch. A program counter below the L1 size is an index into L1, so fetching is a plain 4-byte read from the tile's L1 array. There is no instruction cache in the model, even though the hardware has one per core (BabyRISCV/InstructionCache.md). The only exception is NCRISC on Wormhole, which also has a private 16 KiB instruction RAM at 0xFFC00000. Anything else outside L1 is UndefinedBehavior, and ttsim stops.
  • Advance the PC early. pc + 4 is written before the instruction runs. The comment admits the cost: instructions that use the PC must correct for it. For example, jalr notes "pc is really pc_plus_4 here" (riscv_impl.h:988). It also creates the trick this whole lab relies on: an instruction that cannot finish in this step sets pc -= 4, and the same instruction runs again on the next pass. That is a replay.
  • The two-bit check. Every standard 32-bit RISC-V instruction ends in binary 11. If the word does, it is RISC-V.
  • Dispatch. RISC-V words are decoded by indexing a 256-entry table of function pointers and calling the handler. Every other word goes to tti(), which rotates it right by two bits and pushes it into the coprocessor's instruction FIFO. A04 showed that function line by line.

Step through it with real words. Each one below was fetched by a real core during add_2_integers_in_compute, at the PC shown: three from BRISC's writer kernel and three from TRISC1's math kernel. You will dig these exact words out of the ELF files in lab step 4.

Grid colours: green = integer RV32IM handler, orange = fence / ecall, red = stops on Wormhole (F, V, CSR, atomics), dark = unimplemented.
ttsim's baby core is a dispatch loop, not a pipeline: fetch from L1, set pc += 4, look at two bits, then call one of 256 handlers or push to the coprocessor. "Stall" means "rewind the PC and try again on the next pass".

Memory: where the stalls come from

Loads and stores go through mem_rd and mem_wr. The order of the checks tells you what is fast in the simulator:

  • Misalignment is caught. The ISA docs say an unaligned access is "silently rounded down to the nearest aligned address", and they classify relying on that as NonContractualBehavior (BabyRISCV/README.md:111). ttsim doesn't round: it stops with that category.
  • L1, then local RAM, then MMIO. L1 and the private RAM are plain array accesses that always succeed. dcache_access is an empty function (riscv_impl.h:613-615), so caches cost nothing. Every other address is a device register, handled in tile.cpp, and that is the only place a load can stall. For example, reading the TENSIX_SYNC register returns "not done" until the hart's coprocessor thread is idle (tile.cpp:1900-1903). You will see that stall at work in step 2.
  • Narrow MMIO is refused on Wormhole. 8- and 16-bit loads and stores to device registers stop with UnsupportedFunctionality (riscv_impl.h:651, 660, 703, 709). The messages explain why: on real hardware an 8-bit MMIO store writes the whole 32-bit register.

The Wormhole restrictions

The baby cores implement RV32IM and nothing else (BabyRISCV/README.md:17). ttsim enforces that boundary by stopping at the first instruction outside it, using the error categories from A04:

The ISA docs and ttsim describe fence differently. The docs say fence "is executed as if it were nop, and hence cannot be used to enforce memory ordering" (BabyRISCV/README.md:18). ttsim refuses to run it at all. These two descriptions don't contradict each other: a fence in Wormhole code is almost certainly a bug, because whoever wrote it expected ordering they won't get, so the simulator turns a silent no-op into a loud error. Wormhole code orders memory by other means. The kernel you'll run in step 2 uses load_blocking for that (reader_writer_add_in_riscv.cpp:45-49).

Why 256, and why this index

Every 32-bit RISC-V instruction keeps its major opcode in bits 6:0. Bits 1:0 are always 11, so only bits 6:2 carry information: 5 bits, 32 major opcodes. Many instruction formats keep a 3-bit funct3 field in bits 14:12, which picks the variant: lb, lh, lw and so on all share the LOAD opcode. Glue the two together and you get 5 + 3 = 8 bits, or 256 possibilities. That's the line in step():

uint32_t opcode = ((inst >> 2) & 31) | ((inst & 0x7000) >> 7);   // inst[6:2] | inst[14:12] << 5

((inst & 0x7000) >> 7 moves bits 14:12 down to bits 7:5.) The generator builds the same index from a table of (isa, match, mask, handler) rows:

ttsim/src/riscv_gen_decode.py:113-128 @b3620244
table: list = [None] * 256
for (isa, inst, mask, name) in riscv_decode_table:
    assert isa in {32, 64}, isa
    assert inst & ~mask == 0, (inst, mask)
    assert (inst & 3) == 3, inst
    if mask == 0x007F:
        for funct3 in range(8):
            opcode = (inst >> 2) | (funct3 << 5)
            assert table[opcode] is None
            table[opcode] = (isa, name)
    elif mask == 0x707F:
        opcode = ((inst >> 2) & 31) | ((inst & 0x7000) >> 7)
        assert table[opcode] is None
        table[opcode] = (isa, name)
    else:
        assert False, mask

Two kinds of rows go in:

  • Mask 0x707F: the instruction is identified by opcode and funct3, so it fills exactly one slot. lw is 0x2003: opcode bits 6:2 = 0 and funct3 = 2, so it goes to index 0 + 2×32 = 64, the load<int32_t, int_xlen_t> you saw above. The template arguments say "read 32 bits, sign-extend to XLEN", so lb, lh, lbu and lhu all share one function body, specialised by the compiler.
  • Mask 0x007F: formats with no funct3 field, such as lui, auipc and jal, where bits 14:12 belong to an immediate. The instruction must work whatever those bits are, so the generator copies it into all 8 slots. That's why lui, jal and auipc each appear 8 times.

What doesn't fit in 8 bits is decided inside the handler. alu<0> (index 12) handles add, sub and also mul: it switches on funct7, the top 7 bits (riscv_impl.h:182-212). That's how the M extension gets in without its own table slots. The funct3 value is a template parameter, so each of the eight alu<N> copies only switches over the cases for its own funct3.

Of the 256 slots, 127 are unimplemented in a 32-bit build. The other 129 split into three colours in the figure above:

  • 71 red. 48 floating point (32 of them are the four fused multiply-adds, which have no funct3 and so fill 8 slots each), 16 vector, 6 CSR and 1 atomic. They exist so that Blackhole's baby cores, or the 64-bit build, can use them. On Wormhole every one stops the simulation, as the table in section 1 shows.
  • 55 green. The integer RV32IM handlers: loads, stores, ALU, lui, auipc, branches and jumps.
  • 3 orange. fence (only its PAUSE form works on Wormhole), fence.i and ecall/ebreak.

So a Wormhole program lives in 55 slots, plus PAUSE.

A GPU's SASS decoder is hardware, and you never see it. The nearest software analogue is a functional simulator such as the one inside GPGPU-Sim, which also decodes each warp instruction once and dispatches on opcode. ttsim's table is the textbook "computed goto" interpreter: indexing an array of function pointers turns decoding into one load and one indirect branch. It's cheap enough that the simulator spends its time in memory accesses and in the Tensix model, not in decode.

3. Lab step 2: count instructions per core, inside the kernel

Now instrument step(). Counting every step is easy, but B01 already did it chip-wide (963,752 hart-steps for add_2_integers_in_riscv), and it doesn't answer our question. We want the steps that belong to the kernel. So we need to know, for each hart, when the kernel starts and when it ends.

Finding the kernel window

Every core runs firmware that tt-metal loads at boot. When a program arrives, the firmware computes the kernel's address in the kernel config area of L1 and calls it like a C function pointer. Here is BRISC's version; TRISC (trisc.cc:215-216) and NCRISC do the same:

tt-metal/tt_metal/hw/firmware/src/tt-1xx/brisc.cc:526-528 @7aad8aac
uint32_t kernel_lma =
    (kernel_config_base + launch_msg_address->kernel_config.kernel_text_offset[index]);
auto stack_free = reinterpret_cast<uint32_t (*)()>(kernel_lma)();

In machine code, a call through a function pointer is jalr, which puts the return address in ra (register x1). Disassemble the firmware ELF, which tt-metal built into our private cache, and the call site is easy to find:

tt-metal appends the build hash to TT_METAL_CACHE without a slash (rtoptions.cpp:503-505 normalises the path to end in tt-metal-cache), so your firmware lands in $LAB_HOME/cache/tt-metal-cache13101861097061555864/, next to an unrelated tt-metal-cache/ directory that holds only precompiled headers. Hence the tt-metal-cache1* glob. A DPRINT build (exercise E2) gets a second hash directory, and so does a Blackhole build. After that, set C to the right directory by hand.

That gives a clean rule for the kernel window:

  1. Firmware text sits low in L1 (BRISC's runs from 0x3b20 to 0x4b30, TRISC2's ends at 0x711c). Kernels are loaded above MEM_MAP_END, which is 0x8a60 on Wormhole (computed from wormhole/dev_mem_map.h:58-163). NCRISC kernels run from IRAM at 0xFFC00000, which is higher still.
  2. The window opens at the first step whose PC is ≥ 0x8a60. At that moment ra holds the firmware return address, so save it.
  3. The window closes when the PC equals that saved address, which is the first firmware instruction after the kernel returns.

As a safety check we also count kernel-window steps whose PC is below 0x8a60. If a kernel called back into firmware code, this number would show it. It came out as zero for every core.

Some notes on the design:

  • Counters, not prints. One million steps with a printf each would swamp the run. The counters cost a few additions per step, and the run time didn't change measurably (0.2 s of CPU either way). b03_report() prints them once, called from ttsim_exit() in sim.cpp, which runs when tt-metal closes the device.
  • Replays are detected from outside. Rather than patching every pc -= 4, the hook compares the PC before and after the step. If it hasn't moved, the step did no forward work. That catches stalled loads and stores, stalled .ttinsns, and also a jump to itself, which you'll meet below.
  • Wormhole only. 0x8a60 is Wormhole's MEM_MAP_END. Blackhole has a different memory map and no NCRISC IRAM, so a static_assert stops a Blackhole build of the patched copy instead of letting it print wrong numbers.

Reading the numbers

Here are the counts as bars. Step through the four views. The bars are real counts from the two runs above.

Four things to notice.

  • The kernel is a rounding error. On the whole chip, kernel steps are 0.107% of the total for the compute example and 0.012% (116 of 963,752) for the RISC-V one. In ttsim, an idle firmware loop costs exactly what a kernel instruction costs: one step. Every one of the 72 tiles that ran (ttsim models 80 Tensix tiles on Wormhole; the other 8 were never stepped in these runs) polls its mailbox every clock, and the host decides how many clocks there are (B01). If you want to know what your code did, you have to filter by window, as we did. Counting everything gives you the firmware's profile.
  • The kernels are straight-line. No core had a single replay inside its kernel window. The compute kernel's waits between cores show up as loop iterations (a polling loop is ordinary instructions), not as replays. Step 4 finds them.
  • The replays are all in firmware, and each has a story. We added a temporary print of the PC of each replay on tile 0 (not part of the published patches) and disassembled the firmware at those addresses:
    • TRISC1, 266 replays at 0x6960: lw a5,0(s0) right after the kernel returns. This is tensix_sync() (trisc.cc:222), a read of the TENSIX_SYNC register that stalls until the thread's Tensix instructions have all finished (tile.cpp:1900-1903). The math core returned from its kernel after 155 steps and then spent 266 steps waiting for the coprocessor to catch up, which in turn was waiting on data from the other cores. This is A04's "the RISC-V runs ahead", measured. TRISC2's 23 replays are the same lw at 0x7100.
    • NCRISC, 77 replays at 0x5ecc: the word there is 0x0000006f, j ., a jump to itself. It's the end of wh_iram_trampoline. On Wormhole, the NCRISC can't safely jump from L1 into its IRAM, so it saves its registers, tells BRISC it's ready, and spins on itself until BRISC resets it with its reset PC pointed at the IRAM kernel:
tt-metal/tt_metal/hw/toolchain/wh-iram-trampoline.S:39-43 @7aad8aac
	sw sp, MEM_NCRISC_HALT_STACK_MAILBOX_ADDRESS( zero )
	sb a0, MEM_SUBORDINATE_RUN_MAILBOX_ADDRESS( zero )   /* Tell brisc we're done */

	/*Program flow will end here as ncrisc will go into reset*/
0:	j 0b

BRISC's side is start_ncrisc_kernel_run (brisc.cc:306-322): it writes the resume address into NCRISC_RESET_PC, asserts NCRISC's reset, waits 5 cycles, and deasserts. In ttsim, leaving reset sets only the PC (tile.cpp:1096-1124). The registers keep their values, so ra still held 0x5cd0 when the NCRISC reached 0xFFC00000, and our window logic worked by luck of that detail. The kernel's start-up code restores the saved registers and returns to the same address, so the result is right, but the method depends on registers surviving reset. The NCRISC's total of 2,580 steps, 21 fewer than the TRISCs' 2,601, is presumably the time it spent held in reset.

  • Why does the math core run the fewest instructions? TRISC1 has the smallest instruction cache of the five, ½ KiB (BabyRISCV/README.md:10), and it runs the fewest kernel steps here. The math work isn't in RISC-V code. It's in one MOP that the coprocessor expands into 8 ELWADDs (A04). The next step shows that MOP leaving the core.

Here is the kernel window for TRISC1 as a timeline. The addresses are real; the horizontal axis is not to scale.

A step is not a cycle. A real baby core needs at least 8 cycles for an L1 load, has instruction caches that miss, and stalls on NoC traffic, and ttsim models none of this. The NoC reads in add_2_integers_in_riscv complete instantly, so noc_async_read_barrier() never loops: lab step 4 shows that no instruction in that kernel ran twice. On silicon, that barrier spins until the DRAM data arrives. Use these counts to understand what code runs, never how long it takes.

What this tells you:

  • Every .ttinsn came from inside a kernel. Pushed equals "in kernel" for all three TRISCs, so the firmware itself never uses the escape. BRISC and NCRISC pushed nothing this way: BRISC's 9 boot-time pushes per tile, which A04 found, all use plain sw.
  • The totals match A04 exactly (23, 34, 57), measured through a different hook. That's a good sign that both instruments are right.
  • Zero FIFO-full retries. ttsim refuses a push only when more than 52 instructions are queued or the expanders are busy (tensix.cpp:284-293), and its clock loop drains the FIFOs in the same clock whenever it can (libttsim.cpp:253-282). On silicon, back-pressure is real, so don't conclude from this that the FIFO never fills on hardware.
  • Read TRISC1's list as a story. It's almost all configuration: SETC16 (17 of them) and RMWCIB* write thread configuration registers. Then SEMINIT sets up the semaphore that MATH and PACK share. Near the end comes the actual work: SEMWAIT (wait on the MATH/PACK semaphore until Dst has room), MOP (expands to 8 ELWADDs), SETRWC (set the register-window counters), STALLWAIT, and SEMPOST (tell PACK the result is ready). That's tile_regs_acquire → add_tiles → tile_regs_commit from add_2_tiles.cpp:27-36, at instruction level. One push out of 34 does the arithmetic.
  • Pushes are a small part of the RISC-V work. 34 of TRISC1's 155 kernel steps (22%), 57 of TRISC2's 246 (23%), and 23 of TRISC0's 303 (8%). The rest is address arithmetic, CB pointer updates, and loops that wait on other cores.
B04 follows these instructions after the push: through the MOP and replay expanders, onto each pipe, and through the stalls on Src-valid that make the STALLWAITs above matter.

Now each instruction makes sense. lw a5,16(a3) reads 0xFFB50010, the "tiles received" register of stream 16, which is CB 16 (c_16, the output CB). Even in a simulator with an instant NoC, the kernels do wait for each other. All five harts on a tile advance one step per pass of the clock loop, so a consumer that starts before its producer has finished spins, and you can count the spins. Those counts tell you the order things happened in ttsim. They don't tell you how long anything took on silicon.

This is the poor man's version of GPU PC sampling: Nsight Compute samples warp program counters and attributes them to SASS and source lines. The workflow is the same: collect PCs, map them to the binary, then use line info to get back to source. The difference is that ttsim gives you an exact count of every step instead of a statistical sample, but counts of simulator steps, not time.

6. Exercises, with answers

Each answer below comes from running or reading the code in this orb. Try each one before you open the answer.

E1. Which table slot executes mul a0,a0,a1 (encoding 0x02b50533), and how does it avoid being an add?

The low bits are 11, so it's RISC-V. inst[6:2] = 0x33 >> 2 = 01100 = 12, and funct3 = inst[14:12] = 0, so the index is 12 + 0×32 = 12: alu<0>, the same slot as add and sub. Inside, alu switches on (funct7 << 3) | funct3. funct7 = inst[31:25] = 1, which selects case ( 1 << 3) | 0: value = src0 * src1; // MUL (riscv_impl.h:182-202). The M extension never needed table slots of its own.

E3. Why does TRISC2 report 23 replays outside its kernel, and why can't BRISC ever have that particular kind?

TRISC2's replays are at 0x7100: the same lw a5,0(s0) pattern as TRISC1's at 0x6960, just after the kernel returns (ret 0x70f8). It's tensix_sync() again, waiting for the PACK thread's last instructions to finish. (We printed the PCs with a temporary debug build. Why PACK needed 23 steps and MATH 266 isn't something these counters can tell you; B04 follows the instructions themselves.) BRISC can't have this kind of replay. Its firmware never calls tensix_sync, and in ttsim the TENSIX_SYNC register handler maps the reading core to a thread with trisc_pipe(riscv_id), which accepts only TRISC0–2 and stops with UnimplementedFunctionality for anything else (tile.cpp:1818-1823, 1890-1891). BRISC waits for the other cores in wait_ncrisc_trisc(), which is ordinary polling. That shows up as loop iterations, not replays. BRISC's replay count was 0 in every run.

E4. What happens if an NCRISC kernel contains a .ttinsn? Answer from the code, then say whether that matches the hardware.

tti() checks riscv_id: BRISC goes to pipe 0, and anything else must be TRISC0–2, enforced by TTSIM_VERIFY((riscv_id >= RV32_ID_TRISC0) && (riscv_id <= RV32_ID_TRISC2), UndefinedBehavior, "riscv_id=%d", riscv_id) (riscv_impl.h:1472-1474). NCRISC has id 4, so ttsim stops with UndefinedBehavior: … riscv_id=4. That matches the ISA: "RISCV NC cannot push instructions" (PushTensixInstruction.md:3). The docs don't say what an NCRISC does with a word whose low bits aren't 11. If it treats it as an invalid instruction, that is UndefinedBehavior (BabyRISCV/README.md:25-26). ttsim stops loudly where the hardware would quietly do something.

E5. Our window rule is "PC ≥ 0x8a60 opens, PC == saved ra closes". Name two ways it could silently give wrong numbers, and the evidence that it didn't here.

(1) A kernel that calls a function in firmware text: the PC drops below 0x8a60 while still logically in the kernel. The rule keeps the window open, which is correct, and k_below counts such steps. It was 0 everywhere, so it never happened. (2) An entry where ra isn't the return address. NCRISC on Wormhole doesn't enter by jalr at all: it enters by reset into IRAM. The rule only worked because ttsim keeps registers across reset, so ra was still 0x5cd0, the address after jal wh_iram_trampoline. The evidence that every window was right is that each ret= matched a call site in the disassembled firmware, and every core reported calls=1. Other failure modes: a Blackhole run (a different MEM_MAP_END), or firmware that placed code above 0x8a60.

Recap

  • A baby core in ttsim is a 32-register struct plus a dispatch loop: fetch 4 bytes from L1 (or NCRISC IRAM), set pc += 4 early, check the low two bits, then call a handler or push to the coprocessor. Stalls are replays: the handler sets pc -= 4.
  • The decode table has 256 entries indexed by inst[6:2] | funct3 << 5. Formats without funct3 fill 8 slots each. funct7 (for example, mul vs add) is decided inside the handler. 127 slots are empty, and FP, V, CSR and atomic slots stop a Wormhole run.
  • A word whose low bits aren't 11 is a .ttinsn. tti() rotates it right by 2 and pushes it to the TRISC's own thread (or thread 0 for BRISC). NCRISC is refused.
  • Counting only between the firmware's jalr into the kernel and the return to ra, add_2_integers_in_compute runs 246 / 303 / 155 / 246 / 153 steps on BRISC / TRISC0 / TRISC1 / TRISC2 / NCRISC. That's 1,103 of the chip's 1,029,531 steps: firmware wait loops dominate.
  • The TRISCs pushed 23 / 34 / 57 Tensix instructions, all inside their kernels. TRISC1's 34 contain one MOP that carries all the arithmetic.
  • Replays reveal synchronisation: TRISC1 waited 266 steps in tensix_sync() after its kernel, and NCRISC waited in a j . until BRISC reset it into IRAM.
  • To map a hot PC to source: pc − entry + _start in the .xip.elf, then objdump and addr2line -i. Here, the hot loops were two cb_wait_front polls of CB stream registers.

Check yourself

1. The word at 0x9680 in TRISC1's kernel is 0x88050202. Without running anything, what does ttsim do with it?

Its low two bits are 10, not 11, so step() calls tti(). Rotating right by 2 gives (0x88050202 >> 2) | (0b10 << 30) = 0x22014080 | 0x80000000 = 0xA2014080. Opcode 0xA2 is STALLWAIT in tensix_isa.json. It is pushed into thread T1's FIFO, unless the FIFO is refusing pushes, in which case the PC goes back to 0x9680. The SFPI objdump agrees: it disassembles that word as ttstallwait.

2. Why do lui, auipc and jal each occupy 8 slots of the table, while lw occupies one?

The index includes bits 14:12. For lw those bits are funct3, which tells lw apart from lb, lh and the rest, so only one value of them means lw. In U-type and J-type formats, bits 14:12 belong to the immediate and can be anything. The generator (mask 0x007F) copies the handler into all 8 slots so that every immediate value lands on it.

3. A colleague counts all rv32_step calls and says "add_2_integers_in_riscv ran 963,752 instructions, so the kernel is slow". What's wrong?

Two things. Almost all of those steps are firmware on 72 tiles polling for a go message (the kernel was 116 steps, 0.012%), and the number of polls is set by how often the host clocks the simulator (B01), not by the kernel. Also, a step isn't a cycle: ttsim has no timing model, NoC transfers are instant, and caches are free. Count inside the kernel window, and treat even that as "what ran", not "how long it took".

4. Why is it safe for the patch to detect replays as "PC unchanged after step()", and what else does that test catch?

step() always writes pc + 4 before executing, so the PC can only end where it started if the handler wound it back (pc -= 4, a stall replay) or jumped to its own address. The second case is a j . self-loop, such as the end of wh_iram_trampoline. Both mean "no forward progress this step", which is what we wanted to count. Then we told the two apart by disassembling the PCs.

5. TRISC1, the math core, executed the fewest kernel steps of the three TRISCs (155) and has the smallest instruction cache (½ KiB). Why is that consistent with it doing all the arithmetic?

The arithmetic doesn't run as RISC-V code. TRISC1 pushes one MOP, and the coprocessor's MOP expander turns it into 8 ELWADDs, each covering 8 rows × 16 columns, which adds up to one 32×32 tile. The RISC-V side only configures registers, does the semaphore handshake (SEMWAIT/SEMPOST) and issues that MOP. That takes little code and few steps, so a small instruction cache is enough.
