B01. Meet ttsim

Run real Tenstorrent programs on a virtual Wormhole and Blackhole, learn what the simulator's clock is really counting, and make your first edit to a kernel.

Honesty banner. ttsim is a functional, bit-exact model of the chip. It is not a timing model. Its clock counts are not silicon cycles and say nothing reliable about performance on real hardware. This lab shows you why, using measurements you take yourself.

The question

You run a single-core matrix multiply on a simulated Wormhole. It passes, and the last line of output reads [330591] 8.9 seconds (37.3 KHz). Then you run it again with the matrix engine set to its lowest precision, LoFi. On silicon LoFi does a quarter of the multiplier passes of HiFi4, so it should be faster. The simulator reports [699743], more than twice as many clocks.

Is the simulator wrong? No. It is answering a different question from the one you asked. By the end of this lab you will be able to point at the exact lines of C++ that produce both numbers. You will also know what the bracketed number does measure (the host's polling, mostly) and what you can trust ttsim for: bit-exact results and strict checking of the ISA rules.

All commands below run in this orb, and every output was captured here. Long log lines are trimmed with ….

2. Reading the heartbeat line

The last line of every run, [4501] 0.2 seconds (28.8 KHz), is printed by one function, which runs when the simulator shuts down:

ttsim/src/sim.cpp:98-106 @b3620244
void ttsim_heartbeat() {
    float seconds_elapsed = float(clock()) / CLOCKS_PER_SEC; // XXX this is "seconds of CPU time used" and not "time elapsed"; what do we really want?
    float mhz = g_clock / (seconds_elapsed * 1000000);
    if (mhz >= 10.0f) {
        ttsim_printf("%.1f seconds (%.1f MHz)\n", seconds_elapsed, mhz);
    } else {
        ttsim_printf("%.1f seconds (%.1f KHz)\n", seconds_elapsed, mhz * 1000);
    }
}

The bracketed prefix is added by ttsim_printf, which stamps every simulator message with the current clock (common.cpp:24-31). So the line reads:

Our logs show both caveats. The first Wormhole eltwise_binary run shows user=3.04 s from /usr/bin/time but only 0.3 seconds in the heartbeat, because the 3 s were spent in compiler child processes building the 5 uncached kernels. The matmul shows 9.0 seconds of CPU time against 8.43 s of wall time, because more than one host thread was busy.

What about the [0] 0.0 seconds line near the top? It comes from a separate, short-lived copy of the simulator. During topology discovery UMD needs to know which chip the .so simulates. To find out, it dlopens the image, calls libttsim_init, scans PCI config space, and calls libttsim_exit. No clock is ever run in that copy, so its heartbeat reads 0.

tt-metal/tt_metal/third_party/umd/tt-umd/src/simulation/tt_sim_communicator.cpp:488-503 @7aad8aac
    // Config space only answers while the image is running. …

    …
    struct SimRunGuard {

        ~SimRunGuard() { exit_fn(); }
    } sim_run_guard{sim_exit};

    ImageProbe probe;
    probe.bdfs = scan_pci_endpoints(config_read32);

The device that actually runs your program is then started with a second libttsim_init. For a single chip this is the same loaded image, not a fresh copy: LD_DEBUG=files shows libttsim_wh.so opened three times with a rising direct_opencount and finalised only once, at process exit. That is harmless here because the probe never clocked, so g_clock is still 0 (nothing in ttsim resets it). UMD only copies the .so into a sealed memfd and dlopens /proc/self/fd/N, which gives private globals, when it is asked to (copy_sim_binary, tt_sim_communicator.cpp:294-302), which is off by default.

3. Determinism: same input, same clock

Every pair of runs in the table above gave the same count. That is by design:

  • The library is single-threaded and "creates no threads of its own" (docs/libttsim_api.md).
  • Busy tiles are visited in ascending ID order (libttsim.cpp:250).
  • Every entry point forces the default floating-point environment with FpEnvGuard (libttsim.cpp:13-67), so the results do not depend on how the host has set rounding.
  • The device's WALL_CLOCK register returns g_clock itself (tile.cpp:1034), not host time.

The UMD side also clocks the simulator synchronously from the calling thread. Its comment explains why: "A background clock thread would race with reads/writes and produce non-reproducible runs" (tt_sim_tt_device.cpp:418-427).

The stock matmul has a catch. It fills its inputs from std::mt19937 rng(std::random_device{}()) (matmul_single_core.cpp:203), so every run multiplies different numbers. You can see it in the two Wormhole runs: PCC was 0.98139745 and then 0.98024255. Yet the clock count was 330591 both times. To compare results bit for bit, use the workbench's mm_fid. It is the same program with a seed (MM_SEED), a selectable fidelity (MM_FIDELITY), and a hash over the output:

Same seed, same hash, same clock count. The CPU seconds differ (8.9 vs 9.0) because those depend on the host. With MM_SEED=7 the hash changes to f79d5e7a67b40383, but the count is still [330591]. The number of clocks does not depend on the data at all. The kernel's control flow is the same for any input values, and, as section 4 shows, ttsim charges nothing extra for "harder" numbers.

mm_fid parses MM_FIDELITY with std::atoi, so it expects the enum's numbers: LoFi=0, HiFi2=2, HiFi3=3, HiFi4=4 (tt_metal/api/tt-metalium/base_types.hpp:13-19). MM_FIDELITY=HiFi4 parses as 0 and quietly runs LoFi. We tried it, and it printed math_fidelity = 0 and the LoFi hash 213e53fed10c0383.

Determinism has one important exception, which section 4 explains. When the host itself has several threads touching the device, the count stops being reproducible.

(Results are bit-exact throughout, and HiFi3 and HiFi4 produce identical bits for these inputs, which B07 explains.) To see why the clocks behave like this, we have to find out who turns the crank.

Who advances time? The host does.

The API documentation states the rule in one line: "The simulator does not advance time on its own; it only runs inside libttsim_clock." So who calls libttsim_clock under tt-metal? Search UMD and you find this:

tt-metal/tt_metal/third_party/umd/tt-umd/src/tt_device/tt_sim_tt_device.cpp:334-338 @7aad8aac

    // in the absence of an API reliably called from all spin loops polling the device.

}

It is called at the end of every NoC read the host makes:

Writes have no such hook. Now think about what the host does after it launches a kernel in slow dispatch. It sits in a loop reading each worker core's go_msg mailbox until the core reports DONE (llrt.cpp:338-342, inside wait_until_cores_done at llrt.cpp:444). Each read clocks the chip once. The device moves forward exactly as fast as the host polls it.

Step through it. Switch modes to see how DPRINT and fast dispatch change who supplies the clocks.

DPRINT has a second effect. The host's poll loop deliberately sleeps between polls whenever DPRINT or Watcher is on, so that their own reads can get through:

tt-metal/tt_metal/llrt/llrt.cpp:514-519 @7aad8aac
        // Continuously polling cores here can cause other host-driven noc transactions (dprint, watcher) to drastically
        // slow down for remote devices. So when debugging with these features, add a small delay to allow other
        // host-driven transactions through.
        if (rtoptions.get_watcher_enabled() || rtoptions.get_feature_enabled(tt::llrt::RunTimeDebugFeatureDprint)) {
            std::this_thread::sleep_for(std::chrono::milliseconds(5));
        }

While the main thread sleeps, the print server, which runs on its own std::thread (dprint_server.cpp:998), keeps reading, and each of its reads is a clock. The two threads interleave however the OS schedules them, which is why six runs gave six different counts. Fast dispatch hands the crank to a different loop. Its completion queue is in host memory, so tt-metal clocks explicitly as it polls:

What one clock does inside the chip

That explains where clocks come from. It does not yet explain the fidelity result: the host polls the same way in both matmul runs. For that we need to look inside libttsim_clock. All 70 lines of it are worth reading. (It mentions Tensix instructions such as UNPACR and MVMUL, the Src register banks, and fidelity phases. Here you only need to know that they are Tensix coprocessor instructions (UNPACR fills a Src bank, MVMUL multiplies two of them) and that they can stall; A04 and A06 explain them.) Here is the core:

ttsim/src/libttsim.cpp:250-283 @b3620244 (trimmed)

Read it line by line:

  • Only busy tiles are visited, lowest ID first. next_busy_t_tile scans a bitmask (libttsim.cpp:211-219), so 79 idle Tensix tiles cost nothing.
  • Each active hart executes exactly one instruction per pass. rv32_step fetches, decodes and executes one word (riscv_impl.h:1938-1978). A stall is a replay: a load that cannot complete does pc -= 4 and tries again next pass (riscv_impl.h:731).
  • Each Tensix pipe tries its FIFO head. A handler returns false to stall. For example, UNPACR waits while its Src bank is still valid (tensix.cpp:3169-3172), and MVMUL waits until both Src banks are valid (tensix.cpp:1766).
  • The "hack": the repeat loop. If any Tensix instruction succeeded, the whole tile is clocked again in the same clock, and that includes another step for every hart.

After the Tensix tiles, each active Ethernet core takes 1 step, or 16 steps if it was busy within the last 1024 clocks (libttsim.cpp:288-299, sim.h:404-405). Then g_clock++ (libttsim.cpp:311). Step through one clock:

A ttsim clock is one call to libttsim_clock. In it, each busy tile's harts step one instruction, and they step again for as long as that tile's Tensix pipes keep succeeding. The host decides how many clocks happen. Neither of these is how silicon spends cycles.

  • About 214 hart-steps per clock in add_2 (963,752 / 4,501), although the kernel uses one hart on one core. Firmware on every other core is running wait loops, and each of those harts gets a step per clock too.

Now add each fidelity run's clocks and extra passes together:

LoFi: 699,743 + 190,276 = 890,019     HiFi4: 330,591 + 559,476 = 890,067

The two totals agree to within 48. The matmul tile needs about 890,000 passes either way, and these passes are mostly RISC-V instructions: loop counters, CB polling, tti pushes. Every extra MVMUL that succeeds buys one more pass inside the same clock. HiFi4 has more MVMULs, so it gets more free passes and needs fewer real clocks. The simulator's clock is cheaper exactly when the matrix engine is doing more work.

To confirm it, remove the hack. Make a second copy (ttsim-noloop) and replace the if (!any_tensix) break; with an unconditional break;, so each tile gets exactly one pass per clock. patches/b01-noloop.patch is the counters plus that one change:

With one pass per clock, LoFi and HiFi4 take the same number of clocks to within 48. The output bits are unchanged, so the repeat loop is purely a speed optimisation and never affects results. The runs also took longer in wall time (12.5 s and 15.0 s, against 9.8 s and 8.7 s), which is why the hack exists ("for simulator perf"). Even without it, one MVMUL costs one clock, the same as a NOP, so 2.5× more matrix work does not show up in the count at all. Explore the three views:

GPU architects use two kinds of simulator. Cycle-level models such as GPGPU-Sim or Accel-Sim track pipelines, caches and DRAM queues so they can predict time. Functional emulators run the ISA as fast as possible and only promise correct results. ttsim is firmly the second kind, and its own docs name a separate "performance-modeling sim for shipping silicon" as one of the team's engineering priorities (docs/unsupported_functionality.md:31-33). Treat its clock like an instruction-retired counter that also ticks once per host poll.

5. What ttsim models, and what it leaves out

If the clock is not time, what is ttsim good for? A great deal, as long as you ask it questions about correctness:

ModelledEvidence
Functional behaviour of every implemented instruction: RISC-V, Tensix, NoC, DMA, ARC, EthernetReal tt-metal examples pass unmodified on WH and BH (section 1). The README says many tt-metal, ttnn and LLK tests pass, as well as whole LLMs.
Bit-exact numerics, NaN bit patterns includedREADME, "Numerical Accuracy": "designed to provide bit-exact numerical results relative to silicon for all computations". Our hashes repeat exactly.
The ISA contract, strictly: anything undefined is fatalttsim_error prints [clock] ERROR: Category: func: msg and calls _Exit(1) (common.cpp:33-45). For example, NoC writes must keep (src&15)==(dst&15) (tile.cpp:1588-1589), and fence on WH is rejected (riscv_impl.h:1079-1084).
Ordering that software creates: stalls on Src valid, semaphores, FIFO-full replaysHandlers return false and are retried (tensix.cpp:1766, 3171; riscv_impl.h:1479-1484).
Not modelledEvidenceConsequence
Timing of anythingOne instruction per hart per pass; Tensix instructions repeat for free (section 4)Clock counts are not performance. Use silicon and the profiler for that.
NoC latency and bandwidthA read copies the bytes and bumps the "response received" counter in the same MMIO write that launched it (tile.cpp:1619-1621)Barriers always pass at once, so a missing barrier goes unnoticed (B05).
Contention: NoC links, L1 banks, DRAM queuesL1 is one flat array, uint8_t sram[TENSIX_SRAM_SIZE] (sim.h:355); there are no link or bank queuesBad data placement looks just as fast as good placement.
CachesThe hooks exist but are empty: icache_invalidate, dcache_invalidate and dcache_access have empty bodies (riscv_impl.h:62-70, 613-614)A missing cache flush that would break on silicon may still pass. The README lists "missing synchronization, cache flushes, or memory fences" as a source of divergence.
Every hardware feature"roughly 70% of the WH/BH architectural feature surface" is implemented; the rest is UnsupportedFunctionality on purpose (docs/unsupported_functionality.md:9-11)For example, SFPLOADMACRO, so env.sh sets TT_METAL_DISABLE_SFPLOADMACRO=1.
"Passes on ttsim" means "my program does not break the ISA contract on the paths this run took, and it produced these exact bits." It does not mean "this is fast", and it does not mean "my synchronisation is right". Instant NoC transfers can hide races that silicon would expose. The README warns about this too: ttsim "may evaluate operations in any order permitted by software synchronization".

"Tile" means three things. In ttsim source, a tile is a node on the NoC grid, identified by a type letter: 'T' Tensix, 'E' Ethernet, 'A' ARC, 'P' PCIe, and 'D' for a DRAM channel's NoC endpoints (coord_to_tile, tile.cpp:723). It is not a 32×32 data tile, and it is not quite "a Tensix core" either. This lab always says "Tensix tile" or "data tile". B02 maps every coordinate.

The clock loop

You have already read it in section 4 (libttsim.cpp:244-314). Two details remain. The outer function loops over chips inside each clock and increments a single global g_clock ("single global timebase, advanced once per clock across all chips", :311). And Tensix instructions reach the FIFOs through the interpreter. A 32-bit word whose low two bits are not 11 is not a RISC-V instruction, so rv32_step passes it to tti(). That function rotates it into a Tensix instruction and pushes it, or replays the word if the FIFO is full:

8. Exercises, with answers

Exercise 1. Add volatile uint32_t spin = 0; for (uint32_t i = 0; i < 1000; i++) { spin = spin + i; } before the addition in your overlay. Predict the new clock count, then run it. What if the loop runs 2000 times?

Measured: 1000 iterations gave [9505] (twice), and 2000 gave [14505]. That is +5,004 and +10,004 clocks: exactly 5 clocks per iteration plus 4. Disassemble the JIT-built ELF (the newest brisc.elf under ~/.cache/tt-metal-cache/…/reader_writer_add_in_riscv/) with runtime/sfpi/compiler/bin/riscv-tt-elf-objdump -d and the loop is 5 instructions:

    4ce8:	lw	a4,12(sp)
    4cec:	add	a4,a4,a5
    4cf0:	sw	a4,12(sp)
    4cf4:	addi	a5,a5,1
    4cf8:	bne	a5,a3,4ce8 <.L15>

One instruction per clock for the hart on the critical path, and the host polled once per clock to keep it going. On real silicon the lw/sw to the stack and the taken branch would not each take exactly one cycle.

Exercise 2. In your ttsim-noloop copy, predict the LoFi and HiFi4 clock counts and result hashes before you run them.

The counts should be roughly the passes the tile needed, about 890k for both. Measured: LoFi 889,442 and HiFi4 889,490. The hashes are unchanged (213e53fe… and ef7abcd1…), because the repeat loop only changes when the same instructions run in clock terms, never what they compute. The gap to the conservation sum (890,019 − 889,442 = 577) is close to the 576 extra passes that even add_2 shows, so it is probably work common to every run. We have not traced exactly where it comes from.

Exercise 3. Every run prints [0] 0.0 seconds (0.0 KHz) before the device even opens. Find the code responsible.

TTSimCommunicator::probe_image (tt_sim_communicator.cpp:450-505). It dlopens the image, calls libttsim_init, scans PCI endpoints, and then a guard object calls libttsim_exit, which prints the heartbeat at clock 0. The instrumented build confirms this: that first instance prints COUNT clock_calls=0 … pci_rd=0.

Exercise 4. Using only the counters, why does fast dispatch need 10,946 clocks when slow dispatch needs 4,501?

Two effects. (1) Fast dispatch made only 4,960 BAR reads but 10,946 clock calls, so about 6,000 clocks came from advance_device_execution() in the dispatch wait loops, such as polling the completion queue in host memory (system_memory_manager.cpp:780-786) and waiting for prefetch-queue space (:719-724). (2) The device did more work: 3,283,966 hart-steps against 963,752, because the prefetcher and dispatcher firmware cores were running. Neither effect says anything about how fast fast dispatch is on silicon, which is the whole reason it exists (A17).

Exercise 5. You want a reproducible clock count while debugging with prints. What do you do?

You can't, with DPRINT: its server thread's reads interleave with the main thread's at times set by the OS scheduler (6064, 5115, 5060, 5063, 5058, 5064 in our runs). The ttsim README points to the alternative, "arbitrary debug visibility via source-level modification": edit an instrumented copy of ttsim and call ttsim_printf, which stamps each line with [g_clock] and adds no host reads. Our COUNT line is an example, and the count stayed exactly 4501.

Exercise 6. Run matmul_single_core on BH and WH. Why might BH take fewer clocks (276,921 vs 330,591) while add_2 takes more (6,596 vs 4,501)?

The counts follow instruction counts on the critical path plus host polling. They do not follow hardware speed. Each architecture builds its own firmware and its own LLK code, and the chips have different grids (80 vs 140 Tensix tiles), so the instruction streams and the number of polls differ. We have not broken down which part of the difference comes from where, and neither number predicts which chip is faster. The honest answer is "different code ran". B03's per-core instruction counts let you dig into it.

Recap

  • ttsim is one libttsim.so with 10 exported C functions (check with nm -D). UMD dlopens it, and tt-metal programs run on it unchanged, on both WH and BH.
  • The heartbeat [N] S seconds (R KHz) means: N = g_clock, S = host CPU time, R = N/S.
  • Runs are deterministic: same input, same bits, same clock count. The count does not even depend on the data. Several host threads touching the device (DPRINT, Watcher) break determinism.
  • Time only moves inside libttsim_clock. Under tt-metal, UMD calls it once per host read (after_read), and fast dispatch adds explicit calls. So the clock mostly counts polls.
  • In one clock, each busy tile's harts step one instruction, repeated as long as Tensix instructions keep succeeding. This is why HiFi4 takes fewer clocks than LoFi. Clocks plus free passes is about 890k either way.
  • ttsim models functional behaviour, bit-exact numerics and the ISA contract. It does not model timing, NoC latency, contention or caches. It is the place to test correctness, not performance.
  • A kernel overlay under $LAB_HOME/kernels changes device code without rebuilding: + → * gives "Expected result of 21, got 98".

Check yourself

A colleague posts: "ttsim shows HiFi4 matmul is 2× faster than LoFi on Wormhole." What is wrong, in one sentence of mechanism?

ttsim's clock counts host polls, and it re-clocks a tile for free while Tensix instructions keep succeeding (libttsim.cpp:252-283), so HiFi4's extra MVMULs reduce the count. On silicon each extra fidelity phase costs real cycles, so the claim inverts reality.

In slow dispatch without DPRINT, you add a 10 ms sleep in the host between launching the kernel and the first poll. Does the clock count change?

No. The simulator does nothing between libttsim_clock calls, and a sleep makes no reads, so it adds no clocks. The device simply waits, frozen, for the next poll. (Wall time grows by 10 ms, of course.)

Why does the stock matmul_single_core print a different PCC each run, yet the same clock count?

Its inputs come from std::random_device, so the data changes every run. But the kernel's control flow does not depend on the values, and ttsim charges the same for every instruction whatever its operands. So the instruction stream, and with it the poll count, is identical. mm_fid with MM_SEED fixes the data too, and the hash then repeats.

You forget noc_async_read_barrier() in a reader kernel. Will ttsim catch it?

Almost certainly not. noc_cmd_ctrl copies the data and increments the "read response received" counter immediately, in the same MMIO write that issued the read (tile.cpp:1619-1621), so the data is always there by the time the kernel uses it. Silicon has real latency, and the bug would show up there. B05 explores this.

Which exported function would you call to run the chip for 1000 clocks from your own C program, and what happens if you call libttsim_tile_rd_bytes on a Wormhole build?

libttsim_clock(1000). It loops 1000 times over all chips and increments g_clock each time (libttsim.cpp:302-314). libttsim_tile_rd_bytes is transitional and on WH/BH raises UnsupportedFunctionality, which prints an error and terminates the whole process via _Exit(1) (libttsim.cpp:199-202, common.cpp:33-45).

In ttsim source, what is a "tile", and how many 'T' tiles does a Blackhole build have?

A node of the NoC grid, typed T/E/A/P (plus D for DRAM endpoints), not a 32×32 data tile. Blackhole has NUM_T_TILES 140 (config.h:53), against 80 on Wormhole.
