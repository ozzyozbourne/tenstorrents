B07. Matmul and math fidelity, bit for bit

Catch the matrix engine in the act: dump the SrcA, SrcB and Dst registers around every MVMUL of one output tile, then predict every Dst bit in 200 lines of Python, at every fidelity.

Honesty banner. ttsim is a functional simulator designed to be bit-exact: its README says it aims to compute the same bits silicon would. It is not a timing model. Its clock counts are not silicon performance, and nothing on this page measures speed. What this lab measures is values: which bits land in Dst. "Bit-exact" here means "matches ttsim". ttsim's authors claim ttsim matches silicon; I have no silicon in this orb and did not check that claim.

The question

In A06 you met the matrix engine's odd multipliers: 5 bits of SrcA by 7 bits of SrcB. A BF16 significand has 8 bits (an implicit 1 plus 7 stored bits), so one pass can't multiply two BF16 numbers exactly. The engine splits each significand into a high slice and a low slice. It multiplies the slices in up to four passes, called fidelity phases, and adds the pieces into Dst. LoFi runs one phase, HiFi2 two, HiFi3 three and HiFi4 four. Lab B04 (later in the reading order) counts the cost in the instruction stream: a 2×2-tile matmul (8 tile products) executed 128 MVMULs at LoFi, 256 at HiFi2 and 512 at HiFi4.

That is the story from the documents and from the instruction counts. This lab checks it at the level of single bits:

If you could stop the simulator just before and just after one MVMUL and read SrcA, SrcB and Dst, could you predict every bit of the new Dst yourself? And what does each extra phase change?

We'll do it in four moves. First we measure the end-to-end error of a 640×640×640 matmul at each fidelity. Then we read the 30 lines of ttsim that do the multiplying. Then we add an environment-gated register dump to a copy of ttsim. Finally we write a Python model and score it against every element of every MVMUL of one output tile. All output on this page was produced in this orb with ttsim b3620244 (Wormhole build) and tt-metal 7aad8aac.

Setup

mm_fid is tt-metal's single-core matmul example with two knobs. MM_SEED seeds the std::mt19937 that fills A (640×640) and B (640×640) with BF16 values drawn uniformly from [0, 1). MM_FIDELITY picks the MathFidelity passed to the compute kernel. Pass the enum's number, not its name: LoFi = 0, HiFi2 = 2, HiFi3 = 3, HiFi4 = 4 (tt_llk_wormhole_b0/llk_lib/llk_defs.h:139-145). The value is parsed with atoi, so MM_FIDELITY=HiFi4 silently means LoFi. The program prints the PCC and the mean and max absolute error against a CPU golden, which accumulates in FP32 and rounds once to BF16. It also prints a 64-bit hash of the result bits.

The compute kernel is the stock one. For each output tile it acquires Dst once, then accumulates Kt tile products into it:

tt-metal/tt_metal/programming_examples/matmul/matmul_single_core/kernels/compute/mm.cpp:55-71 @7aad8aac (comments removed)
for (uint32_t mt = 0; mt < Mt; ++mt) {
    for (uint32_t nt = 0; nt < Nt; ++nt) {
        tile_regs_acquire();
        for (uint32_t kt = 0; kt < Kt; kt++) {
            cb_wait_front(cb_in0, 1);
            cb_wait_front(cb_in1, 1);
            matmul_tiles(cb_in0, cb_in1, 0, 0, 0);
            cb_pop_front(cb_in0, 1);
            cb_pop_front(cb_in1, 1);
        }

With M = N = K = 640, Mt = Nt = Kt = 20. The core therefore computes 20 × 20 output tiles, each the sum of 20 tile products, for 8000 matmul_tiles calls. Each output element is a 640-term dot product that lives in Dst the whole time. In this example Dst holds BF16, because the host leaves fp32_dest_acc_en at its default of false (tt_metal/api/tt-metalium/kernel_types.hpp:106-108). Keep that in mind; it will matter more than fidelity.

Step 2: Read the multiplier

Before we dump anything, let's find out what ttsim claims to compute. Every MVMUL goes through tensix_matmul_op in src/tensix.cpp. It first decides which phase this MVMUL is in. The phase is a 2-bit counter per thread, plus a base:

ttsim/src/tensix.cpp:1812 and 725-730 @b3620244
uint32_t fidelity_phase = (p_tensix->fidelity[pipe] + math_fidelity_base(p_tensix, pipe)) & 3;
...
    if (update_fidelity_phase) {               // in math_update_counters, after every MVMUL
        if (fidelity_clear) {
            p_tensix->fidelity[pipe] = 0;
        } else {
            p_tensix->fidelity[pipe] = (p_tensix->fidelity[pipe] + fidelity_incr) & 3;
        }
    }

The counter only moves when an MVMUL's address mode says so. The LLK sets that up: ADDR_MOD_5 resets the row counters and adds fidelity_increment (1 for any fidelity except LoFi) to the phase (llk_math_matmul.h:80-88). The last of the 16 MVMULs in the replay buffer uses it. The MOP then plays the buffer inner_loops times:

tt-metal/tt_metal/tt-llk/tt_llk_wormhole_b0/llk_lib/llk_math_matmul.h:469-476 @7aad8aac
constexpr std::uint32_t inner_loops = high_fidelity ? to_underlying(math_fidelity) : 1;
ckernel_template tmp(1 /* outer loop */, inner_loops, lltt::replay_insn(ckernel::math::replay_buf_offset, replay_buf_len));
if constexpr (high_fidelity)
{
    if (t_dim > 1)
    {
        tmp.set_end_op(TT_OP_SETRWC(p_setrwc::CLR_NONE, 0, 0, 0, 0, p_setrwc::SET_F)); // Reset fidelity phase

So HiFin plays the 16-MVMUL sequence n times, in phases 0, 1, …, n−1, and LoFi plays it once in phase 0. Now the multiply itself. Each Src cell holds 19 meaningful bits: a sign, an 8-bit exponent and a 10-bit mantissa (a TF32 layout; BF16 uses only the top 7 mantissa bits). mvmul receives 16 SrcA values (one column) and 16 SrcB values (one row) for one Dst element, and builds 16 products:

ttsim/src/tensix.cpp:1690-1707 @b3620244
uint32_t man_a = (a & 0x3FF) | 0x400; // 11 bits
uint32_t man_b = (b & 0x3FF) | 0x400;

int32_t exp_prod = exp_a + exp_b + exp_prod_adj;
if (fidelity_phase & 1) {
    man_a = (man_a >> 1) & 31; // 5 bits
} else {
    man_a >>= 6; // 5 bits
}
if (fidelity_phase & 2) {
    man_b = (man_b & 15) << 3; // 7 bits
} else {
    man_b >>= 4; // 7 bits
}

signs[i] = sign_a ^ sign_b;
exps[i] = exp_prod;
mans[i] = man_a * man_b; // up to 12 bits

Read it with a BF16 number in mind. The 11-bit significand is the implicit 1, then 7 BF16 mantissa bits, then 3 zeros.

  • Bit 0 of the phase picks SrcA's slice. Phase bit 0 = 0 takes bits 10..6: the implicit 1 and the top 4 mantissa bits. Phase bit 0 = 1 takes bits 5..1: BF16's remaining 3 mantissa bits followed by two zeros. Bit 0 of the significand is never used, which matches the ISA's note that SrcA's last TF32 mantissa bit is ignored.
  • Bit 1 of the phase picks SrcB's slice. Phase bit 1 = 0 takes bits 10..4: the implicit 1 and the top 6 mantissa bits. Phase bit 1 = 1 takes bits 3..0, shifted up to fill 7 bits. For BF16 only bit 3, the last mantissa bit, can be non-zero.
  • The low slices carry an exponent penalty. fpu_exp_prod_adj subtracts 5 from the product's exponent when bit 0 is set and 7 when bit 1 is set (tensix.cpp:1572-1581). The low slice of SrcA really is worth 2−5 of the high slice's place value, and likewise 2−7 for SrcB.

That is exactly the ISA's BF16 table (SrcASrcB.md:119-125): phase 0 is (A high, B high), phase 1 is (A low, B high), phase 2 is (A high, B low) and phase 3 is (A low, B low). Let's watch it on a real pair of numbers taken from the dump in Step 3: SrcB = 0.94921875 and SrcA = 0.83984375. They are the third terms (k = 2) of the dot product that becomes Dst element (0,0).

A fidelity phase multiplies one slice of every SrcA significand by one slice of every SrcB significand, and the slices are chosen by the two bits of the phase number. The products of phases 1–3 are tiny but well defined, and whether they survive depends on what they are added to.

The products are only half of mvmul. The other half adds them, and that is where the bits get lost. ttsim does it in three rounding steps, which we will need in Python:

  1. Groups of 8. Products 0–7 and 8–15 form two groups. In each group every product is shifted to the group's largest exponent and rounded to an integer, ties away from zero: man = ((man << 1) + (1 << exp_diff)) >> (exp_diff + 1) (tensix.cpp:1729). The 8 integers are then summed with their signs.
  2. Three terms, aligned and pre-rounded. The two group sums and the old Dst value are aligned to the largest of their exponents. When Dst is not FP32, each term is rounded to a multiple of 213 while it is shifted (fpu_align_term with lsb = 13, tensix.cpp:1477-1510). That leaves each term with 11 significant bits relative to the largest exponent.
  3. Renormalise and round to Dst. The three terms are summed, normalised and rounded half-up to 8 significant bits for BF16 (24 for FP32), then re-encoded (tensix.cpp:1532-1569).

Dst also has its own storage encoding. A BF16 value is stored as sign, then the 7 mantissa bits, then the 8 exponent bits in the low byte: dst_decode_bf16 at tensix.cpp:912-916, which matches the ISA's DstDecodeBF16 at Dst.md:105-109. You'll see that encoding in the dump.

Step 3: Instrument ttsim and dump the registers

We want, for each MVMUL on core (0,0): the phase, the formats, the three row addresses, the 16 SrcA rows and 8 SrcB rows it reads, and the 8 Dst rows before and after. That means 41 lines of text per MVMUL. The best place is inside tensix_matmul_op, right after the row addresses and the phase are known and before the arithmetic starts, plus one line after it. We follow the B04 convention of gating everything on environment variables, so the patched simulator behaves exactly like the stock one when they are unset.

$W/build_ttsim.sh dump wh                 # first run: copy ttsim to $LAB_HOME/ttsim-dump and build it
(cd $LAB_HOME/ttsim-dump && patch -p1 < $W/../patches/b07-mvmul-dump.patch)
$W/build_ttsim.sh dump wh                 # rebuild with the dump (about 4 s)
export TT_METAL_SIMULATOR=$LAB_HOME/sim-dump-wh-release/libttsim.so

Three details matter. Raw values: Src cells are dumped as stored, before ttsim's format truncation. Dst cells are dumped through read_dst16b/read_dst32b, so a row that was never written reads as 0, exactly as mvmul sees it. Gating: B07_OUT=file turns the dump on, B07_TILE picks the Tensix tile (default 0, the core at logical (0,0) that runs this example, as in B04), and B07_SKIP and B07_COUNT select a window of MVMULs. A total: when the process exits, the dump's last line, T <n>, records how many MVMULs ran on that tile. Rows 16f to 16f+15 of each register hold face f of a tile. MVMUL 2, for example, multiplies SrcB rows 0–7 (face 0 of in0) by SrcA face 1 and adds into Dst face 1. In block form that is C₀₁ += A₀₀ · B₀₁, and MVMUL 10 later adds A₀₁ · B₁₁. This is the block-matrix identity from A06, with in0 in SrcB and in1 in SrcA (A15's "in0→SrcB, in1→SrcA"). To make sure I wasn't fooling myself about which operand is which, I re-implemented std::mt19937 and libstdc++'s uniform_real_distribution<float> in Python and regenerated mm_fid's inputs for seed 42. SrcB row 0 above (0.375, 0.796875, 0.94921875, …) is A[0][0..15] rounded to BF16 (0.37454, 0.79654, 0.95071, …). SrcA column 0 (0.55078125, 0.6640625, …) is B[0..15][0] (0.55228, 0.66546, …). The faces are stored untransposed.

Step 4: Reproduce Dst in Python

Now the main event. workbench/py/b07_mvmul.py parses a dump and recomputes every result element from that MVMUL's own dumped inputs. It is plain Python with no dependencies. Its core is three small functions that follow the three rounding steps above:

sim-labs/workbench/py/b07_mvmul.py (excerpt)
def phase_pieces(a, b, phase):
    man_a = (a & 0x3FF) | 0x400
    man_b = (b & 0x3FF) | 0x400
    adj = 0
    if phase & 1:
        man_a = (man_a >> 1) & 31   # SrcA bits 5..1: the next five bits after the top five
        adj -= 5
    else:
        man_a >>= 6                 # SrcA bits 10..6: implicit 1 + top four mantissa bits
    if phase & 2:
        man_b = (man_b & 15) << 3   # SrcB bits 3..0: the low four bits, placed at the top of 7
        adj -= 7
    else:
        man_b >>= 4                 # SrcB bits 10..4: implicit 1 + top six mantissa bits
    return man_a, man_b, adj

def group_sums(prods):
    res = []
    for g in range(2):
        grp = prods[8 * g: 8 * g + 8]
        e = max(p[1] for p in grp)
        if e <= 0:
            res.append((0, 0, 0)); continue
        s = 0
        for sign, exp, man in grp:
            d = min(e - exp, 30)
            m = ((man << 1) + (1 << d)) >> (d + 1)   # align to the group's exponent, round ties up
            s += -m if sign else m
        res.append((int(s < 0), e, abs(s) << 13))
    return res
# accumulate(): align the two group sums and Dst, pre-round each to 11 bits, add, round to Dst

It checks the dump three ways. Independent: each MVMUL's 128 results are computed from its own A, B and D lines. Chained: Python keeps its own copy of Dst. It reads only the first D value each row ever shows and then applies its own results, never looking at later D lines. If the model drifted by one bit anywhere in the 20-tile-product accumulation, that comparison would fail, and the wrong value would be carried into the later ones. Phase effect: for each phase, how many Dst elements actually changed. With --isa it also scores the ISA's float functional model, which we'll come back to.

I also checked the model on two other kinds of data, to make sure it wasn't matching by luck on the easy all-positive, BF16-Dst path. With an FP32 Dst (mm_fid32) it matched 40960/40960 at LoFi and 163840/163840 at HiFi4. There phase 3 changed 40,937 of 40,960 elements. With signed inputs (mm_fid_signed), which exercise the sign handling and cancellation, it matched 100% at all four fidelities, and phase 3 changed 192 elements. No fudge factors were needed. The only Wormhole-specific special case in the model is ttsim's own "renormalisation of −1" quirk (tensix.cpp:1533-1537), copied as is.

Is this circular?

Partly, and it's worth being precise about how much. I wrote the Python by reading ttsim's code, so "Python matches ttsim" first of all shows that the reading is complete: no rounding step, operand order or encoding was missed. The parts that are not circular are these. The phase slices and their weights agree with the ISA's independent table. The operands agree with the host's random inputs. The face schedule agrees with the LLK. And the chained check would catch any state ttsim keeps outside the dumped rows. The ISA's own functional model is a useful contrast. Taken literally (FP32 products of the fidelity slices, summed in order, then WriteDstBF16, which truncates), it matches only 44.7% of LoFi elements and 82.8% at HiFi4. The ISA warns about this itself: the model is "a rough guide rather than an exact description" (MVMUL.md:223), and WriteDstBF16 is marked "Approximate; real hardware rounds" (MatrixUnit.md:186-189). I tracked down the gap with two scratch experiments, which are not kept in the workbench:

  • Replacing truncation with round-to-nearest-even in the ISA model raises the match to 94.1% (LoFi) and 97.8% (HiFi4). Rounding the exact sum once, half-up or half-even, gives the same 94.1% at LoFi.
  • Removing only the 11-bit pre-rounding of the three terms (step 2 above) from the exact model drops it from 100% to 94.3% at LoFi.

So the hardware, as ttsim models it, does not "sum exactly, then round once". It rounds the products into two group sums, rounds each group sum and the old Dst value separately to 11 significant bits (3 bits finer than BF16), adds, and only then rounds to BF16. In about 6% of LoFi elements that gives a different BF16 result from a single rounding of the exact sum. Any reference implementation that wants to be bit-exact with ttsim has to model those steps.

Even after a single tile product, HiFi4 is correctly rounded in only 57% of elements. That isn't the multiplier's fault, since at HiFi4 the four pieces of every product add up exactly. It is the adds. Each element of one tile product is written by 8 MVMULs (2 K-halves × 4 phases), and every one of them rounds Dst back to 8 significant bits, after the group alignment and the 11-bit pre-rounding. In this data, phases 2 and 3 are then rounded away almost entirely, as Step 6 shows.

Step 6: When extra phases stop doing anything

Why did phase 3 change nothing, and phase 2 almost nothing? Look at the sizes. For element (0,0), phase 1 adds 0.085 and 0.050 to its two 16-term slabs (1–2.5% of the slab values 3.48 and 4.90). Phase 2 adds 0.011 and 0.010 (0.2–0.3%), and phase 3 adds 0.0003 and 0.00006 (below 0.01%). Each is added to Dst and rounded to BF16. A BF16 value in [2e, 2e+1) has a step of 2e−7. If the term is less than half a step, round-to-nearest gives back the old Dst exactly. As the dot product accumulates, Dst grows (about 8 per tile product here) and its step grows with it. One by one the phases fall below the threshold. The dump lets us count it exactly: for each of the 20 tile products of output tile (0,0), how many of the 2048 Dst element-updates (1024 elements × 2 MVMULs) did phase 1, 2 or 3 actually change?

This also explains why the BF16-Dst errors in Step 1 are mostly below the golden even at HiFi4 (928 of 1024 elements). Once Dst is large, each MVMUL effectively adds only phase 0's truncated products, and the small positive corrections are rounded away every time. The defect is in the accumulator, not the multiplier. So the cheapest accuracy win for this matmul isn't a higher fidelity. It's an FP32 Dst. With fp32_dest_acc_en = true HiFi2 already reaches 0.405 and HiFi3 0.0034, against 1.51 for BF16-Dst HiFi4.

GPU tensor cores normally accumulate BF16 products in FP32, so this trap rarely appears there. On Tensix the accumulator format is your choice, and the default in this example is BF16. Before raising fidelity, ask what Dst can hold. Fidelity buys bits in the products; it can't buy bits that Dst's format will round away.
This is data-dependent. All-positive inputs make Dst grow monotonically, which is the worst case for late phases. With signed inputs in [−1, 1) the sums cancel, Dst stays small relative to the products, and phase 3 changed 192 of 40,960 elements. HiFi3 and HiFi4 then give different hashes (ba04a3c8… vs 41219683…). Measure on your own data.

4. Use B07_SKIP to dump the last output tile instead of the first. How many MVMULs must you skip at LoFi?

The core computes output tiles in order (mt outer, nt inner), each 20 × 16 × phases MVMULs. The last of 400 tiles therefore starts after 399 × 320 = 127,680 MVMULs at LoFi: B07_SKIP=127680 B07_COUNT=320. At HiFi4 multiply both by 4. The Python needs no change, because the chained check starts from whatever Dst the first record shows. I ran it: MM_FIDELITY=0 MM_SEED=42 B07_OUT=$LAB_HOME/dumps/last0.txt B07_SKIP=127680 B07_COUNT=320 $LAB_HOME/mm_fid, then the script reported 40960/40960 independent and chained. The first M line is M 127680 697510 0 5 5 0 1 0 0 512: the last tile's Dst rows start at 512, the other half of Dst. Dumping the first MVMUL of output tiles 1, 2 and 3 the same way gives Dst rows 512, 0 and 512: MATH alternates between the two halves of Dst from one output tile to the next, which is what lets PACK drain one half while MATH fills the other (the Dst handshake of A12). The rows read as zero again at the start.

5. In the trace of MVMUL #0, product k = 3 has exponent 118 while the group maximum is 125. What does the group-of-8 alignment do to its mantissa 2632?

exp_diff = 7, so m = ((2632 << 1) + (1 << 7)) >> 8 = (5264 + 128) >> 8 = 21. 2632 / 128 = 20.56 rounds to 21. The product (0.18359375 × 0.027954102 ≈ 0.00513) keeps only about 5 significant bits once it is aligned to the group's largest product. Small terms next to large ones lose precision before any Dst rounding happens. This is one reason even HiFi4 isn't "exact then round".

Recap

  • Phases are visible in the simulator. Core (0,0) executed exactly 128,000 × {1, 2, 3, 4} MVMULs at LoFi/HiFi2/HiFi3/HiFi4, and the dump's phase field shows each tile product's 16-MVMUL sequence repeated in phases 0, 1, …
  • Each phase multiplies one slice pair. Phase bit 0 picks SrcA's high 5 or low bits; bit 1 picks SrcB's high 7 or low bits. Exponent corrections of −5 and −7 restore their place value. For one real product, the four pieces 50336 + 1694 + 208 + 7 add up exactly to 243 × 215 = 52245.
  • The adds are where bits are lost. Two groups of 8 with ties-away alignment, each term pre-rounded to 11 bits, then rounding to the Dst format. A 200-line Python model of that matched ttsim on 100% of elements: 40,960 to 163,840 per run, independent and chained, for BF16 and FP32 Dst and for signed data. The ISA's float pseudocode matched 44.7–82.8%.
  • With a BF16 Dst, fidelity hits a wall. Phase 3 changed 0 of 40,960 elements, so HiFi3 and HiFi4 are bit-identical. Phase 1 stopped changing anything after the 9th of 20 tile products. The accumulator dominates the error (≈1.5 BF16 ulps). An FP32 Dst is the bigger lever.
  • Don't trust PCC for fidelity decisions. Look at ulp error, the direction of the bias, and the hashes.

Check yourself

An MVMUL runs with fidelity phase 2 on BF16 data. Which bits of each SrcB significand reach the multiplier?

Phase 2 has bit 1 set, so SrcB's low slice: bits 3..0 of the 11-bit significand, shifted left by 3. For BF16 only bit 3 (the last stored mantissa bit) can be 1, so the 7-bit input is 64 or 0. SrcA uses its high slice (bit 0 clear): the implicit 1 and top 4 bits. The product's exponent is reduced by 7.

Why can the chained check catch errors the independent check cannot?

The independent check gives the model ttsim's own Dst-before values for every MVMUL, so an error can't propagate, and any state ttsim keeps outside the dumped rows would go unnoticed. The chained check feeds the model its own previous outputs across all 20 tile products. A single wrong bit would then fail that comparison and be carried forward into the later updates of that element. It also flags (via the "Dst rows changed by something else" counter) any write to these Dst rows that isn't one of the dumped MVMULs. That counter was 0.

HiFi4 costs 4× LoFi in MVMULs. In this lab's default configuration, what did the last 2× of that cost buy?

Going from HiFi2 to HiFi4 changed the mean error from 1.508 to 1.505 (seed 42). Phase 2 changed 134 Dst updates, all in the first tile product, and phase 3 changed none. With a BF16 Dst those phases fall below half a BF16 step once Dst exceeds a few units. Almost nothing, then. The same phases are valuable with an FP32 Dst (0.405 → 0.011).

Why is LoFi's error always in the same direction for these inputs?

LoFi keeps only the high slices, which is truncation of each significand's magnitude toward zero. With all-positive operands every product is then too small or exact, never too large, so errors accumulate instead of cancelling. After one tile product all 1024 elements of tile (0,0) were below the exact value. With signed data the bias per product still points toward zero, but products of both signs partly cancel in the sum.

The dump shows SrcA cell 3f0d0000. Someone decodes it using the ISA's Src layout (exponent in the low 8 bits). What goes wrong, and why does it not matter for MVMUL results?

They would read exponent 0 and garbage mantissa bits, because ttsim keeps Src cells in FP32 order (sign, exponent, mantissa), not the ISA's documented physical layout. It doesn't affect results: ttsim's arithmetic decodes its own layout consistently, and software can only see the difference through bit-casts. Read a ttsim dump with ttsim's layout: 3f0d0000 is 0.55078125.
