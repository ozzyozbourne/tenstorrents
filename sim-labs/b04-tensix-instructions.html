B04. Following Tensix instructions

Teach the simulator to print every instruction one Tensix core executes, then use that trace to watch MOPs expand, the three threads take turns, and each thread stop and wait for another.

Honesty banner. ttsim is a functional, bit-exact simulator: it computes the same bits silicon would. It is not a timing model. The clock counts and "rounds" in this lab say in what order ttsim ran things and which instruction waited for which. They do not say how many nanoseconds anything takes on a real chip. Treat every number below as an ordering or a count, never as performance.

The question

In A04 you counted the instructions each TRISC pushed into the Tensix coprocessor for add_2_integers_in_compute, which adds two bf16 tiles on core (0,0). TRISC1, the MATH core, pushed 37 instructions (34 with .ttinsn, 3 with sw). None of them was an ELWADD, and yet 8 ELWADDs came out of its expanders. In A12 you saw the source: one call, add_tiles(cb_in0, cb_in1, 0, 0, 0), compiled three times. A13 explained the machinery in between: the LLK library, MOP templates and the replay buffer.

Counts tell you how many. They don't tell you when. Here is the question for this lab:

If you could print every Tensix instruction as it leaves its thread's FIFO and runs, on all three threads of one core, what would you see? In what order do UNPACR, ELWADD and PACR actually run, and where does each thread sit and wait?

ttsim can't print that out of the box. But its source is a few C++ files that rebuild in four seconds, and the print we need is a few dozen lines, so we'll add it ourselves. By the end you'll have a trace format, a small Python post-processor that names opcodes using ttsim's own ISA table, and real traces of an eltwise add and a small matmul. Every output block on this page was produced in this orb with ttsim b3620244 (Wormhole) and tt-metal 7aad8aac.

Step 1: An opcode trace for one tile

Where does an instruction "execute"?

To log executed instructions, we need the one place in ttsim where an instruction leaves the FIFO. It's in the clock loop. Each clock, ttsim visits every busy Tensix tile. For each of the three threads (ttsim calls them pipes) it hands the instruction at the head of the FIFO to tensix_decode_and_execute:

ttsim/src/libttsim.cpp:250-283 @b3620244 (trimmed)
for (uint32_t tile_id = next_busy_t_tile(0); tile_id < NUM_T_TILES; tile_id = next_busy_t_tile(tile_id + 1)) {
    TensixTile *p_tile = &g_t_tiles[tile_id];
    // Hack: for simulator perf, we clock a tile repeatedly as long as it successfully executes at least one Tensix instruction
    for (;;) {
        for (...) rv32_step(&p_tile->rv32[rv32_index]);                 // each of the 5 baby RISC-Vs: one step
        ...
            tensix_frontend_step(p_tensix, pipe);                       // MOP/replay expanders refill the FIFO
        ...
        for (uint32_t pipe_mask = p_tensix->inst_pipes_active; ...) {   // pipes in order T0, T1, T2
            uint32_t pipe = __builtin_ctz(pipe_mask);
            ...
                uint32_t inst = p_tensix->inst[pipe][inst_rd_ptr];
                if (tensix_decode_and_execute(p_tensix, pipe, inst)) {  // true: executed, pop it
                    any_tensix = true;
                    inst_rd_ptr = (inst_rd_ptr + 1) % TENSIX_INST_FIFO_SIZE;
                    ...
        }
        if (!any_tensix) {
            break; // no Tensix instructions executed, bail out
        }
    }

Three facts in that loop shape everything we'll see:

  • Returning false means "stall". The instruction stays at the head of its FIFO and is tried again next time. Every wait in this lab (an UNPACR with no free Src bank, an ELWADD with no valid operands, a SEMWAIT on a zero semaphore) is an execute function that returns false.
  • Pipes go in order T0, T1, T2 within one pass. If T1 frees something, T0 can only see it on the next pass, but T2 sees it in the same pass. This turns out to explain one of our stalls exactly.
  • One clock can contain many passes. The "hack" comment says it: as long as some Tensix instruction succeeds, ttsim keeps re-running the tile within the same clock. So g_clock is far too coarse to order instructions: the whole add_tiles body ran at clock 4531. We'll count passes instead and call each one a round. One round gives each RISC-V one step and each pipe one chance to execute.
A round is not a cycle. On silicon, a RISC-V step, an expander step and a backend issue have different latencies, and an MVMUL has a pipeline. ttsim gives each of them one slot per round because it's a functional model. Rounds are good for order and for how many times something was retried. They are not good for durations.

The patch

tensix_decode_and_execute is a five-line wrapper that releases a latched wait if the block mask allows it and then calls the decoder:

ttsim/src/tensix.cpp:5771-5776 @b3620244
bool tensix_decode_and_execute(TensixState *p_tensix, uint32_t pipe, uint32_t inst) {
    if (p_tensix->wait_block[pipe] && block_mask_holds(p_tensix->wait_block[pipe], inst)) {
        p_tensix->wait_block[pipe] = 0;
    }
    return tensix_execute_inst(p_tensix, pipe, inst);
}

We wrap the return value. A failed attempt bumps a per-pipe counter. A successful one writes a line with the clock, the round, the pipe, the raw 32-bit instruction and the number of failed attempts before it. We print the raw word, not a name, because ttsim already has a better name table than anything we'd type: data/wh/tensix_isa.json, the file its decoder is generated from (tensix_gen_decode.py reads it and writes _out/wh/tensix_decode.h). Gating keeps the log small. Nothing is written unless B04_OUT is set, and then only for one tile (B04_TILE, default 0, the tile that runs core (0,0) here) and a mask of pipes (B04_PIPES, default 7).

The setvbuf line was added after a lesson. When ttsim hits an error it ends the process, and our first version lost the trace lines still sitting in stdio's buffer, which are exactly the lines you want when debugging a crash (Exercise 6). Line buffering fixes that. Because "failed attempt" is counted per round, the tries field is exactly the number of rounds the instruction sat at the head of its FIFO, refused to execute.

Naming opcodes with tensix_isa.json

Opcodes are the top byte of the instruction (TT_OP(opcode, params) ((opcode << 24) + params) in ckernel_ops.h). The ISA file maps each name to an opcode and its fields as "hi:lo" bit ranges:

ttsim/data/wh/tensix_isa.json @b3620244 (three of its 128 entries, reformatted)
"ELWADD":    {"opcode": 40,  "args": {"dst": "9:0", "addr_mode": "16:15", "instr_mod19": "20:19", "dest_accum_en": "21:21", "clear_dvalid": "23:22"}},
"SEMWAIT":   {"opcode": 166, "args": {"wait_sem_cond": "1:0", "sem_sel": "9:2", "stall_res": "23:15"}},
"STALLWAIT": {"opcode": 162, "args": {"wait_res": "14:0", "stall_res": "23:15"}},

The post-processor, sim-labs/workbench/py/b04_trace.py, loads that file and turns a6008009 into "SEMWAIT MATH_PACK while==0". It decodes a few fields where they help: the semaphore names come from ckernel_structs.h:15-24, and the STALLWAIT condition bits C0–C14 from the ISA documentation's STALLWAIT.md. One caveat: the JSON has placeholder bit ranges for MOP and REPLAY, because ttsim decodes those four frontend opcodes by hand, so the script decodes them the way mop_ingest and replay_expander do. It has five subcommands: stream, stalls, mops, hist and js.

This is the moral equivalent of running a GPU kernel under an instruction-level tracer (think SASS-level tracing in a simulator such as GPGPU-Sim, or binary instrumentation with NVBit) and post-processing with the ISA tables. The difference is how small it is. The whole Tensix frontend and backend of ttsim fit in one 6000-line file, and our hook is one function.

Step 3: Watching MOPs expand

The X lines show what executed. To see where it came from, we log three more places on the frontend path. A push enters tensix_push_inst, which sends a MOP to the MOP expander and everything else to the replay expander:

ttsim/src/tensix.cpp:295-308 @b3620244
void tensix_push_inst(TensixState *p_tensix, uint32_t pipe, uint32_t inst, bool bypass_mop_expander) {
    if (bypass_mop_expander) {
        replay_expander(p_tensix, pipe, inst);
        tensix_frontend_step(p_tensix, pipe);
        return;
    }
    uint32_t opcode = bits<31,24>(inst);
    switch (opcode) {
        case TENSIX_OPCODE_MOP: mop_ingest(p_tensix, pipe, inst); break;
        case TENSIX_OPCODE_MOP_CFG: mop_cfg(p_tensix, pipe, inst); break;
        default: replay_expander(p_tensix, pipe, inst); break; // everything else is just passthrough
    }
    tensix_frontend_step(p_tensix, pipe);
}

mop_ingest (tensix.cpp:125-157) snapshots the thread's nine MOP config words. mop_next then walks mop_step_inst (161-218) one emitted instruction at a time, whenever the FIFO has room, and each emitted instruction goes through replay_expander (63-116), which may record it, or turn a REPLAY into a playback. The second patch adds a line at each of those points: P for a push, M for an ingested MOP with its config words, E for each emitted instruction, D when an expansion ends with its count, R for a REPLAY, and Y for each instruction played back from the replay buffer.

So add_tiles is three MOPs, one per thread. The math MOP is a double loop: 4 outer iterations (one per 16×16 face), each running the inner op twice (each ELWADD handles 8 rows, and a face has 16) and then the end op SETRWC, which resets the row counters and releases the Src banks.         tmp.set_end_op(TT_OP_SETRWC(CLR_SRC, p_setrwc::CR_AB, 0, 0, 0, p_setrwc::SET_AB));

With face_r_dim = 16 and MAX_FPU_ROWS = 8, innerloop = 2, and num_faces = 4. The unpack MOP uses two inner ops, UNPACR SrcA and UNPACR SrcB. In that case ttsim doubles the inner count and alternates the two (loop_op_flip in mop_step_inst), giving A B A B per outer iteration and 8 in total. That's ckernel_template tmp(num_faces_r_dim, num_faces_c_dim, unpack_srca, unpack_srcb) at llk_unpack_AB.h:130, with 2 × 2 faces. Step through the expander below. It runs the same rules as ttsim's mop_step_inst on the config words captured above.

The story in three lines:

  1. During matmul_init, TRISC1 pushes a REPLAY in load mode (start 16, length 16), followed by 16 MVMULs. The replay expander records them into buffer entries 16–31 instead of passing them on. Execute-while-loading is off, so none of them runs yet. This is lltt::record(ckernel::math::replay_buf_offset, replay_buf_len) with replay_buf_len = 16 for full 32×32 tiles (llk_math_matmul.h:361-364), the 16-MVMUL sequence A06 drew.
  2. Each matmul_tiles pushes one MOP whose inner op is REPLAY play 16,16 and whose inner count is the fidelity (inner_loops = high_fidelity ? math_fidelity : 1, llk_math_matmul.h:469-470). At HiFi4 it emits 4 REPLAYs and one SETRWC.
  3. Each REPLAY plays back 16 MVMULs. So one 32-bit push becomes 4 × 16 = 64 MVMULs, and 8 tile products give 512. At LoFi: 8 × 16 = 128. We also ran HiFi2: 256. Those are A06's "16/32/48/64 MVMULs per tile" at 1, 2 and 4 phases, counted from the instruction stream itself.

MATH pushed 96 instructions and executed 591. Here the expanders do most of the work. The 96 pushes are identical at both fidelities: fidelity lives in the MOP config, not in the code TRISC1 runs. That's why TRISC1 can get away with a ½ KiB instruction cache (A04). The unpack thread uses replay too: its MOPs are of the other type (mop_type 0, the "unpack template"), and each emits a single REPLAY play 0,5 that replays UNPACR SrcA, RDCFG, ADDGPR, REG2FLOP, NOP.

This is the instruction-level view of A13's zoom from add_tiles to an expanded stream, and of the MVMUL ordering in A06. B07 goes one level deeper and dumps one MVMUL's operands.

Step 4: Stalls, and who is waiting for whom

Every stall is an execute function returning false. The stalls subcommand totals the failed attempts by instruction:

$ python3 $W/py/b04_trace.py stalls $LAB_HOME/mm4.trace

T1      MVMUL dst=0 addr_mode=0 clear_dvalid=0              8     629  300

Three kinds of wait, each with its own source line.

(a) UNPACR waits for a free Src bank

ttsim/src/tensix.cpp:3168-3172 @b3620244 (TENSIX_EXECUTE_UNPACR)
    uint32_t src_bank = unpack_block_selection ? p_tensix->src_b_unpack_bank : p_tensix->src_a_unpack_bank;
    uint32_t src_valid = unpack_block_selection ? p_tensix->src_b_valid : p_tensix->src_a_valid;
    if (src_valid & (1 << src_bank)) {
        return false; // stall until not valid
    }

An unpacker writes into the bank it's pointing at, and refuses while that bank still holds data the FPU hasn't released. After a successful unpack it flips to the other bank (src_a_unpack_bank ^= 1, tensix.cpp:3588). Look at round 4390 in the add. T0 had filled SrcA bank 0 (round 4384) and bank 1 (4386), and bank 0 again (4388) after T1's first SETRWC released it at 4387. Its next target was bank 1, which the FPU was still reading. T1's second SETRWC (clear_ab_vld = 3, releasing both operands) ran at round 4390, but T1 runs after T0 within a round. So T0 failed once in round 4390 and succeeded in 4391. It's a one-round stall, and its exact cause is ttsim's pipe order. metal_example_eltwise_binary, which adds 64 tiles, shows the same pattern once per tile: 64 stalls of exactly 1 round each.

(b) MVMUL and ELWADD wait for valid banks

ttsim/src/tensix.cpp:1763-1767 @b3620244 (tensix_matmul_op, used by MVMUL; tensix_elw_op at 1957-1961 is identical)
    uint32_t src_a_bank = p_tensix->src_a_matrix_bank;
    uint32_t src_b_bank = p_tensix->src_b_matrix_bank;
    if (!(p_tensix->src_a_valid & (1 << src_a_bank)) || !(p_tensix->src_b_valid & (1 << src_b_bank))) {
        return false; // stall until both valid
    }

This is the opposite condition, and it's the hardware rule that makes the unpack → math hand-off need no semaphore (the ISA documentation says FPU instructions that read Src "automatically wait for this condition", STALLWAIT.md, notes on C10/C11). In the matmul, the first MVMUL of each matmul_tiles waits. The longest wait, 300 rounds, is the very first. The MATH thread had pushed its MOP long before and the MVMUL sat at the FIFO head the whole time, while T0 executed nothing. Most likely TRISC0 was still waiting in cb_wait_front for the reader kernel to bring the first tiles from DRAM. That is an inference: our trace records Tensix instructions, not RISC-V code.

$ python3 $W/py/b04_trace.py stream $LAB_HOME/mm4.trace --from 4442 --to 4446

Note the order: SrcB first (in0), then SrcA (in1). llk_math_matmul.h:343-344 says so ("in0 - loaded to SrcB, in1 - loaded to SrcA"). The MVMUL fires in the round the second operand lands, because T1 runs after T0. All 8 MVMUL stalls in the trace are on the first MVMUL of a tile product (each waits for a fresh pair of tiles). The other 504 never wait.

(c) SEMWAIT on MATH_PACK

ttsim/src/tensix.cpp:5570-5582 @b3620244 (TENSIX_EXECUTE_SEMWAIT)

        ...

PACK's tile_regs_wait() is SEMWAIT MATH_PACK while==0 (_llk_packer_wait_for_math_done_, llk_pack_common.h:26-29). The packer thread reaches it early, because TRISC2 has nothing else to do, and it sits there until MATH's SEMPOST. In the add that took 72 rounds. In the matmul it happened four times, once per output tile, for 256, 214, 226 and 214 rounds: each output tile takes two whole matmul_tiles of 64 MVMULs. In every case the SEMWAIT passes in the same round as the SEMPOST, because T1 runs before T2.

Don't read "PACK waited 256 rounds" as "the packer is idle 256 cycles per tile on silicon". On a real chip, MVMUL has a 5-cycle latency, unpackers take many cycles per face, and the packer has to wait for a STALLWAIT on MATH to drain the FPU pipeline. ttsim models none of those timings. What carries over is the dependency structure: which instruction waits on which condition, and which thread releases it. Those are properties of the program, and a missing one is a bug on any timing.
On a GPU, the closest analogue of these stalls is warp-scheduler stall reasons ("waiting on a barrier", "long scoreboard"), which profilers sample statistically. Here we can list every stall exactly, with the condition that caused it. In exchange, the simulator has no timing to tell you whether a stall would actually cost anything.

Three observations, each of which you could have predicted from the earlier chapters and can now confirm:

  • Most Tensix instructions are not math. For one tile of eltwise add, 8 of 151 executed instructions are ELWADD. The rest set data formats, address counters, MOP templates and packer registers, or synchronise. Setup is a fixed cost per kernel launch, which is one reason real workloads keep many tiles flowing through one kernel launch (A15).
  • The matmul is dominated by one opcode, and fidelity is a pure multiplier on it. Going from LoFi to HiFi4 adds exactly 384 MVMULs (and 8 SETRWCs). Not one other instruction on any thread changes. Fidelity costs FPU instructions and nothing else, which is why A06 can reduce matmul throughput to "16 × phases MVMULs per tile".
  • The per-tile thread costs are lopsided. Per output tile, MATH executes 128 MVMULs at HiFi4 against PACK's 2 PACRs. In a real kernel the FPU lane is the one that has to stay busy. Anything that makes it wait (an unpacker starved by the NoC, or a packer that hasn't released Dst) shows up as the stall bands in the first animation.

For one more data point, we also ran a 96×96 matmul (3×3×3 = 27 tile products): 1728 MVMULs = 27 × 64, 54 UNPACRs = 27 × 2, and 18 PACRs = 9 output tiles × 2. The formula holds.

Step 6: Exercises, with answers

Exercise 1. Trace only the MATH thread of the add. How many X lines do you get, and how do you ask for it?

We got 48 X lines (and 37 P, 1 M, 12 E, 1 D), which matches T1's column in the full trace. The run still prints Success at [4682]: the gate only filters what is written.

Exercise 2. Predict, then measure: how many MVMULs does the 64×64 matmul execute at HiFi2? What else changes?

The inner loop count is the fidelity value, 2, so each matmul_tiles MOP plays the 16-MVMUL replay twice: 8 × 2 × 16 = 256. Measured with MM_FIDELITY=2 MM_SEED=42: T1 MVMUL 256, total 586 executed instructions, PCC 0.9992975. Only MVMUL and SETRWC counts depend on fidelity, and nothing on T0 or T2 changes.

Exercise 3. The UNPACR stall in the add lasted exactly one round. What change to ttsim's clock loop would make it disappear, and why would that not be a hardware insight?

Visit the pipes in the order T1, T0, T2. Then T1's SETRWC would release the SrcA bank earlier in round 4390, and T0's UNPACR would succeed in the same round. (This is a prediction we did not run. The new order would also shift the rest of the schedule, for example by making each ELWADD see a fresh unpack one round later, so a one-round stall could reappear on T1 instead.) The stall exists because ttsim processes pipes in a fixed order within a round (libttsim.cpp, the pipe_mask loop). On silicon all three threads and the backend units run concurrently, with real latencies, and the question "did the release arrive before the unpack this cycle?" has a hardware answer that ttsim doesn't model. The robust fact is the condition: an UNPACR into a bank the FPU still owns must wait.

Exercise 4. Find the four SEMWAIT stalls on T2 in the matmul trace and explain why each is roughly the same length.

python3 b04_trace.py stream mm4.trace | grep stalled lists them: 256, 214, 226 and 214 rounds. Each output tile is Kt = 2 tile products, each 64 MVMULs (HiFi4) plus a stall on the first MVMUL while T0 unpacks the next pair, and MATH only posts MATH_PACK after both. PACK finishes its previous tile long before that, so it parks on the SEMWAIT for about one output tile's worth of MATH rounds. The four values differ by a few dozen rounds; we did not track down exactly which unpack or reader delays account for each difference.

Exercise 5. Decode 0xa2014080 by hand using tensix_isa.json, then check it against the trace.

Top byte 0xa2 = 162 = STALLWAIT. Its args are wait_res = bits 14:0 = 0x4080, and stall_res = bits 23:15 = 0x014080 >> 15 = 0x002. 0x4080 has bits 7 and 14 set: C7 (an instruction of this thread is in the FPU pipeline) and C14 (one is in the SFPU pipeline). Block mask 0x002 = B1, which blocks Sync-unit instructions. So: "don't let a semaphore instruction through until MATH and SFPU are idle". It is the first half of t6_semaphore_post<MATH | WAIT_SFPU>(MATH_PACK), and the trace shows it immediately before SEMPOST MATH_PACK (round 4398 → 4399). The script prints exactly "STALLWAIT until MATH+SFPU block=0x002".

Recap

  • Every Tensix instruction in ttsim executes in one place, tensix_decode_and_execute, called from the clock loop for the head of each thread's FIFO. A false return is a stall. Wrapping it with a gated fprintf gives a complete per-thread trace for one tile, and naming opcodes with data/wh/tensix_isa.json keeps the names identical to ttsim's decoder.
  • ttsim runs a busy tile for many rounds per clock and visits the pipes in the order T0, T1, T2. Rounds give an order and retry counts, not durations.
  • For one tile of add_2_integers_in_compute: BRISC's boot pushes (ZEROACC, SFPU setup, 4 SEMINITs), then about 100 configuration instructions, then the work: 8 UNPACR on T0, 8 ELWADD + 4 SETRWC on T1, 2 PACR on T2, joined by STALLWAITs and the MATH_PACK SEMPOST/SEMWAIT/SEMGET.
  • Each add_tiles thread body is one MOP: unpack = 2 × (A B A B) = 8, math = 4 × (ELWADD ELWADD SETRWC) = 12, pack = 1. Matmul nests MOP → REPLAY → MVMUL: one push becomes 16 × fidelity MVMULs (512 vs 128 for 8 tile products at HiFi4 vs LoFi). MATH pushed 96 instructions and executed 591.
  • The three stalls: UNPACR waits for its target bank to be released, FPU ops wait for both banks to be valid (hardware hand-off, no semaphore), and PACK's SEMWAIT waits for MATH's SEMPOST (software hand-off). Each released in the round its condition became true.
  • Fidelity changes only MVMUL (and a few SETRWC) counts. Most instructions are setup and synchronisation.

Check yourself

Why can't we use ttsim's clock number to order the instructions of add_tiles?

Because ttsim keeps clocking a tile repeatedly within one clock while it keeps executing Tensix instructions (the "hack" in clock_current_chip). All 33 rounds of the tile's work happened at clock 4531. A per-tile round counter, incremented on every pass, recovers the order. Neither number is a hardware cycle.

TRISC1 pushed zero ELWADDs, yet 8 executed. Where exactly were they created, and what decides how many?

In the MOP expander: mop_next walking mop_step_inst over the config words captured at mop_ingest. The count comes from the template the LLK programmed: outer = 4 (faces), inner = 2 (16 rows per face ÷ 8 rows per ELWADD), plus one SETRWC end op per face, giving 8 ELWADD + 4 SETRWC. The trace's M line shows outer=4 inner=2 end0=SETRWC.

The add needed a semaphore between MATH and PACK but none between UNPACK and MATH. What evidence of that is in the trace?

T1's first ELWADD stalled 269 rounds and executed in the round SrcA and SrcB became valid, with no Sync-unit instruction on T0 or T1 in between: the FPU's own valid-bit check is the hand-off. On the other side, T2's SEMWAIT MATH_PACK stalled 72 rounds and was released only by T1's SEMPOST in round 4399. Dst has no valid bits, so software provides them.

You switch a matmul from HiFi4 to LoFi. Which threads' instruction streams change?

Only T1's, and only in MVMUL (512 → 128 for our 8 tile products) and SETRWC (17 → 9). T0 and T2 execute identical counts of every opcode, and TRISC1 pushes the same 96 instructions. Fidelity is the inner loop count inside the MOP config (inner_loops = math_fidelity, llk_math_matmul.h:469).

The trace shows PACK waiting about 220 rounds per matmul output tile. Can you conclude the packer is a bottleneck-free unit on silicon?

No. ttsim isn't a timing model: rounds give each instruction one slot regardless of real latency, and MVMUL pipelining, unpacker throughput and packer write bandwidth aren't modelled. What you can conclude is the dependency structure: PACK can't start a tile until MATH posts MATH_PACK, and per output tile MATH executes 64× as many MVMULs (128) as PACK executes PACRs (2). Performance questions need silicon or a timing model.

Why does the post-processor decode MOP and REPLAY by hand instead of using their tensix_isa.json field ranges?

Because the JSON's ranges for those four frontend opcodes (MOP, NOP, MOP_CFG, REPLAY) are placeholders such as "len": "4:4". ttsim's generator skips them ("skip for now" in tensix_gen_decode.py), and the expanders decode them by hand: mop_ingest uses bits 15:0, 22:16 and 23, and replay_expander uses bits 0, 1, 13:4 and 23:14. Using the JSON would have reported every REPLAY length as 0 or 1.
