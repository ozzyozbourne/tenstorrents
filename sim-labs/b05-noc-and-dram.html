B05. NoC transactions, DRAM and the alignment trap

Make ttsim print every NoC transfer, watch A09's page interleaving happen one tile at a time, misalign a read and see two separate safety nets catch it, and then patch the simulator so that a missing barrier finally breaks a kernel.

Honesty banner. ttsim is a functional, bit-exact model of the chip. It is not a timing model. Every NoC transfer in stock ttsim completes inside the store instruction that starts it, so the bracketed clock numbers below say nothing about how long a transfer takes on silicon. The routes drawn in the first figure are what NoC 0 would do on a real Wormhole. They are computed from the coordinates ttsim logged, not measured. Section 5 changes the simulator on purpose to model one kind of delay. That patched ttsim is a teaching tool, not a timing model either.

The question

Take the loopback example's kernel. It copies 50 tiles from one DRAM buffer to another through a 2 KiB slot in L1, and after each read it calls noc_async_read_barrier(). Delete that one line and run it in ttsim. It passes. Run it again, and again: it passes every time, with exactly the same result.

Now add 4 to a destination address in a different kernel, so that a 4-byte DRAM read lands at l1 + 4. Nothing about the data is wrong. Every byte goes where you asked. ttsim stops dead with UndefinedBehavior.

So the simulator lets through a kernel that is genuinely broken, and refuses one that looks harmless. This lab explains both outcomes from ttsim's source. Along the way it turns the NoC from A08 and the interleaving from A09 into a log you can read line by line. By the end, a missing barrier will make a kernel fail, in a ttsim you patched yourself.

A08 already showed a NoC log from an instrumented ttsim. This lab builds a slightly different logger: the format is easier to parse, multicast receivers get their own lines, and it then puts the log to work. All commands below were run in this orb on the Wormhole model, and every output shown is real, trimmed only where marked.

1. Build a NoC-logging simulator

Every NoC transfer in ttsim passes through one function. A RISC-V core writes 1 into a command buffer's NOC_CMD_CTRL register, and ttsim's register handler calls noc_cmd_ctrl<tile_type>(tile_id, noc_instance, cmd_buf) (tile.cpp:1708-1717; A08 walks through it). The function runs from line 1397 to 1623. It reads the command buffer's registers, checks dozens of rules, translates coordinates, and then branches on the request kind. Just after translation, at line 1466, it knows everything we want to log:

  • noc_ctrl: the request bits (bit 5 multicast, bit 0 atomic, bit 3 inline, bit 1 write, otherwise read; bit 4 means non-posted, so an ack is expected);
  • src_coordinate, dst_coordinate: NoC 0 physical (x, y), packed as x | y << 6, already translated from whatever the kernel wrote;
  • dst_coordinate_start: the other corner of a multicast rectangle;
  • src_addr, dst_addr: the local addresses at each end, and noc_at_len_be: the length in bytes (for an atomic, the opcode).

Make an editable copy of ttsim and apply the patch:

$W/build_ttsim.sh noclog wh                 # first run copies ttsim to $LAB_HOME/ttsim-noclog
(cd $LAB_HOME/ttsim-noclog && patch -p1 < $P/b05-noclog.patch)
$W/build_ttsim.sh noclog wh                 # rebuild: about 1.5 s
export TT_METAL_SIMULATOR=$LAB_HOME/sim-noclog-wh-release/libttsim.so

What each piece does:

  • tile_to_coord(tile_type, tile_id) turns ttsim's internal tile index back into the NoC 0 position of the core that issued the command. A08's logger printed ttsim's tile number (T0); this one prints T(1,1), which you can find on the A03 map.
  • The kind chain tests the bits in the same order as the branches below it, so the label always matches the branch that will run. Multicast comes first because a multicast write also has the write bit set.
  • ttsim_printf prefixes the current simulator clock in brackets (common.cpp:24-31). The plain printf calls continue the same line.
  • ttsim sets src_addr from NOC_TARG_ADDR and dst_addr from NOC_RET_ADDR (tile.cpp:1436-1451). Because of the naming quirk from A08, TARG is where the data comes from for both reads and writes, so for a read "src" is the remote DRAM or L1 and "dst" is this core's L1, and for a write it is the other way round. Either way the log reads "from src to dst". Atomics and inline writes are the exceptions: ttsim calls the remote tile "src" for both (tile.cpp:1526, 1550).
  • The second hunk sits inside the multicast loop (tile.cpp:1498-1517), after ttsim has skipped columns and rows that the router configuration masks out, and after it has skipped the sender itself. So every recv line is a tile that really received the data.
Logging at one function is enough because ttsim has exactly one door for NoC traffic: the store to NOC_CMD_CTRL. Kernels, firmware and dispatch all go through it.

The kernel is short, and the log is that kernel unrolled:

The host creates two DRAM buffers of 50 bf16 tiles with page_size = 2048 and one 2 KiB L1 buffer, then runs the kernel on logical core (0,0) with NOC::RISCV_0_default (loopback.cpp:42-91). Read the log against that:

  • One core, one NoC. Every line has core=T(1,1) and noc=0. Logical (0,0) is NoC 0 tile (1,1) on ttsim's unharvested Wormhole (A09).
  • One L1 slot. Every read lands at 0x16d800 and every write leaves from it. That is the 2 KiB L1 buffer, allocated top-down just under 0x16E000, the top of the allocatable L1 (A09).
  • Strict alternation. READ, WRITE, READ, WRITE: 50 of each, because each barrier holds the core until the previous transfer has completed. In stock ttsim that wait takes no time at all. Section 5 returns to this.
  • Command buffers. Reads use buf=1 and writes buf=0, tt-metal's fixed assignment (A08). All are ack (non-posted), so the write barrier has acks to count.
  • Two bases. Reads start at 0x2d4c40 and writes at 0x2d7440. The output buffer was allocated after the input: ⌈50/12⌉ = 5 pages × 2048 B = 0x2800 later in every bank, which is A09's lockstep allocation.

Which bank, in what order?

The DRAM tiles in the log are (0,11), (0,1), (0,5), (0,7), (5,1), … and the addresses alternate between 0x2d… and 0x402d…. A09 says page p of an interleaved buffer lives in bank p mod 12, at row ⌊p/12⌋, and that odd Wormhole banks are the second 1 GiB view of a controller. Rather than check 100 lines by eye, check them with a script. noc_banks.py reads the bank table (tile and 1 GiB offset per bank) from the same soc_descriptor sections the allocator uses, maps every DRAM end in the log to a bank, and tests the rule:

Three things to take from the table. First, 50 = 4 × 12 + 2, so banks 0 and 1 get a fifth page and the others get four. Every bank still reserves five page slots (the 0x2800 gap between the two buffers), which is A09's lockstep cost. Second, the bank order is exactly the table A09 printed from the allocator: bank 0 is tile (0,11) at +0, bank 1 is (0,1) at +1 GiB, and so on. Third, banks 0 and 1 are the same controller and the same memory: ttsim keeps one 2 GiB array per controller (config.h:14,35), and the +1 GiB simply indexes its upper half (tile.cpp:2785-2786). The log shows the address the kernel computed. The bank number is the allocator's bookkeeping, and the script recovers it from the (tile, half) pair.

The figure replays the captured log. The 100 transfers, their clock stamps, tiles and addresses are embedded in the page exactly as logged. Each packet is drawn on the route NoC 0 would use on silicon (right first, then down, wrapping at the edges, as in A08), and the hop count is computed from that rule. The bars accumulate bytes per bank.

Step through the first dozen transfers and two patterns appear. The reads sweep the banks 0 → 11 and the writes follow them one step behind, so every bank sees one read and one write per pass. And the hop counts are very uneven. Bank 1's data, at (0,1), is 1 hop from core (1,1). Bank 0's data at (0,11) is 3 hops. Every write to the x = 0 column has to go right all the way round the ring (9 hops of x, then 10 of y for (0,11)): 19 hops. Interleaving spreads load evenly across the banks, but it cannot make them all close. That is A09's point, now visible packet by packet.

The bracketed clocks step by about 20 between a read and its write and about 36 between iterations. That is the simulator's step count for the RISC-V code between the stores: address arithmetic, the barrier's single poll of the counter, and the loop. It is not a transfer time. On silicon a 2 KiB read from 3 hops away is at least about 100 NoC cycles (A08's derivation), and the barrier would spin for all of them.

  1. The read fetches the tile from bank 0, tile (0,11), at 0x3ffff800: just under the top of the 1 GiB bank. This example allocates its buffers with .bottom_up = false (multicast.cpp:47), so they come from the top of DRAM, unlike the default bottom-up DRAM allocation in A09. The output buffer of three pages lands at 0x3ffff000 in banks 0 and 2, and at 0x7ffff000 (+1 GiB) in bank 1.
  2. Three atomics are the receivers saying "ready". Each runs noc_semaphore_inc(remote_sender_semaphore_noc_addr, 1) in inbound_kernel.cpp. ttsim's atomic branch calls the remote end "src", so src=T(1,1):0x8a90 is the sender's semaphore. dst=…:0x4 is where the old value would be returned in the issuing core's L1. op=4220 is 0x107C, the increment opcode, the only one ttsim implements (tile.cpp:1528). The three arrive in the order 4, 3, 2 because the receivers are separate cores, and ttsim happened to clock them in that order.
  3. The tile multicast. One command from T(1,1), command buffer 0, 2048 B, with the rectangle (2,1)–(4,1). ttsim's loop (tile.cpp:1498-1517) writes the same bytes to each tile in the rectangle, so we get three recv lines. The dst field holds the far corner (4,1), because a multicast address packs both corners into the coordinate bits (tile.cpp:1454-1457).
  4. The flag multicast. The sender sets its own copy of the receiver semaphore to VALID, then multicasts those 4 bytes to the same rectangle through command buffer 2, the buffer tt-metal reserves for small register-sized writes. The receivers spin in noc_semaphore_wait(receiver_addr_ptr, VALID) and then continue.
  5. Three writes on NoC 1. Each receiver's outbound kernel runs on the second data-movement core with NOC::RISCV_1_default (multicast.cpp:209-212). Receiver T(2,1) writes page 0, T(3,1) page 1 and T(4,1) page 2, which land in banks 0, 1 and 2: the interleaving rule again.

Now count acknowledgements. A non-posted multicast to three receivers bumps niu_mst_wr_ack_received three times in ttsim (once per receiver, tile.cpp:1511-1514), and tt-metal's software counter for noc_async_write_barrier was raised by num_dests = 3 when the multicast was issued (A08). Pass the wrong num_dests and the two counts never match. Too large a value hangs the barrier, even in ttsim. That is one of the few NoC bugs ttsim can show you, because it comes from counting, not from timing.

A GPU has nothing quite like this. Broadcasting a value to many SMs means writing it to global memory and letting each SM read it, perhaps through L2. Here one packet is copied by the routers into each receiver's private memory, and a second tiny multicast tells them it has arrived. A16 builds the same pattern up into a full multicast matmul.
On Wormhole, ttsim refuses a multicast without path reservation (tile.cpp:1421-1423). It also refuses one whose rectangle contains a non-Tensix tile (tile.cpp:1506). Try a rectangle that crosses the DRAM column at x = 5 and ttsim stops with UnimplementedFunctionality, which is ttsim's way of saying "real hardware would skip that tile, and I don't model that".

4. The alignment trap, caught twice

The rule

A NoC transfer does not copy bytes one at a time. It moves 16- or 32-byte chunks, and a chunk read at the source is written as a chunk at the destination. So the two ends must sit at the same offset within a chunk. The ISA documentation gives the exact table for requests whose NOC_AT_LEN_BE holds a length:

tt-isa-documentation/WormholeB0/NoC/Alignment.md:14-27
||Data to MMIO address|Data to L1 address|Data to other address|Data to host via PCIe|
|**Data from MMIO address**|AL=4|AL≤4 and C4|AL≤4 and C4|AL≤4|
|**Data from L1 address**|AL=4 and C16|C16|C16|Any|
|**Data from other address**|AL=4 and C16|C32|C32|Any|
...
* **C16:** The two addresses must be congruent mod 16, i.e. `SrcAddress % 16 == DstAddress % 16`.
* **C32:** The two addresses must be congruent mod 32, i.e. `SrcAddress % 32 == DstAddress % 32`.

"Other address" means a DRAM tile, PCIe or ARC. So a DRAM → L1 read must be C32, and anything from L1 must be C16. The document opens with: "Violations of the alignment requirements result in UndefinedBehavior" (line 8). The hardware does not raise an error. It just does something unspecified. The allocator pads every page to 32 B on Wormhole precisely so that normal code never comes near this rule (A09).

The DRAM case is C32 on Wormhole (& 31, line 1610) and C64 on Blackhole (& 63, line 1607), where the DRAM alignment is 64 B. Writes check C16 at line 1589. When a check fails, ttsim_error prints the category and the message, flushes stdout and calls _Exit(1) (common.cpp:33-45). The process ends there, with no unwinding and no chance for tt-metal to react.

Spring the trap

Use the smallest kernel that reads DRAM: add_2_integers_in_riscv, which reads two 4-byte integers. The overlay patch moves the first read's destination 4 bytes up:

Watcher and ttsim are two independent checks of the same ISA rule, placed at two different points. The trap is easy to set by accident. Any hand-computed L1 offset that is not a multiple of 32 (a 4-byte header in front of a tile, a struct field, a stick of 2 bf16 values) misaligns a DRAM read on Wormhole, and on Blackhole the step is 64 B. On silicon with Watcher off, nothing tells you.

Why it passes: the counter moves inside the store

Look again at the last two lines of ttsim's read branch above:

tile_rd_bytes is a memcpy out of the DRAM array (tile.cpp:2769-2786). The firmware counts what it issued (noc_reads_num_issued) and spins until the NIU's hardware counter reaches the same value. ttsim answers that counter read from the field it has already incremented (tile.cpp:1354). In stock ttsim the two counts are always equal by the time anyone looks, so the barrier's loop body never runs and removing it changes nothing about the data. The bug is real. ttsim's model has no window in which it could show.

On silicon there is a window. The read request travels to the DRAM tile, the controller fetches the data, and 65 flits come back over the NoC, while the RISC-V core keeps executing. A08 estimated about 100 NoC cycles for exactly this read with no congestion, and DRAM latency and traffic only add to that. The write that follows reads the L1 slot through the NIU when it is issued. If the response has not landed yet, the write ships the previous tile, or whatever was in that L1 before. Worse, whether it does depends on traffic, so the kernel might pass a thousand times and then fail in production.

The edge is sharp and the log explains it. Without the barrier, each write is issued exactly 18 clocks after its read (4373 → 4391). If the data is due on clock 4391 or earlier, completion runs at the top of that clock and the write copies the right bytes. If it is due on 4392, the write wins the race. On this simulator the race window is 18 clocks, roughly the instructions between the two stores. On silicon there is no fixed number. It is "DRAM latency plus NoC latency, versus however fast your code reaches the next use", and that changes with traffic, placement and the compiler.

A barrier is not a performance hint. It is the only thing that turns "I asked for the data" into "the data is here". ttsim completes transfers instantly, so it proves your kernel is correct if transfers were instant, which is a weaker claim than "correct".

It passes, and the reason is in the code. The delay is inserted by the sanitizer macro before the request is issued (debug_insert_delay at sanitize.h:951, which runs riscv_wait on the wall clock). 6. Optional: running off the end of DRAM

ttsim also checks the size of the memory a transfer touches. Every DRAM access in tile_rd_bytes and tile_wr_bytes passes through:

ttsim/src/tile.cpp:2785, 2832 @b3620244
        TTSIM_VERIFY(addr + size <= DRAM_CHANNEL_SIZE, UndefinedBehavior, "DRAM read overrun");
        TTSIM_VERIFY(addr + size <= DRAM_CHANNEL_SIZE, UndefinedBehavior, "DRAM write overrun");

DRAM_CHANNEL_SIZE is 2 GiB per controller on Wormhole (config.h:35), matching the ISA's map: 0x0_0000_0000–0x0_7FFF_FFFF is GDDR6 channels 0 and 1, and 0x0_8000_0000 upwards is reserved (WormholeB0/DRAMTile/README.md:40-42). The overlay b05-overrun-kernel.patch aims the first read of add_2_integers_in_riscv at the last 32 bytes of the controller and asks for 64:

+    src0_dram_noc_addr = (src0_dram_noc_addr & ~0xFFFFFFFFull) | 0x7FFFFFE0;  // B05: last 32 B of the 2 GiB controller ...
-    noc_async_read(src0_dram_noc_addr, src0_l1, sizeof(uint32_t));
+    noc_async_read(src0_dram_noc_addr, src0_l1 - 32, 64);  // B05: ... and read 64 B, running 32 B past its end

The destination is src0_l1 - 32 because src0_l1 is 0x16dfe0, the last 32 bytes of the allocatable L1. My first try, reading 64 B into src0_l1 itself, ran off the top of L1 first, and both layers reported that instead (ttsim: UnsupportedFunctionality: noc_cmd_ctrl: read: dst_addr=0x16dfe0; Watcher: "Local L1 address overflow"). With the fix:

$EX/metal_example_add_2_integers_in_riscv
[4343] ERROR: UndefinedBehavior: tile_rd_bytes: DRAM read overrun

TT_METAL_WATCHER=1 $EX/metal_example_add_2_integers_in_riscv
[6584] ERROR: UndefinedBehavior: tile_rd_bytes: DRAM read overrun
real	0m7.665s

This time Watcher lets it through and only ttsim catches it. Watcher's DRAM check compares against core_info->noc_dram_addr_end (sanitize.h:250-263), which the host fills from soc_d.dram_core_size (risc_firmware_initializer.cpp:929-930), defined as num_dram_views_in_descriptor * dram_view_size (metal_soc_descriptor.cpp:375): 12 × 1 GiB = 12 GiB. That is the size of the whole chip's DRAM, used as the bound for an address on one DRAM tile, which can only hold 2 GiB. An address of 0x8000_0000 is reserved on a Wormhole DRAM tile but passes Watcher's check. I found no comment in tt-metal explaining the choice; it looks like a deliberately loose bound rather than a model of one tile. So the two layers are not nested: each catches things the other misses.

7. Exercises, with answers

E1. Predict the DRAM tile and NoC address of page 37's read in the loopback log, then find the line.

Bank = 37 mod 12 = 1, row = ⌊37/12⌋ = 3. Bank 1 is tile (0,1) at +1 GiB. Address = 0x2d4c40 + 3 × 0x800 + 0x40000000 = 0x402d6440. The log has [6445] NOCLOG READ … src=D(0,1):0x402d6440: the 75th line overall, page 37's read. noc_banks.py checks the same arithmetic for all 50 pages at once.

E2. Misalign loopback instead (l1_buffer_addr + 4 in noc_async_read_page). ttsim reports UnsupportedFunctionality: noc_cmd_ctrl: read: dst_addr=0x16d804, not an alignment error. Why?

The read branch checks the destination range before the alignment (tile.cpp:1602 comes before 1610). 0x16d804 + 2048 = 0x16e004, past the 0x16e000 end of L1, because loopback's L1 buffer sits right at the top. Checks fire in source order, so the first rule broken is the one reported. A 4-byte read (as in add_2) isolates the alignment rule.

E3. In section 4, change the offset from +4 to +16, then to +32. Predict, then run.

+16: 0x16dff0 & 31 = 16 ≠ 0, so it still breaks C32. Measured: [4343] ERROR: UndefinedBehavior: … dst_addr=0x16dff0 does not match. A +16 offset would be legal for an L1 → L1 read (C16), so this is the DRAM-specific rule. +32: aligned, but 0x16e000 is one byte past the end of L1. Measured: UnsupportedFunctionality: noc_cmd_ctrl: read: dst_addr=0x16e000. Had the buffer been lower in L1, +32 would pass both checks and the add would simply use the wrong data: perfectly aligned, still a bug.

E4. In the multicast run, how many times does the sender's NIU_MST_WR_ACK_RECEIVED go up, and what must the firmware's count be for the final noc_async_write_barrier() to return?

Two non-posted multicasts × 3 receivers = 6 increments in ttsim's multicast loop (tile.cpp:1511-1514). The firmware adds num_dests per multicast, so 3 + 3 = 6 (the 4-byte semaphore multicast is counted the same way). The barrier compares the two. If num_dests were 4, the software count would be 8, the hardware count would stop at 6, and the barrier would spin forever, even in ttsim.

E5. Extend b05-delay-reads.patch to delay writes too (data copy and niu_mst_wr_ack_received). Which barrier in loopback now becomes necessary, and what failure would removing it cause?

I have not run this one; this is the expected result. With writes delayed, noc_async_write_barrier() is what keeps the next iteration's read from overwriting the L1 slot before the delayed write has copied it. Remove it and the read for page i+1 lands while write i is still pending, so DRAM receives tile i+1 in tile i's slot. One subtlety: in this simple model the copy happens at completion time. Real hardware reads the source L1 as the request's data flits leave, which is earlier than the ack, so the barrier is conservative. That is why tt-metal also has noc_async_writes_flushed() (data sent) as a cheaper alternative to the full ack barrier.

E6. Why does Watcher catch the misaligned read but not the DRAM overrun, while ttsim catches both?

Watcher's alignment check uses the exact per-target rule (NOC_DRAM_READ_ALIGNMENT_BYTES = 32), but its DRAM range check uses a whole-chip bound (12 views × 1 GiB = 12 GiB) rather than the 2 GiB a single DRAM tile exposes. ttsim stores DRAM per controller (DRAM_CHANNEL_SIZE = 2 GiB) and checks each access against that. A write-up of this mismatch would be a reasonable issue to file upstream.

Recap

  • All NoC traffic in ttsim passes through noc_cmd_ctrl (tile.cpp:1397-1623), entered from the store to NOC_CMD_CTRL. One printf after coordinate translation logs every transfer's kind, NoC, core, ends, addresses, length and multicast rectangle.
  • Loopback's 100 transfers alternate READ/WRITE on NoC 0 from core (1,1). Pages go to bank p mod 12 at row ⌊p/12⌋ for all 50 pages, banks 0–1 get five pages and 2–11 four, and odd banks appear as +1 GiB addresses on the controller's second tile.
  • The multicast example is a read, three semaphore atomics, a 2 KiB multicast to rectangle (2,1)–(4,1) with three receivers, a 4-byte flag multicast, and three NoC 1 writes back to DRAM. Ack counts scale with the number of receivers.
  • Alignment is an ISA rule (C16 from L1, C32 from DRAM on Wormhole, 64 B on Blackhole), and violating it is undefined behaviour. With Watcher on, the kernel's own sanitizer catches it before the request is issued and the host reports it. Without Watcher, ttsim's model of the NIU catches it as UndefinedBehavior and exits. On silicon without Watcher, nothing catches it.
  • Stock ttsim completes each transfer, data and counter, inside the issuing store, so every barrier is already satisfied and a missing barrier cannot fail. Delaying read completion by 19 or more clocks in a patched ttsim makes the barrier-less loopback fail; 18 or less passes, because the write follows its read by exactly 18 clocks.
  • Watcher's debug delays slow the core before a request, so they cannot expose a request-to-completion race in ttsim. Watcher's DRAM range check uses a 12 GiB bound and misses an overrun of a 2 GiB tile that ttsim catches.

Check yourself

1. A colleague's kernel passes in ttsim with Watcher on. Name two kinds of NoC bug it could still contain on silicon.

Races that depend on timing: missing or misplaced barriers (section 5), and ordering between NoC 0 and NoC 1, or between VCs, which ttsim cannot reorder because every transfer is instant (A08). Also anything Watcher checks loosely, such as DRAM addresses below 12 GiB but beyond one tile's 2 GiB (section 6), if the code was never also run without Watcher on ttsim.

2. Why does the Watcher run print no NOCLOG line for the misaligned read, even though the logging ttsim was loaded?

The sanitizer runs before ncrisc_noc_fast_read and parks the core in while (1), so the store to NOC_CMD_CTRL never happens and noc_cmd_ctrl is never called. The logger lives in noc_cmd_ctrl.

3. In stock ttsim, what value does the barrier's first read of NIU_MST_RD_RESP_RECEIVED return, relative to noc_reads_num_issued?

Exactly equal. ttsim incremented niu_mst_rd_resp_received inside the issuing store (tile.cpp:1621), and the firmware incremented its count right after that store (noc_nonblocking_api.h:449-451). The loop condition is false on the first test.

4. Why is the race threshold in section 5 exactly 18/19 clocks, and why is that number meaningless for silicon?

The log shows each write issued 18 ttsim clocks after its read, and the patch completes due reads at the start of a clock, before cores step. A read due at +18 is in L1 when the write executes at +18; one due at +19 is not. The 18 counts simulator steps of the RISC-V code between two stores. Silicon's window is set by DRAM and NoC latency and traffic, which ttsim does not model.

5. Bank 1's tile (0,1) is 1 NoC 0 hop from core (1,1) for read data, but writes to it take far more. How many, and why?

A write from (1,1) to (0,1) carries its data on the request leg, from the core to the DRAM tile. NoC 0 only goes right and down: x from 1 to 0 wraps through 2…9, which is 9 hops, and y does not change. So 9 hops, against 1 hop for read data coming from (0,1) to (1,1). Using NoC 1 for the write would make it 1 hop, which is why the convention puts writers on NoC 1 (A08). Loopback uses NoC 0 for both.
