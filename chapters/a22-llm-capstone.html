The question

Tenstorrent's own performance table lists Llama-3.1-8B on a single Wormhole n150 at 28.3 tokens per second per user in its performance configuration (models/tt_transformers/PERF.md:27). That is about 35 ms per token. In those 35 ms the chip does roughly 15 billion floating-point operations: two per weight, for about 7.5 billion weights. At the HiFi2 rate from A20, 131 TFLOP/s on 64 cores, that arithmetic takes about 0.1 ms. So where do the other 34.9 ms go?

Count bytes instead of FLOPs. In that configuration the MLP's W1 and W3 weights are stored in bfp4 (bfp8 in the last layer) and the rest in bfp8, which comes to about 6.1 GB (derived here from the model's shapes and the formats' bytes per tile, not a published figure). To produce one token the chip has to stream all 6.1 GB out of DRAM, because every layer's weights are needed and together they are about sixty times larger than the roughly 100 MB of L1 on the chip's Tensix cores. At the 240 GB/s that a DRAM-sharded matmul reaches on Wormhole (tech_reports/LLMs/llms.md:1845), that takes at least 25 ms (again derived, a lower bound). The measured 35 ms is within a factor of 1.4 of that.

Why does generating one token take about as long as reading every weight once? And if the time goes into reading weights, why does Tenstorrent's report say batching 32 users is nearly free, while prefilling a 128-token prompt (a TTFT of 104 ms in the same table) costs only three decode steps' worth of time for 128 tokens' worth of work? This chapter answers both questions by following one token through the real code in models/tt_transformers at commit 7aad8aac. Every piece is something you have already met in A05–A21. Here they all run together.

An LLM in inference is two programs. Prefill pushes a whole prompt through the model at once. It is a big matmul and is compute-bound. Decode pushes one token per user through the model. It is a skinny matmul, so it is DRAM-bound, and almost every optimization in tt_transformers exists to cut weight bytes or to hide everything that is not a weight read.

A transformer in one page

Here is a decoder-only transformer such as Llama in small numbers. The token "cat" becomes integer 9031. The embedding table turns that integer into a row of d numbers (d = 4096 for Llama-3.1-8B). That row, called the residual stream, then passes through 32 identical decoder layers. Each layer reads the stream and adds a correction to it:

h = x + Attention(RMSNorm(x))        # look at earlier tokens
y = h + MLP(RMSNorm(h))              # think about this token alone
MLP(z) = W2 · ( SiLU(W1 · z) * (W3 · z) )

Attention is the only place where tokens talk to each other. The layer multiplies the normalized stream by three matrices to get a query q, a key k and a value v for each head. It rotates q and k by an angle that depends on the token's position (RoPE). It then compares this token's q with the k of every earlier token, turns the scores into weights with a softmax, and takes the weighted sum of their v's. Llama uses grouped-query attention, so 32 query heads share 8 key/value heads (model_params/Llama-3.1-8B-Instruct/config.json). After the last layer, a final RMSNorm and the LM head, a 4096 × 128,256 matmul, give one score (logit) per vocabulary word. A sampler then picks the next token.

Notice what generating a second token needs. Its attention compares against the k and v of every earlier token, but those were already computed when the earlier tokens went through the model. If you keep them, you never compute them again. That stash is the KV cache, and it is why inference splits in two:

  • Prefill processes the user's whole prompt in one pass: S tokens through every matmul at once. It fills the KV cache and produces the first new token.
  • Decode then produces one token per user per step. Each step runs the new token through the whole model, appends its k and v to the cache, and reads all the cached ones.

The LLM tech report puts the practical consequence in one table: prefill handles one user and a long sequence with activations in DRAM, while decode handles up to 32 users with one token each and activations in L1 (llms.md:1227-1236). The rest of this chapter is about why.

Three things stand out once you step through both modes.

First, in decode the activations never touch DRAM. The residual stream is width-sharded across 32 cores as one tile row of 32 users (model_config.py:1352-1382), and each op hands the next one a tensor already sharded the way it wants. The report's advice is blunt: avoid "unnecessary ShardedToInterleaved and InterleavedToSharded calls" (llms.md:1860). This is A09's sharding and A20's "activations already in L1" checkbox, applied to a whole model. The only DRAM reads are the weights (orange banks) and the KV cache.

Second, the weights are spread over the DRAM banks, not interleaved. create_dram_sharded_mem_config width-shards each weight across the 12 Wormhole DRAM banks (8 on a p150, 7 on a p100), padding N so that it divides evenly:

tt-metal/models/tt_transformers/tt/model_config.py:3760-3768 @7aad8aac (trimmed)
def create_dram_sharded_mem_config(self, k, n, dram_grid=None):
    dram_cores = self.dram_grid_size.x  # WH has 12 dram cores, P150 has 8, P100 has 7
    padded_size = math.ceil(n / (ttnn.TILE_SIZE * dram_cores)) * (ttnn.TILE_SIZE * dram_cores)
    ...
    shard_spec = ttnn.ShardSpec(dram_grid, (k, padded_size // dram_cores), ttnn.ShardOrientation.ROW_MAJOR)
    return ttnn.MemoryConfig(ttnn.TensorMemoryLayout.WIDTH_SHARDED, ttnn.BufferType.DRAM, shard_spec)

Each bank then holds a contiguous strip of K × (N/12), and the matmul places one reader core next to each bank, so no two banks' traffic shares a NoC route. That is the difference between the ≈190 GB/s an interleaved matmul reads and the ≈240 GB/s a DRAM-sharded one reads (llms.md:1844-1845). It is A08's routing and A20's "the routes cross" wall, fixed at the level of data layout.

Third, the MLP is one fused eltwise op between three matmuls. SiLU is a transcendental and runs on the SFPU (A07), but it is passed as an input activation of the multiply, so the gate tensor is read once and both operations happen in the same kernel:

tt-metal/models/tt_transformers/tt/mlp.py:318-324 @7aad8aac (comments added)
w2_in = ttnn.mul(
    w1_out,
    w3_out,
    input_tensor_a_activations=[self.activation_type],   # SILU unless the model overrides it
    dtype=activation_dtype or ttnn.bfloat8_b,             # the product is stored in bfp8
    memory_config=w1_out.memory_config(),                 # stays width-sharded in L1
)
On a GPU the same layer would keep activations in registers and shared memory inside each fused kernel, and rely on L2 between kernels. Here there is no L2: "stays in L1 between ops" is a layout decision you write into every op's memory_config. If two neighbouring ops disagree about the sharding, a reshard op appears between them, and it costs time just like an extra kernel launch on a GPU.

Who chooses the formats: the model config

Every dtype and fidelity in Figure 1 comes from one place: ModelOptimizations in model_config.py. It groups tensors (TensorGroup: FF1_FF3, FF2, WQKV, WO, KV_CACHE, ACTIVATION) and ops (OpGroup: LI_FF1_FF3, LI_QKV_DECODE, SDPA_PREFILL and so on) and assigns each a precision and a fidelity (model_config.py:79-108). The defaults are:

tt-metal/models/tt_transformers/tt/model_config.py:397-426 @7aad8aac (trimmed)
def _default_settings(self):
    """Default is BFP8/HIFI2 everywhere, activation follows input type (usually BF16)
    Only exceptions:
    - SDPA runs in HIFI4 during prefill (still HIFI2 during decode)
    """
    "TensorPrecision": {
        TensorGroup.FF1_FF3: PrecisionSetting.BFP8,  TensorGroup.FF2: PrecisionSetting.BFP8,
        TensorGroup.WQKV: PrecisionSetting.BFP8,     TensorGroup.WO: PrecisionSetting.BFP8,
        TensorGroup.KV_CACHE: PrecisionSetting.BFP8, TensorGroup.ACTIVATION: None,

    "OpFidelity": {
        OpGroup.LI_FF1_FF3: MathFidelitySetting.HIFI2_FP16,   # "BFP8 with FP16 accumulation to save L1"
        OpGroup.LI_FF2: MathFidelitySetting.HIFI2_FP16,
        OpGroup.LI_QKV_DECODE: MathFidelitySetting.HIFI2,  OpGroup.SDPA_DECODE: MathFidelitySetting.HIFI2,
        OpGroup.LI_O_DECODE: MathFidelitySetting.HIFI2,    OpGroup.LI_QKV_PREFILL: MathFidelitySetting.HIFI2,

        OpGroup.LI_O_PREFILL: MathFidelitySetting.HIFI2,   # FP32 accumulate is important here

The performance() preset changes exactly one thing for most models: FF1 and FF3 drop to bfp4 with LoFi (model_config.py:335-338). The accuracy() preset keeps bfp8 for Llama 3, Mistral-7B and Phi-3-mini, because these "test insensitive to attention precision". Other models get bf16 attention weights and KV cache at HiFi4 (model_config.py:254-301). Qwen2.5-7B is degraded by the performance settings, so it gets bf16 attention there too (model_config.py:313-332). Per-layer overrides also exist: Llama-3.1-8B keeps its last layer's FF1/FF3 in bfp8 (model_params/Llama-3.1-8B-Instruct/performance_decoder_config.json, as PERF.md:13-15 says).

This is the precision ladder from A05, A06 and A20 made concrete. The format and the fidelity move together, as the report's rule of thumb says: "Use HiFi4 for BF16 weights … HiFi2 for BFP8 weights … LoFi for BFP4 weights" (llms.md:1885-1887). The reason is A06's multiplier. A bfp4 mantissa fits in the first fidelity phase, so the extra phases would multiply bits that do not exist. The names map onto real compute kernel configs:

"Which accuracy is enough" is measured, not assumed. The report's targets are PCC ≈ 0.999 for MLP and attention submodules, ≈ 0.998 for a decoder layer and ≈ 0.99 for the whole model, followed by top-1/top-5 token accuracy and perplexity on real data (llms.md:1665-1667). This chapter's simulator run shows why PCC alone is not enough. A layer at PCC 0.9967 still flipped one user's next token, because that user's top two logits were 2.522 and 2.508.

Prefill vs decode on the roofline

Now the opening puzzle can be answered with A20's tool. A matmul's intensity is FLOPs per DRAM byte. For a layer weight of K × N, one pass with M rows of activation does 2·M·K·N FLOPs and must read K·N weights. If the activations stay in L1, that gives

intensity ≈ 2·M ÷ (bytes per weight)

In decode, M is the number of users. In prefill, M is the number of prompt tokens. The formula is the same and only M changes. With bfp8 weights (1088 bytes per 1024-value tile, so about 1.06 bytes per weight) and 32 users, the intensity is 60 FLOP/B, which is exactly A20's decode limit for bfp8. The Wormhole ridge at HiFi2 is 131 TFLOP/s ÷ 288 GB/s ≈ 455 FLOP/B. Decode at batch 32 sits 7.6× to its left, deep in DRAM-bound territory. A 2048-token prefill sits around 3,900 FLOP/B, 8.5× to its right, and is compute-bound. Drag the sliders.

Figure 2. Llama-3.1-8B (7.5 billion weights, embedding excluded) on one Wormhole n150. Compute roofs come from A20's table for the 64 cores a matmul can get. Memory slopes are the 288 GB/s spec and the ≈240 GB/s a DRAM-sharded matmul measures (llms.md:1845). "perf mix" is bfp4 FF1/FF3 plus bfp8 everywhere else, about 0.81 bytes per weight. The step times assume perfect overlap and ignore KV-cache reads, op-to-op gaps and the host. They are lower bounds, not predictions.

The figure explains several design choices at once:

  • Batching decode is nearly free until B·2 / (bytes per weight) reaches the ridge. That point is about 290 users for bfp8 at HiFi2 on the 240 GB/s line (ridge ≈ 546 FLOP/B), well beyond the cap of 32. The report says the same in words: "LLM inference is bound by time to read model weights from DRAM. Batching allows model weight reuse across multiple sequences" (llms.md:1110-1118). The Short-Context, Batch-32 table shows the cost: Llama-3.1-8B on N150 drops from 28.3 to 22.3 tok/s per user while serving 32× as many users (PERF.md:163).
  • Lower fidelity does nothing for decode. Switch HiFi2 to LoFi with B = 32. The roof doubles and the pink dot does not move. The win in the "perf" preset comes from bfp4 bytes, not from LoFi math. LoFi is used because extra phases on 4-bit mantissas are useless, and because a HiFi4 DRAM-sharded decode matmul "would be FLOP-bound on 12 cores" (comments at attention.py:871-872 and mlp.py:197-198).
  • Prefill wants big matmuls and high fidelity where it matters. It is compute-bound, so fidelity sets its speed. That is why SDPA keeps HiFi4 only in prefill, and why prefill uses 2D multicast matmuls (A16) on the full grid: "Use matmul 2D for all matmuls in prefill mode" (llms.md:1536).
  • Short prompts are not yet compute-bound. A 128-token prompt with bfp8 weights sits at about 240 FLOP/B, still left of the ridge, so even this prefill is close to the memory line. The measured 104 ms TTFT covers 128 tokens, while one decode step (35 ms) covers one token per user. Per token, prefill is about 40× cheaper.
The 25 ms lower bound is not reached, and the gap is real. The KV cache is also read each decode step (next section). Some ops (norms, heads, concat) are pure latency. Dispatch adds a gap between every pair of ops. And PERF.md itself is marked "DEPRECATED. PLEASE CHECK THE YAML FILE models/model_targets.yaml" (PERF.md:1), so treat its figures as illustrative at this commit, not as a specification.

The KV cache, in pages

How big is the cache? Each layer stores k and v for 8 KV heads of 128 values each, so 2 × 8 × 128 = 2048 values per token per layer, or 65,536 per token over 32 layers. In bfp8 that is about 70 KB per token. One user with an 8K context holds 570 MB. Thirty-two users at a 1K context hold 2.3 GB, and decode reads all of it every step, as much as a third of the weight bytes. This is why the KV cache defaults to bfp8 (TensorGroup.KV_CACHE above), and why GQA's 8 KV heads instead of 32 matter four times over.

Where should that cache live? A plain tensor of shape [users, heads, max_seq_len, head_dim] reserves the worst case for every user. The paged layout from vLLM (Kwon et al., 2023) splits it into fixed-size blocks and keeps a per-user page table that maps "my block 3" to "physical block 41". tt_transformers adopts it directly. The cache tensor is [max_num_blocks, n_kv_heads, block_size, head_dim] in DRAM (attention.py:550-565), the demo uses block_size 32 (simple_text_demo.py:351), and the page table is an int32 tensor on the device. With 32-token blocks, each block of one head is exactly one tile tall (A05). The animation below replays this chapter's simulator run, then continues it to show how the cache grows.

Flash decode splits each (user, KV head) pair's cached K/V into chunks across several cores, each computing a partial softmax, and then reduces the partials over the NoC. That is A16's semaphores at work. Past 16 cores per head, "the NOC bandwidth between cores will bottleneck" (llms.md:582). Positions can differ per user, which is what continuous batching needs (llms.md:1454).

"Page" now has a third meaning. In A09 a page is the unit a buffer is interleaved in, one tile for TILE layout. Here a KV block is 32 token rows per head, and the page table maps a user's virtual blocks to physical ones. The kernels reach a physical block by indexing an ordinary interleaved DRAM tensor, so a KV block is itself made of several A09 pages (one tile per head). And "sharding" means both "split across cores" and "split across chips" (llms.md:1849-1850).

Trace: taking the host out of decode

A decode step of Llama-3.1-8B is dozens of ops per layer times 32 layers, and many of them run for only microseconds. The report shows an untraced profile where "more time (756us) is spent in between OPs (OP-to-OP gap) than running OPs on device (362us)" (llms.md:1813). The Python thread, the host API, and the command bytes over PCIe (stages 1–3 of the report's five) cannot keep up with the device.

This is exactly A17's trace. Record the whole decode step's commands into a DRAM trace buffer once, then replay them with a single command. The catch is equally from A17: "You cannot allocate or deallocate tensors during a trace. When executing a trace every buffer will be the same size every time" (llms.md:1468). Decode was designed to make that true. The batch is always padded to 32 rows. The KV cache is preallocated. The page table and positions are device tensors whose contents change while their addresses stay fixed. And the sampled token is written into the input buffer of the next step. The generator does exactly this:

tt-metal/models/tt_transformers/tt/generator.py:2488-2512, 2669-2670 @7aad8aac (trimmed, comment added)
trace_id = ttnn.begin_trace_capture(self.model_args[i].mesh_device, cq_id=0)
...
tt_out_trace.append(self.model[i].ttnn_decode_forward(*model_inputs, kv_cache=user_kv_cache,
                                                      on_device_logits=on_device_sampling))
ttnn.end_trace_capture(self.model_args[i].mesh_device, trace_id, cq_id=0)
...
# every later step: copy new host inputs into the same device tensors, then
for i, trace_id in self.trace_ids_decode[on_device_sampling].items():
    ttnn.execute_trace(self.model_args[i].mesh_device, trace_id, cq_id=0, blocking=False)

With tracing, the op-to-op gap typically drops "below 6us" (llms.md:1826). The report's other host-side advice follows from A17 as well: embed on the device (token ids are tiny), return only the last token from prefill, sample on the device, and never tilize or untilize on the host (llms.md:1747-1760). On-device sampling is a top-k over the gathered logits followed by ttnn.sampling with per-user k, p and temperature tensors (tt_sampling.py:1421-1429), so the trace can include it and feed the token straight back.

This chapter's a22_trace_decode_mlp.py captures a decode MLP as a trace under ttsim and replays it three times with new inputs; the last replay is bit-identical to an eager run on the same input (output below). Trace needs fast dispatch, as A17 found. A17 covers the dispatch modes, and lab B09 covers what ttsim can and cannot see.

Many chips: one layer split in two

A 70B model's weights (about 70 GB in bfp8) do not fit in one Wormhole's 12 GB, and even 8B decodes faster when two chips each read half the bytes: 44.2 tok/s on N300 against 28.3 on N150 (PERF.md:27-28). A21 built the tools. Here is how tt_transformers uses them for one layer on a 1×2 mesh.

Figure 4. One Llama-3.1-8B decoder layer, tensor-parallel on an N300 (two chips), decode with 32 users. The scheme is the report's table: QKV and FF1/FF3 column-parallel, WO and FF2 row-parallel (llms.md:1419-1430). Collective sizes are for bf16 activations of 32 × 4096.

On a T3K (8 chips in a ring) the same layer is used. When the ring and shapes allow it, the attention output's all-gather is fused into the WO matmul with all_gather_matmul_async, so communication overlaps compute (attention.py:1054-1072, enabled by model_config.py:873-879). On a Galaxy (8×4) the weights are split in 2-D, with partial sums reduced along one axis and gathered along the other (llms.md:769-790). Collectives are costed exactly as in A21. The report's advice to "try using bfp8 inputs instead of bf16" for them is the same byte-counting lever as bfp4 weights, now on the Ethernet wall (llms.md:1862).

The two-device mesh that does run under ttsim (wh_x2 with the N300 cluster descriptor) is covered in A21 and lab B10. A21 found that with stock tt-metal the fabric-enabled collectives do not complete in the simulator (B10 gets a two-chip all_gather through only with a kernel overlay), so this chapter's runs are single-chip.

1. A tiny Llama layer from TT-NN ops

a22_decoder_layer.py builds a Llama-shaped layer with random weights: d = 384, 12 query heads, 6 KV heads of 32, MLP width 768, vocabulary 768. Every width divides evenly over the 12 DRAM banks. The script uses the same ops, memory configs and format choices as Figure 1, plus the real RotarySetup from tt_transformers. It prefills two users (64 and 32 tokens) one at a time into a paged bfp8 KV cache, runs the final norm, the LM head on the last tile and ttnn.argmax on device, then runs one batched decode step with width-sharded activations and DRAM-sharded matmuls. Read it top to bottom and you can see the chapter. Prefill lives in DRAM and decode in L1. The weights are bfp8 or bfp4 while activations stay bf16, and the SiLU product drops to bfp8 as mlp.py:322 says. The paged cache wrote into exactly the blocks the page table names. The (1, 2, 6, 32) rows of K went to the L1 of one core per user. Decode reproduces the reference's next token for both users. The paged decode attention read K/V rows from shuffled blocks and still gave PCC 0.9965.

Now look at user 1's prefill. The layer output has PCC 0.9967, but the device picked token 690 where PyTorch picked 270. The reference's top two logits were 2.522 and 2.508, within 0.6% of each other, and bfp4 MLP weights moved them by more than that. The --precision bf16 run (bf16 weights and cache, HiFi4 everywhere) is the top of the ladder:

This is why tt_transformers measures top-1 and top-5 token accuracy, not just PCC. A random-weight toy has much flatter logits than a trained model. That is also why PERF.md's Llama-3.1-8B top-1 drops only from 96% to 90% between the accuracy and performance configs (PERF.md:27,82), rather than collapsing.

Two things in this script are not the stock configs. Both work around ways in which Wormhole ttsim stops on the FP32 unpack path, found while building it:

  • FP32 Dst accumulation does not run on Wormhole ttsim. Any kernel built with fp32_dest_acc_en=True stopped the simulator. Default, 1D and 2D matmuls stopped with UndefinedBehavior: tensix_unpacr: unpack_to_dst=0 in_data_format=0 out_data_format=0. The DRAM-sharded matmul stopped with UnsupportedFunctionality: tensix_unpacr: cfg_context_id=1. The same matmuls with FP16 Dst pass. The first error is the one lab B08 traces to its source, and it is not a ttsim bug. After the last unpack straight into Dst, the Wormhole LLK deliberately issues one dummy unpack into SrcA to work around a hardware bug (TEN-3868, tt_llk_wormhole_b0/common/inc/cunpack_common.h:981-983). That dummy unpack keeps the FP32 → FP32 formats of the unpack-to-Dst setup, a combination the ISA does not define for SrcA, and ttsim strictly rejects it as undefined behaviour (tensix.cpp:3456-3458). The same instruction carries the current unpack config context in its CfgContextId field, and ttsim does not model a non-zero config context at all (tensix.cpp:3165), which is the second error. A ttsim that skips only that dummy unpack (lab B11's b11-ten3868.patch) runs both the DRAM-sharded and the 1D matmul with FP32 Dst, so both errors come from it. Silicon runs these kernels. tt_transformers' HIFI2 and HIFI4 configs turn FP32 Dst on, so the script turns it off everywhere and says so in a comment.
  • Converting float32 to bf16 on the device does not run either. ttnn.from_torch(float32_tensor, dtype=bfloat16, mesh_mapper=…), which is what RotarySetup does, stops with the same in_data_format=0 (Float32) error. It is the same unpack-to-Dst path that B08 hits with ttnn.typecast from FP32. Without a mesh mapper, or with a bf16 host tensor, it works. The script casts on the host first. The values are identical.

One host-side error is worth knowing too. Prefill matmuls with DRAM-sharded weights and no program config fail validation with TT_FATAL … DFB 'in1' borrows memory from TensorParameter 'in1', but its TensorSpec is not L1-resident. The default program choice assumed an L1 weight. tt_transformers always passes an explicit program config, and so does the script (a matmul-2D config, llms.md:1532-1556).

A last disagreement is about the hardware itself. Wormhole DRAM bandwidth is quoted as 288 GB/s in some places and 336 GB/s in others. The 192-bit GDDR6 bus gives 288 GB/s at 12 GT/s and 336 GB/s at 14 GT/s, and older spec pages listed 14 GT/s (see A03). The current n150 spec (docs.tenstorrent.com: 12 GT/s, 288 GB/s), the ISA documentation (WormholeB0/DRAMTile/README.md, "Performance": 12 channels × 24 GB/s) and the FlashAttention tech report all say 288 GB/s. This chapter uses 288 GB/s as the spec and the report's measured 240 GB/s for DRAM-sharded reads.

Recap

  • A decoder layer is two RMSNorms, four matmul groups (QKV, WO, W1/W3, W2), RoPE, attention over a KV cache, one fused SiLU multiply and two residual adds. tt_transformers maps each to one or two TT-NN ops.
  • Prefill is one user and S tokens: activations in DRAM, 2D multicast matmuls, causal flash attention at HiFi4, compute-bound once S is a few hundred.
  • Decode is up to 32 users and one token each: activations width-sharded in L1, DRAM-sharded weight reads from all 12 banks, flash decode over a paged cache. It is DRAM-bound with intensity ≈ 2B ÷ bytes-per-weight, so one step costs about one read of all the weights.
  • The levers for decode are bytes: bfp8 everywhere, bfp4 in the MLP, a bfp8 KV cache, GQA, more chips. Fidelity follows the format (HiFi4 bf16, HiFi2 bfp8, LoFi bfp4) and matters for compute-bound prefill.
  • The paged KV cache is [blocks, kv_heads, 32, head_dim] plus a device page table. Positions and page tables are tensors, so decode is shape-static and can be traced, which removes the host from the loop.
  • Across chips: column-parallel then row-parallel, one reduce-scatter and one all-gather per block, costed in link bytes.
  • Under ttsim the real Llama-3.2-1B block runs a decode step at PCC 0.9995 with FP16 Dst. On Wormhole ttsim, FP32 Dst accumulation is the blocker for stock configs: an LLK hardware workaround that ttsim strictly rejects (B08), not a fault in the kernels.

Check yourself

Llama-3.1-8B on an n150 in the performance config decodes at 28.3 tok/s/user at batch 1. Roughly what would you expect at batch 2, and why?

Almost the same, about 28 tok/s per user and therefore nearly double the total. A decode step is bounded by reading ≈6.1 GB of weights (≈25 ms at 240 GB/s), and that read is shared by all users in the batch. The math for 2 users is about 0.2 ms at HiFi2, far below the read. In fact the device already pads the batch to a 32-row tile (tile_padded_batch_rows), so batch 1 and batch 2 run the identical matmul. The Batch-32 table shows the per-user rate dropping only to 22.3, from KV-cache reads and other per-user work.

Switching w1/w3 from HiFi2 to LoFi while keeping bfp8 weights: does decode get faster? Does prefill?

Decode barely changes. It is DRAM-bound, so a higher compute roof does not move the point (Figure 2). Prefill is compute-bound for prompts of a few hundred tokens or more, so its MLP matmuls would get up to 2× faster, at the cost of dropping mantissa bits that bfp8 actually has. That is why the performance preset pairs LoFi with bfp4, where the dropped bits do not exist, and why the decode win comes from bfp4's bytes rather than LoFi.

Why does tt_transformers pass the current position as a device tensor (cur_pos_tensor) rather than a Python list?

Because decode is traced. A trace replays recorded commands against fixed buffers, and runtime values baked in from a Python list would be frozen into the trace. A device tensor's contents can change every step (the host copies new values in, or a device op increments it) while its address stays the same, so the traced paged_update_cache and SDPA ops read the new positions (llms.md:586-588). The page table and the input token buffer follow the same rule.

With block_size 32 and the run's page table [[7, 5, 3, 2], [4, 6, 1, 0]], where does user 1's token at position 70 go?

70 ÷ 32 = 2 remainder 6, so virtual block 2, row 6. User 1's virtual block 2 is physical block 1. The K rows go into physical block 1, row 6, for each of that layer's KV heads.

A layer test passes at PCC 0.9967, but the model's top-1 accuracy drops. How can both be true, and what does the report recommend measuring?

PCC measures how well the whole output vector correlates. A token choice depends only on the order of the top logits, and when two are close (2.522 vs 2.508 in this chapter's run), a tiny error flips it. The report tests bottom-up: submodule PCC ≈ 0.999, decoder ≈ 0.998, model ≈ 0.99, then top-1/top-5 token accuracy and perplexity on a dataset (llms.md:1655-1667). If those fail, move the sensitive groups (often attention, or one layer's MLP) up the precision ladder.

On an N300, why does tt_transformers make QKV column-parallel and WO row-parallel instead of the reverse?

Column-parallel QKV splits by heads, and attention is independent per head, so each chip can run its heads and keep its share of the KV cache with no communication. Row-parallel WO then consumes exactly that head-split output and produces partial sums, so the whole attention block needs one reduction (a reduce-scatter, then the all-gather inside the next norm). The reverse would need the activations gathered before attention and again after.
