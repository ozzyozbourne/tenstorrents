The question

In A12 we wrote compute kernels as if add_tiles were an instruction. It sits inside the loop of the eltwise_binary example like this:

tt-metal/tt_metal/programming_examples/eltwise_binary/kernels/compute/tiles_add.cpp:41-43 @7aad8aac
        tile_regs_acquire();
        // Add the tiles from the input circular buffers and write the result to the destination register
        add_tiles(cb_in0, cb_in1, 0, 0, dst_reg);
add_tiles is one line. How many hardware instructions is it?

Make a guess before reading on. One, because the FPU has an ELWADD instruction? 1024, one per element? Something in between?

Here's a hint from A04 and A06. One ELWADD adds an 8-row by 16-column block, which is 128 numbers. A 32×32 tile is 1024 numbers, so the arithmetic alone takes 1024 / 128 = 8 ELWADDs. The data also has to get into SrcA and SrcB first, and the unpackers move one 16×16 face per instruction, so that's 4 faces × 2 operands = 8 UNPACRs. Sixteen instructions do real work. Then there's bookkeeping: address counters, semaphores, register hand-offs.

The surprising part isn't the total. It's that the RISC-V cores push only a handful of those instructions. Most of them are generated inside the coprocessor by a small loop machine called the MOP expander, which an earlier add_init call programmed. The animation below zooms in on one call. Every name and count in it comes from the real code and from a trace I took in ttsim (shown later).

Two things in that picture are worth keeping. The shape of the work (4 faces, 2 row-blocks each, 2 operands) was decided by an init call and stored in hardware, not in the per-tile code. And the RISC-V side of add_tiles on the MATH core is three pushes, whatever the tile size. That's why TRISC1 gets away with a ½ KiB instruction cache (A04).

A compute-API call compiles to a few RISC-V instructions that push a few Tensix instructions. One of them is usually MOP, and the MOP expander inside the coprocessor turns it into the long, regular instruction stream the engines need. The init call is what programs that expansion.

Three layers between you and the hardware

Between add_tiles and the .ttinsn words in the binary are three layers of header-only C++. Each one is a different team's contract.

"LLK" stands for low-level kernel. tt-llk is also published as its own repository (tenstorrent/tt-llk) and vendored into tt-metal, and its functions follow a naming convention you can grep for: a leading and trailing underscore, _llk_…_.

Layer 1: the compute API

tt-metal/tt_metal/hw/inc/api/compute/eltwise_binary.h:265-275 @7aad8aac

    std::uint32_t icb0, std::uint32_t icb1, std::uint32_t itile0, std::uint32_t itile1, std::uint32_t idst) {
    UNPACK((llk_unpack_AB(icb0, icb1, itile0, itile1)));
    MATH((llk_math_eltwise_binary<
          EltwiseBinaryType::ELWADD,
          BroadcastType::NONE,
          is_fp32_dest_acc_en,

}

ALWI means "always inline". There's no function call at runtime, so the whole chain collapses into straight-line code in each TRISC binary. Notice that MathFidelity::LoFi is hard-coded: addition doesn't need multiplier phases (A06), whatever ComputeConfig says.

That's the whole per-tile math path: point the Dst write address at tile dst_index, run the MOP, reset the Dst counter. set_dst_write_addr ends in TT_SETC16(DEST_TARGET_REG_CFG_MATH_Offset_ADDR32, dst_index) and clear_dst_reg_addr is TTI_SETRWC(p_setrwc::CLR_NONE, 0, 0, 0, 0, p_setrwc::SET_D) (cmath_common.h:260-288). Three pushes, as in the animation.

On a GPU the closest thing is a library like CUTLASS: templates that pick tile shapes and emit mma instructions. The difference is where the loop lives. A CUTLASS mainloop is unrolled into the instruction stream the SM fetches. An LLK loop over faces is written once into the MOP expander's registers, and from then on the coprocessor generates it from a single MOP instruction.

What a Tensix instruction looks like

Every Tensix instruction is a 32-bit word with the opcode in the top byte and operands packed into the low 24 bits. tt-llk spells this out with one macro per instruction, generated from the ISA description:

tt-metal/tt_metal/tt-llk/tt_llk_wormhole_b0/common/inc/ckernel_ops.h:12-13,24,161-162,167,260,263 @7aad8aac
#define TT_INSN(ENCODING)  __builtin_rvtt_ttinsn(::ckernel::instrn_buffer, (ENCODING), 0, 0, 0)
#define TTI_INSN(ENCODING) __builtin_rvtt_ttinsn(nullptr, (ENCODING), 0, 0, 0)

#define TT_OP(opcode, params) ((opcode << 24) + params)

#define TT_OP_ELWADD(clear_dvalid, dest_accum_en, instr_mod19, addr_mode, dst) \
    TT_OP(0x28, (((clear_dvalid) << 22) + ((dest_accum_en) << 21) + ((instr_mod19) << 19) + ((addr_mode) << 15) + ((dst) << 0)))
#define TTI_ELWADD(clear_dvalid, dest_accum_en, instr_mod19, addr_mode, dst) TTI_INSN(TT_OP_ELWADD(...))

#define TT_OP_MOP(mop_type, loop_count, zmask_lo16)    TT_OP(0x01, (((mop_type) << 23) + ((loop_count) << 16) + ((zmask_lo16) << 0)))
#define TTI_MOP(mop_type, loop_count, zmask_lo16)      TTI_INSN(TT_OP_MOP(mop_type, loop_count, zmask_lo16))

There are three name patterns for each instruction:

  • TT_OP_X(...) is just the number. The LLK uses it when it needs an instruction as data, for example to store into a MOP template.
  • TTI_X(...) ("immediate") pushes an instruction whose operands are all compile-time constants. The SFPI compiler turns __builtin_rvtt_ttinsn(nullptr, …) into one 32-bit .ttinsn RISC-V instruction: the Tensix word rotated left by two bits, which the core recognises because its low bits aren't 11. A04 walks through that rotation.
  • TT_X(...) pushes an instruction with runtime operands. The compiler builds the word in a register and stores it with an ordinary sw to instrn_buffer (0xFFE40000).

The builtin only exists when compiling for a TRISC. ckernel_ops.h:7 checks __riscv_xtttensixwh, and anything else gets an .error "TTI_INSN in non-tensix code". I checked which flag defines it: riscv-tt-elf-g++ -mcpu=tt-wh-tensix -dM -E prints #define __riscv_xtttensixwh 1000000, and -mcpu=tt-wh (the BRISC/NCRISC flag) doesn't.

The widget below uses real words from the JIT-compiled trisc1.elf of eltwise_binary. Pick one to see the stored word, the rotation back, and the fields as ttsim decodes them from its data/wh/tensix_isa.json.

The ELWADD that MATH actually executes is the plain constant 0x28000000: clear_dvalid 0, no accumulation, address mode 0, dst 0. The destination row isn't in the instruction. It comes from the Dst read/write counter (RWC), which address mode 0 advances by 8 rows after each ELWADD (eltwise_binary_configure_addrmod, llk_math_eltwise_binary.h:44-49). Eight identical instruction words can therefore write eight different 8-row blocks. A loop machine that can only repeat fixed words needs exactly this property.

Names differ between sources. tt-llk's TT_SETDMAREG (opcode 0x45) is SETGPR in ttsim's tensix_isa.json. The ISA docs also use SETDMAREG. Match on opcode numbers, not names, when you move between tt-metal, ttsim and the ISA docs.

Init functions write a loop into hardware

The MOP expander is a generator with nine 32-bit configuration registers per thread. TT-LLK wraps them in a small class whose comment is the best one-glance description of the hardware:

tt-metal/tt_metal/tt-llk/tt_llk_wormhole_b0/common/inc/ckernel_template.h:16-26 @7aad8aac
    // Here is the basic outline of a MOP loop and the definition of the
    // variables used.
    // LOOP_OUTER: <OUTER_LOOP_COUNT>
    //   START_OP
    //   LOOP_INNER: <INNER_LOOP_COUNT>
    //     LOOP_OP0
    //     LOOP_OP1
    //   END_LOOP_INNER
    //   END_OP0
    //   END_OP1
    // END_LOOP_OUTER

An analogy: a knitting pattern. "*Knit 2, purl 1; repeat from * 4 times; on the last repeat, end with knit 3." The pattern is short, the row is long, and the knitter never improvises. The analogy breaks in one useful place. A knitter can look at the wool. The MOP expander never looks at data, flags or registers, so it can't branch. All it can do is emit fixed words in a fixed order, with two special cases for the last iteration.

For add_tiles the math init builds this template:

tt-metal/tt_metal/tt-llk/tt_llk_wormhole_b0/llk_lib/llk_math_eltwise_binary.h:123-131,141-151 @7aad8aac (comments trimmed)
    const std::uint8_t innerloop = tensor_shape.face_r_dim > MAX_FPU_ROWS ? (tensor_shape.face_r_dim >> MAX_FPU_ROWS_LOG2) : 1;
    const std::uint32_t outerloop = (bcast_type == BroadcastType::COL) ? num_faces_c_dim : num_faces;
    ...
    if constexpr ((eltwise_binary_type == EltwiseBinaryType::ELWADD) || (eltwise_binary_type == EltwiseBinaryType::ELWSUB))
    {
        ckernel_template tmp(outerloop, innerloop, eltwise_binary_func<eltwise_binary_type>(0 /*clr_src*/, acc_to_dest, broadcast_type, addr_mod));
        if (tensor_shape.face_r_dim <= MAX_FPU_ROWS)
        {
            tmp.set_loop_op1(TT_OP_INCRWC(0, MAX_FPU_ROWS, MAX_FPU_ROWS, MAX_FPU_ROWS));
        }
        tmp.set_end_op(TT_OP_SETRWC(CLR_SRC, p_setrwc::CR_AB, 0, 0, 0, p_setrwc::SET_AB));
        tmp.program();
    }

With the default tile (face_r_dim 16, 4 faces, MAX_FPU_ROWS = 8), that's outer = 4 (one per face) and inner = 16 / 8 = 2 (two 8-row ELWADDs per face). The end op SETRWC(CLR_AB, CR_AB, …, SET_AB) runs once per face. Per the ISA's SETRWC functional model, it rewinds the SrcA/SrcB row counters and flips both Src banks back to the unpackers, so the next face can be unpacked. It leaves the Dst counter alone, so Dst keeps advancing: 8 ELWADDs × 8 rows = 64 rows, one 32×32 tile.

program() is where the template reaches hardware:

tt-metal/tt_metal/tt-llk/tt_llk_wormhole_b0/common/inc/ckernel_template.h:320-340 @7aad8aac
inline void ckernel_template::run()
{
    TTI_MOP(1, 0, 0); // run the double-loop template
}

inline void ckernel_template::program()
{
    volatile std::uint32_t *mop_cfg = reinterpret_cast<volatile std::uint32_t *>(TENSIX_MOP_CFG_BASE);

    mop_sync(); // wait until previous mops have completed

    mop_cfg[0] = m_outer_loop_len;
    mop_cfg[1] = m_inner_loop_len;
    mop_cfg[2] = m_start_op0;
    mop_cfg[3] = m_end_op0;
    mop_cfg[4] = m_end_op1;
    mop_cfg[5] = m_loop_op0;
    mop_cfg[6] = m_loop_op1;
    mop_cfg[7] = m_loop0_last_instr;
    mop_cfg[8] = m_loop1_last_instr;
}

TENSIX_MOP_CFG_BASE is 0xFFB80000 (hw/inc/internal/tt-1xx/wormhole/tensix.h:72). Per the ISA docs, each TRISC sees its own thread's nine registers at that address, and the range is write-only: reading it is UndefinedBehavior. mop_sync() is a store to pc_buf_base[2] (ckernel.h:237-240), the RISCV TTSync mechanism that waits for in-flight expansions to finish. The ISA page says why: hardware samples the configuration during expansion, so overwriting it mid-MOP changes a loop that's already running.

Nine stores, all with constants. The C++ template machinery is gone, leaving exactly the data the hardware needs. Both "last" slots hold the same ELWADD because the one-op constructor copies loop_op into them (ckernel_template.h:252-263). The ELWMUL path at higher fidelity puts different instructions there, as the next figure shows.

The unpack side does the same thing on TRISC0 with two loop ops: ckernel_template tmp(num_faces_r_dim, num_faces_c_dim, unpack_srca, unpack_srcb), which is outer 2 × inner 2 for a 2×2-face tile (llk_unpack_AB.h:129-131). When LoopOp1 isn't a NOP, the expander alternates between the two ops and doubles the inner count. That's where the "A, B, A, B" pattern comes from.

The MOP expander, step by step

The ISA documentation gives the expander's behaviour as a Python generator. For template 1, the double loop that ckernel_template uses:

tt-isa-documentation/WormholeB0/TensixTile/TensixCoprocessor/MOPExpander.md:69-105 @be83310 (Blackhole branch and hardware-bug corner case elided)
    OuterCount = MopCfg[0] & 127
    InnerCount = MopCfg[1] & 127
  StartOp    = MopCfg[2]
  EndOp0     = MopCfg[3]
  EndOp1     = MopCfg[4]
  LoopOp     = MopCfg[5]
  LoopOp1    = MopCfg[6]
  Loop0Last  = MopCfg[7] # Overrides LoopOp or LoopOp1 on last iteration of inner loop, if also last iteration of outer loop
  Loop1Last  = MopCfg[8] # Overrides LoopOp or LoopOp1 on last iteration of inner loop, if not last iteration of outer loop
  if IsNop(LoopOp1):
    LoopOpFlip = 0
  else:
    LoopOpFlip = LoopOp ^ LoopOp1 # Inner loop will alternate between the two instructions and will
    InnerCount *= 2               # execute for twice as many iterations.
  ...
  for j in range(OuterCount):
    if not IsNop(StartOp):
      yield StartOp
    for i in range(InnerCount):
      if i != InnerCount-1:
        yield LoopOp
      elif j != OuterCount-1:
        yield Loop1Last
      else:
        yield Loop0Last
      LoopOp ^= LoopOpFlip
    if not IsNop(EndOp0):
      yield EndOp0
      if not IsNop(EndOp1):
        yield EndOp1

Two small tricks are worth noticing. Alternation is an XOR: LoopOpFlip holds the bits where the two ops differ, so XORing toggles between them with no extra state. And NOP (opcode 0x02) means "absent" for the start and end slots, so one fixed-size register file can describe loops with or without prologue and epilogue.

Step through it. The presets are the real configurations from tt-llk. The first two match what ttsim logged for add_tiles.

Some numbers fall straight out of the model. On Wormhole both counts are 7-bit, so the longest possible expansion is 127 outer iterations × (StartOp + 2 × 127 alternating inner ops + EndOp0 + EndOp1) = 127 × 257 = 32,639 instructions, the figure the ISA page quotes. The expander emits one instruction per cycle, and its control flow is "effectively free". There is a one-cycle penalty when the instruction after a MOP isn't another MOP, and the docs suggest hiding it by having the expansion contain a REPLAY (MOPExpander.md:131-137). That's one reason the matmul preset looks the way it does.

There's also a template 0, selected by MOP bit 23 = 0. It's a single loop of up to 128 iterations that picks, per iteration, between an "unpack" sequence (InsnA0, optionally A1–A3 and InsnB) and a "skip" sequence, driven by a 32-bit zero-mask. It's built for sparse unpacking: skip tiles known to be zero. tt-llk wraps it as ckernel_unpack_template (ckernel_template.h:65-118,348-358), and MOP_CFG supplies the mask's upper 16 bits.

ttsim is stricter than the ISA here. For template 1 on Wormhole, ttsim's mop_ingest rejects OuterCount outside 1–32 with UnimplementedFunctionality and InnerCount outside 1–127 with UnsupportedFunctionality (tensix.cpp:144-145), and template 0 with a loop_count above 31, that is more than 32 iterations (UnsupportedFunctionality, tensix.cpp:131; the ISA allows 128). The ISA allows outer counts up to 127. Every real tt-llk template I traced stays well inside ttsim's limits, but a hand-written MOP with a large outer count would stop the simulator, not the silicon.

Eighteen RISC-V instructions per tile on TRISC1. Eight of them push to the coprocessor: six .ttinsn words and two sw stores. The only FPU-related pushes in add_tiles are ttmop and ttsetrwc; the eight ELWADDs that do the arithmetic never appear in the RISC-V binary. The SETC16 value alternates between 0 and 512 rows (0xb2010000 / 0xb2010200 in the trace below) because of the double-buffered Dst from A12: MATH writes one half while PACK drains the other.

This is also why the init call is not optional. The MOP configuration is one global register file per thread, and every init writes all nine words. Call mul_init and then add_tiles, and the MATH thread happily expands the multiply template: ELWMULs, with the multiply's address modes. There's no error. The LLK can't detect it, and the hardware can't either, because the expander doesn't know what the template "should" be.

Init calls aren't one-time setup. Each one replaces the per-thread MOP template, address modes and some configuration. If a kernel alternates operations (add, then exp, then add), call the matching init before each switch. Debug builds have some checks: the eltwise path asserts on a leaked zero-flag state (llk_math_eltwise_binary.h:684-687, only under LLK asserts). Nothing checks that the MOP matches the operation you meant.

The replay buffer

The MOP template can only repeat two loop ops plus a few fixed extras. A matmul tile needs 16 MVMULs that differ in their address-mode bits (A06 tabulated them). That's a straight-line sequence, not a loop body. The replay expander, the next frontend stage after the MOP expander, handles it. Each thread has a 32-entry buffer of instruction words, and one instruction, REPLAY, either records the next N incoming instructions into it or plays N of them back:

tt-isa-documentation/WormholeB0/TensixTile/TensixCoprocessor/REPLAY.md:42-53 @be83310
    if Instruction.Load:
      Exec = Instruction.Exec
      for i in range(Count):
        Instruction = await GetNextIncomingInstruction()
        if Instruction.Opcode == REPLAY:
          UndefinedBehavior() # A REPLAY cannot be one of the instructions loaded
        ReplayBuffer[(Index + i) % 32] = Instruction
        if Exec:
          yield Instruction
    else:
      for i in range(Count):
        yield ReplayBuffer[(Index + i) % 32]

tt-llk exposes it through lltt, a tiny header that ships with the SFPI compiler (runtime/sfpi/include/lltt.h). lltt::record(start, len) emits a REPLAY with Load set, and lltt::replay_insn(start, len) builds a playback REPLAY word as data, for use inside a MOP template. Matmul combines them:

tt-metal/tt_metal/tt-llk/tt_llk_wormhole_b0/llk_lib/llk_math_matmul.h:361-364,469-470 @7aad8aac
    const std::uint32_t replay_buf_len =
        (is_in0_16x32 && is_in1_32x16) ? 4 : ((is_in0_16x32 || is_in1_32x16 || is_in0_32x16 || is_in1_16x32) ? (partial_face ? 4 : 8) : 16);

    lltt::record(ckernel::math::replay_buf_offset, replay_buf_len);
    ...
    constexpr std::uint32_t inner_loops = high_fidelity ? to_underlying(math_fidelity) : 1;
    ckernel_template tmp(1 /* outer loop */, inner_loops, lltt::replay_insn(ckernel::math::replay_buf_offset, replay_buf_len));

replay_buf_offset is 16, with the comment "split replay buffer usage between fpu/sfpu" (cmath_common.h:30). By convention, the FPU's recorded sequences go in slots 16–31 and SFPU code can use 0–15. The order of the two expanders matters. Because the replay expander comes after the MOP expander, a MOP can emit REPLAYs ("loop this recorded sequence 4 times, once per fidelity phase"), but a recorded sequence can't contain a MOP or another REPLAY. ttsim enforces the second rule: "nested REPLAY instruction loaded inside a REPLAY buffer" is UndefinedBehavior (tensix.cpp:65-66).

CUDA Graphs record a sequence of kernel launches once and replay it cheaply. The replay buffer does the same at the level of individual instructions inside one core: record once at init, then play back for every tile with a one-word command. The scale is very different (32 words, not a DAG of kernels), but the reason is the same: the thing issuing commands is slower than the thing executing them.

The JIT: from .cpp to L1

So far the binary has just been there. Where did trisc1.elf come from? Not from tt-metal's build: the example binary metal_example_eltwise_binary contains no device code. CreateKernel(program, "…/tiles_add.cpp", core, ComputeConfig{…}) only records a path and some options. The first time the program is enqueued, tt-metal compiles the kernel at run time, on the host, with a RISC-V cross-compiler, and caches the result. Three things make this worth the complexity:

  • One source, three binaries. A compute kernel becomes three programs, one each for TRISC0/1/2, distinguished by #defines (A12).
  • Specialisation. Compile-time args, defines, CB data formats, math fidelity and Dst mode all become constants. That's how add_init compiled into nine constant stores instead of a table lookup.
  • Freedom to change kernels without rebuilding tt-metal. The kernel overlay in the workbench depends on it.

Step 1: find the file

A relative kernel path is resolved in a fixed order:

tt-metal/tt_metal/impl/kernels/kernel.cpp:48-95 @7aad8aac (bodies condensed)
// If the path is not an absolute path, then it must be resolved relative to:
// 1. CWD
// 2. TT_METAL_KERNEL_PATH
// 3. System Kernel Directory
// 4. TT_METAL_HOME / SetRootDir (API)
fs::path resolve_path(const fs::path& given_file_name, ContextId context_id) {
    if (given_file_name.is_absolute()) { return given_file_name; }                 // Priority 0
    ... fs::current_path() / given_file_name ...                                    // Priority 1
    if (rtoptions.is_kernel_dir_specified()) { ... get_kernel_dir() / given_file_name ... }  // Priority 2
    ... get_system_kernel_dir() / given_file_name ...                               // Priority 3
    ... get_root_dir() / given_file_name ...                                        // Priority 4
    TT_THROW("Kernel file {} doesn't exist in any of the searched paths!", given_file_name);
}
The current directory wins over everything except an absolute path. Run an example from $TT_METAL_HOME and the stock kernel under tt_metal/programming_examples/… is found at priority 1, so your overlay in TT_METAL_KERNEL_PATH is silently ignored. That's why the workbench's env.sh changes into $LAB_HOME/run.

Several details are worth a closer look:

  • -mcpu comes from the HAL. On Wormhole, compute processors get -mcpu=tt-wh-tensix and everything else gets -mcpu=tt-wh (llrt/hal/tt-1xx/wormhole/wh_hal.cpp:185-189). Blackhole uses tt-bh-tensix/tt-bh. Only the -tensix variant defines __riscv_xtttensixwh, which turns on .ttinsn.
  • Optimisation level defaults to O3 for ComputeConfig and O2 for data-movement configs (api/tt-metalium/kernel_types.hpp:83,133). Firmware is built separately at -Os for BRISC/NCRISC and -O3 for TRISCs (from the same log).
  • -flto plus the pch.h force-include: link-time optimisation strips unreachable code, which is how a header-heavy LLK ends up as 716 bytes of text, and a precompiled header keeps compiles fast.
  • -DKERNEL_COMPILE_TIME_ARGS carries compile_args. The compute kernel here has none, but the reader does. From the same log, its BRISC compile has -O2 -mcpu=tt-wh -DKERNEL_COMPILE_TIME_ARGS=2,2048,2,2048: two TensorAccessorArgs, each contributing two words. The define is generated at jit_build/build.cpp:1225-1230, and get_compile_time_arg_val(i) indexes into it.

Step 4: link and load

Each processor's object is linked with kernel_trisc1.ld (or _trisc0, _brisc, …; wh_hal.cpp:207-218) and -Wl,--just-symbols=…/firmware/trisc1/trisc1_weakened.elf. The kernel doesn't carry its own copy of the firmware. It resolves symbols against the already-loaded firmware image, which is built once per build key into the same cache. At load time tt-metal applies an "execute in place" transform so the text can run wherever it's placed (llrt/tt_memory.cpp:33-46, which also writes the .xip.elf you'll see in the cache). In slow dispatch it then writes the binary into L1 at the kernel-config base plus a per-processor kernel_text_offset (impl/program/slow_dispatch.cpp:47-62, hw/inc/hostdev/dev_msgs.h:181-182). The launch message tells each TRISC's firmware where its kernel text starts.

The kernel cache

The cache root is ~/.cache/tt-metal-cache/, or /tmp/tt-metal-cache/ if $HOME isn't usable (build.cpp:192-199). Under it, the layout has two levels of hashing:

<root>/<build_key>/firmware/{brisc,ncrisc,trisc0,trisc1,trisc2,erisc,idle_erisc}/
<root>/<build_key>/kernels/<kernel name>/<kernel hash>/{brisc|ncrisc|trisc0..2}/…elf
  • The build key hashes the whole environment: a per-device build key passed in by the caller, the architecture, all common compile and link flags and defines, and the compiler's version string (build.cpp:539-558). Upgrade SFPI, or turn on Watcher (which adds defines), and you get a fresh tree.
  • The kernel hash is KernelCompileHash(build_key, hlk_desc, kernel->compute_hash()) (impl/program/kernel_compile_utils.cpp:23-31). The directory name is kernel->name() + "/" + hash (program.cpp:3275-3278).
tt-metal/tt_metal/impl/kernels/kernel.cpp:832-848 @7aad8aac (end of Kernel::compute_hash)
    hasher.update(this->kernel_src_.source_);
    hasher.update(this->compile_time_args_.begin(), this->compile_time_args_.end());
    ...
    hasher.update(this->config_hash());

    // Include paths affect compilation: the gcc -I order is significant (left-to-right
    // header resolution), so different lists or orderings must produce different binaries.
    // Header contents are tracked separately via the per-object .dephash mechanism.
    size_t num_include_paths = 0;
    this->process_include_paths([&](const std::string& path) {
        hasher.update(path);

Read that carefully, because it isn't what the workbench README suggests. source_ is the caller-supplied path string, not the file's contents (kernel.cpp:134: "Keep source_ as the caller-supplied path (metadata/watcher/hash)"). Contents are checked by a second mechanism. Every object and ELF has a .dephash sidecar that lists each file the compiler read with a hash of its contents: 155 files for trisck.o, including tiles_add.cpp, eltwise_binary.h, llk_math_eltwise_binary.h and ckernel_template.h. need_compile rebuilds when the object is missing or any listed hash differs (build.cpp:897-900). process_include_paths adds the resolved kernel's directory to the hash (kernel.cpp:415-421). So moving a kernel changes the hash directory, and editing it doesn't.

With TT_METAL_CACHE=/x, the cache root becomes /x/tt-metal-cache with no trailing slash (rtoptions.cpp:505, normalize_path(value, "tt-metal-cache")), and the build key is appended directly (build.cpp:557-558). The result is a sibling directory called /x/tt-metal-cache13101861097061555864/, with the precompiled headers in /x/tt-metal-cache/pch/. It works, but don't go looking for /x/tt-metal-cache/<build_key>/. The default ~/.cache path ends in a slash and doesn't have this problem.
CUDA has the same two-level idea. nvcc can embed PTX that the driver JIT-compiles for the actual GPU, and the driver keeps a compute cache keyed on the PTX and driver version, so the second launch is fast. Tenstorrent goes further: all device code is compiled at run time, from C++ source rather than an IR, with every compile-time argument and CB format folded in as a constant. The cost is a multi-second first run; the benefit is code like nine constant stores for add_init.
The workbench page B00 sets up TT_METAL_KERNEL_PATH overlays. Lab B04 uses an overlay kernel plus an instrumented ttsim to follow the instruction stream per pipe.

Recap

  • Three layers. The compute API (add_tiles) splits work across TRISCs with UNPACK/MATH/PACK. The Metal wrappers (llk_*) turn CB ids into addresses and tile shapes from generated tables. tt-llk (_llk_*_) emits Tensix instructions. All three are inlined away.
  • Encoding. TT_OP(opcode, params) = (opcode << 24) + params. TTI_* compiles to one .ttinsn word (rotated left by 2); TT_* with runtime operands is an sw to 0xFFE40000; TT_OP_* is the word as data. Only -mcpu=tt-wh-tensix enables the builtin.
  • MOPs. Init functions build a ckernel_template (outer × inner loop, two alternating loop ops, start/end ops, last-iteration substitutes) and write it to nine write-only registers at 0xFFB80000 after mop_sync(). Per tile, the LLK pushes TTI_MOP(1,0,0) plus a SETRWC or two. The maximum expansion on Wormhole is 127 × 257 = 32,639 instructions.
  • In the simulator, one add_tiles was 8 pushed instructions and 26 at the wait gates: 8 UNPACR and 8 ELWADD doing the work. Re-running an init replaces the template; nothing checks it matches your operation.
  • Replay. A 32-entry per-thread buffer records straight-line sequences (lltt::record) and plays them back. Matmul records 16 MVMULs in slots 16–31 and has the MOP loop one REPLAY per fidelity phase: 1 MOP → 64 MVMULs at HiFi4.
  • JIT. Kernels are compiled at first use by SFPI's riscv-tt-elf-g++ (-O3 compute, -O2 data movement), from generated chlkc_*.cpp files, with compile-time args passed as -DKERNEL_COMPILE_TIME_ARGS. They're linked against the weakened firmware ELF, made execute-in-place, and written to L1.
  • Cache. <root>/<build_key>/kernels/<name>/<hash>/. The hash covers the path string, the resolved directory, args, defines and config; file contents are checked by .dephash sidecars. Kernel path search: absolute, cwd, TT_METAL_KERNEL_PATH, system directory, runtime root.

Check yourself

1. A kernel calls mul_init(cb0, cb1) once at the top, then later uses add_tiles in a loop without calling add_init. It compiles and runs without errors. What does the MATH thread actually execute, and why is there no error?

It executes the multiply template. add_tiles's math path is just SETC16, TTI_MOP(1,0,0) and SETRWC, and MOP means "expand whatever is in MopCfg". The last init to write MopCfg was the multiply's, so the expander emits ELWMULs with the multiply's address modes. Nothing can catch it: MopCfg is write-only from the RISC-V (reading it is UndefinedBehavior), the expander has no idea what operation was intended, and the API call itself carries no opcode. Results are silently wrong. (The unpack side happens to need the same AB template, but address modes and some configuration also differ between ops.)

2. A template has OuterCount = 3, InnerCount = 2, a non-NOP LoopOp1, a StartOp, EndOp0 set and EndOp1 = NOP. How many instructions does one MOP produce?

18. LoopOp1 isn't NOP, so the inner loop alternates and runs 2 × 2 = 4 times. Each outer iteration emits StartOp + 4 loop ops + EndOp0 = 6, and 3 × 6 = 18. The last inner op of the first two outer iterations is Loop1Last, and the very last one is Loop0Last, but that changes which word is emitted, not how many.

3. Where does the ISA's "up to 32,639 instructions" come from?

On Wormhole, OuterCount and InnerCount are 7-bit fields, so each is at most 127. With a non-NOP LoopOp1 the inner count doubles to 254. Adding StartOp, EndOp0 and EndOp1 gives 257 instructions per outer iteration, and 127 × 257 = 32,639. Note that ttsim only implements outer counts up to 32 on Wormhole, so a template that long would stop the simulator with UnimplementedFunctionality.

4. You edit tiles_add.cpp in place and rerun. Does the kernel's cache directory name change? What if you copy the file into TT_METAL_KERNEL_PATH without editing it?

Editing in place: no. The hash covers the caller's path string, args, defines, config and include paths, not file contents. tt-metal still recompiles, because trisck.o.dephash records a content hash for tiles_add.cpp and need_compile sees the mismatch. The new objects land in the same directory (run 4 in the table). Copying to the overlay: yes. The resolved kernel directory is added to the include paths, and include paths are hashed, so you get a new directory and a compile even though the bytes are identical (run 3).

5. Why does matmul put a REPLAY inside the MOP instead of putting MVMULs in the MOP template directly?

A tile product is 16 MVMULs that differ in their address-mode bits (0x26000000, 0x26008000, 0x26010000, 0x26018000 in a fixed but irregular order). A template-1 MOP can only alternate between two loop ops plus fixed start/end/last words, so it can't express that sequence. The replay buffer can hold any straight-line sequence of up to 32 words. The MOP then supplies the loop: once per fidelity phase (4 at HiFi4), each iteration one REPLAY. As a bonus, emitting a REPLAY from the MOP is the ISA's recommended way to hide the MOP expander's one-cycle transition penalty.

6. Why is -mcpu=tt-wh-tensix used only for TRISC builds, and what would happen if a data-movement kernel included ckernel_ops.h and used TTI_SETRWC?

Only -mcpu=tt-wh-tensix defines __riscv_xtttensixwh and enables the __builtin_rvtt_ttinsn builtin that emits .ttinsn words. BRISC and NCRISC are built with -mcpu=tt-wh. Under that flag ckernel_ops.h falls through to its #else branch, where TTI_INSN expands to an assembler .error "TTI_INSN in non-tensix code", so the build fails. That matches the hardware: NCRISC can't push Tensix instructions at all, and BRISC's pushes enter after the MOP expander, so it can't use MOP anyway.
