09. Memory: L1, DRAM, interleaving and sharding

The chip has no cache to decide where data lives, so software decides. By the end you will be able to take any page of any buffer and say which bank holds it, at what address, and how many NoC hops it is from the core that needs it.

The question

Take a small tensor: 128 × 128 values in bfloat16. That is 32 KiB. The chip works in 32 × 32 tiles, so the tensor is a 4 × 4 grid of 16 tiles, each 2 KiB. Now look at where it could go on a Wormhole chip. The chip has 12 GiB of DRAM, reached through 12 banks along two columns of the die. It also has 64 usable worker cores in this setup, and each has about 1.4 MiB of its own SRAM.

On a GPU you would call cudaMalloc, get one pointer, and let the cache hierarchy find the bytes when a thread asks for them. Tenstorrent chips have no such hierarchy. Nothing moves data closer to the core that will use it, and no hardware tracks which copy is newest. So the opening question of this chapter is a real one:

With no cache, who decides where each byte lives? You do. Usually you decide through a few well-chosen defaults, and the rest of this chapter is about what those defaults are and when to override them.

We will work up to a single picture: the same 16 coloured tiles, moved between DRAM banks and core L1s, with a hop counter on every core. The steps on the way are: why there is no cache, what each level of memory is, how a buffer is cut into pages and dealt round-robin to banks, and how sharding pins pages to the cores that compute on them.

No caches, on purpose

A cache is a deal. You write code as if memory were one big flat array, and the hardware guesses which parts you will touch next and keeps copies nearby. When it guesses right, everything is fast. When it guesses wrong, you stall, and how long you stall depends on what else is happening on the chip. With many cores, the hardware must also keep every copy consistent. That is coherence, and it costs snoop traffic, directory state and silicon area.

Tenstorrent refuses the deal. The Metalium programming guide says so directly. The chips "deliberately omit cache hierarchies found in traditional CPU and GPU architectures". The on-chip SRAM "functions as addressable memory rather than transparent cache". This explicit model "eliminates cache coherency protocols and provides predictable memory access latency, but places responsibility on developers to manage data placement and movement patterns effectively" (METALIUM_GUIDE.md:233-237).

Why is this a good trade for AI work in particular? Look at a matmul or an attention layer. You know every address it will touch before it starts. The access pattern is not data-dependent, so a cache's guessing buys nothing. What it adds is jitter and area. If software already knows the schedule, it can issue the reads itself, early, as DMA over the NoC, and overlap them with compute. You met that NoC in A08.

A GPU has registers, shared memory (a scratchpad you manage), L1 and L2 caches managed by hardware, and HBM. CUDA programmers already hand-manage one level: shared memory. A Tenstorrent chip makes every level work like shared memory. The L1 in each Tensix behaves like a 1.4 MiB block of CUDA __shared__ memory that other cores can also write into over the NoC. DRAM is not mapped into any core's address space at all. You reach it only by DMA.
"No caches" means no data caches between cores and memory. Some small caches do exist, and you should know about them. Each baby RISC-V core has a small instruction cache in front of L1, 0.5–2 KiB according to memory_for_kernel_developers.rst:16. On Blackhole, each baby core also has a 64-byte L0 data cache: four 16-byte lines, not coherent, and flushed by any fence (tt-isa-documentation BlackholeA0/TensixTile/BabyRISCV/README.md, section "L0 Data Cache"). Blackhole's 16 SiFive x280 "big" cores have ordinary coherent caches. None of these sits between DRAM and the compute engines.

The hierarchy: four distances

Without caches, the memory hierarchy is simply a list of places data can sit, ordered by how far it is from the core that wants it. An analogy helps here. Think of a worker at a desk. The worker has a pocket notebook, a desk, a library across campus with a row of checkout counters, and other campuses reachable only by courier.

LevelSize (Wormhole)Who can touch itHow
Local data RAM (pocket notebook)4 KiB (BRISC, NCRISC), 2 KiB (each TRISC)Only its own RISC-V coreOrdinary load/store, 2-cycle load latency. The stack lives here.
L1 (the desk)1464 KiB per Tensix (1536 KiB on Blackhole)All five cores of the Tensix, the unpackers/packers, and any other tile via the NoCLoad/store from RISC-V (≥ 8 cycles), wide ports for the engines, NoC reads and writes
DRAM (the library)12 GiB GDDR6 in 12 banksAnyone, but only through the NoCnoc_async_read/write to a DRAM tile's (x, y, address)
Other chips (other campuses)Another chip's DRAM and L1Only Ethernet coresExplicit packets over Ethernet links. There are no shared addresses.

The sizes come from the ISA documentation: WormholeB0/TensixTile/BabyRISCV/README.md lines 9 and 119 give the local RAMs and the 2- versus ≥8-cycle latencies, and L1.md:3 gives the L1 size. The most important fact in the table is the last column. In a Tensix, a RISC-V core can only load and store to its private RAM and its own L1. Everything else is an address of the form (x, y, local_address), and you reach it by asking the NoC to fetch it. The kernel-developer guide makes the point in code:

tt-metal/docs/source/tt-metalium/tt_metal/advanced_topics/memory_for_kernel_developers.rst:41-43 @7aad8aac
// `dram_addr` is a DRAM address, however the address is not mapped in the RISC-V address space
// and the content must be explicitly fetched from DRAM using NoC APIs and requesting a transfer
uint32_t dram_addr = get_arg_val<uint32_t>(0);

Where the analogy breaks: a real library has one front desk, but this "library" is spread along both edges of the chip, and the walk to it depends on which counter you use. The NoC is a one-way torus (rightwards and downwards on NoC 0, as in A08), so "nearby" is not symmetric. A counter one step to your left can be nine steps away.

L1: a scratchpad, not a cache

The ISA spec itself warns about the name: "This RAM is called 'L1', but this is somewhat of a misnomer, as it is suggestive of a hardware-managed cache, which is not the case - this is plain RAM" (WormholeB0/TensixTile/L1.md:3). So what lives in those 1464 KiB? Looking from address 0 upwards on Wormhole:

  • Reserved runtime area, about the first 35 KiB: the boot code, mailboxes used by the host and dispatch to launch kernels, firmware for each of the five RISC-V cores, NoC counters and fabric routing tables. These are the MEM_* regions in tt_metal/hw/inc/internal/tt-1xx/wormhole/dev_mem_map.h:84-163.
  • Kernel config region, 69 KiB (wh_hal_tensix.cpp:42). Each program places its kernel binaries ("kernel text"), runtime arguments, semaphores and circular-buffer configuration here.
  • The unreserved region, everything else, which starts at 0x19E60 on this build. There are 1,393,056 bytes (1360 KiB) left for your data. Circular buffers (CBs) grow upward from the bottom of this region. L1 buffers, which the allocator manages, grow downward from the top. A11 covers circular buffers. For now, think of them as the per-program staging areas between the reader, compute and writer kernels.

The 1360 KiB figure is not a guess. It is what the allocator reported in the simulator run below: L1 banks=64 bank_size=1393056 B out of worker_l1_size=1499136 B.

Banking inside one L1

"One L1 bank per core" in the allocator's language means one allocation unit per core. Physically, each Wormhole L1 is built from 16 banks of 91.5 KiB, and each bank can do one 128-bit read or write per cycle. Sixteen access ports sit in front of them. Any port can reach any bank, and when two ports want the same bank in the same cycle, one of them waits (L1.md:5). That is why the engines get very different bandwidth from the RISC-V cores (L1.md:25-53):

  • An unpacker can read 4 × 128 bits per cycle. With both unpackers running, they share 5 × 128 bits.
  • Each of the four packers writes 128 bits per cycle.
  • Each NoC has two read and two write connections to L1: 256 bits per cycle each way, which matches the 256-bit router links.
  • A baby RISC-V store is always a "narrow" write. Narrow writes are implemented as a read-modify-write that blocks the bank for five cycles. That works out to one 32-bit store per five cycles, or 6.4 bits per cycle.

Compare 6.4 bits per cycle with 512 bits per cycle for the unpacker. That ratio is why the RISC-V cores direct the work and do not do it. Kernels ask the NoC, the unpackers and the packers to move bytes, and the RISC-V cores mostly write descriptors and wait on counters. The spec puts it bluntly: RISC-V cores are "strongly encouraged to instruct other clients to access L1 on their behalf".

Do not pass the address of a stack variable to noc_async_read. The stack is in core-private local RAM, which is mapped at the same address on every core, and the NoC cannot see it. The guide calls this out as code that "will not work" (memory_for_kernel_developers.rst:88-101). Only L1 addresses can be DMA sources or destinations.

DRAM: controllers, channels and banks

Three words get mixed up here, and different sources use them differently, so let us pin them down for Wormhole.

  • A GDDR6 channel is 1 GiB of memory behind a 16-bit data bus running at 12 GT/s, giving 24 GB/s. Wormhole has 12 of them.
  • A controller (the DRAM "channel" in UMD and soc-descriptor terms, confusingly) owns two GDDR6 channels. Wormhole has 6. Each controller appears on the NoC as three DRAM tiles, so there are 18 DRAM tiles in total. All three tiles of a controller reach the same memory: "Reading from different D1 tiles at the same address returns the same data" (memory_for_kernel_developers.rst:114-115).
  • A bank is what the allocator and kernels count. On Wormhole it is a 1 GiB view: one controller, seen through one chosen tile, at address offset 0 (the first GDDR6 channel) or 1 GiB (the second). 6 controllers × 2 views = 12 banks.

The ISA docs confirm the hardware side: "There are 18 DRAM tiles per Wormhole ASIC, collectively exposing 12x 1 GiB channels of GDDR6". Through the NoC, a DRAM tile's addresses 0x0_0000_0000–0x0_3FFF_FFFF are channel 0 and 0x0_4000_0000–0x0_7FFF_FFFF are channel 1 (WormholeB0/DRAMTile/README.md:3, 40-41). The software side, meaning which tile and which offset form each bank, is in the soc descriptor:

Bank 1 is the same controller through tile 0-1, at offset 1 GiB. You do not have to decode the rest by hand. Blackhole is simpler. It has 8 controllers and 8 banks of 4080 MiB each (dram_bank_size: 4278190080 in blackhole_140_arch.yaml), with no split into two views. The p150 has 32 GB of GDDR6 on a 256-bit bus at 16 GT/s, for 512 GB/s according to the Blackhole spec page.

Sources disagree on "how many DRAM banks does Wormhole interleave over?" The kernel-developer guide's figure says a 64-tile buffer "round-robins across the 6 DRAM controllers" (memory_for_kernel_developers.rst:216). The allocator report says "on Wormhole there are 12 ~1GB DRAM banks" (tech_reports/memory/allocator.md:21). The code follows the allocator: num_dram_channels = soc_desc.get_num_dram_views() (l1_banking_allocator.cpp:236), and the simulator run below printed DRAM banks=12. Consecutive pages therefore alternate between the two GDDR6 channels of one controller before moving to the next controller. So both statements are true in a sense: pages 0 and 1 hit controller 0, and pages 0–11 together touch all 6 controllers.

And ttsim? It models the memory per controller, not per bank. Each simulated chip gets one anonymous mmap per controller, and a comment admits the shortcut:

ttsim/src/config.h:14,35 and src/sim.cpp:37 @b3620244
#define NUM_DRAM_CHANNELS 6 // technically it's 12 channels, 2 for each of the 6 DRAM tiles, but doesn't matter
#define DRAM_CHANNEL_SIZE 0x80000000ull // 2GiB for each of the 6 DRAM tiles (12GB total)
g_dram[i].p_mem = (uint8_t *)mmap(nullptr, DRAM_CHANNEL_SIZE, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE, -1, 0);

A NoC read to any of a controller's three tiles lands in the same 2 GiB array, and the 1 GiB offset that tt-metal adds for odd banks simply indexes into the upper half: memcpy(p, &g_dram[tile_id].p_mem[addr], size) (src/tile.cpp:2785-2786). Because the mapping is MAP_NORESERVE, 12 GiB of "DRAM" costs nothing until it is touched. "Doesn't matter" is right for a functional simulator. It would matter for a timing model, because the two GDDR6 channels are separate 24 GB/s pipes.

Pages and interleaving

A kernel gets one address for a buffer, yet the buffer is spread over 12 banks (or 64 L1s). How do those fit together? Two rules handle it: pages, and lockstep.

Pages

Without a flat address space, you have to choose how big a chunk to store in one place before moving to the next. That chunk is the page: "The chunk size, or the amount of data stored before switching to the next storage location, is referred to as the page size" (memory_for_kernel_developers.rst:133). In practice:

  • Tiled layout: one page = one tile. A bf16 32×32 tile is 2048 bytes. A bfp8_b tile is 1088 bytes: 1024 mantissa bytes plus 64 bytes of shared exponents (tt_backend_api_types.hpp:129).
  • Row-major layout: one page = one row, which ttnn calls a "stick".
  • Anything you like for raw Metalium buffers. shard_data_rm uses 4-byte pages (two bf16 values per stick).

Interleaving: dealing cards

An interleaved buffer deals its pages to the banks like a dealer dealing cards: page 0 to bank 0, page 1 to bank 1, … page 11 to bank 11, page 12 back to bank 0. Every new buffer starts dealing at bank 0 (tensor_layouts.md:97-99). Each bank stores its pages one after another. So page p is the ⌊p/12⌋-th page inside bank p mod 12. Here is that sentence as the device-side code, which runs on a RISC-V core inside a reader kernel:

tt-metal/tt_metal/hw/inc/internal/dataflow/dataflow_api_addrgen.h:226-238 @7aad8aac
template <bool DRAM>
uint64_t get_dram_noc_addr(
    const uint32_t id,
    const uint32_t page_size,
    const uint32_t bank_base_address,
    const uint32_t offset = 0,
    uint8_t noc = noc_index) {
    uint32_t bank_offset_index = interleaved_addr_gen::get_bank_offset_index<true>(id);
    uint32_t bank_index = interleaved_addr_gen::get_bank_index<true>(id, bank_offset_index);
    uint32_t addr =
        (bank_offset_index * align_power_of_2(page_size, interleaved_addr_gen::get_allocator_alignment<true>())) +
        bank_base_address + offset + bank_to_dram_offset[bank_index];
    return noc_address_backend::bank_address<true>(bank_index, addr, noc);
}
  • get_bank_offset_index(id) is id / NUM_DRAM_BANKS: which row inside the bank. When the bank count is a power of two (8 on Blackhole) it becomes a shift. For 12 it is a multiply-by-reciprocal, udivsi3_const_divisor (same file, lines 20-34), because a hardware divide on a baby core takes 6 to 33 cycles (tt-isa-documentation WormholeB0/TensixTile/BabyRISCV/README.md:46-49).
  • get_bank_index is the remainder: which bank.
  • The page size is rounded up to the DRAM alignment: 32 bytes on Wormhole, 64 on Blackhole (LOG_BASE_2_OF_DRAM_ALIGNMENT 5 and 6 in each core_config.h). A 4-byte stick therefore occupies 32 bytes.
  • bank_base_address is the buffer's single address, the same for every bank. That only works because of lockstep allocation, described next.
  • bank_to_dram_offset[bank_index] adds the 1 GiB view offset for the odd Wormhole banks.
  • bank_address finally attaches the bank's NoC (x, y), giving the 64-bit NoC address that noc_async_read takes.

Modern kernels rarely call this directly. They build a TensorAccessor and call noc_async_read_page(i, accessor, l1_addr), which does the same arithmetic for interleaved and sharded buffers, in DRAM or L1, chosen at compile time (memory_for_kernel_developers.rst:219-276). A11 covers the accessor.

Lockstep: one address for all banks

For one address to work in every bank, the allocator reserves the same range in every bank, even banks that get fewer pages. "Each bank reserves the same amount of space for a given buffer regardless of how many banks the data is in" (allocator.md:33). The simulator shows it directly. Three DRAM buffers allocated one after another, with 1, 14 and 1 bf16 tiles:

DRAM interleaved: d0 (1 page) @0x2d4c40, d1 (14 pages) @0x2d5440, d2 (1 page) @0x2d6440

d0 holds one page, which sits in bank 0, yet the next buffer starts 0x800 = 2048 bytes later in all banks. d1 has 14 pages, so banks 0 and 1 hold two pages and banks 2–11 hold one. Every bank still reserves ⌈14/12⌉ = 2 pages, which is why d2 starts 0x1000 = 4096 bytes after d1. That wastes 10 page-slots. In return, kernels get one pointer, and the same pointer works on any chip generation. The kernel guide states the trade-off plainly: "kernels receive a single address parameter instead of N hardware-dependent pointers, at the cost of some memory waste" (memory_for_kernel_developers.rst:181).

Now try it. Pick a page id and a page type. The figure shows the bank, the address computed by the code above, the DRAM tile it lives on, and the NoC 0 route the data takes back to a reader on logical core (0,0), which is NoC tile (1,1) on an unharvested Wormhole.

Try page 0 and page 1. Both live on controller 0, but bank 0 is reached through tile (0,11) and bank 1 through tile (0,1). For the reader at (1,1), the first is 3 hops away and the second only 1: the data goes one step right, and from (0,11) also two steps down across the wrap-around. Now try page 4, on tile (5,1). It is 4 columns to the right of the reader, and NoC 0 only flows rightwards, so the data cannot step back left. It goes right from column 5 through 9, wraps around to column 0 and arrives at column 1: 6 hops. No single reader is close to every bank. Interleaving avoids hot spots by spreading every buffer evenly, and pays for that with distance.

A real run: one stick per bank

shard_data_rm makes the page idea concrete. It writes 16 bf16 values, 2, 4, …, 32, to an interleaved DRAM buffer with 4-byte pages:

Core (0,1) asked for sticks 2 and 3, which means banks 2 and 3: two reads to two different DRAM tiles for 8 bytes of data. That is the price of interleaving with tiny pages. The prints arrive out of order because the four cores run concurrently, and nothing orders their DPRINT output.

Sharding: putting data where the work is

Interleaving answers "where should this buffer live so no bank is a hot spot?" It does not answer "where should this buffer live so the core that computes on it already has it?" That is sharding. You cut the tensor into rectangular shards and assign each shard to one bank. For L1 that means one core. The tensor-sharding report lists the 2D options (tensor_sharding.md:20-161). All dimensions except the last are first flattened into a height H, so the tensor is H × W:

  • Height sharding: horizontal bands. Each shard has the full width W and H/N rows. Good when each row can be processed alone, as in eltwise ops, layernorm over W, and matmul activations split by M.
  • Width sharding: vertical strips. Each shard has the full height and W/N columns. Typical for decode activations: 32 rows and a very wide hidden dimension.
  • Block sharding: a 2D grid of blocks onto a 2D grid of cores, which the report describes as "a 1-to-1 mapping onto a corresponding 2D grid of memory banks". Good for 2D-parallel matmuls.
  • Orientation (ROW_MAJOR or COL_MAJOR) sets the order in which shards are handed to the cores of the grid: along rows of cores first, or down columns first.

Here is our 16-tile tensor again, in every arrangement we have discussed. Watch the hop counters. In the interleaved arrangements, assume the op runs on logical cores (0,0)–(3,0) and that core i needs row i of the tensor. Each count is the number of NoC 0 hops its four tiles travel to reach it, computed with the same right-then-down torus rule as in A08, on the unharvested layout that ttsim models (see In the simulator). Only the returning data is counted, not the read request.

The tensor is the same in every frame, and so are the 32 KiB. Only the owner of each tile changes, and with it the NoC traffic the op will cause. The totals are 158 hops for DRAM interleaved, 199 for L1 interleaved, and 0 for any sharding that matches how the op splits its work. Two details are worth a second look:

  • L1 interleaved is not "local". The data is on-chip, but it is dealt across 64 L1 banks in shuffled order. The allocator deliberately randomises which core is bank 0 (std::shuffle with a fixed seed, l1_banking_allocator.cpp:80-87), presumably to spread small buffers across the grid. The exact order depends on the C++ standard library; the figure uses the order this build printed. So core (0,0) holds none of row 0, and on this layout the traffic is worse than from DRAM.
  • Sharding only pays when the shard matches the work. Width-sharding makes every core hold one tile of every row. For a row-wise op such as a softmax over W, that would be the wrong choice: each core would need the other three cores' tiles. The layout is a promise about the op, not about the tensor.
Interleaving is the default because it is safe for every op: no bank is a hot spot. Sharding is a contract between the data layout and an op's work split. When the contract holds, the op reads from its own L1 and the NoC sits idle.

The last two blocks show what orientation does. With ROW_MAJOR, the second shard (tiles 2, 3, 6, 7) goes to the next core along the row, core (1,0). With COL_MAJOR, it goes to the next core down the column, core (0,1). The cut is identical; only the order in which cores are handed shards changes. Each buffer was freed before the next was created, so all four reuse the address 0x16a000.

Sharding with no data movement at all: vecadd_sharding

The vecadd_sharding example takes the idea to its limit. A, B and C are all sharded in L1, and the circular buffers the compute kernel reads from are placed on top of those L1 buffers. So there is no reader kernel, no writer kernel and no NoC traffic during the add:

Why it matters: the numbers

The LLM tech report ranks the four ways an op can read its inputs on Wormhole (tech_reports/LLMs/llms.md:1844-1852):

SourceWhat the report says
DRAM interleaved"Each tile … is read from a different DRAM bank. This is the ttnn default and is the slowest way to read data. A matmul can expect to read around 190 GB/s on a Wormhole like this."
DRAM shardedEach bank's slice is read by the core closest to that bank: "around 240 GB/s on a Wormhole". Used "for DRAM-bound matmuls and nothing else".
L1 interleaved"Tiles are interleaved across the L1 of all the cores and are read across the NoC."
L1 sharded"particularly fast when the data an OP requires is already placed in L1 of the correct core, avoiding the NOC entirely".

The report's rule of thumb follows: "Activations are placed in L1 and weights placed in DRAM." Activations are produced and consumed by neighbouring ops, so a sharded layout can flow from one op to the next without ever leaving L1. METALIUM_GUIDE calls this an alternative to aggressive fusion: intermediate data "can persist in SRAM across multiple operations without eviction pressure" (METALIUM_GUIDE.md:210). Weights are too big for 64 × 1.4 MiB, so they stream from DRAM, and the next section is about streaming them as fast as the GDDR6 allows.

The DRAM bandwidth story: 267 of 288 GB/s

Start with the ceiling. Each GDDR6 channel moves 16 bits per transfer at 12 GT/s, which is 24 GB/s. Twelve channels give 288 GB/s. Self-refresh and similar overheads cost a few percent, so "well-written software can expect to achieve approximately 92% of the theoretical maximum" (WormholeB0/DRAMTile/README.md:66). Note also that one NoC hop sustains 32 GB/s. A single channel (24 GB/s) is therefore slower than a link (same file, line 70). By the same arithmetic, two channels' traffic sharing a link (48 GB/s) would be more than the link can carry.

The Saturating_DRAM_bandwidth tech report describes how the team actually reached that 92%, and it is a story about placement more than code:

  1. Saturate one bank. A reader that issues a block of reads and then waits on a barrier leaves the bank idle between blocks. The fix is to tag each block with a transaction ID and barrier only on the older block, so one request is always in flight (Saturating_DRAM_bandwidth.md:11-13).
  2. One reader per bank, and each reader reads only its own bank, "otherwise serving multiple readers per bank would cause serious NoC congestion" (line 24).
  3. Put each reader next to its bank. With 12 readers in the top rows, NoC 0 routes for different banks overlap. Placing each reader beside its bank makes the return route a single hop, with no overlap (lines 26-31).
  4. Two readers share each row (DRAM sits in two columns), so their requests still share links. Giving them different virtual channels makes the routers round-robin between them instead of serving them first-come, first-served (line 31).
  5. Harvesting. On n150 and n300 some worker rows are disabled, and which ones varies per chip. A reader whose ideal spot is harvested is shifted right and up until its route overlaps no other (lines 40-42).

The result (line 64-69):

Test (Wormhole)DRAM at 12 GT/sDRAM at 14 GT/s
Spec288 GB/s336 GB/s
DRAM micro-benchmark267 GB/s (92.7%)310 GB/s
Llama3-70 decode matmuls239–260247–294
Mixtral 8x7b decode matmuls243–261267–300

The matmul rows depend on DRAM sharding. The weight tensor in1 is width-sharded into the 12 banks, shard Dk into bank k. The reader and the compute kernel for shard k sit on the core next to bank k, and the small activation tensor is multicast to them (lines 49-56). Compare that with the default: in the interleaved layout every reader touches every bank, which is why the LLM report quotes about 190 GB/s for it. Same chip, same GDDR6, roughly a 25% difference, and all of it from placement. The report's last section adds a trap: 12 rarely divides a weight width evenly in 32-wide tiles, so the last bank gets a ragged shard (lines 72-73).

On a GPU, the memory controller interleaves physical addresses across HBM channels in hardware, usually at a granularity of a few hundred bytes, and you never choose. Here the "interleave" is a software policy at page granularity that you can see and override. That gives you control, and the 190 → 240+ GB/s gap shows it is worth having.

Sidebar: the allocator

Someone has to hand out those base addresses. The allocator is a host-side bookkeeper: it "assigns addresses for Buffers and maintains a record of what is free or in-use", and it never touches device memory itself (allocator.md:3). Its rules fit on one card:

  • First-fit, from either end. One free list per region, where each allocation can ask for the lowest or the highest fitting address (allocator.md:13).
  • DRAM is bottom-up, L1 is top-down. The default is set in one line:
tt-metal/tt_metal/impl/buffers/buffer.cpp:497 @7aad8aac
bottom_up_(bottom_up.value_or(buffer_type == BufferType::DRAM || buffer_type == BufferType::TRACE)),
  • Why L1 grows down: circular buffers are usually not allocator-managed. Each program places its CBs upward from the bottom of the unreserved region, as the code says: "CBs grow up from DEFAULT_UNRESERVED" (program.cpp:2570). Growing L1 buffers from the other end keeps the two from colliding. Before a program runs, a validation step checks that its CBs do not reach the lowest L1 buffer (allocator.md:53-61).
  • Why DRAM grows up: user data grows upward, while things like program binaries are allocated top-down so they do not fragment it (allocator.md:13).
  • Lockstep in every bank, as above. The L1 bank size is whatever the reserved area leaves over:
tt-metal/tt_metal/impl/allocator/l1_banking_allocator.cpp:119-124 @7aad8aac

A few more allocator facts you will meet later:

  • Alignment: addresses and page strides are padded to DRAM_ALIGNMENT so that DRAM-to-L1 reads never break NoC alignment (allocator.md:45-49). Breaking that rule on purpose is a B05 exercise. ttsim reports it as UndefinedBehavior.
  • L1_SMALL is an optional region at the top of L1, kept for small buffers that some ops need (conv2d, for example). You opt in with l1_small_size when opening the device.
  • Memory reports: ttnn.device.dump_device_memory_state(device, prefix="") or the C++ DumpDeviceMemoryState write CSV reports with per-bank usage and the address, size and status of every block (allocator.md:63-93).

Across chips: no shared memory at all

On one chip there is at least a common naming scheme, (x, y, address), and any core can reach any tile through the NoC. Between chips even that is gone. "In a multichip system, there is no concept of shared memory or global addressability across chips for Wormhole or Blackhole" (tech_reports/EthernetMultichip/BasicEthernetGuide.md:188). Only Ethernet cores can send across a link, and only into the L1 of the Ethernet core at the other end. Longer routes are relayed hop by hop. So a tensor "on" a two-chip n300 is really two tensors, one per chip, each allocated by its own allocator with its own lockstep addresses. Keeping them consistent is the job of collective operations that software issues explicitly. ttsim mirrors this: each simulated chip has its own ChipState with its own dram[] mmaps (src/sim.h:572-582), and nothing is shared. A21 builds meshes and collectives on top of this.

Recap

  • There are no data caches and no coherence. That is deliberate: AI access patterns are known ahead of time, so explicit DMA gives predictable latency and saves the area coherence would cost. Small exceptions exist: instruction caches, Blackhole's 64-byte non-coherent L0, and the x280 cores.
  • The hierarchy is: core-private RAM (2–4 KiB, 2-cycle loads) → L1 (1464 KiB per Tensix, 16 banks × 128 bits, plain RAM) → DRAM, reached only by NoC DMA → other chips, reached only over Ethernet. Every non-local address is (x, y, local address).
  • L1 holds firmware and mailboxes, a 69 KiB kernel-config region, then free space where CBs grow up from 0x19E60 and allocator buffers grow down from 0x16E000.
  • Wormhole DRAM has 6 controllers × 2 GDDR6 channels = 12 banks of 1 GiB. Each bank is a (tile, offset) view, and odd banks sit at +1 GiB. Blackhole has 8 banks of 4080 MiB.
  • Buffers are cut into pages: a tile, a row, or any size you choose. Interleaving deals page p to bank p mod N at row ⌊p/N⌋, starting at bank 0. Lockstep allocation gives every bank the same range, so one address works everywhere.
  • Sharding assigns rectangles (height, width or block, with row- or column-major orientation) to specific cores or banks. When the shard matches the op's work split, the op reads its own L1 and does zero NoC hops.
  • Placement is performance. Wormhole reaches 267 of 288 GB/s in a micro-benchmark and 239–261 GB/s in decode matmuls with DRAM-sharded weights, against about 190 GB/s for the interleaved default.
  • The allocator is host-side and first-fit: DRAM bottom-up, L1 top-down, CBs checked against L1 buffers before launch.

Check yourself

1. On Wormhole, a bf16 tiled buffer has 30 pages, interleaved in DRAM. How many bytes does it reserve in each bank, and how many in total?

⌈30/12⌉ = 3 pages per bank × 2048 B = 6144 B per bank, and 12 × 6144 = 73,728 B in total for 61,440 B of data. Banks 0–5 hold 3 pages and banks 6–11 hold 2, but lockstep allocation reserves the same 3-page range in all of them, so that one base address works in every bank.

2. Page 29 of that buffer: which bank, which DRAM tile, and what local address if the buffer starts at 0x2d4c40?

Bank = 29 mod 12 = 5. Row = ⌊29/12⌋ = 2. Local address = 0x2d4c40 + 2 × 2048 = 0x2d5c40. Bank 5 is controller 2's second view, so the 1 GiB offset is added: the NoC request goes to tile (5,11) at address 0x402d5c40. Check it with the page-to-bank figure.

3. Why does the allocator place L1 buffers top-down instead of bottom-up like DRAM?

Because circular buffers are normally placed by each program, not by the allocator, and they grow upward from the start of the unreserved region (0x19E60 here). If L1 buffers also grew upward, the two would compete for the same addresses and fragment each other. Growing from opposite ends leaves one free gap in the middle, and tt-metal checks before launch that the CB top stays below the lowest L1 buffer.

4. A 4 × 4-tile tensor is block-sharded on cores (0,0)–(1,1). Which core holds tiles 2, 3, 6, 7 with ROW_MAJOR orientation, and with COL_MAJOR?

Tiles 2, 3, 6, 7 are the top-right 2 × 2 block, which is the second shard. ROW_MAJOR hands shards to cores along the row first, so it goes to core (1,0). COL_MAJOR goes down the column first, so it goes to core (0,1). The probe run printed exactly this.

5. The DRAM micro-benchmark reaches 267 GB/s, but an interleaved matmul gets about 190 GB/s. The GDDR6 is identical. Where does the bandwidth go?

Into the NoC, not the DRAM. With interleaving, every reader core requests pages from every bank, so routes from different banks cross and share links. One hop carries 32 GB/s, and two channels' worth of traffic is 48 GB/s. The benchmark and the DRAM-sharded matmul put one reader beside each bank, give its return path a single hop, and use separate virtual channels for the two readers in a row. Barriers on transaction IDs then keep each bank busy continuously.

6. On an n300 (two Wormhole chips), can a reader kernel on chip 0 call noc_async_read with the address of a buffer that lives in chip 1's DRAM?

No. A NoC address is (x, y, local address) on this chip's NoC, and there is no global address space across chips. The data has to move explicitly: into an Ethernet core's L1 on chip 0, over the link into the peer Ethernet core's L1 on chip 1, and then onwards. Higher layers such as TT-Fabric and the CCLs do this for you (A21).
