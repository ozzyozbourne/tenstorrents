08. The Network-on-Chip

The question

A Wormhole chip is a grid of 10 × 12 = 120 positions. Eighty of them are Tensix cores, and the rest are DRAM controllers, Ethernet ports, a PCIe port, the ARC management CPU, and a few empty spots (you met this map in A03). No Tensix core sits behind a shared cache hierarchy (each RISC-V core has only a tiny instruction cache), and none can load a byte from another core's memory with an ordinary load instruction. Every byte that moves between two positions travels as a packet over a Network-on-Chip, or NoC.

Look at the chip a little longer and you find something odd. There is not one network but two, and they are physically separate. Each is a one-way street: on NoC 0 data can only move right or down, and on NoC 1 it can only move left or up. So:

Why would anyone build two networks that run in opposite directions, instead of one network where data can go either way?

By the end of this chapter you will be able to answer that with numbers. You will also know how a packet is routed, how big it is, what kinds of request exist, why the network will happily reorder your writes, and how a single 32-bit store from a tiny RISC-V core starts a 2 KiB DMA. Along the way we use the simulator ttsim as executable documentation, and we look at real transfers it logged.

Why a network at all?

Start with the simplest thing that could work: a bus, one shared set of wires that every tile can drive. A bus is cheap, and with four tiles it is fine. But only one tile can talk at a time. With 120 tiles, each one gets on average 1/120 of the bus, and the wires have to stretch across the whole die, so they are long, slow and power-hungry.

The opposite extreme is a crossbar: a switch that can connect any input to any output at the same time. Now all 120 tiles can talk at once, but a full crossbar needs 120 × 120 = 14,400 crosspoints, and every input wire must still reach every output, all the way across the chip.

A mesh takes a third path. Each tile gets a small router that only talks to its immediate neighbours. A packet going far just takes several short hops. Every wire is one tile long, every router is the same small circuit, and when you add tiles you add links in proportion, so total bandwidth grows with the chip. The price is latency proportional to distance, and the possibility that two packets want the same link at the same moment (congestion).

Drag the slider to grow the chip and watch how the three designs scale.

Tenstorrent chips use the mesh idea with one twist: the edges wrap around. The right edge of each row connects back to the left edge, and the bottom of each column connects back to the top. A grid whose edges wrap like this is a 2D torus: roll the grid into a tube and bend the tube into a ring, and you get a doughnut. On a plain mesh a corner tile is far from everything; on a torus no tile is special, because every tile sees the same neighbourhood.

The ISA documentation says it directly: “Each NoC is a 2D torus of NoC routers and NIUs (NoC interface units). Packets initiate at an NIU, and terminate at an NIU, with routers moving packets between NIUs” (tt-isa-documentation/WormholeB0/NoC/README.md:5). Every grid position has a router and an NIU, even the empty ones, which “still contain a router and an NIU” (README.md:21).

The dashed wraparound links in the figure are drawn long because the picture is flat. Real torus chips often fold the ring in the physical layout so that every wire stays short. The Tenstorrent ISA documentation gives one uniform router-to-router latency (9 cycles) and does not describe the physical layout, so this page doesn't say how the wrap links are wired.

One-way streets on a doughnut

Here is the first surprise. A textbook mesh router has links in both directions. Tenstorrent's routers don't. From RoutingPaths.md:11: “All data flow between NoC #0 routers is rightwards and downwards, with the left/right and top/bottom edges connected to each other.” And for the other network (RoutingPaths.md:35): “All data flow between NoC #1 routers is leftwards and upwards.”

Picture a city whose streets are all one-way, and which happens to be built on a doughnut. On NoC 0 you can only drive east or south. To reach the building just west of you, you have to drive east all the way around the doughnut: on a 10-wide grid that is 9 blocks to move 1. Each row is a one-way ring and each column is a one-way ring.

Why build it that way? The METALIUM_GUIDE gives Tenstorrent's reason: “the unidirectional design optimizes power consumption and silicon area utilization” (tt-metal/METALIUM_GUIDE.md:58). A one-way router has one output per axis instead of two, so it is smaller. The wrap is what makes a one-way network usable at all: without it, a packet could never travel left on NoC 0.

Then add the second doughnut with every street reversed, and the westward trip is one block again. The guide puts it this way: “The opposing directional flow of the two NoCs naturally provides efficient return paths for data, regardless of the originating location” (METALIUM_GUIDE.md:58). Try it below.

Play with a few pairs. One step left costs 9 hops on NoC 0 and 1 hop on NoC 1. One step down costs 1 hop on NoC 0 and 11 on NoC 1. The loopback preset is a real transfer the simulator logged later in this chapter: Tensix (1,1) talking to the DRAM tile at (0,11). On NoC 0 that is 9 hops right (wrapping past column 9) plus 10 hops down, 19 in all. On NoC 1 it is 2 hops up (wrapping past row 0) plus 1 hop left, just 3.

Dimension-order routing, and why the second NoC helps

Notice that each route turns at most once. That is no accident. The ISA spec (RoutingPaths.md:17) says unicast packets on NoC 0 “will travel rightwards as necessary, turn at most once, and then travel downwards as necessary”. On NoC 1 they “travel upwards as necessary, turn at most once, and then travel leftwards as necessary” (RoutingPaths.md:41). This scheme is called dimension-order routing: finish moving in one dimension, then move in the other. Each NIU's NOC_NODE_ID register has a bit recording which order its NoC uses. That bit is “in practice always true [X first] at all NoC #0 NIUs and false [Y first] at all NoC #1 NIUs” (MemoryMap.md:189).

Dimension-order routing is deterministic: the route is fixed by the source, the destination and the NoC (RoutingPaths.md:3-8), with no adaptive detours around traffic. That makes it cheap to build and easy to reason about. If two of your transfers collide on a link, they will collide every time.

Now look again at the hop counts. On one ring of length L, going forward d steps costs d hops, and going the other way round costs L−d. So for any pair that differs in both x and y:

hops(NoC 0) + hops(NoC 1) = (10 - dx) + dx + (12 - dy) + dy = 10 + 12 = 22   (Wormhole)

So whichever NoC is longer, the other is shorter, and the better of the two is never more than 11 hops. With only NoC 0, a transfer could need up to 9 + 11 = 20 hops.

The twist: a read is a round trip

Here is where it gets subtle, and where the full answer to our question lies. A read sends a small request to the remote tile, and the remote tile sends the data back. The ISA spec says “unicast request packets, along with all types of response / acknowledgement packets” follow the same routing rule on a given NoC (RoutingPaths.md:17), so the response returns on the same NoC as the request. On a one-way torus, going A→B and then B→A on the same NoC is a full loop in each ring. The round trip is always 22 hops on Wormhole (when x and y both differ), whichever NoC you choose.

So for a read, the second NoC doesn't shorten the round trip. What it changes is which leg carries the data. The request is a single header flit, and the response carries up to 256 data flits. Take the loopback read of DRAM (0,11) by core (1,1):

Issued onRequest (1 flit) (1,1)→(0,11)Response (65 flits for 2 KiB) (0,11)→(1,1)Link-cycles occupied by data
NoC 019 hops3 hops≈ 3 × 65 = 195
NoC 13 hops19 hops≈ 19 × 65 = 1235

Both rows have the same round-trip hop count, but the NoC 1 version drags 2 KiB of data across 19 links instead of 3. Every link it occupies is a link some other core can't use in that cycle. On a busy chip, that is the difference between a quiet network and a congested one. (These are derived counts, assuming the 65 flits of a 2 KiB packet, one header plus 64 data flits, each hold one link for one cycle.)

A write is the reverse: the data travels on the request leg, and only a 1-flit acknowledgement comes back, or nothing at all if the write is posted. For writes, pick the NoC whose forward path is short.

Two opposite one-way tori give every pair of tiles both a short path and a long path, at the cost of building one-way routers twice. Put the heavy data on the short leg. As a bonus, the two networks are physically separate, so they double the bandwidth into and out of every tile.

The second reason matters just as much in practice. Each tile has two NIUs, one per NoC (MemoryMap.md:3), and each can inject one flit per cycle. The METALIUM_GUIDE describes the usual division of labour: “NoC 0 reads data from DRAM (or accept data from other Tensixes) … NoC 1 sends the result to DRAM (or other Tensixes)” (METALIUM_GUIDE.md:49-53). A reader kernel on one data-movement core uses NoC 0 while a writer kernel on the other uses NoC 1 (METALIUM_GUIDE.md:71), so input and output traffic never compete for the same links. It is “just one possible configuration”: some operators “intentionally utilize both NoCs for the same data movement simultaneously, doubling the effective bandwidth” (METALIUM_GUIDE.md:62).

A GPU hides its on-chip interconnect behind the cache hierarchy: an SM issues a load, and a crossbar or mesh to the L2 slices does the rest, out of the programmer's sight. On Tenstorrent the network is part of the programming model. Your data-movement kernel picks the NoC, the destination coordinates and the transfer size, and so it also chooses which links its data occupies.
Routes are fixed, so placement is a performance decision. The DRAM-bandwidth tech report found that placing 12 DRAM readers on the top two rows made “the routes for DRAM bank 2 and bank 10 are overlapped and cause congestion”. Its fix was to put each reader next to its bank, so the response route “just has one hop” (tech_reports/Saturating_DRAM_bandwidth/Saturating_DRAM_bandwidth.md:26-31). That is the heavy-leg rule above, applied to the whole chip.

Flits, packets, hops and bandwidth

What actually moves over a link? A NoC transaction “consists of one or more packets. Each packet consists of one or more flits (exactly one header flit, followed by up to 256 data flits)” (README.md:3). A flit (flow-control unit) is what a link carries in one cycle: the width of the wire bundle between two routers.

A cross-check: Tenstorrent's Hot Chips 2024 slides list the Blackhole “NoC link width 64 Bytes” and “NoC link BW 83 GB/s”, slightly below the 86.4 GB/s derived from the 1.35 GHz clock in the ISA docs. The two sources disagree by about 4%, probably because the slides assume a lower clock (83 GB/s ÷ 64 B ≈ 1.3 GHz), but neither says so. Treat both as peak figures, not something you will measure.

Routers work in cut-through mode: “a router can start forwarding (the flits of) a packet before it has finished receiving the entire packet. This is sometimes called Wormhole switching” (RoutingPaths.md:61-63). (The term predates the chip; the shared name is a coincidence.) Picture a train: the header flit is the locomotive, it sets the route, and the data flits follow nose to tail, spread across several routers at once. So the latency of a whole packet is roughly the header's travel time plus one cycle per data flit, not hops × packet length.

Let's put small numbers on it. Sending one 32×32 bfloat16 tile (2,048 B) over 3 hops on Wormhole:

  • Data flits: 2048 / 32 = 64, plus 1 header = 65 flits.
  • Header arrives after ≈ 5 + 3×9 + 5 = 37 cycles. The last flit arrives about 64 cycles later, so ≈ 101 cycles ≈ 0.1 µs with no congestion.
  • Useful fraction of the link: 64/65 ≈ 98.5%. A maximum packet is 8192 / (8192 + 32) ≈ 99.6%. A 4-byte write is one header flit carrying 4 bytes of payload, so the link is mostly overhead. The spec makes this point: “the amount of useful throughput depends on the ratio of header flits to data flits” (README.md:68).

Now compare the scales. One Wormhole link moves 32 GB/s; the whole Wormhole DRAM system is specified at 288 GB/s at 12 GT/s, and a microbenchmark reached 267 GB/s (Saturating_DRAM_bandwidth.md:64-67). So a single core reading over a single NoC can't come close to saturating DRAM, and it shouldn't try. That is why the tech report used “one DRAM reader per bank” across 12 cores (Saturating_DRAM_bandwidth.md:24).

These latencies are derived from the ISA performance table with zero congestion. They are not measurements, and ttsim, where a transfer completes the moment it is issued, will not reproduce them (see below).

What you can send: reads, writes, atomics, multicast

The NIU understands three request types, chosen by the 2-bit field at the bottom of NOC_CTRL: NOC_CMD_RD (0), NOC_CMD_AT (1) and NOC_CMD_WR (2) (MemoryMap.md:55). Flag bits refine them. The two address registers have a naming quirk worth learning once. NOC_TARG_ADDR is the “target” and NOC_RET_ADDR is the “return” address, but which one is the source of the data depends on the request type (MemoryMap.md:86-91):

ReadTARG (remote, e.g. DRAM)RET (usually your own L1)the response is the data; always sent
WriteTARG (your own L1)RET (remote)1-flit ack if RESP_MARKED; none if posted
Inline write (WR_INLINE)32-bit immediate in NOC_AT_DATATARGack if non-posted
Atomicimmediate operandan aligned 16-byte line in remote L1 (TARG)old value written to RET, if non-posted
Multicast (BRCST_PACKET)your L1every Tensix in a rectangleone ack per receiver if non-posted
  • Posted vs non-posted. A posted write saves the ack packet, but then the sender can never find out when the write has landed. “Optionally posted (i.e. receiver does not send an acknowledgement packet in response once the write completes)” (README.md:31).
  • Atomics act on L1 only, never DRAM or MMIO (Atomics.md:3). The menu is increment (on the low n bits of a word), compare-and-swap, and two swap variants (Atomics.md). Metalium's noc_semaphore_inc is an atomic increment.
  • Inline writes carry their data in the header, so they cost a single flit. Blackhole has “an unfortunate regression [so] that NOC_CMD_WR_INLINE can no longer safely be used to write to L1 addresses” (BH README.md:44). ttsim enforces this: on Blackhole an inline write to L1 is UndefinedBehavior (ttsim/src/tile.cpp:1558-1559).
  • Multicast (the spec calls it broadcast) sends one packet that the routers copy into a tree, so each link carries the data once even though many tiles receive it. Only Tensix tiles receive; other tiles inside the rectangle “opt out” (README.md:33; RoutingPaths.md:23). Reads cannot be multicast (MemoryMap.md:59). Blackhole adds a NOC_BRCST_EXCLUDE register “allowing for non-rectangular broadcasts” (BH MemoryMap.md:56).

How does one packet reach a whole rectangle? With X as the major axis (the default), “packets will travel along the major axis as necessary, then along the minor axis as necessary, and finally on the major axis again as necessary” (RoutingPaths.md:23). In the figure below, the packet goes right to the rectangle's first column, travels down that column, and at every row it forks rightwards.

Multicast is the NoC's answer to a question that comes up constantly in matmul: 64 cores need the same row of A, so must it be read 64 times? No. One core reads it and multicasts it, and the routers copy the flits at each fork. In the ISA example above, one packet reaches 16 Tensix tiles and uses 28 link traversals; 16 separate unicasts from the same source would need 132. A16 builds a full multicast matmul on this idea.

Multicast has a deadlock hazard of its own. Two broadcasts whose trees share links can each grab part of the other's path. The hardware offers NOC_CMD_PATH_RESERVE: “all routers along the path need to reserve virtual channel numbers for the transaction before any data leaves the initiating NIU” (MemoryMap.md:62). Without it, “software is responsible for ensuring that its traffic patterns do not cause deadlocks”. ttsim on Wormhole refuses multicasts without path reservation (tile.cpp:1421-1423), so the multicast matmul passing in ttsim tells us tt-metal sets the flag.

Virtual channels and the dateline

A cut-through network has a classic failure mode. A packet's flits are spread across several routers, and each router holds buffer space for them. If packet P1 holds a buffer that P2 needs, P2 holds one that P3 needs, and so on around a loop back to P1, nobody can move again. That is deadlock. A ring is the perfect place for such a loop, and a torus is made of rings.

The standard cure is the virtual channel (VC): several independent sets of buffers multiplexed over each physical link, so that a packet waiting in one VC doesn't block packets in another. Add a dateline, a fixed point on each ring. Every packet starts on the “before the dateline” VC and switches to the “after the dateline” VC when it crosses that point. A packet never goes all the way round a ring, so it never crosses the dateline twice. Buffers before the line can wait on buffers after the line, but never the other way round, and the cycle of waiting is broken.

Tenstorrent's version, at the level the ISA describes it: each hop assigns a packet a 4-bit virtual channel number made of “one dateline bit, two class bits, and one buddy bit” (README.md:46). The dateline bit “always flips at certain statically predetermined points along the packet's route”. Each router's NOC_NODE_ID says whether the dateline bit can flip on its outbound X or Y port (MemoryMap.md:187-188). The class bits separate traffic kinds: 00 and 01 for unicast requests, 10 for broadcast requests, 11 for responses. Keeping responses in their own class matters: a request can't complete until its response gets through, so responses must never get stuck behind requests. The buddy bit gives each class two lanes, and routers may flip it at each hop to dodge congestion.

On the software side, tt-metal's ordering page says there are “6 VC (numbered 0-5)” per NoC, with unicast writes on VC 1 and multicast writes on VC 4 (docs/.../data_movement/ordering.rst:15-16; dataflow_api_common.h:62-64). The two descriptions agree once you decode them. The 3-bit static VC field in NOC_CTRL is the buddy bit (bit 13) plus the two class bits (bits 14-15) (MemoryMap.md:65-66). The three request classes × 2 buddies give 6 values: VC 1 = class 00, buddy 1; VC 4 = class 10 (broadcast), buddy 0. The dateline bit is not chosen by software, and response VCs aren't selectable.

For ordinary unicast traffic the hardware guarantees deadlock freedom. Software takes on part of that job only when it uses multi-packet linked transactions (VC_LINKED), broadcasts without path reservation, or non-zero arbitration priority (README.md:39-42).

Weak ordering, counters and barriers

Suppose a writer core sends a 2 KiB tile to a reader core, then writes a “ready” flag into the reader's L1. On a CPU with a simple memory model you would expect the flag to arrive last. On the NoC, maybe not.

The rule from the ISA spec (Ordering.md:13): two packets are guaranteed to stay in order only where they share a route and “at every hop along that route, both are assigned the same virtual channel number”. Change any of that and they can overtake each other. tt-metal's ordering page summarises it for writes (ordering.rst:24-28):

  • “If writes are on different NoCs, there is no ordering guarantees.”
  • “If writes are on the same NoC but different VCs, there's also no ordering guarantees.”
  • “If writes are on the same NoC and same VC, they will be ordered based on program order.”

Responses have it worse: “Software has no way of controlling virtual channel number assignment for response / acknowledgement packets … so these types of packets can always get reordered or interleaved” (Ordering.md:18). Even inside one packet, writes into L1 are broken into 16-byte units that “could happen in any order” (Ordering.md:5).

So how does a core know a transfer has finished? Not by watching the network, but by watching counters. Each NIU keeps a bank of them at NIU_BASE + 0x200 (Counters.md:3-9). The two you'll meet constantly are NIU_MST_RD_RESP_RECEIVED (counter 2), which increments when a read response has been written into your L1, and NIU_MST_WR_ACK_RECEIVED (counter 1), which increments when a write acknowledgement arrives. The NIU has no “wait” instruction. tt-metal's firmware keeps its own software count of how many requests it issued, and a barrier is just a loop comparing the two:

The NoC is weakly ordered by design, because reordering is what lets it use free bandwidth. A barrier doesn't stop the network; it makes your core wait until a counter proves the data has landed. This is also “the only approach if software needs ordering between requests which travel on different NoCs” (Ordering.md:32).
Posted writes produce no acks, so noc_async_write_barrier cannot wait for them. And a missing barrier will not show up in ttsim (see below); real silicon will find the race.

Three kinds of coordinates

So far every coordinate on this page has been a NoC 0 coordinate: (0,0) at the top-left, x growing to the right and y growing downwards, the direction NoC 0's data flows (Coordinates.md:7). That is the coordinate system used throughout this page. But there are others.

  1. NoC 1 coordinates put (0,0) at the bottom-right and also count in the direction of data flow, leftwards and upwards (Coordinates.md:13). On Wormhole, x1 = 9 − x0 and y1 = 11 − y0. tt-metal has macros for exactly this: NOC_0_X_PHYS_COORD(noc_index, noc_size_x, x) returns noc_size_x - 1 - x on NoC 1 (noc_nonblocking_api.h:30-31).
  2. Translated coordinates. The NIU can translate coordinates as the command is issued, “which happens as software writes to NOC_CMD_CTRL” (Coordinates.md:19). Firmware programs the tables so that the same numbers mean the same tile on both NoCs, similar tiles get contiguous ranges, and harvested (fused-off) rows move to the end. On Wormhole, x 16-25 and y 16-27 are translated, and 0-15 pass through unchanged. For example, X 18 → NoC 0 x 1, NoC 1 x 8 (the leftmost Tensix column), and Y 18 → NoC 0 y 1 (the topmost Tensix row) (Coordinates.md:27-58).
  3. Logical coordinates are what a Metalium host program uses: CoreCoord{0,0} means “the first worker core”, wherever it physically is. The host turns these into NoC addresses for your kernels. A09 and A10 use them.

Translation has one catch: “when performing broadcasts, StartX ↔ EndX need to be swapped by software, and likewise StartY ↔ EndY … because coordinate translation does not change the direction of data flow” (Coordinates.md:25). A rectangle walked in NoC 1's direction has its corners the other way round. Blackhole goes further: its translation is “combined” across X and Y rather than separable (BH Coordinates.md:26), with translated Tensix columns at x 1-7 and 10-16 and DRAM at x 17-18.

Programming the NIU: one store starts a transfer

We have treated “send a packet” as a single action. From the RISC-V core's side it is a handful of 32-bit stores into memory-mapped registers. Each NIU has four request initiators (tt-metal calls them command buffers), each a block of registers at NIU_BASE + i×0x400, with NIU_BASE = 0xFFB2_0000 for NoC 0 and 0xFFB3_0000 for NoC 1 on Wormhole (MemoryMap.md:3-9, 30-41). tt-metal dedicates them by purpose: buffer 0 for writes, 1 for reads, 2 for small register-sized writes, 3 for atomics (noc_nonblocking_api.h:48-56).

  • noc_cmd_field assembles the NOC_CTRL bits we've met: request type WR, a static VC, the multicast and path-reserve flags, and RESP_MARKED (non-posted) unless the write is posted.
  • NOC_TARG_ADDR_LO = the local L1 source address (for a write, TARG is the source).
  • NOC_RET_ADDR_LO / _COORDINATE = the remote destination: the low 32 address bits, then the upper bits with x and y packed above bit 36 on Wormhole (MemoryMap.md:95-99).
  • NOC_AT_LEN_BE = the length in bytes.
  • The last store, 1 into NOC_CMD_CTRL, is the trigger. The NIU queues the request, assigns a VC and sends it, then clears the bit. Software must not touch the initiator until that bit reads 0 again (MemoryMap.md:150-156). The RISC-V core moves on immediately; the transfer proceeds “asynchronously to RISCV execution” (README.md:56).

noc_cmd_ctrl (tile.cpp:1397-1623) reads like a checklist of this chapter. It decodes NOC_CTRL bit by bit, rejecting features it doesn't model (byte-enable writes, BRCST_XY, arbitration priority) with UnimplementedFunctionality. It checks static-VC classes (“class 2” only for multicast). It translates coordinates with remap_virtual_coordinate, then branches on the five request kinds: multicast, atomic, inline write, write and read. Here is the plain write:

  • The length check enforces the packet limit: NOC_MAX_PACKET_SIZE is 8192 on Wormhole and 16384 on Blackhole (config.h:47, 81). ttsim doesn't model the hardware's automatic splitting of larger requests (Counters.md:167-173).
  • (src_addr & 15) == (dst_addr & 15) is the ISA's “C16” rule: source and destination must be congruent mod 16 for L1 data (Alignment.md:17). Break it and you get UndefinedBehavior, which is lab B05's alignment trap. Reads from DRAM need mod 32 on Wormhole and mod 64 on Blackhole (tile.cpp:1605-1612).
  • tile_wr_bytes(...) copies the bytes into the destination tile's memory, right now, inside the store instruction. No packet, no hops, no flits.
  • Then the counters are bumped immediately. For a non-posted write, niu_mst_wr_ack_received goes up in the same call, as though the ack had already come back.
ttsim delivers every NoC transfer instantly. That is the right call for a functional, bit-exact simulator, but it means ttsim can't show you anything on this page that depends on time: hop latency, congestion, VC interleaving, reordering. By the time a kernel reaches noc_async_write_barrier(), the hardware counter already equals the software count, so the barrier always passes at once, and a missing barrier is invisible. ttsim does catch illegal requests: misalignment, oversized packets, multicast to non-Tensix tiles, inline writes to L1 on Blackhole.

Recap

  • A bus doesn't scale and a crossbar costs N², so Tenstorrent uses a 2D torus of small routers: one router and one NIU per grid position, short links, bandwidth that grows with the chip.
  • There are two physically separate NoCs: NoC 0 flows only right and down, NoC 1 only left and up, both wrapping at the edges.
  • Routing is dimension-order and deterministic: NoC 0 does X then Y, NoC 1 does Y then X. For any pair differing in both axes, the two hop counts sum to width + height (22 on Wormhole), so the shorter NoC is never more than 11 hops.
  • A read's round trip on one NoC is always the full loop; the choice of NoC decides which leg carries the data. Using both NoCs also doubles per-tile bandwidth (by convention, readers on NoC 0 and writers on NoC 1).
  • Packets are a header flit plus up to 256 data flits: 32 B / 8 KiB on Wormhole, 64 B / 16 KiB on Blackhole. One flit per cycle per link, 9 cycles per hop, cut-through. That gives a derived 32 GB/s (WH) or 86.4 GB/s (BH) per link.
  • Requests: read, write (posted or not, inline), atomics on L1, and rectangle multicast to Tensix tiles, which copies data at tree forks.
  • Virtual channels (dateline, class and buddy bits) keep the torus deadlock-free and separate requests from responses.
  • The NoC is weakly ordered. Completion is observed through NIU counters, and barriers spin until a counter matches what software issued.
  • A transfer starts with a few MMIO stores into a command buffer, ending in NOC_CMD_CTRL = 1. ttsim models that store as an instant copy, so it checks legality but not timing or ordering.

Check yourself

On Wormhole, core (7,4) writes 2 KiB to core (6,4). Which NoC should it use, and how many hops is each option?

Same row, one column to the left. NoC 0 can only go right, so it goes 7→8→9→0→…→6: 9 hops. NoC 1 goes left directly: 1 hop. The data travels on the request leg of a write, so use NoC 1. (9 + 1 = 10, the row length, because y is the same.)

A colleague says “my read from DRAM is 19 hops on NoC 0, so I'll switch to NoC 1 and make it 3 hops”. What happens to latency and to link usage?

The round trip stays the same: request plus response is 22 hops on either NoC, because the response returns on the same NoC. What changes is which leg is long. On NoC 0 the 1-flit request takes 19 hops and the 65-flit data response takes 3; on NoC 1 the data takes 19 hops. Switching makes the read occupy roughly six times as many link-cycles and is likely to congest other traffic.

Why can a multicast reach 16 cores with far fewer link traversals than unicasting to each one?

The routers copy flits at the forks of the broadcast tree, so each link in the tree carries the data once. Separate unicasts each walk their own full route from the source, re-crossing the shared links. In the ISA example that is 28 traversals for the tree against 132 for 16 unicasts. Only Tensix tiles receive; other tiles in the rectangle opt out.

A writer sends a tile with noc_async_write on NoC 0, then sets a flag in the reader's L1 with a write on NoC 1. Without a barrier, is the reader guaranteed to see the new tile when it sees the flag?

No. Packets on different NoCs (or different VCs) have no ordering guarantee. The flag can overtake the data. The writer must call noc_async_write_barrier() (wait until NIU_MST_WR_ACK_RECEIVED matches the issued count) before sending the flag. The ISA calls this request-wait-for-response approach the only way to order requests across NoCs.

You delete the barrier from that kernel and it still passes in ttsim. Why, and what does that prove?

ttsim's noc_cmd_ctrl copies the bytes and increments the ack counter inside the store that triggers the transfer. Every transfer has already completed when the next instruction runs, so reordering can't happen and every barrier passes immediately. A pass in ttsim proves the kernel is functionally correct if transfers were instant. It says nothing about races on real hardware.

tt-metal says there are 6 VCs per NoC; the ISA says the VC number is 4 bits. Who is right?

Both. Software chooses a 3-bit static VC (2 class bits + the buddy bit) for requests, and only classes 00, 01 and 10 are for requests: 3 × 2 = 6 values, 0-5. The hardware VC number adds the dateline bit, which flips at fixed points on the route and is not chosen by software, and response traffic has its own class 11. 16 combinations in all, matching the “12 request + 4 response” channels a receiving NIU can process at once (Ordering.md:20).
