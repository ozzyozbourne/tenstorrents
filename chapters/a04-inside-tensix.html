The question

In A03 we walked across the chip and saw a Wormhole die with 80 Tensix tiles in a grid. Now we open one up. The first surprise is that one Tensix tile contains five RISC-V CPUs, and the second is that none of them does the math. So:

Why does one core need five CPUs, none of which does the math?

Here's a toy problem to start. You want to add two 32×32 matrices that sit in local SRAM and write the sum back to SRAM. That's 1024 additions. A simple in-order CPU core could do it in a loop: load, load, add, store, 1024 times. On this chip that loop is painfully slow. As we'll see, a baby RISC-V core can only store to SRAM once every five cycles, so writing the 1024 results alone takes thousands of cycles. The matrix unit next to it can add a whole 8×16 block of numbers per instruction.

So the work splits into two kinds. Deciding what to do (loops, addresses, which tile comes next, when it's safe to proceed) is branchy, scalar work that suits a CPU. Doing it (moving kilobytes and multiplying matrices) is wide, regular work that suits dedicated hardware. A Tensix tile gives each kind its own machinery. Small CPUs make the decisions and push commands to big engines that do the work. Five CPUs are there because there are five streams of decisions to make at once: two for moving data over the network and three for feeding the compute engine.

The rest of this chapter turns that sentence into a picture, then into code, and then into a bug you can reproduce in the simulator.

A map of one Tensix tile

The ISA documentation lists what a Wormhole Tensix tile contains: 1464 KiB of RAM called L1, five "baby" RV32IM cores, two NoC connections plus a NoC overlay, and one Tensix coprocessor. The coprocessor itself holds two unpackers, a matrix unit (FPU), a vector unit (SFPU), a scalar unit (ThCon) and four packers, plus a few small utility devices (TensixTile/README.md). Look at where the arrows go. Data never passes through a RISC-V core on its way to the FPU. It flows L1 → unpacker → SrcA/SrcB → FPU → Dst → packer → L1. The RISC-V cores sit off to the side and only send commands. That's the first answer to the opening question: the CPUs are the control plane, and the coprocessor and NoCs are the data plane.

A Tensix tile is one big data engine (the coprocessor plus two NoC connections) steered by five small CPUs. The CPUs decide what to do; the engines move and compute the bytes.

Five baby RISC-Vs

The ISA docs call them "baby" cores: 32-bit, in-order, single-issue, designed for area and power rather than speed, each meant to run one RV32IM instruction per cycle at 1 GHz on Wormhole (BabyRISCV/README.md). They are named B, NC, T0, T1 and T2. TT-Metalium calls them BRISC, NCRISC and TRISC0–2 and gives each a fixed job:

A few details tell you what kind of CPU these are:

  • RV32IM only. There is no "A" extension (no atomics), no "C" extension (no compressed instructions), and no floating point. fence runs as a nop, so it cannot enforce memory ordering. There is one custom extension, .ttinsn, which we'll take apart below.
  • They cannot fault. Unaligned accesses are silently rounded down. A load from unmapped memory usually hangs forever. Invalid instructions are UndefinedBehavior.
  • The local data RAM is the fast memory. A load from local RAM has 2-cycle latency and never contends. A load from L1 takes at least 8 cycles. The docs strongly recommend putting the call stack and hot variables in local RAM (BabyRISCV/README.md:117-119).

Look at the instruction-memory column too. TRISC1, the core that runs the math, has the smallest instruction cache: half a kilobyte. That only makes sense if the math loop doesn't run as RISC-V code. In practice it lives inside the coprocessor's MOP and replay expanders, so TRISC1 issues a handful of instructions that expand into hundreds. We'll see one MOP become eight ELWADDs in the simulator.

A GPU SM has its own instruction fetch, and its warp schedulers issue math instructions straight from the program stream. A Tensix tile splits that job in two. The RISC-V cores fetch and run ordinary code, and the coprocessor never fetches anything: it only executes what is pushed into it. The nearest GPU analogy is a CPU thread feeding a command queue to a DMA engine or tensor core, except that here the "host" is a tiny in-order core sitting right next to the engine, and there are three of them feeding one engine at once.
"Five cores per tile" does not mean five independent programs on equal footing. In TT-Metalium a compute kernel is one source file compiled three times, once each for TRISC0, TRISC1 and TRISC2, with the UNPACK(...), MATH(...) and PACK(...) macros selecting which lines each copy keeps. That's the topic of A12. This chapter is about the hardware those three copies run on.

L1: 1464 KiB of plain RAM, in 16 banks

"L1" sounds like a cache. It isn't: it's a software-managed scratchpad with no tags and no eviction, and nothing moves in or out unless something is told to move it (L1.md). On Wormhole it is 16 banks of 91.5 KiB. Each bank does one 128-bit read or one 128-bit write per cycle, reached through 16 access ports. Any port can reach any bank, but if two ports hit the same bank in the same cycle, all but one wait. Some ports are shared by several clients, which then take turns round-robin.

The ports do slightly more than the banks underneath them. A narrow read (under 128 bits) reads all 128 and throws the rest away, so it costs the same bandwidth as a full read. A narrow write is a read-modify-write that blocks the port and bank for five cycles. The same 5-cycle read-modify-write is used for atomic increments and compare-and-swap (offered to the NoC and ThCon) and for the packers' near-memory accumulate.

Now look at the baby RISC-V from L1's point of view. Every RISC-V store is a narrow 32-bit store, so it takes five cycles. Every load is narrow too, and only four can be in flight, so well-scheduled loads top out around 18 bits/cycle and dependent loads manage 4. The figure compares the clients L1 serves. Switch it to "cycles to move one BF16 tile" to make the numbers concrete.

A RISC-V core copying a 2 KiB tile word by word needs about 2,560 cycles just for the stores. A single unpacker reads the same tile in about 32. That two-orders-of-magnitude gap is the hardware's way of saying "don't move data with the CPU". The ISA docs say so plainly: RISC-V cores "are strongly encouraged to instruct other clients to access L1 on their behalf", namely the mover, an unpacker plus the packers, or a NoC (L1.md:25-27).

Being able to lw and sw L1 from a kernel doesn't make it cheap. Keep RISC-V code to control: counters, pointers, small arguments. Things that look like a loop over data elements belong to an engine. (Debug prints and small mailboxes are fine.)

Bank conflicts are the other cost. The ISA docs give the bank count and the port assignment, but this chapter doesn't depend on which address bits pick a bank, so I won't guess at it here. For how tt-metal lays out buffers across L1 and DRAM, see A09.

The coprocessor: three threads, one backend

Now the big box. The Tensix coprocessor runs three instruction streams, called threads T0, T1 and T2, at up to one instruction per thread per cycle. Normally RISC-V Ti feeds thread Ti. The key design choice is in the first paragraph of its documentation: "Instructions are not pulled from memory — instead the Baby RISCV cores push instructions to the three threads" (TensixCoprocessor/README.md).

Frontend: one copy per thread

Each thread has its own frontend of three in-order stages, joined by FIFOs:

  1. MOP expander. Turns one MOP instruction into a loop of up to 32,639 instructions (on Wormhole) from a per-thread template (MOPExpander.md).
  2. Replay expander. A 32-entry buffer per thread. REPLAY either records the next N instructions or plays back N recorded ones, for straight-line sequences (REPLAY.md).
  3. Wait gate. Decides when the instruction at the head may enter the backend. It holds the instruction if the unit is busy, if another thread won the unit this cycle, if a mutex is held, if SrcA/SrcB are not yet handed to the FPU, or if a STALLWAIT/SEMWAIT condition isn't met (WaitGate.md).

The two expanders exist because a RISC-V can't push an instruction every cycle and still do its own bookkeeping. With them, a TRISC can push slowly and the backend still gets one instruction per cycle. (How LLK code configures MOPs is in A13.)

Backend: nine units, mostly shared

After the wait gate, an instruction goes to one of nine units: Sync, Unpackers, Matrix (FPU), Packers, Vector (SFPU), Scalar (ThCon), Configuration, Mover and Miscellaneous. They run in parallel, so reordering starts here. The frontend is in order, but an ELWADD on T1 and a PACR on T2 can run in either order unless something forces one to wait.

Each instruction remembers which thread sent it, so per-thread state (some configuration, GPRs, address counters, mutex ownership) stays separate. Most of the backend exists only once, though. That includes the registers the engines work on:

How a TRISC pushes an instruction

If the coprocessor doesn't fetch, how does an instruction get in? Through a memory-mapped store. A Tensix instruction is a 32-bit word, and a TRISC pushes it with an ordinary sw of that word to INSTRN_BUF_BASE = 0xFFE4_0000. The address is the same for all three TRISCs, and each one's store lands in its own thread's FIFO. BRISC can also reach T1 and T2 through 0xFFE5_0000 and 0xFFE6_0000. NCRISC has no mapping at all. If the FIFO is full, the store simply stalls the RISC-V until there's room (PushTensixInstruction.md).

tt-metal names the address in two places:

tt-metal/tt_metal/hw/inc/internal/tt-1xx/wormhole/tensix.h:52 and tt_metal/hw/toolchain/main.ld:414 @7aad8aac
#define INSTRN_BUF_BASE 0xFFE40000
PROVIDE(__instrn_buffer = 0xFFE40000);

The .ttinsn trick

An sw needs a register holding the value and a register holding the address. Before that, each instruction has to be loaded into a register with lui/addi. That's three or so RISC-V instructions per Tensix instruction, and pushing is the most common thing a TRISC does. So the baby cores add one custom encoding. If the low two bits of a 32-bit RISC-V instruction are not 11, the core treats the word as a Tensix instruction: it rotates the word right by two bits and pushes the result to 0xFFE40000. The behaviour is exactly that of the sw.

Why the low two bits? In standard RISC-V, every 32-bit instruction ends in 11, and the other three patterns are reserved for the 16-bit "C" extension, which these cores don't implement. That space was free. The assembler builds .ttinsn IMM32 by rotating IMM32 left two bits. This only works if the top two bits of IMM32 aren't both 1, because those bits become the low bits. So every valid Tensix instruction is below 0xC000_0000, and the docs note that this always holds. Step through it:

Line by line:

  • The tile check. A .ttinsn outside a Tensix tile (on an Ethernet core, for example) is undefined behaviour, so ttsim stops.
  • Choosing the thread. TRISCi pushes to thread i (pipe = riscv_id - RV32_ID_TRISC0). BRISC writes to thread 0 and bypasses the MOP expander. That matches the ISA memory map, where BRISC's store to 0xFFE40000 enters "after T0 MOP expander". NCRISC fails the TTSIM_VERIFY, matching the hardware, where it can't push.
  • Undoing the rotation. (inst << 30) | (inst >> 2) is a rotate right by 2, the inverse of the assembler's rotate left.
  • Back-pressure. If the FIFO is full, ttsim sets the PC back by 4, so the same .ttinsn runs again next step. That's how ttsim models "the store stalls until FIFO space is available". In ttsim, tensix_can_push_inst refuses when the thread's expanders are busy or more than 52 entries are queued (tensix.cpp:284-293). That threshold is ttsim's own choice. The Wormhole ISA page doesn't give a FIFO depth, so don't read 52 as a hardware number.

Two flavours appear here. TTI_ ("immediate") instructions are compile-time constants and become a single .ttinsn. Blackhole goes further. Its TRISC instruction caches can fuse up to four adjacent .ttinsns into one cycle, so a thread can enqueue four Tensix instructions per cycle, although the frontend still dequeues only one per thread per cycle (BlackholeA0 BabyRISCV/README.md). Blackhole's baby cores also get a 64-byte, non-coherent L0 data cache and twice the local RAM (8 KiB for B/NC, 4 KiB for T). They run at 1.35 GHz and are no longer plain RV32IM: they add Zicsr, Zaamo (atomics), Zba/Zbb and parts of F/Zfh, and T2 gets part of V. L1 grows to 1536 KiB.

The RISC-V runs ahead

Look again at the last line of tti(). Once the push succeeds, the function returns and the RISC-V moves on to its next instruction. Nothing waits for the Tensix instruction to execute. The ISA docs make this the central warning about the coprocessor:

"Once a RISCV core has pushed a Tensix instruction, execution of the RISCV core proceeds completely asynchronously to execution of the Tensix Coprocessor. […] the RISCV can get quite far ahead before the pushed instruction actually executes." (TensixCoprocessor/README.md:9)

Think of a restaurant pass. Three waiters (the TRISCs) each spike order tickets onto their own rail (the FIFOs). A waiter who has spiked a ticket goes off to take the next order without waiting for the food. The kitchen (the backend) has one grill (the FPU), one set of plates being plated (Dst) and one pass to the dining room (the packers). The waiters' rails are each strictly first-in, first-out. Nothing on the rails says that table 7's plate can't go out until table 7's steak is cooked. If the plating waiter's ticket reaches the pass first, an empty plate goes out.

Here's where the analogy breaks. Real waiters would notice an empty plate. The Tensix backend won't. The rails also have a fixed length: once a rail is full, the waiter is forced to stand and wait. Back-pressure exists, but it limits how far ahead the RISC-V gets. It doesn't order one thread against another.

Things to watch in each mode:

  • With sync. TRISC0 and TRISC1 have pushed everything by cycle 5 and show "done", while the coprocessor needs about 20 more cycles to finish their work (and the whole tile isn't done until cycle 37). That's "running ahead". TRISC2 gets far enough ahead to fill its FIFO (4 entries in this toy) and stalls. Unless the code explicitly asks to wait (TTSync, or polling a semaphore), back-pressure is the only thing that makes a RISC-V wait for the coprocessor. The PACK thread's SEMWAIT sits red at its gate, and the PACR waits in the FIFO behind it, until MATH's SEMPOST raises MATH_PACK to 1. (A simplification: on the hardware the SEMWAIT itself passes into the wait gate and stays latched there, and the gate holds the PACR behind it. The figure draws the two as one hold.) Then the packer copies a fully written Dst, and the release sequence (STALLWAIT, ZEROACC, SEMGET) hands Dst back.
  • Remove wait and release. TRISC2's program is now a single PACR. It passes its gate almost at once, because nothing tells it to wait. The packer copies Dst while the unpackers are still filling SrcA/SrcB, before any ELWADD has run. The output tile is all stale values.
  • Remove only tile_regs_wait. The PACK thread runs its release early and issues SEMGET while the semaphore is still 0. On silicon that's NonContractualBehavior (the value just stays at 0). ttsim refuses to continue.

How you write kernels with these is A12's job.

Unpack → math needs no semaphore in this kernel. The FPU instruction can't pass its wait gate until the unpacker hands the SrcA/SrcB bank to the matrix unit, and that check is in hardware (WaitGate.md). Dst has no such check, so the math → pack direction needs software synchronization.

The frontend keeps each thread's instructions in order. Nothing keeps the three threads in order relative to each other, or relative to the RISC-V that pushed them. Every cross-thread dependency through shared state (Dst above all) needs an explicit semaphore, mutex or stall.
A second "runs ahead" trap involves no other thread. A RISC-V that pushes an instruction and then writes a configuration register with sw may change the configuration before its own earlier instruction reads it, because that instruction may still be queued. The ISA docs call this out (TensixCoprocessor/README.md:9 and PushTensixInstruction.md "Memory ordering"). The fixes are to change configuration through Tensix instructions in the same stream, or to wait for the coprocessor first. For that wait, TRISCs have TTSync: a load from a special address that doesn't return until the thread has no instructions in flight (BabyRISCV/TTSync.md). tt-llk wraps it as tensix_sync(), which you can see at the top of _llk_math_pack_sync_init_.

The Sync unit: 8 semaphores, 7 mutexes

Everything above runs on a very small piece of hardware (SyncUnit.md):

  • Eight semaphores. Each is a 4-bit Value (reset 0) with a 4-bit Max (reset 15).
    • SEMINIT sets both fields. SEMPOST adds one and SEMGET subtracts one.
    • SEMWAIT blocks the thread at its wait gate while Value == 0 or while Value >= Max. Its block mask picks which kinds of instruction it holds.
    • There is no combined "wait then decrement". That's why the PACK side issues SEMWAIT first and SEMGET later.
  • RISC-V access. TRISC0–2 can lw a semaphore's value, and an sw increments it (even value) or decrements it (odd value). _llk_math_pack_sync_init_ polls semaphore_read(MATH_PACK) this way (llk_math_common.h:108). One hardware bug to know about: after starting a semaphore load, a TRISC must not start another one until the first completes, or it can hang.
  • Seven mutexes, numbered 0 and 2–7. Each is either free or held by T0, T1 or T2. ATGETM waits for a mutex and takes it; ATRELM releases it. tt-llk reserves indices such as REG_RMW = 0 (atomic register read-modify-write across threads) and SFPU = 4 (the SFPU can be fed from both TRISC1 and TRISC2) in ckernel_structs.h:35-44. Blackhole cuts the mutex count to four.

tt-llk names all eight semaphores (ckernel_structs.h:12-24): FPU_SFPU=0, MATH_PACK=1, UNPACK_TO_DEST=2, UNPACK_OPERAND_SYNC=3, PACK_DONE=4, UNPACK_SYNC=5, UNPACK_MATH_DONE=6 and MATH_DONE=7. The Dst handshake needs only one of them. In SyncHalf mode its Max is 2, which lets MATH fill one half of Dst while PACK drains the other (llk_math_common.h:98-120). That's why ttsim's error message says sem_max=2.

Don't confuse these 4-bit hardware semaphores with the TT-Metalium CreateSemaphore / noc_semaphore_* semaphores, which are plain words in L1 that other cores update over the NoC. The Sync unit's semaphores are private to one tile's three Tensix threads and its TRISCs. Cross-core synchronization is A16.

Seeing it in ttsim

Everything above can be checked in the simulator, and I ran each experiment in this orb on ttsim b3620244 (Wormhole build) with the prebuilt tt-metal example add_2_integers_in_compute, which adds two BF16 tiles on core (0,0).

1. Counting pushes

I built an instrumented copy of ttsim with sim-labs/workbench/build_ttsim.sh push wh. My instrumentation is not part of ttsim: it adds a few counters in tti() (the .ttinsn path), in tensix_inst_wr32() (the sw path) and in tensix_push_inst_fifo() (after the expanders), and prints them when the process exits. The patch is sim-labs/patches/a04-push-counters.patch.   • NCRISC pushed nothing, as the hardware requires. 2. Removing the synchronization

Next I used the kernel overlay to put a modified add_2_tiles.cpp at $LAB_HOME/kernels/tt_metal/programming_examples/add_2_integers_in_compute/kernels/compute/, running on the stock ttsim. With only tile_regs_wait(); commented out:

[4499] ERROR: NonContractualBehavior: tensix_semget: sem=0 sem_max=2

ttsim stops at the PACK thread's SEMGET, because the semaphore is still 0. Without its wait, PACK got there before MATH's SEMPOST. The check that fired:

ttsim/src/tensix.cpp:5544-5553 @b3620244
TENSIX_EXECUTE_SEMGET() {
    ...
    TTSIM_VERIFY(p_tensix->sem[sem_index], NonContractualBehavior, "sem=%d sem_max=%d", p_tensix->sem[sem_index], p_tensix->sem_max[sem_index]);
    p_tensix->sem[sem_index]--;
    return true;
}

With both tile_regs_wait(); and tile_regs_release(); commented out, nothing is left for ttsim to flag. The program runs to completion and the result is wrong everywhere:

Mismatch at index 0: expected 18.5625, got 0
Mismatch at index 1: expected 7.328125, got 0

Mismatch at index 1023: expected 8.9375, got 0

All 1024 elements are wrong, and every one reads 0. The packer copied Dst before ELWADD wrote it. A control run with the unmodified kernel prints Success: Result matches expected value! at [4682]. (The bracketed number is ttsim's clock count. ttsim isn't a timing model, so don't read these as performance figures.)

ttsim is functional and deterministic: its threads interleave the same way every run, and here that interleaving exposed the race every time. On silicon, timing decides which thread wins, so a missing semaphore can pass a test for weeks and then fail under different load. A ttsim run that passes doesn't prove a kernel has no races. It only shows that one particular interleaving gave the right answer.
Reproduce both experiments, then trace SEMPOST/SEMGET as they happen, in B04 and B06. To watch the cores come out of reset and see which PCs they start at, see B02.

Recap

  • A Wormhole Tensix tile has 1464 KiB of L1 (16 banks × 91.5 KiB, 128 bits per bank per cycle), five RV32IM baby cores, two NoC connections and one Tensix coprocessor.
  • The cores are the control plane. BRISC and NCRISC run data-movement kernels; TRISC0/1/2 run the UNPACK, MATH and PACK parts of a compute kernel. Each core has 2–4 KiB of fast local RAM (2-cycle loads). L1 is slow for them: ≥8-cycle loads and one store every 5 cycles. Bulk data should move through engines.
  • The coprocessor has three threads, each with an in-order frontend (MOP expander → replay expander → wait gate), feeding nine mostly shared backend units: Sync, Unpack, FPU, Pack, SFPU, ThCon, Config, Mover and Misc.
  • Registers: SrcA/SrcB are 2 × 64 × 16 × 19 bit, double-buffered. Dst is 1024 × 16 × 16 bit (32 KiB) and shared. LReg is 17 × 32 lanes × 32 bit. Details are in A06 and A07.
  • The coprocessor never fetches. A TRISC pushes a 32-bit instruction with sw to 0xFFE40000, or with a one-word .ttinsn: the instruction rotated left by 2, recognised because its low bits aren't 11. ttsim's tti() rotates it back with (inst << 30) | (inst >> 2).
  • After a push, the RISC-V runs ahead. Each thread stays in order internally, but threads aren't ordered against each other or against their RISC-V. The Sync unit (8 four-bit semaphores, 7 mutexes on WH) and STALLWAIT/TTSync restore order. Remove the MATH_PACK handshake and ttsim either reports an error or, with the whole handshake gone, packs zeros.

Check yourself

1. Why is TRISC1 (MATH) given only a ½ KiB instruction cache when it drives the core's most important unit?

Because its hot loop isn't meant to be RISC-V code. TRISC1 pushes a few instructions, typically a MOP, and the MOP and replay expanders turn them into long runs of FPU instructions at one per cycle. In the ttsim count, one MOP from TRISC1 became 8 ELWADDs. The RISC-V code is mostly setup and synchronization, which fits in a small cache.

2. A TRISC fetches the word 0x90000022. What does it do? What about 0x00150513?

0x90000022 ends in binary 10, not 11, so it's a .ttinsn. Rotating right by 2 gives 0xA4000008. The opcode byte is 0xA4 (SEMPOST) with sem_sel = 0b10, which is semaphore 1 (MATH_PACK). The core pushes that into its own Tensix thread. 0x00150513 ends in 11, so it's an ordinary RV32I instruction (addi a0,a0,1) and nothing is pushed.

3. Why must every valid Tensix instruction be below 0xC0000000?

The .ttinsn encoding rotates the instruction left by 2, so its top two bits become the low two bits of the RISC-V word. If both were 1, the word would end in 11 and the core would decode it as a normal RISC-V instruction. Keeping Tensix opcodes below 0xC0 in the top byte guarantees the low bits are 00, 01 or 10, the space RISC-V reserves for compressed instructions, which these cores don't implement.

4. TRISC2 executes its .ttinsn PACR and then immediately reads the output tile from L1 with lw. What can it see, and how would you fix it?

Probably old data. A successful push only means the instruction is in the FIFO. It may still be queued behind a SEMWAIT, or the packer may still be writing. To wait for the coprocessor, the TRISC needs an explicit mechanism, for example TTSync (a load that doesn't return until the thread has no instructions in flight) or a semaphore the Tensix thread posts after a STALLWAIT on the packer. The same reasoning applies to changing configuration registers with sw while earlier instructions that use them are still queued.

5. Why does the unpack → math hand-off in add_tiles need no semaphore, while math → pack does?

SrcA and SrcB have hardware ownership. Each bank has an AllowedClient (unpackers or matrix unit), and an FPU instruction can't pass its wait gate until the bank belongs to the matrix unit. Dst has no ownership tracking. It's one shared array that any thread can read or write, so the packer would happily read it mid-computation. Software provides the missing ownership with the MATH_PACK semaphore.

6. Your kernel passes on ttsim every time. Does that prove it has no synchronization bugs?

No. ttsim is deterministic and is not a timing model, so it tests one interleaving of the three threads. Silicon's interleaving depends on real latencies, contention and data. ttsim's checks (like the SEMGET at 0 check) catch some misuse, but a race whose wrong ordering never happens in ttsim's schedule goes unseen. Review every shared resource (Dst, configuration, CBs) for an explicit hand-off.
