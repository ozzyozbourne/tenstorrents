15. Matmul on one core, then many

Three real tt-metal programs compute the same 640×640 matmul. They read 16,000, 16,000 and 2,400 tiles from DRAM. By the end you will be able to predict those numbers from the loops, and explain why the third program uses only 5 of 64 cores on purpose.

The question

You have written a matmul kernel that runs on one Tensix core and takes time T. The chip has 64 worker cores in the configuration we simulate (an 8×8 grid). You copy the kernel to all 64, give each core 1/64 of the output, and launch. Does it finish in T/64?

Usually it does not, and the reason is not the compute. To see why, count something you can count exactly: tiles read from DRAM. tt-metal ships three versions of the same program in programming_examples/matmul/, and each multiplies two 640×640 bf16 matrices. In tiles that is Mt = Kt = Nt = 20, so A, B and C each have 400 tiles.

ExampleCoresDRAM tile readsTimes each input tile is fetched
matmul_single_core116,00020
matmul_multi_core6416,00020
matmul_multicore_reuse52,400A: 5, B: 1

These are not estimates. They come from the loops, and later in this chapter an instrumented ttsim counts every byte that every core pulls from DRAM and gets exactly these numbers. The minimum, if every input tile were fetched once, would be 800. Spreading the work over 64 cores did not reduce the DRAM traffic at all. It made 64 cores compete for the same 12 DRAM banks.

This chapter builds the matmul up in the order the examples do. First one core and its triple loop, then splitting output tiles over cores, then blocking, which is what actually saves the traffic.

Getting the data into tiles

Before the device sees anything, the host rearranges each matrix. Every example does the same thing right after it builds its random inputs:

tt-metal/tt_metal/programming_examples/matmul/matmul_single_core/matmul_single_core.cpp:225-232 @7aad8aac (condensed)
src0_vec = tilize_nfaces(src0_vec, M, K);
src1_vec = tilize_nfaces(src1_vec, K, N);
...
matmul_single_core(src0_vec, src1_vec, result_vec, false, M, N, K, mesh_device);
// Reverse the tilization to get the result in the row-major format that the CPU expects
result_vec = untilize_nfaces(result_vec, M, N);

A row-major 640×640 matrix stores row 0 (640 values), then row 1, and so on. One 32×32 tile is scattered over 32 different rows, 1280 bytes apart. tilize_nfaces gathers each tile into one contiguous 2048-byte run. Inside the tile it uses the face order from A05: four 16×16 faces (top-left, top-right, bottom-left, bottom-right), each stored row by row. Tiles are emitted in row-major tile order, so tile (mt, kt) of A becomes tile number mt·Kt + kt:

tt-metal/tt_metal/impl/data_format/tilize_utils.cpp:309-317 @7aad8aac
for (size_t row_tile = 0; row_tile < row_tiles; row_tile++) {
    size_t row_tile_start = tile_start;
    for (size_t col_tile = 0; col_tile < col_tiles; col_tile++) {
        if (!transpose_face_order) {
            for (size_t face_h_index = 0; face_h_index < tile_H / face_H; face_h_index++) {
                for (size_t face_w_index = 0; face_w_index < tile_W / face_W; face_w_index++) {
                    size_t src_idx = row_tile_start + (face_w_index * face_W) + (face_h_index * face_H * W);
                    write_face(src_idx, face_H, face_W, W);

So element (r, c) of the original matrix ends up at offset tile·1024 + face·256 + (r mod 16)·16 + (c mod 16), where tile = ⌊r/32⌋·(W/32) + ⌊c/32⌋ and face = 2·⌊(r mod 32)/16⌋ + ⌊(c mod 32)/16⌋. Why do this on the host? Because the DRAM buffer is created with page_size = single_tile_size (2048 bytes, line 82-88), and A09 showed that pages are dealt round-robin to the 12 DRAM banks. After tilizing, "page p" and "tile p" are the same thing, so a reader kernel can fetch tile (mt, kt) with one call: noc_async_read_page(mt*Kt + kt, ...). The output comes back tiled too, which is why the host calls untilize_nfaces before comparing with its CPU golden result.

Tilizing on the host is a teaching shortcut, not the production path. It costs a full pass over each matrix on the CPU. TT-NN can tilize on the device with a dedicated op, and keeps activations in TILE layout from one op to the next so the conversion happens rarely (A18).

One core: the triple loop

A tile matmul is block matrix multiplication with 32×32 blocks. Output tile C(mt, nt) is the sum over kt of A(mt, kt) · B(kt, nt), exactly like the scalar formula, but every "number" is a 32×32 tile. The single-core example splits this across the three kernels of A12: a reader that fetches tiles, a compute kernel that multiplies them, and a writer that stores results.

The reader streams A(mt, kt) and B(kt, nt)

tt-metal/tt_metal/programming_examples/matmul/matmul_single_core/kernels/dataflow/reader_single_core_mm.cpp:30-52 @7aad8aac (condensed)
for (uint32_t mt = 0; mt < Mt; mt++) {
    for (uint32_t nt = 0; nt < Nt; nt++) {
        for (uint32_t kt = 0; kt < Kt; kt++) {
            {                                          // Read A's tile at (mt, kt)
                uint32_t a_tile_index = mt * Kt + kt;  // A is MK, so we stride by Kt
                cb_reserve_back(cb_id_in0, 1);
                uint32_t l1_write_addr_in0 = get_write_ptr(cb_id_in0);
                noc_async_read_page(a_tile_index, s0, l1_write_addr_in0);
                noc_async_read_barrier();
                cb_push_back(cb_id_in0, 1);
            }
            {                                          // Read B's tile at (kt, nt)
                uint32_t b_tile_index = kt * Nt + nt;  // B is KN, so we stride by Nt
                ... same four calls on cb_id_in1 ...
            }
        }  // Kt loop
    }  // Nt loop
}

The loop order is (mt, nt, kt), with kt innermost. For each output tile the reader walks along row mt of A and down column nt of B. It pushes them as a pair into two circular buffers, c_0 and c_1, each two tiles deep (num_input_tiles = 2, host lines 104-115), so the reader can fetch the next pair while compute uses the current one. Count the reads: the body runs Mt·Nt·Kt times and reads two tiles each time, so 2 · 20 · 20 · 20 = 16,000. Row mt of A is read again for every nt, which is Nt = 20 times. Nothing in the kernel remembers that it already fetched those tiles.

The compute kernel accumulates over kt inside one acquire

tt-metal/tt_metal/programming_examples/matmul/matmul_single_core/kernels/compute/mm.cpp:50-87 @7aad8aac (comments trimmed)
compute_kernel_hw_startup<SrcOrder::Reverse>(cb_in0, cb_in1, cb_out);
matmul_init(cb_in0, cb_in1);

for (uint32_t mt = 0; mt < Mt; ++mt) {
    for (uint32_t nt = 0; nt < Nt; ++nt) {
        tile_regs_acquire();
        for (uint32_t kt = 0; kt < Kt; kt++) {
            cb_wait_front(cb_in0, 1);
            cb_wait_front(cb_in1, 1);
            matmul_tiles(cb_in0, cb_in1, 0, 0, 0);   // Dst[0] += in0 · in1
            cb_pop_front(cb_in0, 1);
            cb_pop_front(cb_in1, 1);
        }
        tile_regs_commit();
        tile_regs_wait();
        cb_reserve_back(cb_out, 1);
        pack_tile(0, cb_out);
        cb_push_back(cb_out, 1);
        tile_regs_release();
    }
}

Three details matter here.

  • matmul_tiles accumulates. Its documentation says it computes C = A·B "and accumulates the result to DST (DST += C)" (matmul.h:150-152). So the kt loop needs no explicit add. Twenty calls with the same idst = 0 leave the full dot product in Dst tile 0. Each call is 16 MVMULs per fidelity phase, as A06 showed.
  • The accumulation lives inside one acquire/commit pair. tile_regs_acquire() hands the math thread a half of Dst that is already zero. The zeroing is done by the packer when the previous owner released it: _llk_pack_dest_section_done_ issues a ZEROACC of that half before signalling math (tt_llk_wormhole_b0/llk_lib/llk_pack_common.h:59-76). If you moved acquire and commit inside the kt loop, each partial product would be packed separately and the sum would be lost.
  • in0 goes to SrcB and in1 to SrcA. The hardware instruction is MVMUL: Dst += SrcB @ SrcA, an 8×16 slab of SrcB times a 16×16 block of SrcA (MVMUL.md:1-3). The left matrix of the instruction is SrcB, so the left matrix of your matmul, in0, has to be unpacked into SrcB. That is the reverse of every other two-input op, where in0 lands in SrcA. The template tag on the startup call tells the hardware configuration about the swap:
tt-metal/tt_metal/hw/inc/api/compute/src_order.h:28-31 and compute_kernel_hw_startup.h:68-70 @7aad8aac
enum class SrcOrder : uint8_t {
    Regular = 0,  // icb0 -> SrcA, icb1 -> SrcB
    Reverse = 1,  // icb0 -> SrcB, icb1 -> SrcA
};
...
    constexpr bool reverse = (src_order == SrcOrder::Reverse);
    const uint32_t src_a_cb = reverse ? icb1 : icb0;
    const uint32_t src_b_cb = reverse ? icb0 : icb1;

The startup function programs per-register state (data formats and tile sizes for SrcA and SrcB) once, at the start of the kernel. If in0 and in1 had different formats, say bf16 activations and bfp8 weights, configuring them the "regular" way round would give each register the other operand's format. The comment on matmul_init states the rule: "Matmul maps in0 -> SrcB and in1 -> SrcA (the reverse of other ops), which is why compute_kernel_hw_startup must use SrcOrder::Reverse" (matmul.h:89-91). A06 explained why the swap is not cosmetic: SrcA gets the 5-bit side of the multiplier and SrcB the 7-bit side, so in1 (usually the weights) is the operand that loses more bits at low fidelity.

Step through the loop for a tiny case, Mt = Nt = 2 and Kt = 3. Watch the read badges on A and B. Every A tile ends up read twice, and so does every B tile.

The writer, and a bug that hides in square matrices

The writer is the mirror image: wait for a tile in c_16, write it to page m·Nt + n, pop. One detail is worth showing because it is a real latent bug in the example, and a good lesson about runtime arguments:

tt-metal/tt_metal/programming_examples/matmul/matmul_single_core/matmul_single_core.cpp:169 and kernels/dataflow/writer_single_core_mm.cpp:9-11 @7aad8aac
tt_metal::SetRuntimeArgs(program, writer_id, core, {dst_addr, Mt, Kt, Nt});   // host
...
uint32_t dst_addr = get_arg_val<uint32_t>(0);                                // writer kernel
uint32_t Mt = get_arg_val<uint32_t>(1);
uint32_t Nt = get_arg_val<uint32_t>(2);   // index 2 is Kt, not Nt
Runtime arguments are a bare array of uint32_t with no names and no type checking. The host passes {dst_addr, Mt, Kt, Nt}, but the writer reads index 2 as Nt and gets Kt. The example works only because K = N = 640. Change N to 320 and the writer would loop over the wrong number of columns. It would wait for 400 output tiles that compute never produces (compute only makes 200), and hang. When a kernel hangs or writes garbage, check the argument indices first.

Many cores: splitting the output

Every output tile is independent, so the obvious parallel version gives each core a share of the output tiles and lets each core run the single-core algorithm on its share. The question is how to divide 400 tiles among 64 cores when 64 does not divide 400. tt-metal has a helper for that:

tt-metal/tt_metal/programming_examples/matmul/matmul_multi_core/matmul_multi_core.cpp:110-122 @7aad8aac (comments trimmed)
auto core_grid = mesh_device->compute_with_storage_grid_size();
auto num_output_tiles_total = (M * N) / TILE_HW;
auto [num_cores, all_cores, core_group_1, core_group_2, work_per_core1, work_per_core2] =
    split_work_to_cores(core_grid, num_output_tiles_total);

The implementation is short enough to read whole. If there are at least as many units as cores, it uses every core. Each core gets ⌊units / cores⌋, and the remainder is spread as one extra unit to the first few cores:

tt-metal/tt_metal/common/work_split.cpp:350-400 @7aad8aac (condensed)
if (units_to_divide >= max_num_cores) {
    target_num_cores = max_num_cores;
    all_cores = CoreRangeSet(CoreRange({0, 0}, {num_cores_x - 1, num_cores_y - 1}));
} else { ... }
uint32_t units_per_core_group_1 = units_to_divide / target_num_cores;
uint32_t num_cores_with_more_work = units_to_divide % target_num_cores;
if (units_to_divide % target_num_cores == 0) {
    core_group_1 = all_cores;
} else {
    core_group_1 = num_cores_to_corerangeset(num_cores_with_more_work, grid_size, row_wise);
    ... core_group_2 = the remaining cores, starting right after group 1 ...
    units_per_core_group_2 = units_per_core_group_1;
    units_per_core_group_1++;
}

For 400 tiles on 64 cores, ⌊400/64⌋ = 6 and 400 mod 64 = 16. So group 1 is 16 cores doing 7 tiles each, and group 2 is 48 cores doing 6: 16·7 + 48·6 = 400. row_wise defaults to false, so the cores are filled column by column. Group 1 is therefore logical columns x = 0 and 1. The instrumented run below confirms both the split and the placement.

The host then walks both groups and gives each core a starting tile id and a count. The reader converts each linear output-tile id back to (row, column) and runs the same kt loop as before:

tt-metal/tt_metal/programming_examples/matmul/matmul_multi_core/kernels/dataflow/reader_mm_output_tiles_partitioned.cpp:34-54 @7aad8aac (condensed)
for (uint32_t output_tile = 0; output_tile < num_output_tiles; output_tile++) {
    uint32_t current_tile_id = output_tile_start_id + output_tile;
    uint32_t out_row = current_tile_id / Nt;  // Which row in output
    uint32_t out_col = current_tile_id % Nt;  // Which col in output
    for (uint32_t k = 0; k < Kt; k++) {
        uint32_t tile_A = out_row * Kt + k;  // A is MK, so we stride by Kt
        ...
        uint32_t tile_B = k * Nt + out_col;  // B is KN, so we stride by Nt

Count again. Each output tile still costs 2·Kt = 40 reads, whichever core computes it. A group-1 core reads 7·40 = 280 tiles and a group-2 core 6·40 = 240. In total that is 400·40 = 16,000, exactly the single-core number. The work is spread over 64 cores, but the traffic is not reduced at all. The 7 tiles one core computes are consecutive tile ids, so they mostly share one row of A, and the reader fetches that row again for each of them.

Splitting output tiles over cores divides the compute by the core count but leaves the DRAM traffic unchanged. The traffic depends only on how many times each input tile is fetched, and with one output tile at a time, each input tile is fetched once per output tile that needs it.

Why 64 cores don't give 64×

Now put numbers on it, using two limits only. This is a back-of-envelope model, not a measurement:

  • Compute. At HiFi4, one 32×32×32 tile matmul takes 64 FPU cycles (GEMM_FLOPS.md:107: LoFi 16, HiFi2 32, HiFi4 64), at 1 GHz on Wormhole.
  • DRAM. Wormhole's 12 GDDR6 channels give 288 GB/s in total (A09), shared by every core.

One naive tile-matmul step reads 2 tiles (4096 bytes) for 64 cycles of work, so one core needs 64 bytes per cycle, or 64 GB/s at 1 GHz. Sixty-four cores running the naive loop would need 4096 GB/s, 14 times what the DRAM can deliver. The best speed-up the naive multi-core version can reach is therefore about 288/64 = 4.5×, however many cores you add. A matmul whose loop re-fetches its inputs is a memory-bound kernel, and adding cores does not move you along a memory-bound line.

The fix is to make each fetched tile do more work. Suppose a core owns a b×b block of output tiles rather than one tile. For each kt it reads b tiles of A (a column slice of its rows) and b tiles of B (a row slice of its columns): 2b reads. With them it performs b² tile matmuls, because every A tile meets every B tile. Reads grow like b, work like b². Drag the block size below and play the run. The problem is 2048×2048×2048 (64×64×64 tiles) on an 8×8 grid. Every counter is computed exactly from the loop structure.

Things to notice as you move the slider:

  • Reads halve each time the block side doubles, from 524,288 at 1×1 to 65,536 at 8×8. The formula is total = (number of blocks) × 2b·Kt, so each A tile is fetched 64/b times: once by every block in its block-row.
  • The model speed-up climbs from 4.5× to 36× at HiFi4 as b goes from 1 to 8, and it is DRAM-bound the whole way. At 16×16 the kernel becomes compute-bound, but only 16 blocks exist, so 48 cores are idle and the speed-up drops to 16×. Larger blocks also need more L1, and past 16×16 they do not fit.
  • Switch to LoFi. The compute gets 4× faster, so the DRAM wall is hit sooner. At 1×1 the 64-core version is only 1.1× faster than one core. Faster math makes data reuse more important, not less.
The model ignores everything except the two roofs: NoC link limits, DRAM bank conflicts, read latency (the simple readers wait on a barrier after every tile), host dispatch, and the 72-core grid of a real n150. Most of these make the naive multi-core version worse. Some also slow the one-core baseline the speed-ups are measured against: the naive loop at HiFi4 needs 64 GB/s into one core, but one NoC link carries about 32 GB/s (A09), and the per-tile barrier adds latency. A real single core is therefore slower than the model assumes, so the ratios are not strict ceilings. Treat them as showing the trend. The read counts, by contrast, are exact.
A GPU GEMM uses the same hierarchy under different names. A thread block computes an output tile staged in shared memory (here, a core's per-core block in L1). A warp computes a smaller tile held in registers (here, a subblock in Dst). The loop marches along K in slices (here, in0_block_w). CUTLASS's "Efficient GEMM" note walks through exactly this structure. One difference matters a lot: on a GPU, the L2 cache catches many of the re-reads between thread blocks, so naive tiling is forgiven to some extent. Here there is no cache, so every re-read is a real DRAM read. Cross-core reuse has to be explicit, and that is A16's multicast.

Analogy: 64 cooks share one pantry door. If each cook fetches a carrot every time a recipe mentions one, the doorway is jammed, and hiring more cooks only lengthens the queue. If each cook takes a crate of carrots back to the bench and makes many dishes from it, the door is free. Where the analogy breaks: this pantry has twelve doors (DRAM banks), and the tiles are dealt across all of them, so the queue forms at every door at once. And a cook's bench is small (1.4 MiB), so the crate size is limited.

Blocking: per_core_M, per_core_N, in0_block_w

matmul_multicore_reuse is the blocked version. Each core owns a per_core_M × per_core_N block of output tiles. It marches along K in steps of in0_block_w tiles. At each step it pulls an in0 slab (per_core_M × in0_block_w tiles) and an in1 slab (in0_block_w × per_core_N tiles) into L1, and uses every tile of both slabs for the whole block. This is the "K-block" scheme from the docs' Lab 2 (labs/matmul/lab2/lab2.rst:434-503). The reader makes it concrete:

tt-metal/tt_metal/programming_examples/matmul/matmul_common/kernels/dataflow/reader_bmm_tile_layout.cpp:59-94 @7aad8aac (condensed)
for (uint32_t block = 0; block < num_blocks; block++) {            // num_blocks = Kt / in0_block_w
    cb_reserve_back(cb_id_in0, in0_block_num_tiles);
    cb_reserve_back(cb_id_in1, in1_block_num_tiles);
    for (uint32_t h = 0; h < in0_block_h; h++)                        // per_core_M rows of A
        for (uint32_t w = 0; w < in0_block_w; w++)
            noc_async_read_page(in0_tensor_tile_id, s0, l1_write_addr_in0), ...;
    for (uint32_t h = 0; h < in1_block_h; h++)                        // in0_block_w rows of B
        for (uint32_t w = 0; w < in1_block_w; w++)                    // per_core_N columns
            noc_async_read_page(in1_tensor_tile_id, s1, l1_write_addr_in1), ...;
    noc_async_read_barrier();                                         // one barrier per slab pair
    cb_push_back(cb_id_in0, in0_block_num_tiles);
    cb_push_back(cb_id_in1, in1_block_num_tiles);
}

Each core reads (per_core_M + per_core_N) · in0_block_w tiles per K-block and Kt/in0_block_w K-blocks, so (per_core_M + per_core_N)·Kt tiles in total. Notice that in0_block_w cancels out: it changes how big each slab is, not how many times a tile is fetched. Notice also that the reader issues a whole slab of reads before a single barrier. Many reads are in flight at once, unlike the one-tile-then-wait readers above.

How the example picks its block

The host fixes in0_block_w = 2 and asks a helper for the rest (matmul_multicore_reuse.cpp:98-109). The helper's core rule is an L1 budget:

tt-metal/tt_metal/programming_examples/matmul/matmul_common/bmm_op.hpp:66-72 @7aad8aac
inline uint32_t get_maximum_block_dim(int32_t block_dim, int32_t in0_block_w) {
    int32_t other_dim = (400 - 2 * in0_block_w * block_dim) / (2 * in0_block_w + block_dim);
    if (other_dim > 0) {
        return other_dim;
    }
    return 0;
}

The source gives no comment, but the formula can be solved backwards. Rearranging N ≤ (400 − 2wM)/(2w + M) gives 2wM + 2wN + MN ≤ 400. That is exactly the tile count of the three circular buffers the host creates: in0 double-buffered (2·per_core_M·w), in1 double-buffered (2·per_core_N·w), and one output block (per_core_M·per_core_N) (matmul_multicore_reuse.cpp:123-131). So the budget is 400 tiles, 800 KiB at 2 KiB per tile, out of the ~1360 KiB of free L1 that A09 measured. This reading is my inference from the arithmetic.

For our 640×640 problem, the helper walks candidate per_core_N values in increasing order (products of Nt's prime factors 2, 2, 5). For each it takes the largest per_core_M that fits the budget, and accepts the first pair whose block grid fits on 8×8 cores. N = 2 needs 10 columns of cores, which is too many. N = 4 gives M = 20 (the budget would allow 48), a 1×5 grid of blocks. The run prints exactly that:

 -- Metalium Core Sizing --
 -- per_core_M= 20 -- per_core_N= 4 -- out_subblock_h= 4 -- out_subblock_w= 2 --

So each of 5 cores reads (20 + 4)·20 = 480 tiles, 2,400 in total. All of A goes to every core (5× each) and B is split (1× each), so 2000 + 400 = 2400. The block uses 2·20·2 + 2·4·2 + 80 = 176 tiles of L1, and its intensity is 32·20·4/24 ≈ 107 FLOP/B (next section).

The helper maximises the block size within the L1 budget. It does not maximise the number of cores. For this small problem, that means 5 busy cores and 59 idle ones. In the two-roof model above, the reuse version (5 cores, compute-bound, 1,600 tile matmuls per core ≈ 102 µs at HiFi4) and the naive multi-core version (64 cores, DRAM-bound, 32.8 MB ≈ 114 µs) come out about even. Blocking is not automatically faster. It trades parallelism for traffic, and the right block depends on the shape. TT-NN's production matmul (MatmulMultiCoreReuseMultiCastProgramConfig, A18) combines both: every core gets a block, and multicast removes the remaining duplication (A16).

Subblocks, Dst, and the partials buffer

A 20×4 output block is 80 tiles. Dst holds far fewer. The register file is 1024 rows of 16 datums (Dst.md:3), and a tile is 64 such rows (four 16×16 faces). So Dst holds 16 bf16 tiles. Two halves are needed so math can fill one while the packer drains the other, which leaves 8. With fp32_dest_acc_en it is 4. TT-NN encodes exactly this rule:

tt-metal/ttnn/cpp/ttnn/operations/core/compute_kernel/compute_kernel_config.cpp:142-150 @7aad8aac
uint32_t available_reg_count = (DEST_REGISTER_FULL_SIZE * DATUMS_PER_ROW) / (tile_width * tile_height);
if (!compute_kernel_config.dst_full_sync_en) {
    available_reg_count /= 2;
}
...
if (compute_kernel_config.fp32_dest_acc_en) {
    available_reg_count /= 2;
}

(DEST_REGISTER_FULL_SIZE = 64 * DEST_FACE_HEIGHT = 1024 rows, tensix_types.h:192.) So the per-core block is computed as a sequence of subblocks of out_subblock_h × out_subblock_w ≤ 8 tiles. That is why every entry in the example's SUBBLOCK_HW_CHOICES has h·w ≤ 8, ordered from 8 tiles ({4,2}, {2,4}, {8,1}, {1,8}) down to {1,1} (bmm_op.hpp:112-115). The helper picks the first entry that divides the block, so 20×4 gets 4×2: 5 × 2 = 10 subblocks.

A subblock can only be finished after all K-blocks have passed, but each K-block's slabs leave L1 before the next arrive. So between K-blocks every subblock's running sum has to be parked somewhere. It is parked in L1, in an intermediate CB, c_24. The compute kernel's structure:

tt-metal/tt_metal/programming_examples/matmul/matmul_common/kernels/compute/bmm_large_block_zm.cpp:33-106 @7aad8aac (condensed)
for (uint32_t block = 0; block < num_blocks; block++) {               // K-blocks
    bool last_out = block == (num_blocks - 1);
    cb_wait_front(c_0, in0_block_num_tiles);  cb_wait_front(c_1, in1_block_num_tiles);
    for (in0_subblock ...) for (in1_subblock ...) {                    // subblocks, row-major
        tile_regs_acquire();
        if (enable_reload) {                                            // K-block > 0
            copy_init(c_24); cb_wait_front(c_24, out_subblock_num_tiles);
            for (i ...) copy_tile(c_24, i, i);                          // partials back into Dst
            cb_pop_front(c_24, out_subblock_num_tiles);
            matmul_init(c_0, c_1);
        }
        for (h ...) for (w ...) {                                       // dst_index = h*w_sb + w
            for (inner_dim = 0; inner_dim < in0_block_w; inner_dim++)
                matmul_tiles(c_0, c_1, in0_index, in1_index, dst_index);
            dst_index++;
        }
        tile_regs_commit(); tile_regs_wait();
        if (last_out) { pack all tiles to c_16 }                        // final result
        else {
            if (block == 0) { cb_reserve_back(c_16, out_num_tiles_to_wait); out_num_tiles_to_wait += ...; }
            pack all tiles to c_24 (reserve, pack_tile, push)           // partial result
        }
        tile_regs_release();
    }
    if (spill) enable_reload = true;
    cb_pop_front(c_0, in0_block_num_tiles);  cb_pop_front(c_1, in1_block_num_tiles);
}

And the host gives c_16 and c_24 the same memory: one CircularBufferConfig with two indices, sized for one full output block:

This works because partial and final results are never alive at the same time. Lab 2 describes it as "a single circular buffer allocation and exposing it through two logical views (two different CB indices) that point into the same physical memory" (lab2.rst:857-867). The odd cb_reserve_back(c_16, ...) in K-block 0 is the guard that makes the sharing safe. Before the first partial goes into a slice of the shared space, compute reserves that slice through the output view. That makes it wait until the writer has drained any final tiles still sitting there (from a previous batch). The kernel's own comment: "Wait for tiles in output buffer to be written out since interm and output share memory" (line 82).

Step through a small version: an 8×4-tile block, 4×2 subblocks (what the helper would pick for 8×4), in0_block_w = 2 and Kt = 6, so 3 K-blocks.

Two points are easy to miss in the animation.

  • Reuse happens at two levels. In DRAM terms, every tile in the c_0 and c_1 slabs was fetched once and is used for the whole block. In L1 terms, inside one subblock each in0 tile feeds out_subblock_w matmuls and each in1 tile feeds out_subblock_h, all from the same CB slot. In this figure each in1 slab tile is used by 2 subblocks × 4 rows = 8 matmuls per K-block.
  • Spilling has a cost. With Kt/in0_block_w K-blocks, every output tile goes through Dst → L1 → Dst that many times minus one. For the real example (Kt = 20, in0_block_w = 2), each of the 80 output tiles per core is packed 10 times and reloaded 9 times. That is L1 traffic, which is cheap compared with DRAM but not free. It is also why in0_block_w is worth tuning even though it does not change DRAM reads.
The subblock limit of 8 assumes a bf16 Dst in half-sync mode. Turn on fp32_dest_acc_en (A06 showed why you might) and Dst holds 4 tiles per half. The 4×2 subblock chosen by SUBBLOCK_HW_CHOICES would then overflow. That table is example code with no knowledge of the compute config, and nothing in the example checks it. TT-NN's matmul does: it compares out_subblock_h × out_subblock_w against get_dest_reg_count and refuses configs that do not fit (ttnn/.../matmul/device/matmul_device_operation.cpp:654-660).

Arithmetic intensity per block

Now connect this to the roofline from A01. For one K-block, a core with a Mb×Nb block and slab width w does:

  • FLOPs: 2 · (32Mb) · (32w) · (32Nb) = 65,536 · MbNbw
  • DRAM bytes (bf16): 2048 · w · (Mb + Nb)

intensity = 32 · Mb·Nb / (Mb + Nb) FLOP per byte

The slab width w cancels again. For square blocks this is 16b:

Block (tiles)Intensity (FLOP/B)Where it sits (Wormhole, HiFi4, 64 cores: ridge ≈ 228 FLOP/B)
1×1 (single_core, multi_core)16deep in the memory-bound slope
20×4 (multicore_reuse at 640³)107still memory-bound at full-chip scale
8×8128memory-bound
16×16256just past the ridge

The ridge is 64 cores × 1.024 TFLOP/s (one tile matmul per 64 cycles at 1 GHz) ÷ 288 GB/s ≈ 228 FLOP/B. With the 72 cores of an n150, A01's 74 TF / 288 GB/s gives 257. At LoFi the ridge moves 4× to the right (~910 FLOP/B), which no single-core block that fits in L1 can reach on its own. This is the quantitative reason the production matmul shares tiles between cores (multicast in A16) and shards weights next to their DRAM banks for decode (A09's DRAM-sharded matmul). Per-core blocking alone lifts intensity by a factor of b. Cross-core sharing is what lifts it the rest of the way.

The traffic of a blocked matmul depends on the block's perimeter (Mb + Nb) and its work on the block's area (Mb·Nb). Big, square blocks win, and L1 capacity and core count decide how big they can be.

The bracketed numbers ([330591], [10860], [17560]) are ttsim clock counts, and the seconds are host CPU time. Recap

  • Tilize on the host (tilize_nfaces) turns each 32×32 tile into one contiguous 2048-byte page, with faces in order, so page id = tile id and a reader fetches tile (mt, kt) with one noc_async_read_page.
  • The single-core kernel loops (mt, nt, kt). The reader streams A(mt, kt) and B(kt, nt) through c_0/c_1. matmul_tiles accumulates into Dst[0] across kt inside one acquire/commit, starting from a Dst half the packer has already zeroed. in0 → SrcB and in1 → SrcA because MVMUL is Dst += SrcB @ SrcA, and compute_kernel_hw_startup<SrcOrder::Reverse> tells the hardware configuration.
  • split_work_to_cores divides units over a grid as group 1 (⌈u/c⌉ each) and group 2 (⌊u/c⌋ each): 400 tiles → 16 × 7 + 48 × 6, filled column-major by default.
  • Splitting the output does not split the traffic. Naive single-core and 64-core runs both read 2·Mt·Nt·Kt = 16,000 tiles. With 64 cores the DRAM is the wall (≈4.5× ceiling at HiFi4 in the two-roof model).
  • Blocking with per_core_M × per_core_N makes each fetched tile serve a whole block row or column: reads become (Mb + Nb)·Kt per core. 640³ drops to 2,400 reads, confirmed byte for byte in ttsim. in0_block_w sets slab size and L1 use, not DRAM reads.
  • Subblocks of h×w ≤ 8 tiles (bf16 Dst, half-sync; 4 with FP32) fit the block through Dst. Partials wait in c_24 between K-blocks, sharing memory with c_16.
  • Intensity per block is 32·MbNb/(Mb+Nb) FLOP/B: 16 for one tile, 128 for 8×8, against a ridge of ~228 (HiFi4) or ~910 (LoFi). Reaching it takes cross-core sharing, which is the next chapter.

Check yourself

You change the single-core example to M = 640, K = 1280, N = 640 (fixing the writer bug first). How many DRAM tile reads does the reader make?

Mt = 20, Kt = 40, Nt = 20. The reader loop body runs Mt·Nt·Kt = 16,000 times and reads 2 tiles each time, so 32,000 reads (65.5 MB). Doubling K doubles the reads, because every output tile's dot product is twice as long and nothing is reused.

Why must a matmul compute kernel call compute_kernel_hw_startup<SrcOrder::Reverse>, while an eltwise add uses the default?

The matrix unit's instruction is Dst += SrcB @ SrcA: the left operand of the product comes from SrcB. For C = in0 · in1, in0 must therefore be unpacked into SrcB and in1 into SrcA, the reverse of eltwise ops, where in0 → SrcA. The startup call programs per-register state (formats, tile sizes) once, so it must know which CB feeds which register. With Reverse, it configures SrcA from in1's CB and SrcB from in0's CB. With mismatched formats (bf16 activations, bfp8 weights), getting this wrong would decode each operand with the other's format.

split_work_to_cores on an 8×8 grid with 100 units: what are the two groups?

100 ≥ 64, so all 64 cores are used. ⌊100/64⌋ = 1 and 100 mod 64 = 36, so group 1 has 36 cores doing 2 units each and group 2 has 28 cores doing 1: 72 + 28 = 100. With row_wise = false, group 1 fills columns 0–3 (32 cores) and the first 4 cores of column 4. Group 2 starts right after.

In matmul_multicore_reuse, someone doubles in0_block_w from 2 to 4. What happens to DRAM reads, L1 use, and spills, for the 640³ problem?

DRAM reads do not change: each core still reads (per_core_M + per_core_N)·Kt tiles, since in0_block_w cancels. The input CBs double (in0: 2·20·4 = 160 tiles, in1: 2·4·4 = 32) and the number of K-blocks halves (10 → 5), so each output tile goes through c_24 4 times instead of 9. Also, the helper's budget 2wM + 2wN + MN ≤ 400 is evaluated with w = 4, so it might pick a different block. Here it still gives M = 20 (the bound for N = 4 is (400 − 32)/12 = 30).

A 4×4-tile output block, bf16, reading A and B from DRAM interleaved. What is its arithmetic intensity, and is it memory- or compute-bound on Wormhole at HiFi2 with all 64 cores busy?

32·16/8 = 64 FLOP/B. At HiFi2 a tile matmul takes 32 cycles, so 64 cores deliver 64 × 65,536/32 GFLOP/s ≈ 131 TFLOP/s, and the ridge is 131e12 / 288e9 ≈ 455 FLOP/B. 64 is far below it: memory-bound by a factor of about 7.

The instrumented ttsim shows matmul_single_core at 330,591 clocks and matmul_multi_core at 10,860. Can you conclude the multi-core version is 30× faster on silicon?

No. ttsim's clock is driven by the host polling the device, not by modelled hardware timing, so clock counts measure how long the host waited. (A06 showed LoFi taking more clocks than HiFi4 in ttsim, the opposite of silicon.) What ttsim does tell you exactly is the traffic: both moved 32,768,000 bytes from DRAM. On silicon, both would be DRAM-limited, and the model above suggests the multi-core version tops out around 4.5× at HiFi4.
