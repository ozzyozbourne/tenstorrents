The question: why is exp() so much slower than matmul?

Take one Wormhole Tensix core and give it two jobs.

Job 1: multiply two 32×32 tiles at the lowest fidelity. In A06 you saw that the matrix engine (FPU) does an 8×16 by 16×16 block per MVMUL, which is 2048 multiply-accumulates per cycle. A 32×32×32 tile product is 32,768 multiply-accumulates, so it takes 16 cycles.

Job 2: compute exp(x) for every element of one 32×32 tile. That is only 1024 numbers, with no reduction and nothing to share between them. It should be easy. Yet when I compiled the stock exp_tile kernel in this orb and disassembled it (shown later), the vector engine issues 20 instructions for every 32 elements. A tile is 32 groups of 32 elements, so that is 640 issue slots.

So one core spends 16 cycles on a job with 32,768 multiplies and about 640 cycles on a job with 1024 exponentials. Same core, same clock. The rest of this chapter explains where those numbers come from. In short, there are two separate gaps:

  1. The vector engine's peak is 64× lower than the matrix engine's. That is a design decision, and we will derive it exactly.
  2. exp is not one instruction. It is a small program of multiply-adds, exponent tricks and clamps, and every one of its instructions occupies the whole vector engine for a cycle.
A Tensix core has two math engines. The FPU is a huge, narrow-precision engine built for one job: tile matrix multiply. The SFPU is a small, general-purpose 32-lane FP32 SIMD unit for everything else (exp, sqrt, comparisons, integer tricks). Both work on the same Dst register file.

A second engine on the same registers

Recall the picture from A04. Three baby RISC-V cores (TRISC0, TRISC1 and TRISC2) push instructions into the Tensix coprocessor, which has several backend units. The ISA documentation lists them as Sync, Unpack, Matrix (FPU), Pack, Vector (SFPU), Scalar (ThCon), Config, Mover and Misc. Whatever the "S" once stood for, the ISA manual titles its page "Vector Unit (SFPU)", and that is what it is.

The data path matters more than the name:

  • The unpackers move tiles from L1 into SrcA and SrcB (for the FPU) or directly into Dst.
  • The FPU reads SrcA and SrcB and writes or accumulates into Dst.
  • The SFPU never sees SrcA, SrcB or L1. It reads Dst into its own registers, the LRegs, computes there, and writes back to Dst. The ISA's register-access table lists exactly two ways to write an LReg from outside: SFPLOAD and SFPLOADMACRO. Only one instruction writes Dst from an LReg: SFPSTORE.
  • The packers move Dst back to L1.

This is why every SFPU operation in a compute kernel starts with copy_tile: the tile must first be unpacked into Dst. It is also why SFPU work chains well. Once a tile is in Dst you can apply exp, then a multiply, then a clamp, without touching L1. A12 covers the kernel-side mechanics (tile_regs_acquire and the rest). This chapter stays with the hardware.

The SFPU's instructions travel through the coprocessor like any other Tensix instruction. In Metalium's compute kernels they come from the math thread, TRISC1. You will see real sfpload, sfpadd and sfpstore instructions in the trisc1.elf disassembly below.

On a GPU, the tensor cores and the ordinary FP32 CUDA cores share the same register file, and a warp can switch between them freely. Tenstorrent has the same idea at a different scale: the FPU and the SFPU share Dst. But the SFPU cannot read the FPU's input registers (SrcA/SrcB), and neither engine reads memory directly. Unpackers and packers do that.

32 lanes of 32 bits: the LRegs

The Wormhole ISA manual opens its Vector Unit page with one sentence that sums it up: the SFPU "can be considered as a general-purpose SIMD engine, consisting of 32 lanes of 32 bits." The register file is declared like this:

tt-isa-documentation/WormholeB0/TensixTile/TensixCoprocessor/LReg.md:6 @be833101
union {uint32_t u32; int32_t i32; float f32;} LReg[17][32];

So there are 17 vector registers, each holding 32 lanes, and each lane holds 32 bits that you may read as an FP32 value, an unsigned integer, a two's-complement integer, or a sign-magnitude integer. Software is allowed to reinterpret the bits freely. The 17 registers are not all alike:

LRegWhat it holds
0–7General purpose. This is all you get for live values: 8 vectors of 32 lanes.
8Read-only constant 0.8373 in every lane. SFPI names it CREG_IDX_0P837300003. You will meet this odd number again in the exp section.
9Read-only zero.
10Read-only 1.0.
11–14Programmable constants, written only through SFPCONFIG. The SFPI compiler reserves LReg 11 for -1.0.
15Read-only lane index ×2 (0, 2, 4, …, 62).
16Only reachable from SFPLOADMACRO sequences.

The constants are cheap tricks with real payoffs: a comparison a < 0.5 can be computed as a + (−1.0)×0.5 using LReg 11, with no instruction spent loading −1. You will see the compiler do exactly that later.

The 32 lanes are often drawn as a 4×8 grid (lanes 0–7 in the first row, 8–15 in the second, and so on). Purely lane-wise instructions do not care about this shape. The few cross-lane instructions (SFPTRANSP, SFPSHFT2) move data horizontally or vertically in it, and, as you will see next, the grid matches how lanes map onto Dst.

A 32×32-bit register is 1024 bits, but it is not a byte-flexible SIMD register like AVX-512. The Metalium docs make this point too: an int8 tensor still occupies one lane per element, 32 elements per vector, and not 128. Narrow data types buy you nothing in SFPU throughput.

From Dst to lanes: SFPLOAD and SFPSTORE

Dst is 1024 rows × 16 columns of 16-bit data (or 512 × 16 of 32-bit data). A 32×32 tile is four 16×16 faces (A05), and a face occupies 16 consecutive Dst rows, one face row per Dst row. An LReg holds 32 values. So how do 256 face elements get into 32-lane registers?

The ISA manual gives the exact rule. Here is the core of SFPLOAD's functional model:

tt-isa-documentation/WormholeB0/TensixTile/TensixCoprocessor/SFPLOAD.md:72-89 @be833101
// The top 8 bits of Addr end up selecting an aligned group of four rows of Dst, the
// next bit selects between even and odd columns, and the low bit goes unused.
uint10_t Addr = Imm10 + ThreadConfig[CurrentThread].DEST_TARGET_REG_CFG_MATH_Offset;
...
    uint10_t Row = (Addr & ~3) + (Lane / 8);
    uint4_t Column = (Lane & 7) * 2;
    if ((Addr & 2) || LaneConfig[Lane & 7].DEST_RD_COL_EXCHANGE) {
      Column += 1;
    }

Read it with small numbers. Lane 0 takes row 0, column 0. Lane 1 takes row 0, column 2. Lane 7 takes row 0, column 14. Lane 8 starts the next row. So one SFPLOAD takes four Dst rows and every other column: a 4×8 patch, which is exactly the LReg's 4×8 lane grid. Address bit 1 switches to the odd columns. One face therefore needs 4 row groups × 2 column parities = 8 loads.

In SFPI, the C++ dialect for the SFPU, this all hides behind dst_reg[i]. The index is multiplied by a stride of 2 to form the SFPLOAD address, which is why vector i lands on address 2i:

sfpi 7.92.0 (bundled with tt-metal @7aad8aac) runtime/sfpi/include/sfpi_classes.h:398-400, sfpi_constants.h:16
sfpi_inline constexpr vReg<> operator[] (int ix) const {
  return vReg<> (ix * SFP_DESTREG_STRIDE);
}
constexpr unsigned int SFP_DESTREG_STRIDE = 2;

The sources disagree here. The Metalium guide "Compute Engines and Data Flow within Tensix" says that "dst_reg[0:3] typically contains the first face of the tile, dst_reg[4:7] contains the second face". The ISA's SFPLOAD model, the SFPI stride of 2, the smoothstep example's vectors_per_face = 8, and the compiled binary above all say that one face is dst_reg[0:7] (8 × 32 = 256 elements). Four vectors could only hold 128 elements, half a face. Trust the ISA and the binary.

The load also converts formats. SFPLOAD turns a BF16 Dst value into FP32 by shifting it into the high 16 bits, rebiases FP16 exponents, and passes FP32 or 32-bit integers through. Everything inside the SFPU is 32-bit. The way back is less forgiving: SFPSTORE to a BF16 Dst truncates the mantissa toward zero (SFPSTORE.md:38). That is why tt-metal's bf16 exp path ends with an explicit round-to-nearest (SFP_STOCH_RND) before storing. The source comment gives the reason: "9**2 = 80.8 gets round to 80.5 rather than 81" (ckernel_sfpu_exp.h:156-158).

What the lanes can do

The SFPU can issue one instruction per cycle. Most instructions take 1 cycle; the floating-point multiply/add family takes 2. Grouped by purpose, the Wormhole instruction set looks like this (from the instruction table in VectorUnit.md):

FamilyInstructionsWhat it is for
FP32 arithmeticSFPMAD (a·b+c), SFPADD, SFPMUL, SFPADDI, SFPMULIEverything numeric. SFPADD and SFPMUL are the same multiply-add datapath with a 1.0 or a 0 plugged in.
Lookup / piecewiseSFPLUT, SFPLUTFP32Multiply-add with coefficients picked from LRegs 0–2 according to the magnitude of LReg 3, for piecewise-linear and polynomial approximations.
FP field surgerySFPEXEXP, SFPEXMAN, SFPSETEXP, SFPSETMAN, SFPSETSGN, SFPDIVP2Pull out or overwrite the exponent, mantissa or sign. This is how exp, log, and division by powers of two get cheap.
Integer and bitsSFPIADD, SFPAND, SFPOR, SFPXOR, SFPNOT, SFPSHFT, SFPLZInteger ops, masks, shifts, leading-zero count.
ConversionsSFPCAST, SFPSTOCHRND, SFPLOADIInt↔float, FP32→BF16/TF32 rounding (nearest or stochastic, using a per-lane PRNG), immediates.
MovementSFPLOAD, SFPSTORE, SFPMOV, SFPSWAP, SFPTRANSP, SFPSHFT2, SFPCONFIGDst↔LReg, min/max swaps (used for clamps and sorting), transposes and lane shifts.
PredicationSFPSETCC, SFPENCC, SFPPUSHC, SFPPOPC, SFPCOMPCPer-lane enable masks and a mask stack (next section).

Notice what is missing: there is no divide, no square root, no exp or log instruction on Wormhole. Every transcendental is built from the rows above. Blackhole adds a hardware approximate reciprocal and exp (below).

Two hardware facts shape real SFPU code:

  • Latency hazards are the programmer's problem on Wormhole. SFPMAD takes 2 cycles, and the WH manual says "software must ensure that on the next cycle, the Vector Unit (SFPU) does not execute an instruction which reads from any location written to by the SFPMAD". That is the sfpnop after the sfpadd in the disassembly above. Blackhole stalls automatically, and its build of the same kernel has no sfpnop.
  • Four fifths of the unit idle by default. Internally the SFPU has five sub-units: load, simple, MAD, round and store. In the manual's words, it "can only accept one instruction per cycle from the outside world, so by default four fifths of the Vector Unit (SFPU) is always idle". SFPLOADMACRO lets one load schedule up to four more instructions on the other sub-units, overlapping data movement with math. That is how fast kernels approach peak.
ttsim does not implement SFPLOADMACRO (tensix.cpp:5138 raises UnsupportedFunctionality), so the workbench sets TT_METAL_DISABLE_SFPLOADMACRO=1. LLK kernels then take their #ifdef DISABLE_SFPLOADMACRO paths (for example in calculate_exponential's approximate mode). The results should be the same, but the simulator then runs a different instruction sequence from the one silicon would normally run, and the fallback forgoes the sub-unit overlap that SFPLOADMACRO exists to provide.

If/else without branches: predication

Now the central idea of the chapter. In SFPI you can write:

v_if (x < 0.0f) { y = x * x;    }
v_else          { y = x + 1.0f; }
v_endif;

Thirty-two lanes, each with its own x. Some are negative and some are not. But there is only one instruction stream, pushed by a RISC-V core that cannot see lane values (and has usually run far ahead of the coprocessor anyway, as A04 showed). So the hardware cannot jump. What it can do is switch lanes off.

Step through it. Use All x ≥ 0 to see the case where no lane wants the if branch.

The SFPU has no branches, only masks. v_if/v_else issues both branches to all 32 lanes, and a per-lane flag decides which lanes are allowed to write. Divergent code costs the sum of its branches, even if no lane takes one of them.

The machinery

The ISA defines it precisely. Each lane has a LaneFlags bit, a UseLaneFlagsForLaneEnable bit, and its own 8-entry FlagStack. A lane is enabled if flags are in use and its flag is set:

tt-isa-documentation/WormholeB0/TensixTile/TensixCoprocessor/VectorUnit.md:144-152 @be833101
bool IsLaneEnabled(unsigned Lane) {
  if (LaneConfig[Lane & 7].ROW_MASK.Bit[Lane / 8]) {
    return false;
  } else if (UseLaneFlagsForLaneEnable[Lane]) {
    return LaneFlags[Lane];
  } else {
    return true;
  }
}
  • SFPENCC turns flag-based enabling on or off and can set all flags.
  • SFPSETCC sets each lane's flag from a test on its value: < 0, != 0, >= 0 or == 0. SFPIADD, SFPLZ and SFPEXEXP can also set flags as a side effect.
  • SFPPUSHC/SFPPOPC save and restore the flags on a per-lane stack, so v_ifs can nest. The manual says compilers "are encouraged to map SIMT if / else onto this stack".
  • SFPCOMPC is the else: LaneFlags = Top.LaneFlags && !LaneFlags. It inverts only the lanes that were enabled when the if began.

Notice that only a comparison against zero exists on Wormhole. To test a < 0.5, the compiler first computes a − 0.5. I overlaid the custom_sfpi_add compute kernel with a version whose face function contains a v_if. It computes the same sum both ways (v_if (a < 0.5f) { s = a + b; } v_else { s = b + a; }), so the example's own check still applies, and it passed on both architectures (output in the simulator section). The SFPI compiler turned it into:

Both branches are there, back to back. On Wormhole, LReg 11 (the reserved −1.0) turns a comparison into a multiply-add plus a sign test, and the mandatory sfpnop follows. Blackhole's new SFPGT compares two registers directly, so the predicated body is 6 instructions instead of 8. (The compiler also put the body in the Tensix replay buffer and replays it for vectors 1–7. A13 covers replay.)

ttsim implements all of this with a single 32-bit mask. Every lane-wise instruction computes it the same way and loops over its set bits:

cc holds the 32 LaneFlags as a bitmask, and cc_en is the "use flags" switch (ttsim keeps one switch for the whole unit rather than one per lane). SFPCOMPC becomes cc = cc_stack[top] & ~cc (tensix.cpp:4883-4895), the same formula as the ISA. A masked lane is skipped by the simulator's loop. In hardware it is simply not written, but the instruction still occupies its cycle.

This is exactly SIMT branch divergence. A GPU warp is also 32 lanes, and when its threads disagree on a branch, it runs both paths with lanes masked off. Classic GPUs even used a similar per-warp reconvergence stack. Two differences matter:
  • A GPU checks whether any thread takes a branch and skips the path when none does. The SFPU cannot, because its instruction stream was decided by a RISC-V core that never sees the flags. Press All x ≥ 0 above: the if-branch is still issued.
  • A GPU hides latency by switching among many warps. The SFPU runs one in-order stream with no other "warps" to switch to, so the compiler has to insert sfpnops or find independent work itself.

Building exp() from multiply-adds

With multiply-add, exponent surgery and masks, you can build any function. The oldest exp routine in tt-metal shows all three in a dozen lines, and it is still called by the binary pow kernel (ckernel_sfpu_binary.h:61), on |x| only:

tt-metal/tt_metal/hw/ckernels/wormhole_b0/metal/llk_api/llk_sfpu/ckernel_sfpu_exp.h:470-492 @7aad8aac
sfpi_inline sfpi::vFloat _sfpu_exp_(sfpi::vFloat val) {
    // If exponent is > -1 extract it and replace with -1
    sfpi::vInt exp = exexp(val);
    v_if(exp >= 0) { val = setexp(val, 126); }
    v_endif;

    // Run series in Horner form
    sfpi::vFloat tmp = val * 0.8373f + sfpi::sFloat16b(0.863281f);
    val = val * tmp + 1.0f;

    v_if(exp >= 0) {
        val = val * val;
        for (int s_iter = 0; s_iter < 7; s_iter++) {
            exp = exp - 1;
            // Narrow predication on each loop
            v_and(exp >= 0);
            val = val * val;
        }
    }
    v_endif;

    return val;
}

The idea, before any code: ex for large x is hard, but for x in [0, 1) a quadratic is decent. Write x = 1.f·2k as usual, so x = m·2k+1 with m in [0.5, 1). Then ex = (em)2k+1, and raising to the power 2k+1 is just k+1 squarings. So:

  1. exexp reads the exponent k straight out of the FP32 bits. No arithmetic is needed.
  2. setexp(val, 126) overwrites the exponent field so the value becomes m in [0.5, 1). This happens only in lanes with k ≥ 0, under a mask.
  3. Two multiply-adds evaluate em ≈ 1 + m(0.863281 + 0.8373·m). The 0.8373 is the value hard-wired into LReg 8. The ISA does not say why that constant exists, but this polynomial is a plausible reason.
  4. Square k+1 times, using a narrowing mask: each loop round turns off the lanes that have finished.

Today's default bf16 exp on Wormhole (exp_tile with math_approx_mode = false and a 16-bit Dst) is a different algorithm. It computes x/ln2 + 127, clamps that to [0, 255], splits it into integer and fraction parts with exponent and mantissa instructions, evaluates a quadratic for 2frac, and stitches the result back together with SFPSETEXP. Its comments credit Moroz et al. 2022. It is hand-written with raw TTI_ instruction macros so that every slot is accounted for:

Twenty issue slots per vector, eight vectors per face, four faces per tile: 640 slots per tile, three of them sfpnops per vector just waiting out MAD latency. This is an instruction count from the binary, not a measured cycle count. ttsim cannot measure cycles (see below).

4096 / 64 = 64, independent of clock. The WH figures are straight from the ISA's MatrixUnit.md performance table and SFPMAD.md ("0.064 TFLOP/s (per Vector Unit)"). The BH SFPMAD page gives 0.0864 at 1.35 GHz. The BH FPU figure is my 4096 × 1.35 GHz, since the ISA notes that matrix-unit ratios "broadly apply to Blackhole".

Two honest qualifications:

  • Apples to oranges in precision. LoFi MVMUL multiplies 5-bit by 7-bit mantissas (A06). The SFPU does full FP32. At HiFi4 the FPU drops to 1.024 TFLOP/s, and the gap is 16×.
  • Peak is SFPMAD on every cycle. Real kernels also spend slots on loads, stores, nops, clamps and bit tricks. The exp above does 3 multiply-adds in 20 slots, and without SFPLOADMACRO the load and store sub-units cannot overlap with the MAD.

Why build it this way?

Compare the work per output element. A matmul output element with inner dimension K costs K multiply-adds, often thousands. An elementwise op costs a fixed handful per element. Since matrix multiplies dominate the FLOPs (A01), it makes sense to spend nearly all the area on the FPU and give the SFPU just enough to keep up with an output stream that arrives once per K MACs. The FPU's narrow multipliers are also what make 2048 of them per core affordable, and a general FP32 FMA lane is far larger than a 5×7-bit multiplier. (That last point is engineering inference, not a figure from the docs.)

The design bites when K is small. Here is my own arithmetic, using the counts above. Attention scores with head dimension 128 cost 4 tiles of K, so 4 × 16 = 64 LoFi cycles per 32×32 output tile, and then softmax needs an exp of that same tile, about 640 issue slots. The exponential, not the matmul, becomes the bottleneck. That is why kernels like SDPA have their own hand-tuned exp variants (on Blackhole, the ckernel_sfpu_sdpa_exp_unclamped.h and softmax_k files under tt-llk/tt_llk_blackhole/…/experimental; at this commit the Wormhole tree has no counterpart).

GPUs face the same imbalance. On recent NVIDIA parts, tensor-core throughput exceeds the special-function and FP32 units by a large factor, and attention kernels such as FlashAttention go to great lengths to hide or reduce exponentials. The SFPU's 64× ratio is a vivid local instance of a universal trend.

Not quite IEEE: the FMA that ttsim copies bit for bit

SFPMAD computes a*b + c in FP32, but not to the letter of IEEE 754. The ISA lists the differences:

  • Denormal inputs are treated as zero, and denormal outputs are flushed.
  • The multiply and add are "partially fused". The product keeps more than FP32 precision but not infinite precision, then there is one round-to-nearest-even step.
  • On Wormhole, a negative-zero result becomes +0, and NaN payloads are not canonical.

The ISA ships a bit-exact C model, fma_model_wh and fma_model_bh. Its list of WH-vs-BH differences contains this item: "If r_m = (r_m >> n) | (r_m & 1) ends up doing a shift right by two bits, the higher of those two gets dropped rather than contributing to the sticky bit (this is a hardware bug rather than anything intentional)."

ttsim does not call the host's fmaf. It reimplements the datapath in integer arithmetic, in sfpu_mad (tensix.cpp:4232-4331), with TT_ARCH_VERSION 0 for Wormhole and 1 for Blackhole. Here is the Wormhole rounding tail, bug included:

ttsim/src/tensix.cpp:4313-4321 @b3620244
#else
    uint32_t magnitude = uint32_t((sum < 0) ? -sum : sum);
    uint32_t rounded = std::bit_cast<uint32_t>(float(sum));
    uint32_t sign = rounded & 0x80000000;
    rounded &= 0x7FFFFFFF;
    // WH's two-bit normalization loses bit 1 instead of jamming it: an even tie can round down.
    if ((magnitude >= 0x10000000) && ((magnitude & 63) == 18)) {
        --rounded;
    }

Read it with small numbers. When the aligned integer sum has 29 bits (≥ 228), converting to FP32's 24-bit significand drops the low 5 bits. If those bits are 10010 (18), the true value is above the halfway point (16), so IEEE rounds up. Wormhole's normalizer drops bit 1 (the "2") instead of folding it into the sticky bit, sees 10000, which looks like an exact tie, and rounds to even. If the kept bit is even (bit 5 of the pattern 18 = 010010 is 0), that means rounding down. Hence --rounded.

To find a real instance, I compiled ttsim's sfpu_mad into a scratch program twice (once per TT_ARCH_VERSION) and searched random integer-valued inputs for a WH/BH disagreement. Then I cross-checked the hit against the ISA's own C model:

a=4086.0 b=65391.0 c=11176552.0
exact     = 278364178     (= 8698880·32 + 18: low 5 bits are 10010)
IEEE fmaf = 278364192     (round up, correct)
ttsim BH  = 278364192     fma_model_bh = 278364192
ttsim WH  = 278364160     fma_model_wh = 278364160   <- one ULP low

The low 5 bits of the exact result are 18, exactly the pattern in the code. Wormhole lands one ULP (32 at this magnitude) low; Blackhole and IEEE agree. Two independent implementations, the ISA's model and ttsim's, give the same answer. This is what "bit-exact simulator" means in practice: if your SFPU kernel's last bit differs between WH and BH on silicon, it should differ in ttsim the same way.

Do not expect SFPU results to match torch or NumPy to the last bit, even for a single a*b+c. Partial fusion can also produce results that differ from IEEE on both architectures: my search found cases such as 21441·32913 + 8802433, where WH and BH agree with each other but not with fmaf. Validate SFPU kernels with tolerances or PCC (A05), not bit equality with a CPU.

Wormhole vs Blackhole

The Blackhole ISA page sums it up in one sentence: the SFPU "gains new SFPARECIP, SFPGT, SFPLE, SFPMUL24 instructions, new modes of the existing SFPCAST, SFPPUSHC, and SFPSTOCHRND instructions, small enhancements to the existing SFPAND, SFPMAD, SFPOR, and SFPSHFT instructions, small changes to the existing SFPLOAD and SFPSTORE instructions, and bugfixes to the existing SFPPOPC and SFPSHFT2 instructions. It also clocks at 1.35 GHz rather than 1 GHz."

SFPARECIP is an approximation, and the ISA states its accuracy: for 2−126 ≤ x < 2126, 0.9944 · 1/x < ApproxRecip(x) < 1.0054 · 1/x, from a 128-entry table that supplies 7 mantissa bits. The exp mode is only accurate for 0 ≤ x < 2. Software refines the result. Blackhole's reciprocal starts from the hardware guess and adds Newton–Raphson steps:

Two notes on the sources. A comment inside this excerpt (line 32, elided above) says "SFPI doesn't support SFPLE/SFPGT at the moment". The SFPI 7.92 compiler in this orb did emit sfpgt for an ordinary v_if (a < 0.5f) on Blackhole (shown above), so that comment appears to be stale. Separately, ttsim implements only the plain reciprocal mode of SFPARECIP on Blackhole (tensix.cpp:5343-5347 rejects other modes as UnsupportedFunctionality), so a kernel using the hardware exp mode will not run in the simulator.

Recap

  • The SFPU is a 32-lane × 32-bit SIMD unit next to the FPU. It works only on LRegs (8 general registers plus constants such as 0.8373, 0, 1.0, −1.0 and lane index ×2) and reaches data only through Dst.
  • SFPLOAD/SFPSTORE move a 4-row × 8-column patch (even or odd columns) between Dst and an LReg. One 16×16 face = 8 vectors, and one tile = 32. SFPI's dst_reg[i] uses address 2i. Stores to BF16 truncate.
  • The instruction set is multiply-add plus bit surgery (exponent, mantissa, sign), integer ops, conversions, swaps and lookups. Transcendentals are small programs, such as the 20-instruction-per-vector bf16 exp.
  • Predication: per-lane flags (SFPSETCC, SFPENCC), an 8-deep flag stack (SFPPUSHC/SFPPOPC) and SFPCOMPC for else. Both branches are always issued, and masked lanes still cost their cycle.
  • 64×: MVMUL = 2048 MACs = 4096 FLOP per cycle; SFPMAD = 32 FMAs = 64 FLOP per cycle. WH: 4.096 vs 0.064 TFLOP/s per core. BH: 0.0864 for the SFPU at 1.35 GHz. The gap shrinks to 16× against HiFi4.
  • SFPMAD is partially fused, flushes denormals, and on WH has a tie-rounding bug. ttsim's sfpu_mad reproduces it bit for bit, and agrees with the ISA's C model.
  • Blackhole adds SFPARECIP (approximate 1/x and ex), SFPGT/SFPLE, SFPMUL24, 3-operand AND/OR, automatic MAD stalls, and IEEE-like zero and NaN handling.

Check yourself

1. A kernel calls dst_reg[5] on Wormhole with the Dst base at the start of a face. Which Dst rows and columns does the load read?

The SFPI index 5 becomes SFPLOAD address 10. The top bits give 10 & ~3 = 8, so rows 8–11. Bit 1 of 10 is set, so the odd columns 1, 3, …, 15. Lane L reads row 8 + L/8, column 2·(L mod 8) + 1.

2. In a v_if/v_else where every lane's condition is false, how many cycles does the if-branch cost compared with a version with no v_if at all?

It costs its full instruction count. The SFPU has no "skip if no lane is active". The TRISC pushed the branch's instructions without seeing the flags, and all lanes being disabled only stops them from writing. A GPU warp could skip the path; the SFPU cannot. Only the programmer (or a compile-time constant) can remove it.

3. Derive the 64× ratio between the FPU and SFPU peaks. Why does it become 16× for HiFi4 matmul?

MVMUL: 8×16×16 = 2048 MACs per instruction, 1 instruction per cycle, so 4096 FLOP per cycle. SFPMAD: 32 lanes × 1 FMA = 64 FLOP per cycle. 4096/64 = 64. HiFi4 needs 4 fidelity phases, each a separate MVMUL, so the FPU's effective rate drops to 1024 FLOP per cycle, and 1024/64 = 16.

4. Why does tt-metal's bf16 exp end with SFP_STOCH_RND before SFPSTORE, rather than just storing?

LRegs hold FP32. SFPSTORE to a 16-bit BF16 Dst truncates the mantissa toward zero (SFPSTORE.md:38), which biases results downward. The tt-metal comment gives 9² = 80.8 → 80.5 instead of 81. Rounding to nearest explicitly first gives the correctly rounded bf16, at the cost of one more instruction per vector.

5. Wormhole's SFPMAD computes 4086 × 65391 + 11176552 as 278364160, while IEEE gives 278364192. Is ttsim wrong?

No, ttsim is right. The exact value 278364178 has low bits 10010 below FP32 precision at this magnitude. Wormhole's normalizer drops bit 1 instead of making it sticky, treats the remainder as an exact tie and rounds to even (down). The ISA's own fma_model_wh gives the same 278364160, and Blackhole (and ttsim in BH mode) gives the IEEE answer. A bit-exact simulator must reproduce hardware quirks, not fix them.

6. You need 1/x to FP32 accuracy on Blackhole. Is SFPARECIP enough on its own? What would you add?

No. It gives about 7 correct mantissa bits (error within about ±0.5%). Add Newton–Raphson steps y ← y·(2 − x·y), each two multiply-adds and roughly doubling the correct bits (7 → 14 → 28). Two steps reach FP32's 24 bits, which is what sfpu_reciprocal_iter<2> does. On Wormhole the starting guess has to come from software as well.
