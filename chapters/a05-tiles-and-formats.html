05. Tiles, faces and number formats

The question

Here are sixteen numbers, the kind you might find in one row of a neural network's activations:

0.9, 0.82, −0.37, 0.51, 0.093, −0.64, 0.27, 0.011, −0.15, 0.44, 0.021, −0.71, 0.33, 0.058, −0.22, 0.95

Stored as BF16, each one carries its own 8-bit exponent: 16 numbers, 16 exponents. A Tenstorrent chip will happily store them a different way, with one exponent for all sixteen and only 8 bits per number for the sign and the digits. That saves almost half the memory and half the DRAM bandwidth, which on a memory-bound workload is close to half the run time.

It sounds too good to be true. If one number sets the exponent for everyone, what happens to the others? What if one of the sixteen is 300 instead of 0.9?

The chapter's question: can 16 numbers share one exponent and stay useful? The answer is "usually yes, and here is exactly when not". To get there we need two things first: why the chip groups numbers at all (tiles and faces), and what the bits of an ordinary float mean.

The previous chapter, A04, showed the Tensix core: unpackers feed the matrix engine's SrcA and SrcB registers, results land in Dst, and packers write them back to L1. This chapter is about the shape and the bits of the data that flows along that path. How the matrix engine multiplies those bits, and what "math fidelity" means, is the subject of A06.

Why tiles exist

Start with how a programmer thinks of a matrix: rows, one after another. A 64×64 matrix of BF16 values in row-major order is 64 rows of 64 elements, and each row is 128 bytes. Element (r, c) lives at address r×64 + c.

Now look at what the matrix engine wants. It does not consume rows. It consumes small square blocks: one instruction multiplies an 8×16 block by a 16×16 block (details in A06). The unit that moves through circular buffers, across the NoC and into the unpackers is a 32×32 block called a tile. Ask a row-major buffer for the top-left 32×32 block and you get 32 separate pieces of 64 bytes each, 128 bytes apart. Every one of those is a separate address to compute and, on the NoC, potentially a separate transaction.

The fix is old and simple: store the matrix the way you will read it. In tiled layout the 1,024 elements of a tile sit next to each other in memory, so one tile is one contiguous 2,048-byte page (for BF16). The tt-metal tensor layout report puts it this way:

"In a tiled tensor, pages are represented as 2D tiles, with the default tile size being 32x32, rather than being confined to a single row. For example, with a 64x64 tensor, this results in 4 tiles, each of size 32x32."
tt-metal/tech_reports/tensor_layouts/tensor_layouts.md:50 @7aad8aac

An analogy: a road atlas. A huge map printed as one long scroll, line by line, is "row-major": to see one town you unroll many lines and read a small part of each. The atlas cuts the map into pages so that one region is one page. Where the analogy breaks: atlas pages overlap at the edges and tiles do not, and memory has no second dimension at all; "page" here only means a run of consecutive addresses.

The animation colours every element of a 64×64 tensor by the tile it belongs to (four colours) and the face within the tile (four shades; faces come next). On the right is memory, address 0 at the top left, 128 elements per line. Watch where each tile ends up.

On a GPU, tensors usually stay row-major in global memory and the kernel does the tiling: it loads a block into shared memory, then into tensor-core fragments. Tenstorrent moves the tiling into the storage format itself. Every tensor that the compute engines touch is already in tile order before a kernel sees it, so a kernel reads a whole tile as one page and never computes strided addresses inside it.

Faces, face order and padding

Why is a tile split again into four 16×16 faces? Because 16 is the matrix engine's natural width. SrcA and SrcB are 16 columns wide, and one bank holds 64 rows of 16, which is exactly 1,024 values: one tile, four faces of 16 rows each (tt-isa-documentation/WormholeB0/TensixTile/TensixCoprocessor/SrcASrcB.md:3). The layout report says it directly:

"Each tile is split into faces ("sub-tiles"). By default, tile size is 32x32, and face size is 16x16 -- 4 faces per tile [...] (i.e., face0->face1->face2->face3 on the picture below). The reason for using faces is that the matrix engine natively multiplies 16x16 matrices, and tile multiplication is decomposed into multiple face multiplications."
tt-metal/tech_reports/tensor_layouts/tensor_layouts.md:60-62 @7aad8aac

The sizes are compile-time constants in the host API:

constexpr uint32_t TILE_WIDTH = 32;

The face order is easiest to see in code that actually walks a tile. This is the host-side packer that turns a 32×32 block into a block-float tile (we will meet block floats shortly). The four nested loops are the face order: tile-row of faces tr, tile-column of faces tc, row i inside the face, column j inside the face row.

                ...

So element (r, c) of a tile, with r, c in 0..31, sits at offset face×256 + (r mod 16)×16 + (c mod 16), where face = 2×(r ≥ 16) + (c ≥ 16). Face 0 is top-left, 1 top-right, 2 bottom-left, 3 bottom-right. Converting between the two orders is called tilize and untilize; A15 and A18 show where it happens in practice.

Two variations exist. With transpose_tile=True the faces are stored in column-major order (0 → 2 → 1 → 3) and the values inside each face are transposed too (tensor_layouts.md:83). And the hardware supports tile shapes of 32×32, 16×32, 4×32, 2×32 and 1×32, but "currently TT-Metalium only supports 32x32, with limited functionality for 16x32 in some ops such as matmul" (tensor_layouts.md:57). Assume 32×32 unless an op says otherwise.

Padding is the price of a fixed tile. Each of the last two dimensions is rounded up to a multiple of 32. A 3×5 tensor in tile layout costs a whole tile: 15 useful values out of 1,024. A 33×33 tensor costs four tiles. For the large matrices that dominate AI workloads this overhead is a rounding error. For a batch of small vectors it can dominate, which is why TT-NN also keeps a ROW_MAJOR_LAYOUT (one row per page, tensor_layouts.md:33-34) for data that the matrix engine will not touch.

Four ways to spell a float

Now the bits inside each element. Every floating-point format here works the same way: a sign bit, an exponent that picks a power of two (the "zoom level"), and a mantissa that picks a point inside that power of two. A normal number is (−1)s × (1 + m/2M) × 2e − bias, where M is the number of mantissa bits. Exponent bits buy range; mantissa bits buy precision. The four formats you will meet trade them differently:

FormatSignExponentMantissaRelative step (2−M)Where you meet it
FP3218 (bias 127)231.2×10−7Host tensors, Dst in 32-bit mode, SFPU registers
TF3218109.8×10−4The widest float in SrcA/SrcB; FP32 inputs become this
BF161877.8×10−3The default dtype for activations and weights
FP1615 (bias 15)109.8×10−4Supported, rarer; range only up to about 6.5×104 in IEEE

BF16 is FP32 with the bottom 16 bits cut off: same exponent, same range, only 7 mantissa bits. TF32 is FP32 cut to 10 mantissa bits, 19 bits in total. The ISA documentation defines both that way: "starting with IEEE 754 FP32 and then truncating the mantissa down to 10 bits" for TF32 and "down to 7 bits" for BF16 (FloatBitPatterns.md:29,49). FP16 keeps 10 mantissa bits but shrinks the exponent to 5, which is why it overflows at 65,504 while BF16 reaches about 3.4×1038.

Type a number below and watch it become bits. The error column shows what each format loses. Try 0.1 (no binary format holds it exactly), 16777217 (FP32 itself runs out of mantissa), 70000 (FP16 overflows) and 1e-6 (FP16 goes subnormal).

Two things to notice. First, BF16 and TF32 have the same exponent field as FP32, so converting between them never overflows; only the mantissa changes. FP16 has to squeeze the exponent too, which is where its overflow and subnormal behaviour comes from. Second, the checkbox matters: the host rounds FP32 to BF16 to nearest, but the unpacker truncates when it reads FP32 into a source register, as the next section shows. With 0.1, rounding gives BF16 0x3DCD = 0.10009765625 (error +9.8×10−5); tick the box and truncation gives 0x3DCC = 0.099609375 (error −3.9×10−4), four times worse and always toward zero. Truncation errors do not average out the way round-to-nearest errors do, which matters over a long accumulation.

Inside the core: 19-bit Src, 32-bit Dst

Why does TF32 exist at all? Look at the size of the source registers:

"Each of SrcA and SrcB can be viewed as having 2 banks of 64 rows of 16 columns of 19-bit data."
tt-isa-documentation/WormholeB0/TensixTile/TensixCoprocessor/SrcASrcB.md:3 @be833101

Nineteen bits is 1 + 8 + 10: exactly one TF32. The multipliers behind those registers are built for that width (and A06 shows they are much narrower still, using several passes). Every float format that enters SrcA or SrcB is fitted into those 19 bits (SrcASrcB.md:55-59):

  • TF32 fills them. FP32 from L1 "can be converted to TF32, though the conversion involves throwing away the low 13 bits of mantissa."
  • BF16 is "overlaid onto TF32, with the three least significant bits of the TF32 mantissa set to zero."
  • FP16 (1/5/10) uses the same 19 bits with a 5-bit exponent.
  • An integer "8" type, overlaid on FP16, for integer matmuls.

The simulator makes "throwing away" concrete. This is ttsim's unpacker converting an FP32 datum on its way into a source register. There is no rounding: the bits are masked off.

ttsim/src/tensix.cpp:3472-3482 @b3620244

    if (unpack_to_dst) {

    }
} else if (out_data_format == 5) { // bf16
    ...

    value &= 0xFFFF0000; // drop low 16 bits of mantissa (no rounding)

So a full FP32 multiply never happens in the matrix engine. FP32 survives only where there is room for 32 bits: in Dst, and in the vector engine's registers (A07).

Dst is the opposite of narrow. It is 1,024 rows × 16 columns × 16 bits, which can also be viewed as 512 rows of 32-bit values (Dst.md:3). That is 16 BF16 tiles or 8 FP32 tiles. Here is a detail you will only see if you dump raw register contents from an instrumented simulator: Dst does not store BF16 in the usual bit order. Both the ISA spec (Dst.md:105-115) and ttsim define a shuffle that puts the mantissa in the high byte and the exponent in the low byte:

ttsim/src/tensix.cpp:912-922 @b3620244 (comments added)
static inline uint16_t dst_decode_bf16(uint16_t x) {
    uint16_t e = x & 255;
    uint16_t m = (x >> 8) & 127;
    return (x & 0x8000) | (e << 7) | m;
}

static inline uint16_t dst_encode_bf16(uint16_t x) {
    uint16_t e = (x >> 7) & 255;    // 8-bit exponent from a normal BF16
    uint16_t m = x & 127;           // 7-bit mantissa
    return (x & 0x8000) | (m << 8) | e;   // stored as: sign | mantissa | exponent
}

BF16 1.0 is 0x3F80 in memory and 0x007F inside Dst. Every unit that reads or writes Dst applies these helpers, so software never sees the shuffle. The 32-bit form applies the same shuffle to its high half and leaves the low 16 mantissa bits alone (Dst.md:130-135).

Tensix floats are not quite IEEE. The ISA spec lists the differences (FloatBitPatterns.md). The matrix unit treats FP32/BF16 denormals as zero and treats exponent 255 as an ordinary large number, not infinity or NaN; it outputs that pattern for values too large to represent. For FP16 there is no NaN at all, and exponent 31 is an ordinary exponent to the FPU. Values from PyTorch that rely on inf/NaN semantics may need pre- or post-processing. The bit explorer above prints a note whenever a value hits one of these cases.
TF32 will look familiar: it is the same 1/8/10 layout that NVIDIA's Ampere tensor cores introduced for "FP32" matmuls. The idea is similar: keep FP32's range, multiply with a narrower mantissa, and accumulate in FP32 (on Tensix, only when Dst is in 32-bit mode). Two differences: even with all four fidelity phases the matrix engine does not use every TF32 mantissa bit from SrcA (SrcASrcB.md:115, more in A06), and the conversion differs. The Tensix unpacker truncates FP32 to TF32; it does not round.

Block floating point

Back to the opening question. Look at the exponents of those sixteen activations. Most of them lie between 2−4 and 20. Storing sixteen copies of nearly the same 8-bit exponent is wasteful. Block floating point stores the exponent once per group and gives each value only a sign and a fixed-point magnitude relative to that shared exponent.

An analogy: a group photo with one exposure setting. The camera meters on the brightest face, and everyone else is recorded relative to it. Faces nearly as bright come out fine; faces in deep shadow come out black. The brightest value sets the shared exponent, values near it keep all their bits, and values far below it lose bits from the bottom until nothing is left. Where the analogy breaks: a camera sensor fades gradually, while BFP loses exactly one bit of precision for every halving below the maximum, and a value goes to exactly zero once it falls 8 binades below the maximum. And each 16-value group has its own exposure, so one bright face only darkens its own row.

The format, exactly

The ISA spec defines the family (FloatBitPatterns.md:89-99):

"These consist of either 8 or 4 or 2 bits per datum, where the most significant bit is a sign bit and the remaining bits are a magnitude. Exponents are separate, with each group of 16 datums sharing a common 8-bit exponent (though BFP8a/BFP4a/BFP2a only use the low five bits of the exponent and expect the high three bits to be zero)."

For BFP8 a datum is 1 sign bit and a 7-bit magnitude Mag, and its value is Mag/26 × 2Exp−127. There is no hidden leading 1: the leading 1 is stored explicitly, which is why tt-metal's data format notes say BFP8 really keeps "6 bits total" of the original mantissa (data_formats.md:12). The value with the largest exponent gets Mag in 64..127, i.e. 1.xxxxxx in binary. A value half as large gets 0.1xxxxx, losing one bit. A value 2−7 as large gets at most one bit, and anything smaller becomes 0.

Tenstorrent names: Bfp8_b, Bfp4_b, Bfp2_b are the 8-bit-exponent formats (the "b" matches BF16's exponent, and these unpack to BF16). Bfp8, Bfp4, Bfp2 without the suffix are the "a" variants with a 5-bit exponent that unpack to FP16 (Unpackers/FormatConversion.md:8-9). In TT-NN they appear as ttnn.bfloat8_b and ttnn.bfloat4_b.

The aha: drag the outlier

Each row shows the magnitude bits that survive. Dim red cells are bits spent on alignment: leading zeros that the value needs because its own exponent is smaller than the shared one. The quantizer is a line-by-line port of the real code. Pick the host converter (what ttnn.from_torch(..., dtype=ttnn.bfloat8_b) runs on the CPU) or the device packer in either of its two configurations, explained in the next section.

Things to try, and what they show:

  • No outlier (0.9). The block's largest value is 0.95, so the shared exponent is that of [0.5, 1). Values near 0.5–1 keep 6–7 significant bits. 0.011 is already 6 binades down and keeps a single bit: its stored value is 0.0078, a 29% error. BFP8 is a relative-to-the-block format; values far below the block maximum are always coarse.
  • Outlier at 10. The exponent rises by 4 binades and every other magnitude shifts right by 4. The 0.011, 0.021 and 0.058 values vanish.
  • Outlier at 300. The shared exponent is now that of [256, 512), and everything below 2 (8 or more binades down) is exactly zero. Fifteen of sixteen values are gone. Yet PCC over all sixteen still prints about 0.99998, because the outlier dominates the variance. Remember this when we get to PCC.
  • Switch to BFP4_b. Only 3 magnitude bits, so every stored value is a multiple of 1/8 of the block's top binade. With no outlier the three smallest values collapse; once the outlier reaches 4 (the [4, 8) binade), 10 of the other 15 are zero.
BFP works when the 16 values in a face row have similar magnitudes, which is often true of weights and many activations. It fails, locally and silently, when one value is far larger than its 15 neighbours. The damage is confined to that one face row of 16 values; the other 63 groups in the tile have their own exponents.

Going back to BF16 is easy. The unpacker converts BFP8 to BF16 without loss, because a 7-bit magnitude, once normalized, has at most 6 bits after its leading 1, and BF16 has room for 7. ttsim implements it exactly as the spec's pseudocode (FloatBitPatterns.md:121-133):

ttsim/src/tensix.cpp:3141-3151 @b3620244 (comments on the mag lines and return added)
static inline uint16_t bfp8_to_bf16(uint8_t x, uint8_t exp_bits) {
    uint32_t sign = x >> 7;
    uint8_t mag = x << 1;                 // 7-bit magnitude, moved to the top of a byte
    if (!mag) {
        return sign ? 0xFF80 : 0; // zero-magnitude encodings map to -inf and +0
    }
    uint32_t lz = __builtin_clz(mag) - 24; // perform an 8-bit CLZ
    mag <<= lz;                           // normalize: leading 1 to the top
    exp_bits -= lz; // this will often wrap; seems odd, but spec/silicon are consistent here
    return (sign << 15) | (uint16_t(exp_bits) << 7) | (mag & 0x7E);   // drop the leading 1
}

Two details in that function deserve a second look. A sign bit with magnitude 0 (byte 0x80) does not mean −0: it decodes to BF16 0xFF80, which is −infinity in IEEE terms ("−2128 or −Infinity", FloatBitPatterns.md:99). That is why both packers make sure to never write 0x80. And the exponent subtraction can wrap if the shared exponent is very small, which the comment notes is how silicon behaves too.

Rounding and saturation, bit for bit

To quantize a block, every converter does the same three things: find the largest exponent among the 16 values, shift each mantissa right by its distance from that exponent, and round what falls off the bottom. The sources agree on the first two steps and on one more rule, saturation. They disagree on how to break ties, and there is a configuration that rounds twice.

Saturation: clamp, don't renormalize

If the largest value's mantissa is all ones, rounding up overflows 7 bits (1.1111111 rounds to 10.000000). A correct float conversion would bump the exponent. BFP cannot do that without re-shifting all the other 15 values, so it clamps to the largest magnitude instead. The tt-metal notes say: "If there is an overflow in the mantissa when we round up, we do not recompute the max shared exponent and re-normalize across the 16 numbers. Instead, the mantissa is set to the max value (ie. all 1's)" (data_formats.md:20). The ISA spec has the same rule as if (Mag == 128) Mag = 127;. In practice: BF16 1.9921875 becomes 1.984375 in BFP8_b (on the host, and on the device with bfp8_pack_precise; the default device path differs, as shown below).

Ties: the host and the device packer disagree

The host converter, which runs when you call ttnn.from_torch(..., dtype=ttnn.bfloat8_b), rounds to nearest with ties to even:

tt-metal/tt_metal/impl/data_format/blockfloat_common.cpp:305-325 @7aad8aac (trimmed; the two trailing comments are added)
// Round mantissa to nearest; ties round to even
...
uint32_t round_value = mantissa & MANTISSA_ROUND_MASK;   // the 17 bits below the kept 7
mantissa = mantissa >> MANTISSA_BFP_SHIFT;
uint32_t guard_bit = mantissa & 0x1;

if (round_value > TIE_VALUE or (round_value == TIE_VALUE and guard_bit == 1)) {
    // Round up
    mantissa += 1;
}

mantissa = std::min(mantissa, MANTISSA_BFP_MAX_VAL);      // saturate at 127

The device packer, which runs when a kernel packs Dst into a BFP8_b circular buffer, is specified differently in the ISA documentation: "deterministic round-to-nearest with ties away from zero" (Packers/FormatConversion.md:79). Its reference code works on BF16 input:

tt-isa-documentation/WormholeB0/TensixTile/TensixCoprocessor/Packers/FormatConversion.md:84-103 @be833101 (the "8 bits incl. hidden 1" comment is added)
void BF16ToBFP8(const uint16_t Datums[16], uint8_t* SharedExp, uint8_t BFP8[16]) {
  uint8_t MaxExp = 0;
  for (unsigned i = 0; i < 16; ++i) {
    uint8_t Exp = (Datums[i] >> 7) & 0xff;
    if (Exp > MaxExp) MaxExp = Exp; // NB: Exp == 255 is not special
  }
  *SharedExp = MaxExp;
  for (unsigned i = 0; i < 16; ++i) {
    uint8_t Sign = Datums[i] >> 15;
    uint8_t Exp = (Datums[i] >> 7) & 0xff;
    uint8_t Man = (Datums[i] & 0x7f) | (Exp ? 0x80 : 0);   // 8 bits incl. hidden 1
    unsigned Shift = MaxExp - Exp;
    uint8_t Mag = 0;
    if (Shift < 8) {
      Mag = (Man + (1u << Shift)) >> (Shift + 1); // Round to nearest, ties away from zero
      if (Mag == 128) Mag = 127; // Clamp rather than renormalize
    }
    BFP8[i] = Mag ? ((Sign << 7) | Mag) : 0; // Never 0x80
  }
}

Read the rounding line slowly. Man has 8 significant bits; the result keeps 7 − Shift of them. Adding 1 << Shift adds exactly half of the last kept bit's weight, then the shift drops everything below: round half up, on the magnitude. A value whose exponent is 8 or more below the maximum is zero without any rounding at all. ttsim's packer (src/tensix.cpp:2964-2987) is the same algorithm line for line, so we can test it.

The tie rule is a disagreement between sources, not a typo. tt-metal's data_formats.md and its host code say ties go to even; the ISA spec and ttsim say the device packer sends ties away from zero. Both are true, of different code paths. A tensor quantized on the host and the same tensor quantized on device can differ by one unit in the last place on exact ties. The run below confirms it.

The double rounding you get by default

There is a second packer configuration, and it is the default. Kernels have a bfp8_pack_precise flag that is false unless an op sets it (tt_metal/api/tt-metalium/kernel_types.hpp:111). When it is false, the JIT build picks Bfp8_b as the packer's intermediate format (tt_metal/jit_build/data_format.cpp:329-334), which the ISA describes as an early rounding "To E8M6" (BF16 with 6 mantissa bits) before the BFP conversion (Packers/FormatConversion.md:14,188). typecast to BFP8_b sets the flag to true (ttnn/cpp/ttnn/operations/copy/typecast/typecast.cpp:42; only for BFP8_b, not BFP4_b); ordinary ops such as ttnn.add do not. I ran a second probe, sim-labs/workbench/py/bfp8_double.py, that sends the same values through both (output rearranged into columns; identical on wh and bh):

Every other value in the block then loses a bit, which is why 0.30078125 and 0.2001953125 move further from their true values. Pick "device packer, default" in the figure to reproduce this column. For BFP4_b and BFP2_b the device always rounds to BFP8 first and then truncates (Packers/FormatConversion.md:71). The host instead rounds straight to 3 or 1 bits, so host and device differ much more often for those formats. The figure's self-check includes a BFP4_b run (sim-labs/workbench/py/bfp4_probe.py).

One limit: ttsim rejects stochastic rounding as out of scope (src/tensix.cpp:598-603), so you cannot simulate that mode.

A family tree: HBFP, MSFP and OCP MX

Shared exponents are much older than deep learning. The MSFP paper itself notes that using them to get "a precision approaching floating point while using a fixed-point processor" is "not new in computer architecture". The deep-learning branch of the family tree looks like this:

  • HBFP (Drumond et al., NeurIPS 2018) trained DNNs with "hybrid block floating point": block floating point for the dot products, ordinary floating point for everything else.
  • MSFP (Rouhani et al., NeurIPS 2020, Microsoft) is nearly the same format as Tenstorrent's. Its paper defines a "bounding box" of values sharing the maximum exponent, an 8-bit shared exponent, a sign-magnitude mantissa with no implicit leading bit, and a default box size of 16. MSFPN is named by the sum of the sign, mantissa and shared-exponent widths, so MSFP16 (1 + 7 + 8) has the shape of BFP8_b and MSFP12 (1 + 3 + 8) the shape of BFP4_b. The paper reports MSFP16 at "3× lower cost compared to Bfloat16".
  • OCP Microscaling (MX) (v1.0, September 2023, from AMD, Arm, Intel, Meta, Microsoft, NVIDIA and Qualcomm) standardizes the idea with two changes. The block is 32 elements, with an E8M0 scale (a pure 8-bit power of two). And each element can be a tiny float with its own small exponent, not just a fixed-point magnitude: MXFP8 (E4M3 or E5M2), MXFP6 (E2M3 or E3M2), MXFP4 (E2M1), and MXINT8, which is the closest relative of BFP8.

The tt-metal enum already lists MX formats (MxFp8R, MxFp8P, MxFp6R, MxFp6P, MxFp4, MxInt8, MxInt4, MxInt2), each with a tile size of "32 scales (1 per 32-elem block)" plus data, for example 1056 bytes for MxInt8 (tt_backend_api_types.hpp:130-137). These are for the next-generation Quasar core: the Quasar LLK packer handles them (tt_metal/tt-llk/tt_llk_quasar/common/inc/cpack_common.h:76-80), while the Blackhole JIT code notes "MX formats are absent from the Blackhole DataFormat enum" (tt_metal/hw/ckernels/blackhole/metal/llk_api/data_format_derive.h:32-33). On Wormhole and Blackhole, the block formats are BFP8/4/2.

GPUs mostly reached narrow formats from the other direction: FP16, then FP8 with a per-tensor scale. The MX paper argues that per-tensor scaling "has been shown to be insufficient [...] for sub-8-bit formats", and that fine-grained per-block scales are what make those formats work. Tenstorrent's BFP formats have had per-16-value scales from the start, and they are a storage format for whole tensors, so they save DRAM bandwidth as well as compute.

Measuring correctness: PCC and tolerances

If a BFP8 matmul cannot match an FP32 reference exactly, what should a test check? Tenstorrent's tests overwhelmingly use the Pearson correlation coefficient (PCC) between the device result and a PyTorch "golden":

PCC = Σ(g−ḡ)(c−c̄) / √( Σ(g−ḡ)² · Σ(c−c̄)² )

tt-metal/ttnn/ttnn/comparison.py:137-143, 151 @7aad8aac
n = golden.numel()
g_centered = golden - (golden.sum(dtype=torch.float64) / n).to(golden.dtype)
c_centered = calculated - (calculated.sum(dtype=torch.float64) / n).to(calculated.dtype)
cov = (g_centered * c_centered).sum(dtype=torch.float64)
g_sq_sum = g_centered.pow(2).sum(dtype=torch.float64)
c_sq_sum = c_centered.pow(2).sum(dtype=torch.float64)
denom = torch.sqrt(g_sq_sum * c_sq_sum)
...
cal_pcc = (cov / denom).item()

PCC is 1.0 for a perfect match and falls as the error grows relative to the spread of the data. It does not care about the overall scale of the tensor, and it does not need a hand-picked absolute tolerance. That is why one threshold can serve a whole sweep of tensor shapes.

Because the error is set by the format, so is the threshold. Real tests say it outright:

tt-metal/tests/ttnn/unit_tests/operations/matmul/test_addmm.py:621 @7aad8aac
assert_with_pcc(torch_output_tensor, out_tensor, pcc=0.999 if dtype == ttnn.bfloat8_b else 0.9999)
tt-metal/tests/ttnn/unit_tests/operations/eltwise/test_binary_fp32.py:833 @7aad8aac
@pytest.mark.parametrize("ttnn_dtype, pcc", [(ttnn.bfloat8_b, 0.999), (ttnn.bfloat4_b, 0.97)])

The pattern, roughly: BF16 tests expect four nines, BFP8_b three, and BFP4_b somewhere between 0.9 and 0.98, depending on the op. Softmax with BFP8 input relaxes PCC to 0.99 and loosens rtol/atol too (tests/ttnn/unit_tests/operations/fused/test_softmax.py:1178-1180). Even the allclose fallback in comp_pcc scales with the format: for BF16 or FP16 tensors it widens the relative tolerance to 4 units of the format's epsilon, max(rtol, 4 * max(sixteen_bit_eps)) (comparison.py:78-83), because "a result one ULP from the golden" would otherwise fail.

Even a plain BF16 add is not bit-identical to PyTorch. Running the workbench's 32×32 ttnn.add script on the simulated Wormhole gave:

refs/sim-runs/ttnn/ttnn_add.py, run on ttsim (wh), output trimmed
max abs diff: 0.0078125

PASS
PCC is blind to some bugs. It is invariant to scale and offset: a result that is exactly 2× the golden, or golden + 5, has PCC 1.0. And as the BFP figure showed, one large value can hold PCC above 0.9999 while fifteen others are zero. Pair PCC with a check that does see magnitude (max absolute error, allclose, or a comparison of norms), and look at regions as well as the whole tensor. A slice of all-zero rows hidden in a large tensor barely moves the global PCC.

How do you pick a format, then? A reasonable default: keep activations in BF16, try weights in BFP8_b (half the DRAM traffic, and weights tend to have well-behaved magnitudes within a face row), and measure the model-level metric, not only per-op PCC. BFP4_b is for weights that tolerate it, usually after checking accuracy end to end. A06 adds the other dial, math fidelity: BFP8 operands need only 2 multiplier phases for full precision where BF16 needs 4 (SrcASrcB.md:110-115), so the narrower format is cheaper to compute as well as to move.

Recap

  • A tile is 32×32 values stored contiguously, one page in CBs and DRAM. Inside, four 16×16 faces are stored in order 0 (top-left), 1 (top-right), 2 (bottom-left), 3 (bottom-right), each row-major. Offset = face×256 + (r mod 16)×16 + (c mod 16).
  • Faces exist because SrcA/SrcB are 16 wide and one bank of 64×16 holds exactly one tile. Tile layout pads both trailing dims to multiples of 32; a 3×5 tensor costs a whole tile.
  • FP32 (1/8/23), TF32 (1/8/10), BF16 (1/8/7) and FP16 (1/5/10). Source registers are 19 bits: TF32, BF16 or FP16. The unpacker truncates FP32 to TF32 or BF16. Full FP32 lives only in Dst and the SFPU. Dst stores BF16 with a byte shuffle that software never sees.
  • The FPU is not IEEE at the edges: denormals are zero, exponent 255 is a normal number for FP32/BF16, and FP16 has no NaN.
  • BFP8_b/4_b/2_b: 16 values (one face row) share an 8-bit exponent; each value is a sign plus a 7/3/1-bit magnitude with an explicit leading 1. Tiles are 1088/576/320 bytes (64 exponent bytes plus data). Unpacking to BF16 is lossless.
  • Quantizing: take the max exponent, shift, round, and clamp on overflow (no renormalization). The host rounds ties to even; the device packer rounds ties away from zero; with the default bfp8_pack_precise=false it also rounds to E8M6 first. Values 8 or more binades below the block's maximum become 0.
  • The idea runs HBFP → MSFP (16-value boxes, 8-bit shared exponent; MSFP16 has the shape of BFP8) → OCP MX (32-value blocks, E8M0 scale, small-float elements), which tt-metal lists for Quasar.
  • Correctness is measured with PCC against a golden, with thresholds that loosen as the format narrows (about 0.9999 for BF16, 0.999 for BFP8_b, 0.97 for BFP4_b). PCC misses scale errors and can hide localized collapse, so pair it with a magnitude check.

Check yourself

1. A BF16 tensor is 33×33. How many tiles and bytes does it take in tile layout, and what fraction is useful?

Both dimensions round up to 64, so it is 2×2 = 4 tiles × 2048 B = 8192 B. Useful elements: 33×33 = 1089 of 4096, about 27%. One extra row and column beyond 32 cost three extra tiles. This is why shapes that are multiples of 32 matter.

2. Within one tile, where is element (row 17, column 3) in tile order, and where would it be in row-major order?

Row 17 ≥ 16 and column 3 < 16, so it is in face 2 (bottom-left). Offset = 2×256 + (17−16)×16 + 3 = 531. In row-major order it would be 17×32 + 3 = 547. Same tile, different position: any code that indexes a tiled buffer as if it were row-major silently reads the wrong values.

3. Why is BFP8_b → BF16 lossless, while BF16 → BFP8_b is not?

A BFP8 value is at most a 7-bit magnitude times a power of two. After normalizing, at most 6 bits remain after the leading 1, and BF16 has 7 mantissa bits and the same 8-bit exponent, so every BFP8 value is exactly representable. Going the other way, BF16 has 8 significant bits (with the hidden 1) and its own exponent. BFP8 keeps at most 7 significant bits even for the block's largest value, and one fewer for every binade a value sits below the maximum.

4. A face row holds 1000.0 and fifteen values between 1 and 2. What does BFP8_b store for the fifteen?

1000 is in [512, 1024), exponent byte 127 + 9 = 136. Values in [1, 2) have exponent 127, so Shift = 9. The packer computes a magnitude only when Shift < 8, so all fifteen become exactly 0. (With the host converter the shifted mantissa also rounds to 0.) Only that one face row is affected; the tile's other 63 rows have their own exponents.

5. Your op passes with PCC 0.99998 in BF16 but gives 0.9985 with BFP8_b inputs. Is that a bug?

Not by itself. tt-metal's own tests use 0.999 for BFP8_b where BF16 uses 0.9999 (for example test_addmm.py:621), because BFP8 keeps at most 7 bits per value relative to a shared exponent. Check the result against a magnitude-aware metric too, and look for face rows with outliers. If the PCC drop is concentrated in a few rows, it is the format's behaviour, not a kernel bug, and the fix is a wider format for that tensor.

6. Why does the device packer write +0 when a negative value rounds to a magnitude of zero?

Because the byte 0x80 (sign 1, magnitude 0) does not mean −0 in BFP8. It decodes to BF16 0xFF80, "−2128 or −Infinity" (FloatBitPatterns.md:99). Writing it would turn a tiny negative number into −infinity. The reference code says so: BFP8[i] = Mag ? ((Sign << 7) | Mag) : 0; // Never 0x80, and the host converter likewise adds the sign "only if result is not 0".
