14. One tile's journey

One bf16 tile, followed from host memory to DRAM, across the NoC, through a circular buffer, into the Src registers, through an ELWADD into Dst, out through the packers and back to DRAM. All of it comes from a single instrumented ttsim run, and each step links back to the chapter that taught it.

The question

Eleven chapters have each covered one piece of the machine. A03 drew the grid, A08 the network, A09 the banks, A11 the circular buffers, A12 the three-thread compute kernel, and A13 the MOP expander. Each one made sense on its own. This chapter adds nothing new. It asks one question, again and again:

Where is this tile right now?

"This tile" is tile 0 of metal_example_eltwise_binary: the first 32×32 block of bf16 values in input A, its partner in input B, and the sum they become. The program adds two 64-tile tensors on one core, with the reader, compute and writer kernels you met in A11. We'll follow tile 0, and only tile 0, the whole way round, and we'll stop at every place it sits long enough to have an address.

The difference from the earlier chapters is that every number on this page, including every address, coordinate, bank, opcode, counter value and clock, comes from one run of the simulator. We don't stitch together facts from separate experiments. One trace file has them all, in the order the simulator did them.

One run, one trace

Earlier chapters each built their own probe. A08 and B05 logged NoC commands in noc_cmd_ctrl. B03, B04 and A13 traced Tensix instructions and MOP expansion. A11 used DPRINT overlays to print CB pointers. For this chapter I combined them into one instrumented ttsim (Wormhole build, ttsim b3620244), made with the workbench's build_ttsim.sh. It folds in the existing patches b05-noclog, b04-trace and b04-mop, plus the opcode-name table from b03-tti, so it applies on its own to pristine ttsim (don't apply those patches first), and adds five small hooks that all write into the same file:

  • Host writes and reads that land in a DRAM tile, logged where the PCIe TLB window is decoded (pcie.cpp, tlb_window_write/_read).
  • NoC commands issued by a Tensix core (the B05 hook, copied into the shared file).
  • CB counters: every write to the overlay stream registers that tt-metal uses as tiles_received/tiles_acked (A11), and every read that returns a value the reading hart hasn't seen before. That second rule turns a spin loop into one line: the moment the wait is satisfied.
  • Operand details inside UNPACR (L1 address, Src bank), ELWADD (banks, rows, first datum) and PACR (packer, Dst row, L1 address).
  • Semaphore values after every SEMINIT/SEMPOST/SEMGET/SEMWAIT.

The journey, at three zoom levels

Below, the trace for tile 0 is cut down to 48 events. Each one is a real line from journey.trace with its real clock. To pick the same 48 lines out of your own trace, run python3 sim-labs/workbench/py/a14_journey.py $LAB_HOME/journey.trace (source); only the a0/b0/d0 datums should differ. The slider moves through them in trace order, which is the order in which ttsim executed them. The three panels show the same moment at three zoom levels: the chip (which tile of the 10×12 grid holds the data), the core (which RISC-V is acting, and which CB slot holds the data) and the registers (which Src bank, Dst rows, semaphore or packer). The tile glows wherever its newest copy is. A yellow outline marks the actor of the current event when that event moves no data. The strip at the bottom puts every event on a true clock axis. Notice the tower at 4523.

The tile is never "moved". Every hop is a copy: the host's std::vector, the DRAM page, the CB slot, the Src bank and the Dst rows each hold a version of tile 0 at once. The CB counters and the semaphore exist only to say which copy is the live one and when an old one may be overwritten.

Zoom 1: the chip

Into DRAM. At clock 4091 the host writes page 0 of A, 2048 bytes (32×32 bf16), into DRAM tile D(0,11) at 0x2d4c40. Page 0 of B goes to the same tile at 0x2d7c40. Why that tile? The buffers are interleaved with one tile per page, so page i goes to bank i mod 12 (A09). The soc descriptor maps bank 0 to channel 0's endpoint 0-11 (soc_descriptors/wormhole_b0_80_arch.yaml:11-31). 0x2d4c40 is the bottom of usable DRAM, the first buffer address A09's probe printed. So A, B and the output each start at the same offset in every bank: 0x2d4c40, 0x2d7c40 and 0x2dac40, 12 KiB apart, because each of the 64-page buffers takes 6 pages = 12 KiB of every bank. The trace logs 128 host writes of 2048 B, all at clock 4091. ttsim only advances its clock when the host asks it to, so a burst of host writes shares a single clock value (A10; dispatch itself is A17).

Across the NoC. The reader runs on BRISC of logical core (0,0), which is NoC 0 tile T(1,1) in ttsim's unharvested layout (A03). At clock 4482 it issues a READ on NoC 0, command buffer 1, from D(0,11):0x2d4c40 to its own L1 at 0x19e60. At 4486 it issues the matching read of B into 0x1ae60. The route comes from A08, not from the simulator. NoC 0 runs only right and down, so the one-flit request travels 9 hops right (wrapping) and 10 down, 19 in all. The 2 KiB response rides the short leg, 1 right and 2 down (wrapping), 3 hops. ttsim models no routing. It copies the bytes inside the store that starts the command (tile.cpp:1620), which is why the read and the following received=1 are only 17 clocks apart. In the figure, the hop paths are derived from the routing rule and the copy itself is real.

Back out. The writer on NCRISC uses NoC 1. At clock 4547 it issues a WRITE, command buffer 0, from T(1,1):0x1be60 to D(0,11):0x2dac40, which is page 0 of the output buffer, also in bank 0. On NoC 1 (up, then left) the data leg is 1 hop up, wrapping 1 more, then 1 left: 3 hops. That is the convention from A08 and A11: inbound on NoC 0, outbound on NoC 1, data on the short leg both times. Finally, at clock 7807, after Finish, the host reads D(0,11):0x2dac40 back. It's the first of the output's 64 page reads.

On a GPU, tile 0 would reach registers through ld.global and the cache hierarchy, and the addresses in between (L2 slice, L1 line) would be invisible and chosen by hardware. Here, three of the hops are explicit commands in your kernels (two NoC reads and one NoC write), and the destination of each is an address that your host code chose when it created the CBs.

Zoom 2: the core

Inside T(1,1), five CPUs pass the tile along through three circular buffers in L1. The host made each CB 2 pages of 2048 B (eltwise_binary.cpp:90-108), packed upward from the bottom of free L1. That gives c_0 at 0x19e60, c_1 at 0x1ae60 and c_16 at 0x1be60, each 0x1000 long. Tile 0 always uses slot 0 of each.

Read the trace against this listing and against the reader and writer loops from A11:

  • 4459, BRISC reads c_0's counters (received 0, acked 0) in reserve_back (read_tiles.cpp:44): both slots are free.
  • 4482/4486, the two NoC reads. 4499, BRISC writes c_0 received=1 after async_read_barrier (lines 53-54). This is the publish from A11. Until this store, the bytes at 0x19e60 exist, but no other CPU is allowed to believe them.
  • 4501, TRISC0, spinning in cb_wait_front, sees received=1. At 4508/4509 the same happens for c_1. Only TRISC0 runs these calls (A12).
  • 4507, TRISC2 is already in cb_reserve_back(c_16). Its source line (48) comes after tile_regs_wait, but that call is only a queued SEMWAIT. The RISC-V pushes it and runs ahead (A04).
  • 4523, the Tensix side. c_0 acked=1 and c_1 acked=1 are written by a STOREREG on the unpack thread (the trace's writer is TENSIX, not a RISC-V), and c_16 received=1 by one on the pack thread. The LLK makes these counter updates wait behind STALLWAIT for the unpacker or packer (llk_io_unpack.h:99-102, llk_io_pack.h:58-70), so no other CPU can see "consumed" or "ready" early.
  • 4523, NCRISC sees c_16 received=1 in the same clock. 4547, the NoC write. 4560, acked=1 after the write barrier: slot 0 of c_16 is free again for tile 2.
Source order and execution order differ. In the listing, line 48 (cb_reserve_back) comes after line 46 (tile_regs_wait), yet the trace shows TRISC2 at line 48 sixteen clocks before its SEMWAIT passes. Both lines run on TRISC2, but one is a RISC-V spin and the other is an instruction pushed into the coprocessor, which runs later. If you read a compute kernel as one sequential program, you will misread every trace like this.

Zoom 3: the registers

The register story starts before the data arrives. At clock 4328, MATH (thread T1) has passed tile_regs_acquire's SEMWAIT, with MATH_PACK at 0 of max 2 (A12). At 4331 it pushes one MOP. The trace's ingest line shows the nine config words that A13 found in the binary: outer 4, inner 2, end op SETRWC 0x37cc0003, loop op ELWADD 0x28000000. The expander emits 12 instructions at once (8 ELWADD, 4 SETRWC). They are the same clocks, 4328 and 4331, that A13's own trace showed, because the run is deterministic. Then the first ELWADD waits at the wait gate. It retried 255 times over 192 clocks, because SrcA and SrcB had no valid bank (A04). MATH was ready for tile 0 about 150 clocks before tile 0's bytes even reached the core's L1 (4482).

At 4523 TRISC0 pushes the unpack MOP (outer 2, inner 2, alternating 0x420080c1/0x428080c1, which differ only in bit 23, the unpacker select). Everything else follows in the same clock:

Read it face by face, because that's how the hardware works:

  • Unpack. Each UNPACR moves one 16×16 face (256 datums, 512 B) from L1 into a Src bank and sets that bank valid. Face 0 of A comes from 0x19e60, face 1 from 0x1a060, and so on, 0x200 apart. This is the face layout from A05 seen directly in L1. Format 5 is Float16_b.
  • Banks alternate per face. The SrcA banks used are 0, 1, 0, 1 across the four faces, and the same for SrcB. A06 said a bank can hold a whole tile. The eltwise LLK uses it one face at a time: after two ELWADDs, the MOP's end op SETRWC(CLR_AB) clears both valid bits and flips the matrix unit to the other bank, while the unpacker is already filling it (A13).
  • Math. Each ELWADD adds 8 rows of 16. Dst rows advance 0, 8, 16, … 56 through the RWC counter, so the instruction word is the same constant every time (A13). The first datum in this run is A = 0x3eb5 (0.354), B = 0xbf80 (−1.0), and Dst row 0 holds 0xbf26 (−0.648). Tile 0 occupies Dst rows 0-63, in the first half. Tile 1 goes to row 512 (the SETC16 … 0x200 in the trace), as A12's double-buffered Dst predicts.
  • Hand-off. SEMPOST takes MATH_PACK from 0 to 1. PACK's SEMWAIT (queued 17 clocks earlier) passes in the same issue round.
  • Pack. A PACR with Flush=1 (zero datums, fresh output addresses; PACR.md:40) comes first. Then the pack MOP's single PACR sends all four packers at once (PackerMask 15). Packer k reads Dst rows 16k…16k+15 and writes 256 datums to 0x1be60 + 0x200·k. Packer 0's first datum, 0xbf26, is the same value ELWADD wrote. Then ZEROACC clears the half and SEMGET takes MATH_PACK back to 0.

Count the copies: host → DRAM → L1 → Src → Dst → L1 → DRAM → host. That's seven hops. Three of them are commands your data-movement kernels issue, three are Tensix instructions your compute kernel never names (UNPACR, ELWADD and PACR all come from MOPs), and one is the host driver. In between sit four synchronization points: two CB publishes, one semaphore post and one more CB publish. Each is a single counter changing value.

What the clock numbers mean, and what they don't

Look at the strip under the big figure again. Thirty-two of the 48 events share one clock value, 4523, and that's no coincidence. ttsim's main loop has a deliberate shortcut: "for simulator perf, we clock a tile repeatedly as long as it successfully executes at least one Tensix instruction" (libttsim.cpp:252). During one tick of g_clock, core 0 went round that inner loop from round 4375 to round 4404. That was 30 rounds, with 50 Tensix instructions executed and 144 trace lines. All of the unpacking, all eight ELWADDs, the semaphore hand-off and the packing landed in a single "clock". The B04 patch's round counter is what lets the figure keep them in order.

So, three rules for reading any ttsim trace, this one included:

  1. Clocks are not silicon timing. ttsim is a functional, bit-exact model with no timing model (A09, research/06-feasibility.md). The host drives the clock, the NoC takes zero clocks (A08), and Tensix work is squeezed by the shortcut above. On silicon an ELWADD takes cycles, and a 2 KiB NoC read takes hundreds of nanoseconds. The 192-clock ELWADD stall here says that MATH was early, not how early it would be on hardware.
  2. Order along a dependency is meaningful. Read → publish → wait satisfied → unpack → add → post → pack → publish → write → free. Each step causes the next through a counter, a valid bit or a semaphore, so no correct simulator, and no correct chip, can reorder them.
  3. Order between independent actors is not. I reran with the DPRINT overlay above (which polls the device and so adds host reads). The final clock rose from 7959 to 11479, and tile 0's add moved from clock 4523 to 6707. The 47 data-path and handshake events came out in exactly the same order. One event moved: TRISC2's cb_reserve_back(c_16), which nothing on tile 0's path waits for, appeared earlier in the sequence, before the reader's reserve_back instead of after c_0's push. DPRINT runs are not even repeatable: the host's polling depends on wall time, and a second DPRINT run ended at 11507 with the add at 6744. In that run PACK's SEMGET also swapped places with NCRISC's wait_front, two more actors that do not wait on each other. The dependency chain kept its order both times.
"Tile 0 was in Dst for zero clocks" is true of this ttsim run and false of any real chip. Never use ttsim clock gaps to argue about overlap or speed. Use them to argue about order, and only along a chain of synchronization. For timing on silicon, see the profiler in A20.

Recap

  • Chip. The host writes tile 0 of A and B into DRAM bank 0, tile D(0,11), at 0x2d4c40 and 0x2d7c40. BRISC reads them over NoC 0 into core T(1,1) (logical (0,0)). NCRISC writes the sum over NoC 1 to D(0,11):0x2dac40, and the host reads it back. On each NoC the data takes the 3-hop leg.
  • Core. The data sits in slot 0 of c_0 (0x19e60), c_1 (0x1ae60) and c_16 (0x1be60). Ownership changes hands through counter values: BRISC received=1, then TRISC0 sees it, Tensix STOREREGs set acked=1 and c_16 received=1, then NCRISC sees it and later sets acked=1.
  • Registers. Two MOPs (unpack and math) and one pack MOP become 8 UNPACR, 8 ELWADD, 4 SETRWC and 1 PACR. Src banks alternate per face. Dst rows 0-63 hold the sum. MATH_PACK goes 0 → 1 → 0. Four packers write the four faces 0x200 apart.
  • Every hop is a copy. Synchronization only decides which copy is live.
  • Clocks. ttsim clocks give order, not time. Thirty-two of the 48 events share clock 4523 because ttsim runs a busy core for many rounds per clock. Order along a dependency chain survives instrumentation changes. Order between independent actors does not.

Check yourself

The trace shows the first ELWADD of tile 0 "executed at 4523 after 255 tries over 192 clocks". Which clock was it pushed at, and what was it waiting for?

It reached the wait gate at clock 4331, when MATH's MOP expanded into 8 ELWADDs and 4 SETRWCs (4523 − 192 = 4331). The trace has a D … T1 01800000 12 line at 4331. MATH never waits on a CB (A12), so it got there early. The ELWADD waited for SrcA and SrcB to have a valid bank (tensix_elw_op returns false until both are valid, which the wait gate retries). Only TRISC0's UNPACRs at 4523 set those bits.

Why does the trace attribute c_0's acked=1 to "TENSIX" rather than to TRISC0, even though cb_pop_front is TRISC0 code?

On the unpack core, cb_pop_front doesn't store to the stream register itself. It pushes SETDMAREG, STALLWAIT(…UNPACK) and STOREREG into the coprocessor (llk_io_unpack.h:99-102). The store happens when the STOREREG executes, after the unpacker has finished reading the slot, and ttsim performs it with no RISC-V id (tensix.cpp STOREREG calls tile_mmio_wr32 with 0xFFFFFFFF). That ordering is the guarantee: the reader can't reuse 0x19e60 while UNPACR might still be reading it.

Page 0 of A, B and the output all live in DRAM bank 0 at 0x2d4c40, 0x2d7c40 and 0x2dac40. Why 0x3000 apart, and where would page 1 of A be?

Each buffer is 64 pages of 2048 B, interleaved round-robin over 12 banks. 64/12 rounds up to 6 pages per bank, and 6 × 2048 = 12 KiB = 0x3000 of every bank, so consecutive buffers start 0x3000 apart in each bank. Page 1 goes to bank 1, which the trace shows as D(0,1):0x402d4c40: the same in-bank offset plus the 1 GiB address_offset that odd-numbered banks have on Wormhole (A09).

The reader's two NoC reads and its received=1 store are 13-17 clocks apart. On silicon, roughly how would that gap compare, and why can't ttsim tell you?

On silicon the gap would be at least the NoC round trip plus DRAM latency for 2 KiB: a request travelling 19 hops and a 65-flit response on 3 hops, plus DRAM access. That's hundreds of cycles or more, and it varies with traffic. ttsim completes the copy inside the store that issues the command (tile.cpp:1620), so the gap it shows is just the RISC-V instructions between the two stores. It has no routing, no link contention and no DRAM model. The order (read, then barrier, then push) is meaningful. The gap is not.

If you changed tiles_per_cb from 2 to 1 for c_16, which events in tile 0's journey would change, and which of tile 1's?

Tile 0's path would be the same: c_16 starts empty, so PACK's cb_reserve_back passes at once and the addresses don't change (c_16 would still start at 0x1be60, at half the size). Tile 1 is different. With one page, PACK's cb_reserve_back for tile 1 must wait until NCRISC sets c_16 acked=1 (clock 4560 for tile 0), so tile 1's pack can't overlap tile 0's NoC write. It would also pack into 0x1be60 instead of 0x1c660. This is A11's one-page versus two-page pipeline (A11), and ttsim would only show it as a change in event order, not as lost time.

In this ttsim run, at the end of any clock, is tile 0 ever "in Dst"? What does that tell you about using the simulator?

No. All of its Dst activity (8 ELWADDs, PACR, ZEROACC) happens inside clock 4523. At the end of 4523 the live copy is already c_16 in L1. Use ttsim to check where data goes and in what order the handshakes fire. Don't use it to check how long data stays anywhere.
