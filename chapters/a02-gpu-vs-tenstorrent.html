02. Two philosophies: GPU vs Tenstorrent

GPUs hide memory latency with thousands of threads and hardware caches. Tenstorrent instead tells every core exactly what to fetch and when. This chapter covers what each bet buys, what it costs, and why the two are slowly meeting in the middle.

The question

Imagine you are a cook in a busy kitchen. You can work in one of two ways.

In the first, you reach for an ingredient whenever you need it. If it is on the counter, good. If not, someone runs to the storeroom while you wait. To make the counter useful, a helper watches what you reach for and keeps the most recently used things nearby, guessing that you will want them again. That helper is a cache.

In the second, you have the recipe in advance. Before you start, a runner fetches exactly the ingredients for the next step and puts them on your counter, while you are still busy with the current step. Nobody guesses. The counter holds what the recipe says it should, and nothing else. That counter is a scratchpad, and the runner is a DMA engine.

Neural-network math is unusual among programs because we almost always have the recipe. A matrix multiply touches its inputs in an order that is fixed before the first multiply happens. That leads to this chapter's question:

If you knew exactly which data each core needs next, would you still want a cache?

Before answering, watch what a cache does with a pattern it cannot predict well. The figure below plays one simple, very common pattern: a loop that touches the same n tiles over and over, with only 4 slots of fast memory. The top row is a cache with least-recently-used (LRU) replacement, the textbook policy. The bottom row is a program that knows the loop and decides in advance what to keep.

So the answer to the opening question is mostly no, with two qualifications. First, a cache is a fine thing to have when you don't know the pattern, and much code is like that. Second, knowing the pattern is not enough: someone also has to issue the fetches early enough that the math never waits. The rest of this chapter is about how GPUs and Tenstorrent each deal with that second problem.

The GPU bet: many threads, hardware caches

A GPU began as a machine for shading millions of pixels, each computed by the same small program. NVIDIA's programming model still reflects that. You launch a kernel with a huge number of threads, often millions. Threads are grouped into thread blocks, and each block runs on one streaming multiprocessor (SM). Inside the SM, threads are grouped in 32s called warps. All 32 threads of a warp execute the same instruction at the same time on different data. NVIDIA calls this SIMT, single instruction multiple threads. If threads in a warp take different branches, the inactive ones are masked off while the others run, so divergent code wastes lanes (CUDA Programming Guide §1.2.2.2).

Hiding latency by having something else to do

The defining trick is how a GPU copes with slow memory. Suppose a warp issues a load from DRAM and must wait many cycles for the answer. A CPU would try to predict, prefetch and reorder around the wait. A GPU instead keeps many warps resident on each SM at once, each with its own registers already allocated, and when one warp stalls the scheduler simply issues an instruction from another warp that is ready. Switching costs nothing because nothing has to be saved: every resident warp's registers live in the SM's large register file all the time. A microbenchmarking study of the Graphcore IPU sums up the GPU approach as hiding latency through "oversubscription of threads to cores and the ability to inexpensively switch among threads" (Jia et al., 2019, §1.2).

The numbers for an H100 SXM5 show how seriously NVIDIA takes this (Hopper architecture blog, compute-capability table):

  • 132 SMs, each with 4 fourth-generation Tensor Cores (528 in total) and 128 FP32 lanes.
  • Up to 64 warps (2,048 threads) resident per SM.
  • 65,536 32-bit registers per SM: a 256 KB register file per SM, about 33 MB across the chip. That is as big as the L1 storage, because it is what makes free warp switching possible.

The memory hierarchy

Below the registers, the H100 SXM5 has (same sources):

  • 256 KB per SM of combined L1 data cache and shared memory. The split is configurable, with up to 228 KB usable as shared memory.
  • 50 MB of L2 cache shared by all SMs.
  • 80 GB of HBM3. NVIDIA's product page gives 3.35 TB/s. The earlier architecture blog says "over 3 TB/s" and lists 3,000 GB/s as not yet final.

Two of these deserve a closer look:

  • The L1 and L2 caches are what the cook's helper was: hardware that keeps recently used lines nearby without the program asking. They make ordinary code fast with no effort from the programmer.
  • Shared memory is the opposite: a programmer-managed scratchpad that threads in a block explicitly fill and read. Every fast GPU matrix multiply (cuBLAS, CUTLASS and hand-written kernels) loads tiles of A and B from global memory into shared memory, synchronizes, computes from shared memory, and repeats. So GPUs already have the scratchpad idea. It sits beside the caches rather than replacing them.
Keep this in mind for the rest of the chapter: a well-tuned GPU GEMM is already a software-managed, explicitly staged program. The difference with Tenstorrent is not that one side can plan and the other cannot. It is about what the hardware is built around. A GPU spends silicon on caches, a huge register file and warp schedulers so that unplanned code also runs well. Tenstorrent spends almost nothing on caches (only tiny per-core instruction caches) and asks every program to plan.

The GPU's peak dense BF16 Tensor Core throughput on an H100 SXM is about 989 TFLOPS. NVIDIA's product page lists 1,979 TFLOPS "with sparsity", and the dense figure is half that; the earlier architecture blog gave a preliminary 1,000. Its board power is up to 700 W. As chapter A01 showed, 989 TFLOPS over 3.35 TB/s gives a ridge point of roughly 295 FLOP per byte. Any kernel below that intensity is waiting for HBM, however many warps it has.

A second lineage: systolic arrays and the TPU

In 1982, H. T. Kung asked how a special-purpose chip could compute faster than its memory could feed it. His answer was the systolic array: a grid of simple cells through which data "pulses" rhythmically, "much as blood circulates to and from the heart". The point is reuse: "once a data item is brought out from the memory it can be used effectively at each cell it passes while being 'pumped' from cell to cell" (Kung, Why Systolic Architectures?, IEEE Computer 1982). Kung's paper even names matrix multiplication as the archetypal compute-bound problem, since "every entry in a matrix is multiplied by all entries in some row or column".

Think of a bucket brigade instead of a crowd running back and forth to the well. Each bucket is fetched once and then passed hand to hand, and every hand uses it.

Google's first TPU (Jouppi et al., ISCA 2017) put that idea into a datacenter chip:

  • A 256 × 256 systolic matrix unit: 65,536 8-bit multiply-accumulators, 92 TOPS peak.
  • A 28 MiB software-managed on-chip memory, with no cache.

The paper's abstract makes an argument this chapter will keep returning to:

The TPU's deterministic execution model is a better match to the 99th-percentile response-time requirement of our NN applications than are the time-varying optimizations of CPUs and GPUs (caches, out-of-order execution, multithreading, multiprocessing, prefetching, …) that help average throughput more than guaranteed latency.

The paper reports the TPU as about 15–30× faster than a contemporary K80 GPU or Haswell CPU on Google's inference workloads, with 30–80× better TOPS per watt. Those comparisons are against 2015-era parts, so read them as evidence for the idea rather than as a ranking against today's GPUs.

The analogy breaks here: a Tenstorrent core is not a systolic array. Its matrix engine computes on small register files (SrcA, SrcB, Dst; chapter A06), not on a large pulsing grid of cells. What Tenstorrent inherits from this lineage is the memory philosophy (software-managed SRAM, no caches, predictable timing), not the systolic datapath.

Spatial and dataflow chips, briefly

A third family spreads both memory and compute across the die and moves data between many small units. They differ in who decides when data moves:

  • Graphcore IPU (GC2). 1,216 tiles, each one core plus 256 KiB of local SRAM, 304 MiB in total. "Except for the register file, the IPU offers no memory other than the distributed memories local to each tile." The memories are scratchpads, not caches. Execution follows the bulk synchronous parallel model: every tile computes on local data, then all tiles exchange data, then all synchronize (Jia et al., Dissecting the Graphcore IPU, 2019).
  • Groq TSP. Taken furthest towards determinism. Groq's Hot Chips 34 talk lists "no 'reactive components' like arbiters, crossbars, replay mechanisms, caches", 220 MB of on-chip SRAM, and a compiler that does "cycle-accurate instruction scheduling", so it "knows the exact location of every tensor on-chip" at every cycle. Peak is about 750 INT8 TOPS at 900 MHz.
  • Cerebras WSE (first generation). Taken furthest in size: a whole wafer with 400,000 cores, 18 GB of on-chip memory "fully distributed along with compute datapaths", and "dataflow scheduling in hardware" that is "triggered by data" and filters out zeros (Cerebras, Hot Chips 31).

All three agree with the TPU on one thing: large SRAM, no cache, with software deciding where data lives. Tenstorrent belongs to this family, but with its own mix of choices.

Tenstorrent's choices

A Tenstorrent chip is a 2D grid of tiles connected by a network-on-chip. Most tiles are Tensix cores; others hold DRAM controllers, Ethernet, PCIe and management. The Wormhole ASIC has 80 Tensix tiles (products expose 64, 72 or 80). Blackhole has 140 on the die (tt-isa-documentation WormholeB0/README.md:4, BlackholeA0/README.md:4). Chapter A03 explains why sold products enable fewer. Here are the design choices, each with the evidence for it.

1. A grid of independent cores, not a pool of threads

Each Tensix runs its own programs. There is no warp scheduler and no hardware multithreading. The tt-metal guide's section for GPU experts says it plainly: each baby RISC-V core "implements single-threaded execution without hardware multithreading capabilities", and the design "omits SIMT … as well as traditional latency-hiding mechanisms" (METALIUM_GUIDE.md:239-248). The usual programming style is still SPMD (the same kernel on many cores with different arguments), but the cores are not in lockstep (METALIUM_GUIDE.md:64).

2. About 1.5 MB of software-managed SRAM per core

Each Tensix has 1464 KiB (Wormhole) or 1536 KiB (Blackhole) of SRAM called "L1". The ISA documentation warns that the name "is somewhat of a misnomer, as it is suggestive of a hardware-managed cache, which is not the case — this is plain RAM" (WormholeB0/TensixTile/L1.md:3). On a Blackhole card with 120 enabled cores, that adds up to the 180 MB quoted on docs.tenstorrent.com. Compare that with an H100's 50 MB of L2 plus 132 × 256 KB of L1/shared memory. Tenstorrent has more SRAM but no data cache in front of it.

3. Explicit data movement over two NoCs

A Tensix cannot load from DRAM. There is no load instruction that reaches it. Instead its cores ask a NoC interface to copy bytes between its own L1 and some other tile's memory (DRAM or another Tensix). Each chip has two NoCs. Each is a 2D torus, and they run in opposite directions (WormholeB0/NoC/README.md:5-9). The guide describes the absence of caches as deliberate: SRAM "functions as addressable memory rather than transparent cache. Data movement requires explicit operations … This explicit model eliminates cache coherency protocols and provides predictable memory access latency, but places responsibility on developers" (METALIUM_GUIDE.md:233-237). Chapter A08 covers why there are two networks.

4. Small RISC-V cores for control, separate engines for math

Each Tensix contains five "baby" RV32IM cores, two NoC connections, unpackers, a matrix unit (FPU), a vector unit (SFPU) and packers (WormholeB0/TensixTile/README.md:4-14). The RISC-V cores do not do the heavy math. In the ISA documentation's words, they "are not intended to achieve high performance on their own; they are intended to oversee the other components that actually drive performance". The suggested split is two cores overseeing the NoC and three overseeing the math coprocessor (WormholeB0/TensixTile/README.md:16). In practice this becomes three kernels per core: a reader, a compute kernel and a writer, linked by circular buffers in L1 (METALIUM_GUIDE.md:71-86). Chapter A04 opens this box. Blackhole adds 16 SiFive x280 "big" RISC-V cores, which can run Linux, in four L2CPU tiles (BlackholeA0/README.md:6).

5. Ethernet on the die for scale-out

Instead of NVLink-style links plus a switch, each chip has Ethernet tiles, so chips connect directly to each other:

  • Wormhole: 16 Ethernet tiles at 100 GbE each (WormholeB0/README.md:6).
  • Blackhole: 14 tiles at 400 GbE, paired into 800 GbE QSFP-DD ports; a p150 wires up four ports (BlackholeA0/README.md:7).

The chips "have sufficient NoC bandwidth and processing capability to function as network switches themselves" (METALIUM_GUIDE.md:260). Chapter A21 covers meshes and TT-Fabric.

6. Open source

The TT-Metalium SDK and the ttsim simulator are both Apache-2.0 (the LICENSE files in both repositories at the pinned commits), and the ISA is documented publicly in tt-isa-documentation. That openness is why this series can show you real kernel code, the instructions it compiles to, and a simulator that runs them. NVIDIA's CUDA toolkit and GPU ISA are proprietary, although many NVIDIA libraries, CUTLASS among them, are open source.

7. The original thesis: conditional execution

Tenstorrent's founding pitch was not "a cheaper GPU". It was dynamic computation. The 2021 IEEE Micro paper Compute Substrate for Software 2.0 (Vasiljevic, Bajic et al.) describes four approaches: block sparsity of activations, per-packet dynamic precision, conditional computation such as mixture-of-experts executed on the device rather than the host, and runtime control flow. It reports that "75% sparsity in activations (induced dynamically at runtime) results in 4x speedup on BERT layers" on Grayskull, and calls a full-model figure "work in progress", with a projected score.

Treat this as design intent, not an established result. These are vendor measurements and projections on the first-generation chip, and I found no independent reproduction. Today's TT-Metalium programming model, which the rest of this series teaches, is mostly dense SPMD: reader/compute/writer kernels on 32×32 tiles. Independent cores with their own control flow make conditional execution possible; this series does not claim it is a measured advantage.

Here is what explicit data movement looks like in real code. This is the reader kernel of tt-metal's single-core matmul example. It runs on one of the data-movement RISC-V cores and fetches tiles of A and B, in exactly the order the compute kernel will consume them:

tt-metal/tt_metal/programming_examples/matmul/matmul_single_core/kernels/dataflow/reader_single_core_mm.cpp:30-53 @7aad8aac
for (uint32_t mt = 0; mt < Mt; mt++) {
    uint32_t itileB = 0;
    for (uint32_t nt = 0; nt < Nt; nt++) {
        for (uint32_t kt = 0; kt < Kt; kt++) {
            {                                          // Read A's tile at (mt, kt)
                uint32_t a_tile_index = mt * Kt + kt;  // A is MK, so we stride by Kt
                cb_reserve_back(cb_id_in0, 1);
                uint32_t l1_write_addr_in0 = get_write_ptr(cb_id_in0);
                noc_async_read_page(a_tile_index, s0, l1_write_addr_in0);
                noc_async_read_barrier();
                cb_push_back(cb_id_in0, 1);
            }

            {                                          // Read B's tile at (kt, nt)
                uint32_t b_tile_index = kt * Nt + nt;  // B is KN, so we stride by Nt
                cb_reserve_back(cb_id_in1, 1);
                uint32_t l1_write_addr_in1 = get_write_ptr(cb_id_in1);
                noc_async_read_page(b_tile_index, s1, l1_write_addr_in1);
                noc_async_read_barrier();
                cb_push_back(cb_id_in1, 1);
            }
        }  // Kt loop
    }  // Nt loop
}  // Mt loop

Read it as the runner in the kitchen:

  • a_tile_index = mt * Kt + kt: the kernel computes which 32×32 tile it needs next. Nothing is inferred from past accesses.
  • cb_reserve_back: wait until there is a free slot in circular buffer 0, a queue in this core's L1.
  • noc_async_read_page(..., l1_write_addr_in0): ask the NoC to copy that tile from DRAM into that slot. This line is the DRAM trip, written out in the program.
  • noc_async_read_barrier: wait until the copy has landed.
  • cb_push_back: tell the compute kernel, running on other RISC-V cores, that the tile is ready.

This simplest example re-reads tiles of A for every output column instead of keeping them. The blocked and multicast versions in chapters A15–A16 fix that. Because every DRAM trip is a line of code, you can count them by reading the loops, which is exactly what the next figure does.

The same matmul on both machines

Take a small blocked matrix multiply measured in tiles: C (2×3 tiles) = A (2×4) × B (4×3). Each output tile C[i][j] is the sum over k of A[i][k] · B[k][j]. Both machines run the same loop order as the reader kernel above (i, then j, then k), so they make the same 48 tile accesses in the same order. Both get the same amount of fast memory. The only difference is who decides what that memory holds.

  • Left: a cache machine. LRU replacement. A miss is a DRAM trip, and compute stalls while it is fetched.
  • Right: a scratchpad machine. The program keeps the current row of A (4 slots), streams B through 2 slots, and a reader fetches each tile one step before compute needs it.

Use the buttons to change the fast-memory size.

Run it at 6 slots, then at 8. The two results together are the honest version of the "cache vs scratchpad" story:

  1. When capacity is tight, the policy matters. At 6 slots LRU makes 48 DRAM trips where the plan makes 32. The cache keeps evicting the A tile it is about to reuse, just as in the first figure.
  2. When capacity is ample, a cache is just as frugal. At 8 slots both make 32 trips. Caches are good, and a GPU programmer who sizes blocks well gets this behaviour, or stages the tiles in shared memory and gets the scratchpad behaviour directly.
  3. The difference that remains is timing. The cache learns about each miss when it happens. The scratchpad program issued each load before it was needed. Somebody must cover that latency. A GPU covers it with other warps. A Tensix covers it with a dedicated data-movement core running ahead, which the next section shows.
The "stall ticks" in the figure are illustrative: 3 ticks per miss and one compute access per tick. They model neither a GPU nor a Tensix. The DRAM-trip counts, however, are exact for the loop and capacities shown; the page computes them by simulating LRU and the plan.

Two ways to hide latency

Every machine that talks to DRAM must do something useful while it waits. The figure below compares the two strategies on toy numbers.

  • Top: a GPU SM with one math unit and a variable number of warps. Each warp loads a tile (6 cycles of waiting) and then computes on it (2 cycles of math). The scheduler gives the math unit to any warp whose data has arrived.
  • Bottom: a Tensix with three single-threaded roles. A reader takes 4 cycles to bring a tile in over the NoC, compute takes 3 cycles, and a writer takes 2 cycles to send the result out. They are connected by circular buffers whose depth (slots per buffer) you can see change.

Each strategy has a price.

  • The GPU's is silicon and power spent on state: a 256 KB register file per SM, so dozens of warps can sit ready, plus schedulers and caches. In return, a programmer can write plain per-thread code and still get decent overlap.
  • The Tensix's is programmer effort. Someone has to write the reader, size the buffers and order the fetches. In return, the hardware is simpler, and the program states what moves and when it is requested. What sits in L1 never depends on how a cache happens to behave on a given run, although NoC contention can still vary the exact timing (question 4 below).
GPUs also use software pipelining: double-buffered shared memory and asynchronous copies (cp.async on Ampere, TMA on Hopper) are standard in fast kernels. So the comparison is not "the GPU can't pipeline". It is "the GPU also has oversubscription to fall back on, and Tenstorrent has only the pipeline".

The unit of work: a 32×32 tile

On a GPU the natural unit is the thread and its element. Tensor Cores work on small matrix fragments, but you reach them through warps. On Tenstorrent, the unit that moves, queues and computes is a tile of 32×32 elements (TILE_HEIGHT = 32, TILE_WIDTH = 32 in tt_metal/api/tt-metalium/constants.hpp:19-20). A tile is made of four faces of 16×16, "because the matrix engine natively multiplies 16x16 matrices" (tech_reports/tensor_layouts/tensor_layouts.md:60-62).

One picture to carry forward. Chapter A05 covers faces, padding and the block-float formats in which 16 values share one exponent; chapter A06 covers how the FPU multiplies faces.

The tile matters for this chapter's argument because it makes the access pattern coarse and regular. A GPU kernel computes addresses per thread, and the hardware has to coalesce them into memory transactions and catch reuse in caches. A Tenstorrent kernel deals in whole tiles. In the reader above, one noc_async_read_page moves one 2 KB bf16 tile, because the example's buffers use one tile per page. When the unit is that large and that predictable, "fetch exactly the next tiles" is a short loop rather than a heroic optimization.

"Tile" means three different things in this series: a 32×32 data tile (this section), a Tensix tile (a grid position on the chip, as in "Ethernet tile"), and a node in ttsim's NoC model. When the context is unclear, the text will say which one it means.

Convergence: Hopper's TMA and warp specialization

The two philosophies are moving towards each other, and the clearest evidence comes from NVIDIA itself.

The Tensor Memory Accelerator (TMA). Hopper added a hardware unit that "can transfer large blocks of data and multidimensional tensors from global memory to shared memory and back again". Its programming model is single-threaded: "a single thread in a warp is elected to issue an asynchronous TMA operation", and other threads wait on a barrier for completion (Hopper architecture blog). That is a DMA engine moving a tile into a scratchpad, started by one thread and signalled through a barrier. It is close to noc_async_read plus a circular-buffer push.

Warp specialization. CUTLASS 3 kernels for Hopper split a thread block into two groups:

  • A producer warp group that "loads data from global memory into shared memory buffers using the new Tensor Memory Accelerator".
  • A consumer warp group that waits for "the buffer is filled and then launches tensor core MMA operations", then releases the buffer for the next load (CUTLASS Efficient GEMM docs).

FlashAttention-3 uses the same scheme. It even moves registers away from the producer warps, which only issue TMA, to the consumers that do the math (setmaxnreg; Shah et al., 2024). Put that next to a Tensix:

Even CUDA's programming guide now has a section on "tile programming", where the programmer "writes per-block code that operates on tiles" and leaves the mapping to threads to the compiler (CUDA Programming Guide §1.2.2.3).

Do not overread this. A Hopper SM still has caches, SIMT warps and a large register file. Warp specialization is a software pattern built on hardware that can also run code which never heard of it. Tenstorrent made that pattern the hardware's only mode. The fair summary is that the fastest GPU kernels found their way to the same producer/consumer, explicit-tile structure that Tenstorrent requires from the start.

Recap

  • A cache guesses; a scratchpad is told. When the access pattern is unknown, caches are excellent. When it is known, as in a matmul, software can choose what to keep and when to fetch it, and the guessing hardware buys little that the program could not decide itself. LRU can even do badly on cyclic patterns slightly larger than the cache.
  • GPUs hide latency by oversubscription. SIMT warps of 32 threads, up to 64 warps per H100 SM and a 256 KB register file make warp switching free. Caches (256 KB L1/shared per SM, 50 MB L2) serve unplanned code, and shared memory serves planned code.
  • Systolic arrays and the TPU showed that reusing each fetched value many times, plus deterministic software-managed memory, beats caches for NN inference. Groq, Graphcore and Cerebras also chose large SRAM with no cache.
  • Tenstorrent is a grid of independent Tensix cores, each with about 1.5 MB of plain SRAM. All movement is explicit over two opposite-direction NoCs, directed by small RISC-V cores, with Ethernet on the die and Apache-2.0 software. Its original conditional-execution thesis is design intent, not a measured advantage.
  • The unit of work is a 32×32 tile of four 16×16 faces. It is what is fetched, queued and computed.
  • Latency hiding on a Tensix comes from pipelining: reader, compute and writer run ahead of each other through circular buffers, and throughput is set by the slowest stage.
  • Hopper's TMA and warp specialization show the best GPU kernels converging on the same producer/consumer, explicit-tile structure that Tenstorrent requires from the start.

Check yourself

1. In the matmul figure with 8 slots, the cache and the scratchpad both make 32 DRAM trips. Has the scratchpad lost its advantage?

Not entirely. Traffic is equal, because 8 slots hold the A row plus one B column and LRU then keeps the A row. But the cache discovers every one of its 32 misses only when compute asks for the data, so a single thread stalls on each. The scratchpad program issued each load before it was needed, so its compute did not stall after the first fill. A GPU recovers that timing advantage with other warps (oversubscription) or with explicit async copies into shared memory. Note also that the scratchpad's count is the same at 6 slots, while the cache's jumps to 48: the plan's behaviour does not depend on how the replacement policy reacts to capacity.

2. Why does an H100 SM need a 256 KB register file when each thread uses at most 255 registers?

Because latency hiding by warp switching only works if switching is free, and that means every resident warp's registers must already be in the register file. Up to 64 warps × 32 threads = 2,048 threads per SM can be resident, sharing 65,536 registers. The register file is the price of oversubscription. A Tensix pays nothing like it because each baby core runs a single thread and covers latency by pipelining through L1 buffers.

3. In the latency figure, the reader takes 4 cycles, compute 3 and the writer 2. What throughput would circular buffers of depth 8 give, and why?

Still one tile every 4 cycles. Once there are enough slots for the stages to overlap (depth 2 already allows that here), throughput is set by the slowest stage, the reader. Deeper buffers absorb jitter, but they cannot make the reader faster. To go faster you must speed up the bottleneck, for example by issuing several NoC reads before one barrier, splitting reads across both NoCs or cores, or reducing traffic through reuse and multicast. Chapters A11, A15 and A16 cover these.

4. Graphcore, Groq and Tenstorrent all have large SRAM and no cache. How does Tenstorrent differ from Groq in who decides timing?

Groq's compiler schedules the whole chip cycle by cycle. Functional units run in lockstep and the hardware deliberately has no arbiters, so timing is fully static. Tenstorrent's cores each run their own programs asynchronously and synchronize at run time through circular buffers and semaphores. NoC transfers can still contend with one another. Tenstorrent's data placement is explicit, but its timing is decided dynamically by handshakes, not by a global static schedule.

5. "H100 does 989 TFLOPS and a p150 does 664, so the H100 is 1.5× faster." What is wrong with this sentence?

The figures use different formats: BF16 dense on the H100, Tenstorrent's one-phase "BLOCKFP8" rate on the p150. At the same nominal format the H100 lists 1,979 dense FP8 TFLOPS, while the p150's full-precision BF16 rate is about a quarter of its one-phase peak. Peak numbers also ignore memory: the p150's ridge point is about 1,300 FLOP/B against about 295 for the H100, so far more of its workloads are bandwidth-bound unless data is reused from SRAM. Power, price and die size differ too. Peak-versus-peak comparisons answer almost no practical question.

6. Do Hopper's TMA and warp specialization turn an H100 into a Tenstorrent chip?

No. They let a GPU kernel adopt the explicit producer/consumer, tile-into-scratchpad pattern, and the fastest Hopper GEMM and attention kernels do. But the SM still has hardware caches, SIMT warps, a large register file and a scheduler, so code that ignores the pattern still runs reasonably. On a Tensix there is no fallback: without an explicit NoC read, data never reaches L1. The convergence is in how the best kernels are structured, not in what the hardware requires.

  • H. T. Kung, "Why Systolic Architectures?" (1982): the origin of systolic arrays, short and still very readable.
  • Jouppi et al., "In-Datacenter Performance Analysis of a Tensor Processing Unit" (ISCA 2017): TPU v1, its 28 MiB software-managed memory and the determinism argument.
  • NVIDIA Hopper Architecture In-Depth: H100 SMs, caches, registers, TMA and thread block clusters.
  • CUDA Programming Guide: Programming Model: warps, SIMT, shared memory vs caches, and the newer tile programming model.
  • CUTLASS: Efficient GEMM in CUDA: how the fastest GPU GEMMs tile, pipeline and warp-specialize.
  • Shah et al., "FlashAttention-3" (2024): producer/consumer warp specialization with TMA on Hopper.
  • Jia et al., "Dissecting the Graphcore IPU Architecture via Microbenchmarking" (2019): a scratchpad-only, bulk-synchronous many-core chip, measured.
  • Groq at Hot Chips 34 (Abts): "design for determinism" taken to its limit.
  • Vasiljevic, Bajic et al., "Compute Substrate for Software 2.0" (IEEE Micro 2021): Tenstorrent's own statement of its thesis, including dynamic and conditional execution.
  • TT-Metalium Guide: the official architecture overview, including the sections "Where is the cache hierarchy" and "Tenstorrent hardware for GPU experts".
