The question

Here is a complete compute kernel from tt-metal's examples. It adds two bf16 tiles. Read the comments on the right of each line:

tt-metal/tt_metal/programming_examples/add_2_integers_in_compute/kernels/compute/add_2_tiles.cpp:18-49 @7aad8aac (comments trimmed)
    // Metalium API Calls                              Involved Cores
    compute_kernel_hw_startup(cb_in0, cb_in1, cb_out0);  // Unpack, Math, Pack
    add_init(cb_in0, cb_in1);                  // Unpack, Math

    cb_wait_front(cb_in0, 1);  // Unpack
    cb_wait_front(cb_in1, 1);  // Unpack

    tile_regs_acquire();  // Math
    add_tiles(cb_in0, cb_in1, 0, 0, 0);  // Unpack, Math
    tile_regs_commit();  // Math

    tile_regs_wait();  // Pack
    pack_tile(0, cb_out0);  // Pack
    tile_regs_release();  // Pack

    cb_pop_front(cb_in0, 1);  // Unpack
    cb_pop_front(cb_in1, 1);  // Unpack

    cb_push_back(cb_out0, 1);  // Pack

Every line names one, two or three "cores". In A04 you met them: TRISC0, TRISC1 and TRISC2, three baby RISC-V CPUs that each push instructions into one thread of the Tensix coprocessor. TRISC0 drives the unpackers, TRISC1 the matrix and vector engines, TRISC2 the packers. They have separate program counters, separate instruction caches and separate 2 KiB data RAMs. There is no OS on them and no thread library.

Yet there is one kernel_main(). So:

How can one source file run on three CPUs at once, with some lines on one CPU, some on two, and some on all three?

And once it does, how do three CPUs that share no variables agree that the result in Dst is finished and safe to pack? That's this chapter. We'll answer the first question with the C preprocessor, the second with one 4-bit semaphore, and then use the simulator to look at the generated files, print from each TRISC, and break the agreement on purpose.

Three copies of one file

Before thinking about macros, look at what the JIT compiler actually builds. When the host calls CreateKernel(program, "…/add_2_tiles.cpp", core, ComputeConfig{…}), tt-metal doesn't compile that file directly. It first writes small wrapper files, one per TRISC, into the kernel's directory in the JIT cache:

That's the whole trick: three four-line files that differ in their first line, each including the same source. Each one is compiled into its own ELF, in trisc0/, trisc1/ and trisc2/. (A small quirk: when TT_METAL_CACHE is set, the build key is glued onto the tt-metal-cache directory name without a slash. The default is ~/.cache/tt-metal-cache/<key>/.)

Note the two lines before kernel_main(). Before your code runs, the MATH copy clears Dst and the UNPACK copy clears the Src registers. Keep that in mind for the matmul section: Dst starts at zero.

So the build is three compilations of the same translation unit with different defines. The design is close to the oldest trick in embedded C: one source, conditional compilation, several binaries. What makes it powerful here is the API built on top of it.

The macros that grey out lines

In the math build, MATH(x) becomes x and UNPACK(x) and PACK(x) become nothing. The other two builds work the same way. Now every compute API function is written as a list of per-thread pieces. add_tiles is two lines:

tt-metal/tt_metal/hw/inc/api/compute/eltwise_binary.h:265-275 @7aad8aac
template <bool is_fp32_dest_acc_en = DST_ACCUM_MODE>
ALWI void add_tiles(
    std::uint32_t icb0, std::uint32_t icb1, std::uint32_t itile0, std::uint32_t itile1, std::uint32_t idst) {
    UNPACK((llk_unpack_AB(icb0, icb1, itile0, itile1)));
    MATH((llk_math_eltwise_binary<
          EltwiseBinaryType::ELWADD,
          BroadcastType::NONE,
          is_fp32_dest_acc_en,
          MathFidelity::LoFi,
          EltwiseBinaryReuseDestType::NONE>(icb0, icb1, idst, true /* clear_fp32_dst_acc */)));
}

On TRISC0 this function is "unpack tile itile0 of CB icb0 into SrcA and tile itile1 of icb1 into SrcB". On TRISC1 it is "run ELWADD into Dst tile idst". On TRISC2 it's an empty inline function, and the compiler deletes it. (The double parentheses let a template argument list with commas pass through the macro as a single argument.) ALWI is inline __attribute__((always_inline)) (common_globals.h:7), so no call remains either.

Now picture the source shown three times, once per TRISC, with each copy's dead lines greyed out. Then let the three programs run. That's the figure below. The kernel is the loop from the eltwise_binary example (tiles_add.cpp:27-57), with short names.

The phrase to keep from the figure is that control flow is replicated and work is not. Anything not inside an UNPACK, MATH or PACK wrapper runs on all three TRISCs. That includes your for loops, get_arg_val calls, local variables and if statements. Each TRISC computes them independently in its own registers and RAM. The API calls inside the loop then contribute different instructions on each core.

That leads to the first rule of compute kernels. All three copies must take the same path through the control flow. If TRISC1 loops 8 times and TRISC2 loops 7 times, the eighth commit has no matching wait. Nothing crashes, but someone waits forever. Runtime arguments and compile-time arguments are safe to branch on, because all three cores see the same values. A value only one thread can see is not safe. An example is something MATH reads out of Dst, or a CB value that only UNPACK has waited for.

The nearest GPU idea is warp specialization. In a Hopper GEMM, one kernel source has an if (warp_role == producer) … else … split: producer warps issue TMA loads and consumer warps run tensor-core MMAs, and they synchronize through barriers in shared memory. Tensix does the split at compile time instead, with the preprocessor, and the roles are fixed by hardware: TRISC0 can only usefully drive the unpackers, because its pushes go to thread 0. The analogy breaks in two places. A GPU's specialized warps run genuinely different code paths that you write. Here the three paths are mechanically derived from one, and their loop structure must match exactly. And a GPU barrier waits for threads, while the Dst semaphore below waits for coprocessor instructions, which may finish long after the RISC-V that pushed them has moved on.

The plain DPRINT appears three times, tagged TR0, TR1 and TR2. Each targeted print appears once, on its own core. Two cautions about reading this log:

  • Line order across cores isn't time order. Each RISC writes its own print buffer, and the host server drains the buffers in its own order. Order is meaningful only within one TR tag.
  • A TRISC's view of the semaphore is a snapshot of the coprocessor, not of the program. TRISC1 read MATH_PACK = 0 right after tile_regs_commit(). Commit had only pushed a STALLWAIT and a SEMPOST into the math thread's FIFO. Those may not have executed yet. They might also have executed, and the packer may already have taken the count back. The TRISC can't tell which. This is A04's "the RISC-V runs ahead", seen from a kernel.
Reproduce the per-TRISC prints, then add your own in B06 · Circular buffers and semaphores, which also traces SEMPOST/SEMGET as ttsim executes them.

Who owns the circular buffers

In A11, a CB had a consumer side (cb_wait_front, cb_pop_front) and a producer side (cb_reserve_back, cb_push_back). In a data-movement kernel all four run on one RISC. In a compute kernel they're split by role:

tt-metal/tt_metal/hw/inc/api/compute/cb_api.h:44, 76, 92-98, 130-136 @7aad8aac (trimmed)
ALWI void cb_wait_front(uint32_t cbid, uint32_t ntiles) { UNPACK((llk_wait_tiles(cbid, ntiles))); }

ALWI void cb_pop_front(uint32_t cbid, uint32_t ntiles) { UNPACK((llk_pop_tiles(cbid, ntiles))); }

ALWI void cb_reserve_back(uint32_t cbid, uint32_t ntiles) {
    PACK((llk_wait_for_free_tiles<false, false, false>(cbid, ntiles)));
}

ALWI void cb_push_back(uint32_t cbid, uint32_t ntiles) {
    PACK((llk_push_tiles<false, false>(cbid, ntiles)));
}

This makes sense once you ask who touches each side. Only the unpacker reads input CBs, so only TRISC0 needs to know when input is ready and when it's done with it. Only the packer writes output CBs, so only TRISC2 needs to know about free space and new tiles. TRISC1 never waits on a CB at all. It doesn't need to, because its ELWADD can't pass the wait gate until the unpacker has handed SrcA/SrcB to the matrix unit (A04).

The pop and push have a subtle detail worth reading. TRISC0 may run cb_pop_front while its UNPACR is still queued, so the "tiles acked" counter in L1 can't be updated with a plain RISC-V store. Instead, the TRISC pushes the update into its own Tensix thread, behind a stall:

tt-metal/tt_metal/hw/ckernels/wormhole_b0/metal/llk_io/llk_io_unpack.h:99-102 and llk_io_pack.h:60-70 @7aad8aac (trimmed)
    // pop (TRISC0)
    get_local_cb_interface(input).tiles_acked += num_tiles;
    TT_SETDMAREG(0, get_local_cb_interface(input).tiles_acked, 0, LO_16(4));
    TTI_STALLWAIT(p_stall::STALL_THCON, p_stall::UNPACK);
    TT_STOREREG(4, tiles_acked_addr_tensix);

    // push (TRISC2)
    get_local_cb_interface(output).tiles_received += num_tiles;
    ...
    TT_SETDMAREG(0, tiles_received_new, 0, LO_16(p_gpr_pack::NUM_MSGS_RECEIVED));
    TTI_STALLWAIT(p_stall::STALL_THCON, p_stall::PACK);  // wait for pack to finish
    TT_STOREREG(p_gpr_pack::NUM_MSGS_RECEIVED, tiles_received_addr_tensix);

The counter is written by a STOREREG that waits for the unpacker (or packer) to go idle. So the reader kernel on another RISC never sees "tile consumed" before the unpacker has actually read it, and the writer never sees "tile ready" before the packer has written it. You get this for free. It's also why calling pop or push early in source order is not a race.

Source order between different TRISCs doesn't matter. Source order within one TRISC does. The docs' recommended loop calls cb_wait_front before tile_regs_acquire. The eltwise_sfpu example does the opposite (eltwise_sfpu.cpp:23-31). Both are correct, because wait_front compiles only into TRISC0 and acquire only into TRISC1. They're never in the same program. What would break things is reordering two lines that land on the same TRISC, such as tile_regs_release before pack_tile, which are both on PACK.

The Dst handshake

Unpack-to-math needed no software. Math-to-pack does, because Dst has no hardware ownership (A04): the packer will happily read Dst halfway through an ELWADD. So the API gives four calls, two per side:

CallRuns onMeansBecomes (Wormhole LLK)
tile_regs_acquire()MATH"I want a section of Dst to write"SEMWAIT MATH_PACK, block while Value ≥ Max
tile_regs_commit()MATH"My section is finished"STALLWAIT (math and SFPU done), SEMPOST MATH_PACK; flip to the other half
tile_regs_wait()PACK"I want a finished section to read"SEMWAIT MATH_PACK, block while Value = 0
tile_regs_release()PACK"I've packed it; take it back"STALLWAIT (pack done), ZEROACC that section, SEMGET MATH_PACK; flip to the other half

The wrappers are as thin as you'd hope. On Wormhole the UNPACK pieces of acquire and commit are empty functions (llk_unpack_common_api.h:374-377); the comments say they matter only for Quasar's unpack-to-dest.

template <DstSync Dst, bool is_fp32_dest_acc_en>
inline void _llk_pack_dest_section_done_()
{
    TTI_STALLWAIT(p_stall::STALL_MATH, p_stall::PACK); // wait for pack to finish
    if constexpr (Dst == DstSync::SyncFull)
    {
        constexpr std::uint32_t CLEAR_MODE = is_fp32_dest_acc_en ? p_zeroacc::CLR_ALL_32B : p_zeroacc::CLR_ALL;
        TTI_ZEROACC(CLEAR_MODE, ADDR_MOD_1, 0);
    }
    else
    {
        constexpr std::uint32_t CLEAR_MODE = is_fp32_dest_acc_en ? p_zeroacc::CLR_HALF_32B : p_zeroacc::CLR_HALF;
        TT_ZEROACC(CLEAR_MODE, ADDR_MOD_1, (dest_offset_id) % 2);
    }
    _llk_packer_set_math_semaphore_<p_stall::NONE>();   // SEMGET MATH_PACK
    if constexpr (Dst == DstSync::SyncHalf)

        flip_packer_dest_offset_id();
        select_packer_dest_registers<Dst>();
    }
}

Read the semaphore's Value as "number of Dst sections full of finished results that the packer hasn't released yet". MATH may start a new section while that number is below Max. PACK may start reading while it's above zero. With Max = 2, MATH can be one whole section ahead of PACK. The operands decode cleanly against ckernel_instr_params.h:241-254: STALL_TDMA = 0x1, STALL_SYNC = 0x2, STALL_MATH = 0x40, STALL_SFPU = 0x100, STALL_ON_ZERO = 1 and STALL_ON_MAX = 2. TRISC0's binary contains no MATH_PACK instructions at all. Its only semaphore instructions are two SEMGETs on mask 32 (semaphore 5, UNPACK_SYNC), which the unpacker uses to double-buffer its own configuration (llk_unpack_AB.h:264-280). That machinery belongs to A13.

How many tiles fit

Dst is 1024 rows of 16 datums (A06), and a 32×32 tile takes 64 rows in 16-bit mode. The LLK computes capacity from exactly two switches, the sync mode and the accumulator width (get_dest_max_tiles, tt-llk ckernel.h:652-658, with DEST_REGISTER_FULL_SIZE = 64 * 16 rows in tensix_types.h:192):

bf16 Dst (fp32_dest_acc_en = false)fp32 Dst (fp32_dest_acc_en = true)
Half sync (default, dst_full_sync_en = false)8 tiles per acquire4 tiles
Full sync (dst_full_sync_en = true)16 tiles8 tiles

The tile index you pass to add_tiles(…, idst) or pack_tile(idst, …) is relative to the current section, so index 0 means "the first tile of whichever half I currently own". That's why the eltwise loop can use dst_reg = 0 every iteration and still ping-pong.

Some comments in the sources are stale. reg_api.h's doc comment calls Dst "an array of 16 tiles", and three examples' comments say each acquire gives you 8 tile registers, regardless of configuration (add_2_tiles.cpp:26, eltwise_binary and custom_sfpi_add tiles_add.cpp). The examples' own comment in custom_sfpi_add even says commit "transfer[s] register ownership to the unpacker". It goes to the packer. Trust the table, which follows the code.

Breaking the handshake in ttsim

A04 removed tile_regs_wait and watched ttsim stop at a SEMGET on a zero semaphore, and then removed wait and release together and got a tile of zeros. Here are two different mistakes, each one an extra call rather than a missing one. Both are easy to make when refactoring a loop. Every run below used the overlay directory and the stock Wormhole ttsim.

Experiment 1: release twice

ttsim stops the whole process. The first release brought MATH_PACK from 1 to 0. The second one's SEMGET found Value already at 0, and ttsim's Sync-unit model refuses to continue:

ttsim/src/tensix.cpp:5544-5553 @b3620244 (trimmed)

    ...

    p_tensix->sem[sem_index]--;
    return true;
}

In the message, sem=0 is the semaphore's value, not its index. On silicon there would be no error. The ISA says that decrementing a zero semaphore is NonContractualBehavior and that "current silicon leaves the Value at zero" (SEMGET.md). Your kernel would keep running. In this one-tile kernel it would even give the right answer. In a loop, the extra release also flips the packer's half pointer an extra time, so the packer and the math thread would then disagree about which half is which. ttsim refusing is the friendlier outcome. (The silicon behaviour here is from the ISA documentation; I can only run ttsim.)

A control run of the same host program with the stock kernel printed "run 1 finished", "run 2 finished" and "Success". Here is what the leaked count did. The second program started with Value = 1. Its PACK thread's tile_regs_wait saw 1 ≠ 0 and went straight through, so the packer copied Dst, which was all zeros from run_kernel's zeroacc(), before MATH had done anything. Its release took Value back to 0. That freed MATH's startup spin loop, and MATH then did the add into a Dst that nobody would ever pack again. The program "finished" normally. The bug from program 1 corrupted program 2.

Unbalanced handshakes are time bombs. ttsim catches a SEMGET at zero and a SEMPOST at or above Max (tensix.cpp:5538-5539), because the ISA calls those NonContractualBehavior. An extra commit that stays within Max is legal hardware behaviour. No simulator check can flag it, and it surfaces as wrong data in a different kernel. The rule is mechanical: per loop iteration, MATH does exactly one acquire and one commit, and PACK exactly one wait and one release. The docs add that you must commit and release even if you pack nothing (compute_engines_and_dataflow_within_tensix.rst:118-120).
Trace the SEMINIT/SEMWAIT/SEMPOST/SEMGET stream instruction by instruction, and write your own reader/compute/writer kernel, in B06. To follow the MOPs above as they expand into ELWADDs and PACRs per pipe, see B04 · Following Tensix instructions.

Startup and init functions

Every compute kernel begins with compute_kernel_hw_startup, called once. It's the clearest example of a function spread across all three cores:

TRISC0 programs the unpackers with the input CBs' formats and tile shapes. TRISC1 initializes the MATH_PACK semaphore (the SEMINIT you saw in the disassembly) and programs the ALU's source formats. TRISC2 programs the packer for the output CB's format and sets up its Dst offset registers. Those formats come from the host's CB configuration. The JIT bakes them into chlkc_descriptors.h as arrays indexed by CB number; in the add example, CBs 0, 1 and 16 have format 5 (Float16_b) and tile size 2048 bytes.

SrcOrder::Reverse exists for one operation. A06 showed that a matmul's in0 goes to SrcB and in1 to SrcA, so the matmul example starts with compute_kernel_hw_startup<SrcOrder::Reverse>(cb_in0, cb_in1, cb_out) (mm.cpp:50). The header's doc comment warns that the function does slow MMIO-style configuration writes that need idle engines, so it is "unsafe to call this function in the middle of a kernel" (compute_kernel_hw_startup.h:43-46).

After startup comes an operation-specific init: add_init, copy_init, matmul_init, exp_tile_init and so on. These are also split by thread (for example, add_init runs llk_math_eltwise_binary_init on MATH and llk_unpack_AB_init on UNPACK, eltwise_binary.h:37-47). What they program is mostly the per-thread MOP templates and address modes that the per-tile calls then fire, plus, for SFPU ops, constants in the SFPU's programmable registers. How a MOP works is A13's subject. For now, think of an init as loading the instrument and the per-tile call as pulling the trigger. If you switch operations mid-kernel, you need the new op's init first.

How much does a forgotten init matter? I removed one init at a time from the sfpu_eltwise_chain kernel (which computes softplus, below) and ran it. The example checks its output against a CPU golden with Pearson correlation and requires PCC > 0.999:

FPU ops and SFPU ops

Compute API calls come in two shapes, and the shape tells you which engine runs them.

  • FPU ops take CB arguments. add_tiles(cb_a, cb_b, i, j, idst), mul_tiles and matmul_tiles unpack straight from L1 into SrcA/SrcB and have the matrix unit (A06) write Dst. One call does unpack and math.
  • SFPU ops take only Dst indices. exp_tile(idst), log_tile(idst) and add_binary_tile(i0, i1, iout) have no CB argument, because the vector unit (A07) can only see Dst. Their data has to be put in Dst first, with copy_tile(cb, i, idst).

copy_tile is itself an FPU op. On TRISC0 it unpacks to SrcA; on TRISC1 it runs a datacopy that, for a bf16 Dst, uses MOVA2D to move SrcA into Dst eight rows at a time. With an fp32 Dst or some integer formats it falls back to ELWADD or unpacks straight to Dst (tile_move_copy.h:126-134; llk_math_eltwise_unary_datacopy.h:343-384). Because they're constexpr, changing fidelity means a different binary. The kernel's cache hash includes all four settings (ComputeKernel::config_hash, impl/kernels/kernel.cpp:662-686), so each combination is compiled and cached separately. Four facts about how they are used, each read from the API headers:

  • Fidelity only affects multiplies. add_tiles and sub_tiles pass MathFidelity::LoFi as a literal (eltwise_binary.h:269-274, shown above), because addition doesn't multiply. mul_tiles and matmul_tiles pass MATH_FIDELITY (eltwise_binary.h:239-244; matmul.h:175). What the phases mean for precision, with measurements in ttsim, is in A06.
  • APPROX is a default, not a switch. Many SFPU APIs pass APPROX into their LLK. log_tile_init and log_tile do (compute_kernel_api.h:308-337), and so does add_binary_tile (eltwise_binary_sfpu.h:115-124). But exp_tile has its own template parameter, template <bool approx = false, …> (exp.h:36-44, 80-85), and never reads APPROX. With math_approx_mode = true, exp_tile(0) is still the accurate exp; you'd write exp_tile_init<true>() and exp_tile<true>(0) to get the fast one. Check each op's header.
  • fp32_dest_acc_en sets DST_ACCUM_MODE, which halves Dst's tile capacity (the table above) and changes several LLK code paths, such as datacopy's choice of MOVA2D versus ELWADD.
  • dst_full_sync_en selects DstSync::SyncFull: the SEMINIT Max becomes 1, and you trade overlap for twice the tiles per acquire.
The approximate SFPU paths are where ttsim and silicon can part ways. Approximate exp uses SFPLOADMACRO unless DISABLE_SFPLOADMACRO is defined, and ttsim doesn't implement that instruction, so the workbench sets TT_METAL_DISABLE_SFPLOADMACRO=1 (A07). In the simulator you then test a different instruction sequence from the one silicon runs by default.

A first SFPI kernel

The SFPU ops so far came from tt-metal's library. The custom_sfpi_add example shows how to write your own and plug it into a compute kernel. A07 took apart what the lanes do. Here we look at the plumbing: how a function written in SFPI ends up on exactly one TRISC.

Recap

  • One source, three binaries. The JIT writes chlkc_unpack.cpp, chlkc_math.cpp and chlkc_pack.cpp, each a #define TRISC_… plus #include of your kernel. Each is compiled with -DUCK_CHLKC_… into trisc0/1/2.elf. You can read all of them in the kernel cache. Before kernel_main, MATH clears Dst and UNPACK clears Src.
  • UNPACK(x), MATH(x) and PACK(x) expand to x on one TRISC and to nothing on the other two. Every compute API call is a list of such pieces. Control flow is replicated and work is not, so all three copies must take the same path through loops and branches.
  • CB calls are split by role. cb_wait_front and cb_pop_front run on UNPACK; cb_reserve_back and cb_push_back run on PACK. Their counter updates go through STALLWAIT and STOREREG so they never run ahead of the engines. MATH needs no CB calls: SrcA/SrcB validity is enforced in hardware.
  • The Dst handshake is one 4-bit Sync-unit semaphore, MATH_PACK. Acquire = SEMWAIT while Value ≥ Max; commit = STALLWAIT + SEMPOST; wait = SEMWAIT while Value = 0; release = STALLWAIT + ZEROACC + SEMGET. Max is 2 in half sync (ping-pong, 8 bf16 / 4 fp32 tiles per acquire) and 1 in full sync (16 / 8 tiles).
  • Unbalanced handshakes: a double release made ttsim stop with NonContractualBehavior: tensix_semget: sem=0, though silicon would silently continue. A double commit passed silently, left MATH_PACK at 1, and made the next program pack an all-zero tile.
  • compute_kernel_hw_startup configures all three engines and seeds the semaphore, once. *_init functions reprogram the engines (MOPs, address modes, SFPU constants) for an op. A missing SFPU init gave PCC around 0.8 or NaN with no error.
  • FPU ops (add_tiles, mul_tiles, matmul_tiles) read CBs. SFPU ops read Dst only, so they need copy_tile, which is itself an unpack plus an FPU MOVA2D. SFPU chains (softplus = exp, add, log) stay in Dst. matmul_tiles accumulates, relying on release's ZEROACC for a clean start.
  • Config becomes constexpr MATH_FIDELITY, APPROX, DST_ACCUM_MODE and DST_SYNC_MODE. Add/sub always use LoFi. exp_tile ignores APPROX in favour of its own template parameter.

Check yourself

1. A kernel puts DPRINT("i={}\n", i); inside its tile loop, which runs 4 times. How many lines appear, and why?

Twelve: four from each of TR0, TR1 and TR2. DPRINT isn't wrapped in a per-thread macro, and neither is the loop, so all three binaries contain the loop and the print. Use DPRINT_MATH (or _UNPACK or _PACK) to print once per iteration, from one TRISC. Expect the lines from different TRISCs to be interleaved in no meaningful order, because each RISC has its own print buffer.

2. Someone "optimizes" a compute kernel by wrapping the whole loop in if (n_tiles_from_cb_value > 0), where the value is read from a tile in an input CB right after cb_wait_front. What goes wrong?

cb_wait_front runs only on TRISC0. TRISC1 and TRISC2 skip the wait and read the CB location before the data has necessarily arrived, so they can see a different value from TRISC0 and take a different branch. The three copies then disagree on how many acquire/commit and wait/release pairs to execute, and one thread blocks forever on a semaphore. Branch only on values all three TRISCs see identically, such as runtime and compile-time arguments.

3. In half-sync mode with a bf16 Dst, MATH has committed two sections and PACK hasn't released either. What is MATH_PACK's value, and what happens at MATH's next tile_regs_acquire?

Value 2, equal to Max (SEMINIT 2 in _llk_math_pack_sync_init_). The acquire's SEMWAIT uses STALL_ON_MAX, so the math thread blocks until PACK's release does a SEMGET (2 → 1). Note that the TRISC1 RISC-V doesn't necessarily block. It may keep pushing instructions until its FIFO is full. It's the coprocessor's math thread that waits at the gate.

4. Why can a matmul kernel call matmul_tiles Kt times into Dst tile 0 for each output tile without ever zeroing Dst?

matmul_tiles accumulates (Dst += in0·in1). The previous output tile's section was cleared by tile_regs_release, whose LLK issues a ZEROACC on the section it just packed before the SEMGET. The very first sections were cleared by run_kernel's zeroacc() before kernel_main. So every acquire hands MATH a zeroed section, provided every acquire was matched by a release.

5. A double tile_regs_commit passed in ttsim, but a double tile_regs_release was stopped. Why the asymmetry?

ttsim checks what the ISA calls NonContractualBehavior: SEMPOST when Value is already at Max, and SEMGET when Value is 0. In a one-tile kernel with Max = 2, a second SEMPOST takes Value from 1 to 2, which is legal, so nothing fires. A second SEMGET takes it from 0 to below zero, which isn't. The legal but unbalanced commit leaves Value = 1 after the kernel, and the next program's pack wait passes immediately, which is exactly what produced the all-zero tile in the run_twice experiment.

6. You set math_approx_mode = true and math_fidelity = LoFi for an add_tiles + exp_tile kernel and see no change in results. Is the config broken?

No. add_tiles hard-codes MathFidelity::LoFi because addition uses no multiplier phases, so the fidelity setting has nothing to change. exp_tile takes its approximation mode from its own template parameter (default false) and doesn't read APPROX, so it stays accurate. You'd need exp_tile_init<true>() and exp_tile<true>(i). Fidelity would matter for mul_tiles or matmul_tiles, and APPROX for ops such as log_tile.
