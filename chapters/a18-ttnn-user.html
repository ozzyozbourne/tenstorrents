The question

Here is a small PyTorch tensor: 3 rows, 40 columns, the numbers 1 to 120 in bfloat16. It occupies 240 bytes. Hand it to TT-NN and ask it to put the tensor in the layout the hardware computes on:

t  = ttnn.from_torch(x, dtype=ttnn.bfloat16)      # x.shape == (3, 40)
tt = ttnn.to_layout(t, ttnn.TILE_LAYOUT)
d  = ttnn.to_device(tt, device)

Then ask it what it built. This is the real output from ttsim (script a18_pad.py, shown in the simulator section):

from_torch    : Layout.ROW_MAJOR Shape([3, 40]) padded Shape([3, 40])
to_layout TILE: Layout.TILE Shape([3, 40]) padded Shape([32, 64]) tile Tile with shape: [32, 32]
on device     : BufferType.DRAM TensorMemoryLayout.INTERLEAVED
pages 2 x 2048 bytes
padded view   : (32, 64)  nonzero: 120 of 2048
row 0, cols 36..43: [37.0, 38.0, 39.0, 40.0, 0.0, 0.0, 0.0, 0.0]
row 3, cols 0..3  : [0.0, 0.0, 0.0, 0.0]
to_torch      : (3, 40) bit-identical: True

Our 120 numbers now live inside 2048 slots, in two 2048-byte pages, in DRAM. The tensor still says its shape is [3, 40], but it carries a second shape, [32, 64]. When we bring it back to torch, the 120 numbers return bit for bit, and the 1928 zeros silently disappear.

What does ttnn.from_torch (and its friends) do to your tensor? Answering that question properly is most of what it takes to use TT-NN well. The rest of this chapter is about the choices TT-NN asks you to make: layout, dtype, where the bytes live, and how hard the math engine should work.

Where TT-NN sits

Chapters A10 to A17 built programs the hard way. To add two tensors in A10–A12 we wrote a reader kernel, a compute kernel and a writer kernel, created circular buffers, set runtime arguments, built a Program and enqueued it. That is TT-Metalium: a low-level runtime that gives you cores, L1, the NoC and a kernel compiler, and nothing else.

TT-NN is the operator library built on top of it. It is the layer a PyTorch user recognises: tensors, ttnn.add, ttnn.matmul, ttnn.softmax, about the size of a deep-learning framework's op set. Each op is C++ code that, when you call it, picks kernels, sizes circular buffers, splits the work across cores, builds a Metalium program, caches it, and enqueues it. Python reaches it through nanobind bindings. Model code (models/ in tt-metal) and compilers (TT-MLIR, TT-Forge, TT-XLA, the subject of A19) emit TT-NN calls rather than kernels.

LayerYou writeYou still decide
TT-Metalium (A10–A17)kernels, CBs, Programs, runtime argseverything
TT-NN (this chapter)op calls on tensorslayout, dtype, memory config, sometimes the core grid, program config and fidelity
Compilers (A19)a PyTorch or JAX modelmostly nothing; the compiler chooses the TT-NN calls

The right-hand column is the interesting one. TT-NN removes the kernel writing, but it does not hide the hardware. The 32×32 tile, the split between DRAM and L1, block floating point and math fidelity all show up as arguments you are expected to understand. Chapters A05–A09 are the reason those arguments exist.

On a GPU, PyTorch picks the memory for you (global memory, through a caching allocator) and every tensor is a flat strided array. Layout and placement are mostly invisible; caches and the hardware scheduler take care of locality. TT-NN cannot do that, because there are no caches (A09). So placement becomes part of the tensor: a ttnn.Tensor knows whether it is tiled, which kind of memory holds it and which cores own which piece. The nearest GPU analogue is the choice between a row-major array and a tensor-core-friendly swizzled layout, except that here every op consumes and produces the swizzled form.

Opening a device is one call. Even for a single chip, TT-NN gives you a mesh, because the Python open_device is bound directly to the mesh version:

Anatomy of a ttnn.Tensor

A ttnn.Tensor is data plus a description of how that data is laid out. The description has six parts, and the opening output already showed all of them:

  • shape, the logical shape you asked for: [3, 40].
  • padded_shape, the shape of what is actually stored: [32, 64] once tiled.
  • dtype: BFLOAT16, BFLOAT8_B, FLOAT32, UINT32 and so on.
  • layout: ROW_MAJOR or TILE, plus the tile shape (32×32 by default).
  • storage: HOST (a buffer in your process) or DEVICE (a buffer in DRAM or L1).
  • memory_config, for device tensors: which memory, and how the pages are spread out.

Four functions move a tensor between these states, and it pays to know which ones touch the device:

CallWhat changesWhere the work happens
ttnn.from_torch(x, dtype, layout, device, memory_config)torch → ttnn; optionally tilize, convert dtype and upload in one gohost, then a write to the device if device is given
ttnn.to_layout(t, ttnn.TILE_LAYOUT)ROW_MAJOR ↔ TILE (adds or strips padding)on the host for a host tensor; a tilize/untilize op on the device for a device tensor
ttnn.to_device(t, device, memory_config) / ttnn.from_device(t)storage HOST ↔ DEVICE; layout and dtype unchangeda buffer write or read (A17)
ttnn.to_torch(t)ttnn → torch; untilize, strip padding, convert dtypehost (reads back first if needed)

Two defaults matter. from_torch gives you ROW_MAJOR unless you ask for TILE, except for the block-float dtypes, which only exist as tiles:

tt-metal/ttnn/cpp/ttnn-nanobind/pytensor.cpp:781-783 @7aad8aac

    (dst_dtype == DataType::BFLOAT4_B || dst_dtype == DataType::BFLOAT8_B || is_mx(dst_dtype));
auto layout_ = layout.value_or(tile_layout_by_default ? Layout::TILE : Layout::ROW_MAJOR);

And when you pass device=, you get DRAM_MEMORY_CONFIG (DRAM, interleaved) unless you say otherwise. That default is what the opening output printed.

ROW_MAJOR vs TILE: what padding costs

You met the 32×32 tile and its four 16×16 faces in A05, and saw a host program tilize matrices by hand in A15. TT-NN does the same thing, but now the unit of storage, the page, depends on the layout. The tensor-layouts tech report puts it in one sentence each: in row-major layout "each row of a 2D tensor corresponds to a single page", and in tiled layout "pages are represented as 2D tiles" (tech_reports/tensor_layouts/tensor_layouts.md:33-50). Higher dimensions are folded into the height first, so a [1, 4, 6, 8] tensor is stored as [24, 8] (same file, line 20).

You can watch both page shapes on the device. This run uploads the 3×40 tensor in row-major layout and then asks the device to tilize and untilize it (a18_devtilize.py):

device RM  : Layout.ROW_MAJOR Shape([3, 40]) padded Shape([3, 40]) pages 3 x 80 B
device TILE: Layout.TILE Shape([3, 40]) padded Shape([32, 64]) pages 2 x 2048 B
padding is zero: True  data intact: True
untilized  : Layout.ROW_MAJOR Shape([3, 40]) equal: True

Row-major: three pages, one per row, 40 × 2 bytes = 80 B each. Tiled: two pages of 32 × 32 × 2 = 2048 B. Step through what happened in between. Use the shape buttons to try other sizes.

The face order inside a tile comes from the host tilizer, the same loop A15 quoted: for each tile, for each face row, for each face column, write a 16×16 face.

    size_t row_tile_start = tile_start;
    for (size_t col_tile = 0; col_tile < col_tiles; col_tile++) {
        if (!transpose_face_order) {
            for (size_t face_h_index = 0; face_h_index < tile_H / face_H; face_h_index++) {
                for (size_t face_w_index = 0; face_w_index < tile_W / face_W; face_w_index++) {
                    size_t src_idx = row_tile_start + (face_w_index * face_W) + (face_h_index * face_H * W);
                    write_face(src_idx, face_H, face_W, W);
A TILE tensor stores padded_shape, not shape. Every dimension you hand TT-NN is rounded up to a multiple of 32 in the last two dimensions, and one page is one tile. A [1, 32] vector costs as much as a [32, 32] matrix.

Why accept the padding? Because every compute kernel from A12 onward moves and computes whole tiles: the unpacker reads a tile from a circular buffer, the FPU multiplies faces, the packer writes a tile back. A row-major tensor would have to be tilized before any math, and many ops require TILE_LAYOUT on their inputs. ROW_MAJOR is still useful for things the math engine never touches, such as embedding tables and index tensors, and for the moment you hand data back to torch.

Where does the tilizing happen? Two places, and in this commit TT-NN prefers the host for a single device. The C++ behind from_torch can upload the raw row-major data first and convert it on the device, but for a single device it takes that path only when no layout, dtype or sharding change is needed, so there is nothing to convert. The comment says why:

tt-metal/ttnn/core/tensor/py_to_tt_tensor.cpp:305-314 @7aad8aac
// TODO: #https://github.com/tenstorrent/tt-metal/issues/40850
// For single-device tensors, we cannot enable layout/data type changes due to tt-sim CI failures
// caused by limited support for the SFPLOADMACRO instruction.
// ...
const bool is_data_transformation_required = layout != Layout::ROW_MAJOR ||
                                             src_dtype != convert_to_data_type<T>() || src_dtype != dst_dtype ||

That "tt-sim" is the simulator this series uses. So from_torch(..., layout=TILE_LAYOUT, device=d) tilizes on the CPU and uploads tiles. Calling ttnn.to_layout on a tensor that is already on the device runs a real tilize op on the Tensix cores instead, which is what a18_devtilize.py did. Both produce the same bytes.

The word page changes meaning with the layout. For a TILE tensor a page is one tile (2048 B in bf16); for a ROW_MAJOR tensor it is one row (W × element size). buffer_page_size() tells you which you have. Anything that reasons about "page p goes to bank p mod 12" (A09) is reasoning about these pages.

Dtypes: bfloat16, bfloat8_b, bfloat4_b

A05 built the formats from first principles: bfloat16 is a truncated float32 (8 exponent bits, 7 stored mantissa bits); bfloat8_b and bfloat4_b are block-floating-point formats in which 16 values share one 8-bit exponent and each value keeps a sign and 7 or 3 mantissa bits. In TT-NN these are just dtype= arguments. What you should know as a user is what they cost and what they buy.

The cost side is in the tile-size function. A bfp tile stores its mantissas plus one exponent byte per 16-value face row, padded to the L1 alignment:

tt-metal/tt_metal/impl/data_format/tile.cpp:136-145 @7aad8aac
uint32_t Tile::get_tile_size(const DataFormat& format) const {
    uint32_t l1_alignment = MetalContext::instance().hal().get_alignment(HalMemType::L1);
    uint32_t aligned_exp_size = tt::round_up(face_shape[0] * num_faces, l1_alignment);
    switch (format) {
        case DataFormat::Bfp2:
        case DataFormat::Bfp2_b: return (tile_hw / 4) + aligned_exp_size;
        case DataFormat::Bfp4:
        case DataFormat::Bfp4_b: return (tile_hw / 2) + aligned_exp_size;
        case DataFormat::Bfp8:
        case DataFormat::Bfp8_b: return tile_hw + aligned_exp_size;

For a 32×32 tile, face_shape[0] × num_faces = 16 × 4 = 64 exponent bytes. So a bfloat8_b tile is 1024 + 64 = 1088 B and a bfloat4_b tile is 512 + 64 = 576 B, against 2048 B for bfloat16. The device reported exactly those page sizes in the run below. Halving the bytes halves the DRAM traffic, which, as A01 and A22 argue, is what bounds most inference.

Three lessons fall out of those twelve numbers. First, bfloat8_b weights cost almost nothing in accuracy (PCC 0.99994 against 0.99996) for 47% fewer bytes. The LLM tech report puts it bluntly: "BFP8 weights always work and BFP4 weights work for some matmuls particularly in the MLP" (tech_reports/LLMs/llms.md:1883). Second, bfloat4_b loses about 0.7% PCC at storage time: the round-trip alone gives PCC 0.993, and no fidelity setting can win it back. Third, fidelity and dtype interact through the hardware described in A06: a format that fits SrcA's 5-bit slice needs only phase 0.

The BFP formats share an exponent along each 16-value face row. One large value in a row of small ones flushes the small ones toward zero (A05's draggable outlier). Random Gaussian weights, as here, are the friendly case. Activations with outliers are not, which is one reason to quantize weights before activations and to check PCC after each step.

Memory configs: DRAM or L1, interleaved or sharded

A device tensor's pages have to live somewhere. A09 described the hardware: 12 DRAM banks on Wormhole (8 on Blackhole), and one L1 bank per Tensix core. TT-NN describes the choice with a MemoryConfig, which has two independent axes:

tt-metal/tt_metal/api/tt-metalium/buffer_types.hpp:12-16, 38-44 @7aad8aac
enum class TensorMemoryLayout {
    INTERLEAVED = 0,
    HEIGHT_SHARDED = 2,
    WIDTH_SHARDED = 3,
    BLOCK_SHARDED = 4,
...
enum class BufferType {
    DRAM,
    L1,
    SYSTEM_MEMORY,
    L1_SMALL,
    TRACE,
};

Buffer type picks the memory. DRAM is large (gigabytes) and far away; L1 is 1464 KiB per core on Wormhole (A09) and next to the compute. Memory layout picks how pages are spread. Interleaved deals pages round-robin across all banks of that memory, so every core reads from everywhere and no bank is a hot spot. Sharded cuts the tensor into rectangles and gives each one to a specific core (for L1) so that the core computing on a rectangle already holds it.

The shard rectangle is described by a ShardSpec:

tt-metal/tt_metal/api/tt-metalium/buffer.hpp:36-44 @7aad8aac
struct ShardSpec {
    /* The individual cores the shard grid is mapped to */
    CoreRangeSet grid;

    /* Canonical tensor shape where the depth dimensions ([:-2] are folded along y) */
    std::array<uint32_t, 2> shape;

    /* The sequence order of the grid cores that the shards are laid out onto. */
    ShardOrientation orientation = ShardOrientation::ROW_MAJOR;

Three numbers decide everything: which cores, the shard's height and width, and the order in which shards are handed to cores. Height sharding uses full-width shards, width sharding uses full-height shards, block sharding cuts both ways. This animation follows a 128×128 bfloat16 tensor (4×4 tiles) into each layout, using the exact grids and shard shapes that ttsim printed in the run below.

All four layouts run under ttsim. The script converts two DRAM tensors to each sharded layout with ttnn.to_memory_config, adds them there, and checks the sum (a18_shard.py):

Blackhole gives the same shard specs and PCCs, with a compute grid of 11-10 instead of 8-8. Notice the two addresses. The DRAM tensor starts at 0x2d4c40, the first free DRAM address that A09's probe found. The L1 tensor starts at 0x16d800, exactly 2048 B below the top of Wormhole's 1464 KiB (0x16E000) L1: its 16 pages are spread over 64 L1 banks, so each bank needs at most one page, placed at the top. That is A09's allocator at work, DRAM bottom-up and L1 top-down. The core grid prints as x-y, so [0-0 - 0-3] means cores (0,0) through (0,3), one column of four.

The helper that built these configs is short and worth reading, because its checks are the rules of 2D sharding:

tt-metal/ttnn/ttnn/core.py:214-223 @7aad8aac
elif strategy == ShardStrategy.HEIGHT:
    total_cores = core_grid.x * core_grid.y
    if shard_height % total_cores != 0:
        raise RuntimeError("Invalid sharding core_grid")
    shard_shape = shard_height // total_cores, shard_width
elif strategy == ShardStrategy.WIDTH:
    total_cores = core_grid.x * core_grid.y
    if shard_width % total_cores != 0:
        raise RuntimeError("Invalid sharding core_grid")
    shard_shape = shard_height, shard_width // total_cores

Two ways to get it wrong, both tried on ttsim (a18_shard_edge.py):

3-core height shard helper FAILED: Invalid sharding core_grid
16-row shards FAILED: TT_FATAL: Physical shard shape (16, 128) must be tile {32, 32} sized!

128 rows do not split over 3 cores, and a hand-written ShardSpec with 16-row shards cannot hold whole 32×32 tiles. A TILE tensor's shard must be a whole number of tiles in both directions.

Interleaved spreads pages over banks for bandwidth balance. Sharded assigns rectangles to cores for locality. Height, width and block only differ in which way you cut.
The nearest GPU idea is choosing which thread block loads which tile into shared memory, except that on a GPU that choice lives inside the kernel and disappears when it returns. A sharded TT-NN tensor stays in the cores' L1 between ops, so the next op can start from data that is already local. The closest analogue is keeping activations resident in shared memory across a fused kernel; TT-NN gets that effect across separate ops.
The ready-made ttnn.L1_HEIGHT_SHARDED_MEMORY_CONFIG (and its WIDTH and BLOCK siblings) has shard_spec=std::nullopt; you can print it to check. It tells an op "produce a sharded output and work out the spec yourself", which some ops accept as an output config. To shard an existing tensor you need a full spec, from create_sharded_memory_config or a hand-built ShardSpec.

Ops, and checking them with PCC

With tensors in place, ops look like PyTorch. Inputs in TILE layout, outputs in TILE layout, and unless you pass memory_config= the output lands in DRAM interleaved. These are the TT-NN calls of the script for the three ops below; the full script (a18_ops.py) adds the seed, the input tensors, the torch references and the PCC helper:

a = torch.randn(64, 64, dtype=torch.bfloat16); b = torch.randn(64, 64, dtype=torch.bfloat16)
ta = ttnn.from_torch(a, layout=ttnn.TILE_LAYOUT, device=device)
tb = ttnn.from_torch(b, layout=ttnn.TILE_LAYOUT, device=device)
tc = ttnn.add(ta, tb)

tx = ttnn.from_torch(x, layout=ttnn.TILE_LAYOUT, device=device)   # 64x128
tw = ttnn.from_torch(w, layout=ttnn.TILE_LAYOUT, device=device)   # 128x96
ty = ttnn.matmul(tx, tw)

ts = ttnn.softmax(ttnn.from_torch(s, layout=ttnn.TILE_LAYOUT, device=device), dim=-1)
add     64x64     PCC 0.999998  max|err| 0.0312  out BufferType.DRAM
matmul  64x128@128x96 PCC 0.999984  mean|err| 0.0472  shape Shape([64, 96])
softmax 32x64     PCC 0.999722  row sums [0.9995536804199219, 1.000579833984375, 0.9993896484375]

The same script on the Blackhole build of ttsim prints identical numbers. How should you read them? A05 defined PCC, the Pearson correlation between the device result and a torch reference; it checks the shape of the answer but not its scale, so pair it with an absolute error. The LLM tech report asks for a PCC of about 0.999 for small submodules such as an MLP, about 0.998 for a decoder layer and about 0.99 for the full model (tech_reports/LLMs/llms.md:1665-1666).

  • The add is not bit-identical to torch's bfloat16 add. The largest error, 0.0312, is one bfloat16 step for values between 4 and 8. Both sides round to bfloat16, and the research notes for this series found about 12% of elements one ulp apart on a 32×32 add, so expect PCC near, but not at, 1.
  • The matmul accumulates 128 products per output. Its error depends on the fidelity and on how the accumulator is rounded, the subject of the next section.
  • softmax uses the SFPU's exponential (A07) in an approximate mode by default for bfloat16 inputs, and the rows sum to 1 only within about 0.1%.

Program configs and compute kernel configs

Most ops take two optional configuration objects, and they answer different questions.

A compute kernel config answers "how should each core's math engine work?" It is one struct, shared by all ops and architectures:

tt-metal/ttnn/cpp/ttnn/operations/core/compute_kernel/compute_kernel_config.hpp:19-27 @7aad8aac
struct ComputeKernelConfig {
    tt::tt_metal::MathFidelity math_fidelity = tt::tt_metal::MathFidelity::LoFi;
    bool math_approx_mode = true;
    bool fp32_dest_acc_en = false;
    bool packer_l1_acc = false;
    bool dst_full_sync_en = false;
    ttnn::operations::compute_throttle_utils::ThrottleLevel throttle_level =
        ttnn::operations::compute_throttle_utils::ThrottleLevel::NO_THROTTLE;
};

Each field is something you met at the kernel level. math_fidelity is the number of multiplier phases from A06. math_approx_mode selects the SFPU's approximate functions (A07). fp32_dest_acc_en makes Dst hold float32 instead of bfloat16, at the cost of half of its capacity (A12). packer_l1_acc lets the packer add into the output buffer in L1 rather than overwrite it, a second way to combine partial sums over K blocks (A15 reloaded them into Dst instead). In C++, WormholeComputeKernelConfig and BlackholeComputeKernelConfig are both aliases of this one struct (same file, lines 38-40); the scripts here use the Wormhole name.

A program config answers "how should the work be split across cores?" It is op-specific. For matmul there are several, and the 2D multicast one is the program of A15 and A16 with its blocking parameters exposed:

Here is one for a 128×256 by 256×128 matmul, which is 4×8 by 8×4 tiles, on a 2×2 grid. Each core owns a 2×2-tile block of the output (per_core_M = per_core_N = 2), consumes K two tiles at a time (in0_block_w = 2, which must divide Kt = 8), and computes its block in 1×2-tile subblocks that fit in Dst:

    compute_with_storage_grid_size=(2, 2), in0_block_w=2,
    out_subblock_h=1, out_subblock_w=2, per_core_M=2, per_core_N=2,
    transpose_mcast=False, fused_activation=None)
y = ttnn.matmul(tx, tw, program_config=pc)

Now the trap. Run that matmul four ways (a18_progcfg.py):

default (auto config)    PCC 0.999977  mean|err| 0.0831
auto + HiFi2             PCC 0.999963  mean|err| 0.1079
auto + HiFi2 + l1_acc    PCC 0.999977  mean|err| 0.0831
program_config + HiFi2   PCC 0.999963  mean|err| 0.1079
program_config only      PCC 0.999888  mean|err| 0.3181
program_config + HiFi4   PCC 0.999963  mean|err| 0.1133

Passing a program config, and nothing else, made the answer almost four times worse. The program config itself is innocent: with HiFi2 it gives exactly the auto path's 0.1079. What changed is the default fidelity, which the matmul op chooses like this:

tt-metal/ttnn/cpp/ttnn/operations/matmul/device/matmul_device_operation.cpp:3331-3336, 3382-3388 @7aad8aac

...

    arch,

Read it as a rule. If you let TT-NN choose everything, a bfloat16 matmul runs at HiFi2 with packer_l1_acc on. The moment you pass a program_config or a core_grid, or both inputs are block-float, the default drops to LoFi. And if you pass a compute kernel config, it replaces all of these defaults, including packer_l1_acc, which is why "auto + HiFi2" lost the auto path's 0.0831: the struct's own default turns L1 accumulation off. With it back on, the result matches the auto path exactly.

Whenever you pass a program_config to a matmul, pass a compute_kernel_config too, and state every field. The op will not warn you that it lowered the fidelity.

One more measurement separates fidelity from the accumulator. With bf16 inputs, the reference is now the fp32 product of the same bf16-rounded inputs, so only the device's arithmetic is being judged (a18_fid.py, packer_l1_acc=False):

fp32_dest_acc_en=False MathFidelity.LoFi    mean|err| 0.31691  max|err| 1.7826
fp32_dest_acc_en=False MathFidelity.HiFi2   mean|err| 0.10234  max|err| 0.9157
fp32_dest_acc_en=False MathFidelity.HiFi3   mean|err| 0.10931  max|err| 0.9344
fp32_dest_acc_en=False MathFidelity.HiFi4   mean|err| 0.10931  max|err| 0.9344
[10142] ERROR: UnsupportedFunctionality: tensix_unpacr: cfg_context_id=1

Two findings. HiFi3 and HiFi4 are identical, and both slightly worse than HiFi2. That fits A06's reading of ttsim's MVMUL: with a bfloat16 Dst, each phase's partial products are aligned and rounded to Dst's 8-bit significand before they are added, so extra phases add rounding steps without adding bits that survive. The error floor here is the bfloat16 accumulator, not the multiplier. The way to lower it is fp32_dest_acc_en=True, and that is where the run stopped: the first matmul with an FP32 Dst hit an unpacker configuration (cfg_context_id=1) that ttsim v1.15.0 reports as UnsupportedFunctionality. On silicon this setting is common; under this simulator it is out of reach for matmul.

The fidelity effects above are for random Gaussian inputs on one shape. They are a measurement, not a law. The general rule from A06 holds: fidelity buys bits on the multiplier side, the Dst format decides how many of them survive, and the weight dtype can make both moot.

The generated sources in our private cache confirm it: the reader's and writer's kernel_includes.hpp include files from kernels_ng/dataflow/, and the compute kernel's chlkc_math.cpp (and its unpack and pack siblings) include kernels/compute/eltwise_binary_no_bcast.cpp. Note is_sfpu: the same op can be compiled to an FPU kernel (A06) or an SFPU kernel (A07) depending on dtypes and options. For a bfloat16 add it chose the FPU.

An op call is a program-cache lookup. The first call with a new combination of shapes, dtypes, layouts and memory configs builds (and maybe compiles) a program; later identical calls reuse it and only patch addresses. Keep shapes stable and the expensive part happens once.

From a torch model to ttnn calls

Porting a model is mostly a translation exercise, plus deciding the choices from this chapter once per tensor. Take a two-layer MLP:

mlp = torch.nn.Sequential(torch.nn.Linear(256, 512), torch.nn.GELU(), torch.nn.Linear(512, 256))

The translation, as run on ttsim (a18_progcfg.py, second half):

W1 = ttnn.from_torch(mlp[0].weight.T.contiguous(), dtype=ttnn.bfloat8_b, layout=ttnn.TILE_LAYOUT, device=device)
b1 = ttnn.from_torch(mlp[0].bias.reshape(1, -1), dtype=ttnn.bfloat16, layout=ttnn.TILE_LAYOUT, device=device)
W2 = ttnn.from_torch(mlp[2].weight.T.contiguous(), dtype=ttnn.bfloat8_b, layout=ttnn.TILE_LAYOUT, device=device)
b2 = ttnn.from_torch(mlp[2].bias.reshape(1, -1), dtype=ttnn.bfloat16, layout=ttnn.TILE_LAYOUT, device=device)
h   = ttnn.linear(tx, W1, bias=b1, activation="gelu")
out = ttnn.linear(h, W2, bias=b2)
MLP 128x256 -> 512 -> 256 (bfp8 weights)  PCC 0.999934

Each line carries one of the decisions:

PyTorchTT-NNWhy
nn.Linear.weight is [out, in]transpose once, at load timettnn.linear computes x @ W with W as [in, out]; TT-NN's own helper does the same (ttnn/ttnn/model_preprocessing.py:25-28)
bias of shape [out]reshape(1, -1), TILEa 2D row that broadcasts down the rows; padded to 32 rows like everything else
fp32 parametersweights bfloat8_b, bias and activations bfloat16the ladder above: weight bytes halve at almost no cost
GELU moduleactivation="gelu"one argument; with no core grid, as here, TT-NN runs it as a separate unary op after the matmul (ttnn/cpp/ttnn/operations/matmul/matmul.cpp:323-329). To fuse it into the matmul kernel, use a program config's fused_activation field
tensors between layersstay on the device, TILEno host round trips or re-tilizing between ops; only the input is converted and only the output is read back

Real models add the remaining choices: activations sharded in L1 for decode, program configs for the large matmuls, and a compute kernel config per op. They also follow an accuracy discipline. The LLM tech report recommends testing each submodule against the reference model (PCC about 0.999) before whole layers and the full model (about 0.99), which is the check we just ran at toy scale. A22 does it for a transformer, and A19 shows how a compiler can make these translations for you.

On a GPU, porting this MLP needs no code: it already runs on CUDA. The closest analogy to the TT-NN port is preparing a model for a TensorRT-style engine: weights are converted and laid out once, precision is chosen per layer, and activations are fused into the GEMM epilogue. The difference is that in TT-NN you make those choices in Python, op by op.

Recap

  • TT-NN is the operator library on top of TT-Metalium. Each op builds, caches and enqueues a Metalium program; you stop writing kernels but keep choosing layout, dtype, memory placement and math settings.
  • A ttnn.Tensor has a logical shape and a stored padded_shape. In TILE layout the last two dimensions are rounded up to multiples of 32 and one page is one 2048-byte bfloat16 tile with four 16×16 faces inside. Our 3×40 tensor became 32×64: 2 pages, 5.9% useful.
  • from_torch defaults to ROW_MAJOR (TILE for block floats) and DRAM interleaved; for a single device it tilizes on the host. to_layout on a device tensor tilizes on the cores.
  • bfloat8_b tiles are 1088 B and bfloat4_b tiles 576 B. bfp8 weights cost little accuracy; bfp4 loses it at storage time, which no fidelity recovers.
  • A MemoryConfig is buffer type (DRAM or L1) times memory layout (interleaved, height, width or block sharded). Shards must be whole tiles and must divide the tensor. All of them run on ttsim.
  • Compute kernel configs set fidelity, approximation and accumulation; program configs set the core split. Passing a matmul program config without a compute config silently drops the fidelity from HiFi2 to LoFi.
  • ttnn.add becomes binary_ng, a program-cache lookup, and on a miss three kernels on five RISC-V cores. A19 opens that machinery.

Check yourself

A tensor of shape [2, 7, 50] in TILE layout, bfloat16. How many pages does it occupy and how big is each?

Padding applies to the last two dimensions of each slice, before the outer dimensions are folded into the height. So 7 rounds up to 32 and 50 to 64, giving padded_shape [2, 32, 64], which is stored as a 64×64 2D buffer: 2×2 = 4 tiles, 4 pages of 2048 B. Only 700 of 4096 stored values are data. On ttsim: Shape([2, 7, 50]) Shape([2, 32, 64]) 4 2048. A tempting wrong answer is to fold first (14 rows → 32), giving 2 pages; padding is per slice.

You pass program_config=pc to a bfloat16 matmul and its PCC drops from 0.99998 to 0.99989. You did not touch fidelity. What happened, and what is the fix?

In matmul_device_operation.cpp the default fidelity is HiFi2 only if there is no program config, no core grid and not two block-float inputs; otherwise LoFi. Your program config lowered the fidelity. Pass a compute_kernel_config with the fidelity (and packer_l1_acc) you want. Our run went from 0.3181 to 0.1079 mean error with HiFi2.

Why does bfloat4_b give the same matmul result at LoFi and HiFi2, while bfloat8_b does not?

In a matmul, in1 (the weights) is unpacked into SrcA, whose multiplier input is 5 bits per phase (A06, A15). A bfp4 value has at most 3 significant bits, so phase 0 already sees all of it; HiFi2's second phase multiplies SrcA's low slice, which is zero. A bfp8 value has up to 7 significant bits, so phase 0 drops the bottom two and LoFi's error is roughly doubled.

A 128×128 tensor is block-sharded on a 2×2 grid with ROW_MAJOR orientation. Which core holds tile 6 (row 1, column 2 of the 4×4 tiles)?

The shard is 64×64 = 2×2 tiles. Tile row 1 is in block row 0; tile column 2 is in block column 1. Block (r=0, c=1) goes to core (x=1, y=0), which is [0-0 - 1-1]'s top-right core.

The second identical ttnn.add took 0.01 s instead of 1.13 s. Which steps were skipped, and what would make the next call slow again?

The program-cache lookup hit, so the program factory (kernel selection, CB sizing, work split) and the JIT build were skipped; only runtime arguments such as buffer addresses were patched before the program was enqueued. Changing anything that enters the cache key, such as a shape, dtype, layout or memory config, gives a new key and a new program. A new kernel binary would only be compiled if the kernel cache did not already hold one for those compile-time arguments.
