The question

In A18 you used TT-NN the way most people do: make two tensors, call one function, read the answer.

c = ttnn.add(a, b)        # a, b: 32x32 bfloat16, TILE layout, in DRAM

From A10–A14 you also know what the chip needs before it can add anything. It needs a reader kernel to pull tiles over the NoC into circular buffers, a compute kernel that the JIT compiles three times, once each for UNPACK, MATH and PACK, a writer kernel to push results back, circular buffers with sizes and data formats, and runtime arguments on every core that tell each kernel where its tensor lives and how many tiles are its share. That is a lot of decisions, and ttnn.add takes only two arguments.

What happens between ttnn.add(a, b) and the FPU? Who decides which kernels to run and how many cores to use? Who compiles them, and why is the second call about a hundred times faster than the first?

Below is the whole descent for that call, as it actually ran in this orb. Every layer takes a description from the layer above and emits a more concrete artifact for the layer below. Step through it once now. The rest of the chapter takes each layer apart.

Figure 1 (the "aha"). One ttnn.add on a 32×32 bf16 tile descending the stack on simulated Wormhole. The kernel directory names, hash numbers, defines and addresses are copied from the run in Run it in the simulator.

Notice where the expensive work sits. Steps 3–5 build things: an output tensor, a program description, compiled binaries. Step 6 only uses them. TT-NN is built so that a second call to the same op skips steps 4 and 5. That is the program cache, and most of the design you are about to see exists to make it safe.

Two kinds of work: the plate and the paper

Think of an old print shop. Making a printing plate is slow: someone has to set the type, lock the frame and ink it. Printing a page from a finished plate is fast. A shop that prints the same flyer every week keeps the plate in a rack and only feeds in new paper.

A TT-NN op splits its work the same way:

  • The plate is everything that depends on what is computed: which kernel source files run, their #defines and compile-time arguments, the circular-buffer layout, the set of cores. Changing any of these means a different binary or a different L1 layout. In tt-metal these become a Program, and the kernels get JIT-compiled (A13).
  • The paper is everything that depends on where the data happens to be this time: the DRAM address of a, of b and of the output, and sometimes how many tiles each core should process. These are runtime arguments. They are words written into each core's L1 just before launch, and a kernel reads them with get_arg_val.

The program cache is the plate rack. Its key has to capture everything that would change the plate, and nothing that only changes the paper. If the key includes too much, every call misses and you rebuild forever. If it includes too little, you print with the wrong plate: a stale kernel or the wrong buffer address, and the result is silently wrong.

The analogy has two limits. First, a real plate does not care which paper you feed it, but a cached Program still holds the old addresses in its runtime-argument slots. Someone has to overwrite them before each reuse, and that job (override_runtime_arguments) is the subtle part of writing an op. Second, there are really two racks. The program cache holds whole Program objects in host memory for the life of the process. The JIT cache from A13 holds compiled ELF files on disk across processes. You will see both in the measurements.

On a GPU, a + b in PyTorch launches a CUDA kernel that was compiled when PyTorch was built. Launching it means pushing a pointer and a few scalars. Specialisation to shapes and dtypes happens through templates instantiated ahead of time. Tenstorrent kernels are compiled at run time, specialised by #defines and compile-time arguments, and a launch has to configure circular buffers and per-core arguments on up to 64+ independent cores. So TT-NN looks less like cuBLAS and more like a JIT system with a cache, in the same family as Triton's per-signature kernel cache or torch.compile's guards.

Anatomy of a device operation

The C++ type that owns one op's plate-making is called a device operation. tt-metal ships a toy one, ExampleDeviceOperation, as a template for new ops. Its header is short enough to read in full. Here is the part that matters:

tt-metal/ttnn/cpp/ttnn/operations/examples/example/device/example_device_operation.hpp:18-31, 50-54 @7aad8aac
struct ExampleDeviceOperation {
    // Define the operation attributes. This is used to store all variables needed by operations that aren't tensors.
    struct operation_attributes_t {
        bool attribute;
        int some_other_attribute;
    };

    // Define the tensor arguments. This is used to store all tensors passed in and/or out of the operation.
    // ...
    struct tensor_args_t {
        // This example will use a tensor that can only be used as an input
        const Tensor& input_tensor;
    ...
    using spec_return_value_t = tt::tt_metal::TensorSpec;
    ...
    using tensor_return_value_t = Tensor;

The op's inputs are split into two structs, and the split is deliberate. operation_attributes_t holds the non-tensor settings: for add, the op type, output dtype, memory config, which cores to use. tensor_args_t holds the tensors. The framework hashes both to build the cache key (shown later), and it walks tensor_args_t by reflection to find every Tensor it has to validate. The return types say what comes back: a TensorSpec describes an output before it exists (shape, dtype, layout, memory config), and a Tensor is the allocated result.

Then come the functions, all static. A device operation keeps no state of its own:

tt-metal/ttnn/cpp/ttnn/operations/examples/example/device/example_device_operation.hpp:84-99 @7aad8aac
    using program_factory_t = std::variant<SingleCore, MultiCore>;

    static program_factory_t select_program_factory(const operation_attributes_t&, const tensor_args_t&);

    // Validate the operation when it creates a program. Also called on cache hit by default.
    static void validate_on_program_cache_miss(const operation_attributes_t&, const tensor_args_t&);

    // Optional: override to use lighter validation on cache hit.
    // If not provided, the framework calls validate_on_program_cache_miss.
    // static void validate_on_program_cache_hit(const operation_attributes_t&, const tensor_args_t&);

    // Compute the output specs based on the operation attributes and tensor args.
    static spec_return_value_t compute_output_specs(const operation_attributes_t&, const tensor_args_t&);

    // Create the output tensors based on the operation attributes and tensor args.
    static tensor_return_value_t create_output_tensors(const operation_attributes_t&, const tensor_args_t&);
  • program_factory_t is a std::variant of program factories, each a different way to build the program. The example has two, SingleCore and MultiCore. Matmul has seven, from a simple multi-core one to the 2D-multicast and DRAM-sharded ones you met in A15/A16 (matmul_device_operation.hpp:24-31).
  • select_program_factory picks one of them from the attributes and tensors. Its answer is a variant index, and the cache stores that index alongside the program.
  • validate_on_program_cache_miss checks the call and throws on bad input (wrong layout, mismatched shapes). The name says when it runs: only on a miss, unless the op provides a cheaper validate_on_program_cache_hit. Even without one, the hit path calls the miss version (device_operation.hpp:285-289), so a hit is still validated.
  • compute_output_specs is pure shape and type arithmetic. add uses it to broadcast shapes and pick the output dtype, and to make integer division return FP32 (binary_ng_device_operation.cpp:504-520).
  • create_output_tensors usually just allocates a device tensor from that spec (example_device_operation.cpp:31-35). It also handles a caller-supplied output_tensor, which is how in-place ops work.

The C++ entry point that users call is a small free function that fills the two structs and hands them to the framework:

tt-metal/ttnn/cpp/ttnn/operations/examples/example/device/example_device_operation.cpp:40-46 @7aad8aac
ttnn::operations::examples::ExampleDeviceOperation::tensor_return_value_t example(const Tensor& input_tensor) {
    using OperationType = ttnn::operations::examples::ExampleDeviceOperation;
    auto operation_attributes = OperationType::operation_attributes_t{true, 42};
    auto tensor_args = OperationType::tensor_args_t{input_tensor};

    return ttnn::device_operation::launch<OperationType>(operation_attributes, tensor_args);
}

ttnn.add follows the same shape. The Python name is a nanobind binding of the C++ ttnn::add. A macro expands that to invoke_binary_ng(..., BinaryOpType::ADD, ...) (binary.cpp:20-44, 1230). That function fills BinaryNgDeviceOperation::operation_attributes_t, about twenty fields long, and ends with the same one line: return ttnn::device_operation::launch<OperationType>(operation_attributes, tensor_args); (binary_ng_device_operation.cpp:807). Everything interesting happens inside launch.

The life of one call

Here is launch, trimmed to its spine:

Two details are easy to miss. First, the output tensor is allocated before the op's own validate_on_program_cache_miss runs. validate_input_tensors is only the framework's generic check: every input is on a device and allocated (device_operation.hpp:551-558). The op-specific validation happens later, inside the cache-miss branch. Second, every op runs on a MeshDevice, even a single chip. ttnn.open_device returns a 1×1 mesh (A18), and the adapter turns the op's program into a mesh workload, one program per device range. use_workload is the enqueue. The program is inserted into the cache only after it has been enqueued successfully, so a program that fails to compile or does not fit in L1 never pollutes the cache. The JIT build itself does not happen in the factory. It happens inside the enqueue: EnqueueMeshWorkload calls compile() in fast dispatch, and slow dispatch compiles inside LaunchProgram (tt_metal/distributed/distributed.cpp:125-138). The factory only describes kernels. tt-metal turns the descriptions into ELFs the first time they are needed.

On a hit there is no select_program_factory decision, because the index is in the cache entry. There is no factory call and no new Program, so nothing goes to the JIT. What remains is validation and the paper: rewriting runtime arguments, and possibly circular-buffer addresses, for the tensors of this call. apply_descriptor is the name the framework's adapters give that step. Depending on the factory flavour it calls the op's own override_runtime_arguments or patches buffer addresses for the op automatically.

Do not read "validate → specs → factory" as the order of execution. Tutorials often list the device-operation methods in that order. At this commit the actual order is: generic input check → create_output_tensors (which calls compute_output_specs) → hash and look up → then validate_on_program_cache_miss. compute_output_specs must therefore cope with inputs that have not been validated yet. binary_ng's own comment notes a related ordering trap: its hash function runs "before validate_on_program_cache_miss" and so has to tolerate unreadable buffers (binary_ng_device_operation.cpp:271-275).

Program factories: four ways to say "build this"

A program factory turns attributes and tensors into a program. Over time tt-metal has accumulated several flavours. The framework recognises each one by C++ concepts and adapts them all to a mesh workload (operation_concepts.hpp:25-153, device_operation.hpp:244-275). There are four you should recognise.

1. The imperative factory: create + override_runtime_arguments

The oldest style. create builds a Program with the host API from A10 (CreateCircularBuffer, CreateKernel, SetRuntimeArgs) and returns it together with a shared_variables_t: whatever override_runtime_arguments needs later to find its slots again, such as kernel handles and core lists. The concept that defines this flavour says exactly that:

tt-metal/ttnn/api/ttnn/operation_concepts.hpp:25-34 @7aad8aac
template <typename T>
concept ProgramFactoryConcept = requires {
    typename T::cached_program_t;

    [](const auto& operation_attributes, const auto& tensor_args, auto& tensor_return_value) {
        auto cached_program = T::create(operation_attributes, tensor_args, tensor_return_value);

        T::override_runtime_arguments(cached_program, operation_attributes, tensor_args, tensor_return_value);
    };
};

A compact real example is the experimental RGB-to-YUV op:

The weakness is obvious once you see it: create and the override must agree, slot by slot, on what argument args[0] is. If they drift apart, the op still works on the first call (a miss) and returns wrong data on the second (a hit). A test that calls an op only once will never catch this.

2. The descriptor factory: create_descriptor

The current tutorial steers new ops to a declarative style. The factory returns a ProgramDescriptor: plain data listing kernels, circular buffers and semaphores. The framework builds the Program from it with Program{desc} (mesh_device_operation_adapter.hpp:592):

tt-metal/tt_metal/api/tt-metalium/program_descriptors.hpp:221-228 @7aad8aac
struct ProgramDescriptor {
    using KernelDescriptors = ttsl::SmallVector<KernelDescriptor, 3>;
    using SemaphoreDescriptors = ttsl::SmallVector<SemaphoreDescriptor, 3>;
    using CBDescriptors = ttsl::SmallVector<CBDescriptor, 5>;

    KernelDescriptors kernels;
    SemaphoreDescriptors semaphores;
    CBDescriptors cbs;

Each KernelDescriptor carries a kernel_source (a file path or inline source code), core_ranges, compile_time_args, defines, per-core runtime_args and a config: Reader, Writer, generic DataMovement or Compute (program_descriptors.hpp:133-166). Runtime arguments may contain Buffer* entries instead of raw addresses. The framework records where those landed and, on a cache hit, patches them with the current addresses, so the op author never writes an override at all. That is the tutorial's selling point: "No manual buffer address patching — the framework auto-patches buffer addresses on cache hits" (docs/source/ttnn/ttnn/adding_new_ttnn_operation.rst:72).

ttnn.add's binary_ng op uses this flavour. Here is the compute kernel it declares:

This matters for the cache, as you will see. binary_ng still provides its own override_runtime_arguments even though it is a descriptor factory. The reason is in its hash, which we come to below.

This is the acquire/commit/wait/release handshake from A12. BINARY_OP is a macro, so one source file serves add, sub and mul. Activations get fused in through PROCESS_*_ACTIVATIONS, which expand to nothing here. The device operation's real work is choosing these defines.

Changing the dtype changes the kernel. A float32 ttnn.add in the same orb built eltwise_binary_sfpu_no_bcast instead. For ADD, is_binary_sfpu_op picks the SFPU when both inputs are FLOAT32 (binary_ng_device_operation.cpp:55-58), and resolve_fast_and_approximate_mode defaults to true so that bf16 add keeps the FPU (binary.cpp:922-925).

A TT-NN op is mostly a decision procedure: from shapes, dtypes, layouts and memory configs it chooses kernel files, defines, compile-time arguments, circular buffers and a core split. The arithmetic itself lives in a few short kernels that it reuses. To learn what an op really does, list what the JIT built under $TT_METAL_CACHE/.../kernels/.

The program cache: hit, miss, and patching

The cache itself is an ordinary hash map that belongs to the device:

tt-metal/tt_metal/api/tt-metalium/program_cache.hpp:144-170 @7aad8aac (trimmed)
struct ProgramCache {
    bool contains(const ProgramCacheKey& program_key) const { return this->cache_.contains(program_key); }
    CachedProgramFactory& get(const ProgramCacheKey& program_key) { return this->cache_.at(program_key); }
    void insert(const ProgramCacheKey& program_key, CachedProgramFactory&& program) { ... }
    void enable() { is_enabled_ = true; }
    void disable() { is_enabled_ = false; }
    ...
    std::size_t num_entries() const { return this->cache_.size(); }

private:
    bool is_enabled_ = true;
    bool allow_cache_misses_ = true;
    std::unordered_map<ProgramCacheKey, CachedProgramFactory, ProgramCacheKeyHasher> cache_;
};

It is enabled by default (is_enabled_ = true). Older tutorials call device.enable_program_cache() first, but at this commit that call is a no-op unless you disabled the cache earlier. The Python MeshDevice exposes enable_program_cache, disable_and_clear_program_cache, clear_program_cache and num_program_cache_entries (ttnn/core/distributed/distributed_nanobind.cpp:369-382, 516-517). allow_cache_misses_ is a guard: switch it off (set_program_cache_misses_allowed(False)) and any miss throws (device_operation.hpp:414-416). Model code does this around trace capture so that nothing gets compiled while a trace records (for example models/demos/k2_horizon_7b_qb2/tt/generator.py:654); tt-metal does not switch it off for you.

The key is a 64-bit hash plus an exact "canonical" string that resolves hash collisions (device_operation.hpp:404-413). By default the hash covers the op's type and everything reflection can see in both argument structs:

tt-metal/ttnn/api/ttnn/device_operation.hpp:76-86 @7aad8aac
    if constexpr (DeviceOperationWithCustomProgramCacheConcept<device_operation_t>) {
        ...
        return ttsl::hash::hash_objects_with_default_seed(
            ttsl::hash::type_hash<device_operation_t>,
            device_operation_t::compute_program_hash(operation_attributes, tensor_args));
    } else {
        ZoneScopedN("Compute default program hash");
        return ttsl::hash::hash_objects_with_default_seed(
            ttsl::hash::type_hash<device_operation_t>, operation_attributes, tensor_args);
    }

What does "a Tensor in tensor_args" contribute? Its reflected attributes are storage and tensor_spec (ttnn/api/ttnn/tensor/tensor.hpp:252-253), and both storage types expose an empty attribute list (storage.hpp:41-42, 203-204). So by default the key includes the shape, dtype, layout and memory config of every input, and never the buffer address. That is exactly the plate/paper line. Matmul uses this default; its header comments that it deliberately does not define a custom hash (matmul_device_operation.hpp:45-49).

binary_ng draws the line somewhere else. Its tensor_args_t defines its own to_hash, which the hasher uses in place of reflection:

tt-metal/ttnn/cpp/ttnn/operations/eltwise/binary_ng/device/binary_ng_device_operation.hpp:133-141 @7aad8aac
    struct tensor_args_t {
        const Tensor& input_tensor_a;
        std::optional<Tensor> input_tensor_b;
        std::optional<Tensor> output_tensor;

        // Operand dtypes, memory configs, Alignment, and Tile, plus each sharded operand's shape in
        // pages. Omits logical shape by design, so differently-shaped interleaved calls share one cache entry.
        ttsl::hash::hash_t to_hash() const;
    };

"Omits logical shape by design." An interleaved add of 32×32 and an add of 64×128 hit the same cached program. That is safe only because the shape-dependent quantities (tile count, how tiles split across cores, strides) are runtime arguments and not compile-time ones, and because the program's kernels already cover the whole worker grid. binary_ng therefore cannot rely on the framework's automatic address patching. It writes an override that re-runs the same argument builder its create_descriptor used:

tt-metal/ttnn/cpp/ttnn/operations/eltwise/binary_ng/device/binary_ng_program_factory.cpp:413-422 @7aad8aac
// SINGLE SOURCE OF TRUTH for binary_ng per-core runtime args.  Run by BOTH create_descriptor()
// (cache miss) and BinaryNgDeviceOperation::override_runtime_arguments() (cache hit).
//
// binary_ng's compute_program_hash intentionally EXCLUDES the tensor volume, so one cached program
// is shared across differently-shaped calls.  On a cache hit the descriptor is NOT rebuilt, so every
// shape/work-split-dependent per-core arg (c_start_id, per-core tile counts, strides, D/N/C/Ht/Wt,
// compute_tiles, freq/counter, packed scalar, ...) would otherwise stay frozen at the first-miss
// shape and corrupt results.  override_runtime_arguments() re-runs THIS builder for the current
// tensors and re-applies each arg every dispatch.

This answers the question from the imperative factories: how do you stop create and the override from drifting apart? Make them call the same function. The comment's warning is the general rule: anything left out of the key must be rewritten on every hit. Read it line by line. The add with a new shape did not add an entry, but the matmul with a new shape did. That is the to_hash comment, confirmed by experiment. New op type, dtype or output memory config each made a new entry. The 64×128 add wrote its output at a different address from the 32×32 one (0x2d6c40 against 0x2d5c40) and still matched torch to within bf16 rounding, so the override really did rewrite the addresses and tile counts. Misses cost 0.5–2 s here, almost all of it JIT compilation: the JIT reported 0 hits out of 34 builds. About 1.4 ms per call, or 12%, in that run (a rerun printed 11.38 / 13.85 / 11.69 ms, about 2.3 ms or 18%: host wall time under the simulator varies), and most of the 11 ms is ttsim simulating the cores. Do not read these as silicon numbers (A17, B01). On hardware the device time for one tile is microseconds, so the same host-side saving is a much larger share of the total. The telemetry line has a clean count, though. With the cache off, every call rebuilt its Program and asked the JIT for its three kernels again, each answered from an in-process dedup table. 303 = 3 × 100 calls with the cache off + 3 for the first call after re-enabling. A run with 20 calls per phase printed 63 = 3 × 20 + 3. The 200 cache-on calls asked for nothing.

The cache bug you will write. If your op reads something on the device that is not in the key and not rewritten on a hit, the first call is right and later calls are wrong. The classic case is a scalar baked in as a compile-time argument but left out of the hash. binary_ng's attributes list spells this out: "Runtime scalar/tolerance values are excluded; they are patched as runtime args" (binary_ng_device_operation.hpp:76). Always test an op by calling it at least twice, with different tensors and values.

Your own op, no C++: ttnn.generic_op

To build an op you normally write a device operation in C++ and rebuild TT-NN. There is a shortcut that needs no rebuild. ttnn.generic_op is a device operation whose "factory" just returns a ProgramDescriptor that you pass in from Python:

tt-metal/ttnn/cpp/ttnn/operations/generic/generic_op.hpp:13-25 @7aad8aac

// This includes: cb attributes, data movement attributes, compute attributes, rt args, compile time args.
// Unlike other operations, must create and pass in output tensor with the input tensors.
// See tests/ttnn/unit_tests/gtests/test_generic_op.cpp for some examples.
// The main use case right now is an interface for PyKernel to pass dynamic kernel paths.
...
// Convenience entry point for single ProgramDescriptor (SPMD mode)
Tensor generic_op(const std::vector<Tensor>& io_tensors, const tt::tt_metal::ProgramDescriptor& program_descriptor);

So I wrote one: sqdiff(a, b) = (a − b)², computed on a single core with an FPU subtract followed by an SFPU square on the same Dst tile. TT-NN has its own squared difference, so this op is only practice. The reader and compute kernels are inline C++ strings (SourceType.SOURCE_CODE), and the writer reuses a stock TT-NN kernel by path. Here is the heart of the compute kernel:

tenstorrent-from-zero/sim-labs/workbench/py/a19_sqdiff_generic.py (COMPUTE string)
    for (uint32_t i = 0; i < n_tiles; ++i) {
        cb_wait_front(0, 1); cb_wait_front(1, 1); cb_reserve_back(16, 1);
        tile_regs_acquire();
        sub_init(0, 1);
        sub_tiles(0, 1, 0, 0, 0);   // FPU: Dst[0] = a - b
        square_tile_init();
        square_tile(0);             // SFPU: Dst[0] = Dst[0]^2
        tile_regs_commit();
        tile_regs_wait();
        pack_tile(0, 16);
        tile_regs_release();
        cb_push_back(16, 1); cb_pop_front(0, 1); cb_pop_front(1, 1);
    }

And the Python that describes the program, one KernelDescriptor per kernel. This is the same structure binary_ng builds in C++:

I called it three times with new random tensors each time:

Every buffer moved between calls, yet there is one cache entry and every result matches torch. That is because generic_op's hash covers kernel sources, core ranges, compile-time arguments, defines and CB layout, but only the number of runtime arguments, not their values:

tt-metal/ttnn/cpp/ttnn/operations/generic/device/generic_op_device_operation.cpp:57-72 @7aad8aac

        return ttsl::hash::hash_objects_with_default_seed(
            kernel.kernel_source,
            kernel.source_type,
            kernel.core_ranges,

            kernel.named_compile_time_args,

On a hit, the descriptor adapter sees raw uint32_t runtime arguments that it cannot map back to buffers. So it takes its "slow path": it calls the factory again to get your new descriptor and copies only its runtime arguments into the cached Program (mesh_device_operation_adapter.hpp:758-762). Nothing is recompiled. The JIT cache directory shows two kernels named Kernel_Source_Code (the inline ones; they collapse into one name directory) and writer_unary_interleaved_start_id.

Two traps from writing this op. (1) The kernel APIs are mid-migration. The stock reader uses the newer Noc/DataflowBuffer objects while the compute side still uses cb_wait_front, and both compile at this commit. Pin examples to a commit. (2) The writer's first compile-time argument is the output CB index, so the CB and the arguments must agree (16 here). Get it wrong and the kernel waits forever on an empty CB.

The layers above: TT-MLIR, TT-XLA, TT-Forge

So far a person has written every op call. Real models arrive as PyTorch or JAX programs, and nobody wants to hand-translate a transformer into ttnn.* calls (A22 shows what that looks like when experts do it). The compiler stack above TT-NN does the translation automatically.

Provenance. Everything in this section comes from Tenstorrent's public documentation and READMEs, read on 2026-10-30. tt-mlir, tt-xla and tt-forge are separate repositories that are not pinned or built in this series, so none of it was run or checked against source here. The one link checked in source is TT-NN's side of it: ttnn.generic_op exists, and its header names PyKernel (a tt-mlir feature) as its main user.

Per the docs, the pieces are:

  • TT-Forge is the umbrella name: "Tenstorrent's end-to-end compiler stack. It consists of frontends (TT-XLA, TT-Forge-ONNX), a middle and backend compiler (TT-MLIR), and a cookbook ... (TT-Blacksmith)."
  • TT-XLA is the front end for PyTorch and JAX. It "ingests JAX models via jit compile and PyTorch models through torch-xla, providing StableHLO (SHLO) graphs to the TT-MLIR compiler", and plugs into both frameworks as a PJRT plugin, pjrt_plugin_tt.so, which bundles tt-mlir and tt-metal. From PyTorch you write torch.compile(model, backend="tt").
  • TT-Forge-ONNX is the front end for ONNX, TensorFlow and PaddlePaddle models.
  • TT-Torch, the earlier PyTorch 2.0 / torch-mlir front end, is deprecated. Its README now points to TT-XLA.
  • TT-MLIR is the compiler. Its main dialects (an MLIR dialect is a named family of IR operations) are ttir ("Named ops on tensors (akin to shlo, tosa, etc)"), ttnn ("models the tt-nn API ... as closely as possible"), d2m ("generic compute ... similar to linalg.generic, but with constructs that map well to the Tenstorrent execution model"), ttkernel ("intended to be a 1-1 mapping to tt-metalium kernels") and ttmetal (host-side buffer and program-enqueue operations).

There are two roads through TT-MLIR, and they correspond to the two halves of this chapter:

  1. The TT-NN road. TTIR is lowered to the ttnn dialect, where every op is a TT-NN call with a chosen layout, for example memref<2x4x!ttcore.tile<32x32, bf16>, #dram>, <interleaved>. The optimizer picks layouts and sharding, and the result is serialised to a .ttnn flatbuffer, "a compiled binary file intended to be loaded and executed by the TTNN backend runtime". At run time each op in that file becomes an ordinary TT-NN call, which enters device_operation::launch exactly as in Figure 2. The program cache, factories and kernels are the ones you just read.
  2. The direct-to-metal (D2M) road. TTIR is lowered to d2m.generic regions and then to ttkernel, so the compiler generates its own reader/compute/writer kernels instead of using TT-NN's hand-written ones. The ttnn.jit docs explain how this meets TT-NN: the D2M pipeline "wraps the generated kernels in ttnn.generic operations that contain the necessary host side program setup. Each ttnn.generic op requires a ProgramDescriptor." In other words, compiler-generated kernels enter tt-metal through the same generic_op door your sqdiff used. Its selling point is fusion: a @ttnn_jit.jit()-decorated chain like exp → neg → exp → add → multiply is compiled "into a single fused kernel" instead of five separate ops, each of which would write its intermediate tensor back to memory.
Figure 4. The compiler stack from a framework graph down to tt-metal kernels. Boxes with a green edge were exercised in this orb. Grey-edged boxes, and the IR excerpts shown for them, are quoted from the TT-MLIR, TT-XLA and TT-Forge docs and were not run here.
The stack has the same shape as the GPU world's. TT-XLA's PJRT plugin plays the role of the CUDA backend inside XLA, the ttnn dialect is like XLA calling into cuDNN and cuBLAS, and the D2M road is like Triton or XLA's own fusion emitter generating kernels. The difference is the bottom layer. On a GPU a generated kernel is one SIMT program. Here every generated op is still three or more cooperating kernels per core, joined by circular buffers.

Recap

  • A TT-NN op is a device operation: two argument structs (operation_attributes_t, tensor_args_t) and static functions (validate_on_program_cache_miss/hit, compute_output_specs, create_output_tensors, select_program_factory), handed to device_operation::launch.
  • launch checks inputs, allocates the output from its spec, hashes the arguments and looks up the program cache. On a miss it validates, selects a factory, builds a program, enqueues it (the JIT compiles here) and caches it. On a hit it validates, then only patches runtime arguments and enqueues.
  • Factories come in flavours: imperative create + override_runtime_arguments, declarative create_descriptor returning a ProgramDescriptor, Metal 2.0 create_program_artifacts, and mesh-workload factories. The docs recommend descriptors, while matmul and much of the tree already use Metal 2.0 specs.
  • The cache key is the plate/paper line: by default op type plus attributes plus each tensor's spec (shape, dtype, layout, memory config) and never addresses. binary_ng deliberately drops the shape, so one entry serves every interleaved shape, at the price of rewriting all per-core arguments on each hit.
  • To see what an op really ran, give it an empty TT_METAL_CACHE and read kernels/<name>/<hash>/, including defines_generated.h and kernel_includes.hpp.
  • ttnn.generic_op runs any ProgramDescriptor from Python: your own op, with the program cache, and no C++ rebuild.
  • Above TT-NN, per the docs: TT-XLA (PyTorch via torch-xla, and JAX, through PJRT) and TT-Forge-ONNX feed TT-MLIR. TT-MLIR either lowers to TT-NN calls (a .ttnn flatbuffer) or generates kernels directly (D2M), which reach the chip through ttnn.generic/generic_op.

Check yourself

You call ttnn.add on 32×32 tensors, then on 64×128 tensors, both bf16 interleaved in DRAM. How many program-cache entries are there, and what happens on the second call?

One. binary_ng's tensor_args_t::to_hash omits the logical shape, so the second call hashes to the same key and hits. On the hit, no factory runs and nothing is compiled. override_runtime_arguments re-runs the shared argument builder: the output now has 8 tiles instead of 1, split over 8 cores of the 8×8 grid, and the buffer addresses are new. The run in this chapter shows exactly that: entries=1 before and after, and the output at 0x2d6c40 instead of 0x2d5c40, correct to bf16 rounding.

Why does a 64×64 matmul after a 32×64 @ 64×32 matmul create a new entry, while add did not?

Matmul uses the default hash: type_hash plus reflected attributes plus reflected tensor_args, and a Tensor reflects its tensor_spec, which includes the shape. Matmul's program really does depend on shape (blocking, subblocks, grid, CB sizes), so it should not share programs across shapes. Add's program differs only in runtime arguments, so its authors could afford to drop the shape from the key.

An op author bakes a user-supplied scalar into the compute kernel as a #define but forgets to put it in operation_attributes_t's hashed fields. What symptom will users see?

The first call with each new set of shapes, dtypes and configs is correct. Every later call with a different scalar hits the cached program, which still has the old #define compiled in, so it silently computes with the old value. A test that calls the op once passes. The fix is either to include the scalar in the key, which costs a compile per value, or to pass it as a runtime argument and rewrite it on every hit, as binary_ng does with "runtime scalar/tolerance values".

The cold run took 1.96 s for the first add and 0.02 s for the first add in a second process. The program cache starts empty in both processes, so why the difference?

The program cache lives in memory and dies with the process, so the second process also missed and rebuilt the Program. But the expensive part of a miss is the JIT compilation of five RISC-V binaries (3 TRISC + NCRISC + BRISC), and that output is cached on disk under TT_METAL_CACHE, keyed by a hash of the kernel's source, defines and compile-time arguments. The second process found all of them ("34/34 hits"). Program building without compiling costs on the order of a millisecond.

In the generic_op run, the input and output addresses changed on every call, yet there was one cache entry and correct results. Which part of the key ignores the addresses, and who rewrote them?

generic_op's hash covers kernel source, core ranges, compile-time arguments, defines, config and CB layout, but for runtime arguments only runtime_args.size(). The addresses are runtime-argument values, so they do not change the key. On the hit, the descriptor adapter had no buffer bindings to patch, because the arguments were raw uint32_t, so it re-invoked the factory to get the new descriptor and applied its runtime arguments to the cached program, without rebuilding or recompiling.

A PyTorch model is compiled with torch.compile(model, backend="tt"). Name the artifacts on the TT-NN road from that call to a kernel running on a Tensix core.

Per the docs: torch-xla traces the model and hands a StableHLO module through TT-XLA's PJRT plugin. TT-MLIR converts it to TTIR, lowers it to the ttnn dialect with layouts chosen, and serialises a .ttnn flatbuffer. The runtime executes each op in it as a TT-NN call. From there it is this chapter, verified in the orb: device_operation::launch → cache key → factory → ProgramDescriptor/Program → JIT-compiled ELFs per RISC-V → enqueue → reader on NCRISC, compute on TRISC0–2, writer on BRISC.
