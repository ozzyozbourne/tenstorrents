The question

What is the least code that makes the chip compute 14 + 7?

On a CPU the answer is one line. On a GPU it is about a dozen: allocate device memory, copy the inputs over, launch a kernel, copy the result back. On a Tenstorrent chip the official answer is the add_2_integers_in_riscv programming example: a 135-line host file and a 57-line kernel. That sounds like a lot for one addition, but most of those lines are comments. Each remaining line answers a question the chip forces on you, because (as A09 showed) the chip has no caches and no shared address space. Nothing moves unless somebody moves it.

So before reading any code, list the questions a program must answer to add two numbers on a machine like that:

  1. Which chip? A host can see several.
  2. How does the host talk to it? Through a queue of commands, not by function calls.
  3. Where do the inputs live on the device? In DRAM, at addresses an allocator chooses.
  4. Where can a core actually touch them? Only in its own L1. A Tensix core cannot load from DRAM; it has to ask the NoC to copy the data into L1 first.
  5. What code runs, on which of the five RISC-V CPUs in the core?
  6. How does that code learn the addresses?
  7. How does the result get back?

Every line of the example answers one of these seven questions. The chapter goes through them in order, then runs the program, edits it, and breaks it in the simulator.

The shape of every Metalium program

Strip away the comments and the host side of any TT-Metalium program has the same five-beat rhythm:

  1. Open a device and get its command queue.
  2. Allocate buffers on the device.
  3. Describe a Program: which kernel source files run on which cores, with which arguments.
  4. Enqueue writes, the program, and reads onto the queue.
  5. Wait for the queue to drain, then close.

The kernel side is a C++ function called kernel_main(). It is compiled for one of the baby RISC-V cores from A04 and runs bare-metal: no OS, no malloc, no printf. It reads its arguments from a fixed spot in L1, moves data with the NoC, computes, and returns.

If you know CUDA, the mapping is close: MeshBuffer::create ≈ cudaMalloc, EnqueueWriteMeshBuffer ≈ cudaMemcpyAsync host→device, EnqueueMeshWorkload ≈ a kernel launch on a stream, Finish ≈ cudaStreamSynchronize. There are three differences. First, the kernel cannot dereference a DRAM pointer: it must copy the data into on-core SRAM itself. Second, you choose which core and which CPU inside that core runs your code, rather than launching a grid of anonymous threads. Third, kernels are compiled from source by a JIT on first use, like NVRTC, not ahead of time by nvcc.

The host↔device timeline

Before the line-by-line tour, look at what happens in time when you run the program. The figure uses wall-clock times I measured in this orb on the Wormhole simulator. Pick a scenario and press Play. The bars are drawn to scale against the 4-second axis.

The simulator section shows the measurements behind the figure. Three things to take from it:

  • The device work is tiny and constant. ttsim reports [4501] simulated clocks for this program in every scenario. (ttsim is a functional model, so those clocks are not a performance measure. They are steady because the device does exactly the same work each time.)
  • The first run is dominated by compilation on the host. With an empty cache, tt-metal compiles firmware for every RISC-V type plus a precompiled header (about 3 s here), then compiles your kernel (about 0.4 s). That is 3.8 s for a 4-byte add.
  • The cache makes the compile bars disappear. The second run hits 9/9 JIT cache entries and takes 0.36 s. Edit the kernel source and only your kernel's entry misses (8/9 hits, 0.75 s).
Kernels are compiled from source when the program is first enqueued, and the result is cached. A slow first run is the JIT, not your kernel.

The research notes (research/06-feasibility.md) recorded "1.08 s cold / 0.36 s warm" for this example. My kernel-only-cold runs took 0.74–0.76 s and my fully empty-cache runs took 3.75–3.92 s. The two sources disagree on the cold figure. The likely cause is that the earlier "cold" run had the firmware cached and only the kernel cold, but I could not confirm how that run was set up. The warm figures agree exactly. This chapter's JIT is a black box until A13, which opens up the build steps, the cache key and the kernel path search.

The host program, line by line

1. Which chip? create_unit_mesh

tt-metal/tt_metal/programming_examples/add_2_integers_in_riscv/add_2_integers_in_riscv.cpp:29-34 @7aad8aac

The current API has only one kind of device handle, the MeshDevice: a 2D grid of chips that you address as a single object. A single chip is a 1×1 mesh, which is what create_unit_mesh(device_id) builds. The older CreateDevice/EnqueueProgram API you may see in old blog posts has gone. Because one chip is just the smallest mesh, the same five-beat program scales to many chips (A21) without changing its shape.

The defaulted parameters show what "opening a device" decides: how much L1 to reserve for special regions, how many command queues to create (one by default), and which cores run the dispatch firmware. You can ignore all of them for now. Opening the device is also when firmware is built and loaded onto every core: RiscFirmwareInitializer::run_async_build_phase is profiled as "FW builds and Device Inits" (tt_metal/impl/device/firmware/risc_firmware_initializer.cpp:109-110). That is the big red bar in the timeline.

2. How does the host talk to it? The command queue

mesh_command_queue() returns the device's command queue. Every interaction with the device after this point (writing a buffer, running a program, reading a buffer) is a command pushed onto this queue, and commands execute in FIFO order. The example relies on that ordering: the comment at line 119 says "a read will not run before the prior kernel finishes". On real hardware in the default fast dispatch mode, the queue is a ring buffer that dispatch firmware running on reserved cores consumes. Under ttsim the workbench sets TT_METAL_SLOW_DISPATCH_MODE=1, and the host performs each command itself, synchronously. The program is written the same way in both modes. A17 explains what sits between "enqueue" and "a kernel starts".

3. Where do the inputs live? MeshBuffer and page size

A buffer is described by two small configs:

  • DeviceLocalBufferConfig says what the buffer looks like on each chip: where it lives (BufferType::DRAM or BufferType::L1) and its page size.
  • ReplicatedBufferConfig says how big it is. "Replicated" means every chip in the mesh gets a full copy. With a 1×1 mesh that is just one copy.

The page is the interleaving unit from A09. An interleaved buffer is cut into pages, and the pages are dealt round-robin across the banks: page 0 to bank 0, page 1 to bank 1, and so on. Real programs use one tile per page (32×32 bf16 = 2048 B). Here the whole buffer is one 4-byte integer, so it is a single page, and page 0 always lands in bank 0. The kernel's address generator computes bank_index = id − (id / NUM_DRAM_BANKS) · NUM_DRAM_BANKS, which is 0 for id 0 (tt_metal/hw/inc/internal/dataflow/dataflow_api_addrgen.h:20-43).

The program creates six buffers: three in DRAM (two inputs and one output) and three in L1 (scratch space on core (0,0)). The L1 buffers are needed because, as the comment at lines 48-50 says, "the Tensix core does not have direct access to DRAM". The host does not choose any addresses; the allocator does. I printed them from the kernel in the simulator (see below):

BufferTypeAddress chosen by the allocator (WH sim)

Two patterns are worth noticing. Each 4-byte buffer takes a 0x20 = 32-byte slot, because the allocator rounds sizes up to its alignment. And the L1 addresses count down from near the top of the 1.5 MB L1, while the DRAM ones count up. The allocator internals are a sidebar in A09. What matters here is that the kernel knows none of these addresses at compile time; somebody has to tell it.

4. Getting the inputs onto the device: EnqueueWriteMeshBuffer

The host vectors hold 14 and 7. EnqueueWriteMeshBuffer is a thin template (distributed.hpp:72-85) that checks the vector is at least as large as the buffer (a TT_FATAL otherwise) and calls mesh_cq.enqueue_write_mesh_buffer. blocking=false lets the host carry on while the copy is queued. That is safe because the queue is in order: the program that reads these buffers is enqueued later.

5. Describing the work: CreateProgram and CreateKernel

A Program is a container: "the main container that bundles kernels, circular buffers, and/or semaphores for execution on device" (host_api.hpp:101-111). Creating one does nothing on the device. It is a description that you fill in, then submit. CoreCoord{0,0} is a logical coordinate: the first Tensix worker, not NoC position (0,0). (A08 explained why logical and NoC coordinates differ.)

tt-metal/tt_metal/programming_examples/add_2_integers_in_riscv/add_2_integers_in_riscv.cpp:91-95 @7aad8aac

    core,
    DataMovementConfig{.processor = DataMovementProcessor::RISCV_0, .noc = NOC::RISCV_0_default});

CreateKernel takes four things:

  • A source path, not a binary. Nothing is compiled yet. OVERRIDE_KERNEL_PREFIX is set by tt_metal/programming_examples/CMakeLists.txt:8 to "tt_metal/programming_examples/", so the path the runtime actually searches for is tt_metal/programming_examples/add_2_integers_in_riscv/kernels/reader_writer_add_in_riscv.cpp. This matters when you overlay your own copy in the simulator section.
  • Where it runs. A CoreCoord, a CoreRange or a CoreRangeSet. One core here.
  • Which CPU inside the core, which is the job of the config type. DataMovementConfig means "one of the two data-movement RISC-Vs", and ComputeConfig means "the three TRISCs together" (A12).
  • Which NoC that CPU issues its transfers on.
tt-metal/tt_metal/api/tt-metalium/kernel_types.hpp:23-39 @7aad8aac
enum class DataMovementProcessor {
    RISCV_0 = 0,  // BRISC; Core DM0 on Quasar
    RISCV_1 = 1,  // NCRISC; Core DM1 on Quasar
    ...
};

enum NOC : uint8_t {
    RISCV_0_default = 0,
    RISCV_1_default = 1,
    NOC_0 = 0,
    NOC_1 = 1,
};

RISCV_0 is BRISC and RISCV_1 is NCRISC, the two data-movement cores from A04. NOC::RISCV_0_default is just another name for NoC 0. The processor and the NoC are independent choices. By convention a reader kernel runs on RISCV_0/NoC0 and a writer on RISCV_1/NoC1, so the two traffic streams use the two opposite tori from A08. This example does both reading and writing from one kernel on BRISC/NoC0, which is fine for 12 bytes of traffic.

The rest of DataMovementConfig (kernel_types.hpp:65-85) holds compile_args, named_compile_args, defines and opt_level (default O2). All of these change the generated binary, which leads to the next question.

Runtime args vs compile-time args

tt-metal/tt_metal/programming_examples/add_2_integers_in_riscv/add_2_integers_in_riscv.cpp:98-109 @7aad8aac
SetRuntimeArgs(
    program,
    kernel_id,
    core,
    {
        static_cast<uint32_t>(src0_dram_buffer->address()),
        static_cast<uint32_t>(src1_dram_buffer->address()),
        static_cast<uint32_t>(dst_dram_buffer->address()),
        static_cast<uint32_t>(src0_l1_buffer->address()),
        static_cast<uint32_t>(src1_l1_buffer->address()),
        static_cast<uint32_t>(dst_l1_buffer->address()),
    });

The kernel learns the six allocator-chosen addresses through runtime arguments: a list of 32-bit words per (kernel, core) pair. At launch they are written into the kernel-config region of that core's L1. The kernel reads word i with get_arg_val<uint32_t>(i), which is literally a load from a fixed L1 address (shown below). The number of args is bounded by that L1 space; get_arg_val's doc gives the valid index range as 0 to 341 (dataflow_api.h:135-146). There is also SetCommonRuntimeArgs/get_common_arg_val for words shared by every core running the kernel (host_api.hpp:416).

The alternative is compile-time arguments: DataMovementConfig{.compile_args = {...}}, read in the kernel with get_compile_time_arg_val(i) (tt_metal/hw/inc/api/compile_time_args.h:64). These are baked into the binary: the JIT passes them as -DKERNEL_COMPILE_TIME_ARGS=… (tt_metal/jit_build/build.cpp:1229), so the compiler can constant-fold them, unroll loops by them, and size arrays with them. The price is that a new value means a new binary. The header comment on defines says it directly: "Each unique combination of defines will produce a unique compiled instantiation" (kernel_types.hpp:70-72), and compile args behave the same way.

Runtime argsCompile-time args
Host APISetRuntimeArgs, SetCommonRuntimeArgs.compile_args, .named_compile_args, .defines
Kernel APIget_arg_val<T>(i)get_compile_time_arg_val(i) (a constexpr)
Lives inL1, written at each launchThe instruction stream itself
Changing it costsA few words of L1 writeA JIT compile (the orange bar), then a cache entry
Typical contentsBuffer addresses, tile counts, start offsets per corePage sizes, tile formats, loop bounds, CB indices, booleans that select code paths
Rule of thumb: things that change between runs or between cores (addresses and counts) are runtime args. Things that shape the code (layouts, sizes, formats, flags) are compile-time args. Buffer addresses are the canonical runtime arg, because the allocator may give a different address on every run.
Putting a buffer address in a compile-time arg works on the first run and then silently recompiles every time the allocator moves the buffer. Worse, if the address happens to stay the same, a stale assumption can survive for weeks. Addresses go in runtime args.

6. Submitting: MeshWorkload, EnqueueMeshWorkload, Finish

tt-metal/tt_metal/programming_examples/add_2_integers_in_riscv/add_2_integers_in_riscv.cpp:113-114 @7aad8aac
workload.add_program(device_range, std::move(program));
distributed::EnqueueMeshWorkload(cq, workload, /*blocking=*/false);

A MeshWorkload maps programs onto regions of the mesh. device_range covers the whole mesh (MeshCoordinateRange(mesh_device->shape())), which here is the single chip at (0,0). On a bigger mesh you could put different programs on different chips in one workload. The program is moved in, because the workload now owns it.

EnqueueMeshWorkload is where the orange JIT bar happens. In fast-dispatch mode it compiles the workload, loads the binaries and generates dispatch commands before enqueueing. In slow-dispatch mode the comment says it "normally JIT-compiles inside LaunchProgram":

tt-metal/tt_metal/distributed/distributed.cpp:127-138 @7aad8aac
if (env.get_rtoptions().get_fast_dispatch() && !emulated) {
    mesh_workload.impl().compile(mesh_cq.device());
    mesh_workload.impl().load_binaries(mesh_cq);
    mesh_workload.impl().generate_dispatch_commands(mesh_cq);
} else if (...Mock) {
    // Slow dispatch normally JIT-compiles inside LaunchProgram, ...
    mesh_workload.impl().compile(mesh_cq.device());
}
mesh_cq.enqueue_mesh_workload(mesh_workload, blocking);

Either way, the first time a given kernel source and config is enqueued, it is compiled. Finish(cq) (distributed.hpp:128) blocks until everything on the queue has completed. This example does not call Finish, because its next step is a blocking read, which waits for everything ahead of it in FIFO order. The hello-world examples have no read, so they call Finish explicitly.

The kernel, line by line

Now switch to the device side. This file is compiled for BRISC and runs exactly once, on core (0,0).

kernel_main() is the entry point for every kind of kernel (data movement and compute alike). The firmware already running on BRISC calls it when the launch message arrives and goes back to waiting when it returns.

get_arg_val is all there is to argument passing:

tt-metal/tt_metal/hw/inc/api/dataflow/dataflow_api.h:147-152 @7aad8aac
template <typename T>
FORCE_INLINE T get_arg_val(int arg_idx) {
    // only 4B args are supported (eg int32, uint32)
    static_assert("Error: only 4B args are supported" && sizeof(T) == 4);
    return *((tt_l1_ptr T*)(get_arg_addr(arg_idx)));
}

It is one load from L1. There is no marshalling and no type information: argument 3 is "the L1 address of src0" only because the host put that word in position 3. Get the order wrong and the kernel happily reads from the wrong place.

InterleavedAddrGen<true> (true = DRAM) is a tiny struct that turns "page id of this interleaved buffer" into a 64-bit NoC address:

tt-metal/tt_metal/hw/inc/internal/dataflow/dataflow_api_addrgen.h:281-304 @7aad8aac
struct InterleavedAddrGen {
    static constexpr bool is_dram = DRAM;
    uint32_t bank_base_address;  // Base address for the whole tensor.
    const uint32_t page_size;    // Num bytes in page.
    ...
    std::uint64_t get_noc_addr(const uint32_t id, const uintptr_t offset = 0, uint8_t noc = noc_index) const {
        uint32_t bank_offset_index = interleaved_addr_gen::get_bank_offset_index<DRAM>(id);
        uint32_t bank_index = interleaved_addr_gen::get_bank_index<DRAM>(id, bank_offset_index);
        uint32_t addr = this->get_addr(id, bank_offset_index, bank_index, offset);
        return noc_address_backend::bank_address<DRAM>(bank_index, addr, noc);
    }
};

This is A09's interleaving written as code. Page id goes to bank id mod N, at row id / N within that bank. The 32-bit buffer address becomes the low part of the NoC address, and the high bits name which DRAM endpoint to talk to. For src0 the simulator printed noc addr src0=0x2c00002d4c40: the low bits are the buffer address 0x2d4c40, and the high bits 0x2c0… encode the NoC coordinates of the DRAM endpoint that serves bank 0. (A11 decodes the format.) As the source comment warns, "the parameters here must match the parameters used in the host code": if the page size here differs from the host's page_size, every page after the first is read from the wrong offset within its bank. This is the older address-generator style. Modern kernels use TensorAccessor, which gets these parameters from compile-time args so they cannot drift. A11 covers it.

tt-metal/tt_metal/programming_examples/add_2_integers_in_riscv/kernels/reader_writer_add_in_riscv.cpp:30-43 @7aad8aac

uint32_t* dat1 = (uint32_t*)src1_l1;

(*out0) = (*dat0) + (*dat1);

noc_async_read(src_noc_addr, dst_l1_addr, size) asks this core's NoC interface to fetch size bytes from a remote NoC address into local L1. It is asynchronous: the call programs a command into the NoC hardware and returns immediately, before any byte has moved. That is why both reads can be in flight at once. noc_async_read_barrier() spins until every read this core has issued has completed. Only after the barrier may you touch src0_l1 and src1_l1.

Treat both calls as a black box for now: "start a copy" and "wait for all my copies". A11 opens it up: how the barrier knows the reads are done (a counter of acknowledged transactions), the write-side variants, and alignment rules. One alignment rule already applies here: the low bits of the source and destination addresses must match. Reading into src0_l1 + 4 makes ttsim stop with UndefinedBehavior: … alignment of src_addr=0x2d4c40 and dst_addr=0x16dfe4 does not match (recorded in research/06-feasibility.md). Lab B05 reproduces it.

After the barrier, the add is ordinary C on ordinary pointers. L1 is plain memory to the RISC-V, so *dat0 is an lw instruction. This is the core's only "compute" in the whole program, and it runs on a data-movement CPU, not on the matrix or vector engines. The host comment says why: "Data Movement cores are … still fully capable of performing simple arithmetic operations like addition. Just slower." A12 does it properly on the FPU.

Where each value lives

Here is the whole program as a sequence of places. Step through it and watch the three numbers. The addresses are the ones the allocator actually chose in the simulator run.

Count the hops: each input crosses three memories (host RAM → DRAM → L1 → register) and the output crosses three on the way back. On a CPU the caches would do this for you, invisibly. Here, every arrow in the figure is a line of code someone wrote. That is the price of having no caches, and also the source of control: A15 and A16 are about choosing these arrows carefully enough that the compute engines never wait for them.

A GPU kernel would write c[0] = a[0] + b[0] on global-memory pointers. The DRAM→register path still exists there, but the load/store unit and the cache hierarchy run it. On Tensix the DRAM→L1 step is an explicit DMA that you issue and wait on. A GPU's closest equivalent is cp.async into shared memory followed by a wait, which you only reach for when you are tuning.

The store that has not landed yet

Why does the kernel load from dst_l1 and throw the value away? Because of two facts about the baby RISC-V cores, both from the ISA documentation:

  1. A store can retire before it reaches memory. The load/store unit has "a four-entry store queue and an eight-entry retire-order queue", and "stores can retire before their write-request makes it into the memory subsystem" (tt-isa-documentation/WormholeB0/TensixTile/BabyRISCV/MemoryOrdering.md @be83310).
  2. fence does nothing. "The RISCV fence instruction is treated as a no-op by the baby RISCV cores, so it cannot be used to enforce stronger ordering" (same file).

Meanwhile, noc_async_write works by storing a command into the NoC's registers, after which the NoC reads dst_l1 by itself. The RISC-V and the NoC are separate clients of L1. So the danger is that the NoC command reaches the NoC and the NoC reads L1 before the sw of 21 has been processed. The NoC would then ship the stale old value to DRAM. Step through both versions:

Here is how load_blocking achieves the right-hand ordering:

tt-metal/tt_metal/tt-llk/tt_llk_wormhole_b0/common/inc/ckernel.h:155-183 @7aad8aac
// important note: FENCE on Wormhole is a NOP
//
// this code provides a blocking load by doing the following:
// - issue a LOAD transaction to the address
// - issue an instruction that requires the data from the LOAD transaction
//     - block the pipeline until the LOAD transaction completes
// - memory clobber
...
asm volatile(
    "lw %[raw], (%[ptr])\n\t"
    "and %[raw], %[raw], %[raw]"
    : [raw] "=r"(raw)
    : [ptr] "r"(ptr)
    : "memory");

This is a recipe straight out of MemoryOrdering.md. A store followed by a load from exactly the same address is emitted and processed in order, and an instruction that consumes the loaded register cannot enter the integer unit until the load's response arrives. So by the time the next instruction (the store that programs the NoC) issues, the store of 21 has been processed. The "memory" clobber stops the compiler from moving memory operations across it.

The simulator will not catch you here. I commented out the load_blocking line in an overlay copy and ran it three times on ttsim: each time Success: Result is 21, at [4497] clocks. ttsim is a functional model and does not reproduce the store-queue timing that makes this race real on silicon. Passing in the simulator is not proof that a kernel's memory ordering is correct. B05 covers which bugs hide in ttsim. The general rule: whenever a RISC-V writes data with ordinary stores and then hands that data to another agent (the NoC, or by pushing a CB), make the store land first.

DPRINT: your first tool

You may have noticed a line in the kernel that the walkthrough skipped: DPRINT("Adding integers: {} + {}\n", *dat0, *dat1);. A kernel has no terminal. DPRINT gives it one. Each RISC-V writes formatted records into a small buffer in its own L1, and a host-side print server polls those buffers and prints the records with a prefix that says where they came from.

The two hello-world examples are the cleanest demonstration. The data-movement one creates the same kernel source twice on core (0,0), once on each data-movement CPU:

TR0 is TRISC0 (UNPACK), TR1 is TRISC1 (MATH) and TR2 is TRISC2 (PACK). Each line only exists in one of the three binaries, so one source produced three programs. The JIT cache stats are consistent with this: the add example (one BRISC binary), the data-movement hello-world (BRISC and NCRISC) and the compute hello-world (three TRISCs) reported 9, 10 and 11 cache entries respectively.

Print order is not execution order. On a second run the same compute example printed TR1, TR2, TR0 instead of TR1, TR0, TR2, even though ttsim is deterministic and the device ran the same instructions. The host print server polls each RISC's buffer in turn, so lines from different RISCs interleave in whatever order it happens to drain them. Within one RISC, order is preserved. To reason about cross-core ordering, print a counter or a value, not the line order.

Rules from docs/source/tt-metalium/tools/device_print.rst that you will hit in practice:

  • Enable with TT_METAL_DPRINT_CORES (lines 17-24): 0,0, a list (x1,y1),(x2,y2), a range, all, worker or dispatch. The coordinates are logical. The doc says that whether this variable is defined "determines whether printing is enabled during kernel compilation", so DPRINT changes how kernels are built, not just what the host shows. TT_METAL_DPRINT_RISCVS=BR restricts printing to some RISCs (line 29), and TT_METAL_DPRINT_FILE sends output to a file (line 30).
  • Every format string must end in \n (lines 37-45). The server flushes a RISC's buffer only on a newline, and "any tail still buffered at device detach is dropped". If your print never appears, this is the most common cause.
  • fmt-style formatting (lines 64-68): {}, {:x}, {:.5f}, and bf16 values via bf16_t.
  • Tiles can be printed from circular buffers with TSLICE/TileSlice (lines 130-192). That is useful from A11 onwards, and lab B06 uses it to watch CB pointers.
DPRINT is not free. Under ttsim the add example rose from [4501] to between [5944] and [6115] simulated clocks with DPRINT on, varying from run to run (the research notes recorded 6611 on another run; the count depends on host polling). On silicon it adds real time and L1 traffic. Leave it off when measuring.

Recap

  • Every Metalium host program has five beats: open (MeshDevice::create_unit_mesh, where one chip is a 1×1 mesh), allocate (MeshBuffer::create with a DRAM or L1 DeviceLocalBufferConfig and a page size), describe (CreateProgram, CreateKernel, SetRuntimeArgs), enqueue (writes, EnqueueMeshWorkload, reads) on an in-order command queue, and wait (Finish or a blocking read).
  • CreateKernel takes a source path, a set of cores and a config. DataMovementConfig{RISCV_0, NOC_0} picks BRISC on NoC 0. The processor and the NoC are independent choices.
  • Runtime args are 32-bit words in L1, read with get_arg_val. Compile-time args are baked into the binary. Addresses and counts go at runtime; layouts and sizes go at compile time.
  • A kernel cannot touch DRAM. It asks the NoC to copy pages into L1 (noc_async_read), waits (noc_async_read_barrier), computes, and copies back. InterleavedAddrGen turns a page index into a bank plus a 64-bit NoC address.
  • Baby RISC-V stores can retire before they land, and fence is a no-op. Before handing data the CPU stored to the NoC, force it into L1 with load_blocking. ttsim will not catch you if you forget.
  • Kernels are JIT-compiled on first enqueue and cached by content. The first run (3.8 s) is almost all compilation; a warm rerun takes 0.36 s, and the device work (4501 sim clocks) never changes.
  • DPRINT, enabled with TT_METAL_DPRINT_CORES, prints per-RISC with prefixes BR, NC, TR0, TR1 and TR2. Each line must end in \n, and lines from different RISCs can interleave in any order.

Next, A11 opens the noc_async_* black box and replaces the six hand-placed L1 buffers with circular buffers, the mechanism that lets a reader core and a compute core agree that a tile is ready without sharing a single variable.

Check yourself

The example allocates three L1 buffers in addition to the three DRAM buffers. Why can't the kernel add the DRAM values directly?

A Tensix RISC-V has no load path to DRAM. Its loads and stores reach only its own L1 (and some local registers). DRAM is reachable only through the NoC, as an asynchronous copy into L1. So each input must first be copied to an L1 buffer, and the result must be stored in L1 before the NoC can copy it out. That is why there is one L1 buffer for each DRAM buffer.

You grow the DRAM buffers to 2048 bytes and set page_size = 2048 on the host, but leave the kernel's InterleavedAddrGen at sizeof(uint32_t). Does anything break for this example? When would it?

(You do have to grow the buffer too: a 4-byte buffer with a 2048-byte page fails at creation with TT_FATAL, because an interleaved buffer's size must be divisible by its page size, tt_metal/impl/buffers/buffer.cpp:285-290.) For this example, probably not: the kernel only reads page 0, which lands in bank 0 at the buffer's base address whatever the page size. It breaks as soon as the kernel reads more than one page. The kernel computes bank and offset from its own page_size, so page 1 and later would be fetched from the wrong offsets. This is why the source comment says the parameters "must match", and why TensorAccessor (A11) derives them from the buffer through compile-time args.

You want to run the same kernel on 64 cores, each processing a different slice of a tensor. Which values go in compile-time args and which in runtime args?

Each core's start tile index and tile count differ per core, and the buffer addresses can change between runs, so those are runtime args (SetRuntimeArgs per core, or SetCommonRuntimeArgs for the addresses if they are shared). The page/tile size, the data format and any flags that select code paths are the same everywhere and shape the code, so they are compile-time args. Then all 64 cores share a single compiled binary.

Why is the second run of the example about ten times faster than the first, when the simulated clock count is identical?

The clock count measures the device work, which is the same: write, launch, run, read. The difference is on the host. The first run JIT-compiles firmware for every RISC-V type plus a precompiled header at device open (about 3 s here), then compiles the kernel on first enqueue (about 0.4 s). Both results go into the JIT cache keyed by content, so the second run gets 9/9 hits and skips compilation entirely.

A colleague removes the load_blocking line, runs on ttsim, sees "Success: Result is 21", and concludes the line is unnecessary. What is wrong with that reasoning?

ttsim is a functional model. It does not reproduce the baby RISC-V store queue, where a store can retire before its write reaches L1, or the timing between the RISC-V and the NoC as separate L1 clients. On silicon, noc_async_write programs the NoC with stores to a different memory region, and these can overtake the pending L1 store, so the NoC can read the stale value. And because fence is a no-op, there is no cheaper fix. The test passing in a model without the hazard says nothing about hardware that has it.

The compute hello-world prints three lines with TR0, TR1 and TR2, but the source contains a single kernel_main. How?

A compute kernel is compiled three times, once for each TRISC (UNPACK, MATH and PACK), with a different define each time. DPRINT_UNPACK, DPRINT_MATH and DPRINT_PACK each expand to a real print on only one of those builds and to nothing on the other two. So each TRISC runs its own binary and prints its own line. A12 builds on this "one source, three CPUs" idea.
