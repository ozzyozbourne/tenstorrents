The question

In A10 one line launched the kernel:

distributed::EnqueueMeshWorkload(cq, workload, /*blocking=*/false);

A few microseconds later on silicon, the BRISC on core (0,0) is running kernel_main. But that BRISC has no idea what a "workload" is. It sits in a loop in its firmware and checks one byte of its own L1 over and over. Somebody has to put a program into its L1, put six argument words next to it, describe the circular buffers, and then flip that byte. Afterwards, somebody has to notice that the kernel has finished.

What actually happens between EnqueueMeshWorkload and a kernel starting? And who is "somebody"?

There are two answers, and tt-metal implements both. In slow dispatch the host CPU does every step itself, one PCIe transaction at a time. In fast dispatch the host writes a compact list of commands into its own memory, and two Tensix cores on the chip, running firmware called the prefetcher and the dispatcher, fetch those commands and carry them out. This chapter takes both apart. Every count of PCIe transactions below was measured in the simulator with an instrumented copy of ttsim.

What a launch has to deliver

Start from the worker's side, because that fixes what any dispatch scheme must do. Here is the loop the BRISC firmware spins in between kernels:

The core polls a go message in a mailbox area of its L1. The go message is four bytes, and the last byte, signal, is the one that matters:

struct go_msg_t {
    union {
        uint32_t all;

            uint8_t dispatch_message_offset;

    };

When signal becomes RUN_MSG_GO (0x80), the firmware reads the launch message next to it. The launch message is a kernel_config_msg_t (dev_msgs.h:166-196). It says where the kernel-config region is, where each processor's runtime args start (rta_offset), where each binary's text sits (kernel_text_offset), which circular-buffer slots are in use (local_cb_mask), which processors are enabled (enables), and a mode byte that says who launched it: the host or the dispatcher. So a launch has to deliver five things, and then detect a sixth:

  1. The binaries, written into the core's L1 kernel-config region.
  2. The runtime args (and common runtime args), at the offsets the launch message names.
  3. The circular-buffer configs: address, size, page count and page size for each CB, and the semaphore initial values.
  4. The launch message.
  5. The go message, last, because flipping it is what starts the core.
  6. Done. When the kernel returns, the firmware sets signal = RUN_MSG_DONE. If a dispatcher launched it (mode == DISPATCH_MODE_DEV), the firmware also sends a NoC increment to that dispatcher's semaphore, using master_x/master_y from the go message to find it (brisc.cc:600-616).

That last detail is the seed of everything in this chapter. A worker can report "done" in two ways: by changing a byte that somebody reads, or by pushing a message to somebody. The first way is cheap only if the reader is close by.

How the host reaches a core: BARs and TLB windows

Before comparing the two schemes, we need to know how the host writes a byte into the L1 of core (0,0) at all. The chip is a PCIe device. Linux exposes its memory-mapped regions, its BARs (base address registers), and Tenstorrent's kernel driver, tt-kmd, lets user space mmap them through /dev/tenstorrent/N. UMD, the user-mode driver that tt-metal links, does exactly that (tt-umd/src/pcie/pci_device.cpp:481-487). On Wormhole, BAR0 is 512 MiB.

But the chip's address space is not flat. Every NoC address is a tile coordinate (x, y) plus a 36-bit address inside that tile (A08). The host's loads and stores, though, carry only a linear offset into BAR0. The bridge between the two is a set of TLB windows in the PCIe tile. Each window is a slice of BAR0 that you point at an aligned region of one tile's address space by writing a 64-bit configuration register. The ISA documentation describes the layout:

There are 186 configurable TLB windows, which collectively occupy the low 496 MiB of bar 0. The first 156 windows are each 1 MiB in size, the next 10 windows are each 2 MiB in size, and the final 20 windows are each 16 MiB in size. … The final 16 MiB window is reserved for use by the kernel driver. (WormholeB0/PCIExpressTile/TLBs.md)

The configuration array starts at BAR0 offset 0x1FC0_0000. In each 64-bit entry, the low N bits are local_offset, the high bits of the 36-bit target address (N = 16, 15 or 12 for 1, 2 or 16 MiB windows). The next fields are x_end, y_end, x_start and y_start (6 bits each), then noc_sel, mcast and a 2-bit ordering mode. UMD has the same numbers (wormhole_implementation.hpp:40-51, 196-205), and so does ttsim, which shows the translation as code:

Two consequences follow. First, a window can point at only one tile (or one multicast rectangle of Tensix tiles) at a time. UMD keeps a few windows pinned to fixed targets and reprograms a shared 16 MiB window whenever it needs a new destination. In ttsim, UMD routes almost all of its writes through window 166, so a write to a new tile costs one or more config writes first. Second, the PCIe tile treats host writes and host reads very differently. A write is posted: the CPU sends it and moves on. A read is a round trip: the request crosses PCIe and then the NoC, and the CPU stalls until the data comes back. The ISA documentation measured this on one Zen 5 desktop. A host memcpy to device L1 ran at 22.65 GB/s through a write-combining, posted-writes TLB. A memcpy from device L1 ran at 0.10 GB/s, with a latency of at least 671 ns (PCIExpressTile/README.md, Performance). The page's own conclusion is blunt: "For retrieving data from the device, none of the host-initiated operations are particularly good for throughput. Software is encouraged to use device-initiated operations instead."

Host writes to the device are cheap and posted. Host reads from the device are slow round trips. A good dispatch scheme lets the host write and lets the device do all the reading, including reading the host's own memory.

The device can do that. The PCIe tile's NoC address space has a 3.999 GiB window at NoC address 0x8_0000_0000, which goes through an outbound iATU to host memory (same README, "NoC to Host"). The memory has to be pinned so that it cannot move. UMD allocates 1 GiB hugepages (tt-umd/src/hugepage.cpp:29 uses /dev/hugepages-1G) and asks the kernel driver to pin each one. The driver returns both a physical address and the NoC address at which the chip can reach it (tt_pin_pages(…, &physical_address, &noc_address), pci_device.cpp:684). Measured from a Tensix core in the PCIe tile's row, device-initiated reads of host memory ran at 24.5 GB/s, and device-initiated writes at 26.4 GB/s.

In ttsim there is no kernel driver and no real hugepage. UMD's TTSimTTDevice reads the BAR addresses out of the simulated PCI config space (tt_sim_tt_device.cpp:166-186). Logical core (0,0) appears as translated (18,18). Around these 41 data writes the host made 405 writes to TLB configuration registers, so the launch cost 446 BAR writes. It also made 364 BAR reads, almost all of them polls of address 0x4a0. Per launch, slow dispatch is 446 posted writes and 364 round-trip reads, every one of them issued by the host CPU while it does nothing else.

A GPU driver never polls a kernel's completion with MMIO reads in a loop. It writes commands into a ring buffer in host memory, rings a doorbell register, and the GPU's command processor fetches the commands and later writes a fence value back into host memory. Slow dispatch is what you get without a command processor. Fast dispatch, below, builds one out of two ordinary Tensix cores.

Fast dispatch: the chip feeds itself

Fast dispatch is the default. It turns the problem around. The host never addresses the workers. It describes the work as a stream of command packets and writes that stream into a ring buffer in its own pinned memory, the issue queue. On the chip, a core running cq_prefetch pulls the packets across PCIe, and a core running cq_dispatch executes them: writes, multicasts, "send the go signal", "wait for the workers". Results and completion records come back into a second ring in host memory, the completion queue, which the host reads with ordinary loads from its own RAM. Toggle the two modes and step through. The counters are the per-launch numbers I measured.

Put the two modes side by side and the difference is not the amount of data. Fast dispatch actually moves more bytes than slow dispatch's data writes (about 1.2 KB against 748 B per launch), because commands carry headers. The difference is who waits for whom. In slow dispatch the host stalls on 364 round trips. In fast dispatch the host's only device traffic is seven posted writes. Everything that must wait, such as "is the worker done?" or "has the command arrived?", waits on the chip, where the round trip is a few hundred nanoseconds of NoC rather than a trip across PCIe and back.

Fast dispatch has a simple shape. The host writes commands into its own memory and rings a doorbell. The chip pulls the commands, executes them with NoC writes, collects "done" signals as NoC semaphore increments, and pushes completions back into host memory. The host never reads the device to make progress.

Here is the doorbell itself. Note the stall bit, which trace will use later:

PREFETCH_Q_LOG_MINSIZE is 4 (dispatch_settings.hpp:106), so an entry holds the command size in 16-byte units. That is why the captured doorbell above wrote 0x6 for a 96-byte command. The sfence comes first so that the command bytes in host memory are visible before the prefetcher is told about them. The window was created once, pinned to the prefetcher core (create_io_window, system_memory_manager.cpp:266-270), so ringing the doorbell needs no TLB reprogramming. The fast-dispatch launches I measured made zero TLB-config writes.

The host's wait loop for the completion queue reads a pointer in host memory and, tellingly, contains a hook for the simulator:

On silicon the chip runs on its own clock while the host spins on its own memory. ttsim advances only when somebody calls libttsim_clock. In slow dispatch UMD clocks it once per device read (after_read, tt_sim_tt_device.cpp:334-338). Fast dispatch makes no device reads while it waits, so tt-metal has to clock the simulator explicitly. B01 shows how that changes the clock count.

How big are the two rings? Each command queue gets a region of the hugepage. A quarter of it, rounded down to 4 KiB pages, is the completion queue, and the rest is the issue queue (system_memory_cq_interface.cpp:15-18). Both are circular, with a toggle bit that flips on every wrap, so a reader can tell a full ring from an empty one. The read and write pointers count in 16-byte units.

Inside the prefetcher and the dispatcher

The two firmware kernels are ordinary data-movement kernels, compiled by the same JIT as yours. In the simulator's cache they appear as kernels/cq_prefetch/…/brisc and kernels/cq_dispatch/…/brisc, plus a cq_dispatch_subordinate built for NCRISC (and a cq_dispatch_subordinate_compute built for the three TRISCs). Their header comments are the best summary there is:

tt-metal/tt_metal/impl/dispatch/kernels/cq_prefetch.cpp:5-10 @7aad8aac
// Prefetch kernel
//  - 3 flavors: _hd (host and dram), _h (host only), _d (DRAM only)
//  - fetches commands from host (if applicable), executes
//  - uses HostQ for host handshaking, ComDatQ for commands (from host),
//    double buffered ScratchBuf for out of band data (e.g., from DRAM)
//  - syncs w/ dispatcher via 2 semaphores, page_ready, page_done
tt-metal/tt_metal/impl/dispatch/kernels/cq_dispatch.cpp:5-11 @7aad8aac
// Dispatch kernel
//  - receives data in pages from prefetch kernel into the dispatch buffer ring buffer
//  - processes commands with embedded data from the dispatch buffer to write/sync/etc w/ destination
//  - sync w/ prefetcher is via 2 semaphores, page_ready, page_done
//  - page size must be a power of 2
//  - # blocks must evenly divide the dispatch buffer size
//  - dispatch buffer base must be page size aligned

The two "flavors" exist for multi-chip systems. A chip that is not wired to PCIe (the second ASIC of an n300, for instance) cannot read host memory itself, so an _h prefetcher on the chip with the PCIe link forwards its commands to a _d prefetcher on the remote chip over Ethernet. A single PCIe-attached chip, like ours, runs the combined _hd flavor. The command vocabulary is small and readable:

Read a program launch as a sentence in this language. Prefetcher commands say where the bytes come from: inline from the issue queue, or relayed from DRAM pages. Dispatcher commands say what to do with them: WRITE_PACKED for runtime args (one header, many destinations), WRITE_PACKED_LARGE for the binaries and kernel config, which can be multicast to rectangles of cores (program/dispatch.cpp:1942-1957 pairs a WRITE_PACKED_LARGE of program binaries with a prefetcher RELAY_PAGED_PACKED from DRAM, or RELAY_RINGBUFFER when the prefetcher cache is in use). Then SEND_GO_SIGNAL, and a WAIT before anything that depends on the result. This is also why A16's multicast matters beyond kernels: the dispatcher sends one config payload to 64 cores with one multicast, where slow dispatch would make 64 separate trips.

Two layers of flow control keep the pipeline honest. The host must not overrun the fetch queue, so fetch_queue_reserve_back rereads the prefetcher's read pointer when it runs out of entries. That is a BAR read, but only when the queue is full (system_memory_manager.cpp:705-724). The prefetcher must not overrun the dispatcher's ring, which is what the page_ready/page_done semaphores are for. And the dispatcher must not reuse a worker's launch-message slot before the worker has finished with it, which is why workers keep a small ring of launch messages and increment the dispatcher's counter when done.

The prefetcher and the dispatcher spin even when there is no work. They are kernels that never return, polling their queues in L1. On silicon that costs nothing but the two cores. In ttsim each spinning RISC-V executes an instruction on every simulated clock, which is part of why the simulator is slower in fast dispatch (see the measurements below).

Where the dispatch cores live, and why your grid shrank

Those two cores have to live somewhere. The choice is a DispatchCoreConfig, which you can pass to create_unit_mesh:

tt-metal/tt_metal/api/tt-metalium/dispatch_core_common.hpp:17-28 @7aad8aac

private:

    std::optional<DispatchCoreAxis> axis_;

    DispatchCoreConfig() : type_(DispatchCoreType::WORKER) {}

The default is WORKER: Tensix cores. The resolver agrees (type.value_or(DispatchCoreType::WORKER), dispatch_core_common.cpp:36). It also picks the axis: a column on Blackhole (unless the fabric is using Tensix cores), a row otherwise (:37-40).

The guide and the code disagree. METALIUM_GUIDE.md:516 says fast dispatch dedicates "one RISC-V core per queue", "typically placed on an unused Ethernet tile". In the code at 7aad8aac, the default is Tensix (WORKER) cores. A single command queue uses at least two of them: a prefetcher and a dispatcher, each running on its core's BRISC, as the simulator run below shows. Ethernet placement is available on request (DispatchCoreType::ETH). The distributed trace example asks for it explicitly: "8 Chip Wormhole systems can only support 2 MeshCQs when Ethernet Dispatch is enabled" (4_distributed_trace_and_events/distributed_trace_and_events.cpp:128-134). Trust the code.

Harvesting comes first. Chips with a defective row or column ship with it fused off, and the product name in the YAML is literally keyed on how many were harvested (core_descriptor.hpp:24-25). ttsim's single-chip Wormhole models an N150 with harvesting mask 0x40, and its single-chip Blackhole models a P150 with mask 0xC0 (ttsim/src/tile.cpp:30, 41). Then fast dispatch takes a row or a column off the end of the grid. You lose eight cores to run two firmware kernels because the grid must stay a rectangle for the logical-coordinate scheme. The other six cores in that row are simply not handed out.

On silicon, slow dispatch gives you the cores back: "When slow dispatch is on, use full logical grid (no dispatch cores to reserve)". But that rule has an exception for simulators (core_descriptor.cpp:243-249, condition !fast_dispatch && !is_simulator_or_emulated()), so on ttsim you see 8 × 8 in both modes. I checked: my test program printed compute grid 8x8 under slow dispatch, fast dispatch, two queues and ETH dispatch alike.

A GPU's command processor is dedicated silicon that you never see in the SM count. Tenstorrent spends general-purpose cores on the job instead, which is flexible (the dispatcher is just C++ you can read and change) but visible: it is the row missing from your grid. Ethernet dispatch moves the job onto Ethernet cores. Those are RISC-V cores too, but they do not count toward the compute grid.

Two command queues and events

One queue executes strictly in order. That is the contract A10 relied on: "a read will not run before the prior kernel finishes". It also means a large input upload blocks the next program even when the two are independent. The fix is a second hardware queue: num_command_queues = 2 (the maximum, MAX_NUM_HW_CQS = 2 in hostdevcommon/common_values.hpp:19). Each queue gets its own issue and completion rings and its own prefetcher/dispatcher pipeline. The two run independently, so ordering between them is your job. You order them with events:

tt-metal/METALIUM_GUIDE.md:534-537 @7aad8aac
// Wait for the current tail operation on queue 0 to complete
// before proceeding on command queue 1
MeshEvent event = mesh_device->mesh_command_queue(0).enqueue_record_event();
mesh_device->mesh_command_queue(1).enqueue_wait_for_event(event);

An event is a counter. enqueue_record_event puts a command into queue A that, once everything before it has completed, writes a new event ID. The ID goes to the completion queue for the host, and to the other dispatcher's L1 for device-side waits. enqueue_wait_for_event puts a command into queue B that blocks B's dispatcher until that ID appears. Neither call blocks the host. The bookkeeping is visible in SystemMemoryManager::get_next_event and set_last_completed_event (system_memory_manager.cpp:319-390). The convention in the guide and the performance report is queue 0 for programs and queue 1 for I/O, so that the next input uploads while the current model runs (AdvancedPerformanceOptimizationsForModels, section 2).

My test program does exactly that dance on ttsim. It writes on CQ1, records an event, makes CQ0 wait, launches on CQ0, records again, makes CQ1 wait, and reads on CQ1. It gave correct results every iteration (hw CQs 2 … bad=0).

Trace: record once, replay many times

Fast dispatch removed the host's waiting, but not its thinking. For each op the host still has to look up the program, assign runtime args, build the command bytes and copy them into the issue queue. A model of a few hundred small ops can be bound by that host work: the device sits idle in the gaps between ops while the host prepares the next one. The performance report shows exactly such a profile: "the device is stuck stalling waiting for the host in order to receive commands to run operations".

The fix is to do the thinking once. Metal Trace records the command bytes of a sequence of ops into a DRAM buffer, then replays that buffer with a single command. Step through capture and replay:

Three rules follow from the mechanism, and the report states them all. Everything in a trace is frozen: "the input/output tensor shapes, addresses, etc. do not change". So inputs must live in preallocated, persistent buffers that you overwrite between replays. Trace "only supports capturing and executing operations, and not other commands such as reading/writing tensors". And the trace buffer needs DRAM. If you reserve a trace_region_size and the trace outgrows it, capture fails and tells you the size it needed ("Creating trace buffers of size …B … but only …B is allocated for trace region"). At 7aad8aac the default is 0 (DEFAULT_TRACE_REGION_SIZE), and then the trace buffer is allocated top-down in ordinary DRAM instead (mesh_trace.cpp:65-83).

Why is trace impossible in slow dispatch? Look at what replay is: a command that tells the prefetcher to read a DRAM buffer. With no prefetcher there is nothing to execute it, and slow dispatch never produces command bytes to record in the first place. The slow-dispatch queue says so directly:

tt-metal/tt_metal/distributed/sd_mesh_command_queue.cpp:487-493 @7aad8aac
void SDMeshCommandQueue::record_begin(const MeshTraceId&, const std::shared_ptr<MeshTraceDescriptor>&) {
    TT_THROW("Not supported for slow dispatch");
}

void SDMeshCommandQueue::record_end() { TT_THROW("Not supported for slow dispatch"); }

void SDMeshCommandQueue::enqueue_trace(const MeshTraceId&, bool) { TT_THROW("Not supported for slow dispatch"); }
This is the same idea as CUDA Graphs: capture a stream's launches once, then launch the whole graph with one call to cut per-kernel CPU overhead. The constraints rhyme as well: fixed addresses and shapes, no allocation inside the capture, and a warm-up first.

Read the table in three passes.

  • The host's PCIe traffic collapses. 446 writes and 364 reads become 7 writes and 0 reads. The 7 are the doorbells and completion-pointer updates, and the TLB window log shows them: five 4-byte writes to translated (18,26) at 0x1a3fc…0x1a40c with values 6, 6, 0x22, 8 and 0xc, and two to (19,26) at 0x19e80. Those values are the five command sizes in 16-byte units: 96, 96, 544, 128 and 192 bytes. A variant of the program that skipped the launch logged only 6, 6, 8 and 0xc, which pins the 544-byte command as the program. The device read host memory exactly 5 times per launch, once per command.
  • Trace shrinks what crosses PCIe, from about 1.07 KB of commands per launch to 640 B. For one tiny kernel that saving is small. It grows with the number of ops captured, because the replay command stays the same size. Replay did add about 37 BAR reads per iteration (each with a TLB reprogram): 4-byte reads of address 0x4a0, the go-message mailbox, on one core: physical (2,11) in ttsim's numbering, which by ttsim's Tensix row and column tables is translated (19,26), the dispatcher core. I did not track down which host routine issues them, and a two-iteration run showed 16 rather than 37, so the count varies.
  • The simulator gets slower, not faster. In ttsim, wall time follows clock calls, at about 12 µs each in both modes. Fast dispatch needs ten times the clocks per launch: two firmware cores spin and interpret commands one instruction per clock, and the host's completion-queue loop clocks the chip while it waits. On silicon the comparison goes the other way, because silicon's costs are PCIe round trips, which fast dispatch removes. ETH dispatch costing far fewer clocks is a ttsim modelling detail, not a performance result. Do not draw performance conclusions from any of these clock numbers.
The per-launch count for slow dispatch scales with the number of cores. Every core gets its own binary, args, launch message and go message, and then the host polls every core. The fast-dispatch count does not scale that way, because the dispatcher multicasts configs and the go signal and collects "done" as semaphore increments. A one-core example therefore understates the gap.

Recap

  • A launch must deliver binaries, runtime args and CB configs into each core's L1, then a launch message, then a go message (signal = RUN_MSG_GO = 0x80), and then learn that the core has set RUN_MSG_DONE.
  • The host reaches the chip through BAR0's TLB windows: a store at a BAR offset becomes a NoC write to (x, y, addr), set by a 64-bit config register at 0x1FC0_0000 + 8·index. Host writes are posted and cheap. Host reads are slow round trips.
  • Slow dispatch: the host writes everything itself and polls every core's go message. One one-core launch cost 446 BAR writes (405 of them TLB reprogramming) and 364 BAR reads.
  • Fast dispatch: the host copies commands into an issue queue in pinned host memory and rings a 4-byte doorbell per command. cq_prefetch pulls the commands, and cq_dispatch executes writes, multicasts, go signals and waits. Workers report done with NoC increments, and completions land in host memory. Per launch: 7 BAR writes, 0 BAR reads.
  • Dispatch cores default to Tensix (WORKER), on the last row (Wormhole) or column (Blackhole). With harvesting, that is why an n150 gives 8 × 8 and the simulated Blackhole 11 × 10. The guide's "typically an Ethernet tile" does not match the code's default.
  • Two hardware queues run independently and synchronise with events. Trace records command bytes into DRAM and replays them with one EXEC_BUF. It needs fast dispatch, and it works on ttsim.

Next, A18 climbs above all of this. In TT-NN every op you call becomes one of these programs, and ttnn.begin_trace_capture is the trace you just watched.

Check yourself

Fast dispatch moved slightly more bytes across PCIe per launch than slow dispatch moved in its data writes. Why is it still the fast one on silicon?

Because the cost is not bytes, it is waiting. Slow dispatch's 364 BAR reads are round trips: each one stalls the CPU for at least several hundred nanoseconds (≥ 671 ns in the ISA doc's measurement), and they happen in series. Its 405 TLB reprograms are serial too. Fast dispatch's host traffic is 7 posted writes, and all the reading is done by the device: the prefetcher reading host memory, and the dispatcher waiting on semaphores over the NoC. Device-initiated reads were measured at 24.5 GB/s, against 0.10 GB/s for a host memcpy from the device.

The doorbell entry for a command was 0x22. How many bytes was the command, and why does the host write the size rather than a pointer?

0x22 = 34 units of 16 bytes = 544 bytes (PREFETCH_Q_LOG_MINSIZE = 4). The issue queue is a ring that the prefetcher reads in order, so the prefetcher already knows where the next command starts: right after the previous one. It only needs to know how much to fetch. That keeps the doorbell to one 4-byte posted write. The most significant bit of the entry is spare for the stall flag that trace replay uses.

You open an n150 with fast dispatch and get a 8 × 8 compute grid, yet the die has 80 Tensix cores. Account for all 16 missing cores.

One row of 8 is harvested at the factory: an n150 is nebula_x1, with 72 functional Tensix (ttsim models this with harvesting mask 0x40). Of those 9 rows, the core descriptor reserves the last one for dispatch (dispatch_cores: [[0,-1] … [7,-1]]). One queue only needs two of its cores (a prefetcher and a dispatcher), but the compute grid must stay a rectangle. So that leaves 8 × 8 = 64.

A colleague wants to trace a model under the simulator workbench and gets "Not supported for slow dispatch". What is going on, and what is the fix?

The workbench's env.sh exports TT_METAL_SLOW_DISPATCH_MODE=1, so the command queue is an SDMeshCommandQueue, whose record_begin throws (sd_mesh_command_queue.cpp:487-489). Trace replay is an EXEC_BUF command executed by the prefetcher firmware, and slow dispatch has no prefetcher and produces no command bytes to record. Unset the variable (env -u TT_METAL_SLOW_DISPATCH_MODE …). Trace then works on ttsim. Do a warm-up run before capturing, and reserve a trace_region_size big enough for the trace (or leave it 0 to let this commit allocate the trace buffer dynamically).

Queue 1 writes an input buffer. Queue 0 then launches a program that reads it. Without an event, what can go wrong, and why can't the single-queue FIFO rule save you?

The two queues have independent issue rings and independent prefetcher/dispatcher pipelines, so nothing orders a command on one queue relative to a command on the other. The program on queue 0 can start before queue 1's write has landed, and read stale data. FIFO order holds only within one queue. queue1.enqueue_record_event() followed by queue0.enqueue_wait_for_event(e) makes queue 0's dispatcher block until queue 1 has completed everything before the event, without blocking the host.

In ttsim, fast dispatch took 3,552 simulated clocks per launch against 364 for slow dispatch. Does that mean fast dispatch is slower?

No. ttsim is functional, not a timing model, and its clock only advances when the host drives it. In slow dispatch that happens once per device read (UMD's after_read). In fast dispatch it happens through advance_device_execution() in the wait loops, while two firmware cores spin and interpret commands one instruction per clock. The clocks measure how the simulation was cranked, not how long silicon would take. On silicon, fast dispatch exists precisely because it removes the host's PCIe round trips.
