The question

In A10 one kernel did everything: it copied two numbers into L1, waited, added them, and copied the sum out. That works for 4 bytes. For 64 tiles it wastes the core, because while the CPU waits for a copy, nothing else happens. A04 showed that a Tensix core has five RISC-V CPUs precisely so that this need not happen. One CPU can fetch tile 8 while three others compute tile 7 and the fifth writes tile 6 back to DRAM.

That raises a coordination problem. The fetching CPU (BRISC) and the computing CPUs (the TRISCs) run separate programs, each compiled on its own, each with its own private data RAM. A C variable in the reader kernel does not exist in the compute kernel. So:

How do two processors with no shared variables agree that a tile is ready, and that its slot is free again?

They share exactly two things: the L1 SRAM, where the tile bytes sit, and a few memory-mapped hardware registers that every CPU in the core can read and write. This chapter builds the protocol that tt-metal runs on top of those, the circular buffer (CB), from the ground up. We start with the kernels at each end of the pipe, then the CB itself, then the tools for when it jams.

Reader, compute, writer

The eltwise_binary programming example is the template for most single-core programs. It adds two 64-tile bf16 tensors with three kernels on core (0,0):

  • A reader on RISCV_0 (BRISC), using NoC 0. It copies tile i of A into CB c_0 and tile i of B into c_1.
  • A compute kernel on the three TRISCs. It takes one tile from each input CB, adds them, and puts the result in c_16. A12 covers it in full; here it is just "the thing between the two CBs".
  • A writer on RISCV_1 (NCRISC), using NoC 1. It copies each tile from c_16 to the output buffer in DRAM.

  noc_async_write_barrier()   // bytes have landed
  cb_pop_front(cb_out, 1)     // free the slot

The two loops mirror each other. The reader is a producer into a CB and the writer is a consumer from one. The compute kernel is both: a consumer of c_0 and c_1, and a producer into c_16. Every function in these loops is one of two kinds: a NoC call (start a copy, wait for copies) or a CB call (claim a slot, publish it, wait for it, release it). We take them in that order.

Async copies and the barriers that end them

noc_async_read(src_noc_addr, dst_l1_addr, size) and noc_async_write(src_l1_addr, dst_noc_addr, size) each program a NoC command buffer and return at once (A08 showed the stores that do it). Nothing has moved yet. The _page variants used above just compute the NoC address of page i through an address generator first.

A08 explained why you then need a barrier: the NoC is weakly ordered. Packets on different NoCs or virtual channels can overtake each other, and the only way a core learns that its transfer finished is by watching NIU counters. A barrier is a spin loop that compares a hardware counter with a software count of what this core issued. There are several barriers, and they differ in which counter they watch:

Which barrier, where?

The reader has no choice. Its cb_push_back tells compute "this slot holds a tile", so the bytes must be in L1 first, and only noc_async_read_barrier proves that. Push before the barrier and the unpacker may read a half-written tile.

The writer has a choice. Its cb_pop_front says "this slot may be overwritten". All the writer must know is that the NoC has finished reading the slot. It does not need to know that DRAM has the data. That is the case for noc_async_writes_flushed, and the example's own comment says so:

tt-metal/tt_metal/programming_examples/eltwise_binary/kernels/dataflow/write_tile.cpp:28-40 @7aad8aac
for (uint32_t i = 0; i < n_tiles; i++) {
    // Make sure there is a tile in the circular buffer
    cb_out.wait_front(1);
    // write the tile to DRAM
    noc.async_write(cb_out, out0, tile_size_bytes, {}, {.page_id = i});
    noc.async_write_barrier();  // This will wait until the write is done. As an alternative,
                                // noc_async_write_flushed() can be faster because it waits
                                // until the write request is sent. In that case, you have to
                                // use noc_async_write_barrier() at least once at the end of
                                // data movement kernel to make sure all writes are done.
    // Mark the tile as consumed
    cb_out.pop_front(1);
}

The flushed variant lets the writer free the slot without waiting for the data to reach DRAM and the acknowledgement to travel back, which matters when the CB is shallow. You still need one real barrier before the kernel exits, because the program is not done until the data has landed.

The sources differ on what "departed" means. tt-metal describes noc_async_writes_flushed as waiting for writes "to depart" (dataflow_api.h:1966-1968), and the Ethernet guide says it tells you "when the write has left the sender L1" (tech_reports/EthernetMultichip/BasicEthernetGuide.md:198). The ISA's counter table is more careful. It says NIU_MST_NONPOSTED_WR_REQ_SENT is incremented "before the data reads from L1 … are complete", and the counter that drops "after the data reads from L1 … are complete" is NIU_MST_WRITE_REQS_OUTGOING_ID (tt-isa-documentation WormholeB0/NoC/Counters.md:130-134). I could not settle whether that gap can be observed on silicon. The matmul lab takes the safe line: "the sender calls noc_async_write_barrier() to wait until the multicast data transfer completes before reusing the CB slot" (docs/.../labs/matmul/lab3/lab3.rst:500). Use a full write barrier until you have profiled a reason not to.

What is in a NoC address?

A10 printed noc addr src0=0x2c00002d4c40 and promised to decode it. On Wormhole a NoC address is 48 bits: 36 bits of local address, then 6 bits of x, then 6 bits of y:

tt-metal/tt_metal/hw/inc/internal/tt-1xx/wormhole/noc/noc_parameters.h:163-164,256-258 @7aad8aac
#define NOC_ADDR_LOCAL_BITS 36
#define NOC_ADDR_NODE_ID_BITS 6
...
#define NOC_XY_ADDR(x, y, addr)                                                                                      \
    ((((uint64_t)(y)) << (NOC_ADDR_LOCAL_BITS + NOC_ADDR_NODE_ID_BITS)) | (((uint64_t)(x)) << NOC_ADDR_LOCAL_BITS) | \
     ((uint64_t)(addr)))

So 0x2c0_0002d4c40 splits into a low 36 bits of 0x0002d4c40 (the buffer's address in the bank) and a high part of 0x2c0 = 0b001011_000000, which is y = 11, x = 0. That is DRAM tile (0,11), which A09's table lists as the endpoint for bank 0. With 36 local bits, the 1 GiB offset of the odd Wormhole banks (0x40000000) fits in the local part. You will see it in a Watcher message later.

Finding the pages: InterleavedAddrGen and TensorAccessor

A10's kernel built its address generator by hand: InterleavedAddrGen<true>{.bank_base_address = addr, .page_size = 4}. The kernel has to restate two facts the host already knows, the memory type (as a template flag) and the page size. As A10 warned, if they drift apart, every page after the first is read from the wrong offset. InterleavedAddrGenFast (used by add_2_integers_in_compute's reader) adds a data format but has the same weakness.

TensorAccessor fixes this by having the host describe the buffer into the compile-time arguments:

  • Host: TensorAccessorArgs(*buffer).append_to(compile_args) appends a few words describing the buffer.
  • Kernel: TensorAccessorArgs<offset>() reads those words, as constexpr values, starting at compile-time-arg index offset. TensorAccessor(args, base_address) combines them with the runtime address.

Because one kernel often reads several tensors, the words are laid end to end, and each accessor tells you where the next one starts:

tt-metal/tt_metal/programming_examples/loopback/kernels/loopback_dram_copy.cpp:24-28 @7aad8aac
constexpr auto in0_args = TensorAccessorArgs<0>();
const auto in0 = TensorAccessor(in0_args, dram_buffer_src_addr);

constexpr auto out0_args = TensorAccessorArgs<in0_args.next_compile_time_args_offset()>();
const auto out0 = TensorAccessor(out0_args, dram_buffer_dst_addr);

How many words does one accessor use? It depends on the buffer, which is why you chain the offsets instead of hard-coding them:

...
static constexpr uint32_t next_compile_time_args_offset() { return CTA_OFFSET + num_compile_time_args(); }

An interleaved buffer needs two words: a flags word and the aligned page size. A sharded buffer adds its rank, bank count, tensor shape, shard shape and packed bank coordinates. The flags word is a bit set: Sharded = 1, IsDram = 2, and bits for which parts to pass at runtime instead (hostdevcommon/.../tensor_accessor/arg_config.hpp:17-29). I checked this in the simulator with a DPRINT in eltwise_binary's reader. It printed:

0:0-0:BR: cta: 2 2048 2 2048  in1 offset=2

Compile-time args 0–1 are input A: flags 2 (DRAM, interleaved) and a 2048-byte page. Args 2–3 are input B, and in0_args.next_compile_time_args_offset() is 2. If A were ever height-sharded, its block would grow, B's would move, and the chained offset would follow. A hard-coded TensorAccessorArgs<2> would quietly read A's shard shape as B's flags.

An address generator turns "page i of this buffer" into a 64-bit NoC address. TensorAccessor gets the buffer's layout from compile-time args written by the host, so the kernel cannot disagree with the allocator, and the same kernel code handles DRAM or L1, interleaved or sharded. Chain multiple accessors with next_compile_time_args_offset().

The tech report lets you move parts of the description (rank, bank count, shapes, bank coordinates) to common runtime args with ArgConfig flags. That trades a little address arithmetic for fewer recompiles when shapes change (tech_reports/tensor_accessor/tensor_accessor.md:34-47). With a static rank, construction is free: "everything is precomputed in compile time" (same file, line 199).

A circular buffer from first principles

Back to the question. The reader puts a tile into L1. How does compute learn it is there? Build the answer up from the smallest thing that could work.

Attempt 1: a flag

Reserve one tile-sized slot in L1 and one shared word, full. The reader waits for full == 0, copies the tile in, and sets full = 1. Compute waits for full == 1, uses the tile, and sets full = 0. This is correct, because each side only acts after seeing the other's write. But it is strictly alternating: while compute works, the reader cannot start the next tile, and while the reader waits on DRAM, compute sits idle. One slot means no overlap.

Attempt 2: a ring of N slots and two counters

Give the pair N slots, used in order 0, 1, …, N−1, 0, 1, …. Now one shared flag is not enough. The classic single-producer single-consumer ring uses two monotonically increasing counters, each written by only one side:

  • received: how many pages the producer has published in total. Only the producer writes it.
  • acked: how many pages the consumer has released in total. Only the consumer writes it.

Everything else follows by subtraction. Pages holding data: received − acked. Free pages: N − (received − acked). Because each counter has one writer, no lock or atomic is needed. A reader of a counter can only see it too low (stale), never too high, and a stale value only makes a side wait a little longer. Counting totals instead of positions also avoids the classic ring-buffer ambiguity where "read index == write index" could mean empty or full. And since only the difference matters, the counters may wrap: tt-metal does the subtraction in uint16_t, so they wrap at 65536 without harm, as long as fewer than 65536 pages are ever outstanding.

The counters say how many slots are full. They do not say where. Each side therefore also keeps a private pointer: the producer a write pointer (where its next page goes) and the consumer a read pointer (where its next page comes from). Both start at the base of the ring, move forward one page size at a time, and jump back to the base at the end. Neither side ever needs the other's pointer. Both are simply following the same sequence.

Where tt-metal puts them

The two counters live in hardware registers. Each Tensix has a set of NoC overlay stream registers that every one of its five CPUs can reach as memory-mapped I/O. tt-metal repurposes two scratch registers of stream n as the counters of CB n:

The pointers are ordinary C structs, one array per CPU, in each CPU's own memory. The firmware fills them in from the program's CB configuration at every launch (hw/inc/internal/circular_buffer_init.h):

tt-metal/tt_metal/hw/inc/internal/circular_buffer_interface.h:85-105 @7aad8aac
struct LocalCBInterface {
    uint32_t fifo_size;
    uint32_t fifo_limit;  // range is inclusive of the limit
    uint32_t fifo_page_size;
    uint32_t fifo_num_pages;

    uint32_t fifo_rd_ptr;
    uint32_t fifo_wr_ptr;

    // Save a cycle during init by writing 0 to the uint32 below
    union {
        uint32_t tiles_acked_received_init;
        struct {
            uint16_t tiles_acked;
            uint16_t tiles_received;
        };
    };

    // used by packer for in-order packing
    uint32_t fifo_wr_tile_ptr;
};

That is eight words, or 32 bytes per CB. Here is a nice consequence. A TRISC on Wormhole has 2 KiB of private data RAM (A09), and 32 CBs × 32 B is already 1 KiB of it. That is why the device header sets NUM_CIRCULAR_BUFFERS = 32 on Wormhole, "limited by 2KB TRISC memory", and 64 on Blackhole (hw/inc/api/circular_buffer_constants.h:14-27).

On a GPU the same pattern appears when you hand-pipeline global→shared memory copies: a ring of shared-memory stages, a producer that issues async copies and a consumer that waits on per-stage barriers (CUTLASS-style multistage pipelines). The difference is who the parties are. On a GPU they are warps or threads in one SM, synchronising through shared-memory barriers. Here they are separate in-order CPUs running separate binaries, and the "barrier" is two counters in MMIO registers that only ever count up.
Analogy check: think of a shelf of N numbered slots, a cook and a waiter. The cook keeps a tally of plates put out and the waiter a tally of plates taken. Each looks at the other's tally to decide whether to act, and each remembers privately which slot is next. The analogy breaks in one important way: a cook would never put a plate where there is no shelf, but the CB hardware has no idea where the shelf ends. Only the pointers know about the end, and only by an exact-equality check. That is the next section's trap.

The six calls, exactly

Here is the whole data-movement API, with what each call does to the four pieces of state. "Page" is the CB's unit, set on the host. It is usually one tile.

Read the real code for the two producer calls. They are short:

tt-metal/tt_metal/hw/inc/api/dataflow/dataflow_api.h:406-428 @7aad8aac
void cb_reserve_back(int32_t operand, int32_t num_pages) {
    uintptr_t pages_acked_ptr = (uintptr_t)get_cb_tiles_acked_ptr(operand);

    // while the producer (write-side interface) is waiting for space to free up "tiles_pushed" is not changing
    // "tiles_pushed" is updated by the producer only when the tiles are pushed
    uint32_t pages_received = get_cb_tiles_received_ptr(operand)[0];

    int32_t free_space_pages;
    WAYPOINT("CRBW");
    {
        SYNC_WAIT("SYNC-CB-RESERVE", operand);
        do {
            // uint16_t's here because Tensix updates the val at tiles_acked_ptr as uint16 in llk_pop_tiles
            ...
            invalidate_l1_cache();
            uint16_t pages_acked = (uint16_t)reg_read(pages_acked_ptr);
            uint16_t free_space_pages_wrap =
                get_local_cb_interface(operand).fifo_num_pages - (pages_received - pages_acked);
            free_space_pages = (int32_t)free_space_pages_wrap;
        } while (free_space_pages < num_pages);
    }
    WAYPOINT("CRBD");
}
  • received is read once, outside the loop. The comment says why: only this CPU writes it, so it cannot change while we wait.
  • acked is re-read on every iteration, because the consumer is changing it.
  • The arithmetic is in uint16_t: the 16-bit wrap described above.
  • Nothing moves. Reserve is purely a wait, so you may call it more than once before a push (cb_pages_reservable_at_back, line 377, is the non-blocking version).
tt-metal/tt_metal/hw/inc/api/dataflow/dataflow_api.h:208-224 @7aad8aac
void cb_push_back(const int32_t operand, const int32_t num_pages) {
    uint32_t num_words = num_pages * get_local_cb_interface(operand).fifo_page_size;

    volatile tt_reg_ptr uint32_t* pages_received_ptr = get_cb_tiles_received_ptr(operand);
    SYNC_SIGNAL("SYNC-CB-PUSH", operand);
    pages_received_ptr[0] += num_pages;

    get_local_cb_interface(operand).fifo_wr_ptr += num_words;

    // this will basically reset fifo_wr_ptr to fifo_addr -- no other wrap is legal
    // producer always writes into contiguous memory, it cannot wrap
    ASSERT(get_local_cb_interface(operand).fifo_wr_ptr <= get_local_cb_interface(operand).fifo_limit);
    if (get_local_cb_interface(operand).fifo_wr_ptr == get_local_cb_interface(operand).fifo_limit) {
        // TODO: change this to fifo_wr_ptr
        get_local_cb_interface(operand).fifo_wr_ptr -= get_local_cb_interface(operand).fifo_size;
    }
}

Push bumps the shared counter, which is the moment the consumer may see the data, and then advances the private pointer. The wrap is ==, not >=. Keep that in mind. The consumer's pair is symmetric: cb_wait_front (lines 479-493) spins on received − acked ≥ n between the CWFW and CWFD waypoints, and cb_pop_front (lines 260-275) bumps acked and advances the read pointer with the same exact-equality wrap.

Writing into the slot does not publish it. Only push does. So between reserve and push the producer may fill the slot however it likes: several small NoC reads, or even random access, as the doc comment says (lines 184-188). Likewise the consumer may read the visible pages in any order between wait and pop.

The aha: watch the ring

Below, a producer (the reader) and a consumer (compute) share one CB. The producer takes P time units to fill a page (NoC read plus barrier) and the consumer C to use one. Choose 1, 2 or 4 pages and press Play. Red in the strips is time spent spinning in cb_reserve_back or cb_wait_front. Turn on jitter to make each page's time vary between 0.4× and 1.6× its nominal value, as real DRAM reads do.

This figure is a model: one page per step, fixed or jittered durations, and the producer and consumer loops above. It is not a measurement. ttsim has no timing model (see below), and the real compute kernel is itself a three-CPU pipeline (A12). The model gets the protocol right, though. The producer may start page k only when page k−N has been popped, and the consumer only when page k has been pushed. With 1 page and P = C = 4, 40 tiles take 320 units, because the two sides strictly alternate. With 2 pages they take 164 units, close to the ideal of 160.

Read it against the table. The CB is two 2048-byte pages starting at 0x19e60, the bottom of L1's unreserved region (A09). Each push adds one to received and moves wr by 0x800. Every second push, wr reaches limit = 0x1ae60 and snaps back to the base. acked is written by the compute kernel on another CPU, and here it has always caught up by the next reserve. A matching overlay of the writer showed the consumer side of c_16: rd alternating between 0x1c660 and 0x1be60, with received and acked equal after each pop.

One more rule carries over from A10. A push is a hand-off, just like a NoC write. If a data-movement CPU fills a CB page with its own stores (not a NoC read), those stores may still be in its store queue when received ticks. Force them into L1 first (A10's load_blocking), and only then push. ttsim will not catch you if you forget.

Two rules the counters cannot enforce

The counters keep the producer from overrunning the consumer. They know nothing about addresses, so two rules are left to you.

Rule 1: pushes in one lap must add up to exactly the CB size

The doc comment states it with numbers: "on a CB of size 12, cb_push_back(5) followed by cb_push_back(7) is correct (total 12 = CB size). However, cb_push_back(7) followed by cb_push_back(7) on the same CB is incorrect (total 14 != 12)" (dataflow_api.h:190-197; pops have the same rule). Step through both to see why. The key moment is step 4 of the bad pattern: the counters say 12 pages are free, so the reserve succeeds, but only 5 pages are left before the end of the ring, and the pointer cannot wrap in the middle of a reservation.

To try it for real without a new host program, I used eltwise_binary's 2-page CB and an overlay whose reader pushes 1 page and then 2 pages (a lap of 3 on a ring of 2). With TT_METAL_WATCHER=1 the run stopped in 10.7 s:

Device 0 worker core(x= 0,y= 0) virtual(x=18,y=18): BRISC tripped an assert on line 219.
Note that file name reporting is not yet implemented, and the reported line number for the
assert may be from a different file. Current kernel:
tt_metal/programming_examples/eltwise_binary/kernels/dataflow/read_tiles.cpp.
TT_THROW: Watcher detected tripped assert and stopped device.

Line 219 of dataflow_api.h is exactly the ASSERT(fifo_wr_ptr <= fifo_limit) in cb_push_back shown above. Without Watcher the same kernel did not hang and did not crash. It "finished" in about a second, and the host's check reported 62,293 wrong values out of 65,536, starting at index 2048, the first element of tile 2. That is silent corruption from one wrong push count.

Counters decide when; pointers decide where. The counters never let you overrun the consumer, but only the exact-equality wrap keeps the pointers inside the ring. Choose push and pop sizes that tile the CB exactly, usually by making the CB size a multiple of the chunk you move.

Rule 2: repeated waits are cumulative

cb_wait_front(n) asks "are at least n pages visible?", not "have n more pages arrived?". The doc comment gives the trap: "4 calls of cb_wait_front(8) followed by a cb_pop_front(32) would produce incorrect behavior. Instead 4 calls of cb_wait_front() waiting on 8, 16, 24, 32 tiles should be issued" (dataflow_api.h:457-461). After the first wait, 8 pages are visible, so the next three wait_front(8) calls return at once. The kernel then works on, and pops, pages 8–31 before they have been pushed. The counter value it compares against is received − acked, and acked only moves on a pop.

Circular buffers on the host

A CB is created by the host, per program and per core range. Here is one of eltwise_binary's three:

tt-metal/tt_metal/programming_examples/eltwise_binary/eltwise_binary.cpp:90-98 @7aad8aac (comments trimmed)
constexpr uint32_t tiles_per_cb = 2;
tt::CBIndex src0_cb_index = tt::CBIndex::c_0;
CreateCircularBuffer(program, core, CircularBufferConfig(
    /*total_size=*/tiles_per_cb * tile_size_bytes,                    // The total size of the circular buffer in bytes
    /*data_format_spec=*/{{src0_cb_index, tt::DataFormat::Float16_b}})// The circular buffer index and data format it'll hold
    .set_page_size(src0_cb_index, tile_size_bytes));
  • Index. tt::CBIndex::c_0 … c_31 on Wormhole, up to c_63 on Blackhole (hostdevcommon/api/hostdevcommon/kernel_structs.h:12-76). The kernel names a CB only by this number, and the same number reaches the stream registers. The examples use low indices for inputs and c_16 for the output. That is a convention, not a rule.
  • Total size and page size. fifo_num_pages = total / page. The page is the unit of every push, pop, reserve and wait. Here it is one bf16 tile, 2048 B, two pages per CB.
  • Data format. Data-movement kernels see it only through get_tile_size(cb). The compute kernel's unpacker and packer are configured from it (A12), which is why a CB has a format at all.
  • Where it lives. At launch the host writes four words per CB into the kernel-config region: base address, size, number of pages and page size. Each CPU's firmware copies them into its own LocalCBInterface (circular_buffer_init.h:41-60), and BRISC has TRISC0 zero the stream-register counters at boot and again after every run, so each launch starts from 0 (brisc.cc:391, 559 trigger init_sync_registers, trisc.cc:97-106, 136-139). The addresses come from the program, which packs CBs upward from the bottom of the unreserved region. The DPRINT overlays showed c_0 at 0x19e60, c_1 at 0x1ae60 and c_16 at 0x1be60, each 4 KiB after the last. Index 16 comes straight after index 1 in memory, because unused indices take no space.
"Up to 32 CBs" is true on Wormhole only. The example's comment says "The hardware supports up to 32 circular buffers" (eltwise_binary.cpp:89). The device header gives 32 on Wormhole and 64 on Blackhole, and the host header says the count is "architecture-specific" (host_api.hpp:175), pointing new code at hal::get_num_dataflow_buffers() (tt-metalium/circular_buffer_constants.h:15-27). The header also notes that CBs are "TEMPORARY code structure", eventually to be replaced by Dataflow Buffers.

A CB can also be laid over an existing L1 buffer with .set_globally_allocated_address(*buffer). That is how A09's vecadd_sharding ran without readers: the sharded tensor already was the CB. Nobody pushes those input pages, so its compute kernel deliberately never calls cb_wait_front on them. The comment warns that doing so "will hang forever as no one is producing data to the circular buffers" (vecadd_sharding/kernels/add_sharding.cpp:12-16). A waiting kernel watches the counters, not the bytes.

Double buffering and the pipeline

The ring figure had one producer and one consumer. A real program chains them: reader → c_0/c_1 → compute → c_16 → writer. Compute is a consumer of one CB and a producer of another, and its order matters. tiles_add.cpp waits for its inputs, does the math, and only then calls cb_reserve_back(c_16). It pushes the output and only after that pops the inputs (tiles_add.cpp:34-57). So a full output CB stalls compute while it still holds its input pages, and that in turn stalls the reader. Back-pressure propagates upstream one CB at a time.

The Gantt chart below uses exactly those orderings. Each stage has a per-tile time (R, C, W). The CB depth applies to all three CBs. Set all three to 4 and compare depth 1 with depth 2.

The arithmetic behind the picture: with depth 1 a stage can only start tile k+1 after its downstream neighbour has released tile k, so neighbouring stages cannot overlap, and the period is the sum of two adjacent stages (8 here). With depth 2, every stage has somewhere to put its next tile while the previous one is still in use, and the period drops to the slowest stage (4). In this model, 8 tiles at R = C = W = 4 take 68 units at depth 1 and 40 at depth 2: 12 for the first tile to pass through all three stages, then 7 × 4. Depth 4 does not improve on depth 2 here, because nothing varies. Turn jitter on to see where it helps.

The price is L1. eltwise_binary's three 2-page CBs cost 3 × 2 × 2 KiB = 12 KiB out of the 1360 KiB A09 measured as free, so double buffering is nearly free here. It stops being free in A15, where matmul CBs hold whole blocks of tiles.

Double buffering means a CB of (at least) two chunks: the producer fills one while the consumer drains the other. With one chunk the stages take turns. With two, the pipeline runs at the speed of its slowest stage. Extra depth only absorbs variation. It cannot make the slowest stage faster.

Two dialects: free functions and Device 2.0 objects

You may have noticed that eltwise_binary's writer called cb_out.wait_front(1) and noc.async_write(...), not cb_wait_front and noc_async_write_page. tt-metal currently has two kernel-API styles:

  • The classic free functions in api/dataflow/dataflow_api.h: cb_reserve_back(id, n), get_write_ptr(id), noc_async_read_page(i, accessor, addr) and so on. These are what everything so far has quoted.
  • The Device 2.0 objects in api/dataflow/noc.h and api/dataflow/circular_buffer.h: Noc noc; CircularBuffer cb(id); noc.async_read(src, dst, size, src_args, dst_args). Sources and destinations are typed objects (a TensorAccessor, a CircularBuffer, a UnicastEndpoint, a CoreLocalMem), and a traits system works out the addresses. The migration guide sells it as "Type Safety: Template-based traits system prevents common errors at compile time" (device_api_migration_guide.md:26-31).

Here is the guide's own example, the same tile reader in both dialects:

On a data-movement CPU, cb.reserve_back is cb_reserve_back. On a TRISC the same class turns into the packer's LLK call, a preview of A12's "one source, three CPUs". The destination-address trait just returns dst.get_write_ptr() + args.offset_bytes (circular_buffer.h:193-197).

Which this series uses. The series teaches and writes kernels in the classic free-function style and shows Device 2.0 when we quote code that uses it, such as eltwise_binary. There are three reasons. The free functions are the layer the objects call, so they are what you see in Watcher waypoints and LLK code. They map one-to-one onto the protocol table above. And most programming examples at this commit still use them. A rough grep at 7aad8aac counts about 50 kernel files under programming_examples using the free CB functions against 4 constructing CircularBuffer objects. In ttnn's kernel directories it is the other way round: roughly 380 files construct CircularBuffer objects against under 60 that call the free functions (the exact numbers depend on the regex). So expect to read both, and expect new library code to be Device 2.0.

Debugging hangs with Watcher

Get a CB protocol wrong and the usual symptom is not a crash but silence. Some CPU spins forever in cb_wait_front or cb_reserve_back, the host blocks in Finish, and nothing prints. DPRINT needs you to guess where to print. Watcher needs no guess. With TT_METAL_WATCHER=<seconds> set, tt-metal compiles debug code into firmware and kernels, and a host thread periodically dumps every core's state to $TT_METAL_LOGS_PATH/generated/watcher/watcher.log. Its features, from docs/source/tt-metalium/tools/watcher.rst:15-21:

  • Waypoints: the last 4-character marker each of the five CPUs passed. By convention a trailing W means "waiting at the top of a loop" and D "done waiting" (lines 94-97).
  • NoC sanitizing: every transaction is checked for bad coordinates, addresses and alignment before it reaches the hardware.
  • CB out-of-bounds checks on NoC transactions that touch an active CB.
  • Asserts such as the one in cb_push_back, which are compiled out when Watcher is off.

The waypoints you will meet most often are already in the code we read:

WaypointWhereMeaning when stuck
CRBWcb_reserve_backProducer waiting for free pages. The consumer is not popping.
CWFWcb_wait_frontConsumer waiting for pages. The producer is not pushing.
NRBW, NWBW, NWFWread barrier, write barrier, writes_flushedWaiting on the NoC. A transfer never completes (bad address, dead endpoint).
NARW/NARD, NAWW/NAWDinside noc_async_read/write, around the sanitizer and the issue (dataflow_api_raw.h:71-74, 167-171)Issuing a transfer.
UABW/UABD, MWDW/MWDDcompute: unpack A+B; math waiting for Dst (A12)The compute side's last landmark. Its CB waits have no waypoint of their own.

Read it field by field, as you would on a real chip:

  • BRISC NTW: the reader (k_id 1) has returned, and the firmware is waiting for the other CPUs to finish. So the producer is done, and whoever is waiting on its CBs will wait forever.
  • NCRISC CWFW: the writer (k_id 2) is in cb_wait_front. It is waiting on c_16, the only CB it reads.
  • TRISC0 UABD: the unpacker's last landmark is the end of an unpack. Its CB wait has no waypoint, so a TRISC stuck after UABD with the writer in CWFW points at compute waiting for input.
  • Nothing changes across about 60 dumps, so this is a hang, not slowness.

Conclusion: the producer stopped early, and the fix belongs in the reader's loop bound. If instead you saw CRBW on BRISC, the jam would be downstream: a consumer that never pops.

What ttsim does not show you

  • ttsim has no CB concept. The "received" and "acked" registers are ordinary storage in its model of the overlay stream registers. A write stores the value, masked to 17 bits, and a read returns it (ttsim/src/tile.cpp:1767-1815 @b3620244). The whole protocol on this page is tt-metal software running on simulated RISC-Vs, which is also why it runs faithfully: ttsim only has to get the loads and stores right.
  • A missing barrier usually goes unnoticed. A08 showed that ttsim completes each NoC transfer inside the store that starts it. I commented out both barriers in loopback_dram_copy.cpp, so the kernel writes each tile back to DRAM without waiting for it to arrive. Three runs, three Test Passed, each at [7113] clocks. On silicon that kernel races. Lab B05 digs into this.
  • No timing. The bracketed clock counts are host-driven simulator steps, not cycles, so ttsim cannot tell you how much double buffering buys on real hardware; A20's profiler can.
The hands-on version is B06 · Circular buffers and semaphores. It watches CB pointers with DPRINT, traces the compute side's handshake, and has you write your own reader/compute/writer kernel trio.

Recap

  • A single-core program is a pipeline: a reader (BRISC, NoC 0) → CB → compute (TRISCs) → CB → writer (NCRISC, NoC 1). Each data-movement loop is reserve/wait, get pointer, async NoC copy, barrier, push/pop.
  • noc_async_* only starts a copy. noc_async_read_barrier waits for read responses, noc_async_write_barrier for write acks (landed), and noc_async_writes_flushed only for departure. Push only after the read barrier. Free a CB slot after a write barrier, or after writes_flushed if you accept the caveat, and always end with a real barrier.
  • A NoC address on Wormhole is y:6 | x:6 | local:36 bits. TensorAccessor builds it from compile-time args the host appends with TensorAccessorArgs(buf).append_to(...): 2 words for an interleaved buffer, more for sharded. Chain them with next_compile_time_args_offset().
  • A CB is an SPSC ring in L1. Two monotonically increasing 16-bit counters, received (written only by the producer) and acked (written only by the consumer), live in per-CB stream registers visible to all five CPUs. Private wr and rd pointers live in each CPU's own memory.
  • reserve_back and wait_front only spin. push_back and pop_front bump a counter, then advance a pointer, which wraps only on exact equality with the limit. So pushes and pops per lap must sum to the CB size, and repeated waits without pops must be cumulative.
  • The host creates CBs with CreateCircularBuffer(program, cores, CircularBufferConfig(total, {{idx, format}}).set_page_size(idx, page)): 32 indices on Wormhole, 64 on Blackhole, packed upward from the bottom of free L1.
  • One page means the stages take turns. Two pages let the pipeline run at its slowest stage. More depth only absorbs jitter.
  • Kernels come in two dialects: the classic free functions (used in this series) and Device 2.0 Noc/CircularBuffer objects, which are thin typed wrappers over them.
  • Watcher turns a silent hang into a diagnosis (CRBW = consumer not popping; CWFW = producer not pushing; NTW = BRISC done), sanitizes NoC transactions, and checks CB bounds and asserts. ttsim runs the protocol faithfully but has no timing, so it will not expose missing barriers.

Next, A12 opens the box in the middle. The compute kernel's cb_wait_front runs on the unpacker's CPU and its cb_reserve_back on the packer's, and a second handshake moves tiles between them.

Check yourself

A reader calls cb_push_back immediately after noc_async_read_page, and calls noc_async_read_barrier after the push. What can go wrong, and would ttsim show it?

The push increments received, which tells compute the page is ready, but the NoC read may not have finished writing the page into L1. The unpacker can then read stale or partly written data. In ttsim the read completes inside the store that issues it, so the data is already there and the test passes. On silicon it is a race. The barrier must come before the push.

A CB has 8 pages. The producer always pushes 3 at a time. What happens, and what are two fixes?

The write pointer moves 3, 6, then 9 pages, which is past the 8-page limit. The wrap check is exact equality, so it never fires. The third reservation's data spills one page past the CB, and the pointer keeps running off the end. With Watcher on, the ASSERT(wr <= limit) in cb_push_back trips. Without it you get silent corruption, as in the 62,293 wrong values above. Fixes: make the CB a multiple of the chunk (6 or 9 pages), or push in chunk sizes whose sequence sums to 8 per lap (for example 3, 3, 2).

Why can cb_reserve_back read received once outside its spin loop but must re-read acked every iteration?

Each counter has exactly one writer. received is written only by the producer, which is the CPU now spinning, so it cannot change during the wait. acked is written by the consumer on another CPU, and it is the value the producer is waiting for. The single-writer rule is also why no lock is needed: a stale read of acked can only under-estimate free space, which delays the producer but never lets it overwrite unconsumed data.

A kernel reads two interleaved DRAM tensors and one height-sharded L1 tensor, in that order, through TensorAccessors. Where does each one's compile-time-arg block start?

The first interleaved accessor uses 2 words (flags and page size), so it is at offset 0 and the second starts at 2. The second also uses 2 words, so the sharded one starts at 4. Its block is longer (rank, bank count, shapes, bank coordinates). Write each as TensorAccessorArgs<prev.next_compile_time_args_offset()>() rather than hard-coding 0, 2, 4, so that a layout change on the host cannot shift one tensor's words into another's.

The Watcher log shows CRBW,CWFW,UABD,MWDD, K for core (0,0), unchanged for a minute. Which CB is jammed and who is at fault?

BRISC (the reader) is in cb_reserve_back, so an input CB is full and compute is not popping it. NCRISC (the writer) is in cb_wait_front, so the output CB is empty and compute is not pushing to it. Both point at the compute kernel, which has stopped consuming and producing. The TRISC fields (last landmarks UABD/MWDD) say it got past its last unpack and math waits. The usual causes are a compute loop count that does not match the reader's and writer's, or a compute kernel blocked in its own cb_reserve_back on the wrong CB index. Compare the three kernels' tile counts and CB indices.

Your three stages take R = 6, C = 2, W = 2 per tile. You go from 2-page CBs to 8-page CBs. How much faster does it get?

In steady state, not at all. With two pages the pipeline already runs at its slowest stage, the reader at 6 per tile, and compute and the writer just spend more time waiting. Deeper CBs absorb variation in stage times; they cannot make the reader faster. The fix is to make the reader faster: more cores reading in parallel (A15), better placement and NoC choice (A08, A09), or bigger transfers.
