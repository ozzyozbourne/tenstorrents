16. Multicast and cross-core synchronization

How one core hands the same data to many cores with a single packet, how cores that share no memory agree on when that data is safe to use, and how the multicast matmul uses four roles and four semaphores to do both.

The question

In A15 we spread a matmul over a grid of cores. Each core computes one block of the output C = A·B. To do that it needs a band of rows of A and a band of columns of B. Look at a row of cores in that grid: every core in it computes a different set of output columns, but all of them need the same rows of A. In the simple multi-core version, every core fetches its own copy from DRAM.

Sixty-four cores need the same row of A. Must it be read sixty-four times?

No. One core can read it once and hand it to the others over the Network-on-Chip. That raises two new problems. The first is cost: sending 63 separate copies over the NoC is cheaper than 63 DRAM reads, but it still loads the links near the sender heavily. The second is trust. The receivers share no memory with the sender and have no common clock. How does a receiver know that the bytes in its L1 are the new block and not the old one? And how does the sender know that a receiver has finished with the previous block, so that overwriting its buffer is safe?

The figure below shows both answers on an 8×8 block of cores. Press Play and watch the counters on the right.

So multicast fixes the cost: the routers copy flits at the forks of a tree, so every link carries the data once (A08 covered the routing). The counter that climbs to 63 and the flag that follows the data fix the trust problem. The counter and the flag are both plain 32-bit words in L1, and Metalium calls them semaphores. This chapter is about those words: what they are, how kernels use them, why the protocol is shaped the way it is, and what happens in the simulator when you get it wrong.

On a GPU, threads in a block synchronize with __syncthreads(), and blocks share data through L2 and global memory, usually with a kernel boundary in between. Tensix cores share no cache and no memory, and there is no grid-wide barrier instruction. Every cross-core handoff is written by hand as explicit messages: a write of data and a write (or atomic increment) of a word that someone else polls. Multicast is closer to a hardware broadcast in a distributed-memory machine than to anything inside a GPU.

Two things called “semaphore”

You have met a semaphore already. In A04 the Sync unit's MATH_PACK semaphore stopped the packer from reading Dst before the math thread had finished writing it, and A12 wraps that in tile_regs_commit and tile_regs_wait. The word “semaphore” in this chapter means something else. Keep them apart:

Tensix Sync-unit semaphore (A04, A12)

  • Where: a hardware register inside one Tensix tile's coprocessor. There are 8, each a 4-bit value with a 4-bit max.
  • Who can touch it: only that tile's three Tensix threads (with SEMPOST, SEMGET, SEMWAIT) and its TRISCs (by load and store).
  • What waits: an instruction in a Tensix thread stalls in hardware at its wait gate until the condition holds.
  • Purpose: ordering the unpack, math and pack threads on the same core, for example the Dst handoff.
  • Set up by: the LLK init code. A kernel author normally never names one.

Metalium semaphore (this chapter)

  • Where: a 32-bit word in each core's L1, in the kernel-config area, one 16-byte-aligned slot per ID (get_semaphore(id) = base + id × L1_ALIGNMENT, and L1_ALIGNMENT is 16 on Wormhole and Blackhole).
  • Who can touch it: the local RISC-Vs with ordinary loads and stores, and any other core through the NoC: an atomic increment, a 4-byte write, or a 4-byte multicast.
  • What waits: software. noc_semaphore_wait is a spin loop on a load.
  • Purpose: handshakes between cores: “I am ready”, “your data has landed”.
  • Set up by: the host, with CreateSemaphore(program, cores, initial_value). Every core in the range gets its own copy at the same L1 address.

The second kind is really just a convention. Nothing in the hardware marks that L1 word as special. What makes it work is that the NoC can perform an atomic increment on a word in another core's L1. An atomic is a single-flit request, and the receiving NIU performs the read-modify-write on its own L1, so increments from many cores never lose a count (MemoryMap.md:79; A08).

tt-metal/tt_metal/hw/inc/api/dataflow/dataflow_api.h:1688-1691 @7aad8aac
template <ProgrammableCoreType type = ProgrammableCoreType::TENSIX>
FORCE_INLINE uintptr_t get_semaphore(uint32_t semaphore_id) {
    return (uintptr_t)sem_l1_base[static_cast<int>(type)] + semaphore_id * L1_ALIGNMENT;
}

On the host, CreateSemaphore picks the lowest ID that is free on every core in the range and records the initial value. Before the kernels start, the runtime writes that value into each core's slot at KERNEL_CONFIG base + semaphore offset + 16 × ID (program.cpp:2672-2688, semaphore.cpp:36). The kernel gets only the ID, usually as a runtime argument, and turns it into an address with get_semaphore.

The docstring for CreateSemaphore says “each core can have up to eight 4B semaphores” (host_api.hpp:283). The code at the same commit allows 16: NUM_SEMAPHORES = 16 (impl/buffers/semaphore.hpp:16), and create_semaphore throws only when a core already has 16 (program.cpp:2732-2736). The code is what runs, so the limit is 16 at 7aad8aac. Every example in this chapter uses 4 or fewer.

Core to core: one tile, one counter

Start with the smallest version: two cores, one tile. The NoC_tile_transfer example reads a tile of 16-bit integers (all equal to 14) from DRAM into core 0, sends it to core 1 over the NoC, and core 1 writes it back to DRAM. Each core runs a reader kernel and a writer kernel, and one semaphore ID is created on both cores with initial value 0:

const auto core1_physical_coord = mesh_device->worker_core_from_logical_core(core1);

...

Each core gets the other core's NoC coordinates and the same semaphore ID. Since every core has its own copy of semaphore sem_id at the same address, one ID names two words: “my counter” and “your counter”. Here is core 1's side. It reserves room for the incoming tile, tells core 0 it is ready, then waits:

tt-metal/tt_metal/programming_examples/NoC_tile_transfer/kernels/dataflow/reader1.cpp:30-39 @7aad8aac
cb_reserve_back(src1_cb_index, one_tile);  // Reserve space for incoming tile

// Indicate readiness for data transfer to core 0
uint64_t sem_addr = get_noc_addr(core_0_x, core_0_y, semaphore);
noc_semaphore_inc(sem_addr, 1);
noc_async_atomic_barrier();

// Wait until core 0 will finish data transfer
noc_semaphore_wait(sem_ptr, 1);  // Wait to get tile from core 0
noc_semaphore_set(sem_ptr, 0);   // Reset semaphore
  • get_noc_addr(x, y, semaphore) builds a 64-bit NoC address: core 0's coordinates plus the L1 address of the semaphore, which is the same on both cores.
  • noc_semaphore_inc sends an atomic increment through the atomic command buffer (write_at_cmd_buf, buffer 3), non-posted by default, with a 32-bit wrap (dataflow_api.h:2396-2416).
  • noc_async_atomic_barrier spins until the atomic's response has come back, the same counter idea as the write barrier in A08.
  • noc_semaphore_wait(sem_ptr, 1) polls core 1's own copy until core 0 bumps it. Then core 1 resets it to 0 so the word can be used again.

Core 0's writer mirrors it: wait for core 1's increment, write the tile, wait for the write to be acknowledged, then increment core 1's semaphore.

tt-metal/tt_metal/programming_examples/NoC_tile_transfer/kernels/dataflow/writer0.cpp:31-46 @7aad8aac
// Wait for core 1 to be ready
noc_semaphore_wait(sem_ptr, 1);
...
// Send data to core 1
noc_async_write(data_l1_ptr, core1_noc_addr, input_data_tile_size_bytes);
noc_async_write_barrier();

// Indicate finish writing to core 1
noc_semaphore_inc(sem_addr, 1);
noc_async_atomic_barrier();
noc_semaphore_set(sem_ptr, 0);  // Reset semaphore

The noc_async_write_barrier() between the data and the increment is the important line. The write and the atomic go out through different command buffers and different VCs. The barrier waits for the write's acknowledgement, which the receiving NIU sends once the data is in L1. So when the increment arrives, the tile is already there. This is the “request, wait for the response, then issue the next request” approach, which the ISA calls the only way to order requests that travel on different NoCs or VCs (Ordering.md:32). It costs one round trip per handoff. Multicast will let us avoid it.

Logical cores on the host, NoC coordinates in the kernel

Look again at that DPRINT banner: “worker core 0-0 (virtual 18-18)”. The host program names cores in logical coordinates, where (0,0) is the first usable worker, whatever its position on the die. A kernel that builds a NoC address needs the coordinates the NIU understands. worker_core_from_logical_core does the conversion on the host. On Wormhole it returns translated coordinates (A08): the Tensix columns become X 18 and up, and the rows Y 18 and up. So logical (0,0) is (18,18) and logical (0,1) is (18,19). On NoC 0 the NIU maps those back to physical (1,1) and (1,2), as the ttsim log below shows.

Two rules follow:

  • APIs that place things take logical coordinates: CreateKernel, CreateCircularBuffer, CreateSemaphore, SetRuntimeArgs.
  • Anything a kernel puts in a NoC address takes NoC coordinates: get_noc_addr(x, y, addr), get_noc_multicast_addr(x0, y0, x1, y1, addr). So the host converts and passes them as runtime arguments.

Translation buys portability. Harvested rows (fused off for yield) move out of the numbering, so the same program works on every chip. It also means the same numbers address the same core on NoC 0 and NoC 1, which matters below because senders and receivers in the matmul use different NoCs.

Passing a logical coordinate straight into get_noc_addr is a classic bug. On Wormhole, (0,1) is not a translated Tensix coordinate (those start at 18). The ISA passes coordinates 0–15 through untranslated, so (0,1) on NoC 0 is the physical position x 0, y 1, which is a DRAM tile, not the core you meant (A08). The A08 loopback log shows real traffic to D(0,1). The write would land in DRAM, and the receiver would wait forever for a flag that went somewhere else.

Multicast: one packet, a rectangle of receivers

Now give the sender three receivers instead of one. The contributed/multicast example puts a sender (it calls it the coordinator) on logical core (0,0) and receivers on (1,0)–(3,0). The host converts the receiver range's two corners to NoC coordinates and counts the receivers:

Three parameters define a multicast write, and each one has a trap.

The rectangle

get_noc_multicast_addr(x_start, y_start, x_end, y_end, addr) packs a rectangle of NoC coordinates and one L1 address into the 64-bit destination. The data lands at the same L1 address on every receiver. That is why the example allocates the same circular buffers on all cores and why the sender multicasts from its own CB's write pointer: the address is valid everywhere only because every core's L1 is laid out identically. Destinations must be Tensix cores; any other tile inside the rectangle opts out of receiving (MemoryMap.md:114). The rectangle can't be an arbitrary shape (Blackhole adds an exclude register, which ttsim doesn't implement: tile.cpp:1701-1705).

The corner order depends on the NoC. A NoC 1 packet travels left and up, so the ISA says that for broadcasts “StartX ↔ EndX need to be swapped by software” (Coordinates.md:25). ttsim enforces it: on NoC 1 it requires start ≥ end, on NoC 0 start ≤ end (tile.cpp:1489-1497). The matmul kernels below do this swap by passing the corners in a different order depending on which NoC the kernel runs on.

num_dests

The hardware doesn't need to be told how many cores are in the rectangle. Firmware does, because a non-posted multicast produces one acknowledgement per receiver, and the write barrier waits until the ack counter reaches the expected total. ncrisc_noc_fast_write adds num_dests to that expected total for every packet it issues (wormhole/noc_nonblocking_api.h:513-518). If you pass the wrong number, the barrier waits for acks that will never come (too high), or exits before all receivers have their data (too low).

Including or excluding the sender

tt-metal/tt_metal/hw/inc/api/dataflow/dataflow_api.h:917-924 @7aad8aac
 * With this API (non-loopback multicast), the multicast sender can be part
 * of the multicast destination range, but data will NOT be written to self.
 * The num_dests argument should NOT count self. For example, when mcasting to
 * an 8x8 grid that includes self, num_dests should be 63.
 * The destination range must not be just self (i.e. at least one other core
 * must be in the range). If the multicast sender also needs to receive the
 * data (i.e. must perform a local L1 write), the other API variant
 * *noc_async_write_multicast_loopback_src* can be used.

The difference is one bit in NOC_CTRL. NOC_CMD_BRCST_SRC_INCLUDE (bit 17) decides whether an initiating NIU inside its own rectangle receives its own packet (MemoryMap.md:68). The plain ncrisc_noc_fast_write leaves it clear (noc_nonblocking_api.h:496-499). The loopback variant, ncrisc_noc_fast_write_loopback_src, sets it (noc_nonblocking_api.h:538-541), and then num_dests must count the sender too, 64 for the 8×8 grid. There are matching noc_semaphore_set_multicast and noc_semaphore_set_multicast_loopback_src calls for 4-byte flags. ttsim models the bit exactly: when it walks the rectangle it skips the source tile unless bit 17 is set (tile.cpp:1507-1508).

A multicast is described by three things that must agree: a rectangle of NoC coordinates (corners ordered for the NoC in use), one L1 address valid on all receivers, and num_dests, which is bookkeeping for the barrier. num_dests counts the source only if you use the _loopback_src variant.

The sender/receiver handshake

With one sender and many receivers, the protocol uses two semaphores, and the step-through below follows it. The sender semaphore lives on the sender and counts “I'm ready” messages. The receiver semaphore lives on each receiver and holds a flag: INVALID (0) or VALID (1), defined in hostdevcommon/common_values.hpp:13-14.

  1. A receiver frees space in its buffer (cb_reserve_back), sets its own receiver semaphore to INVALID, and atomically increments the sender's semaphore.
  2. The sender reads the data from DRAM, then waits until its semaphore equals N, the number of receivers. It resets the semaphore to 0 for next time.
  3. The sender multicasts the data, then multicasts the 4-byte value VALID into every receiver's receiver semaphore.
  4. Each receiver waits until its receiver semaphore reads VALID, then hands the buffer to compute (cb_push_back).

The figure has two receivers. Use the selector to see what each rule protects against.

Every rule in the protocol earns its place:

  • Receivers set INVALID before they increment. The receiver semaphore is a one-shot flag. If a stale VALID is left over from the previous block, the next wait passes before the new data has arrived. Setting INVALID before the increment is safe because the sender can't send the next VALID until that increment has arrived.
  • The sender waits for exactly N, then resets to 0. Waiting for all N means every receiver has a free buffer, so the multicast overwrites nothing that is still in use. Note that noc_semaphore_wait spins while *sem_addr != val (dataflow_api.h:2118-2120). It tests for equality, not “at least”. If the counter ever passes N, the sender hangs. (noc_semaphore_wait_min is the “at least” version.)
  • The sender writes VALID into its own copy first. noc_semaphore_set_multicast(src, dst, n) sends 4 bytes from an L1 address, so the value has to live somewhere in the sender's L1. The matmul kernels store VALID in the sender's own receiver-semaphore slot once at start-up (reader_bmm_tile_layout_in0_sender_in1_sender.cpp:77-84).
  • Receivers wait on their own L1. Polling local L1 costs no NoC traffic. All the NoC traffic is one increment per receiver and one flag per receiver per block.

Why the flag cannot overtake the data

In the two-core example the writer put a full noc_async_write_barrier() between the data and the “done” increment. The multicast sender doesn't. It issues the data multicast and the flag multicast back to back. A08 showed that the NoC reorders packets freely, so why is that safe?

Because of the one ordering guarantee the NoC gives. Two packets that share a route and get the same virtual channel number at every hop can't overtake or interleave each other (Ordering.md:13). A broadcast tree is fixed by its source, its rectangle and its NOC_CMD_BRCST_XY bit (Ordering.md:11). tt-metal's ordering page puts the rule for writes in three lines:

tt-metal/docs/source/tt-metalium/tt_metal/apis/kernel_apis/data_movement/ordering.rst:24-28 @7aad8aac
* If writes are on different NoCs, there is no ordering guarantees.

* If writes are on the same NoC but different VCs, there's also no ordering guarantees. You might as well use different CMD_BUFs to avoid serialization.

* If writes are on the same NoC and same VC, they will be ordered based on program order, regardless whether you use the same CMD_BUF or different ones.

The data and the flag satisfy every condition:

  • Same NoC: both calls use the kernel's default noc_index.
  • Same VC, set statically: both use NOC_MULTICAST_WRITE_VC = 4 (dataflow_api_common.h:63), and every write sets NOC_CMD_VC_STATIC (noc_nonblocking_api.h:496). With a static VC, routers may only flip the dateline bit, and they flip it at the same places for packets on the same route (Ordering.md:14).
  • Same tree: same source, same rectangle, same X-major default.
  • Same program order out of the NIU: on Wormhole “the order in which software writes to NOC_CMD_CTRL determines the order in which those requests leave the NIU” when they have the same VC number (Ordering.md:16), even though the data goes through command buffer 0 and the flag through command buffer 2 (write_reg_cmd_buf, dataflow_api.h:1771-1806).

At the receiving NIU, both requests arrive on the same VC, one after the other. The flag is a 4-byte write to a different address, though. Is there a guarantee that the data's writes into L1 have committed before the flag's write does? The ISA lists receiver-side guarantees for same-VC packets: write then read, overlapping writes, MMIO writes (Ordering.md:20-26). Two non-overlapping L1 writes are not on that list. tt-metal relies on the same-VC property, and the matmul kernel states the assumption in a comment, quoted below. Flag this as an assumption the software makes, not a sentence you can point to in the ISA.

The matmul's in0 sender spells this out, including the one place where it needs more:

On Blackhole, according to that comment, the program-order guarantee across command buffers no longer holds: each command buffer has its own FIFO, so a later request in buffer 2 can leave the NIU before an earlier one in buffer 0. noc_async_writes_flushed() spins until the NIU's NIU_MST_NONPOSTED_WR_REQ_SENT counter matches the number of non-posted writes issued (blackhole/noc_nonblocking_api.h:728-730; dataflow_api.h:1978-1990). That means every data packet has left the NIU. It doesn't wait for acks, so it's much cheaper than a barrier. Once the data is ahead of the flag on the wire, the same-VC rule keeps it ahead. The ISA's Blackhole ordering page just says the behaviour is “similar, but not identical” to Wormhole (BlackholeA0/NoC/Ordering.md:3), so the kernel comment is the most specific source on this difference.

The contributed/multicast coordinator kernel sends data then flag with no noc_async_writes_flushed() on any architecture (coordinator_kernel.cpp:56-64). By the matmul kernel's own comment, that is a race on Blackhole silicon. ttsim can't show it, because it completes every transfer inside the store that starts it (A08). It passed on ttsim's Blackhole model too, and that pass proves nothing about this race.
Data then flag, with no barrier, is correct only if both packets use the same NoC, the same statically assigned VC and the same route, and (on Blackhole) the data has been flushed out of the NIU before the flag is issued. Break any of these and you need noc_async_write_barrier() between them, which costs a full round trip.

The multicast matmul: four roles, four semaphores

Now scale the idea up to matmul_multicore_reuse_mcast. As in A15, every core owns a per_core_M × per_core_N block of output tiles and loops over K in steps of in0_block_w = 2 tiles. In each step it needs an in0 block (its rows of A, per_core_M × 2 tiles) and an in1 block (its columns of B, 2 × per_core_N tiles).

The reuse pattern is the whole point:

  • All cores in one row of the grid compute the same output rows, so they need the same in0 block.
  • All cores in one column compute the same output columns, so they need the same in1 block.

So only the left column reads in0 from DRAM and multicasts it east along its row, and only the top row reads in1 from DRAM and multicasts it down its column. That gives every core one of four roles, each with its own reader kernel:

They are two copies of the handshake above, one per operand. On a left-column core, the in0 sender semaphore is the counter its row's receivers increment. On an interior core the same ID is unused. Its in0 receiver semaphore is the flag its row's sender multicasts VALID into. The host computes each core's rectangles in NoC coordinates:

Three details are worth reading closely. The in0 rectangle starts one core to the right of the sender, so the sender isn't in it, and num_dests = C − 1. The host passes the in0 corners as (right, left+1), and the NoC 0 sender kernel swaps them back when it builds the address: get_noc_multicast_addr(end_x, end_y, start_x, start_y, ...) (in0_sender_in1_sender.cpp:133-138). The top-row in1 senders run on NoC 1 and pass (bottom, top+1) unswapped (in0_receiver_in1_sender.cpp:137-142), which is the corner order NoC 1 needs. And the copy-pasted comments label the in1 arguments “in0”. The kernel reads them as in1 (args 26-34).

The interior receiver is the simplest of the four. It owns no data, and per block it just runs the receiver half of the handshake twice:

tt-metal/tt_metal/programming_examples/matmul/matmul_common/kernels/dataflow/reader_bmm_tile_layout_in0_receiver_in1_receiver.cpp:74-89 @7aad8aac
for (uint32_t block = 0; block < num_blocks; block++) {
    // Operand 0
    cb_reserve_back(cb_id_in0, in0_block_num_tiles);

    // Set in0 semaphore value to INVALID
    noc_semaphore_set(in0_mcast_receiver_semaphore_addr_ptr, INVALID);

    // Atomic increment source core counter
    uint64_t in0_mcast_sender_semaphore_noc_addr =
        get_noc_addr(in0_mcast_sender_noc_x, in0_mcast_sender_noc_y, in0_mcast_sender_semaphore_addr);
    noc_semaphore_inc(in0_mcast_sender_semaphore_noc_addr, 1);

    // wait on in0 semaphore value to become VALID (set by mcast sender after it multicasts data)
    noc_semaphore_wait(in0_mcast_receiver_semaphore_addr_ptr, VALID);

    cb_push_back(cb_id_in0, in0_block_num_tiles);
    // ... the same four steps again for operand 1 (in1) ...

Notice that the receiver never touches the data. The bytes arrive in its circular buffer by multicast, at the address the sender computed from its own CB write pointer. This works only because every core's CBs are created identically and every core advances through them in lockstep, one block per handshake. The in0 and in1 CBs hold two blocks each (in0_CB_tiles = in0_block_tiles * 2, line 124), so the next block can arrive while compute works on the current one.

The arithmetic, for the configuration the prebuilt example uses (its CMake file defines TT_METAL_CI_MODE, which selects M = 2048, N = 1024, K = 512: CMakeLists.txt:17, matmul_multicore_reuse_mcast.cpp:470-473). In tiles that is Mt = 64, Nt = 32, Kt = 16. The host picks per_core_M = 32 and per_core_N = 4 (printed in the run below), so the grid is Nt/4 = 8 columns by Mt/32 = 2 rows, and there are Kt/2 = 8 K-blocks.

  • Per block, with multicast: 2 in0 senders × 64 tiles + 8 in1 senders × 8 tiles = 192 DRAM tile reads. Over 8 blocks: 1,536.
  • Without multicast (every core reads its own in0 and in1 blocks): 16 × (64 + 8) × 8 = 9,216. That is 6× more.
  • Multicasts: each in0 send is 128 KiB = 16 packets of 8 KiB plus 1 flag = 17, so 2 × 17 × 8 = 272. Each in1 send is 16 KiB = 2 packets plus 1 flag = 3, so 8 × 3 × 8 = 192. Total 464.
  • Atomic increments: in0: 2 rows × 7 receivers; in1: 8 columns × 1 receiver. That's 22 per block, 176 in all.

The next section checks every one of those numbers against the simulator. Two things the grid shape makes visible: on a 2-row grid, each in1 “multicast” reaches a single core, so it could just as well be a unicast; and in0 dominates the traffic because each in0 block is 8× bigger than an in1 block. On the 8×8 illustrative grid the savings rise to 8×.

The GPU analogue of this pattern is a thread block loading a tile of A and a tile of B into shared memory once and reusing them across the block's threads. Here the “shared memory” is distributed: each core holds a copy, and the copies are made by the NoC, in hardware, at the forks of a broadcast tree.

Both in0 senders' counters reached 7 within about 30 clocks (row 2 from 4562 to 4594, row 1 from 4633 to 4649), long before the senders finished their 64-tile DRAM reads, so a wait for exactly 6 could never succeed. Zero multicasts were issued.

3. The flag sent before the data

One more, to show what ttsim cannot catch. I swapped the coordinator's two multicasts so VALID goes first:

[4571] NOC0 T0 buf2 MCAST_WR  ack   src T(1,1)[asked 1,1]:0x8aa0 -> dst T(4,1)[asked 21,18]:0x8aa0 len=4
[4571]       A16 mcast flag value=1 delivered to 3 tiles
[4594] NOC0 T0 buf0 MCAST_WR  ack   src T(1,1)[asked 1,1]:0x19e60 -> dst T(4,1)[asked 21,18]:0x19e60 len=2048
[4594]       A16 mcast data delivered to 3 tiles
[✅ PASS] All 3 receiver tiles match the golden tile.

The flag landed 23 clocks before the data, and the test still passed: the receivers took longer than that to get from their wait to their first read of the tile. On silicon the gap would be the data's transit time, and nothing would stop a receiver reading old bytes.

4. num_dests off by one

Finally, the bookkeeping: noc_async_write_multicast(..., num_dests + 1) in the coordinator. (The run used stdbuf -oL, so the log survives the timeout kill.)

[4574] NOC0 T0 buf0 MCAST_WR  ack   src T(1,1)[asked 1,1]:0x19e60 -> dst T(4,1)[asked 21,18]:0x19e60 len=2048
[4574]       A16 mcast data delivered to 3 tiles
[4594] NOC0 T0 buf2 MCAST_WR  ack   src T(1,1)[asked 1,1]:0x8aa0 -> dst T(4,1)[asked 21,18]:0x8aa0 len=4
[4594]       A16 mcast flag value=1 delivered to 3 tiles
[7239] NOC1 T2 buf0 WRITE     ack   src T(3,1)[asked 6,10]:0x1a660 -> dst D(0,1)[asked 9,10]:0x7ffff000 len=2048
[7241] NOC1 T1 buf0 WRITE     ack   src T(2,1)[asked 7,10]:0x1a660 -> dst D(0,11)[asked 9,0]:0x3ffff000 len=2048
[7242] NOC1 T3 buf0 WRITE     ack   src T(4,1)[asked 5,10]:0x1a660 -> dst D(0,5)[asked 9,6]:0x3ffff000 len=2048
(no further output; killed by timeout)

The hardware ignored the wrong count. The rectangle still reached exactly 3 tiles, all three receivers got the tile and wrote it to DRAM. Only the sender hung: its noc_async_write_barrier() expects 4 + 3 = 7 acknowledgements, and ttsim delivers one per real receiver, 6. That is the num_dests section in one log. The number is never sent to the network. It exists only to tell the barrier how many acks to wait for.

What these runs show about the simulator: ttsim catches synchronization bugs only when they turn into a hang, and whether they do depends on an interleaving that DPRINT and Watcher change. A pass in ttsim means “correct for this one interleaving, with instant transfers”. It doesn't mean the protocol is right. Reason about the protocol directly (every wait has exactly one matching message, every flag is reset before it is re-armed, data and flag share a NoC and VC), and use ttsim plus deliberate timing changes, like the busy loop above or Watcher's TT_METAL_WATCHER_DEBUG_DELAY, to shake out the cases you missed.

When a ttsim run hangs, the Watcher's waypoints tell you where. noc_semaphore_wait marks itself NSW on entry and NSD on exit (dataflow_api.h:2115,2122), so a core stuck on NSW in watcher.log is waiting for a semaphore that will never arrive. Remember, though, that turning Watcher on can make the hang go away, as the table shows.

Recap

  • “Semaphore” means two things. The Tensix Sync-unit semaphore is a 4-bit hardware counter that orders the three Tensix threads inside one core. The Metalium semaphore is a 32-bit word in L1, created by the host with CreateSemaphore, one copy per core at the same address, and updated over the NoC by other cores.
  • Cross-core sync is built from three NoC operations: atomic increment (noc_semaphore_inc), 4-byte write or multicast (noc_semaphore_set_remote, noc_semaphore_set_multicast), and a local spin (noc_semaphore_wait, which tests for equality).
  • Host APIs take logical cores. Kernel NoC addresses need NoC coordinates from worker_core_from_logical_core, passed as runtime args (translated (18,18) for logical (0,0) on Wormhole).
  • A multicast is a rectangle (corners ordered for its NoC), one L1 address valid on every receiver, and num_dests, which is barrier bookkeeping. The sender is excluded unless you use _loopback_src, which sets BRCST_SRC_INCLUDE and counts the sender in num_dests.
  • The handshake: receivers set INVALID, then increment the sender. The sender waits for exactly N, resets to 0, multicasts the data, then multicasts VALID. Receivers wait for VALID.
  • Data then flag needs no barrier only because both use the same NoC, the same static VC (4) and the same tree. On Blackhole the sender must also call noc_async_writes_flushed() between them, because separate command-buffer FIFOs may issue out of order.
  • The multicast matmul gives each core one of four roles. The left column multicasts in0 along rows, the top row multicasts in1 down columns, with two handshakes (four semaphores) per block. In the ttsim run that took DRAM reads from 9,216 to 1,536 tiles, with 464 multicasts and 176 atomics, all matching the arithmetic.
  • ttsim shows protocol bugs only as hangs, and only for some interleavings. Missing INVALID passed until a delay exposed it, N−1 passed or hung depending on DPRINT and Watcher, and a flag sent before its data passed.

Check yourself

1. A colleague's compute kernel uses tile_regs_wait(), and their reader uses noc_semaphore_wait(). They say both use “the semaphore”. What is different about them?

tile_regs_wait ends up as a Tensix SEMWAIT on a 4-bit Sync-unit semaphore (MATH_PACK). It is a hardware stall that orders the MATH and PACK threads on the same core, and no other core can touch it. noc_semaphore_wait is a software loop that reads a 32-bit L1 word created by CreateSemaphore. Other cores update that word by NoC atomic increments or writes. Different storage, different waiting mechanism, different scope.

2. You multicast from core (0,0) to an 8×8 grid that includes it, using noc_async_write_multicast with num_dests = 64. What goes wrong, and what are the two possible fixes?

The plain call leaves BRCST_SRC_INCLUDE clear, so only 63 cores receive and 63 acks come back. But the firmware added 64 to its expected-ack count, so the next noc_async_write_barrier() waits forever for the 64th. Fix it either by passing 63, or by using noc_async_write_multicast_loopback_src with 64 if the sender also needs the data in its own L1 at that address.

3. Why must a receiver set its flag to INVALID before incrementing the sender's counter, not after?

The increment is what allows the sender to send the next data and VALID. If the receiver incremented first, the sender could multicast VALID before the receiver's “set INVALID” store, which would then wipe out the new VALID and leave the receiver waiting forever. The ttsim N−1 run shows this order of events. If it never sets INVALID at all, the stale VALID from the previous block lets the wait pass before the new data arrives.

4. The sender multicasts data then the VALID flag with no barrier on Wormhole. You change the flag to go out on NoC 1 while the data goes on NoC 0. Is it still correct?

No. The ordering guarantee holds only for packets on the same NoC and the same VC along the same route. On different NoCs the flag can arrive first, and a receiver would read stale data. You would need noc_async_write_barrier() after the data, which waits for every receiver's ack, before sending the flag. Note that ttsim would very likely still pass, because its transfers complete instantly.

5. In the 8×2 run, why does each in0 multicast report “delivered to 7 tiles” when its rectangle (2,1)–(9,1) is 8 positions wide?

The 8-wide span of NoC x positions includes x = 5, a non-Tensix column on Wormhole. Only Tensix NIUs receive broadcasts; the others are opted out (MemoryMap.md:114). The 8 logical columns map to x = 1-4 and 6-9, the sender is at x = 1, so there are 7 receivers, matching num_dests = num_cores_c - 1 = 7.

6. How many DRAM tile reads would the 8×8 illustrative grid need per K-block with and without multicast, using the same per-core blocks (in0 64 tiles, in1 8 tiles)?

With multicast, only the 8 left-column cores read in0 (8 × 64 = 512) and the 8 top-row cores read in1 (8 × 8 = 64): 576. Without it, all 64 cores read both: 64 × 72 = 4,608. That's 8× fewer. In general the saving is the grid size divided by the number of senders, weighted by block sizes. It grows with the grid, which is why multicast matters more on bigger chips.
