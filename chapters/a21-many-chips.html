21. Many chips: Ethernet, meshes and TT-Fabric

By the end you will know how chips that share no memory cooperate. Each chip has Ethernet cores that push bytes from one chip's SRAM into another's. A fabric routes those pushes across a mesh, and a handful of collective operations, costed in bytes per link, let one model run on 2, 8 or 32 chips.

The question

A Wormhole Galaxy holds 32 chips. No chip can load a byte from another chip's memory. There is no shared address space, no coherent cache and no switch. Tenstorrent's Ethernet guide puts it bluntly: "In a multichip system, there is no concept of shared memory or global addressability across chips for Wormhole or Blackhole" (tech_reports/EthernetMultichip/BasicEthernetGuide.md:188). Yet a 70-billion-parameter model runs across those 32 chips as if they were one device.

How do 32 chips with no shared memory act as one?

Inside one chip you have met this problem before. In A08 and A16, Tensix cores had no shared variables either. They cooperated by pushing data into each other's L1 over the NoC and bumping semaphores to say "it's there". Multichip Tenstorrent extends the same idea by one level. A few special cores on each chip push bytes over Ethernet cables into another chip's SRAM. Firmware on those cores forwards packets hop by hop, and a small vocabulary of collective operations turns all of that into "the same tensor, split across 32 chips". This chapter climbs that ladder one rung at a time: wire, packet, fabric, mesh, tensor, collective and parallel model.

Why scale out at all

Start with capacity. A model with 70 billion parameters stored in BF16 needs 70×109 × 2 B = 140 GB just for its weights. An n150 card has 12 GB of GDDR6 (Wormhole specifications), so you would need at least twelve chips before computing anything. A Wormhole Galaxy's 32 chips hold 384 GB (Galaxy page).

Then speed. A22 shows that generating one token takes roughly as long as reading every weight once from DRAM. If the weights are split over 8 chips, each chip reads only an eighth of them, and all eight DRAM systems stream at once. Splitting the model multiplies the memory bandwidth you can use, not just the capacity. It also introduces a cost that did not exist before: the chips must exchange partial results. All the engineering in this chapter exists to make that exchange cheap.

Scaling out buys capacity and aggregate DRAM bandwidth. You pay for it in bytes that must cross chip-to-chip links, and those links are slower than anything inside a chip. Every multichip design decision is about moving fewer bytes across fewer links.

The only way off the chip: Ethernet cores

Look again at the Wormhole grid from A03. Besides Tensix, DRAM, PCIe and ARC tiles, there are two rows of Ethernet tiles. The guide describes the core type:

  • Every Wormhole contains 16 Ethernet cores on the NoC (BasicEthernetGuide.md:74).
  • Each one has a single RISC-V processor (called the ERISC), 256 KB of L1 (about 150 KB of it free for kernels) and an Ethernet subsystem. It has no Tensix compute units (:78-99).
  • Each core connects to 0 or 1 links, and each link runs at a theoretical 100 Gbps per direction, which is 12.5 GB/s (:101-105; tech_reports/CCLs/CCL_bandwidth.md:17-20).
  • With all 16 links active a chip has 1,600 Gbps per direction, or 400 GB/s counting both directions (:122).

Blackhole changes the numbers but not the shape. The bring-up guide lists 14 Ethernet cores per chip, each with two RISC-V cores and 512 KB of L1 (tech_reports/Blackhole/BlackholeBringUpProgrammingGuide.md:55-56). Each link runs at 400 Gbps = 50 GB/s per direction (CCL_bandwidth.md:20).

Put these numbers next to the chip's memory. A single Wormhole DRAM channel delivers about 43 GB/s and a link 12.5 GB/s, so they are "of the same order" (CCL_bandwidth.md:84-89). A collective, though, gets only the few links on one axis, while a local op gets the whole memory system. Latency is also real: one Ethernet hop takes 530–620 ns (BasicEthernetGuide.md:313), and a fabric hop measures 711 ns on Wormhole and 515 ns on Blackhole (CCL_bandwidth.md:101-104).

What can an Ethernet core do? Only one thing crosses the cable: the ERISC copies a block of its own L1 into the L1 of the Ethernet core at the other end of its link. The guide's primitive is eth_send_packet(src, dst, words). It is non-blocking, and the sender cannot tell on its own when the bytes have landed, so any protocol that reuses a buffer has to build its own acknowledgements (BasicEthernetGuide.md:192-201). ttsim models the primitive at exactly that level:

ttsim/src/tile.cpp:2028-2033 @b3620244
// eth_send_packet (ETH_TXQ_CMD_START_DATA): copy local L1 to the peer eth tile's L1
uint32_t saved_chip_id = g_current_chip_id;
ttsim_select_chip(remote_chip_id);
eth_set_busy(&g_e_tiles[remote_tile_id]);
memcpy(&g_e_tiles[remote_tile_id].sram[dest_addr], &p_tile->sram[start_addr], size_bytes);
ttsim_select_chip(saved_chip_id);

The simulator switches to the peer chip, marks the peer's Ethernet tile busy and does a memcpy from this tile's SRAM into the peer tile's SRAM. The peer comes from a static table of cables (remote_chip_id, remote_tile_id, from eth_peer()). There is no wire timing and no packet loss, because ttsim is a functional model. On silicon the same command fragments the payload into Ethernet frames of at most 1500 B, each carrying 50+ B of headers, FEC and CRC (BasicEthernetGuide.md:107-118).

On NVLink-connected GPUs, one GPU can load from and store to another GPU's memory, and libraries like NCCL build collectives on top of that. Tenstorrent has no remote loads at all. Every byte that crosses chips is pushed by a small RISC-V core sitting at the cable, into a buffer the receiver agreed to provide. It resembles NCCL's ring kernels, except that the "network card" is a programmable core you can put your own kernel on.
The sources disagree on several link numbers.
  • Wormhole link speed. The tech reports say 100 Gbps (12.5 GB/s) per link per direction (BasicEthernetGuide.md:105, 159; CCL_bandwidth.md:19). The Galaxy product page lists a system interface of "3.2 Tbps Ethernet (16 x 200Gbps)", which reads like 200 Gbps links. That line describes the box's external ports, though, and the same page's "41.6 Tbps Ethernet Internal Connectivity" is exactly 100 Gbps per link: a 4×8 mesh has 52 neighbour pairs × 4 links = 208 links, × 100 Gbps × 2 directions = 41.6 Tbps (my arithmetic).
  • Galaxy memory. The same page calls Galaxy's memory "globally addressable", while the Ethernet guide says there is "no concept of shared memory or global addressability". I follow the tech reports, which describe the programming model you actually use.
  • Blackhole Ethernet count. Hot Chips 2024 says "10x 400 Gbps" (slides). The bring-up guide lists 14 Ethernet cores, and ttsim marks 12 of them live, with "eth tiles 12,13 harvested" (ttsim/src/tile.cpp:68). A p150 card exposes 4 QSFP-DD 800G ports (Blackhole specifications), which is 3.2 Tbps, the equivalent of 8 links at 400 Gbps (my arithmetic).
  • Blackhole Galaxy I/O. The TT-Fabric spec says 11.5 TB/s (TT-Fabric-Architecture.md:104) and the Hot Chips slide says 11.2 TB/s.

From two chips to thirty-two

Chips come wired together in a few standard products. A cluster descriptor YAML file tells the software which chip's Ethernet channel connects to which, and which chips have a PCIe connection to the host (BasicEthernetGuide.md:140-145). The smallest system is the n300 card. Here is its descriptor in full, as UMD ships it for testing:

tt-metal/tt_metal/third_party/umd/tests/cluster_descriptor_examples/wormhole_N300.yaml:11-18 @7aad8aac
ethernet_connections: [
   [{chip: 0, chan: 8}, {chip: 1, chan: 0}],
   [{chip: 0, chan: 9}, {chip: 1, chan: 1}],
]

chips_with_mmio: [
   0: 0,
]

Two cables connect chip 0's Ethernet channels 8 and 9 to chip 1's channels 0 and 1. Only chip 0 is "MMIO", meaning reachable over PCIe. The guide spells out the consequence: the right-hand chip "is only accessible through ethernet via the first, local chip", and the dispatcher "reserves one of the links for its own use", so user kernels get 100 of the 200 Gbps per direction (BasicEthernetGuide.md:155-159). Wormhole's spec sheet agrees on the 200G internal chip-to-chip connection. Pick a system below.

Read the figure as a set of rules that the rest of the chapter relies on:

  • Links come in bundles. Neighbouring chips are joined by 2 (n300, T3000, Blackhole) or 4 (Wormhole Galaxy) parallel links. A transfer can use one link or spread over several.
  • Not every chip sees the host. On n300 and T3000, half the chips are reached only by tunnelling through a PCIe-attached chip's Ethernet cores. That tunnel costs a link: "every device on the tunnel (the host-attached one included) reserves one routing plane per direction for dispatch. Where every device is host-attached, nothing is reserved" (CCL_bandwidth.md:52).
  • Topology is a choice of cabling. The same Wormhole chips form a line, a ring, a 2D mesh or a torus depending on how the cables are plugged (BasicEthernetGuide.md:134-138).
"Channel" means three different things in this chapter. An Ethernet channel is the index of an Ethernet core on a chip (chan: 8 above). An EDM or fabric channel is a ring of buffer slots in an Ethernet core's L1 (next section). A host channel, in the fast-dispatch error you will meet later, is a region of host memory used by a command queue. In the same spirit, a link is one cable lane between two Ethernet cores, while a routing plane is the set of links with the same index across all chips.

One packet's trip across the link

Suppose a Tensix core on chip A wants to write 4 KB into a core on chip C, two hops away. It cannot reach C's NoC. It also cannot use the Ethernet hardware directly, because only an ERISC can send. So the worker hands the data to a forwarding service that runs on the Ethernet cores. tt-metal calls that service the Erisc Data Mover (EDM), and it is the building block of TT-Fabric. The comment at the top of the router kernel describes it:

tt-metal/tt_metal/fabric/impl/kernels/edm_fabric/fabric_erisc_router.cpp:61-82 @7aad8aac (trimmed)
The fabric Erisc Data Mover (EDM) is a component that can be used to build *very* simple linear topology fabrics.
One of these EDMs can be instantiated on each ethernet link. ...
There are two sender channels and one receiver channel. "Sender" and "receiver" are relative to the Ethernet link,
not the chip. Sender sends over the link and receiver receives from the link.
- Sender channel 0 : Accepts packets from a workers on the local chip
- Sender channel 1: accepts packets from an upstream EDM (i.e. an upstream
  EDM receiver channel on the same chip but different core)
The receiver channel accepts packets from the Ethernet link and can do one (or both) of:
- Write the packet to local chip if it is the intended destination (unicast or mcast)
- Forward the packet to the next chip in the line if:
  - Unicast and not the target chip
  - Multicast and this chip is in the multicast target range

So each ERISC is a tiny store-and-forward switch with three queues in its L1. One queue holds traffic from local workers, one holds pass-through traffic from the neighbouring EDM, and one receives from the cable. The TT-Fabric spec draws the 1D version with 8 slots per sender channel and 16 in the receiver channel (TT-Fabric-Architecture.md:674-700). Slot counts actually depend on L1 and on the configured packet size (CCL_bandwidth.md:42), so treat 8 and 16 as an example. Step through one packet's trip:

An Ethernet core is a store-and-forward switch built from a RISC-V core and some L1. Workers hand it packets over the NoC, it pushes them L1→L1 across a cable, and credits flowing back keep every buffer from overflowing. Multi-hop traffic is just this, repeated.

TT-Fabric: a network stack made of RISC-V cores

Point-to-point EDMs were enough for the first collectives, but each operation had to set up its own routes and handshakes, which is fragile. The guide lists the traps: kernels on two chips start at different times, so the far side may still be reading a buffer from the previous op (BasicEthernetGuide.md:357-375). TT-Fabric generalises the EDM into a persistent, layered network. The spec maps it onto the OSI picture (TT-Fabric-Architecture.md:169-416):

LayerWhat TT-Fabric does there
1–2 (hardware)Ethernet MAC/PHY. In TT-link mode the controller adds a 16-byte header, delivers straight into the receiver's L1 at an address from that header, and runs go-back-N retransmission, so upper layers "never see data loss due to ethernet frame CRC errors" (:183-196).
3 TT-routingDevices are addressed by (MeshId, DeviceId). Within a mesh, packets are source-routed: the sender embeds the hop-by-hop route in the header. The design supports up to 1024 meshes of 256 devices (:207-220). Routes are dimension-ordered to avoid deadlock (:878-907).
4 TT-transportVirtual channels made of sender/receiver buffers. Ring and torus topologies use bubble flow control to avoid cyclic deadlock, and a separate control VC carries control messages (:394-410).
5 TT-sessionThe API kernels call. A packet carries "the complete destination memory address where the data must be written"; flow-controlled sockets are built on top (:412-416).

Two structural ideas matter for performance.

Routing planes. Wormhole has 4 Ethernet links in each of the east, west, north and south directions, and Blackhole has 2. TT-Fabric maps them one to one: "the first ethernet port on any edge only routes over first ethernet port of the other edges". This yields 4 (Wormhole) or 2 (Blackhole) independent copies of the network, called routing planes. Traffic stays deterministic, and a collective can use several planes in parallel (TT-Fabric-Architecture.md:386-392). The num_links knob you will meet in older CCL code "selects routing planes per direction", and "the weakest hop sets it for the whole collective" (CCL_bandwidth.md:50).

Data plane vs control plane. The NoC plus Ethernet carry the data. PCIe is the control plane that launches routers, configures routing tables and collects status such as link-down events and dropped packets (TT-Fabric-Architecture.md:127-157). On Wormhole the single ERISC runs the whole router. On Blackhole the router's work is split across the Ethernet core's two RISC-V cores (:422).

There is also an older, smaller network underneath. Every Wormhole ERISC boots with base routing firmware from the board's SPI flash. Its job is to let the host reach chips that are not on PCIe, and it is "used by the 'Slow Dispatch' dispatcher path and is further used to bootstrap more higher level components, such as Fast Dispatch" (BasicEthernetGuide.md:180-182). Keep that in mind: it is exactly the path our simulator runs use to reach the second chip, and also where the all-gather attempt breaks.

MeshDevice, MeshBuffer, MeshWorkload

Now go up to the host API. Since A10 you have used MeshDevice::create_unit_mesh(0), a 1×1 mesh. The "mesh" was never decoration. At this commit TT-Metalium only has the mesh API, and a single chip is the degenerate case. TT-Distributed's design document states the goal: present a multi-device system as "1) a large virtual device that has, 2) a distributed shared memory space, and 3) a set of programmable Tensix cores" (tech_reports/TT-Distributed/TT-Distributed-Architecture-1219.md:70). The "shared memory space" here is a host-side abstraction. Moving data between chips still requires the Ethernet pushes described above.

Three objects carry the idea:

  • MeshDevice: a logical 2D grid of chips, such as MeshShape(2, 4), with one command queue that "coordinate[s] execution across all devices, ensuring lock-step parallel execution" (Programming_Mesh_of_Devices_with_TT-NN.md:46, 62).
  • MeshBuffer: one allocation across every chip. The allocator lives at mesh scope and does lock-step allocation, so a buffer has the same address on every chip (TT-Distributed-Architecture-1219.md:184). It is either replicated (each chip gets a full copy) or sharded (each chip gets a piece).
  • MeshWorkload: a set of Programs, each bound to a range of mesh coordinates. The same program can run everywhere (SPMD), or different programs can run on different sub-grids.

Lock-step allocation sounds like a minor convenience, but collectives depend on it. If the output buffer sits at address X on every chip, a kernel on chip 3 can write "to address X on my neighbour" without ever asking the neighbour. The all-gather kernel you will see below relies on exactly this. Launching a program on a whole mesh looks like single-chip code with one extra object:

tt-metal/tt_metal/programming_examples/distributed/1_distributed_program_dispatch/distributed_program_dispatch.cpp:36-45 @7aad8aac
// Instantiate a MeshWorkload and attach the example program. We'll broadcast
// this program by enqueueing it across all devices in our 2x4 mesh.
auto mesh_workload = MeshWorkload();
auto target_devices = MeshCoordinateRange(mesh_device->shape());

mesh_workload.add_program(target_devices, std::move(example_program));
EnqueueMeshWorkload(cq, mesh_workload, false /* blocking */);

// Synchronize the mesh command queue to ensure the workload has completed.
Finish(cq);

MeshCoordinateRange(mesh_device->shape()) means "every chip". A smaller range would target a sub-mesh, and a second add_program call could put a different program on the rest. A sharded MeshBuffer is described by a global shape and a shard shape:

Distributed tensors in TT-NN

At the TT-NN level (A18), a tensor on a mesh is one Python object whose storage is a MeshBuffer. When you move a torch tensor to the mesh, a mapper decides what each chip gets, and when you bring it back, a composer decides how to put the pieces together:

  • ShardTensorToMesh(mesh, dim) splits the tensor along dim, one piece per chip.
  • ReplicateTensorToMesh(mesh) gives every chip a full copy.
  • ConcatMeshToTensor(mesh, dim) concatenates the per-chip pieces back along dim.

At this commit these three names are thin, deprecated wrappers:

tt-metal/ttnn/ttnn/distributed/distributed.py:724-737 @7aad8aac
# Deprecated. Use `ttnn.replicate_tensor_to_mesh_mapper` directly.
def ReplicateTensorToMesh(mesh_device: MeshDevice):
    mapper = ttnn.replicate_tensor_to_mesh_mapper(mesh_device)
    return ReplicateTensorToMeshWrapper(mapper)

# Deprecated. Use `ttnn.shard_tensor_to_mesh_mapper` directly.
def ShardTensorToMesh(mesh_device: MeshDevice, dim: int):
    return ttnn.shard_tensor_to_mesh_mapper(mesh_device, dim)

# Deprecated. Use `ttnn.concat_mesh_to_tensor_composer` directly.
def ConcatMeshToTensor(mesh_device: MeshDevice, dim: int):
    return ttnn.concat_mesh_to_tensor_composer(mesh_device, dim)

For 2D meshes, ttnn.create_mesh_mapper takes one placement per mesh axis, for example "shard dim 3 across rows, replicate across columns". Once a tensor is distributed, ops are SPMD: ttnn.add(a, b) on two sharded tensors launches the same program on every chip, and each chip adds its own shards. If the shards line up, no byte crosses a chip boundary. Bytes cross only when an op needs data another chip holds, and that requires a collective.

Collectives: all-gather, reduce-scatter, all-reduce

Three collectives cover almost every multichip model:

  • All-gather: each of N chips holds a shard, and afterwards every chip holds all N shards, concatenated.
  • Reduce-scatter: each chip holds a full-size partial sum. Afterwards chip i holds the i-th slice of the total sum.
  • All-reduce: every chip ends with the full total. It is a reduce-scatter followed by an all-gather (CCL_bandwidth.md:62).

The naive all-gather is "everyone sends their shard to everyone". On a ring of N chips, though, a shard bound for a chip three hops away crosses three links, so the links nearest the busiest chips carry far more traffic than others. The classic trick is to pass data around the ring in N−1 steps. At every step, every chip sends exactly one chunk to its neighbour, so all links are busy at once and none is busier than another. Step through it. T is the size of the full tensor, so each chunk is T/N.

Count the bytes. For an all-gather, each link carries N−1 chunks of T/N, which is (N−1)/N · T. That is almost T no matter how many chips there are. A reduce-scatter has the same count with an addition at each hop, and an all-reduce costs twice that. These are exactly the "bottleneck bytes" in Tenstorrent's CCL report (CCL_bandwidth.md:66-71):

CollectiveBytes through the bottleneck linkT = 8 MB, N = 8, Wormhole (12.5 GB/s)
all_gather(N−1)/N × T7 MB → 560 µs
reduce_scatter(N−1)/N × T7 MB → 560 µs
all_reduce2(N−1)/N × T14 MB → 1,120 µs

Three refinements bring the cartoon closer to the code.

Line or ring. On a line, an end chip has one link, and everything it lacks must come through it. On a ring, every chip has two links on the axis, so traffic splits into two halves that flow in opposite directions. That halves the bytes per direction and cuts the diameter from N−1 hops to N/2 (CCL_bandwidth.md:58-60). A ring needs deadlock avoidance, though. Bubble flow control and extra acknowledgements "cost every packet", so each ring link runs somewhat slower (:75-80).

TT-NN's unicast all-gather is the ring algorithm, literally. Its program factory says so:

tt-metal/ttnn/cpp/ttnn/operations/ccl/all_gather/device/all_gather_unicast_factory.cpp:17-24 @7aad8aac
// Store-and-forward AllGather (line/ring over a single mesh axis; for Fabric 1D and 2D)
//
// Every device relays stripes to its neighbor one hop at a time; a shard reaches far devices by being
// re-forwarded at each hop. Forward and backward directions run on separate cores. Per direction: the reader
// (CB producer, no fabric) reads iteration 0 from local input and later iterations from what upstream relayed
// into our output; the writer (CB consumer) unicasts each stripe one hop to the neighbor's output (same
// address on every device). Direction/topology are runtime args, so both kernels compile once and run on all
// cores. Two semaphores: barrier_sem (init handshake) and data_valid_sem (relay gate + completion).

Every idea from this chapter appears in that comment. The algorithm relays one hop at a time, as in the animation, and runs both ring directions at once on separate cores. It writes to "the neighbor's output (same address on every device)", which works only because MeshBuffer allocation is lock-step. A semaphore gates the relay, so a chunk is forwarded only after it has arrived; that is the cross-chip version of A16's semaphores. There is also a multicast variant that sends each shard once as a fabric multicast that every router on the line both consumes and forwards, and it is often the one you get. select_program_factory picks between them (all_gather_device_operation.cpp:217-271). On Wormhole it chooses unicast only on a ring or torus axis with at least 64 pages per device shard (20 if pages are 4 KB or larger), so a line gets multicast. On Blackhole it chooses multicast only for small per-link volumes with large pages. The ring reduce-scatter kernels likewise split each slice into even and odd chunks, one per direction, and run ring_size/2 + 1 iterations (experimental/ccl/reduce_scatter_minimal_async/device/kernels/ring_reduction.cpp:55-57).

Fixed costs. A collective also pays per-call setup: launching kernels, opening fabric connections, an entry barrier so that no chip writes into a neighbour that has not started, and an exit wait. On Wormhole the barrier and the exit wait each cost about 0.7 µs plus 0.95 µs per hop (CCL_bandwidth.md:108-120). For small tensors, such as one decode token's activations, these microseconds dominate the bytes.

In Python, the current calls are short. The num_links and topology arguments that older docs pass are now "Deprecated and ignored" (all_gather_nanobind.cpp:51-56), and the fabric configuration decides the topology instead:

ttnn.set_fabric_config(ttnn.FabricConfig.FABRIC_1D)     # before opening the mesh
mesh = ttnn.open_mesh_device(ttnn.MeshShape(1, 8))
g = ttnn.all_gather(t, dim=3)                           # optional: cluster_axis=0|1 on a 2D mesh
r = ttnn.reduce_scatter(partials, dim=3)
A collective's cost is bytes per link divided by link bandwidth, plus a few microseconds per hop. All-gather and reduce-scatter move about T per link and all-reduce about 2T, almost independent of the number of chips. Adding chips does not make collectives cheaper per link. It makes the other work, compute and weight reads, cheaper.

Data, tensor and pipeline parallelism on a mesh

With bytes-per-link costs in hand, the question becomes: how should a model be cut so that it needs the fewest, smallest collectives? Take one matmul, Y[M,N] = X[M,K] · W[K,N], on 4 chips. There are three basic ways to split it, and one clever pairing. The TT-NN LLM report defines them (tech_reports/LLMs/llms.md:1242-1248, 1363-1395):

  • Data parallel: every chip has the whole W and a different slice of the batch (rows of X). There is no communication in the forward pass, but every chip pays the full weight memory.
  • Tensor parallel, column: W is split by output columns (N). Each chip needs the whole X and produces a column slice of Y. If the next op needs the full Y, all-gather it.
  • Tensor parallel, row: W is split by input rows (K), and X must be split the same way along K. Each chip produces a full-size partial Y. Sum the partials with a reduce-scatter (or all-reduce).
  • Column then row: the MLP pattern. Column-parallel FF1 leaves its output split along exactly the dimension that row-parallel FF2 needs split, so the two matmuls run back to back with no communication. One all-reduce at the end is all it costs.

The figure uses the Llama-3-70B MLP shapes from the LLM report: X is [32, 8192] (32 users, one token each), FF1 is [8192, 28672] and FF2 is [28672, 8192], all in bf16, on 4 chips. Blocks are not drawn to scale.

The arithmetic behind the numbers in the figure (bf16, N = 4, 1 MB = 106 B):

  • W1 = 8,192 × 28,672 × 2 B = 469,762,048 B = 448 MiB. One quarter is 112 MiB.
  • FF1's output H = 32 × 28,672 × 2 B = 1,835,008 B. All-gathering it costs 0.75 × that = 1,376,256 B per link, which is 110 µs at 12.5 GB/s.
  • FF2's output Y = 32 × 8,192 × 2 B = 524,288 B. A reduce-scatter costs 393,216 B per link (31 µs), and an all-reduce 786,432 B (63 µs).
  • Gathering after every matmul (FF1, FF3 and FF2) costs 2 × 1,376,256 + 393,216 = 3,145,728 B per link. Column→row needs only the one all-reduce: 786,432 B, a quarter of that.

The rule the LLM report draws: work out the data movement for each scheme, then pick the one with "the lowest overall data movement" (llms.md:1397-1399). The report's table of constraints (:1401-1407) is the bookkeeping. Column-parallel needs its input gathered in K and produces output fractured along N (the table writes "Fractured in K", meaning the next matmul's K). Row-parallel needs its input fractured in K and produces full-size partials.

Two dimensions. On a Galaxy's 8×4 mesh, weights are split along both axes. For W [K, N] the report gives a per-chip block of [K/4, N/8]. Activations are sharded along one cluster axis and replicated along the other, and collectives run along one axis at a time, for example a reduce over cluster_axis=1 followed by a gather over cluster_axis=0 (llms.md:771, 1388-1393). This is why ttnn.all_gather takes a cluster_axis: each row (or column) of the mesh runs its own independent ring. Data parallelism composes with all of this. For example, a 32-chip Galaxy could run four independent 8-chip tensor-parallel replicas of a model.

Pipeline parallelism cuts the model by layers instead: chips 0–7 run layers 1–20, chips 8–15 run layers 21–40, and so on, and activations are passed point to point between stages. Each boundary moves one activation tensor rather than a collective, but the stages must be kept busy with a stream of micro-batches. In tt-metal this lives at the multi-mesh level: "Each rank manages an independent mesh, enabling pipeline parallelism", with one mesh_id per stage (Programming_Mesh_of_Devices_with_TT-NN.md:347-356). The TT-Distributed notes say such workloads "often necessitate MPMD execution models" (TT-Distributed/MultiHostMeshRuntime.md:22), so it is a different programming style from the SPMD tensor parallelism above.

These are the Megatron-LM ideas (column-parallel then row-parallel, with one all-reduce per MLP), applied to a mesh. The difference is the interconnect. A DGX's NVSwitch gives every GPU pair the same bandwidth, so the "ring" is a software choice. On a Tenstorrent mesh the ring is the cabling, which makes cluster_axis and topology first-class parameters of every collective.
Two things the cartoon hides. First, the bytes-per-link formulas assume the collective's links are its own. On n300 and T3000, one routing plane goes to dispatch, and the weakest hop sets the usable plane count for the whole axis. Second, small collectives are latency-bound: a decode-step all-reduce of a few hundred KB pays several microseconds of fixed cost (barriers, connection setup, about 0.7 µs per hop) next to tens of microseconds of wire time. A22 shows why decode lives in exactly that regime.

Recap

  • Chips share no memory. The only way across is an Ethernet core pushing its L1 into the L1 of the Ethernet core at the other end of a cable. Wormhole has 16 such cores (1 RISC-V, 256 KB, 100 Gbps = 12.5 GB/s each way). Blackhole has 14 (2 RISC-V, 512 KB, 400 Gbps = 50 GB/s). The sources disagree on some counts and speeds, as listed above.
  • Systems are cabled meshes. n300 is 2 chips with 2 links, one of them reserved for dispatch to the non-PCIe chip. T3000 is 2×4 with 2 links per pair. Galaxy is 32 chips (4×8, or an 8×4 torus) with 4 links per pair on Wormhole and 2 on Blackhole.
  • The EDM turns an Ethernet core into a store-and-forward switch: two sender channels (local and pass-through), one receiver channel, and credits flowing back. TT-Fabric layers routing (source-routed, dimension-ordered), transport (VCs, bubble flow control) and session APIs on top, replicated across 4 (Wormhole) or 2 (Blackhole) routing planes. PCIe is the control plane.
  • MeshDevice, MeshBuffer (lock-step: same address on every chip) and MeshWorkload make the mesh one SPMD device. TT-NN's mappers ShardTensorToMesh, ReplicateTensorToMesh and ConcatMeshToTensor decide who holds what.
  • Collectives cost bytes per link: about (N−1)/N·T for all-gather and reduce-scatter, and twice that for all-reduce, plus fixed per-hop latency. TT-NN's unicast all-gather is a bidirectional, store-and-forward ring relay. A heuristic picks it or a multicast variant.
  • Cut models to minimise those bytes. Column→row tensor parallelism costs one all-reduce per MLP. Data parallelism costs no communication but replicates weights. Pipeline parallelism passes activations between per-stage meshes.
  • In ttsim (wh_x2, 2×1), mesh buffers and sharded TT-NN ops work, and the host's traffic to chip 1 visibly crosses Ethernet channels 8/9 ↔ 0/1. With stock tt-metal, collectives do not run. They need the fabric, and with the fabric up the host's tunnel to chip 1 starves, because the remote-transfer pinning to the dispatch link is silicon-only (tt_cluster.cpp:1404). B10's yield-interval overlay works around this.

Check yourself

On an n300, chip 0 sends chip 1 a 1 MB shard and receives chip 1's 1 MB shard (an all-gather with N = 2). How many bytes cross the link in each direction, and what is the ideal wire time on the one link left for user kernels?

(N−1)/N · T with T = 2 MB and N = 2 gives 1 MB in each direction. The two directions are independent, so they overlap. At 12.5 GB/s per direction that is 80 µs, or about 83 µs at the roughly 12.0 GB/s payload ceiling after framing (CCL_bandwidth.md:36), plus a few microseconds of fixed setup. Only one of the two links is available because the other is reserved for dispatch to the non-PCIe chip.

Why does ttnn.add on two tensors sharded with the same ShardTensorToMesh(dim=2) move zero bytes between chips, while ttnn.all_gather must move about T per link?

An elementwise op on identically sharded inputs needs, on each chip, only the shards that chip already holds, so the SPMD program runs locally everywhere. An all-gather's output on each chip includes shards that live on other chips. Those bytes must be pushed through Ethernet cores, and on a ring every link ends up carrying N−1 chunks of T/N.

The MLP uses column-parallel FF1 followed by row-parallel FF2. Why not row-parallel FF1 followed by column-parallel FF2?

Row-parallel FF1 would produce full-size partials of H [32, 28672], which must be reduced (about 0.75 × 1.835 MB per link for a reduce-scatter) before FF2 can use them. Then column-parallel FF2 needs its input H whole on every chip, so another gather would follow. Column-parallel FF1 instead leaves H split along exactly the dimension that row-parallel FF2 splits K on, so no communication is needed between the two. The only collective is one all-reduce of the narrow output Y [32, 8192]. This works because the MLP expands and then shrinks, putting the collective on the smaller tensor.

An all-reduce is a reduce-scatter followed by an all-gather. Why is that better than a "reduce to chip 0, then broadcast" scheme on a ring?

Reduce-to-root funnels the whole tensor T into one chip through at most two links, and the broadcast pushes T back out the same way, so the links next to the root carry most of the traffic while the rest sit idle. RS+AG keeps all N links busy at every step with chunks of T/N, for a total of 2(N−1)/N · T per link, which is nearly the minimum: every chip must receive about T of information it did not have and send about the same. The cost is 2(N−1) latency steps instead of about 2·N/2 hops, which matters only for tiny tensors.

The fabric-enabled all-gather run failed while uploading a shard, before the all-gather started. What in the dbrw ETH log tells you which path that upload uses, and why could enabling the fabric affect it?

The log shows the host's writes to chip 1 crossing chip 0's Ethernet channels 8 and 9, the only cables to chip 1, because chip 1 has no PCIe (chips_with_mmio: [0]). That is the base-firmware remote-IO tunnel running on those Ethernet cores. Fabric initialization puts router kernels on the same cores. On silicon, tt-metal pins UMD's remote transfers to the dispatch link, whose routers yield often. In the simulator that pinning is skipped (tt_cluster.cpp:1404), so requests also land on the 9↔1 link. Its routers yield only after 10,000 idle passes, and after start-up B10 saw them stop yielding. The host's requests there are never drained, and UMD times out with "Timeout waiting for Ethernet core service remote IO request flush". The instrumented run fits this: after fabric init, chip 1 goes nearly silent. B10 traces it and works around it.

A ring halves the bytes per direction compared with a line. Why does the CCL report measure line collectives on a line fabric rather than on a ring fabric?

A ring fabric needs deadlock avoidance on every router: bubble flow control (inject only with at least two free slots) and first-level acknowledgements that double credit traffic. Those cost every packet, so even traffic that never wraps around runs slower on a ring-configured fabric (CCL_bandwidth.md:75-80). Measuring a line on a line fabric avoids paying for deadlock avoidance it does not need.
